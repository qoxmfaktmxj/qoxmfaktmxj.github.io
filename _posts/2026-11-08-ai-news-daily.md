## 배경 — 이번 주말의 뉴스는 ‘모델 성능’보다 작업 계약에 가깝다

공급자의 발표를 한 줄로 줄이면 ‘AI 코딩이 더 편해졌다’가 된다. 그러나 네 글을 함께 읽으면 단순 편의성보다 조직의 운영 계약이 눈에 띈다. 대화에서 저장소를 추정해 세션을 시작하는 것은 입력 경계의 변화다. 여러 IDE와 클라우드·로컬 세션을 넘나드는 것은 실행 경계의 변화다. 코드 리뷰 API와 근거 출처는 검증 경계의 변화다. 사용률 대시보드는 성과를 판단하는 관측 경계의 변화다. 자동 병합과 보조 승인은 최종 행동 경계의 변화다. 이 경계들을 따로 설계하지 않고 하나의 ‘Copilot 사용’ 정책으로 합치면 실제 책임자가 불명확해진다.

예를 들어 Slack 채널의 한 줄 요청이 이슈를 만들고 작업 세션을 시작했다고 하자. 질문자는 어느 저장소인지 명시하지 않았다. 저장소가 잘못 추정돼도 코딩 에이전트는 그 저장소에 PR을 만들 수 있을 것이다. 이후 Copilot 코드 리뷰가 지침과 MCP 도구를 참조해 코멘트를 남긴다면, 리뷰가 사용한 자료의 출처와 버전은 구현 과정의 근거와 다르다. 대시보드는 사용자가 Chat과 에이전트 창 모두에 참여한 것으로 셀 수 있지만, 이 숫자만으로 PR의 품질이나 배포 사고 감소를 입증하지 않는다. Agent Merge가 검사 완료를 기다려도 비즈니스 요구가 틀렸거나 데이터 마이그레이션이 위험하다면 ‘검사 통과’가 제품 승인까지 대신하지 않는다.

이 글에서 **공식 사실**은 각 변경 기록에 직접 적힌 기능·조건이다. **운영 해석**은 해당 사실을 팀의 개발·보안·인사시스템 같은 서비스에 적용했을 때 고려할 설계다. 후자는 GitHub가 모든 조직에 보증한 동작이나 법적 자문이 아니다. 공개 소스는 제품의 기능 목록을 보여 주지만, 조직별 오류율·생산성 향상·ROI를 독립적으로 증명하지 않는다.

## 1. Copilot 코드 리뷰 — 설정 API보다 중요한 것은 ‘정책의 유효 범위’

GitHub의 첫 변경은 코드 리뷰를 단일 버튼이 아니라 정책 관리 대상으로 본다. 기업 관리자는 모든 조직의 코드 리뷰 사용 가능 여부를 정하거나 조직 관리자에게 결정을 맡길 수 있다. 조직 관리자는 허용 범위 안에서 기능 사용 여부, 기본 리뷰 노력 수준, 러너 구성을 관리한다. 저장소 관리자는 리뷰 노력 수준과 사용자 지정 지침·MCP 도구 사용 여부를 다룬다. 상위 수준에서 관리하는 설정은 아래 수준에서 덮어쓸 수 없다. 이 계층은 편리한 UI 구조가 아니라 권한 위임의 경계다. 조직 A에서 허용한 도구를 저장소 B가 자동으로 쓸 수 있다고 가정하지 말아야 한다.

API 지원도 동일하지 않다. 기업·조직 수준의 설정 엔드포인트와 조직 러너 엔드포인트는 GitHub App이나 fine-grained PAT를 지원하지 않는다고 공식 글이 명시한다. 저장소 설정 엔드포인트는 둘 다 지원하며, 읽기에는 `Administration: read`, 변경에는 `Administration: write`가 필요하다. Classic PAT는 저장소 관리자 접근이 필요하다. 즉 ‘정책을 API로 자동화할 수 있다’와 ‘현재 쓰는 봇 토큰 하나로 전 계층을 관리할 수 있다’는 전혀 다른 문장이다. 구현할 때는 호출 주체와 토큰 종류를 설정 계층별로 구분해야 한다. 기업 관리자 권한을 가진 장기 토큰을 CI에 넣어 각 저장소 설정까지 일괄 수정하는 방식은 최소 권한의 이점을 잃는다.

정책 설정은 조직마다 운영 이유가 다르다. 보안이 중요한 저장소는 MCP 도구를 제한하고, 문서 저장소는 더 가벼운 리뷰 노력을 택할 수 있다. 제품 팀의 공통 기준이 있다면 기업·조직 수준에서 최소선을 정하고, 저장소별 예외는 이유와 만료일을 기록하는 식이 낫다. 단지 최신 기능이 나왔기 때문에 전 저장소에서 자동 리뷰를 켜는 것은 판단이 아니다. 원문의 정책 계층을 실제 조직의 데이터 민감도·PR 규모·브랜치 보호 규칙에 대응시켜야 한다.

### 리뷰의 ‘출처’는 정확성 보증서가 아니라 조사 단서다

GitHub는 API로 Copilot이 쓴 리뷰와 코멘트를 명시적으로 식별하고, 사용 가능한 경우 노력 수준을 볼 수 있으며, 특정 코멘트의 근거로 Copilot이 보고한 스킬·MCP 서버·사용자 지정 지침을 확인할 수 있다고 했다. 이 메타데이터는 코멘트가 왜 나왔는지 조사하는 데 유용하다. 그러나 ‘스킬을 사용했다’는 표기만으로 스킬 내용이 최신이거나, MCP 서버가 신뢰할 만한 데이터를 반환했거나, 코멘트의 결론이 정확하다고 증명하지 않는다. 출처 보고와 근거의 사실성은 다른 층이다.

운영자는 리뷰 코멘트를 조사할 때 코드 리비전, 리뷰 실행 시각, 해당 지침의 버전, MCP 응답의 범위, 코멘트가 참조한 파일을 연결해 보는 편이 좋다. 원문은 모든 실행의 완전한 재현 가능성이나 모든 메타데이터의 항상 제공을 약속하지 않는다. 특히 노력 수준은 ‘메타데이터가 있을 때’ 보인다고 설명한다. 값이 비어 있으면 최저 노력으로 간주하는 자동화는 잘못된 결론을 낼 수 있다. 누락을 ‘미관측’으로 분리해야 한다.

리뷰 개요도 더 작아졌지만 중요한 변화는 제외 범위의 가시성이다. 건너뛴 파일과 내용이 제외된 파일을 ‘Files not reviewed’ 하나에 모으고 파일명과 이유 링크를 표시한다. 빈 섹션은 생략하고 긴 목록에는 초과 개수를 보인다. 간결함 때문에 PR 작성자가 요약만 읽고 끝낼 수 있지만, 제외 파일 목록은 검토 완료의 분모다. 전체 파일 수 80개 중 20개가 제외되었다면 ‘리뷰 완료’는 80개 전체에 대한 보증이 아니다. 변경된 파일이 코드 생성물인지, 비밀 설정인지, 데이터 마이그레이션인지에 따라 제외의 위험도도 다르다. 리뷰 코멘트가 없다는 사실과 문제없다는 사실을 혼동하지 않는다.

### Balanced effort의 여러 모델은 ‘다수결 증명’이 아니다

공식 변경 기록은 Balanced effort 리뷰가 세 리뷰어 모델을 사용하고 다른 모델이 그 결과를 결합한다고 말한다. 이는 한 모델의 단일 판단과 다른 검토 구조라는 정보이지, 세 모델의 오류가 독립이거나 합성 모델이 모든 중요한 결함을 발견한다는 통계적 보장은 아니다. 세 모델이 같은 입력 누락, 같은 잘못된 요구사항, 같은 제외 파일에 영향을 받으면 서로 일치한 오판을 할 수 있다. 재현 가능한 테스트, 실제 런타임의 형식 검사, 소유자 검토가 계속 필요하다.

리뷰가 실패하거나 시간 초과될 때 한 번 자동 재시도하고, 선호 모델이 사용할 수 없으면 다른 적격 모델로 전환할 수 있다는 수정도 공개됐다. 따라서 같은 PR에서 시각에 따라 리뷰 실행 모델이 달라질 가능성을 운영상 고려해야 한다. 원문은 정확한 모델 이름이나 모든 전환의 세부 기록을 보장하지 않으므로, 팀이 품질 차이를 분석하려면 API가 실제 제공하는 메타데이터부터 확인해야 한다. ‘재시도했으니 성공’으로 처리하지 말고 최종 리뷰 상태와 미검토 범위를 확인한다.

### 비용, 자동 요청, 예외의 연결

코드 리뷰 에이전트 세션에 소비한 AI 크레딧이 표시되고, 자동 리뷰를 요청하는 저장소 규칙은 bypass 목록을 지원한다. exempt actor에게 자동 리뷰가 붙지 않는다는 뜻이다. 이 편의는 조직의 정책 문서에 반영해야 한다. 우회 목록의 주체가 보안 수정 봇인지, 릴리스 자동화인지, 단순히 리뷰를 피하고 싶은 개발자인지에 따라 위험이 달라진다. 봇이 만든 PR에 대한 자동 리뷰 요청 조건도 수정됐지만, 조직 또는 기업이 소유한 앱, GitHub Actions, Dependabot, 외부 라이선스 차단 설정, 조직의 비용 부담이라는 조건을 원문 그대로 확인해야 한다. 단순히 ‘모든 봇 PR을 지원한다’고 일반화하지 않는다.

월간 비용을 볼 때는 생성된 리뷰 수뿐 아니라 재시도, 리뷰 노력 수준, 변경 파일의 규모, 자동 요청 범위를 함께 봐야 한다. 크레딧은 소비를 보여 주지만 리뷰가 실제 결함을 줄인 정도를 보여 주지 않는다. 리뷰가 너무 장황하거나 틀렸을 때 개요에서 부정적 평가 후 구체적 이유를 선택하는 피드백 경로도 생겼다. 팀 내부의 품질 평가에서 같은 분류—틀린 지적, 사소한 지적, 동의하지 않는 승인 평가, 과도한 길이—를 사용할 수 있다. 다만 공급자에게 제출하는 피드백의 내용과 조직의 코드·보안 정책을 함께 검토한다.

### 정책 변경을 위한 작은 운영 절차

1. 현재 기업·조직·저장소 설정을 읽어 기준선을 남긴다. API가 허용하는 토큰 형태와 권한을 각 계층에서 확인한다.
2. 중앙에서 고정할 항목과 저장소가 조절할 항목을 분리한다. 원문의 상속 규칙을 사용해 ‘하위가 상위를 덮어쓰지 못함’을 운영 정책과 일치시킨다.
3. 지침·스킬·MCP 도구의 소유자, 버전, 갱신 절차를 정한다. 출처 표기가 나오는지 시험 PR로 확인하되, 표기만으로 내용 정확성을 승인하지 않는다.
4. 정상·대형·이진·생성 코드·마이그레이션 PR에서 제외 파일 표기를 점검한다. 무엇을 사람이 반드시 읽어야 하는지 정한다.
5. 리뷰 노력 수준별 소요 시간, 크레딧, 실제로 유효한 코멘트 비율을 비교한다. 같은 PR을 반복해 유리한 사례만 선택하지 않는다.
6. 자동 리뷰 규칙과 우회 목록을 관리한다. 우회는 누가 왜 필요했는지, 언제 재검토할지 기록한다.
7. 모델의 승인 성격 평가와 저장소의 브랜치 보호·CODEOWNERS·검사 규칙을 혼동하지 않는다. AI 리뷰는 인간 책임 체계를 보조한다.

## 2. 영향 대시보드 — 측정의 범위가 넓어졌다고 성과가 늘어난 것은 아니다

두 번째 변경은 조직이 AI 코딩을 어떻게 ‘사용’으로 세는지 바꾼다. Copilot 영향 대시보드의 Agent adoption 차트에 Copilot Chat과 VS Code Agents 창이 더해져, 기능 참여를 아홉 경험에 걸쳐 볼 수 있다. 28일 기업·조직 보고의 `copilot_feature_engagement.totals_by_feature`에 `chat`과 `vscode_agent` 항목이 추가된다. 과거 보고서는 기존 일곱 기능만 담으므로, 같은 그래프에 새·옛 기간을 연결하면 측정 도구 자체의 변화가 추세처럼 보일 수 있다. 새 기능 노출 이후 참여 수가 상승해도 생산성 상승분과 분리해야 한다.

‘Passive users’라는 명칭은 ‘Chat-first users’로 바뀐다. GitHub가 설명한 이 집단은 Copilot에 활동이 있으나 28일 동안 채택 단계에 해당하는 기능을 적어도 이틀 사용하지 않아 채택 단계에 들어가지 않은 사람이다. ‘수동적’이라는 이름은 활동을 과소평가했고 새 이름은 사용 패턴을 더 정확하게 표현하려는 것이다. 그러나 API의 코호트 값은 여전히 `No Cohort`이고 코호트 인원 수도 변하지 않는다. 관리자 보고서의 표시명만 바뀐 상황을 실제 조직 문화의 급격한 변화로 해석하면 안 된다.

중요한 조건은 Chat과 VS Code Agents 창이 **기능 참여**에 표시되지만 **채택 단계 판정에는 들어가지 않는다**는 점이다. 둘을 더해 ‘채택 단계 사용자가 늘었다’고 요약하면 원문과 반대다. 참여 기준은 28일 기간 안에 해당 기능을 최소 이틀 사용한 것이다. 사용자는 여러 기능에 중복 포함될 수 있고, Chat 측정에는 agent mode를 포함한 Copilot Chat 사용이 들어간다. 따라서 기능별 참여 수의 합은 고유 사용자 수가 아니다. 팀별 기여율을 만들려면 사용자 단위 중복 제거와 자격이 있는 라이선스 보유자라는 분모를 별도로 정의해야 한다.

### 좋은 지표와 나쁜 대리지표

‘AI를 쓰는 개발자가 몇 명인가’라는 질문과 ‘AI가 배포 품질을 개선했는가’라는 질문은 별개다. 전자에는 라이선스 활성 사용자, 기능별 참여, 반복 사용, 팀별 접근성이 필요하다. 후자에는 PR 리드타임, 리뷰에서 실제로 해결된 결함, 롤백, 장애, 보안 수정 속도, 사용자 문제 해결 시간이 필요하다. 기능 참여가 높아도 작업이 더 쉬워졌다는 보증은 없다. 반대로 채팅만 사용한 사람이 코드 자동 완성 기능에 참여하지 않는다고 해서 무가치한 사용자는 아니다. 인프라 설계나 장애 조사에 채팅을 활용할 수 있다. 이 발표의 가치는 지금까지 빠졌던 사용 형태가 드러난다는 것이지 성과 측정이 자동으로 완성된다는 것이 아니다.

앞으로 대시보드의 두 시점 비교에는 최소한 네 개의 주석이 필요하다. 첫째, 새 `chat`·`vscode_agent` 필드가 어느 시점부터 자료에 있는가. 둘째, 조직의 사용 지표 정책이 활성화됐는가. 셋째, 기간 중 라이선스 대상과 구성원이 바뀌었는가. 넷째, VS Code·IDE 버전 또는 원격·로컬 환경의 차이 때문에 텔레메트리 누락이 생겼는가. GitHub 공식 REST 문서는 Copilot 사용 지표 정책이 `Enabled everywhere`여야 해당 엔드포인트를 쓸 수 있다고 설명한다. 데이터가 없을 때 ‘사용자가 없다’고 단정하지 말고 권한·정책·보고 시차를 점검한다.

GitHub 공식 문서는 28일 보고가 마지막으로 처리된 완전한 기간을 가리키고, 다운로드 링크가 제한된 만료 시간을 가진다고 명시한다. 자동 보고 파이프라인은 URL을 영구 저장하는 대신 보고 날짜, 조회 시간, 내려받은 원본의 버전·해시를 기록하는 편이 안전하다. 일별 보고는 정확히 그 날에 처리된 데이터를 대상으로 한다. 보고 생성 주기와 시간대가 운영팀의 주간 회의 기간과 다르면 월요일 아침 수치가 예상보다 늦거나 적게 보일 수 있다. 원본 리포트의 시작·종료일을 확인한 뒤 시각화한다.

### 예시: ‘도입률 120%’라는 잘못된 보고가 생기는 경로

100명의 라이선스 보유자가 있고, 60명이 Chat, 45명이 VS Code Agents, 30명이 다른 기능에 참여했다고 가정해 보자. 단순 합계는 135명이지만 이는 각 기능을 한 사람이 여러 번 사용할 수 있다는 사실을 무시한다. 고유 사용자는 60–100명 사이 어딘가일 수 있다. 이 가상 수치는 GitHub의 실제 고객 데이터가 아니다. 계산 원리를 보여 주는 예다. 개인별 지표를 가져와 중복을 제거할 권한이 없다면 ‘기능별 참여 합계’를 ‘사용자 도입률’로 명명하지 않는다. 대신 기능별 그래프와 고유 사용자 그래프를 별도로 제시한다.

또 다른 오류는 ‘Chat-first’가 늘어났으므로 코딩 에이전트 도입이 성공했다는 주장이다. Chat-first는 채택 단계에 들어가지 않은 집단이므로 그 증가를 코딩 에이전트의 성숙도로 읽으면 정반대 해석이 된다. 반대로 해당 코호트가 줄어도 사람들이 Copilot을 떠났는지, 다른 기능으로 이동했는지, 라이선스 정책이 바뀌었는지는 수치 하나로 알 수 없다. 코호트 이동을 보려면 동일한 사용자 집합의 기간별 변화를 살펴야 하고, 개인 수준 데이터는 조직의 개인정보·근로자 모니터링 정책에 따라 제한해야 한다.

### 운영 담당자를 위한 계측 계약

| 질문 | 필요한 정의 | 이번 변경과의 관련 | 혼동하면 생기는 오류 |
| --- | --- | --- | --- |
| 누가 활동 중인가 | 기간, 라이선스 분모, 고유 사용자 | 두 새 기능의 참여 추가 | 기능 합산을 사용자 수로 계산 |
| 어떤 기능을 쓰는가 | 기능별 최소 이틀 사용 여부 | `chat`, `vscode_agent` 필드 | 단일 세션 사용을 28일 참여로 간주 |
| 채택 단계는 어디인가 | GitHub의 별도 단계 규칙 | 단계 규칙은 불변 | 새 기능 추가로 단계가 바뀌었다고 주장 |
| 왜 `No Cohort`인가 | API 값과 UI 표시명 매핑 | UI는 Chat-first로 이름 변경 | API 값 변경을 전제로 파이프라인 장애 |
| 결과가 좋아졌는가 | 결함·리드타임·회수·사용자 가치 | 대시보드만으로 답 못 함 | 사용량을 성과로 등치 |
| 자료가 없나 | 지표 정책, 권한, 보고 시차 | 공식 문서의 접근 조건 | 0과 미수집을 동일하게 저장 |

지표를 인사 평가에 곧장 쓰는 것은 특히 위험하다. 코딩 업무의 종류가 다르고, 설계·리뷰·장애 대응은 도구 사용 흔적보다 결과의 질이 중요하다. Copilot을 자주 쓰는 사람에게 높은 점수를 주면 피상적인 호출을 늘릴 유인이 생긴다. 팀의 학습·도구 배포·라이선스 수요를 판단하는 집계 지표로 쓰고, 개인의 역량 판단에는 실제 작업물과 맥락을 함께 보아야 한다. 이 윤리적 주의는 제품 발표가 보장한 운영 규정이 아니라 측정 도구를 조직에 적용할 때 필요한 편집적 판단이다.

## 3. 앱·CLI·IDE의 주간 릴리스 — ‘같은 계정’이어도 작업과 승인 경계는 다르다

주간 변경 기록은 하나의 제품 발표라기보다 여러 작업 환경의 조각을 모은 것이다. Copilot 앱의 Agent Merge는 PR에서 설정하고 필수 검사나 규칙을 기다리는 동안 유지할 수 있다. 이는 개발자가 매번 검사 종료를 지켜보지 않아도 된다는 장점이 있다. 하지만 ‘조건이 충족되면 병합’할 수 있는 시스템이 되었다면 조건의 정의가 중요해진다. 보호 브랜치 규칙이 느슨하거나 잘못된 테스트가 통과하면 자동화는 그 결함을 더 빠르게 통과시킬 수 있다. 반대로 필수 승인이 제대로 구성된 저장소라면 검사가 끝나도 규칙을 기다리는 흐름이 중간 대기 상태를 줄인다. 원문은 모든 저장소에서 사람 검토가 자동으로 강제된다고 말하지 않는다.

개인 지침을 통해 어떤 도구 요청을 재질문 없이 승인할지 Copilot에게 안내하는 보조 승인 기능도 소개됐다. **선택 적용이며 로컬 세션에 적용**한다는 범위를 꼭 붙여야 한다. 도구를 매번 승인하는 피로를 줄일 수 있지만, 허용 목록이 넓어질수록 그 도구를 호출한 코드·문서·프롬프트의 신뢰 수준이 중요해진다. 사람의 승인이 불필요한 읽기 도구와 외부에 변경을 가하는 쓰기 도구를 같은 승인 규칙으로 묶지 않는다. 에이전트가 로컬에서 접근할 수 있는 파일·환경 변수·네트워크는 클라우드 세션의 격리와 다를 수 있으므로, 보조 승인을 켤 때 실행 장소부터 확인한다.

앱에서는 대화가 문맥 한도에 도달했을 때 압축하거나 사용 공간을 볼 수 있고, 사이드바의 ‘New’로 파일을 끌어 새 세션을 시작할 수 있다. CSV·TSV는 고정 헤더와 원문 보기 옵션이 있는 표로 열린다. 병합·종료된 PR의 고정 세션을 보관하거나 여러 세션을 일괄 고정 해제할 수 있다. 이런 편의는 단순 화면 개선처럼 보이지만 운영 측면에서는 오래된 세션이 현재 작업처럼 계속 노출되는 문제를 줄인다. 다만 세션 정리는 감사 기록의 보존과 별개다. 대화 압축도 최초 요구사항·승인·실패한 테스트의 기억을 영구적으로 보장하지 않는다. 장기간 작업은 이슈·PR·설계 문서에 결정 사항을 남겨야 한다.

CLI의 `/settings`는 플러그인과 MCP 서버 등을 검색 가능한 통합 대시보드에서 관리한다. 도구 목록이 한곳에 모이면 설치·설정은 쉬워지지만, 어떤 서버가 어느 저장소에서 쓰이는지, 연결된 자격 증명은 무엇인지, 출력이 모델 컨텍스트에 어떤 신뢰도로 들어오는지는 여전히 운영자가 판단해야 한다. 특히 MCP 서버는 외부 자료의 전달 경로일 수 있다. 설정을 찾아보기 쉬워졌다는 사실을 사용 승인으로 오해하지 않는다. 팀 표준은 허용된 서버 목록·소유자·연결 권한·버전·회수 절차를 별도로 정해야 한다.

JetBrains Air에서는 Copilot으로 여러 에이전트 세션을 추적하고, IDE 안의 로컬 작업이나 Air Teams를 통한 클라우드 작업을 진행할 수 있다. 기존 Copilot 구독을 활용한다는 공식 설명이 있다. Xcode의 내장 코딩 도우미와 Copilot 통합은 **Xcode 27.3 베타부터 공개 미리보기**다. 이를 모든 안정판 Xcode에 이미 제공되는 일반 출시로 쓰지 않는다. VS Code 1.145의 실험적 채팅 보기 모드는 추론과 도구 호출을 간결하게 접거나 자세히 펼치는 선택이다. 보기 모드는 **표시 방식**이지 추론의 정확도나 도구 호출 허용 범위가 달라졌다는 발표가 아니다. 운영 리포트를 만들 때 앱·CLI·IDE별 세션 사용을 같은 의미의 ‘작업 완료’로 합치면 안 된다.

### 복수 환경을 쓰는 팀의 작업 분리

- **로컬 CLI·IDE:** 빠른 편집과 현재 개발자의 자격 증명·파일 시스템에 가까운 작업에 맞는다. 터미널 명령과 비밀정보 접근을 어떤 범위까지 허용할지 검토한다.
- **클라우드 세션:** 장시간 작업을 개발자의 노트북에서 떼어낼 수 있다. 저장소 접근, 빌드 네트워크, 로그, 결과를 가져오는 경로를 별도 검토한다.
- **채팅 기반 시작:** 이해관계자와 개발자가 같은 요구 문맥을 볼 수 있다. 대화의 모호함, 잘못된 저장소 추정, 채널 구성원 공개 범위를 점검한다.
- **PR 기반 완료:** 변경 파일과 CI 결과를 리뷰할 수 있다. 배포·병합·데이터 변경의 승인 주체를 명확히 한다.

같은 ‘에이전트 세션’이라고 해서 네 위치를 하나의 정책으로 덮을 수는 없다. 로컬에서 승인한 도구가 클라우드에서도 허용된다고 가정하지 않고, 클라우드에서 제한한 네트워크가 로컬에도 적용된다고 가정하지 않는다. 어떤 환경에서 시작하고 어디서 코드를 실행하며 누가 결과를 승인하는지 PR에 남기면 사고 조사의 범위가 좁아진다.

### Agent Merge 도입 전에 확인할 질문

첫째, 필수 검사가 정확히 무엇을 검증하는가? 타입 검사와 단위 테스트만 있으면 데이터 삭제·권한 변경·외부 API 비용은 놓칠 수 있다. 둘째, PR 작성자가 자기 PR을 승인할 수 있는가? 승인 규칙이 자기 승인이나 봇 승인으로 우회되면 자동 병합이 보호 규칙을 기다린다는 이점은 작아진다. 셋째, 검사 결과가 마지막 커밋에 매여 있는가? 오래된 커밋의 녹색 상태로 새 변경이 병합되지 않도록 브랜치 규칙을 확인한다. 넷째, 배포 리스크가 높은 시간대나 마이그레이션에는 별도 릴리스 창이 있는가? 병합 가능성과 배포 가능성을 분리한다. 이 질문은 GitHub가 새로 강제한 기능이라는 뜻이 아니라 자동 병합을 안전하게 운영하기 위한 체크리스트다.

## 4. `@GitHub` in Slack·Teams — 대화가 개발 작업의 입력이 될 때

GitHub는 Slack과 Teams에서 `@GitHub`를 통해 버그 조사, 이슈 작성, 구현 및 PR 개설을 시작하는 경험을 일반 제공한다고 발표했다. Teams Canvas에서는 계획·코드 변경·미리보기를 대화 옆에서 함께 살펴볼 수 있다. 온보딩 과정은 메시지에서 저장소를 찾아 다시 선택하지 않아도 세션을 시작할 수 있도록 줄었고, 로그인 상태나 기본 저장소의 유무, 저장소 변경, 앱 접근 요청 같은 경계 상황도 개선됐다고 한다. 후속 메시지에 응답하지 못하던 문제의 수정도 명시됐다. 생성된 이슈와 PR에는 ‘Slack/Teams의 @username 대화에서 생성’했다는 귀속 문구가 붙는다.

여기서 ‘대화에서 코드를 만든다’를 ‘채팅 문구가 완성된 요구사항이다’로 읽으면 곤란하다. 팀 대화는 보통 상황 보고, 추측, 임시 우회, 최종 결정이 섞여 있다. 이슈를 만들기 전 에이전트가 문제와 요청을 어떤 문장으로 요약했는지 확인해야 한다. 구현에 들어갈 때는 재현 단계, 기대 결과, 변경하지 말아야 할 범위, 영향 받는 사용자를 구분한다. 채널에 붙여 넣은 로그는 개인정보와 자격 증명을 포함할 수 있으므로, 대화 내용을 작업 컨텍스트로 넘기기 전에 최소화한다. 사용자가 볼 수 있는 채널의 범위와 저장소·PR의 공개 범위가 다를 수도 있다. 대화의 귀속 문구가 있다고 해서 원본 대화 전체가 PR 독자에게 보이거나, 반대로 비공개 채널의 모든 내용이 안전하게 가려진다고 단정하지 않는다. 실제 연결·표시 범위를 조직 환경에서 확인해야 한다.

저장소 자동 추정은 재선택을 줄이지만 다중 저장소 조직에는 새로운 검증점이 된다. 같은 제품의 웹, 모바일, 백엔드가 별도 저장소일 수 있다. ‘로그인 오류를 고쳐줘’만으로는 어느 서비스인지 명확하지 않다. 가장 최근 대화에 나온 저장소가 맞다고 해도 변경할 권한·테스트 환경·릴리스 담당자가 다를 수 있다. 코딩 세션 시작 전에 추정한 저장소 이름과 브랜치, 예상 변경 경로를 사람에게 드러내는 흐름이 좋다. 원문은 제품이 저장소를 식별한다고만 설명하므로 언제 어떤 확인 UI가 뜨는지 조직별 동작은 직접 검증해야 한다.

Teams Canvas의 장점은 계획과 변경·미리보기를 대화 흐름에서 함께 볼 수 있다는 것이다. 이 장점이 설계 승인으로 곧장 바뀌지는 않는다. 미리보기에 로그인된 사용자가 어떤 테스트 데이터로 화면을 보았는지, 공유된 화면이 실제 프로덕션 권한을 반영하는지, 캡처가 최신 커밋인지 확인해야 한다. 특히 인사시스템에서는 직원 정보·승인 결재·휴가 잔여일 같은 민감한 데이터가 대화와 미리보기에 노출될 수 있다. 실제 직원 데이터 대신 합성·익명화 자료를 쓰고, PR에서는 권한 검사를 별도로 확인한다. UI에서 버튼이 보이지 않는 것과 API에서 권한이 막힌 것은 다른 증거다.

### 대화에서 PR까지의 권장 검증 체인

1. **요청 캡처:** 질문자가 원하는 결과, 재현 가능한 문제, 요청 범위, 민감도, 마감 조건을 요약한다. 대화 원문을 그대로 제품 요구사항으로 승격시키지 않는다.
2. **저장소 확인:** 추정한 저장소·브랜치와 예상 변경 대상이 맞는지 확인한다. 다중 저장소 문제라면 단일 PR로 해결되는지 판단한다.
3. **작업 계약:** 허용할 파일·도구·네트워크·데이터 범위를 정한다. 테스트 명령과 금지할 동작을 명시한다.
4. **중간 검토:** 계획, 변경 파일, 실행한 검증, 실패한 명령을 대화나 PR에서 읽을 수 있게 한다. ‘완료’보다 ‘무엇을 검증했는지’가 중요하다.
5. **최종 리뷰:** 요구를 제시한 사람의 의도 검토, 코드 소유자의 구현 검토, CI·보안 결과를 서로 대체하지 않는다.
6. **귀속과 보존:** 이슈·PR의 대화 귀속 문구가 충분한 추적 정보를 담는지 확인하고, 민감한 원문을 무단 복제하지 않는다.
7. **회수:** 잘못된 저장소·요구로 작업을 시작했다면 PR을 닫고 새 이슈로 정정하는 절차를 둔다. 이미 공개된 정보가 있다면 별도로 회수한다.

이 체인은 제품이 자동으로 수행한다고 발표한 단계가 아니다. 공식 변경이 새 입력 경로를 열었기 때문에 팀이 설계해야 할 통제다. 이전에는 개발자가 이슈를 수동으로 쓰면서 암묵적으로 수행하던 범위 확인이, 대화에서 곧장 세션이 시작되면 빠지기 쉽다. 속도를 얻은 곳에 검증 단계를 재배치해야 한다.

## 개발자에게 의미 — 네 발표를 하나의 개발 수명주기로 연결하기

**요구 정의:** Slack·Teams 대화는 현장 맥락을 빠르게 포착한다. 그러나 대화가 구조화된 명세보다 우월한 것은 아니다. 이슈로 변환할 때 문제와 해결 제안을 구분하고, 사용자의 실제 필요와 개발자가 상상한 기능을 분리한다. 문서로 남긴 수락 조건이 없으면 에이전트가 그럴듯한 구현과 그 구현에만 통과하는 테스트를 만들어도 실패가 드러나지 않을 수 있다.

**실행:** 앱, CLI, JetBrains Air, Xcode, VS Code로 작업 표면이 넓어졌다. 동일한 변경이라도 실제 작업 장소에 따라 접근 가능한 비밀정보와 도구가 달라진다. 프로젝트의 공통 지침과 환경별 승인 설정을 분리한다. 로컬 보조 승인 설정을 팀 전체 정책으로 착각하지 않는다. MCP 서버 목록을 볼 수 있다는 사실만으로 특정 서버의 내용을 신뢰하지 않는다.

**검증:** 코드 리뷰 API가 정책과 출처를 노출하니, AI 코멘트를 기계적으로 감사할 수 있는 단서가 늘었다. 그러나 가장 필요한 질문은 그대로다. 어떤 파일이 빠졌는가? 어떤 코드 리비전을 봤는가? 그 코멘트가 실제 요구사항과 맞는가? 테스트와 정적 분석이 잡지 못한 계약 오류가 있는가? AI 리뷰의 세 모델이 같은 잘못된 전제에 서 있지 않은가? 리뷰를 ‘승인 버튼’으로 쓰기보다 사람 검토가 집중할 영역을 정하는 도구로 써야 한다.

**병합:** Agent Merge는 대기 업무를 줄이지만 무엇을 기다려야 하는지는 조직의 보호 규칙이 결정한다. 필수 검사, 승인, 릴리스 창, DB 마이그레이션 정책을 분리하지 않으면 ‘자동 병합 가능’이 ‘안전한 배포’로 오인된다. 고위험 변경은 별도의 수동 검토를 남기는 것이 합리적일 수 있다.

**측정:** 새 대시보드 필드로 이전에 보이지 않던 활동이 보인다. 이것은 관측의 개선이다. 조직은 도입률, 유용성, 품질, 비용, 위험을 서로 다른 지표로 봐야 한다. 참여가 두 배 늘었더라도 실제 결함 수정 시간이 그대로라면 성과의 해석은 달라진다. 반면 팀의 소수 인원이 복잡한 문제 해결에 도움을 받고 있다면 총 사용량이 낮다고 바로 중단할 이유도 없다.

### 인사시스템 같은 실제 서비스에 적용한 예시

직원이 ‘휴가 잔여일이 틀리다’고 Teams에 올렸다고 가정하자. 이는 GitHub의 공개 사례가 아니라 운영 설계를 설명하는 가상 예시다. `@GitHub`가 해당 대화를 이슈로 전환하면 먼저 직원의 실제 휴가 데이터와 대화 내용이 개발 저장소에 복제되지 않았는지 확인한다. 문제는 화면 표시 오류일 수도 있고, 백엔드 계산·근태 데이터·승인 정책의 차이일 수도 있다. 저장소 자동 추정이 웹 프런트엔드로 향했다고 해서 계산 로직이 그 저장소에 있다는 뜻은 아니다. 코딩 에이전트의 PR이 UI 숫자만 바꾸지 않았는지, 취업 규칙과 승인 이력이 테스트에 반영됐는지 사람이 검토한다.

Copilot 코드 리뷰가 ‘권한 체크를 보강하라’고 코멘트를 남겼다면 어떤 사용자 지침·도구 자료를 근거로 했는지 볼 수 있는 경우가 있다. 하지만 근거가 있다고 해서 실제 회사의 인사 정책과 맞는 것은 아니다. 제외된 파일에 권한 정책 마이그레이션이 있다면 AI 리뷰에 코멘트가 없어도 사람이 읽어야 한다. 모든 CI가 통과해 Agent Merge가 가능해져도 실제 직원 정보에 영향을 주는 변경에는 제품 소유자와 운영 담당자의 결재가 필요할 수 있다. 이후 대시보드에서 Chat과 에이전트 사용량이 늘어도 휴가 계산 오류가 줄었는지, 문의 해결 시간이 개선됐는지를 따로 측정한다.

이 예시의 핵심은 AI 코딩의 성능을 부정하는 데 있지 않다. 개발 흐름이 빨라질수록 요구·권한·근거·배포·성과의 각 계약을 더 명시적으로 만들어야 한다는 것이다. AI가 작성한 코드의 양은 제품 가치가 아니다. 정확한 요구를 검증 가능한 방식으로 안전하게 운영까지 연결했을 때 가치가 생긴다.

## 운영 포인트 — 월요일에 실제로 확인할 항목

### 1) 관리자 정책과 접근 권한

기업·조직·저장소 코드 리뷰 설정을 누가 바꿀 수 있는지 목록화한다. 상위 정책이 아래 설정을 잠그는 항목을 문서화한다. 중앙 관리 자동화가 있다면 GitHub App·fine-grained PAT가 기업·조직 엔드포인트에 쓰이지 않는다는 제약을 먼저 확인한다. 저장소 엔드포인트의 `Administration: read/write` 범위를 필요한 작업에만 부여한다. 개인 토큰을 조직 공용 비밀처럼 사용하지 않는다. 설정 변경 이력에는 변경 전후 값, 이유, 요청자, 실행 주체, 회수 방법을 남긴다.

### 2) 리뷰 범위와 품질

시험 PR을 만들고 Copilot 귀속 필드, 노력 수준, 보고된 스킬·MCP·지침, 제외 파일 목록을 확인한다. 어느 필드가 실제 API에서 빠질 수 있는지 기록한다. 리뷰에 언급되지 않은 파일이 더 중요한 변경일 수 있으므로, 변경 파일 전체와 제외 목록을 함께 읽는다. 리뷰 코멘트의 유효성은 ‘지적 후 실제 수정된 결함’, ‘틀린 지적’, ‘판단 불가’를 나누어 평가한다. 피드백의 수가 아닌 실제 수정 결정이 중요한 결과다.

### 3) 사용률 리포트의 기준선

28일 기업·조직 보고에 새 `chat`·`vscode_agent` 필드가 있는지 확인한다. 과거 기간은 일곱 기능, 현재는 아홉 기능이라는 주석을 대시보드에 남긴다. `No Cohort` API 값을 Chat-first라는 표시명과 매핑하되 코호트 판정이 바뀌었다고 처리하지 않는다. 여러 기능의 참여 수를 합산해 고유 사용자를 만들지 않는다. 사용 지표 정책과 접근 권한을 점검하고, 0·미수집·처리 중을 별도 상태로 표시한다.

### 4) 대화 기반 작업의 입력 검증

Slack·Teams에서 어떤 채널이 코드 작업 시작에 적합한지 정한다. 비공개 인사·보안·고객 사건 대화는 저장소 이슈로 원문을 복제하지 않도록 다룬다. 저장소 자동 추정이 잘못될 수 있는 다중 저장소 요청을 시험한다. 생성된 이슈·PR의 귀속 문구가 누구에게 무엇을 보여 주는지 확인한다. Canvas나 미리보기의 접근 범위와 테스트 데이터 정책을 명시한다. 후속 메시지를 이어가면서 요구사항이 바뀌면 이슈의 수락 조건도 함께 갱신한다.

### 5) 자동 승인·병합의 안전한 범위

로컬 보조 승인은 읽기·쓰기·외부 요청을 같은 규칙으로 묶지 않는다. Agent Merge를 켜는 저장소에는 최신 커밋의 필수 검사, 필수 리뷰, CODEOWNERS, 배포 정책을 검토한다. 데이터 스키마·권한·결제·개인정보 관련 PR은 검사 통과만으로 병합하도록 설계하지 않는다. 자동 병합을 취소하고 수동 처리로 전환할 경로가 있어야 한다. 실패한 검사나 리뷰 실패가 재시도로 가려지지 않도록 최종 상태를 기록한다.

### 6) 성과를 검증할 관찰 계획

한 달을 기준으로 도입·품질·시간·비용의 네 범주를 따로 측정한다. 도입에는 실제 활성 사용자와 기능별 참여를, 품질에는 배포 후 결함과 되돌림을, 시간에는 이슈부터 PR·배포까지의 기간을, 비용에는 크레딧과 사람의 검토 시간을 포함한다. 작업 난이도와 팀 구성이 달라지면 전후 비교에 주석을 붙인다. 사용률 증가를 성과라고 먼저 결론내린 뒤 지표를 고르지 않는다. Copilot을 쓰지 않은 작업과 비교할 때도 작업 종류·리스크·기간이 비슷한지 먼저 확인한다.

## 주말 심층 해설 — 코드 생성보다 ‘검토 가능한 작업 기록’이 중요해지는 이유

AI 코딩 도구의 초기 가치는 개발자가 쓰려던 코드 조각을 빨리 완성하는 데 있었다. 지금은 대화로 작업을 시작하고, 에이전트가 여러 세션에서 코드를 바꾸고, 다른 AI가 리뷰하고, 조건이 충족되면 병합하며, 관리자가 그 사용량을 분석하는 흐름이 하나의 제품군 안에 들어온다. 작업 단위가 커질수록 최종 diff만으로는 의사결정의 경로를 이해하기 어렵다. 어떤 요구로 시작했는지, 왜 그 저장소를 골랐는지, 어떤 도구 요청을 자동 승인했는지, 리뷰에서 어떤 파일을 못 봤는지, 어느 검사와 사람이 승인했는지를 남겨야 한다.

기록이 많다고 자동으로 좋은 것은 아니다. 로그 전체를 PR에 복사하면 비밀정보가 섞이거나 중요한 결정이 묻힐 수 있다. 검토 가능한 기록은 **결정, 근거, 예외, 결과**를 구분한다. 예를 들어 ‘테스트 통과’는 결과이고 ‘이 테스트가 휴가 계산의 경계값을 다룬다’는 근거다. ‘코드 리뷰가 완료됨’은 절차 상태이고 ‘민감한 마이그레이션 파일은 리뷰에서 제외돼 사람이 검토함’은 예외 처리다. ‘개발자가 승인함’은 결정이지만 어떤 권한과 역할로 승인했는지는 별도 정보다. AI가 더 빠르게 결과물을 늘릴수록 이 작은 차이가 운영 품질을 좌우한다.

이번 GitHub 변경 중 명시적 귀속과 자료 출처는 이런 기록의 일부를 기계가 읽을 수 있게 하는 진전이다. 그러나 메타데이터를 해석하는 규칙이 없으면 ‘출처 존재’만을 근거로 무비판적 승인으로 이어질 수 있다. 대시보드 필드도 같은 성질이다. 관측 범위가 넓어지면 의사결정의 재료는 많아지지만, 측정 변화 자체가 추세를 왜곡할 수 있다. 좋은 자동화는 정보를 숨기지 않고 사람이 판단할 지점을 작게 만든다. 나쁜 자동화는 서로 다른 책임을 하나의 녹색 배지로 압축한다.

### 실패 유형별 대응표

| 상황 | 무엇을 먼저 확인할까 | 즉시 취할 조치 | 장기적으로 고칠 설계 |
| --- | --- | --- | --- |
| 대화에서 엉뚱한 저장소에 PR 생성 | 저장소 추정·요청 문장·권한 | PR 중단, 올바른 저장소 재지정 | 저장소 확인 단계와 다중 저장소 분류 |
| Copilot 리뷰에 코멘트가 없음 | 리뷰 상태·미검토 파일·실패/재시도 | 사람이 주요 변경을 읽음 | 제외 파일·최종 상태를 PR 체크로 표시 |
| 리뷰가 틀린 보안 결론 제시 | 참조 지침·도구·코드 리비전 | 코멘트 반박과 근거 기록 | 지침 소유자·버전 관리, 회귀 사례 추가 |

| Chat-first 수치가 변함 | UI 명칭과 API `No Cohort` | 변환 로직 점검 | 표시명·원본값 매핑을 버전 관리 |
| 자동 병합 후 결함 | 필수 검사·승인·최신 커밋 | 롤백·원인 조사 | 고위험 변경의 별도 게이트 |
| 로컬 세션이 예상치 못한 도구 사용 | 보조 승인 지침·도구 권한 | 지침 회수·세션 중지 | 읽기/쓰기/외부 호출 구분 |

| GitHub App으로 상위 정책 수정 실패 | API 계층·지원 토큰 종류 | 권한을 확대하지 않고 호출 경로 변경 | 계층별 관리자 자동화 분리 |
| 대화 귀속이 민감 정보를 노출 | 이슈·PR 설명과 채널 접근 | 노출 범위 축소·문구 수정 | 민감 채널의 작업 생성 제한 |

이 대응표는 GitHub가 발표한 오류 목록이 아니다. 발표된 기능과 제약에서 도출한 실무 시나리오다. 특히 API 정책 수정 실패가 났을 때 무작정 더 강한 토큰을 발급하지 않는 것이 중요하다. 어느 계층의 어떤 엔드포인트가 그 토큰 종류를 지원하는지 먼저 확인해야 한다. 지표가 증가했을 때도 성과가 좋다는 발표를 먼저 하지 않고 측정 정의가 바뀌었는지 살핀다.

**편집 메모:** 네 GitHub 항목은 한 공급자의 제품 변경이므로 전체 AI 산업의 공통 추세를 통계적으로 대표하지 않는다. ‘개발 생산성 증가’, ‘보안 사고 감소’, ‘AI 리뷰 정확도 개선’ 같은 성과 수치는 이 발표들에서 독립적으로 확인되지 않았다. 위의 인사시스템 예시, 운영 절차, 실패 대응표는 공개 기능을 실제 팀에 적용하기 위한 제안이며 공급자 보증이나 실제 고객 성과가 아니다. 오늘 확인할 수 있는 확실한 변화는 **정책을 API로 관리하고 결과 출처를 일부 확인할 수 있게 된 점, 측정에 두 사용 경험이 추가된 점, 여러 환경에서 에이전트 작업 흐름이 확장된 점, 팀 대화가 개발 작업의 시작점이 된 점**이다. 이를 유용한 제품 성과로 만드는 책임은 요구사항과 승인·측정의 경계를 설계하는 팀에 남아 있다.

## 실무 설계 부록 — 발표 기능을 팀의 운영 기준으로 번역하기

다음은 뉴스 요약이 아니라 팀이 실제 도입 전에 토론할 수 있는 설계 질문이다. 각 항목에서 ‘공식 확인’과 ‘권장 검증’을 분리한다. 특히 공급자가 공개하지 않은 정확도, 비용 절감률, 조직별 안전성은 임의로 채우지 않는다. 주말에 새 모델 발표가 없는 만큼, 토요일의 네 변경이 월요일 개발 흐름에 미치는 영향을 깊게 해설한다.

### A. 정책 계층을 ‘누가 켜는가’가 아닌 ‘누가 예외를 승인하는가’로 읽기

공식 확인: Copilot 코드 리뷰 설정에는 기업, 조직, 저장소의 계층이 있고 상위 관리 설정을 하위가 덮을 수 없다. 이 구조는 중앙에서 항상 같은 설정을 강제하라는 뜻은 아니다. 서비스 유형이 다른 조직은 중앙의 금지선과 저장소의 조정 가능 영역을 따로 정해야 한다. 예를 들어 기업은 민감 저장소에서 특정 외부 MCP를 금지하고, 조직은 기본 리뷰 노력 수준을 정하며, 저장소는 테스트 코드 위주 프로젝트의 추가 지침을 켤 수 있다. 이 예는 GitHub의 기본 정책이 아니라 가능한 설계다.

실무에서는 설정의 값보다 **예외의 생명주기**가 중요하다. 급한 보안 패치를 위해 특정 봇의 자동 리뷰를 우회했다면, 우회 항목이 영구히 남지 않도록 이유·담당자·만료 조건을 기록한다. 예외를 허용하는 관리자에게 필요한 권한과 그 예외를 실제로 사용하는 작업 주체의 권한도 다르다. 한 명의 토큰이 기업 정책과 개별 PR 실행까지 모두 담당하면 사고 범위가 커진다. 정책 계층별 자격 증명 제약은 제품의 사소한 API 불편이 아니라 권한 분리 설계의 힌트다.

검증할 수 있는 결과는 ‘설정 API 호출이 성공함’뿐만이 아니다. 저장소의 실제 리뷰 요청이 정책을 따르는지, 우회 목록에 속한 주체에게 리뷰가 붙지 않는지, 상위 정책 잠금이 UI와 API에 일관되게 반영되는지 시험해야 한다. 실험은 테스트 저장소에서 시작하고, 부정 사례—권한 없는 토큰의 변경 요청, 상위 정책과 충돌하는 저장소 설정, 누락된 필드—를 함께 확인한다. 성공 사례만으로 정책 강제를 입증하지 않는다.

### B. 리뷰 코멘트 출처를 감사 가능한 증거로 만드는 최소 단위

공식 확인: 리뷰·댓글의 Copilot 귀속을 식별할 수 있고, 사용 가능한 경우 노력 수준과 코멘트에 대한 스킬·MCP·지침 출처가 보인다. 이 정보가 있다고 해서 사용한 외부 자료의 모든 내용이 보존되는 것은 아니다. ‘MCP 서버 X를 참조했다’는 이름만으로 그 서버가 당시 어떤 문서 버전을 반환했는지 알 수 없다. 따라서 조직의 지식 도구를 AI 리뷰에 연결한다면 서버 응답의 문서 ID·시각·리비전을 별도 감사 로그로 남길지 판단해야 한다. 반대로 과도한 로깅은 저장소 내용과 개인정보를 불필요하게 복제할 수 있으므로 최소화가 필요하다.

코멘트의 진위를 검토할 때는 네 가지 대조가 유용하다. 첫째, 코멘트가 가리키는 코드 줄이 최종 커밋에도 있는가. 둘째, 해당 지침은 현재 브랜치와 적용 대상에 맞는가. 셋째, MCP가 준 자료가 제품 규정인지 참고 예제인지 구분되는가. 넷째, 코멘트를 따른 수정이 다른 요구사항을 깨뜨리지 않는가. AI 리뷰의 설명이 자신감 있게 쓰였다는 사실은 어느 항목도 대신하지 못한다. 코멘트를 수용한 사람의 판단을 기록하면 나중에 같은 오탐이 반복되는지도 볼 수 있다.

좋은 출처 기록은 ‘AI가 말했다’라는 불투명한 권위 대신 ‘어떤 도구·지침을 참고한 한 코멘트’로 격하한다. 이 격하는 AI를 과소평가하려는 것이 아니라 재검토 가능성을 높인다. 출처가 틀렸다면 문서 또는 MCP 서버를 고치고, 코멘트의 해석이 틀렸다면 리뷰 지침이나 피드백을 수정한다. 모든 오류를 프롬프트 한 줄에 누적하면 근본 원인을 놓친다.

### C. ‘Files not reviewed’를 품질 게이트의 분모로 다루기

공식 확인: 새 리뷰 개요는 건너뛴 파일과 내용이 제외된 파일을 한 섹션에 모으고 파일명과 이유를 연결한다. 검토된 파일 수가 줄어도 리뷰 코멘트가 없어 보일 수 있다는 사실을 더 쉽게 확인할 수 있다. 그러나 초과 목록은 접혀 있을 수 있고 요약이 간결해진 만큼 독자가 중요한 예외를 지나칠 가능성도 있다. PR 템플릿에는 총 변경 파일과 검토 제외 파일 중 보안·DB·권한·인프라 파일의 존재 여부를 별도로 표시하는 방안을 고려할 수 있다.

파일 수를 단순 비율로만 보지 않는 것도 중요하다. 100개의 번역 파일 중 2개가 제외된 것과 3개 파일짜리 PR에서 권한 정책 파일 1개가 제외된 것은 위험도가 다르다. 경로·확장자·소유자·변경 종류를 조합한 분류가 필요하다. 생성 코드나 대형 바이너리는 사람이 줄마다 읽기 어렵지만, 생성기의 입력과 출력 검증·배포 영향은 볼 수 있다. ‘AI가 못 봄’은 곧 ‘아무도 볼 수 없음’이 아니다. 별도 검증을 설계할 수 있다.

실패 모드는 리뷰 상태를 단일 녹색 표시로 축약하는 것이다. 리뷰 완료, 일부 미검토, 실패 후 재시도, 모델 전환, 사람 승인 대기를 각각 별도 상태로 보는 편이 좋다. GitHub의 발표는 UI 개요가 더 명확해졌다는 사실이지, 모든 팀의 브랜치 보호에 미검토 파일 게이트가 자동 추가됐다는 뜻이 아니다. 팀이 필요한 게이트를 직접 설계해야 한다.

### D. 리뷰 노력 수준을 비용과 위험의 함수로 선택하기

공식 확인: 리뷰 노력 수준은 설정에서 관리할 수 있고, API로 확인할 수 있는 경우 리뷰에 사용한 수준의 메타데이터가 있다. Balanced effort에는 세 리뷰어 모델과 결합 모델이 사용된다. 더 많은 모델을 쓴다고 언제나 더 값진 지적이 나온다는 발표는 아니다. 저장소의 PR 유형별로 비용·지연·유효 코멘트 수를 함께 측정해야 한다.

실무 예를 들어 단순 문서 오탈자는 낮은 노력으로도 충분할 수 있고, 인증·정산·권한 경계는 높은 노력과 사람 전문가가 모두 필요할 수 있다. 문제는 PR 제목만 보고 위험을 자동 판정할 때 생긴다. ‘문서 업데이트’라는 제목 아래 정책 코드가 함께 바뀌면 낮은 노력의 리뷰가 중요한 부분을 놓칠 수 있다. 변경 경로와 내용, 영향 범위를 기준으로 분류하고 불확실하면 사람에게 올리는 쪽이 낫다. 어떤 수준을 선택하든 미검토 파일과 실패 상태는 별도로 표시한다.

비용 최적화도 단순 크레딧 최소화가 아니다. 값싼 리뷰가 높은 오탐률로 사람의 시간을 더 쓰게 만들거나, 값비싼 리뷰가 실제로 중요한 결함을 발견하면 단순 실행 비용 비교가 무의미하다. 유효 코멘트당 비용, 사람이 검토에 쓴 시간, 배포 후 되돌림을 비교하되 PR 난이도와 팀의 차이를 통제해야 한다. 숫자를 만들기 위해 모든 PR을 같은 수준으로 강제할 필요는 없다. 위험별 정책이 더 실용적일 수 있다.

### E. 사용률 보고의 스키마 변경을 제품 성과와 분리하기

공식 확인: 기업·조직 28일 보고에 `chat`과 `vscode_agent` 필드가 추가됐고 과거 보고에는 없다. 이를 데이터웨어하우스에 적재할 때는 새 필드의 부재를 0으로 채울지 `null`로 남길지가 중요하다. 과거에 수집하지 않은 수치를 0으로 만들면 그 시기의 사용자가 전혀 없었던 것처럼 보인다. 이 변경에서는 ‘미관측’을 별도 값으로 남기는 것이 비교의 정직성을 지킨다. 현재 기간에서 실제 0은 필드가 존재하면서 참여자가 0인 경우에만 붙인다.

이름 변경 역시 두 층으로 저장하는 편이 안전하다. 원본 API의 `No Cohort`는 안정된 기계 값이고 UI의 ‘Chat-first’는 설명용 표시명이다. 화면 언어와 명칭은 바뀔 수 있으므로 ETL의 키를 표시명으로 잡지 않는다. 과거 ‘Passive’ 라벨이 있던 보고와 새 라벨을 한 그래프에 놓을 때는 동등한 코호트 판정인지 공식 설명을 확인해 주석을 붙인다. 이번 발표에서는 코호트 크기와 단계 규칙이 변하지 않는다고 명시됐다.

사용자의 한 달 참여는 복잡하다. 28일 동안 이틀 이상 Chat을 사용했더라도 실제 프로젝트에 실질적인 기여를 했는지는 알 수 없다. 반대로 복잡한 장애 분석에 한 번만 사용해 큰 도움을 받은 사람은 ‘참여’ 기준에 못 들어갈 수 있다. 측정은 필요한 질문에 맞는 분모와 단위를 택해야 한다. 라이선스 수요를 볼 때는 반복 사용자가 중요하고, 성과를 볼 때는 해결한 작업의 가치와 품질이 중요하다. 한 지표가 두 질문의 답일 수는 없다.

### F. 매체별 텔레메트리 차이를 염두에 둔 비교

공식 확인: 이번 주간 릴리스는 앱, CLI, JetBrains Air, Xcode 베타, VS Code 실험 화면에 걸친다. 그러나 영향 대시보드의 새 필드는 Chat과 VS Code Agents 창을 대상으로 한다. ‘Copilot을 사용하는 모든 환경이 새 필드에 같은 방식으로 집계된다’고 추론하면 안 된다. 특히 Xcode는 공개 미리보기 단계이고, VS Code의 채팅 보기 모드는 표시 실험이다. 제품별 기능 출시 단계와 대시보드의 계측 범위는 다르다.

조직이 IDE 팀을 비교할 때는 도구 보급률부터 확인한다. 어떤 팀은 Xcode 베타를 사용할 수 없고, 어떤 팀은 JetBrains Air를 쓰며, 다른 팀은 서버 개발 때문에 CLI 중심일 수 있다. 기능별 참여 수를 팀 경쟁표로 만들면 환경 차이가 개인의 열의처럼 보인다. 보고서는 지원된 버전과 기능, 대상 사용자 수, 보고의 누락 가능성을 함께 보여 줘야 한다. 새로운 필드가 없다고 해서 특정 IDE의 업무가 AI 지원을 받지 않았다는 뜻은 아니다.

또한 세션을 여러 개 열 수 있다는 기능은 작업 생산성의 한 신호일 뿐이다. 동시에 진행된 세션이 같은 파일을 바꾸거나 같은 요구를 중복 구현하면 오히려 합치는 시간이 늘 수 있다. 세션별 작업 범위와 파일 소유, 충돌 검토, 병합 순서를 명시해야 한다. 동시성이 높을수록 완료 개수보다 **완료된 기능이 하나의 릴리스에서 일관되게 동작하는가**가 더 중요한 지표가 된다.

### G. Slack·Teams 대화의 ‘요청자’를 개발 승인자로 오인하지 않기

공식 확인: `@GitHub`가 만든 이슈와 PR에는 Slack·Teams 대화와 `@username` 귀속 문구가 들어간다. 귀속은 누가 시작했는지 알려 주는 단서다. 그것만으로 그 사람이 제품 소유자, 코드 소유자, 보안 승인자라는 뜻은 아니다. 특히 단체 채널에서 다른 사람이 질문한 버그를 제3자가 요약해 `@GitHub`에 전달했다면 귀속 문구는 최종 요구사항 승인자를 충분히 나타내지 못할 수 있다.

따라서 이슈에는 ‘요청한 사람’과 ‘수락 조건을 승인한 사람’을 분리해 기록하는 것이 좋다. 사내 지원 채널의 질문자는 실제 문제를 잘 알지만 수정 방향을 결정할 권한은 없을 수 있다. 반대로 관리자는 정책 권한이 있지만 실제 장애의 재현 방법을 모를 수 있다. 대화 기반 작업 흐름이 성공하려면 두 종류의 지식을 결합해야 한다. 비공개 대화에서 나온 민감한 정보는 개발 이슈에 원문으로 옮기지 말고 문제 해결에 필요한 최소 재현 자료만 남긴다.

대화에서 직접 PR을 만들 수 있어도 완료 통지는 대화에만 남겨서는 안 된다. 나중에 감사하거나 장애를 조사할 때 PR에서 요구·검증·결정에 접근할 수 있어야 한다. 반대로 PR에 비공개 대화의 전체 로그를 복제하면 정보 최소화 원칙을 깨뜨릴 수 있다. 필요한 사실만 구조화해 양쪽을 링크하고, 접근 권한이 다른 독자에게 보이는 범위를 점검한다.

### H. 저장소 자동 식별의 정확도를 시험하는 방법

공식 확인: `@GitHub`는 메시지에서 저장소를 식별해 재선택 단계를 줄인다. 이 기능이 항상 올바른 저장소를 고른다는 정확도 수치는 공개되지 않았다. 따라서 실무 시험에는 명확한 단일 저장소 요청뿐 아니라 유사한 이름의 저장소, 여러 서비스가 얽힌 장애, 저장소 이름이 없는 요청, 과거 대화에 나온 저장소와 새 요청의 대상이 다른 경우를 포함한다. 결과는 ‘맞음/틀림’만이 아니라 얼마나 쉽게 사람이 확인하고 수정할 수 있는지도 평가한다.

오류 비용도 다르다. 잘못된 저장소에서 읽기만 한 세션과, 그곳에 코드를 변경해 PR을 연 경우의 영향이 다르다. 민감 저장소에서 외부 MCP 도구를 사용한 경우는 더 크다. 그래서 낮은 위험의 자동 추정은 허용해도, 쓰기·PR 생성 단계에는 저장소와 브랜치를 명시적으로 보여 주는 방식이 적합할 수 있다. 이 역시 공급자의 기본 동작을 단정하는 문장이 아니라 조직이 원하는 승인 경계를 정하는 제안이다.

저장소 자동 식별은 다중 저장소 기능 개발에도 한계가 있다. 인사시스템의 모바일 앱, API, 정책 서비스가 별도 저장소라면 한 대화에 여러 PR이 필요할 수 있다. 단일 저장소로 너무 빨리 축소하면 화면만 수정하고 계산 오류를 남길 수 있다. 먼저 문제의 소유 서비스를 찾고, 다른 저장소와의 인터페이스를 확인하고, 각 저장소의 테스트·릴리스 순서를 정해야 한다. 자동화가 입력 결정을 도와도 시스템 경계의 설계는 사람의 책임이다.

### I. 자동 병합을 위한 ‘충족 조건’의 품질

공식 확인: Agent Merge는 PR에서 설정할 수 있고 필수 검사나 규칙을 기다리는 동안 켜진 상태를 유지한다. 따라서 ‘한 번 설정하고 나면 나중에 조건이 맞았을 때 병합’하는 운영이 가능해진다. 이때 조건의 품질은 자동 병합의 품질 상한선이다. 필수 검사가 빌드 성공만 확인하고 중요한 비즈니스 불변식을 시험하지 않으면, 자동 병합은 그 공백을 메우지 못한다. 변경이 마이그레이션을 포함한다면 코드 테스트 외에 롤백 가능성과 실제 데이터 상태를 평가해야 한다.

검사와 승인에도 시각이 있다. 작성자가 마지막 커밋을 푸시한 뒤 이전 승인과 검사를 계속 유효하게 볼 것인지, 브랜치를 최신 main과 맞추었는지, 병합 직전 종속 서비스가 바뀌었는지 확인한다. 브랜치 보호는 이러한 문제에 대응하는 구성 옵션을 제공할 수 있지만, 이 발표 자체는 특정 조직의 구성이 안전하다고 보증하지 않는다. 자동 병합을 켜는 팀은 실제 규칙을 감사하고 시험 PR에서 충족·미충족·실패 후 수정의 상태를 확인해야 한다.

사람이 최종 책임을 지는 위치를 명확히 한다. 저위험 문서 수정은 사전 승인된 검사를 마친 뒤 자동 병합해도 좋을 수 있다. 권한 체계, 급여 계산, 대량 데이터 수정은 별도 승인이 필요하다. ‘에이전트가 만든 PR이므로 더 엄격하다’ 또는 ‘AI 리뷰가 있으니 더 느슨해도 된다’ 중 하나로 고정할 필요는 없다. 변경의 영향·복구 난이도·검증 가능한 범위를 기준으로 분류한다.

### J. 보조 승인의 적용 장소와 권한 구분

공식 확인: 개인 지침을 통한 도구 요청의 보조 승인은 opt-in이며 로컬 세션에 적용한다. 개발자가 매번 승인하던 도구를 사전에 허용하면 흐름은 빨라질 수 있다. 그러나 허용 대상을 ‘읽기’라고만 분류해도 네트워크로 내용을 보낼 수 있는 명령, 비밀 환경 변수를 출력하는 명령, 복구하기 어려운 파일 변경이 섞일 수 있다. 도구 이름보다 실제 인자와 대상 경로, 네트워크·자격 증명 접근을 봐야 한다.

실용적인 시작점은 읽기 전용·정해진 경로·저위험 명령의 범위를 좁히는 것이다. 외부 전송, 배포, 계정 설정, 대량 파일 삭제, 브랜치 병합은 별도 확인으로 남긴다. 어떤 명령을 ‘자동 승인’할지 문서화할 때는 허용 조건과 제외 조건을 함께 적는다. 단순히 ‘git 명령 허용’처럼 넓은 문구는 조회부터 원격 푸시까지 묶어 버린다. 승인 피로를 줄이는 목적과 영향 통제를 동시에 만족하려면 작업별 정책이 필요하다.

로컬 세션의 승인 지침을 클라우드 작업과 동일하게 보지 않는다. 개인 노트북의 환경 변수와 클라우드 런타임의 토큰 수명·파일 시스템은 다르다. 주간 릴리스는 로컬 적용만을 명시했으므로 이를 원격 세션의 새 자동 승인 기능으로 소개하면 사실 오류다. 실행 환경이 바뀔 때 기존 지침이 따라오거나 따라오지 않는지는 실제 제품 문서와 시험으로 확인해야 한다.

### K. MCP 서버 통합 설정과 리뷰 근거의 교차점

공식 확인: Copilot CLI의 `/settings`는 플러그인과 MCP 서버 등을 찾는 통합 화면이고, 코드 리뷰 API는 코멘트에 쓰였다고 보고된 MCP 서버 출처를 보여 줄 수 있다. 하나는 도구를 **연결하는 곳**, 다른 하나는 도구가 **영향을 준 흔적**이다. 연결과 사용이 구분되면 운영자는 ‘허용된 서버가 실제 리뷰에 자주 쓰이는가’, ‘안 쓰는 서버가 과도한 권한을 가진 채 남았는가’를 조사할 수 있다. 다만 두 발표가 모든 환경에 동일한 서버 목록과 완전한 호출 로그를 제공한다고 말하는 것은 아니다.

MCP 서버를 관리할 때는 입력과 출력의 신뢰도를 따져야 한다. 개발 문서 검색 서버가 반환하는 오래된 예시는 모델의 코멘트에 권위 있게 섞일 수 있다. 사내 정책 서버가 관리자 전용 문서를 반환하면 일반 개발자의 PR 리뷰에 그 내용이 누출될 수 있다. 악의적인 저장소 파일이 서버가 제공한 내용처럼 전달될 수도 있다. 서버 이름을 감사 로그에 남기는 것은 좋은 출발이지만, 문서 권한·버전·검색 범위·오류 응답 처리까지 확인해야 한다.

도구를 껐는데도 과거 리뷰가 그 출처를 표시하는 것은 정상일 수 있다. 감사 당시 어떤 버전이 허용됐는지 남겨야 현재 설정과 과거 실행을 혼동하지 않는다. 반대로 새 정책이 적용됐는지 시험하려면 설정 값을 읽는 것에 그치지 않고 새 리뷰 세션에서 도구가 실제로 사용 가능한지 확인한다. 정책 변경의 효과와 기록의 해석은 서로 다른 검증이다.

### L. 실패한 리뷰의 재시도와 대체 모델을 어떻게 보고할까

공식 확인: 실패하거나 시간 초과된 리뷰는 한 번 자동으로 재시도하며, 선호 모델이 없으면 다른 적격 모델로 전환할 수 있다. 이 기능은 일시적 장애로 리뷰 결과가 사라지는 일을 줄이려는 개선이다. 하지만 운영자가 볼 때 ‘한 번 실패했다’와 ‘최종적으로 리뷰가 완료됐다’는 둘 다 사실일 수 있다. 리포트가 최종 상태만 보여 주면 장애 경향이 가려지고, 최초 실패만 보여 주면 실제 PR의 최종 검토 상태를 과소평가한다. 가능하다면 실행 시도와 최종 상태를 분리해 관찰한다.

대체 모델 사용은 품질 비교에도 영향을 준다. 어떤 기간에 선호 모델 가용성이 낮아 다른 모델의 비율이 높았다면 코멘트 수·형태가 달라질 수 있다. 이 변화가 실제 품질 차이인지, PR 유형이 달랐는지, 메타데이터에 없는 다른 이유인지 구별해야 한다. 원문은 모든 리뷰에 모델 이름이 반드시 제공된다고 하지 않으므로 확인 가능한 정보의 범위를 먼저 파악한다. 모르는 부분을 표준 모델로 채워 넣으면 지표가 더 잘못된다.

자동 재시도가 있다고 해서 리뷰를 무한정 기다릴 수는 없다. 릴리스 시간에 리뷰가 계속 실패하면 사람이 검토하는 우회 절차와 기록이 필요하다. 우회는 에이전트 자체의 실패를 숨기기 위한 편의가 아니라, 제품 리스크에 맞는 대체 검증을 수행하기 위한 경로다. 나중에 시스템이 복구되면 놓친 PR의 표본을 다시 살펴 품질 차이를 평가할 수 있다.

### M. ‘채팅 기반 개발’의 보존과 접근권을 설계하기

공식 확인: Slack·Teams의 대화가 이슈·PR로 이어지고 생성물에는 대화·사용자 귀속 문구가 있다. 이것은 협업의 문맥을 이어 주지만 채널과 저장소의 보존·접근 정책이 같다는 뜻은 아니다. 채널은 짧은 보존 기간을 가질 수 있고, 공개 저장소의 이슈는 장기간 남을 수 있다. 비공개 채널에서 논의한 고객 사례를 이슈에 옮기면 의도하지 않은 공개가 발생한다. 반대로 대화가 삭제되면 귀속 문구만으로 왜 특정 요구가 결정됐는지 설명하기 어려울 수 있다.

따라서 생성 이슈에는 최소한의 구조화된 요구를 남긴다. 제목은 증상이 아니라 해결해야 할 사용자 문제를 드러내고, 본문은 재현 방법·기대 결과·영향 범위·수락 기준을 담는다. 민감 자료는 적절한 저장소·접근 제어가 있는 사고 관리 시스템을 참조하고, PR 본문에는 직접 복제하지 않는다. ‘대화에서 생성됨’은 출처의 시작점일 뿐, 요구사항 문서와 권한 승인 기록을 대신하지 않는다.

팀이 평가할 또 다른 질문은 후속 메시지의 범위다. 대화가 길어지며 원래 요청과 다른 새로운 기능으로 바뀌면 같은 세션·PR을 계속 쓰는 것이 맞는지 판단해야 한다. GitHub는 후속 메시지에 응답하지 못하던 문제를 고쳤다고 발표했지만, 무제한의 문맥 보존이나 모든 요구 변경의 자동 추적을 보증한 것은 아니다. 변경된 수락 기준은 이슈나 PR에 반영하고, 범위가 크게 달라지면 새 작업으로 분리한다.

### N. 크레딧과 리뷰 품질을 함께 보는 비용 관리

공식 확인: 코드 리뷰 에이전트 세션에 사용한 AI 크레딧이 표시된다. 따라서 조직은 실행 비용을 더 잘 볼 수 있다. 그러나 비용 화면의 숫자는 개발자의 읽기·수정 시간, 잘못된 코멘트로 인한 재작업, 배포 후 결함 비용을 포함하지 않는다. AI 리뷰가 세 건의 유효 결함을 찾아 사람 검토 시간을 줄였다면 크레딧만으로는 비싸 보일 수 있고, 코멘트가 많지만 대부분 오탐이면 저렴해도 낭비다.

운영 지표로는 PR당 크레딧, 유효 코멘트당 크레딧, 리뷰 소요 시간, 사람에게 채택된 제안 비율, 고위험 PR에서 발견된 결함을 나누어 본다. ‘코멘트가 많다’는 지표는 오히려 장황함을 보상할 수 있으므로 피한다. 부정적 평가 사유 중 ‘너무 장황함’과 ‘틀리거나 지나치게 사소함’을 분리해 추세를 보아야 한다. 동일 조직 안에서도 언어·저장소·PR 크기가 달라 비교의 분모를 통일해야 한다.

비용 상한을 설정할 때는 자동 리뷰가 붙는 이벤트의 범위를 먼저 점검한다. 봇 PR, 작은 문서 변경, 동일 PR의 반복 리뷰가 불필요하게 누적될 수 있다. 우회 목록을 무조건 넓히는 대신 반복 리뷰 조건, 변경 규모, 위험 분류를 조정한다. 반대로 중요한 보안 PR에서 비용 때문에 리뷰를 생략한다면 위험 감소라는 본래 목적을 해칠 수 있다. 비용 최적화는 품질·위험과 공동 최적화해야 한다.

### O. 주간 릴리스의 서로 다른 출시 단계를 한데 묶지 않기

공식 확인: Slack·Teams의 `@GitHub`는 일반 제공이고, Xcode 27.3 베타의 Copilot 통합은 공개 미리보기다. VS Code의 채팅 보기 모드는 실험적이다. 같은 주간 정리에 실렸어도 가용성·안정성·지원 환경은 다르다. ‘Copilot이 모든 IDE에서 동일하게 출시됐다’는 요약은 실제 선택에 도움을 주지 않는다. 조직의 개발 환경 목록과 현재 사용 중인 버전을 대조해야 한다.

공개 미리보기 기능은 팀에 큰 가치를 줄 수 있지만, 안정판 IDE가 필요한 릴리스 작업에서 그 기능을 기본 전제로 삼기는 어렵다. 베타를 쓰는 소규모 시험팀을 두고, 호환성·세션 연결·코드 변경·로그를 확인하는 것이 낫다. 실험적 보기 모드는 사람의 인지 부담을 줄일 수 있으나, UI에서 추론 단계를 접었다고 검토 책임까지 사라지는 것은 아니다. 세부 단계를 봐야 할 고위험 작업과 간결한 보기가 편한 일상 작업을 구분한다.

주간 발표는 제품군의 다양한 방향을 보여 준다. 그러나 한 기능의 설명을 다른 제품에 그대로 적용하지 않는 태도가 중요하다. 로컬 보조 승인 지침을 Slack 에이전트의 일반 정책처럼 쓰거나, Xcode 공개 미리보기를 Copilot 코드 리뷰 API의 필수 조건처럼 연결하면 기술 문서가 혼란스러워진다. 각 기능의 적용 표면과 출시 상태를 표로 관리하면 팀 내 전달 오류를 줄일 수 있다.

### P. AI 코딩 도입을 평가하는 파일럿 설계

네 발표를 바탕으로 파일럿을 구성한다면 먼저 범위를 좁힌다. 예를 들어 문서·테스트·낮은 위험의 화면 수정을 한 저장소에서만 허용하고, 대화에서 이슈 생성·코딩 세션·코드 리뷰·사람 승인·병합까지의 경로를 관찰한다. 성공 조건은 ‘PR이 열렸다’가 아니다. 요청자가 수락 조건을 확인했는지, 저장소 선택이 맞았는지, 검증 결과가 재현 가능한지, 제외된 파일이 없는지 또는 사람이 처리했는지, 배포 후 문제가 없는지를 본다.

비교 대상을 선택할 때는 난이도와 리스크가 비슷한 작업을 고른다. AI 도구를 쓴 쉬운 작업과 쓰지 않은 어려운 장애를 비교해 생산성 우위를 주장하면 측정이 왜곡된다. 파일럿 기간에는 팀의 기존 테스트·리뷰 규칙을 보존하고, 새 기능의 효과만 관찰한다. 지표 수집 정책과 개인별 프라이버시 규정을 먼저 확인한다. 상위 관리자 API 접근이 필요한 실험과 저장소 관리자 API만으로 가능한 실험은 별도 환경에서 수행한다.

종료 시에는 세 가지 결과를 분리한다. 첫째, 기능이 실제 환경에서 작동하는가. 둘째, 팀이 검토 가능한 품질로 작업을 끝냈는가. 셋째, 그 방법을 확장할 때 비용·권한·교육 부담이 감당 가능한가. 첫째가 참이어도 둘째·셋째가 자동으로 참이 되지 않는다. 반대로 작은 파일럿의 실수 한 번으로 전체 제품의 가치를 부정할 필요도 없다. 오류 유형을 찾아 정책·문서·검증 절차를 개선할 수 있는지 판단한다.
