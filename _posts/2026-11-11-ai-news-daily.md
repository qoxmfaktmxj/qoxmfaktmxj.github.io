## 배경 — 11월 10일 발표가 하나의 흐름으로 보이는 이유

모델 발표의 첫 문장은 보통 더 긴 문맥, 더 높은 벤치마크, 더 뛰어난 코딩 능력이다. 하지만 개발 조직이 도입을 결정할 때 묻는 질문은 더 넓다. 어디에서 호출하는가, 어느 데이터 경계를 지키는가, 누가 모델을 조직에 켤 수 있는가, 결과가 틀렸을 때 어떻게 알아차리는가, 비용이 사용자의 행동과 어느 정도 함께 증가하는가. 같은 모델 이름도 Google API와 GitHub Copilot에서는 과금, 권한, 프롬프트 흐름, 관찰 가능성이 다르다. “Carbon을 쓴다”는 말 하나로 아키텍처를 설명할 수 없다.

오늘 공개된 공식 자료의 구성을 보면 제품 경쟁이 모델 단독에서 **실행 환경·평가·조달·감사**로 이동한 점이 선명하다. Google의 Carbon은 도구·모델을 여러 단계 연결하는 장기 작업을 강조한다. 같은 날 MKA는 실제 업무처럼 시각 자료와 산출물 형식을 한꺼번에 평가한다. GitHub는 모델 선택을 개발 도구 안으로 들여오지만 관리자가 정책을 통제하게 한다. AWS의 AgentCore 글은 에이전트 성과를 목표 성공, 도구 매개변수, 개인정보 노출, 긴 대화의 일관성으로 나눠 측정한다. Bedrock 호출 로그의 중앙 집계 글은 어떤 요청이 어느 계정·역할·모델에서 나왔는지 추적하자고 제안한다. 이 층들이 빠지면 모델의 품질 향상이 실제 서비스의 신뢰성으로 이어지는지 알기 어렵다.

또 하나의 변화는 검색·발견 인터페이스다. OpenAI의 Business Hub는 기업이 ChatGPT 안에서 자신의 정보와 상품 피드를 제공하고 고객 접점을 만드는 구조를 제시한다. 이는 검색엔진 최적화의 단순 대체가 아니라, **어떤 기업 정보가 누구의 통제 아래 최신 상태로 제공되는가**라는 새로운 데이터 운영 문제다. AWS의 웹 검색 예제도 모델에 검색을 허용하는 것에서 끝나지 않고 날짜, 도메인, 인용 증거를 코드로 검증한다. 서비스 운영자가 사실성의 마지막 단계를 모델의 어휘 유창성에 맡기지 않는다는 공통점이 있다.

이 글은 발표를 세 층으로 분리한다. **확인된 발표 사실**은 원문의 범위·숫자와 함께 소개한다. **개발자에게 의미**는 구현 시 바뀌는 선택을 해석한다. **운영 포인트**는 공급자가 증명하지 않은 부분을 별도의 테스트로 남긴다. 특히 프리뷰, 베타, 일반 제공, 특정 국가·구독 등급은 서로 다른 상태다. 숫자에는 측정 대상과 데이터셋을 붙이고, 공급자 내부 평가의 성과를 모든 조직의 성능 보장으로 바꾸지 않는다.

## 1. Gemini 4 Carbon: 제한된 보안 배포에서 일반 개발 경로로

Google은 2주 전 사이버 보안 방어자에게 Fairwind 프로그램으로 먼저 제공했던 Gemini 4 Carbon의 이용 범위를 넓혔다. 유료 Gemini API·AI Studio·Android Studio의 개발자 경로, 기업용 Gemini 경로, Google AI Ultra 구독자의 Antigravity·Gemini 앱·검색 AI Mode를 나눠 안내한다. 제품마다 제공 시점과 권한이 같지 않으며 소비자 채널은 순차 배포다. Google은 Carbon을 대다수 코딩·지식 업무에 적합하다고 보는 Argon보다 더 깊은 추론, 복잡한 다단계 코딩, 열린 과학 탐색에 배치한다. 즉 “신형이니 모든 호출을 교체”하라는 제품 설명이 아니다. [Google 모델 발표](https://blog.google/innovation-and-ai/models-and-research/gemini-models/gemini-4-carbon-now-available/) · [개발자 발표](https://blog.google/innovation-and-ai/technology/developers-tools/gemini-4-carbon-developers/)

가격 설명에는 특히 주의가 필요하다. Google은 발표 시점의 **도입 가격**을 입력 100만 토큰당 2달러, 출력 100만 토큰당 10달러라고 적으며 Argon과 같다고 설명한다. 같은 가격표여도 Carbon이 더 많은 토큰을 사용해 탐색과 검증을 이어 간다면 최종 과제 비용은 늘 수 있다. 모델 선택에서 `단가 × 실제 토큰 수`와 도구 호출·재시도·대기 시간까지 합친 **완료 과제당 비용**을 분리해야 한다. 복잡한 결함 조사에서 한 번에 성공해 재작업이 줄어들면 비싼 모델이 전체로는 경제적일 수도 있고, 간단한 분류에서는 반대일 수 있다. 발표의 가격은 영구 계약가격이 아니라 공개 시점의 소개 가격이므로 배포 전 공식 가격표를 다시 확인해야 한다.

Google은 CursorBench 4.0, Perplexity WANDR, Zapier AutomationBench에서의 선두 성적과 외부 경쟁 모델 대비 과제당 비용 우위를 주장한다. MKA에서는 품질 2위와 선두 모델 대비 평균 6배 낮은 과제 비용을 적는다. 이는 서로 다른 평가의 결과이므로 한 숫자로 합산하거나 “모든 코딩 과제에서 6배 저렴”이라고 표현하면 안 된다. 내부 프로젝트의 빌드 시스템, 한국어 요구사항, 사내 문서의 형식, 접근 권한에 따라 결과는 크게 달라질 수 있다. 연구·보안 성과도 Google 또는 발표에 포함된 초기 파트너의 환경에서 얻은 내용이다.

보안 부분에서는 강력한 방어 능력과 오용 방지의 긴장이 드러난다. Google은 내부 프로젝트의 스캔 재현율 100%, 분류 정밀도 95%를 보고하고, 별도 모의 공격 환경의 차단률 99%, 공격 시도당 성공률 0.8% 등을 적었다. **각 수치의 분모와 시험 환경은 서로 다르다.** 또한 Gray Swan의 간접 프롬프트 주입 평가에서 성공률 0%를 제시하면서도 복잡한 공격 분포에서는 추가 개선이 필요하다고 인정한다. 실무적으로는 보안 모델을 코드 분석·패치 초안의 보조자로 삼되, 실제 취약점 재현·영향 평가·공개 절차를 별도 통제해야 한다. 공격을 잘 찾는 모델이라도 도구 권한을 넓게 주면 침해면이 커질 수 있다.

### 개발자에게 의미

- 모델을 **업무 단계별로 라우팅**할 이유가 커졌다. 설계 검토와 복잡한 버그 추적에는 Carbon, 짧은 변환·정형 응답에는 더 가벼운 선택지를 비교할 수 있다.
- “코딩 능력”은 최종 코드의 정확도만이 아니다. 실패한 빌드에서 복구하고 화면을 확인하는 반복 과정, 기존 테스트의 의미를 보존하는지까지 봐야 한다.
- 모델 교체 실험은 같은 프롬프트 한 번으로 끝나지 않는다. 작업 난도와 리포지터리 규모별로 성공률·도구 호출 수·토큰·p95 완료시간을 측정한다.
- 보안 검토 모델의 증거를 문서화해야 한다. 발견한 취약점의 재현 단계, 패치가 막는 원인, 새 회귀가 없는지 사람이 확인할 수 있어야 한다.

### 운영 포인트

**프로덕션 전 측정 계약**을 먼저 만든다. 동일한 과제 묶음에서 모델별 완료율, 잘못된 변경률, 사용자 수정을 요구한 비율, 과제당 지출을 기록한다. 코드 수정형 에이전트는 통과 테스트 수뿐 아니라 불필요한 파일 변경과 권한을 넘는 명령 실행 여부를 기록한다. 의료·금융·인사처럼 오류 비용이 높은 업무는 평균 점수 대신 치명 오류의 상한을 정의한다. Carbon의 출시가 조직의 검증을 대신하지 않는다.

## 2. GitHub Copilot의 Gemini 4 Carbon: 같은 이름, 다른 계약과 정책

GitHub는 Gemini 4 Carbon을 Copilot Pro+, Max, Business, Enterprise 사용자에게 일반 제공한다고 발표했다. 선택 가능한 표면에는 Visual Studio Code·Visual Studio·Copilot CLI·GitHub Copilot coding agent·웹·모바일·JetBrains·Xcode·Eclipse가 포함된다. 실제 노출은 점진 배포라서 같은 요금제 사용자에게 동시에 보이지 않을 수 있다. GitHub는 Carbon 사용을 **사용량 기반 과금에서 공급자 정가**로 청구한다고 적고, 구체 요율은 별도 모델·가격 문서를 확인하도록 안내한다. Google AI Studio에서의 API 가격과 Copilot 청구서의 금액이 자동으로 동일하다고 추정해서는 안 된다. [GitHub 변경 공지](https://github.blog/changelog/2026-11-10-gemini-4-carbon-in-github-copilot)

조직 관리자에게 중요한 문장은 모델 정책이다. GitHub의 설명에 따르면 Business·Enterprise에서 새 모델은 **기본 모델 활성화 설정**을 따르며, 관리자가 전역 기본을 끄거나 개별 모델을 명시적으로 비활성화하지 않았다면 자동 활성화된다. 어제의 다른 모델 공지에서 기본 비활성화 정책을 보았다고 오늘도 같다고 가정하면 안 된다. 모델별로 현재 설정, 적용되는 조직·엔터프라이즈 계층, 사용자에게 보이는 선택지를 확인해야 한다. 배포가 점진적이므로 “정책은 활성인데 선택기에 없다”는 상태도 일시적으로 발생할 수 있다.

코딩 에이전트에 제공되는 모델은 단순 채팅보다 더 많은 코드와 메타데이터를 다룰 수 있다. 관리자는 어느 저장소를 에이전트가 읽고 쓸 수 있는지, 어떤 브랜치 보호가 있는지, 의존성 취약점과 비밀값 검사가 PR에 적용되는지 확인해야 한다. 새 모델이 강한 보안 코딩을 목표로 한다는 설명은 자동으로 안전한 PR을 뜻하지 않는다. 모범 사용은 특정 모델을 전 직원에게 즉시 열어 보는 것보다, 대표 프로젝트에서 변경의 정확도와 비용을 보고 범위를 넓히는 것이다.

### 개발자에게 의미

- **동일 과제를 API와 Copilot에서 별도 벤치마크**한다. 도구, 컨텍스트 압축, 저장소 인덱싱, 사용자 개입 방식이 다르다.
- IDE에서 성공한 프롬프트가 CLI나 coding agent에서 동일하게 성공하는지 확인한다. 자동 수정과 단순 제안의 실패 비용은 다르다.
- 조직 정책의 “자동 활성화”가 의도에 맞는지 정리한다. 신규 모델 출시가 곧 새로운 처리 경로 도입이 될 수 있다.
- 청구 보고서에서 모델별 호출량과 완료 작업을 연결한다. 사용자당 정액으로만 보고 예산을 잡으면 사용량 기반 비용을 놓칠 수 있다.

## 3. MKA: 문서 이해·도구 사용·결과물 제작을 하나의 과제로 측정

Google과 Artificial Analysis가 공개한 Multimodal Knowledge Agent(MKA)는 텍스트 문제를 잘 푸는지보다 **시각적으로 복잡한 업무 자료를 읽고 결과물을 만드는지**를 겨냥한다. 발표에 따르면 10개 분야와 83개 직업의 전문가가 200개 평가 과제를 만들었으며, 각 과제는 숙련된 전문가가 3~8시간 걸릴 만한 다단계 작업을 모델에 맡긴다. 입력은 도면, 도표, 이미지, 스프레드시트 등으로 이루어지고, 출력은 보고서·덱·시트 같은 실제 산출물이다. 평가표는 과제당 대략 70개의 예/아니요 조건으로 구성되며, 사실 정확도 75%, 시각 설계 25%로 가중한다. [Google 평가 소개](https://blog.google/innovation-and-ai/models-and-research/gemini-models/multimodal-knowledge-agent-benchmark/) · [공개 과제](https://huggingface.co/datasets/google/multimodal-knowledge-agent)

이 설계의 장점은 “정답 문장” 하나로 측정하기 어려운 실무를 다루는 데 있다. 예를 들어 HR 대시보드용 보고서를 만든다면 원본 문서의 수치를 맞히는 것뿐 아니라 표의 관계, 설명의 빠짐, 레이아웃의 읽기 쉬움이 모두 중요하다. 하지만 평가의 각 항목이 어떤 사용자에게 얼마나 중요한지는 조직마다 다르다. 법무·의료에서는 사실 오류 한 건이 시각 완성도보다 훨씬 더 큰 위험일 수 있고, 홍보 자료에서는 시각적 전달력이 다른 무게를 가진다. MKA의 75:25를 자사 평가 정책의 정답으로 받아들이지 말고 **평가 축을 분리하는 사례**로 읽어야 한다.

평가 환경 통제도 눈여겨볼 점이다. 모든 모델에 같은 오픈소스 에이전트 하네스 Stirrup, 같은 도구·샌드박스·턴 예산을 사용한다. 채점 에이전트는 Google이 아닌 모델을 기반으로 파일을 열고 페이지를 렌더링하며 시트 수식 등을 확인한다고 설명한다. 전문가 평가와 자동 채점의 일치율은 96%라고 보고한다. 그래도 일치율은 채점자가 모두 옳다는 뜻이 아니고, 전문가와 자동 채점이 같은 빈틈을 놓칠 수도 있다. 200개 본 평가는 비공개로 유지해 학습 데이터 유입 가능성을 줄이고, 형식 검토용 10개는 공개했다. 비공개 평가의 장점은 오염 방지지만 제3자가 모든 문항을 직접 재현하기 어렵다는 한계도 있다.

Google은 Carbon이 품질 2위이면서 최고 품질 모델 대비 평균 과제 비용이 6배 낮다고 말한다. 이 비교는 **MKA 평가에서 테스트된 모델과 비용 계산법**에 한정된다. 모델 한 번의 토큰 요금만이 아니라 30~130회에 이르는 평균 턴 수 차이까지 비용에 영향을 줄 수 있다. 한 과제가 성공하기까지 얼마나 많은 도구 호출과 수정을 반복하는가가 멀티모달 에이전트의 진짜 경제성을 바꾼다.

### 사내 평가로 옮길 때

1. 기존 문서·표·이미지 중 개인정보를 제거한 실제 과제를 뽑는다. 텍스트로만 복사해도 풀 수 있는 문제라면 멀티모달 능력 검증이 아니다.
2. 사실 정확도와 표현·디자인을 **별도 점수**로 보관한다. 한쪽이 다른 쪽의 실패를 가리지 않게 한다.
3. 수식, 합계, 날짜, 출처 링크는 기계적으로 확인할 수 있는 기준을 우선 작성한다. 평가 모델의 인상평만으로 승인하지 않는다.
4. 작업 전체의 턴 수·실행 시간·도구 실패·재시도·총비용을 기록한다. 최종 출력만 저장하면 개선 원인을 알 수 없다.
5. 동일 문서를 다른 레이아웃, 잘린 이미지, 스캔 품질 저하, 표 머리글 변형으로 바꿔 견고성을 본다.
6. 업무 담당자에게 “쓸 수 있는가”와 “무슨 부분을 고쳐야 하는가”를 별도로 묻는다. 점수의 평균보다 수정 비용이 더 실용적일 수 있다.

## 4. Businesses in ChatGPT: 발견·정보 공급·기업 대화의 경계를 새로 그리다

OpenAI는 Businesses in ChatGPT 베타와 Business Hub를 발표했다. 적격 기업은 ChatGPT에서 조직을 **인증(claim)**하고 이름·정보를 관리하며 가격과 재고가 포함된 상품 피드를 제공할 수 있다고 한다. Hub는 기업 언급, 웹사이트 클릭, 인용된 사이트와 관련한 발견 주제 등 집계된 인사이트를 보여 준다. OpenAI는 개인별 대화나 Business Agent 채팅 내용을 기업에 공유하지 않으며, 충분한 상호작용이 있는 경우에만 집계 인사이트를 제공한다고 설명한다. 다만 구체적인 집계 임계값은 이 발표에서 명시하지 않는다. [OpenAI 발표](https://openai.com/index/introducing-businesses-chatgpt/)

Business Agent는 일반 ChatGPT 답변과 분리된 대화다. 사용자가 모델 답변에서 기업 프로필을 보고 자발적으로 별도 에이전트를 열어 상품·서비스를 문의하는 구조다. 기업이 스폰서한 Business Agent를 광고의 목적지로 연결할 수 있지만, 스폰서 위치는 라벨을 붙여 일반 답변과 분리한다고 OpenAI는 설명한다. 이 구분은 중요하다. 기업이 제공한 상품 정보, ChatGPT의 독립적 추천, 유료 노출, 기업과 직접 나누는 상담은 서로 다른 신뢰 수준과 이해관계를 가진다. 화면에서 이 경계를 희미하게 만들면 사용자는 누가 말하는지 알기 어렵다.

현 시점 Business Agent의 가용 범위는 **미국의 자격 있는 전자상거래·온라인 서비스 기업**이다. Business Hub에서 조직을 등록할 수 있는 지역의 범위와 Business Agent를 실제로 운영할 수 있는 범위가 같지 않다. Shopify 판매자의 연동 경로는 별도로 제시되지만 Shopify를 쓰는 모든 상점에 동일한 기능이 즉시 열린다는 뜻은 아니다. 한국 기업의 고객지원 채널로 바로 채택 가능한지 여부는 지역·업종 적격성 정책을 확인해야 한다.

기업 정보 운영 측면에서는 상품 피드의 **진실원천(source of truth)** 문제가 생긴다. 가격·재고·정책이 자사 웹사이트, 피드, 상담원 답변, 결제 화면에서 어긋나면 자연어 에이전트의 유창함이 오히려 분쟁을 키운다. 지원시간, 반품 조건, 배송가능 지역, 채용공고의 유효일 같은 변동 자료에 만료 시간과 갱신 책임자를 정해야 한다. Business Agent가 답을 모를 때 임의 약속을 하지 않고 공식 주문·상담 경로로 넘기는 규칙도 필요하다.

### 제품·운영팀 체크포인트

- **표시 출처:** 독립 ChatGPT 응답, 기업 제공 정보, 스폰서 노출, 기업 에이전트 대화를 사용자가 구분할 수 있는지 확인한다.
- **갱신 주기:** 가격·재고·약관·지원 정책이 바뀌면 피드가 언제 갱신되고 기존 답변의 잘못된 정보를 어떻게 발견할지 정한다.
- **권한·인증:** 누가 조직을 claim하고 상품 피드를 올릴 수 있는지 승인·회수 절차를 둔다.
- **대화 한계:** 거래나 결제 단계에 이르는지, 개인 정보가 언제 기업에게 전달되는지 실제 제품 흐름과 정책을 검토한다.
- **성과 해석:** 기업 언급이나 클릭의 증가는 매출·만족도 향상을 곧바로 증명하지 않는다. 중복·계절성·광고효과를 분리한다.

## 5. AgentCore Evaluations: 좋은 답변과 완료된 업무는 다른 지표다

AWS는 에이전트 평가를 “어떤 평가기 이름을 쓸까”에서 시작하지 말고 **업무 성공 → 관찰 가능한 행동 → 적절한 평가 수준**의 순서로 설계하라고 제안한다. 고객지원 에이전트는 친절한 응답을 했는가보다 실제 요청이 해결됐는지, 개인정보를 내보내지 않았는지, 잘못된 도구를 부르지 않았는지가 중요하다. 연구 에이전트는 문장이 그럴듯한지보다 근거가 완전하고 출처와 일치하는지가 중요하다. 하나의 총점은 성능 향상과 안전성 악화를 상쇄해 버릴 수 있다. [AWS 평가 플레이북](https://aws.amazon.com/blogs/machine-learning/the-agent-evaluation-playbook-built-in-deepeval-and-autoeval-on-agentcore/)

AgentCore의 기본 평가기에는 응답 정확성·충실성·관련성·지시 준수, 세션 전체의 목표 성공률, 도구 선택·매개변수 정확성, 스킬 선택·지시 준수, 유해성·고정관념, 기대한 도구 경로와 실제 경로의 비교 등이 있다. DeepEval의 관리형 평가기는 다중 턴 대화의 완결성·지식 유지·PII 누출 같은 축을 포함한다. AutoEval에는 악성 출력 또는 과도한 불가능 판단 등 별도 신호가 있다. 이 목록은 “전부 켜야 한다”는 체크리스트가 아니다. 에이전트가 어떤 행동을 해서는 안 되는지와 업무 실패 비용을 먼저 적은 뒤 필요한 평가를 골라야 한다.

특히 **trace 단위와 session 단위**를 나눌 필요가 있다. 도구 매개변수가 한 번 틀리면 한 trace에서 포착할 수 있지만, 사용자의 3턴 전 요구를 잊거나 전체 환불 절차를 끝내지 못한 경우는 대화 전체를 봐야 한다. 반대로 세션 목표가 달성됐더라도 중간에 허가되지 않은 DB 조회를 했다면 결과만으로는 합격시킬 수 없다. 따라서 결과 평가와 경로 평가를 함께 둬야 한다. 기계적 사실 검증이 가능한 부분은 LLM 판정기에만 맡기지 말고 규칙·로그·테스트로 보조한다.

AWS는 한 호출에서 여러 축을 별도 점수로 내는 다차원 평가기도 설명한다. 예를 들어 “정확성 5점, 규정 준수 2점, 말투 5점”을 하나의 4점으로 평균 내면 규정 실패를 가릴 수 있다. 차원별 점수를 유지하면 배포 게이트를 독립적으로 걸 수 있다. 고객지원 에이전트의 문체 개선이 개인정보 노출률 증가를 상쇄하지 못하도록 하는 것이다. 평가 점수의 정의, 입력 필요 조건, 판정 프롬프트를 버전 관리하고, 같은 사례에 사람이 붙인 라벨과 평가기의 결과를 정기적으로 비교해야 한다.

### 개발자에게 의미

- 평가를 단일 “답변 품질” 지표로 만들지 않는다. **목표 달성·근거·도구 경로·금지 행동**을 별도 열로 둔다.
- 모델 교체 전후에 동일한 회귀 사례를 사용한다. 잘 되는 사례만 추가해 평균을 높이지 않는다.
- 긴 대화의 앞부분 요구를 마지막 응답이 보존했는지 확인한다. 마지막 한 턴만 평가하면 중간 누락을 놓친다.
- 스킬·도구를 쓰는 에이전트는 최종 답변뿐 아니라 선택한 도구와 인자를 평가한다.

### 운영 포인트

평가기로 얻은 점수는 모니터링 시작점이지 책임의 이전이 아니다. 금전·인사·의료 관련 행동에는 사람이 승인해야 할 선을 정한다. 평가 데이터에 실제 고객 대화를 넣을 때는 개인정보 처리·보관·접근권한을 먼저 정해야 한다. 무엇보다 **실패 사례의 원문과 재현 조건**을 남기고, 모델·도구·프롬프트·지식베이스가 바뀔 때 같은 사례를 다시 실행해야 한다.

## 6. AgentCore Web Search 예제: 검색 결과를 인용으로 바꾸는 데 필요한 코드

AWS가 공개한 의존성 감시 예제는 npm, PyPI, 컨테이너 기본 이미지에 관한 새 소식을 매일 찾아 보안팀에 보고한다. 모델은 검색어와 요약을 만들지만, 코드가 검색 기간, 차단 도메인, 분기당 최대 4회 검색, 결과 검증을 고정한다. 세 분기를 병렬 실행하므로 한 번의 실행에서 최대 12번 검색하며, AWS의 예제 시험에서는 세 분기가 36초에 끝나 순차 실행 99초보다 빨랐다고 보고한다. 이 시간은 해당 예제 환경의 측정이며 모든 네트워크·계정에서의 성능 보장이 아니다. [AWS 예제](https://aws.amazon.com/blogs/machine-learning/build-a-daily-dependency-watcher-with-langgraph-and-amazon-bedrock-agentcore-web-search/)

중요한 차이는 **검색 결과가 모델에게 보이는 문장인 동시에 애플리케이션이 검증할 수 있는 구조화된 자료**로 돌아온다는 점이다. 예제는 보고 항목의 URL이 실제 그 분기 검색 결과에 있었는지, 패키지명이 제목이나 본문에 나타나는지, CVE나 권고문 ID가 원문에 있는지, 발표일이 감시 기간 안에 있는지 확인한다. 발표일이 없으면 기간 밖으로 취급한다. 이는 “모델이 URL을 쓰면 출처가 있다”는 낙관적 규칙보다 훨씬 좁고 안전하다. 다만 URL 일치와 문자열 포함은 그 취약점이 실제 우리 서비스에 영향을 준다는 증명까지 해주지는 않는다. 버전 범위, 적용 여부, 패치 가능성은 추가 확인이 필요하다.

AWS는 AgentCore Web Search가 AWS 자격 증명으로 서명된 요청을 받고 AWS가 운영하는 웹 인덱스에서 결과를 제공한다고 설명한다. 외부 검색 API 키를 별도로 저장하지 않고, IAM으로 호출을 통제할 수 있다는 운영상 이점이 있다. 도메인 허용·제외, 발표일 범위를 지정할 수 있고, Gateway를 거쳐 여러 에이전트에 같은 소스 정책을 적용하는 경로도 소개한다. 그러나 이것이 공개 웹의 모든 발표를 빠짐없이 찾는다는 뜻은 아니다. 공식 보안 권고의 누락을 줄이려면 패키지 공급자의 RSS·보안 공지·OSV·GitHub Advisory 등 별도 경로를 함께 두어야 한다.

이 예제에서 일반화할 수 있는 원리는 **모델에게 줄 수 없는 권한을 프롬프트가 아닌 코드에서 차단**하는 것이다. “최근 한 달 소식만 찾아”라는 지시문은 모델이 지키지 않을 수 있고, 악의적 웹페이지 내용이 검색 범위를 바꾸라고 지시할 수도 있다. 반면 `published_after`, 도메인 정책, `max_searches`를 실행 도구가 강제하면 모델의 자의적 확대가 어렵다. 반환된 결과는 다시 코드에서 검사하고, 이미 보낸 항목은 저장소와 대조해 중복 보고를 막는다. 시간·비용·노이즈를 함께 관리하는 설계다.

### 인사시스템·일반 웹앱에 응용한다면

- 의존성 목록을 **실제 배포 이미지와 lockfile**에서 만들고, 개발용 패키지와 운영 노출을 구분한다.
- 취약점 공지의 URL·ID·게시일 외에 영향받는 버전 범위를 파싱한다. 우리 버전이 해당하지 않으면 경보를 낮춘다.
- 업데이트가 가능한지, 변경이 필요한 코드가 있는지, 안전한 대체 버전이 있는지 담당자가 승인하게 한다.
- 긴급 권고를 매일 한 번만 보지 말고 중요도에 따라 별도 알림 경로를 둔다.
- AI 검색 결과에 없는 사실은 추정으로 메우지 않는다. 공식 원문에 접근하지 못하면 “확인 불가”로 남긴다.

## 7. Bedrock의 Kimi K3.1 Pro Highspeed: 모델 선택보다 추론 경계가 먼저다

AWS는 Moonshot AI의 Kimi K3.1 Pro Highspeed를 Amazon Bedrock에서 쓸 수 있다고 소개했다. 원문에 따르면 Kimi K3의 3조 파라미터급 오픈 가중치 아키텍처와 100만 토큰 문맥을 기반으로 후속 학습을 강화했으며, Moonshot AI는 일반 Pro 대비 출력 속도가 2~3배라고 보고한다. Bedrock 경로에서는 도구 호출, 구조화 출력, 이미지 입력, 스트리밍, 추론 정도 조절을 지원한다. 이미 Kimi K3를 쓰는 개발자는 모델 ID 변경으로 시험할 수 있다고 AWS는 안내하지만, **교체가 곧 동작 동등성**을 뜻하지 않는다. 프롬프트, 스키마, 오류 처리, 토큰 사용은 회귀 시험해야 한다. [AWS 발표](https://aws.amazon.com/blogs/machine-learning/introducing-kimi-k3-1-pro-on-amazon-bedrock/)

지역 프로필은 기술적 편의와 규제 조건을 함께 결정한다. `global.moonshotai.kimi-k3.1`은 지원 상용 AWS 리전으로 라우팅하며 AWS는 대체로 더 낮은 토큰 단가를 설명한다. 미국 내 처리 경계가 필요하면 `us.moonshotai.kimi-k3.1`, 인도 내 처리가 필요하면 `in.moonshotai.kimi-k3.1`을 선택할 수 있다. 글로벌 경로가 더 싸다고 민감 데이터 업무에도 자동 적용하면 데이터 레지던시 요건을 위반할 수 있다. 반대로 지역을 고정해도 **애플리케이션의 로그·백업·모니터링 데이터**가 같은 경계 안에 있는지는 별도로 확인해야 한다.

AWS는 데이터가 AWS 경계에서 처리되고 Moonshot AI와 공유되지 않으며 모델 훈련에 사용되지 않는다고 설명한다. 추론 요청에 대해 zero data retention과 운영자 접근 제한도 언급한다. 이는 공급자가 공지한 Bedrock의 처리 정책이다. 우리 조직의 앱 로그, API Gateway 요청 로그, 에러 추적 시스템, 사용자가 저장한 대화, 캐시에는 별도의 보존 정책이 적용될 수 있다. “모델 제공자가 보관하지 않는다”와 “서비스 어디에도 정보가 남지 않는다”는 다른 문장이다.

비용과 지연을 다루는 옵션도 있다. Flex는 Standard의 절반 가격을 제시하지만 응답이 더 늦을 수 있다. 평가·요약·백그라운드 작업은 후보지만 실시간 사용자 응답은 지연 목표와 비교해야 한다. 명시적 프롬프트 캐싱은 반복되는 시스템 지시와 문서 앞부분을 재활용한다. AWS의 설명에 따르면 캐시 중단점 앞에는 최소 256토큰의 안정된 콘텐츠가 필요하고, 읽기·쓰기의 단가가 다르며, 캐시 콘텐츠는 최소 30분 유지된다. 캐시가 자주 적중하는지, 초기에 쓰는 비용이 절감분보다 작은지, 문서 변경 시 낡은 내용이 재사용되지 않는지를 측정해야 한다.

### 개발자에게 의미

- 긴 컨텍스트 창을 **전부 채우는 기본값**으로 쓰지 않는다. 필요한 근거를 선별해 보내는 검색·요약 설계와 비교한다.
- `reasoning_effort`를 과제 난도별로 조정한다. AWS는 값을 설정하지 않으면 최대 수준을 쓴다고 설명하므로 단순 업무에서 지연·출력 토큰이 불필요하게 커질 수 있다.
- 모델 ID·리전 프로필·서비스 티어를 배포 설정에 고정하고 로그에 남긴다. 코드가 같아도 프로필이 바뀌면 비용·경계가 달라진다.
- 유효한 구조화 출력이라도 업무상 틀릴 수 있다. 스키마 검증 후 원자료와 도메인 규칙을 다시 대조한다.

## 8. Gemini for healthcare: 통합된 맥락이 곧 자율 의료 결정은 아니다

Google Cloud는 의료기관의 전자 건강기록, 청구, 임상 지침, 공공 보험 데이터 등 분절된 자료를 연결하는 **Gemini for healthcare**를 프리뷰로 발표했다. 기록 종합과 사전 승인(prior authorization) 검토처럼 여러 시스템을 가로지르는 작업을 지원하며, HCA Healthcare, Highmark Health, Northwell Health를 초기 파트너로 언급한다. 발표는 정의된 보호 장치와 적절한 인간 감독 아래에서 업무를 수행한다고 설명한다. 프리뷰와 초기 파트너의 사례를 모든 병원에 즉시 사용 가능한 의료 자동화로 확대해서는 안 된다. [Google 공식 요약](https://blog.google/innovation-and-ai/infrastructure-and-cloud/google-cloud/gemini-for-healthcare/) · [Google Cloud 상세 소개](https://cloud.google.com/blog/products/ai-machine-learning/gemini-for-healthcare)

의료 데이터에서 어려운 점은 자료의 수집보다 **시점과 권한의 충돌**이다. 오래된 약물 목록, 서로 다른 기관의 진단 코드, 환자의 동의 범위를 벗어난 기록, 바뀐 보험 규칙이 동시에 있을 수 있다. 에이전트가 여러 시스템의 정보를 연결해도 어느 기록을 우선해야 할지, 누가 최종 판단하는지 명시하지 않으면 자동화의 속도가 위험을 키울 수 있다. 기술적으로는 원본 기록의 식별자·시각·작성자·변경 이력과 함께 요약 근거를 표시해야 한다. 데이터 결손은 추정이 아니라 미확인으로 보여야 한다.

Google이 인용한 “임상의가 주당 약 28시간을 행정업무에 쓴다”는 수치는 2024년 Google Cloud·Harris Poll 자료를 연결한 설명이다. 이 숫자가 새 제품의 절감 시간을 뜻하지 않는다. 제품이 어느 유형의 행정 시간을 얼마나 줄였는지는 별도 임상·운영 평가가 필요하다. 사전 승인 업무에서 처리 속도는 중요하지만 잘못 승인·거절한 건의 비용, 사람의 검토 부담, 환자 통보의 정확도도 함께 측정해야 한다.

### 운영 포인트

의료 업무의 에이전트는 일반 사무 보조와 다른 출시 조건이 필요하다. 원본 데이터 접근을 최소 권한으로 제한하고, 식별 가능한 환자 정보의 학습·평가 반입을 통제한다. 모델이 제안한 결정, 사람이 수정한 내용, 최종 결정을 각각 기록해 사후감사를 가능하게 한다. 사용자가 “AI가 판단했다”고 오해하지 않도록 역할을 명확히 표시한다. 인사시스템도 건강정보·급여·징계처럼 민감한 데이터가 섞이면 비슷한 설계 원칙이 적용된다. 다만 의료 규제 요건을 그대로 HR 시스템에 적용한다는 뜻은 아니다.

## 9. Hugging Face Decision Models: 생성하지 않아도 되는 답을 생성하지 않기

Hugging Face는 `pipeline("decision")`을 통해 **상태(state) + 질문 + 허용된 답 → 결정 + 확률**의 인터페이스를 설명했다. 예를 들어 고객의 “이중 결제 환불” 문의를 Billing·Technical·Sales 중 어디로 보낼지 선택하고 각 가능성의 분포를 함께 반환한다. 문장 생성 모델에게 JSON을 써 달라고 요구하는 방식과 달리, 애플리케이션이 이미 알고 있는 선택지에 확률을 부여하는 것이다. 발표는 선택(choice), 순서가 있는 점수(score), 예/아니요 확률(noul)이라는 세 기본 유형을 소개한다. [Hugging Face 기술 글](https://huggingface.co/blog/decision)

이는 전통적 분류기와도 다르다. 일반 분류기의 라벨 집합은 보통 학습 시 모델 헤드에 고정된다. 제로샷 분류는 추론 시 후보 라벨을 바꿀 수 있지만, 여러 종류의 질문을 하나의 일관된 요청으로 다루는 데는 추가 조합이 필요하다. Decision Model은 런타임에 후보를 지정하고 질문의 유형에 맞게 결과 분포를 돌려주는 인터페이스에 초점을 맞춘다. 다만 이 설계가 모든 분류기보다 정확하거나 빠르다는 보장은 별도의 비교가 필요하다. 예시의 0.997 같은 확률도 “실제 정답일 확률이 99.7%”라고 곧바로 해석하면 안 된다. 모델의 출력 분포는 업무 데이터에서 **캘리브레이션**을 검증해야 한다.

실무적으로는 라우팅·우선순위·정책 분기처럼 선택지가 분명한 곳에 적합한 실험이다. 지원 티켓을 어느 팀으로 넘길지, HR 문의를 휴가·급여·채용으로 나눌지, 긴급성을 낮음·보통·높음으로 정할지 같은 문제다. 반면 규정 해석, 사용자 상황 설명, 예외 판단처럼 자유로운 이유 제시가 필요한 곳에는 결정 하나만으로 충분하지 않다. 안전한 설계는 결정 모델로 좁은 분기를 제안하고, 임계값 아래이거나 후보가 엇비슷하면 사람 또는 추가 질문으로 넘기는 것이다.

### 파일럿 측정 항목

1. 실제 업무의 라벨 분포를 기록한다. 흔한 범주만 높은 정확도를 내고 드문 중대 사건을 놓치지 않는지 살핀다.
2. 확률을 구간별로 나눠 예측과 실제 정답 빈도를 비교한다. 출력 숫자를 신뢰도로 표시하려면 이 과정이 필요하다.
3. 잘못 라우팅했을 때의 복구 비용을 측정한다. 단순 재배정과 개인정보 부서 오발송은 손실이 다르다.
4. 새로운 업무 범주가 생길 때 후보 설명의 변경만으로 충분한지 검증한다. 동의어·한국어 표현·약어에 취약할 수 있다.
5. 기계가 즉시 처리할 임계값과 사람에게 보낼 구간을 운영 데이터로 정한다. 예시 한 건의 높은 확률로 임계값을 정하지 않는다.

## 10. Hugging Face Hub와 Google Cloud Marketplace: 구매 경로와 서비스 경로는 별개

Hugging Face는 조직 계정을 Google Cloud Marketplace의 청구 계정에 연결할 수 있다고 안내했다. Team·Enterprise 구독뿐 아니라 Jobs, Inference Endpoints, Inference Providers, GPU Spaces, 추가 저장공간 등의 사용료가 기존 클라우드 청구서에 나타난다. 기존 공급업체 등록과 회사 카드 발급의 병목을 줄일 수 있지만, 실제 서비스의 실행 위치나 데이터 이동 경로가 Google Cloud 내부로 자동 변경된다는 뜻은 아니다. **청구 통합과 인프라 통합은 다르다.** [Hugging Face 안내](https://huggingface.co/blog/hub-gcp-marketplace)

연동 절차에는 Marketplace 구독, 결제 계정 선택, Hugging Face 조직 연결, Hugging Face 측 승인 단계가 있다. 조직 관리자만 연결 대상 조직을 선택할 수 있다. 승인 대기 동안 기존 결제 수단이 있으면 그 수단으로 청구가 계속되며, 기존 카드 사용 조직은 다음 청구 기간부터 새 경로로 전환될 수 있다. 이 전환 시점은 예산과 회계 처리에 중요하다. 버튼을 눌렀다는 이유로 그날부터 모든 비용이 Cloud 청구서로 이동했다고 기록하면 한 달치 비용이 두 곳에 분산돼 보일 수 있다.

Hugging Face는 월 포함 크레딧을 먼저 적용한 뒤 종량 사용을 Google Cloud에 보고한다고 설명한다. 클라우드 마켓플레이스로 결제할 때 별도 크레딧을 추가하는 기능은 사용할 수 없다고도 적었다. 조직 연결·해제는 감사 로그에 기록된다. 개발팀에는 구매가 쉬워진 만큼 **누가 어느 조직에 GPU Jobs를 켤 수 있는지**가 더 중요해진다. 중앙 청구로 묶여도 프로젝트·팀·모델별 비용 귀속이 자동으로 해결되는 것은 아니다.

### 운영 체크리스트

- 연결할 Hugging Face 조직과 Google Cloud 프로젝트·청구 계정의 소유자를 문서화한다.
- 승인 대기, 전환 월, 첫 통합 청구서에서 기존 카드와 클라우드 청구를 함께 대조한다.
- 구독 포함 크레딧과 종량제 GPU·추론 사용량의 구분을 비용 리포트에 남긴다.
- Jobs·Endpoints·Spaces의 지역, 공개 범위, 데이터 접근권한을 별도로 검토한다.
- 조직 연결 해제 시 청구 수단과 서비스 중단 가능성을 사전에 확인한다.

## 11. Bedrock Tokenomics Data Lake: 관찰 가능성과 민감 데이터의 중앙집중

AWS는 여러 계정의 Bedrock 모델 호출 기록을 중앙 계정에 모아 Athena에서 질의하는 참조 아키텍처를 소개했다. 각 계정에서 Bedrock invocation logging을 CloudWatch Logs에 쓰고, 구독 필터가 중앙 계정으로 전달한다. Lambda가 압축된 배치를 풀고 무관한 메시지를 제거·필드 정리한 뒤, Firehose가 Parquet로 S3에 저장하며 Glue 테이블과 Athena가 이를 읽는다. CloudFormation 템플릿과 예제 코드를 제공하지만, 중앙 스택을 설치한 뒤 각 소스 계정 스택을 배포하고 **호출 로깅을 별도로 활성화**해야 한다고 명시한다. 스택 설치만으로 데이터가 수집되는 것은 아니다. [AWS 데이터 레이크 설명](https://aws.amazon.com/blogs/machine-learning/amazon-bedrock-tokenomics-data-lake/)

한 호출에 모델, 계정·시각·IAM 역할, 입력·출력 토큰, 중단 사유와 함께 **프롬프트 및 모델 응답**이 남을 수 있다는 것이 이 구조의 장점이자 핵심 위험이다. 중앙 계정에 모으면 팀별 비용, 비효율적인 긴 프롬프트, `max_tokens`로 잘린 답변, 모델 사용 분포를 찾기 쉽다. 동시에 이전에는 각 계정에 흩어져 있던 고객 질문·소스 코드·인사정보가 한 곳에 모일 수 있다. 비용 최적화라는 목적만으로 모든 원문을 무기한 저장할 필요는 없다. 메타데이터와 원문 저장을 분리하고, 원문 마스킹·암호화·보존기간·열람 감사를 정해야 한다.

비용 계산도 단순하지 않다. 토큰 수와 모델 ID로 추정 단가를 곱하면 대략적인 호출 비용을 얻을 수 있지만, 할인·캐시 읽기·서비스 티어·계약·지역·청구 시차를 반영하지 않으면 청구서와 다를 수 있다. AWS는 Cost and Usage Report와 연결해 지출을 분석하는 경로를 설명한다. 좋은 비용 대시보드는 “이번 달 토큰 1억”보다 **어떤 기능이, 어떤 결과를 얻기 위해, 얼마를 썼는가**를 답해야 한다. 사용량은 성공률과 함께 봐야 불필요한 비용을 찾을 수 있다.

### 운영 포인트

- 호출 원문을 남기는지, 해시·토큰·모델 메타데이터만 남기는지를 데이터 등급별로 정한다.
- 원문이 남는다면 민감 필드 마스킹과 중앙 계정 접근권한을 최소화한다.
- 각 계정의 로그 활성화 상태를 주기적으로 점검한다. 대시보드의 빈칸이 사용량 0인지 수집 장애인지 구분한다.
- 비용 추정치와 실제 청구서를 정기 대조한다. 캐시·Flex·지역 차이를 원인별로 기록한다.
- 에이전트의 실패율과 토큰 사용량을 함께 보아 “싼 실패 반복”과 “비싸지만 한 번에 성공”을 구분한다.

## 12. OpenAI·Upwork 연구: 일자리 수보다 업무 조합을 먼저 봐야 한다

OpenAI와 Upwork의 공동 연구는 프리랜서 공고와 ChatGPT 사용 활동을 비교해 AI가 무엇을 대체하고 어떤 결합 업무를 만드는지 살핀다. 공개 글에 따르면 분석한 63개 업무 범주 중 43개는 ChatGPT에서 많이 수행되는 활동이 Upwork 공고 점유율에서는 상대적으로 감소하는 방향을 보였다. 그러나 나머지 20개는 반대였다. 여기서 쓰는 지표는 **업무별 공고 비중**이다. 특정 업종의 절대 일자리 수, 개별 프리랜서의 소득, AI 사용의 인과 효과를 바로 말해 주지 않는다. [OpenAI 연구 요약](https://openai.com/index/ai-effect-on-freelance-work/)

연구는 AI 관련 공고의 업무 조합이 2023년 초에서 2025년 말 사이 약 45% 다양해졌다고 보고한다. 균등하게 흔한 업무 수로 환산하면 약 14.6개에서 21.2개로 넓어졌다는 설명이다. AI 관련 프로젝트는 시급 공고 금액이 유사한 반면 고정 금액 예산과 투입 시간이 더 커지는 패턴을 보였고, 연구진은 이것이 더 넓은 프로젝트 범위와 관련 있을 수 있다고 해석한다. 예를 들어 AI 생성 영상과 편집·모션 그래픽을 따로 발주하지 않고 하나의 완성물로 묶는 식이다. AI가 모든 일을 없앴다는 이야기보다 **요구되는 결과물의 단위가 바뀐다**는 해석이 자료에 더 가깝다.

인사시스템과 조직 설계에 주는 시사점은 직무명을 고정된 작업 묶음으로 보지 말라는 것이다. 채용공고에 “AI 활용 가능”을 적는 것과 실제로 필요한 작업을 정의하는 것은 다르다. 기획, 데이터 정리, 모델 도구 사용, 품질 검수, 개인정보 관리가 하나의 과제에 붙는다면 역할·교육·성과 측정도 달라져야 한다. 그러나 Upwork라는 플랫폼의 공고 데이터를 한국의 전 산업 고용 전망으로 옮기면 안 된다. 시장·언어·기간·고객 유형이 다르다.

### 제품팀의 질문

- 사용자가 직접 AI로 처리하는 부분과 전문가에게 맡기는 부분을 서비스 흐름에서 구분했는가?
- 자동화로 사라진 작업 시간이 품질 검수·통합·고객 소통 시간으로 이동했는지 측정했는가?
- ‘AI로 빠르게 제작’한 산출물의 수정·승인·유지보수 비용을 누가 부담하는가?
- 새로운 직무 요구가 생겼다면 교육과 평가 기준을 기존 직무명에 억지로 끼워 넣지 않았는가?

## 13. 교육의 ‘지도 격차’와 돌봄자의 AI 사용: 보급보다 사용 조건이 중요하다

OpenAI는 유럽·중동·아프리카의 교육 협력에서 학생이 AI를 이미 쓰는 속도와 교사가 사용법을 지도받는 속도 사이의 격차를 강조했다. 글이 인용한 ThinkYoung 조사에서는 조사 대상 학생의 79%가 숙제·과제에 AI를 사용했다고 응답한 반면, 사용법을 배웠다는 응답은 47%였다. 이는 특정 조사 대상과 질문에서 나온 수치이며 모든 나라의 학생에게 그대로 적용할 수 없다. OpenAI는 교사의 시간 절감과 도입률은 초기 신호이지만, 독립적 사고·지식 보유·학습 효과에 대한 지속적 평가가 필요하다고 적었다. [OpenAI 교육 글](https://openai.com/index/closing-ai-guidance-gap-education/)

같은 날 OpenAI는 미국 5개 도시에서 돌봄자와 지역사회 건강 관련 단체가 참여하는 AI Skills Jam을 소개했다. 일정과 체크리스트 정리, 신뢰할 수 있는 자료의 쉬운 말 설명, 지역 자원 탐색, 모임 토론 가이드 준비처럼 **일상 보조**를 예시로 든다. 동시에 개인정보 보호와 한계 이해를 가르치고, 의료·법률·재무 전문 조언을 대체하지 않도록 안내한다고 밝혔다. OpenAI 분석의 “미국에서 주당 4천만 건 넘는 의료 관련 ChatGPT 메시지가 다른 사람의 건강을 묻는다”는 수치는 공급자 자체 추정이다. 돌봄자 교육의 효과나 의료 결과 개선을 입증한 수치가 아니다. [OpenAI 돌봄자 글](https://openai.com/index/helping-caregivers-use-ai-in-everyday-life/)

이 두 소식은 **도구 접근과 안전한 사용 능력**이 다르다는 사실을 보여 준다. 사용자에게 AI 버튼을 제공했다고 해서 올바른 출처 선택, 개인정보 판단, 결과 검증, 전문인에게 넘길 시점을 배우는 것은 아니다. 학교에서는 과제별 AI 사용 허용 범위, 출처 표시, 자기 생각의 확인 방법이 필요하고, 돌봄자에게는 잘못된 의학 정보의 징후와 의료진에게 물어야 하는 경계가 필요하다. 제품이 다루는 지식의 위험도가 높아질수록 사용 지침은 도움말 뒤에 숨기는 문구보다 실제 작업 흐름의 일부가 되어야 한다.

인사시스템에도 유사한 문제가 있다. 직원이 급여·휴가·징계·건강정보를 AI에 물을 수 있지만, 답변이 현재 회사 규정과 국가별 법규를 반영하는지 확인해야 한다. 모델이 모르는 경우 사람 담당자에게 연결하는 경로, 조직 문서의 최종 수정일, 사용자가 제공한 개인 자료가 어디에 남는지의 설명이 필요하다. “AI 활용률”만 성과 지표로 삼으면 잘못된 사용이 늘어도 성공처럼 보일 수 있다.

## 오늘의 교차 분석 — 모델 출시 소식에서 시스템 설계로

### A. 동일 모델의 세 가격표를 혼동하지 말 것

Carbon은 Google API, Google 구독 제품, GitHub Copilot에서 각각 접점이 다르다. API의 입력·출력 토큰 도입 가격과 Copilot의 사용량 기반 모델 청구, 구독자의 제품 접근권은 서로 바꿔 계산할 수 없다. Bedrock의 Kimi K3.1도 Standard·Priority·Flex와 지역 추론 프로필, 캐시 쓰기·읽기에 따라 비용이 달라진다. 재무 계획에는 **모델 단가**, **완료 과제당 비용**, **사용자당 월간 지출**, **실패 후 재시도 비용**을 별도 열로 둬야 한다.

### B. 새 모델의 기본값은 보안 정책이 될 수 있다

GitHub Copilot은 신규 모델 자동 활성화 기본값이 적용될 수 있음을 명시한다. Google Carbon의 API 경로와 GitHub의 모델 선택기는 권한과 과금 방식이 다르다. AWS의 글로벌 추론 프로필은 지역을 달리할 수 있다. Hugging Face Marketplace 연결은 구매 권한을 바꾼다. 결국 “새 모델을 사용할 수 있다”는 변화는 **누가 어떤 데이터를 어디로 보낼 수 있는가**의 변화일 수 있다. 기능 출시 알림을 읽는 책임자와 조직 정책을 변경하는 책임자를 같은 사람으로 가정하면 누락이 생긴다.

### C. 평가는 정확성 하나보다 계약의 집합이다

MKA는 입력 파일의 시각 요소와 최종 결과물의 품질을 평가한다. AgentCore는 목표 달성, 도구 선택, 개인정보 노출, 긴 세션의 완결성을 나눠 본다. Decision Models는 확률을 반환하지만 그 확률의 캘리브레이션은 별도 문제다. 세 발표를 합치면 “모델이 잘한다”는 하나의 점수는 실무에서 거의 의미가 없다는 결론에 가깝다. 제품이 성공이라고 부를 조건, 실패했을 때의 복구 경로, 절대 해서는 안 되는 행동을 먼저 작성해야 한다.

### D. 출처 표시만으로 사실성은 완성되지 않는다

AWS의 의존성 감시 예제는 URL·패키지명·CVE·게시일의 일치 여부를 코드로 확인한다. OpenAI Business Hub는 기업이 제품 정보를 제공하지만 가격·재고 갱신을 운영해야 한다. 의료·교육 자료는 작성 시각과 전문가 검토가 특히 중요하다. 출처가 있는 문장도 오래됐거나, 잘못된 상품에 연결됐거나, 그 출처가 주장하지 않는 결론으로 확장됐을 수 있다. **인용의 존재**, **인용의 적합성**, **주장의 진실성**, **우리 업무에 대한 적용성**은 네 단계다.

### E. 로그가 많아질수록 데이터 보호 설계도 커진다

에이전트 평가에는 추적 정보가 필요하고, 토큰 비용 분석에는 호출 기록이 필요하다. 하지만 원문 프롬프트와 응답을 중앙 저장하면 관찰 가능성이 커지는 동시에 민감 데이터의 집적도 커진다. 사용 목적에 따라 원문 없이 충분한 지표가 있는지 구분한다. 원문이 필요한 사고조사에는 제한된 보관기간과 접근승인·감사 절차를 둔다. 특히 의료·인사·금융 정보에는 ‘나중에 분석할지도 몰라서 전부 저장’이 합리적인 기본값이 아니다.

## 개발자를 위한 실행 순서 — 이번 주에 할 수 있는 일

**1. 모델 인벤토리부터 갱신한다.** 사용 중인 서비스마다 공급자, 실제 호출 API, 모델 ID, 리전, 사용 등급, 조직 활성화 정책을 기록한다. Google Carbon의 API 호출과 Copilot 선택을 하나의 항목으로 합치지 않는다. 신규 모델은 가격표와 제공 지역을 별도 근거 링크로 붙인다.

**2. 대표 과제를 난도별로 분류한다.** 간단한 라우팅, 문서 요약, 코딩 수정, 시각 문서 제작, 장기 에이전트 실행은 서로 다른 측정 대상이다. 모든 유형에 같은 프롬프트·같은 모델을 적용해 평균을 내면 차이가 희석된다. 오류 비용이 높은 과제는 별도 표본을 둔다.

**3. 평가 계약을 작성한다.** 각 과제에서 기대하는 최종 결과, 필수 근거, 허용된 도구, 금지된 동작, 사람의 승인이 필요한 단계를 문장과 기계 검사로 나눈다. AgentCore의 평가기 이름은 이 계약 이후에 고른다. MKA처럼 시각 결과물이 필요한 과제는 정확성·디자인을 분리한다.

**4. 출처 검증을 코드에 넣는다.** 검색형 에이전트가 반환한 URL이 실제 검색 결과에 있었는지, 날짜가 범위 안인지, 특정 상품·패키지·정책을 원문이 실제로 다루는지 확인한다. 출처 없는 주장에는 자신감 높은 문장 대신 “확인되지 않음”을 출력하도록 한다.

**5. 비용을 완료 작업과 연결한다.** 모델별 토큰 수와 캐시, 서비스 티어, 도구 호출 수, 재시도를 모아 과제당 지출을 계산한다. Bedrock 호출 원문을 수집한다면 먼저 보존기간과 마스킹 정책을 정한다. 청구서와 추정치가 다를 수 있음을 대시보드에 표시한다.

**6. 한 번에 전면 전환하지 않는다.** 새 모델은 내부 대표 과제, 제한된 사용자, 관찰 가능한 성능·비용 목표, 명확한 롤백 기준으로 시작한다. 프리뷰 제품과 일반 제공 모델의 출시 게이트를 같게 보지 않는다. 담당자의 “사용 가능”과 법무·보안·운영의 “서비스에 적용 가능”은 다른 승인이다.

## 운영 포인트 — 발표의 빈칸을 제품팀 질문으로 바꾸기

| 영역 | 오늘 확인한 변화 | 출시 전 남은 질문 |
|---|---|---|
| 모델 | Carbon의 다중 채널 확대, Kimi K3.1의 Bedrock 제공 | 실제 작업 성공률과 완료 비용, 지역별 가용성은? |
| 권한 | Copilot 모델 정책, Business Hub 조직 인증 | 누가 활성화하고 누가 철회하며, 변경 이력은 어디에 남는가? |
| 평가 | MKA의 멀티모달 과제, AgentCore의 trace·session 평가 | 우리 업무의 치명 오류와 사람 검토 기준은 무엇인가? |
| 데이터 | 의료 시스템 연결, 호출 로그 중앙화 | 어떤 원문이 어느 계정에 얼마나 오래 저장되는가? |
| 검색 | AgentCore Web Search의 출처·날짜 정책 | 공식 원문 누락, 인용 불일치, 재발행 자료를 어떻게 처리하는가? |
| 조달 | Hugging Face의 Google Cloud 청구 연동 | 결제 전환일과 서비스·데이터 경계를 혼동하지 않았는가? |
| 사용자 | Business Agent, 교육·돌봄자 프로그램 | AI 답변, 기업 답변, 전문가 판단의 경계가 명확한가? |

**권장 배포 게이트:** 작은 기능이라도 `근거 있는 정확성`, `금지 행동 없음`, `권한 경계 준수`, `비용 상한`, `장애·오류 시 되돌리기`의 다섯 항목은 분리해서 확인한다. 하나의 평균 평가 점수가 다섯 조건을 대신할 수 없다. 서비스별로 허용 가능한 손실이 다르므로 임계값을 공급자 발표 수치에서 복사하지 않는다.
