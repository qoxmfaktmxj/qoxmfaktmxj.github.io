## 배경: ‘하나의 모델이 전부 한다’는 설계에서 벗어나는 이유

일반적인 AI 제품 요구사항은 겉으로는 하나의 대화로 보인다. 고객이 문제를 설명하면 서비스가 상황을 분류하고, 필요한 문서를 찾고, 행동을 결정하고, 실제 데이터를 바꾸고, 결과를 보여준다. 그러나 각 단계는 서로 다른 오류 비용을 갖는다. 문의 분류를 잘못하면 적절한 부서로 넘기는 데 시간이 걸린다. 승인 없이 예약을 바꾸면 계약과 결제에 직접 영향이 생긴다. 위성 변화 탐지에서 다른 계절의 영상을 비교하면 실제 토지 변화가 없어도 지도가 달라 보인다. 수요 예측의 평균값이 맞아도 상위 분위수가 지나치게 낮으면 재고 부족이 발생할 수 있다.

따라서 과제의 단위를 작게 정의해야 한다. `이 입력이 환불 정책에 해당할 확률은?` 같은 제한된 판단과 `고객 계정의 청구 기록을 수정해도 되는가?`라는 상태 변경은 같은 호출로 묶을 필요가 없다. 전자는 빠른 분류 API가 도움이 될 수 있다. 후자는 권한, 승인, 변경 전후의 DB 불변조건, 감사 기록이 먼저다. OlmoEarth의 임베딩 역시 그 자체가 ‘산불 피해’ 정답이 아니다. 공간·시간 특징을 재사용할 수 있게 만든 입력이며, 과제별 라벨과 검증이 필요하다. IBM의 앙상블 또한 특정 SKU의 수요 예측 정책을 완성하지 않는다. 기준 시점, 예측 구간, 결측값 처리와 신뢰구간 보정이 따로 필요하다.

이 분리는 제품 성능을 낮추는 관료적 절차가 아니다. 어디에서 실패했는지 분리할 수 있어야 실제로 빠르게 개선한다. 분류가 잘못됐는지, 도구가 잘못 호출됐는지, 도구는 맞았지만 DB 커밋이 실패했는지, 예측은 맞았으나 UI가 분위수를 잘못 표시했는지를 각각 재현할 수 있다. 관측 단위가 없다면 모델을 교체하거나 프롬프트를 늘리는 조치가 모든 문제의 만능 답처럼 보인다. 오늘의 발표들은 각자 다른 영역에서 **값을 만드는 단위와 값을 입증하는 단위를 맞추는 방향**을 보인다.

## 1. Decisions API — 생성 답변 대신 경계가 있는 판단을 산출한다

### 발표에서 실제로 제공한 것은 무엇인가

OpenAI는 Decisions API를 GPT-6 Luna를 활용하는 별도 전용 엔드포인트로 일반 공개했다고 밝혔다. 개발자는 **질문, 허용되는 답, 판별에 필요한 문맥**을 정의한다. 입력은 텍스트뿐 아니라 이미지와 네이티브 JSON도 가능하다. 질문의 설명에 이미지도 포함할 수 있다. 출력은 자유형 장문이 아니라 세 형태 중 하나다. `predicate`는 조건이 참일 확률을 0~1로 추정한다. `choice`는 미리 정의한 옵션 하나를 고르고 그 확률·신뢰도 정보를 함께 준다. `score`는 순서가 있는 평가 수준의 확률 가중 평균을 반환한다. 제품 이미지에서 손상이 보이는지, 에이전트가 계속 진행·재시도·사용자 질문 중 무엇을 해야 할지, 손상 정도가 어느 수준인지가 원문 예시다.

이 구분은 사소해 보여도 데이터 계약에는 큰 차이를 만든다. `predicate`가 0.81을 반환했다고 해서 ‘위험’이라는 텍스트를 생성한 것과 같지 않다. 서비스가 0.81을 어떤 행동에 매핑할지는 별도 정책이다. `choice`의 `retry`는 허용 후보 중 최댓값일 수 있지만 다른 후보와 확률이 비슷하다면 고신뢰 결론으로 읽을 수 없다. `score`는 수준의 순서와 간격을 전제하므로, ‘낮음·중간·높음’의 숫자화가 업무적으로 타당한지 먼저 확인해야 한다. 최고 등급의 평균 점수만 볼 것이 아니라 각 등급 분포와 사람이 실제로 취할 행동을 점검해야 한다.

공식 발표에 따르면 공개 베타 이후 요청당 질문 수 상한은 200개에서 400개로 늘었고, 반복되는 문맥에 대한 프롬프트 캐싱, 미국·EU 추론 거주지, 아시아 일부 지역의 용량 확대, GPT-Live와의 네이티브 연동이 추가됐다. 최대 10배 빠르다는 표현은 같은 GPT-6 Luna를 Responses API에서 호출해 제한된 판단을 만드는 경우와 비교한 공급자의 설명이다. 입력 크기, 질문 수, 이미지 포함 여부, 네트워크 지역, 캐시 적중률에 따라 실제 p50·p95 지연은 달라진다. `최대` 수치를 서비스 SLA로 옮겨 적지 않는다.

GPT-Live 통합은 연속 대화 도중 작은 판단을 트리거로 발생시키는 구조다. 원문 예시는 대화 전사 업데이트를 이용해 아바타 표정을 고른다. 고객지원에서는 명확화 질문, 담당자 라우팅, 상담원 연결 여부를 판단할 수 있다고 설명한다. 이때 이벤트 스트림의 빠른 반응이 실제 고객 경험으로 이어지려면 전사 지연, 오인식, 트리거 중복, 늦게 도착한 이벤트를 처리해야 한다. 말하는 사람이 바뀌거나 사용자가 방금 한 말을 정정하면 첫 판단을 취소할 수 있어야 한다. 정답이 늦게 도착한 경우 과거 이벤트가 최신 UI 상태를 덮어쓰지 않게 순서 번호를 붙이는 것이 합리적이다. 이는 발표 기능 자체가 아니라 서비스를 붙일 때의 운영 설계다.

### 개발자에게 의미: 모델 출력과 정책 결정을 분리한다

분류 결과는 ‘추천’이지 권한의 근거가 아니다. 고객 메시지를 긴급 사례로 분류해 우선순위를 올리는 것과 자동으로 환불을 실행하는 것은 다른 권한 단계다. 후자에는 청구 기록·환불 한도·과거 환불·계정 상태를 조회한 결정적 정책 엔진이 필요하다. `choice`의 후보를 `refund`, `deny` 두 개로만 만들면 인간 상담원 연결이나 증빙 요청 같은 안전한 중간 옵션이 사라진다. 가능한 답 집합의 설계가 모델 성능 이상으로 중요하다.

좋은 시작은 단일 반복 결정을 좁게 잡는 것이다. 예를 들어 지원 문의를 `배송`, `결제`, `제품`, `기타`, `사람에게 전달`로 나누고, 지난달의 실제 처리 결과를 검증셋으로 만든다. 단순 정확도 외에 `사람에게 전달`해야 할 사례를 자동 경로로 보낸 비율, 특정 언어·고객군에서의 오류, 초기 문맥이 부족한 문의의 거부율, 의사결정이 고객 결과에 미치는 비용을 본다. 클래스 빈도가 치우쳐 있다면 전체 정확도 95%도 중요한 소수 사례를 놓칠 수 있다. 규칙 기반 경로, 기존 LLM 경로, Decisions API 경로를 같은 표본과 같은 비용 계산으로 비교한다.

확률은 그대로 의사결정의 확률이라고 단정하지 않는다. `predicate=0.8`인 묶음에서 실제 정답이 약 80%인지를 확인하는 **보정(calibration)** 검사가 필요하다. 시기와 고객군에 따라 보정이 달라질 수 있다. 이메일 제목처럼 짧은 입력과 이미지가 포함된 긴 입력에서 임계값을 다르게 잡아야 할 수도 있다. 불확실성이 클 때는 추가 질문 또는 사람 검토 경로를 선택한다. 이는 토큰을 조금 더 써도 오류 비용을 줄일 수 있는 명시적 설계 선택이다.

API 설계에서는 질문 문구, 허용 답 목록, 문맥 스키마를 함께 버전 관리한다. 선택지 하나를 추가하면 동일 입력의 출력 분포가 달라질 수 있다. 프롬프트 캐싱을 사용한다면 재사용 가능한 정적 문맥과 요청별 민감 정보를 분리해야 한다. 캐시 키가 다른 고객의 문맥을 섞지 않는지, 저장·보존 정책이 계약에 맞는지 확인한다. 400개 질문을 한 번에 보낼 수 있다는 이유만으로 서로 다른 사용자의 민감 데이터를 무조건 한 배치에 합치지 않는다. 배치 실패의 재시도 단위, 타임아웃, 부분 실패의 회수 방법도 정한다.

### 운영 포인트: 가격은 입력 토큰 하나로 끝나지 않는다

공식 발표는 입력 100만 토큰당 0.10달러, 캐시된 입력 0.01달러, 출력 토큰 요금 없음이라고 적었다. 저렴해 보이는 단가는 의사결정 문맥의 크기와 호출 빈도에 곱해 봐야 한다. 같은 고객의 거래 내역 전체를 매 단계 다시 보내면 호출 수가 적어도 입력이 커진다. 반대로 일괄 질문은 네트워크 왕복을 줄이지만 가장 늦은 하위 판단이 전체 배치를 지연시킬 수 있다. 과금 모델과 시스템 지연을 함께 기록한다.

실험에서는 사용자 요청당 판단 호출 수, 입력 토큰의 중앙값·상위 분위수, 캐시 적중률, 지역별 왕복 시간, 모델 추론 시간, 최종 행동까지의 지연을 나눠 측정한다. 실시간 음성에는 평균 지연보다 발화 중단과 재개 순간의 p95가 중요하다. 대량 비동기 정산에는 요청당 비용과 실패한 배치 재시도 비용이 더 중요하다. 제공사의 속도 비교와 내부 서비스의 체감 속도는 다른 지표다. 가격과 제공 지역은 바뀔 수 있으므로 배포 시점의 공식 가격·가용성 문서를 다시 확인한다.

실패 때의 기본 동작도 필요하다. 분류 API가 응답하지 않는다면 결제나 계정 변경을 허용하는 방향으로 조용히 통과시키지 않는다. 해당 결정을 보류하고 규칙 기반 검토 또는 상담원 경로로 넘긴다. 반면 단순 UI 색상 반응이면 중립 표정으로 폴백해도 된다. 같은 API라도 후속 행동의 위험이 다르기 때문에 장애 정책을 사용 사례별로 설계해야 한다.

## 2. ThinkingBox-Training — 에이전트의 말을 채점하지 않고 최종 상태를 채점한다

### 배경: 도구 호출의 그럴듯함과 업무 완료는 다르다

에이전트 평가에서 흔한 오류는 ‘그럴듯한 단계’를 ‘업무가 끝났다’로 읽는 것이다. 고객지원 에이전트가 여러 도구를 알맞게 호출하고 “해결했습니다”라고 말해도 배송 예외가 열린 상태라면 실제로는 해결되지 않았다. ThinkingBox-Bench는 이 간극을 겨냥한다. 발표에 따르면 507개 과제마다 실제 백엔드와 도구를 제공하고, 시뮬레이션된 사용자가 상호작용한 뒤 마지막 DB 레코드와 부수효과를 실행 가능한 검사로 채점한다. 평가 대상은 특정 인간 정답의 도구 호출 순서를 그대로 재현했는지가 아니라 **최종 업무 상태가 요구 조건을 충족하는가**다.

이번 발표의 진전은 같은 형식의 터미널 상태 검사 결과를 학습 보상으로 전환했다는 점이다. 학습용 과제는 벤치마크 507개와 분리됐다. Qwen3.8-27B에 대해 학습용 187개 과제를 골라 50단계 GRPO 강화학습을 수행했다. 각 rollout은 단순 텍스트 완성이 아니라 분리된 백엔드와 MCP 세션, 모의 사용자와의 상호작용을 갖는 전체 에피소드다. 도구 호출 해석, 인자 형식, reasoning 추출, 과제 상태 처리의 코드가 학습과 평가에서 같아야 보상이 실제 배포 에이전트의 행동을 가리킨다고 연구팀은 설명한다.

‘최종 상태’도 무조건 숫자 1개로 충분한 것은 아니다. 예약 변경 과제라면 올바른 예약 행뿐 아니라 불필요한 결제·환불이 **발생하지 않았음**까지 검사해야 한다. 에이전트가 요청한 행을 수정하면서 다른 고객의 레코드도 바꿨다면 부분 성공이 아니다. 원문은 잘못된 변경, 빠진 변경, 추가 부수효과를 실패로 본다고 설명한다. 다수의 검사에는 결정적 실행 검사를 쓰고, DB 상태만으로 좁은 요구를 판별하기 어려운 소수 항목에는 LLM 판정자를 이용해 이진 결론을 만든다. 따라서 ‘완전히 인간 또는 LLM 판정이 없는 보상’이라고 과장하면 안 된다.

### 수치 읽기: 평균 성공과 반복 성공은 다른 제품 질문이다

연구팀은 507개 과제를 각각 20회 실행했다. 따라서 10,140개 시도가 평가 표본이다. 기본 모델의 성공 시도는 5,242개, 51.70%였고 학습 후 6,163개, 60.78%였다. 차이는 **9.08%포인트**다. 20회 모두 성공한 과제는 38개에서 107개로 늘어 약 2.8배가 됐다. 반대로 20회 중 적어도 한 번 성공한 과제는 453개에서 446개로 **7개 감소**했다. 이것은 모델이 ‘더 넓은 문제를 풀게 됐다’기보다 일부 문제를 훨씬 일관되게 풀도록 확률 질량이 이동했음을 시사한다. 연구팀도 그 해석을 제시하며 모든 도메인에서 도달 범위가 늘었다고 주장하지 않는다.

발표의 도메인별 표에서는 `pass@1`과 관측된 20/20 성공이 소매, 자동차보험, 여행, 네오뱅크, 컨설팅 다섯 영역 모두에서 상승했다. 그러나 ‘한 번이라도 해결’ 지표는 네오뱅크·컨설팅에서만 올랐고 소매·여행·자동차보험에서는 내려갔다. 자동차보험의 범위 손실이 7.0%포인트였다는 수치도 공개됐다. 제품이 희귀한 예외 사례를 넓게 처리해야 한다면 반복 성공 하나만으로 학습을 승인할 수 없다. 반대로 고객 결제처럼 동일한 보통 과제를 거의 매번 똑같이 처리해야 한다면 한 번의 최대 가능성보다 반복 성공이 중요한 지표다.

반복 20/20은 운영 신뢰도의 유용한 관찰 지표지만, 수학적으로 ‘실패 확률 0’을 증명하지 않는다. 20번 모두 성공한 과제라도 21번째에 실패할 수 있다. 과제별 표본이 20개이기 때문에 희귀 실패율을 정밀하게 추정하기 어렵다. 실무에서는 과제별 20회 반복과 더불어 정책 위반처럼 치명적인 실패에는 별도의 장기 표본·시뮬레이션·사후 모니터링이 필요하다. 통계적 신뢰구간과 사용자군별 실패 분해도 함께 봐야 한다. 연구 결과를 특정 회사의 SLA로 복사하면 안 되는 이유다.

### 학습 과제를 고르는 방법이 보상 함수만큼 중요하다

GRPO는 같은 과제에 대한 여러 시도를 비교해 유리한 행동을 학습한다. 8개 시도가 전부 실패하면 보상 벡터가 모두 0, 전부 성공하면 모두 1이다. 그룹 내부에서 상대적으로 나은 시도가 없으니 과제 보상으로부터 배울 대조가 약하다. 연구팀은 기본 모델을 학습 전에 여러 번 시험해 각 후보 과제의 성공 가능성을 추정했다. 성공 `k`회, 시도 `n`회에 대해 Jeffreys 사전분포를 사용한 `Beta(k+0.5, n-k+0.5)` 사후분포를 계산하고, 거의 못 푸는 과제와 거의 항상 푸는 과제를 제외했다. 이 기준은 특정 모델의 현재 능력에 종속된다. 다른 모델에 같은 과제가 같은 난이도일 수 없다.

구간 경계 0.08·0.40·0.60·0.90은 이 실험의 하이퍼파라미터이며 보편적 난이도 법칙이 아니다. 연구팀은 학습 도중 계속 난도를 다시 추정하지 않고 기본 모델로 한 번 분류한 풀을 고정했다. 이는 반복 평가와 백엔드 실행이 비싼 환경에서 선택한 절충이다. 모델이 빨리 개선되면 초기에 적당했던 과제가 너무 쉬워질 수 있고, 다른 과제는 여전히 지나치게 어렵다. 자체 학습 시스템에 적용할 때는 재탐색의 이득과 시뮬레이션·도구 실행 비용을 함께 추산해야 한다.

훈련 수치의 해석에도 주의가 필요하다. 연구팀은 24개 H100, 업데이트당 18개 그룹×8개 rollout(144개 에피소드), 50단계의 전체 파라미터 학습을 공개했다. 이 스택은 단일 프롬프트 튜닝보다 훨씬 많은 기반 시스템을 요구한다. 백엔드가 타임아웃 나면 에이전트의 오답으로 기록하지 않고 그룹을 다시 채웠고, 보상 편차가 없는 그룹은 교체했다. 장애를 오답으로 섞으면 모델은 환경 실패를 자신의 행동 결과로 학습한다. 운영 평가에서도 같은 원칙을 적용해야 한다. 도구 권한 오류, DB 락, 네트워크 시간초과, 판정자 오류는 원인 코드를 분리한다.

### 개발자에게 의미: 프로덕션 상태 변경을 위한 평가 계약

에이전트가 DB를 바꾸는 서비스라면 테스트 계약을 `입력 문장 → 예상 답변`만으로 만들지 않는다. `초기 상태`, `허용 도구`, `권한`, `필수 선행 승인`, `최종 상태에서 참이어야 할 조건`, `바뀌면 안 되는 레코드`, `중복 실행 조건`을 한 과제로 묶는다. 예를 들어 ‘예약을 다운그레이드해 달라’는 요청에서 관리자 승인이 필요하다면 승인이 없을 때 예약·결제 둘 다 그대로 남아야 한다. 에이전트가 공손하게 승인 필요성을 설명했더라도 이미 환불을 실행했다면 실패다. 반대로 설명 문장은 조금 달라도 승인 없이 아무 변경을 하지 않았다면 핵심 상태 보존은 맞았다.

이 평가 계약은 단지 학습을 위한 장치가 아니라 릴리스 회귀 테스트로도 쓸 수 있다. 프롬프트, 모델 버전, 도구 스키마, 승인 정책, DB 마이그레이션 중 어느 하나가 달라졌을 때 동일 과제를 재실행한다. 성공률뿐 아니라 치명적인 추가 부수효과를 따로 집계한다. 마이그레이션으로 컬럼 의미가 바뀌었다면 판정기도 함께 갱신해야 한다. 그렇지 않으면 새 시스템이 맞게 동작해도 평가가 실패하거나, 더 나쁘게는 새 오류를 통과시킬 수 있다.

### 운영 포인트: ‘신뢰 가능한 성공 1건당 비용’을 조건과 함께 본다

발표는 20회 캠페인의 추정 추론 비용이 925.80달러에서 855.58달러로 줄고, 성공 시도 1건당 추정 비용이 0.177달러에서 0.139달러로 줄었다고 계산했다. 20회 모두 성공한 과제당 추정 비용은 24.36달러에서 8.00달러가 됐다. 이 값은 모델 추론 비용을 기준으로 한 상대 비교 지표이지 클라우드 청구서가 아니다. 학습 실행비와 학습 과제 선별용 probe 비용도 제외돼 있다. 자체 서비스의 전체 소유 비용을 계산할 때는 시뮬레이터, DB 복제, 데이터 제작, 사람 검토, 장애 재시도, 학습, 관측 시스템을 더해야 한다.

또한 20회 모두 성공한 과제라는 분모가 모델마다 달라진다. 덜 중요한 많은 과제를 반복 성공해 분모를 키우는 것보다 중요한 결제·권한 과제의 실패율을 낮추는 편이 제품 가치는 더 클 수 있다. 오류 비용에 가중치를 둔 지표와 치명적 실패 0건 조건을 별도로 둔다. 에이전트의 최종 설명과 실제 DB 상태가 다를 때는 상태를 우선 진실로 삼고, 고객에게는 수정된 상태와 복구 절차를 알려주는 설계를 준비한다.

## 3. OlmoEarth v1.3 — 지구 영상의 재사용 가능한 표현을 공개한다

### 배경: 위성 원자료를 매 과제마다 처음부터 처리하는 비용

토지 피복 분류, 농작물 유형, 산불 피해, 광산 활동 탐지에는 이미지 한 장보다 계절·연도에 걸친 관측이 중요하다. 센서마다 측정 방식도 다르다. Sentinel-1은 레이더, Sentinel-2와 Landsat은 다중분광 자료를 제공한다. 구름, 계절성, 궤도, 해상도, 결측 시점이 섞여 있어 한 사용 사례를 검토하는 데도 대량의 데이터 준비와 GPU 추론이 필요하다. OlmoEarth v1.3의 핵심 변화는 이 복잡한 위성 시계열을 지구 전역의 **픽셀별 특징 벡터**로 미리 계산해 배포한다는 점이다. 응용팀은 동일한 원자료 처리 파이프라인을 무조건 재구축하지 않고 라벨과 작은 분류기를 얹어 가설을 시험할 수 있다.

공식 글은 1년의 Sentinel-1·Sentinel-2·Landsat 시계열을 입력으로 받아 10m 픽셀마다 128차원 벡터 하나를 만든다고 설명한다. 앞의 64차원만을 사용하는 절반 크기 표현도 함께 고려했다. 이는 각 픽셀이 128개의 독립적 환경 변수로 해석된다는 뜻은 아니다. 신경망이 학습한 잠재 표현이므로 개별 차원에 ‘산불’ 또는 ‘옥수수’라는 이름을 붙일 수 없다. 변화 감지는 서로 다른 연도의 벡터 사이 차이를 활용하지만, 큰 벡터 변화가 모두 불법 채굴 같은 단일 원인이라고 결론낼 수 없다. 모델은 이상 신호를 가리키고, 현장 확인이나 원본 영상 대조가 의미를 부여한다.

AllenAI는 27개 평가, 여섯 대륙, 여러 과제에서 AlphaEarth Foundations 및 Tessera v2와 비교했다고 밝힌다. 128차원 임베딩은 27개 중 20개에서, 64차원 버전은 18개에서 최고 점수였다고 한다. 이는 발표팀의 정해진 평가 구성에서의 결과다. 개발자는 자신의 나라·계절·해상도·라벨 품질·대상 물체 크기에 대한 전이 성능을 따로 검증해야 한다. 예컨대 10m 픽셀의 평균적 특징으로 좁은 도로나 작은 건물을 직접 분리하는 작업은 공간 해상도의 한계를 받을 수 있다. 넓은 농경지와 산림 변화 같은 과제와 같은 기준으로 평가하면 안 된다.

### 데이터 공개의 실제 범위와 출처 추적

발표에는 전 지구 연도별 임베딩이라는 표현이 있지만 출시 시점의 연도 범위는 구분해야 한다. 2023년, 2024년, 2025년 자료가 전 지구를 덮고, 2017~2022년은 일부 국가에 제공된다. 글은 연당 약 150TB의 아카이브라고 설명한다. 모든 사용자가 150TB 전체를 내려받아야 하는 것은 아니다. 관심 지역과 연도, 필요한 차원 수만 선택하는 접근이 중요하다. 64차원 표현은 저장·전송량을 줄이지만 특정 과제의 품질 손실은 직접 확인해야 한다. 공개된 출처 표는 20km 타일·연도마다 모델이 읽은 Sentinel/Landsat 장면과 원본 카탈로그 링크를 추적할 수 있게 한다고 한다. 원본이 무엇인지 밝히는 것은 재현성과 오류 조사에서 중요한 기능이다.

Embeddings Explorer는 지도에서 연도를 바꾸고, 유사한 장소를 찾고, 소수의 라벨 포인트로 작은 분류기를 학습해 GeoTIFF로 내보낼 수 있는 탐색 도구다. 계정과 고급 환경 구성이 필요 없다고 소개한다. 이 도구가 내보낸 지도가 즉시 정책 집행에 쓸 수 있는 검증된 제품이라는 뜻은 아니다. 소수 라벨로 만든 분류기는 라벨을 찍은 지점 근처와 비슷한 지형에서 좋고 다른 지역에서는 실패할 수 있다. 지도 전체의 오류는 랜덤한 픽셀 표본보다 **서로 떨어진 지역과 다른 계절**을 홀드아웃해 측정해야 한다. 인접 픽셀을 훈련과 평가로 나누면 거의 같은 공간이 양쪽에 들어가 성능이 부풀 수 있다.

출시 글의 페루 La Pampa 사례는 연도 간 임베딩 변화를 광산 확대·회복·재개 가능성과 비교해 보여준다. 이는 탐색 데모와 외부 관측을 함께 제시한 사례이지 임베딩 차이만으로 불법 행위를 자동 판정하는 법 집행 시스템은 아니다. 계절과 강우, 화재, 농작물 교체, 센서 관측 수의 변화도 벡터 차이에 영향을 줄 수 있다. 특정 토지 변화 주장에는 원본 이미지, 다른 공개 자료, 현지 도메인 전문가의 확인을 결합해야 한다.

### 개발자에게 의미: 사전 계산된 특징의 장점과 함정

임베딩을 활용한 최소 실험은 대상 지역의 특정 연도 타일을 가져와 라벨 데이터와 공간적으로 정렬하고, 간단한 분류기와 기존 기준 모델을 같은 홀드아웃에서 비교하는 것이다. 라벨 좌표가 10m 픽셀의 경계와 어긋나면 성능을 정확히 판단하기 어렵다. 다각형 라벨은 픽셀 중심, 겹침 비율, 경계 제외 규칙을 명시해야 한다. 훈련에 사용하지 않은 연도와 지역을 평가해 시간·공간 전이를 확인한다. 사람이 ‘변화’라고 표시한 날짜와 연간 임베딩의 관측 창이 맞는지도 살핀다. 같은 해 안의 특정 주간 변화가 중요한 과제에는 연도당 벡터 하나가 지나치게 거칠 수 있다.

실무 파이프라인은 `원본 장면 → 전처리/모델 버전 → 연도·타일 임베딩 → 라벨 정렬 → 분류/변화 점수 → 사람 검증`으로 추적 가능해야 한다. 임베딩 벡터를 저장할 때 공간좌표계, 픽셀 범위, 모델 버전, 연도, 64/128차원 선택을 함께 남긴다. 모델 버전이 바뀌면 벡터 공간이 바뀔 수 있으므로 구형과 신형 벡터의 거리나 코사인 유사도를 그대로 이어 붙이지 않는다. 기존 임계값이 유효한지 다시 보정한다. 공개 데이터의 라이선스와 원영상의 조건은 별도로 확인한다. 발표팀은 OlmoEarth Artifact License를 언급하므로, 사용하려는 모델·데이터·파생 지도에 적용되는 정확한 조건을 확인해야 한다.

### 운영 포인트: 전 지구 규모의 숫자를 제품 지표로 바꾸는 법

연당 약 150TB라는 숫자는 ‘무료라서 저장 비용이 없다’는 뜻이 아니다. 조직이 다루는 지역만 가져와도 네트워크 전송, 객체 저장, 압축, 검색 인덱스, 분석 작업 비용이 생긴다. 타일별 요청과 캐시, 연도별 증분 갱신, 지도를 사용자에게 보여주는 타일 서비스의 성능을 별도로 설계한다. 모든 픽셀을 온라인 요청 시마다 분류하면 지연과 비용이 커질 수 있으므로, 일정 주기로 일괄 점수를 만들고 조회에는 준비된 타일을 쓰는 방식이 적합할 수 있다. 반면 긴급 재난 대응처럼 최신성이 중요한 경우 연도별 공개 임베딩만으로 충분하지 않다. 날짜 범위를 자유롭게 선택해 같은 모델을 실행하는 경로를 검토해야 한다.

모델 학습 비용 수치도 분리해 읽는다. AllenAI는 이전 v1.2 대비 학습 계산 시간 53%, v1 대비 18%, 탄소 배출 각각 50%와 22%라고 발표했다. 최종 사전학습 실행의 임대 H100 비용을 약 2,720달러로 추산한다. 이는 데이터 수집·전처리·실험 반복·전 지구 임베딩 생성·배포·인력 비용을 포함한 총 개발비가 아니다. 또한 연구팀의 장비·가격·조건에 따른 추산이며 다른 조직의 재현 비용과 같지 않다. 운영팀은 자신이 **이미 계산된 임베딩을 이용**하는지, **직접 새 시기의 임베딩을 생성**하는지에 따라 완전히 다른 비용 표를 만들어야 한다.

## 4. Granite Timeseries Ensemble R1 — 예측 모델 선택을 기본 구성으로 묶는다

### 무엇이 공개됐는가: 가중치 합병이 아닌 구성 레시피

시계열 예측 서비스는 모델 하나를 고른 뒤 끝나지 않는다. 매출과 전력 부하, 공장 센서의 패턴과 허용 오차가 다르다. 계절성이 강한 시계열, 불규칙한 이벤트가 많은 시계열, 긴 예측 지평, 짧은 지평에 적합한 모델이 다를 수 있다. IBM Research는 네 Granite 사전학습 모델을 하나의 Forecaster 인터페이스로 호출하는 앙상블을 제시한다. 기본 구성은 PatchTST-FM-r1(패치 Transformer), PatchTST-FM-r2(패치 Conformer), FlowState-r1.1(상태공간 모델), TTM-r3(MLP mixer)다. 네 모델의 가중치를 새 하나의 모델로 합친 것이 아니라 구성 파일을 통해 각각의 체크포인트를 내려받아 실행한다. 첫 실행의 다운로드 시간과 네 모델의 메모리 요구를 감안해야 한다.

기본 `Probabilistic Ensemble`은 각 모델의 분위수 예측을 확률 공간에서 같은 영향력으로 합친 뒤 원하는 분위수를 산출한다. 과거 타깃값을 사용해 새 가중치를 학습하는 절차가 없으므로 처음 보는 시계열에서 시작점으로 쓸 수 있다. 대안인 `IQR Ensemble`은 구성 모델이 예측한 사분위 범위가 좁을수록 더 큰 비중을 주며, 샘플·대상·미래 시점별 가중치가 달라진다. 결합된 분위수가 역전되지 않도록 isotonic regression을 쓴다. 단, 좁은 구간이 반드시 더 정확하거나 더 잘 보정됐다는 뜻은 아니다. 과신하는 모델이 오히려 지나치게 큰 영향을 받는 위험이 있으므로 옵션의 온도와 최대 가중치 제한을 조정하고 실제 백테스트로 확인해야 한다.

기본 인터페이스는 중앙 예측값뿐 아니라 기본적으로 0.1~0.9 분위수를 반환한다. 0.1과 0.9 사이를 ‘명목상 중앙 80% 구간’이라 부를 수 있지만 실제 결과의 80%가 그 안에 들어오는지는 데이터로 확인해야 한다. 인기 상품 수요가 프로모션 때 급증한다면 고정된 계절 패턴에서 만든 구간은 급증기를 반복적으로 놓칠 수 있다. 운영 결정을 0.9 분위수에 연결한다면 구간 과소 추정이 재고와 비용으로 이어진다. 예측 모델의 중앙값 오차와 구간 보정은 다른 문제다.

### 지표를 정확하게 읽기: 0.683 대 0.685의 의미

IBM은 97개 GIFT-Eval 데이터 구성에서 추가 미세조정 없이 네 개별 모델과 두 앙상블을 비교했다고 한다. 기본 확률 앙상블의 MASE는 0.683, IQR 앙상블은 0.684, 가장 좋은 단일 PatchTST-FM-r2는 0.685였다. 이 비교에서 낮을수록 좋은 MASE의 차이는 **0.002**로 작다. 집계 평균 순위는 기본 앙상블이 더 좋아 모델 선택의 위험을 줄이는 기본값이라는 해석이 가능하다. 그러나 한 조직의 한 SKU가 반드시 더 정확해진다는 보장은 없다. 평균이 좋아도 특정 구간의 최악 예측은 나빠질 수 있다.

확률 예측 지표 CRPS/MWQL에서는 PatchTST-FM-r2가 0.467, 두 앙상블은 0.471이다. 구성 모델이 이 표에서 집계 값은 더 낫다. 평균 CRPS 순위에서는 IQR 앙상블이 표의 여섯 예측 중 가장 낮은 47.619를 보인다. 집계 점수와 평균 순위의 차이는 데이터셋 간 분포가 다르고 어떤 성능을 평균내는가에 따라 결론이 달라짐을 보여준다. `최고 성능` 한 단어로 압축하면 이 중요한 선택 조건을 잃는다. 공식 글도 앙상블이 전체 리더보드의 정점이 아니며 허가 조건이나 미세조정 여부가 다른 일부 시스템은 더 좋은 점수를 냈다고 설명한다.

기본 네 모델과 앙상블 레시피는 허용적인 라이선스라고 발표했다. 그러나 추가 IBM Research 체크포인트를 포함하는 확장 레시피에는 비상업적·연구용 제한처럼 별도 조건이 있다고 명시한다. 패키지 전체의 이름만 보고 모든 조합을 상업 서비스에 쓸 수 있다고 판단하지 않는다. 배포하려는 구성 파일의 각 멤버 카드와 종속성을 검토해야 한다. 모델 다운로드 시 체크포인트 버전을 고정하지 않으면 동일한 애플리케이션 커밋에서도 시간이 흐른 뒤 다른 가중치를 받아 예측이 변할 수 있다.

### 개발자에게 의미: 먼저 백테스트의 시간 규칙을 정한다

시계열 실험의 핵심은 **예측 원점에서 실제로 알 수 있던 정보만 사용**하는 것이다. 9월 1일에 10월 수요를 예측하는데 9월 말 집계나 프로모션 결과를 입력하면 미래 정보가 샌다. 과거 데이터를 임의로 섞은 랜덤 분할보다, 여러 시점에서 모델을 실행하는 롤링 백테스트가 서비스에 가깝다. 예측 길이, 갱신 빈도, 업무 휴일, 재고 부족 때문에 판매량이 실제 수요를 숨기는 경우, 품절 이후 0으로 기록된 데이터를 어떻게 처리할지까지 정한다.

비교 대상은 기본 확률 앙상블, IQR 앙상블, 가장 강한 단일 모델뿐 아니라 현재 운영 중인 계절 Naive나 통계 모델이어야 한다. 대형 모델 네 개가 단순 기준보다 조금 나은데 처리 비용은 크게 오른다면 가치가 없다. 예측 성능을 데이터셋 전체 평균뿐 아니라 예측 지평별, 상품군별, 희소 시계열별, 새 상품별, 프로모션 기간별로 나눈다. 중앙값 예측 오류에는 MASE, 재고 부족 위험에는 상위 분위수의 quantile loss와 실제 구간 포함률을 본다. 모델의 80% 예측 구간이 현실에서 60%만 포함한다면 업무 의사결정에 그대로 쓰면 안 된다.

IBM 글은 현재 구성에서 다변량 채널을 서로 독립적으로 예측한다고 명시한다. 다른 제품 가격, 캠페인, 기온이 수요에 미치는 교차 영향을 자동으로 학습하는 모델이라고 추정해서는 안 된다. 각 멤버의 입력 문맥 길이, 예측 지평, 전처리, 결측값 처리도 달라 어댑터가 생긴다. 결측이 많거나 측정 주기가 바뀌는 산업 센서에서는 모델 간 예측을 결합하기 전에 같은 시간축과 단위를 사용하는지 검증한다. 분, 시간, 일 단위를 혼동한 앙상블은 단일 모델보다 위험할 수 있다.

### 운영 포인트: 네 배의 모델은 네 배 이상의 복잡성을 만들 수 있다

앙상블의 출력 하나를 만들 때 네 체크포인트를 로드하고 네 예측 경로를 유지해야 한다. 메모리·시작 시간·CPU/GPU 사용량·서비스 장애면이 늘어난다. 동시에 실행할 수 있으면 최종 응답 지연은 가장 느린 모델에 좌우될 수 있고, 순차 실행이면 시간이 합쳐질 수 있다. 일부 멤버가 실패했을 때 남은 모델로 예측을 내놓을지, 전체 요청을 실패로 처리할지, 강한 단일 모델로 폴백할지를 사전에 정한다. 남은 모델의 예측 구간은 원래 앙상블과 보정 특성이 달라지므로 조용히 같은 의미로 표기하지 않는다.

모니터링에는 예측 결과뿐 아니라 **해당 시점의 입력 데이터, 네 멤버별 예측, 결합 결과, 모델·레시피 버전, 오류 코드, 추론 시간**을 남긴다. 실제 정답이 도착하면 지평별 오차를 연결한다. 재학습이 없다고 운영 관리가 필요 없는 것은 아니다. 데이터 분포 변화, 새로운 제품군, 센서 교체, 긴 결측 구간에서 예측 구간의 포함률이 떨어질 수 있다. 편차가 지속되면 해당 세그먼트를 별도 모델 또는 인간 계획으로 보내는 것이 합리적이다.

## 5. FDE 글이 제시한 교훈 — 기술을 현장 결과로 연결하는 순서

### OpenAI가 말한 ‘배포 격차’

OpenAI의 FDE 글은 모델이 벤치마크에서 할 수 있는 일과 조직이 업무에서 안정적으로 사용할 수 있는 일 사이의 간극을 설명한다. 이는 새로운 모델의 성능 발표가 아니라 고객 도입 경험을 공개한 글이다. 글은 결과에서 시작하고, 먼저 실제 사용자가 가치 있다고 느낄 정도의 작업을 만든 뒤, 반복 가능한 도구로 일반화하며, 모델 자체가 못하는 부분은 평가셋과 피드백을 연구팀에 전달하는 순서를 제안한다. 이 순서는 홍보 문구와 실무 교훈을 분리해서 읽을 만하다. 사례별 수치는 해당 고객·업무·측정 범위에서 나온 공급자의 설명으로만 취급한다.

반도체 고객 사례에서는 2025년 중반 약 15명의 FDE가 10개 이상의 사용 사례를 다뤘다고 한다. 지시형 테스트 생성, 근본 원인 분석, 아키텍처 보조 도구를 만들고 3~6개월에 걸쳐 초기 운영과 사용을 시작했다. 글은 테스트 생성 시간 약 48% 절감, 커널 최적화 성능 중앙값 22% 개선, 일부 디버깅 시간을 몇 주에서 몇 시간으로 압축했다고 보고한다. 그러나 검사 대상 칩, 팀 숙련도, 측정 방식, 대조군은 공개 글만으로 완전히 재현할 수 없다. 다른 반도체 회사의 48% 절감을 예산 계획에 기입해서는 안 된다.

처음에는 사용 사례별 맞춤 애플리케이션을 만들었으나 나중에 Codex를 중심으로 공통 harness를 두고 기능을 플러그인·스킬로 옮겼다고 설명한다. 그 결과 프로젝트별 맞춤 코드의 약 90%를 제거한 사례가 있다고 한다. 이는 첫날부터 아무 맞춤 구현 없이 시작하라는 뜻이 아니다. 팀은 현장 제약을 파악하고 평가를 만든 뒤, 여러 과제에 반복되는 기능이 무엇인지 확인해 공통화했다. 너무 일찍 추상화하면 제품에 맞지 않는 범용 프레임워크가 되고, 너무 늦으면 프로젝트마다 다른 연결 코드가 유지비를 키운다.

통신 고객의 음성 서비스 사례에서는 초기 평가 약 60%가 업무 투입 기준에 부족해 연구팀과 고객팀이 함께 기능 호출·명령 준수의 부족한 부분을 구체화했고, 약 6개월 동안 평가가 80%, 이어 90% 이상으로 올랐다고 한다. 여기서 중요한 것은 ‘모델이 언젠가 좋아지겠지’라는 기대가 아니라 현장 과제를 재현 가능한 평가로 변환했다는 점이다. 숫자는 특정 평가셋의 변화다. 실제 통화의 다양성과 고객 만족, 규제 준수까지 모두 90%라는 의미는 아니다.

### 개발자에게 의미: 무엇을 만들고 무엇을 버릴지 기록한다

현장형 AI 프로젝트의 첫 산출물은 완성된 챗봇 화면이 아니라 **문제 정의와 실패 사례 모음**이어야 한다. 누가 결과를 쓰는지, 기존 업무가 얼마나 걸리는지, 오류가 어느 단계에서 비싼지, 데이터 접근 권한이 무엇인지, 사람이 어디에서 개입해야 하는지를 기록한다. 이후 실제 작업을 작게 자동화하고, 모델 교체 전후의 업무 결과를 같은 평가셋으로 재본다. 성공하면 구현을 서비스 경계에 맞춰 축소하고, 사용되지 않는 UI나 연결 코드는 제거한다. 공통 플랫폼을 만들더라도 도메인별 정책, 승인, 데이터 스키마, 평가셋은 남는다.

도입 보고서에는 `절약된 시간`의 분모가 무엇인지 써야 한다. 모델 응답 시간, 직원이 검토한 시간, 오류를 수정한 시간, 감사와 예외 처리 시간이 모두 다르다. ‘AI가 한 번에 생성했다’는 횟수보다 최종 업무가 완료된 건수와 정정율, 고객에게 미친 영향이 더 중요하다. FDE 글의 사례를 참고한다면 기술을 세 단계로 나눠 결재한다. **가치 검증**에서는 소수 실제 사례를 풀 수 있는지, **반복성 검증**에서는 다른 팀에서도 동일 결과가 나오는지, **플랫폼화**에서는 중복 코드를 줄이면서 변경 책임이 명확해지는지를 본다.

### 운영 포인트: 공급자 사례를 자기 조직의 가설로 바꾸는 방법

숫자를 카피하는 대신 ‘우리 조직에도 그 병목이 있는가’를 검증한다. 반도체 도구가 유효했다면 우리에게는 테스트 작성이 병목인지, 리뷰가 병목인지, 시뮬레이터 대기가 병목인지 측정한다. 고객지원 음성 모델이 나아졌다면 우리 통화의 언어·억양·잡음·정책 예외에서도 그런지 평가한다. 회계 자동화가 처리량을 올렸다면 오류 수정과 책임자의 승인 시간이 포함된 총 처리량을 재본다. 한 조직에서 좋은 결과가 난 공통 harness도 다른 조직의 권한·보안·배포 구조에는 맞지 않을 수 있다.

## 발표 다섯 건을 함께 읽는 실무 설계: 공통 원칙 여섯 가지

### 1) 결과를 무엇으로 판정할지 먼저 적는다

Decisions API에는 정답 선택지와 임계값, ThinkingBox에는 DB 최종 상태, OlmoEarth에는 지상 라벨과 시간·공간 범위, Granite에는 실제 수요와 예측 지평, FDE 프로젝트에는 사용자 업무 완료 기준이 필요하다. 이 정의 없이 모델을 평가하면 벤더가 공개한 지표와 내부 필요가 우연히 같기를 바라는 셈이다. 평가 지표는 기술적 편의가 아니라 업무 손실을 반영해야 한다. 잘못 분류한 1건과 승인 없는 환불 1건의 오류 비용은 같지 않다.

### 2) 데이터의 ‘언제’를 보존한다

고객 문의 라우팅 문맥은 결정 시점까지의 기록만, DB 에이전트의 도구 응답은 승인 시점까지의 상태만, 토지 변화 감지에는 어느 연도의 영상인지, 시계열 예측에는 예측 원점에서 무엇을 알았는지를 보존한다. 날짜가 어긋난 데이터는 오프라인 평가를 쉽게 부풀린다. 위성의 연간 특징으로 특정 날의 이벤트를 판정하거나, 수요 예측에 미래 프로모션 결과를 넣는 것은 서로 다른 모양의 같은 데이터 누수다.

### 3) 모델 출력과 실행 권한 사이에 정책 경계를 둔다

분류가 `승인`을 골랐다고 해서 바로 DB를 바꾸지 않는다. 에이전트가 ‘완료’라고 말했다고 실제 데이터가 맞는 것은 아니다. 변화 지도가 붉게 나왔다고 규제 위반이 확정된 것은 아니다. 수요 예측의 0.9 분위수가 높다고 자동 주문이 무조건 정당화되는 것도 아니다. 모델은 증거 또는 제안의 하나이고, 변경 권한은 검증 가능한 정책·사람 승인·감사 가능성에 의해 통제되어야 한다.

### 4) 평균만 보지 말고 분포와 반복성을 본다

Decisions API의 평균 지연보다 지연 상위 구간과 분류 오류의 손실이 중요할 수 있다. ThinkingBox에서는 평균 성공이 오르면서도 한 번이라도 해결하는 과제 수가 줄었다. OlmoEarth의 20/27 평가는 지역·과제별 편차를 감추고, Granite의 좋은 평균 MASE는 확률 예측 지표의 우위를 의미하지 않는다. 제품 대시보드에서 하나의 큰 숫자보다 **세그먼트, 최악 사례, 신뢰구간, 반복 테스트**를 볼 수 있게 한다.

### 5) 비용의 분자와 분모를 공개한다

입력 토큰 단가, 20회 평가당 추론 추정액, 사전학습 최종 실행비, 네 모델의 총 추론 메모리, 현장 개발 코드량은 서로 다른 비용이다. 개발팀 보고서에는 비용을 무엇에 나눴는지 적는다. `성공 시도 1건`, `반복 성공 과제 1건`, `지도 1㎢·연도`, `SKU 1개·예측일`, `직원 업무 1건`은 서로 대체되지 않는다. 필요한 분모에 맞춰 총 소유 비용을 다시 계산해야 도입 결정을 할 수 있다.

### 6) 되돌릴 경로를 제품 계약에 포함한다

새 판단 API가 장애면 규칙 또는 사람으로, 에이전트의 DB 변경이 어긋나면 상태 복원으로, 임베딩 버전 변경이 지도 품질을 떨어뜨리면 구형 타일로, 앙상블이 시간 제한을 넘기면 검증된 단일 모델로 돌아가야 한다. 폴백은 단순한 백업 엔드포인트 이름이 아니라 결과의 의미가 어떻게 바뀌는지 UI와 로그에 드러내는 절차다. 데이터 변경을 취소하는 방법과 평가 실패 시 배포 중단 조건까지 사전에 적어야 안전하게 속도를 낼 수 있다.

## 오늘 바로 실행 가능한 검증·운영 체크리스트

### A. 경계가 있는 의사결정 API를 검토한다면

1. 반복 호출되는 판단 하나를 고르고, `predicate`·`choice`·`score` 중 업무 결과에 맞는 타입을 선택한다. 질문과 선택지의 버전을 고정한다.
2. 실제 과거 사례를 시간 순서대로 나눠 평가셋을 만든다. 빈도가 낮지만 비용이 큰 사례를 별도 묶음으로 둔다.
3. 기존 규칙·LLM 경로와 같은 입력에서 정확도, 보정, 오류 비용, p95 지연, 요청당 총 입력 토큰을 비교한다.
4. 불확실할 때의 추가 질문과 사람 검토 경로를 명시한다. 모델의 선택을 곧장 결제·계정 변경 권한으로 연결하지 않는다.
5. 캐시와 배치의 고객별 데이터 경계를 검사하고, 실제 사용 지역·보존 조건·현재 가격 문서를 확인한다.

### B. 상태를 바꾸는 에이전트를 운영한다면

1. 각 과제에 초기 DB 상태, 정답 상태, 바뀌면 안 되는 행, 필요한 승인과 도구 권한을 적는다.
2. 같은 과제를 여러 번 실행해 평균 성공과 반복 성공, 적어도 한 번 성공, 치명적 부수효과를 따로 보고한다.
3. 모델 오답과 백엔드 타임아웃·도구 권한 오류·판정기 실패를 서로 다른 코드로 기록한다.
4. 실제 DB 변경과 사용자에게 보낸 완료 설명이 일치하는지 대조한다. 불일치하면 성공 메시지를 우선 신뢰하지 않는다.
5. 학습을 검토한다면 과제 선별 probe, 시뮬레이터, 보상 판정, 평가 오염 방지, 실행비까지 전체 비용을 추산한다.

### C. 지리 임베딩을 시험한다면

1. 지역·연도·대상 물체 크기와 필요한 업데이트 속도를 먼저 정해 연간 10m 표현이 과제에 맞는지 확인한다.
2. 64차원과 128차원을 같은 공간 홀드아웃에서 비교해 저장비와 품질을 함께 측정한다.
3. 인접 픽셀과 같은 농경지가 훈련·평가에 동시에 들어가지 않도록 공간 분할한다.
4. 큰 벡터 변화는 원본 영상·출처 표·현지 자료로 해석한다. 변화 점수를 단일 원인의 확정 판정으로 표기하지 않는다.
5. 모델·임베딩·라벨·GeoTIFF의 버전과 라이선스를 묶어 보관하고, 새 버전이 나오면 임계값을 다시 검증한다.

### D. 시계열 앙상블을 시험한다면

1. 실제 예측 시점을 재현한 롤링 백테스트를 구성한다. 미래 정보가 들어오는 열을 금지한다.
2. 현재 운영 기준, 강한 단일 모델, 두 앙상블을 동일한 지평과 데이터에서 비교한다.
3. MASE와 분위수 손실, 명목 80% 구간의 실제 포함률을 나눠 보고한다.
4. 네 체크포인트의 다운로드·메모리·추론 지연·모델별 장애를 측정한다. 라이선스와 버전을 각 멤버별로 고정한다.
5. 모델 하나가 실패하면 어떤 예측을 반환할지, 폴백 결과를 어떻게 표시할지 먼저 정한다.

### E. 현장 AI 프로젝트를 시작한다면

1. 데모 문장보다 업무 결과와 오류 비용, 실제 담당자의 검토 시간을 먼저 정의한다.
2. 도메인 전문가와 예외 사례를 모아 초기 평가셋을 만든다. 초기 모델이 못하는 작업을 숨기지 않는다.
3. 첫 가치가 입증될 때까지는 필요한 맞춤 코드를 쓰되, 반복되는 연결과 평가만 공통 도구로 추출한다.
4. 확대 전 다른 팀·다른 데이터에서 같은 효과가 재현되는지 확인한다.
5. 공급자의 사례 수치를 내부 목표치로 복사하지 않고 각 지표의 분모와 측정 범위를 다시 적는다.

## 숫자와 주장에 대한 편집자 주

오늘 글의 `최대 10배`, `51.70→60.78%`, `20/27`, `0.683`, `약 48%`는 각각 다른 발표자의 다른 실험·제품 사례에서 나왔다. 제공사가 발표한 숫자라는 점은 확인했지만 이 포스트가 별도 실험으로 재현한 것은 아니다. 특히 속도, 평균 정확도, 반복 신뢰성, 지도 전이 성능, 시계열 점수, 현장 업무 생산성은 단위가 다르다. **서로 합산하거나 ‘AI가 전체적으로 몇 % 개선됐다’고 쓰지 않는다.** 기술을 구매·배포하는 독자는 원문의 조건과 자기 조직의 동일 조건 실험을 함께 확인해야 한다.

또한 오늘의 글에서 권하는 보정 검사, 공간 홀드아웃, 폴백, 승인 경계, 관측 로그는 발표사가 모두 같은 방식으로 제공하는 공식 기능이 아니라 **발표 내용을 실제 서비스에 적용하기 위한 편집자의 운영 제안**이다. 기능 존재와 권장 구현을 섞지 않기 위해 명확히 구분했다. 공식 문서의 가격·제공 지역·라이선스·모델 버전은 시간이 지나 바뀔 수 있으므로 이 글의 발행일 기준 스냅샷으로 읽어야 한다.
