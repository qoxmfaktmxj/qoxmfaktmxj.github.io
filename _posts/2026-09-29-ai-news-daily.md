## 배경: AI의 논의 단위가 “답변”에서 “행동”으로 바뀌고 있다

초기의 생성형 AI 제품은 대개 질문과 답변의 관계로 이해할 수 있었다. 사용자가 프롬프트를 입력하고 모델이 문장, 코드, 이미지 또는 요약을 반환한다. 틀린 결과는 복사하지 않거나 다시 물으면 된다. 이 구조에서도 정확성, 편향, 개인정보 보호가 중요하지만, 모델의 출력이 외부 세계의 행동으로 바뀌는 마지막 단계에는 보통 사람이 있었다.

에이전트형 제품은 이 거리를 짧게 만든다. 목표를 받은 시스템은 저장소를 읽고, 문서를 찾고, 파일을 바꾸고, 테스트를 돌리고, 티켓을 갱신하고, API를 호출하고, 배포 후보를 만들 수 있다. 한 번의 응답이 아니라 수십 분 또는 수 시간 이어지는 실행이 된다. 그 과정에는 계획, 권한 요청, 재시도, 실패, 사용자 질문, 외부 서비스의 응답 지연, 취소, 재개가 들어간다. 따라서 제품의 기본 단위는 `프롬프트 → 답변`이 아니라 `의도 → 계획 → 실행 → 검증 → 승인 → 산출물 → 감사`가 된다.

OpenAI News에 유엔 안전보장이사회 관련 항목이 올라온 맥락은 이 전환을 공적 차원에서도 생각하게 한다. 이 Daily News는 index에서 확인한 제목과 날짜를 넘어 발언 내용을 추정하지 않는다. 그러나 AI가 공적 안전과 책임의 장에서 다뤄진다는 사실은, AI가 점점 더 실제 의사결정과 운영 체계에 연결되고 있음을 보여 준다. 제품팀은 “모델이 무엇을 말했는가”뿐 아니라 “시스템이 실제로 무엇을 하도록 허용했는가”에 답할 준비가 있어야 한다.

## Top News 1. OpenAI News가 던지는 질문: 책임은 출시 뒤의 설명문이 아니다

OpenAI의 공식 News index는 9월 23일자 최신 항목으로 “Sam Altman’s remarks at the United Nations Security Council”을 표시한다. 공식 index만으로는 발언의 세부 주장이나 정책 결론을 단정할 수 없다. 다만 이 제목은 AI가 더 이상 연구실과 제품 출시 행사만의 주제가 아니라, 공적 안전·국제적 책임·거버넌스의 언어로 논의되는 기술이라는 점을 상기시킨다.

개발자에게 이 맥락이 중요한 이유는 거버넌스가 별도 부서의 문서 작업으로 끝나지 않기 때문이다. 에이전트가 고객 데이터를 읽고, 코드를 수정하고, 외부 서비스에 내용을 보내고, 배포 또는 권한 변경을 제안할 수 있다면 책임은 API와 UI에 구현되어야 한다. 사용자는 무엇을 위임했는지 알아야 하고, 시스템은 어떤 범위에서 행동했는지 남겨야 하며, 고위험 행동은 적절한 순간에 멈춰야 한다.

### 책임 있는 실행의 네 가지 최소 조건

1. **의도 보존**: 사용자의 목표와 허용 범위를 기록한다. “보고서를 작성해 달라”는 요청이 고객 원문 전체를 외부 도구에 올릴 권한으로 변하면 안 된다.
2. **가시성**: 사용자는 내부 추론 전문을 볼 필요는 없지만, 현재 작업·이미 발생한 영향·다음 위험 행동은 이해할 수 있어야 한다.
3. **실질적 개입**: 승인 거부와 취소가 화면상의 장식이 아니라 큐, 하위 작업, 외부 요청에 실제로 전파되어야 한다.
4. **추적성과 복구**: 결과가 나빴을 때 실행 순서, 정책 판정, 영향 범위를 재구성하고 가능한 범위에서 되돌릴 수 있어야 한다.

이 네 조건은 AI에만 특수한 규칙이 아니다. 권한 있는 소프트웨어의 기본 품질이다. 다만 자연어 지시와 도구 실행이 연결되는 AI 제품에서는 목표가 바뀌고, 모델 출력이 비결정적이며, 장시간 실행이 일어나기 때문에 더 엄격하게 설계해야 한다.

### 제품 요구사항으로 번역하기

책임을 구현하려면 추상적인 “안전한 AI” 체크박스보다 구체적인 객체가 필요하다. `Task`에는 목표, 소유자, 완료 조건, 위험 등급, 허용 도구를 둔다. `Run`에는 시작 시점, 모델·도구 버전, 작업 공간, 정책 스냅샷을 둔다. `Step`에는 분석·수정·검증처럼 사용자가 이해할 수 있는 단계를 둔다. `Approval`에는 행동, 대상, 범위, 승인자, 만료 시각을 둔다. `Artifact`에는 diff, 테스트 결과, 보고서, 배포 후보를 둔다. `AuditEvent`는 이 객체들을 시간순으로 연결한다.

이런 분리는 과한 모델링이 아니다. “취소했는데 무엇이 이미 실행됐는가?”, “어느 승인으로 이 외부 전송이 허용됐는가?”, “테스트 실패 뒤 왜 배포가 계속됐는가?” 같은 실제 질문에 답하는 최소 구조다.

## Top News 2. GitHub의 AI·ML 채널: 개발자 AI는 워크플로 제품이 되어야 한다

GitHub의 공식 AI & ML 채널은 기초 개념부터 고급 기법, 실무 사례까지 AI·ML 관련 자료를 제공하며, GitHub Copilot에 관한 자세한 실무 안내는 공식 문서로 연결한다고 설명한다. 또한 GitHub Universe 2026이 10월 28–29일 샌프란시스코와 온라인에서 열린다고 예고한다. 이 정보는 단순한 행사 홍보 이상의 의미를 갖는다. 개발자 AI는 독립된 모델 데모가 아니라 저장소, 이슈, 코드 리뷰, CI, 보안 정책, 팀 협업이라는 기존 워크플로 위에서 가치가 발생한다.

코드를 한 번 생성하는 기능은 쉽게 비교된다. 반면 실제 팀이 원하는 것은 변경 범위를 파악하고, 기존 규칙을 지키며, 테스트 결과를 읽고, 실패 이유를 설명하고, 리뷰 가능한 산출물을 남기고, 필요한 순간에 사람에게 넘기는 흐름이다. 이 흐름이 없다면 뛰어난 코드 제안도 개발 환경에서는 신뢰를 얻기 어렵다.

### 챗 인터페이스보다 중요한 것은 작업 수명 주기다

개발자 에이전트의 사용자는 “로그인 오류를 고쳐 달라”고 말할 수 있다. 하지만 그 문장은 하나의 실행이 아니라 목표다. 에이전트가 저장소를 탐색한 뒤 인증 모듈 두 개를 수정하고, 테스트가 하나 실패해 중단한 과정은 별도의 실행이다. 사용자는 같은 목표로 다시 시도하거나, 다른 브랜치에서 재개하거나, 계획만 검토할 수 있다.

따라서 `Task`와 `Run`을 분리해야 한다. Task는 의도와 완료 조건을 보관하고, Run은 특정 커밋과 환경에서 발생한 한 번의 실행을 보관한다. 이 분리가 있으면 실패한 실행을 숨기지 않고, 재시도와 재개를 구별하며, 어떤 결과가 어느 환경에서 만들어졌는지 알 수 있다. 팀 환경에서는 특히 중요하다. 작업을 요청한 사람, 실행을 검토한 사람, 배포를 승인한 사람이 서로 다를 수 있기 때문이다.

### 개발자 도구의 상태 기계

다음 상태를 명시적으로 다루는 제품이 운영에 강하다.

| 상태 | 의미 | 사용자에게 보여 줄 정보 |
|---|---|---|
| `draft` | 목표는 있으나 실행 조건이 고정되지 않음 | 목표, 예상 범위, 아직 확정되지 않은 전제 |
| `planned` | 검토 가능한 계획이 생성됨 | 수정 후보, 검증 방식, 다음 승인 지점 |
| `running` | 도구 호출 또는 하위 작업이 진행 중 | 현재 단계, 작업 공간, 진행 중인 영향 |
| `waiting_for_input` | 안전하게 진행하려면 사용자 정보가 필요 | 질문, 선택지, 응답하지 않을 때의 상태 |
| `waiting_for_approval` | 구체적 행동에 대한 승인이 필요 | 대상, 범위, 만료, 되돌림 가능성 |
| `verifying` | 변경 뒤 테스트·검토·품질 게이트 수행 | 통과/실패 항목, 남은 위험 |
| `blocked` | 정책·자격 증명·의존성 문제로 진행 불가 | 차단 이유, 허용된 다음 행동 |
| `completed/cancelled/failed` | 종료 상태 | 산출물, 이미 발생한 영향, 재개 또는 복구 경로 |

상태는 화면 장식이 아니라 계약이다. 중복 이벤트가 왔을 때, 네트워크가 끊겼을 때, worker가 재시작될 때, 사용자가 취소했을 때 무엇이 바뀌는지 서버와 UI가 같은 의미로 해석해야 한다.

### 승인에는 사람이 읽는 요약과 기계가 검증하는 payload가 모두 필요하다

“외부 전송을 승인하시겠습니까?”라는 문구는 너무 넓다. 좋은 승인에는 대상 도메인, 데이터 분류, 파일 또는 레코드 수, 목적, 만료, 되돌림 가능성이 담긴다. 예를 들어 “export-job-42가 15분 동안 redacted-summary.csv를 승인된 저장소로 전송”처럼 행동·대상·범위·시간을 묶어야 한다. 실행기는 승인 화면의 설명을 신뢰하는 대신 실제 요청이 그 payload와 일치하는지 다시 검증해야 한다.

이 방식은 높은 위험 작업만 느리게 하고 낮은 위험 작업의 마찰을 줄인다. 읽기 전용 조회나 로컬 정적 분석은 자동으로 진행할 수 있다. 반면 외부 전송, 권한 변경, 프로덕션 배포, 삭제는 더 좁고 짧은 승인을 요구한다. 좋은 거버넌스는 모든 자동화를 막는 것이 아니라 위험에 맞는 통제 비용을 배치하는 일이다.

## Top News 3. Google AI의 묶음: 모델·연구·개발자 경험을 따로 설계하지 말 것

Google의 공식 AI 뉴스 채널은 “AI를 모두에게 유용하게 만들기 위한 작업”을 소개하며 Gemini App, Research, Developers, 최신 업데이트를 같은 정보 구조 안에 둔다. 이 구성 자체가 중요한 제품 신호다. AI 생태계는 연구 성과, 모델 API, 사용자 앱, 개발자 도구, 안전 정책이 따로 움직이는 것이 아니라 서로 영향을 주는 연결된 시스템이다.

개발 팀이 모델 API만 평가하면 실제 제품 위험을 놓치기 쉽다. 모델은 좋아도 프롬프트 관리가 불가능하거나, tool schema가 모호하거나, 비용이 예측되지 않거나, 운영 로그에 민감 정보가 쌓이거나, 실패 시 사용자가 다음 행동을 알 수 없으면 제품은 안정적으로 확장되지 않는다. 반대로 UI만 다듬어도 모델의 한계, 지연, 비결정성, 데이터 경계가 설계에 반영되지 않으면 신뢰를 잃는다.

### 하나의 AI 기능을 네 층으로 점검하라

**모델 층**에서는 정확도, 지연, 비용, 컨텍스트 한계, 안전한 거부, 버전 변경 영향을 측정한다. **도구 층**에서는 입력 schema, 출력 검증, 최소 권한, idempotency, timeout, 재시도 정책을 설계한다. **제품 층**에서는 목표 설정, 상태 표시, 승인 UX, 실패 설명, 산출물 검토를 만든다. **운영 층**에서는 데이터 보존, 관측성, 비용 경보, incident 대응, 회귀 평가, 롤백을 관리한다.

네 층 중 하나라도 비어 있으면 에이전트는 데모에서만 좋아 보일 가능성이 높다. 예를 들어 모델이 파일 수정을 잘해도 도구 층에 경로 제한이 없으면 범위가 넓어진다. 제품 층에 취소 결과가 없으면 사용자는 멈춘 줄 알지만 worker가 남아 있을 수 있다. 운영 층에 비용·오류 관측성이 없으면 프롬프트 변경 하나가 장애로 이어져도 원인을 찾기 어렵다.

### 변경 관리는 모델 교체보다 넓다

AI 제품의 행동은 모델 버전만으로 결정되지 않는다. 시스템 프롬프트, 검색·retrieval 구성, tool schema, 권한 정책, 실행 환경, 재시도 로직, 승인 UI가 모두 행동에 영향을 준다. 그러므로 모델이나 도구를 바꿀 때는 응답 품질만 비교하지 말고 다음을 함께 측정해야 한다.

- 고위험 도구 호출 비율과 승인 요청량이 바뀌는가?
- 경로·환경·수신 도메인 같은 범위 drift가 늘어나는가?
- 정책 차단의 오탐과 정상 업무 방해가 증가하는가?
- 취소와 재시도가 실제로 중복 side effect를 만들지 않는가?
- 비용·지연·오류율이 사용자 경험과 운영 예산을 넘지 않는가?

이 질문은 모델을 덜 쓰자는 뜻이 아니다. 모델의 개선을 실제 제품 안정성으로 연결하기 위한 배포 규율이다.

## Top News 4. AWS ML 채널이 상기시키는 것: AI는 배포되는 순간 운영 시스템이 된다

AWS의 공식 Machine Learning 채널은 AI 관련 기술과 서비스 정보를 제공한다. index의 세부 글을 이 글의 사실 근거로 확장하지는 않지만, 클라우드 환경의 관점은 분명하다. 모델 호출이 프로덕션 시스템에 들어가는 순간 AI는 애플리케이션, 네트워크, 자격 증명, 데이터 파이프라인, 모니터링, 비용 관리, 장애 대응의 일부가 된다.

많은 팀이 모델 선택과 프로토타입 제작에는 시간을 쓰지만, 실행 환경의 경계를 나중에 붙인다. 그러나 에이전트에서는 이 순서가 위험하다. 모델이 호출할 수 있는 도구, 사용할 수 있는 토큰, 접근 가능한 데이터, 나갈 수 있는 네트워크, 재시도 가능한 횟수는 모두 제품의 실제 권한을 구성한다. 프롬프트에서 “하지 마라”고 말하는 것만으로는 실행 권한을 줄일 수 없다.

### 운영에서 반드시 분리할 네 가지 경계

1. **데이터 경계**: 어떤 데이터 분류가 어떤 모델·리전·외부 서비스로 갈 수 있는지 정의한다. 로그와 trace도 데이터로 취급한다.
2. **도구 경계**: 읽기, 쓰기, 삭제, 외부 전송, 배포를 같은 권한으로 묶지 않는다. 도구별 allowlist와 입력 검증을 둔다.
3. **환경 경계**: 개발, staging, production의 자격 증명과 네트워크를 분리한다. staging의 승인으로 production을 실행하지 못하게 한다.
4. **시간 경계**: 장기 자격 증명과 무기한 승인을 피한다. 세션, approval, export URL, runner 권한에 만료를 둔다.

### 취소와 재시도는 기능이 아니라 안전 설계다

네트워크 환경에서는 요청의 결과가 모호할 수 있다. 클라이언트가 응답을 받지 못했더라도 서버는 이미 요청을 처리했을 수 있다. 이때 무작정 재시도하면 중복 배포, 중복 티켓 생성, 중복 전송이 발생한다. 외부 side effect마다 idempotency key, 작업 ID, 상태 조회 방법을 설계해야 한다.

취소도 마찬가지다. 취소 버튼을 누르면 새 작업 생성은 막을 수 있지만 이미 실행 중인 프로세스, 큐에 들어간 하위 작업, 외부 API 요청은 서로 다른 상태일 수 있다. 제품은 단순히 “취소됨”이라고 표시하지 말고 `요청됨`, `전파 중`, `확인됨`, `부분 취소`, `취소 불가`를 구별해야 한다. 사용자는 낙관적 메시지보다 이미 생긴 영향과 남은 확인 작업을 알아야 한다.

## 개발자에게 의미하는 것: 다음 스프린트에서 구현할 제어면

### 1. 권한을 역할이 아니라 행동·대상·시간으로 모델링하라

`admin`, `editor`, `viewer` 같은 역할은 출발점일 뿐이다. 에이전트 실행에서는 같은 editor도 특정 디렉터리의 문서는 바꿀 수 있지만 인프라 설정은 건드리면 안 될 수 있다. 같은 deploy 권한도 staging에는 가능하지만 production에는 change ticket과 짧은 승인 시간이 필요할 수 있다.

권한 정책을 `누가`만이 아니라 `무슨 행동을`, `어떤 대상에`, `어느 환경에서`, `언제까지` 수행할 수 있는지로 표현하면 제품과 보안팀이 같은 언어로 대화할 수 있다. 실행기 역시 이 조건을 매 도구 호출 직전에 확인해야 한다.

### 2. 사용자용 이벤트와 내부 telemetry를 분리하라

사용자에게는 “인증 모듈 두 파일을 분석 중”, “staging 테스트 18개 중 17개 통과”, “외부 전송은 아직 시작하지 않음” 같은 의사결정 가능한 정보를 보여 준다. 내부 운영에는 request ID, 모델·도구 버전, 정책 규칙 ID, 지연, 비용, 재시도, 오류 코드를 남긴다. 두 이벤트 흐름은 연결되어야 하지만 같은 보존 기간이나 접근 권한을 가질 필요는 없다.

이 분리는 개인정보와 디버깅 양쪽에 도움이 된다. 원시 프롬프트와 명령 출력 전체를 무기한 보관하는 대신, 필요한 구조화된 증적을 남기고 민감한 원문은 최소화·마스킹·짧은 보존으로 다룬다. 감사 로그 역시 공격 표면이라는 사실을 잊으면 안 된다.

### 3. 계획은 안전의 증명이 아니라 변경 감지의 기준이다

계획 모드는 사용자가 방향을 검토하는 데 유용하다. 하지만 계획이 상세하다고 그 뒤의 모든 행동이 자동 승인되는 것은 아니다. 실행 중 의존성, 파일 구조, 권한, 도구 응답이 달라질 수 있기 때문이다. 계획에는 목표, 예상 산출물, 접근 범위, 도구 종류, 검증 방법, 불확실성, 다음 승인 지점을 적고, 실제 행동이 크게 달라지면 drift로 감지해 재계획 또는 재승인을 요구해야 한다.

### 4. 실패 분류를 UX에 노출하라

모든 오류를 “다시 시도해 주세요”로 표시하면 사용자는 위험한 중복 실행을 하게 된다. `retryable`은 제한된 재시도와 backoff를, `needs_input`은 구체적인 질문을, `policy_blocked`는 허용된 대안과 담당 경로를, `partial_effect`는 이미 일어난 행동을, `irreversible_effect`는 즉시 대응을 보여 줘야 한다. 실패를 숨기지 않는 에이전트가 장기적으로 더 신뢰받는다.

결국 지금 팀이 만들어야 할 핵심은 더 화려한 챗 창이 아니다. **의도(Intent), 가시성(Visibility), 개입(Intervention), 추적성(Traceability)**을 갖춘 실행 제어면이다. 그 위에서만 모델의 성능이 신뢰할 수 있는 업무 가치로 바뀐다.

## 더 깊이 보기 1: 에이전트 제어면의 참조 아키텍처

제어면이라는 표현이 추상적으로 들릴 수 있다. 실제 시스템에서는 다음 다섯 층으로 나누어 생각하면 구현과 책임 분담이 쉬워진다.

첫 번째는 **Intent layer**다. 여기에는 사용자가 요청한 목표, 완료 조건, 허용된 범위, 소유자, 우선순위, 민감도 등급이 있다. 자연어 입력은 편리하지만 그대로 실행 계약이 되면 안 된다. 시스템은 “무엇을 원하는가”와 “무엇을 해도 되는가”를 구분해 저장해야 한다. 예를 들어 “월간 인사 보고서를 준비해 달라”는 의도는 자료를 요약하고 초안을 만드는 것을 뜻할 수 있지만, 전 직원 원본 데이터를 외부 모델에 전송하거나 수신자에게 자동 발송하는 것까지 뜻하지는 않는다.

두 번째는 **Planning layer**다. 에이전트는 의도를 실행 가능한 단계와 예상 영향으로 바꾼다. 좋은 계획은 단순한 할 일 목록보다 구체적이다. 읽을 데이터, 쓸 파일, 사용할 도구, 외부 네트워크 접근 여부, 테스트와 검증 방법, 중단 조건, 사람의 승인이 필요한 지점을 표시한다. 계획은 사용자에게 이해 가능한 요약이면서 정책 엔진이 검토할 수 있는 구조화된 입력이어야 한다. 계획이 실제 실행과 달라질 때는 “더 진행”이 아니라 범위 변경으로 기록한다.

세 번째는 **Policy layer**다. 이 층은 모델의 판단과 독립적으로 행동을 허용·제한·승인 대기로 보낸다. 프롬프트의 지시는 도움 되지만 보안 경계가 아니다. 정책은 도구 이름, 대상 경로, 데이터 분류, 수신 도메인, 환경, 사용자 역할, 시간, 세션 신뢰도 같은 검증 가능한 조건을 본다. 정책 결정에는 rule ID와 사유를 남겨야 한다. 그래야 사용자는 왜 막혔는지 이해하고, 운영팀은 어느 규칙이 정상 업무를 방해하는지 개선할 수 있다.

네 번째는 **Execution layer**다. 실제 파일 작업, API 호출, 브라우저 작업, 배포, 데이터베이스 변경은 이 층에서 일어난다. 실행기는 짧은 자격 증명, 환경별 네트워크 경계, 입력 schema 검증, timeout, rate limit, idempotency key를 가져야 한다. 중요한 점은 실행기가 계획이나 UI를 맹신하지 않는다는 것이다. 실행 직전에도 권한과 approval payload를 다시 검증해야 한다. 이 마지막 검증이 없으면 승인 화면과 실제 요청 사이의 틈이 공격 또는 버그의 통로가 된다.

다섯 번째는 **Evidence layer**다. 실행 결과, 테스트, 승인, 정책 판정, 취소, 오류를 재구성 가능한 형태로 남긴다. 증적은 모든 원문을 저장한다는 뜻이 아니다. 데이터 최소화가 필요하다. 누가 어떤 행동을 어떤 대상에 수행했는지, 어떤 정책과 승인으로 허용됐는지, 결과와 영향이 무엇인지가 우선이다. 민감한 원문은 마스킹·암호화·짧은 보존·별도 접근 통제를 적용한다.

이 구조에서 모델은 Planning layer의 강력한 구성 요소이지만 전체 시스템의 단일 통제자가 아니다. 모델이 더 좋아져도 Policy·Execution·Evidence 층을 대체하지는 못한다. 반대로 이 층들이 단단하면 모델을 교체하거나 여러 모델을 병행해도 제품의 안전 계약을 유지하기 쉬워진다.

## 더 깊이 보기 2: 위험도 기반 자동화 매트릭스

모든 AI 행동에 동일한 승인을 붙이면 사용자는 피로해지고 결국 무시한다. 아무 승인도 붙이지 않으면 에이전트의 편의가 권한 과잉으로 변한다. 현실적인 해법은 영향도와 가역성을 기준으로 자동화 수준을 나누는 것이다.

| 작업 특성 | 권장 기본값 | 예시 | 필수 증적 |
|---|---|---|---|
| 낮은 영향·높은 가역성 | 자동 실행 + 결과 요약 | 문서 초안, 로컬 정적 분석, 임시 파일 생성 | 실행 ID, 산출물, 삭제 가능 여부 |
| 중간 영향·가역성 있음 | 세션 범위 승인 + 검증 게이트 | 제한된 코드 수정, staging 테스트, 내부 요약 | 변경 범위, 테스트 결과, 승인 시각 |
| 높은 영향·가역성 있음 | 행동별 승인 + 환경 제한 | 제한된 외부 공유, staging 배포, 권한 변경 제안 | 대상, 만료, 정책 판정, 롤백 절차 |
| 높은 영향·낮은 가역성 | 다중 승인 + 독립 검증 | production 배포, 고객 데이터 삭제, 법적·금융 실행 | 승인자, payload hash, 실행 결과, 사후 검토 |

이 매트릭스는 조직을 느리게 만드는 장치가 아니다. 낮은 위험 영역에서는 자동화를 넓히고, 높은 위험 전환에서만 사람의 판단과 검증 비용을 집중하는 방법이다. 시간이 지나면 팀은 실제 incident, 승인 거부율, rollback 성공률, 사용자 불만을 바탕으로 분류를 조정할 수 있다. 중요한 것은 위험 등급이 문서 속 숫자가 아니라 정책과 UI의 동작으로 이어지는가다.

## 더 깊이 보기 3: 팀 리더가 보는 운영 지표

AI 기능의 성공을 “모델을 몇 번 호출했는가” 또는 “자동화가 몇 건 성공했는가”로만 보면 위험하다. 높은 완료율은 위험한 작업을 충분히 차단하지 못한 결과일 수도 있고, 낮은 완료율은 좋은 정책이 실제 문제를 발견한 신호일 수도 있다. 운영 지표는 품질, 안전, 비용, 사람의 부담을 함께 봐야 한다.

품질 지표에는 Task 완료율, 재작업률, 사용자 수정량, 테스트 통과율, 산출물 채택률이 들어간다. 안전 지표에는 정책 차단율, 고위험 행동의 승인 거부율, 범위 drift, 취소 성공률, 부분 영향 사건 수가 들어간다. 운영 지표에는 p50·p95 지연, tool 오류율, 재시도 횟수, 큐 적체, 환경별 비용이 들어간다. 사람의 부담을 보는 지표에는 승인당 평균 판단 시간, 같은 유형의 반복 승인 수, 차단 사유를 이해하지 못한 비율, incident 후 복구 시간이 들어간다.

이 지표들은 서로 연결해서 해석해야 한다. 예를 들어 승인 거부율이 높다면 사용자가 지나치게 보수적인 것이 아니라 계획이 모호하거나 승인 시점이 늦다는 뜻일 수 있다. 정책 차단율이 갑자기 증가하면 공격 증가일 수도 있지만 tool schema 변경이나 정상 경로의 설정 오류일 수도 있다. 비용이 늘어났다면 모델 성능 저하가 아니라 재시도 루프나 불필요한 컨텍스트 전달이 원인일 수 있다. 관측성의 목적은 숫자를 만드는 것이 아니라 원인을 빠르게 좁히는 것이다.

## 더 깊이 보기 4: 실제 업무 시나리오 세 가지

### 시나리오 A — 코드 수정과 테스트

사용자가 “로그인 오류를 고쳐 달라”고 요청한다. 나쁜 설계에서는 에이전트가 저장소 전체를 탐색하고 관련 없는 설정까지 수정한 뒤, 테스트 실패를 무시하고 커밋을 시도한다. 화면에는 `working`만 표시되고 취소 후 무엇이 바뀌었는지 알 수 없다.

좋은 설계에서는 Task에 완료 조건을 기록한다. Run은 특정 커밋과 브랜치에서 시작한다. 에이전트는 `인증 흐름 분석`, `src/auth 범위 수정 제안`, `단위 테스트 실행`, `diff 검토 대기`처럼 의미 있는 이벤트를 보낸다. 파일 쓰기는 허용 경로 안에서만 수행하고, 테스트 실패 뒤에는 실패 원인과 선택지를 보인다. 커밋과 push는 별도 고위험 행동이며, 취소 시 변경 파일 목록과 테스트 상태가 artifact로 남는다.

### 시나리오 B — 업무 데이터 요약과 외부 공유

“이번 주 고객 피드백을 요약해 파트너에게 보내 달라”는 요청에는 데이터 읽기, 분류, 요약, 외부 전송이 섞여 있다. 좋은 시스템은 이 행동을 한 권한으로 묶지 않는다. 내부 데이터 읽기의 범위를 제한하고, 요약 초안은 내부 artifact로 먼저 만든다. 전송 직전에는 수신자, 도메인, 첨부물, 데이터 등급, 보존 경로를 명시한 승인을 요구한다. 수신자가 추가되거나 파일이 바뀌면 기존 승인은 무효가 된다.

### 시나리오 C — 장시간 배포와 모바일 개입

에이전트가 staging 배포, 헬스 체크, 롤백 계획을 진행하는 동안 사용자는 이동 중일 수 있다. 모바일 제어면은 진행 상황과 승인 요청을 보여 줄 수 있지만, 작은 화면의 `승인` 버튼이 전체 production 권한을 뜻해서는 안 된다. 대상 환경, 버전, 현재 지표, rollback 가능 여부, 승인 만료를 표시하고 실행기는 payload를 다시 검사해야 한다. runner가 오프라인이면 “원격 보기만 끊겼는지”와 “실행이 멈췄는지”를 분리해 알려야 한다.

## 오늘 바로 적용할 운영 원칙 12가지

1. 목표(Task)와 한 번의 실행(Run)을 같은 ID로 관리하지 않는다.
2. 자연어 지시를 고권한 실행으로 바로 연결하지 않는다.
3. 보기, 지시, 승인, 취소, 관리 권한을 하나의 역할로 섞지 않는다.
4. 승인은 행동·대상·범위·만료·정책 버전에 바인딩한다.
5. 모든 외부 side effect에 idempotency key와 결과 조회 경로를 둔다.
6. 취소 요청과 실제 취소 확인을 구분한다.
7. 재개 전에는 브랜치, 환경, 정책, 승인 만료, 기존 diff를 비교한다.
8. 사용자용 이벤트와 내부 telemetry의 데이터 최소화 규칙을 분리한다.
9. 로그에도 마스킹, 접근 제어, 보존 기간, export 감사를 적용한다.
10. 모델·프롬프트·도구 변경을 운영 변경으로 취급하고 회귀 평가한다.
11. 정책 차단은 이유와 허용된 대안을 설명해야 한다.
12. incident와 near-miss를 다음 릴리스의 eval과 runbook에 반영한다.
