# AI Daily News | 2026년 11월 27일

**확인 시점: 2026년 11월 27일 11:30 KST.** 오늘은 화려한 범용 모델 발표보다 실제 AI 시스템의 **입력·검색·협업·측정**을 잇는 네 가지 공식 자료를 읽는다. NVIDIA는 11월 26일 문서 구조 추출 모델 Nemotron 3.5 Parse의 합성 학습 데이터, 미세조정 절차와 DFlash2 추론 가속 결과를 공개했다. 네 자료의 성격은 다르다. NVIDIA 글은 **모델·학습·서빙 레시피**, Google 글은 **관리형 검색 서비스 안내**, Hugging Face 글은 **제한된 과제의 학습 실험**, ggml-org 글은 **재현 가능한 성능 관찰 도구**다. 서로의 결과를 직접 비교하는 벤치마크가 아니다. 그러나 제품을 만드는 팀의 작업 순서로 놓으면 연결된다. 문서의 표·차트·읽기 순서를 보존해 추출하고, 인덱스에서 관련 구간을 찾아, 에이전트가 근거를 공유하며 답을 만들고, 그 모든 단계의 지연과 비용을 측정해야 한다. 이 글은 발표문이 입증한 범위와 현장에서 검증할 영역을 구분한다.

## 배경 — 문서형 AI는 하나의 모델 호출이 아니다

사람이 보고서를 읽을 때는 페이지 번호, 표의 행·열, 그래프 축, 문맥에 붙은 각주가 자연스럽게 함께 보인다. 기계에는 그렇지 않다. PDF에는 읽기 순서가 뒤섞인 글자 조각이 있을 수 있고, 스캔에는 문자가 이미지로만 남아 있다. 엑셀에서는 보이는 값과 수식이 다르며, 한 탭의 열 제목이 다른 탭의 항목을 규정한다. 동영상에서는 화면에 나온 글자와 음성에서 말한 내용이 서로 다른 신호다. 문서 AI가 실패하는 지점은 최종 답변 모델의 추론 이전, **원본을 어떤 중간 표현으로 바꾸느냐**에서 이미 결정되기 쉽다.

흔한 파이프라인은 원본 저장 → 렌더링·파싱 → 구조화 → 구간 분할 → 임베딩 → 검색 → 재정렬 → 근거 확인 → 답변이다. 각 화살표에서 정보가 손실될 수 있다. 표의 ‘2025’와 ‘2026’ 열이 바뀌면 추출 문장이 문법적으로 그럴듯해도 실적 해석은 정반대다. 페이지와 구간의 연결을 잃으면 검색 결과가 좋아 보여도 사용자는 원문으로 되돌아가 검증할 수 없다. 근거의 일부만 모델에 보여주면 범위를 넘는 결론을 낼 수 있다. 운영자가 보고 싶은 것은 최종 정확도 하나가 아니라 단계별 **충실도·검색율·인용 일치율·완료율·지연·비용**이다.

오늘 공개된 자료는 이 파이프라인의 서로 다른 구간을 다룬다. NVIDIA는 페이지 이미지에서 구조화 결과를 만드는 **앞단**을, Google은 저장된 파일을 검색 가능한 구간으로 바꾸고 위치를 붙여 돌려주는 **중간단**을 다룬다. Hugging Face는 정보가 여러 주체에 흩어졌을 때 통신이 과제를 실제로 돕는지라는 **협업단**을, ggml-org는 모델을 실행할 때 입력 처리와 출력 생성의 **성능단**을 살핀다. 네 가지를 한 공급자의 완성형 제품처럼 연결하면 안 된다. 아래의 결합 시나리오는 제품 발표가 아니라 편집자가 제안하는 검증 설계다.

## Top News 1 — NVIDIA, 문서 구조 추출을 데이터·보상·서빙까지 확장

[NVIDIA의 11월 26일 기술 글](https://huggingface.co/blog/nvidia/building-on-nemotron-35-parse-open-data-fine-tunin)은 기존 Nemotron 3.5 Parse 모델 위에 새로 공개한 자료를 설명한다. 모델은 페이지 이미지를 입력으로 받아 텍스트, 표, 차트, 읽기 순서, 제목·문단 등 의미 클래스와 바운딩 박스를 구조화해 돌려준다. [공식 모델 카드](https://huggingface.co/nvidia/Nemotron-3.5-Parse)는 스캔 문서와 렌더링한 PDF, 슬라이드, 양식 등에 적용할 수 있고 Markdown·HTML·JSON 형태로 결과를 내보낼 수 있다고 안내한다. 중요한 점은 **페이지 이미지 모델**이라는 것이다. PDF 바이트를 넣으면 문서 전체의 표 연결과 페이지 간 순서를 자동으로 복원한다는 뜻이 아니다. 모델 카드의 PDF 예시는 각 페이지를 먼저 이미지로 렌더링하며, 페이지 간 이어지는 표는 별도 처리 대상이라고 명시한다.

### 왜 ‘글자만 읽기’로는 부족한가

OCR의 문자 오류율이 낮아도 문서 질의응답이 틀릴 수 있다. 예를 들어 두 열짜리 실적 표에서 숫자 `18.2`를 정확히 읽었더라도 ‘매출’ 열 대신 ‘영업이익’ 열에 붙이면 의사결정은 잘못된다. 차트 막대에는 숫자가 적혀 있지 않고 눈금과 높이로 값을 추정해야 할 수 있다. 이미지 속 표제와 각주를 섞거나, 차트 범례 색을 잘못 연결하면 그럴듯한 허위 데이터가 생성된다. 따라서 추출 품질은 텍스트 인식, 구조 인식, 위치 인식, 관계 복원의 합이다. NVIDIA는 이 세부 요소를 학습시키기 위해 정답이 알려진 합성 자료를 크게 늘렸다고 설명한다.

이번 공개는 [Synthetic Charts V1](https://huggingface.co/datasets/nvidia/Synthetic-Charts-V1) 약 998만 예시, [Synthetic Tables V1](https://huggingface.co/datasets/nvidia/Synthetic-Tables-V1) 100만 예시, [OCR Synthetic Multilingual v2](https://huggingface.co/datasets/nvidia/OCR-Synthetic-Multilingual-v2) 약 790만 예시다. 차트 자료는 렌더링된 그림과 범주·계열·수치 주석을, 표 자료는 행·열·헤더 관계를 보존하는 목표를, OCR 자료는 다양한 글꼴·레이아웃·언어의 페이지와 모델 출력 형식에 맞는 목표를 제공한다. 큰 수량이 곧 다양한 실제 계약서·의무기록·한국어 공문에 대한 품질을 보장하지는 않는다. 합성 분포가 실제 사용자의 흐린 사진, 도장, 비정형 손글씨, 줄바꿈 규칙과 얼마나 겹치는지 따로 확인해야 한다.

### SFT와 RLVR가 각각 맡는 일

NVIDIA가 설명한 학습 절차는 두 단계다. 지도 미세조정(SFT)은 이미지와 정답 구조의 쌍을 보여 주어 텍스트·레이아웃·표·차트·다국어 문서를 어떻게 표현할지 가르친다. 그 다음 검증 가능한 보상에 기반한 강화학습(RLVR)은 뽑은 구조가 맞는지, 출력이 반복 없이 끝났는지 등 평가 가능한 기준을 활용해 **정확성과 완료의 일관성**을 높인다. 같은 페이지에 표현상 여러 타당한 직렬화가 가능하므로 정답 문자열 하나만 강제하는 방법과는 다르다. 그렇다고 보상 설계가 자동으로 쉬운 것은 아니다. 바운딩 박스가 맞아도 표의 관계가 틀리거나, 문자열은 맞지만 출처 위치가 틀릴 수 있다. 무엇을 보상하는지에 따라 모델이 실제 업무에는 중요하지 않은 형식만 최적화할 수도 있다.

[NVIDIA의 측정 노트](https://huggingface.co/datasets/nvidia/Nemotron-Parse-Blog-Assets/blob/main/measurement-notes.md)는 통제된 개발 체크포인트 비교에서 전체 점수가 SFT 66.24에서 GRPO 후 71.38로 올랐다고 밝힌다. 표 점수는 75.04에서 80.22, 차트는 47.86에서 52.01이었다. 반복 출력 플래그는 2,078페이지 중 126에서 29로, 9,000토큰 상한에 걸린 출력은 185에서 35로 줄었다. 여기서 반복 플래그는 일반적인 ‘환각률’ 측정이 아니며, 상한에 닿은 페이지 수는 출력 완결성의 한 지표다. 이 비교는 **동일 조건의 개발 체크포인트**에 관한 것이며 모델 카드의 최종 공개 모델 점수 75.20과 혼동하면 안 된다. 후자의 값은 triple-pass 구성을 포함한 별도 보고 비교다.

이 숫자를 제품에 적용할 때는 분모와 측정 범위를 먼저 써야 한다. 2,078페이지의 점수 개선이 실제 고객 문서의 성능 개선을 직접 예측하지 않는다. 특정 언어, 표 디자인, 축 단위, 글꼴 크기별로 층화하면 평균 뒤에 숨은 실패가 드러난다. 반복이 줄어도 잘못된 금액을 매끈하게 출력할 수 있다. 반대로 단순한 서식 오류가 표 점수에는 크게 반영되더라도 사용자의 질문에는 영향이 작을 수 있다. 위험이 큰 업무에서는 숫자와 단위, 행·열, 원본 위치를 별도로 확인하는 항목별 평가가 필요하다.

### 추론 가속은 어떤 조건에서 나온 수치인가

문서 파서는 페이지 하나에 긴 구조 출력을 생성한다. NVIDIA는 이미지 전처리를 고정 캔버스에서 동적 직사각형 입력으로 바꾸고, 압축한 시각 토큰을 디코더의 접두부로 제공하며, 그룹화 쿼리 어텐션을 사용했다고 설명한다. 추가로 작은 초안 모델인 DFlash2가 최대 32토큰을 제안하고 원본 모델이 한 번에 검증하는 speculative decoding을 제공한다. 발표 자료는 32토큰 구성에서 평균 약 14개 초안 토큰이 받아들여졌다고 한다. 이때 32개를 항상 한 번에 채택한다는 뜻이 아니다. 채택률과 초안 모델의 연산 부담이 결합돼 실제 성능이 결정된다.

측정 노트에 따르면 **단일 H200, BF16, 같은 2,078페이지의 native single-pass 처리량**에서 동시성 512일 때 Parse 2.0은 약 2.98페이지/초, Parse 3.5의 speculative decoding 없는 구성은 약 13.48페이지/초, DFlash2 구성은 약 20.44페이지/초다. 동시성 1에서는 Parse 3.5 기본 0.5385페이지/초와 DFlash2 4.1042페이지/초로 발표됐다. 이는 각 방식의 고유 프롬프트·호환 런타임을 사용하는 비교이며 생성 결과 길이가 다를 수 있다. 모델 시작, 이미지 로딩, 워밍업, 직렬화, HTTP는 측정에 포함하지 않았다. 따라서 이 숫자를 곧바로 사용자 요청당 종단 간 지연으로 읽으면 안 된다. 배치 크기, 페이지 길이, 렌더링 시간, 결과 저장, 네트워크 지연이 들어간 자체 측정이 필요하다.

NVIDIA는 어려운 표·차트에 대해 전체 페이지를 한 번 읽은 뒤 해당 영역만 잘라 다시 읽는 double-pass, 더 자세한 탐지·재추출을 하는 triple-pass도 제시한다. 공식 글은 공개 참조 평가에서 single-pass 대비 double-pass와 triple-pass가 각각 ParseBench 점수 2.18과 2.46을 추가한다고 설명한다. 품질 증분이 가속의 장점을 얼마나 소모하는지는 문서 종류와 동시성에 따라 달라진다. 모든 페이지를 세 번 읽는 정책보다는 **어려운 페이지를 판별해 선택적으로 재처리하는 조건**을 설계하는 편이 낫다는 것이 편집상의 제안이다. 이것은 NVIDIA가 보증한 최적 정책이 아니다.

### 도메인 적응 사례가 보여 주는 것과 보여 주지 않는 것

NVIDIA의 미세조정 레시피는 치과 차트인 odontogram을 사용하는 합성 양식 사례를 들었다. 기본 모델은 인쇄된 치아 번호를 읽지만 시술 표의 의도된 관계를 놓쳤고, SFT 후 여섯 행을 맞춘 사례 이미지가 제시된다. 같은 합성 생성기에서 만든 **보류된 256장 양식**의 측정에서는 sampled pass@1이 기본 모델 0.00%, SFT 후 95.85%, RLVR 후 96.58%라고 한다. pass@1은 여덟 번 중 한 번만 성공하면 되는 지표가 아니라 한 번 샘플링했을 때의 추정 성공률이다. 성공 조건도 자연스러운 종료, 정확한 차트 내용, 정규화한 페이지 텍스트의 무오류 등 엄격한 정의가 붙어 있다.

큰 개선이 흥미로운 이유는 모든 치과 양식에 바로 적용된다는 약속 때문이 아니다. **정확한 이미지·라벨 쌍과 검증기**가 있을 때 좁은 도메인의 구조를 모델에 가르칠 수 있다는 설계 예시이기 때문이다. 실제 의료 문서에는 다양한 병원 서식, 손글씨, 수기 수정, 기호가 있어 동일 생성기의 합성 보류 집합보다 훨씬 어렵다. 운영 검증에서는 생성 방식이 다른 독립 양식과 실제 데이터의 비식별 샘플을 분리해 측정하고, 안전성과 개인정보 처리를 함께 검토해야 한다. 고객용 문서에 그대로 연결하려면 모델의 사용 조건과 원격 코드 실행 요구사항, 모델·데이터 버전 고정도 확인해야 한다.

## Top News 2 — Google Agent Retrieval, 파일에서 페이지·시간 인용이 있는 검색 결과까지

[Google 개발자 블로그의 11월 24일 안내](https://developers.googleblog.com/from-files-to-cited-answers-in-one-api-call-managed-ingestion-and-searchdocuments-in-agent-retrieval/)는 Agent Retrieval(이전 Vector Search 2.0)의 **관리형 수집**과 `SearchDocuments`를 설명한다. 기존의 검색 증강 생성(RAG)은 파일을 읽고, 청크로 나누고, 임베딩을 만들고, 벡터 저장소 스키마를 맞추고, 검색·재정렬을 결합하는 작업이 필요했다. 새 공개 프리뷰는 Cloud Storage의 파일을 데이터 스토어에 가져오면 파싱·분할·임베딩·색인을 관리형으로 처리하고, 데이터 스토어와 텍스트 질의를 지정하는 검색 호출에서 관련 문서 구간을 반환한다. 이때 문서 결과에는 페이지 범위, 비디오 결과에는 시작·종료 시각이 붙는다.

개발자가 직접 만든 파이프라인보다 항상 좋다는 주장은 아니다. 관리형 서비스는 반복적인 배관을 줄이지만, 분할 방식과 자료 접근 권한, 데이터가 바뀌었을 때 재색인 시점, 검색 결과의 충분성은 여전히 설계할 문제다. Google 글도 기반 Collection을 직접 검색하는 길을 남겨 둔다. 복잡한 필터나 특수 임베딩 전략이 필요하면 한 단계 아래로 내려갈 수 있다는 뜻이다. 서비스가 제공하는 ‘한 번의 검색 호출’은 **수집·인덱싱 전체가 한 번의 호출로 즉시 끝난다**는 뜻이 아니다. 가져오기는 장시간 실행 작업이고, 문서 수와 비디오 길이에 따라 시간이 걸린다.

### ‘출처가 있는 결과’와 ‘정답’은 다르다

문서 검색 결과의 페이지 범위는 답변을 검증할 수 있게 하는 중요한 메타데이터다. 그러나 검색 단계가 반환한 페이지가 실제 정답을 포함하는지, 모델이 그 페이지를 올바로 해석했는지, 인용문과 숫자가 정확히 일치하는지는 별도 문제다. 페이지 68을 달고도 2022년의 매출을 2023년 값이라고 쓰면 출처 표식이 오류를 치유하지 않는다. 영상의 60–80초 구간이 반환됐더라도 모델이 그 구간에 없는 발언을 요약할 수 있다. 따라서 제품의 ‘근거 있는 답’은 최소한 **검색 결과의 위치 정확성 → 결과 텍스트·이미지의 의미 정확성 → 답변 문장의 인용 일치성**이라는 세 관문을 지나야 한다.

Google 글의 예시는 18개 Alphabet 투자자 PDF를 공개 Cloud Storage 버킷에서 약 9분 만에 페이지 인용 가능한 검색 결과로 바꾸고, 약 19분짜리 비디오를 0.3–0.5초의 질의 응답 검색 결과로 찾았다고 설명한다. 이 수치는 제품의 일반 SLA가 아니라 글에서 제시한 **특정 예시 실행**이다. 동영상 두 데이터 스토어에 가져오기는 글의 실험에서 20–45분 걸렸다. 수집 시간과 검색 시간은 다른 지표이며 섞어서는 안 된다. 파일의 크기·영상 해상도·리전·동시 작업 수·색인 상태가 달라지면 값도 달라진다.

### 분할 방식이 인용의 모양을 바꾼다

Google의 설명은 문서에 기본 청크 분할과 페이지 분할을 구별한다. 청크 분할은 텍스트를 대략 100–500토큰 단위로 나누며 레이아웃 파싱과 함께 표·제목을 탐지할 수 있다. 페이지 분할은 한 페이지를 하나의 구간으로 만든다. 두 방식 모두 페이지 정보를 기록할 수 있지만, 인용의 정밀도와 검색 단위가 달라진다. 한 문단에 질문의 답이 집중된 문서라면 작은 청크가 효율적일 수 있다. 한 페이지의 그림과 각주를 함께 해석해야 하면 페이지 단위가 나을 수 있다. 다만 한 페이지의 위·아래에 전혀 다른 주제가 있다면 페이지 단위 검색은 모델에 불필요한 내용도 보낸다.

사용자는 ‘몇 페이지에서 찾았는가’와 ‘몇 페이지를 읽었는가’를 구분해야 한다. 검색 결과가 68페이지를 가리킨다면 그 페이지에서 바로 답을 작성하기보다 원문과 주변 페이지, 표의 머리글을 확인할 필요가 있다. 특히 연간 보고서의 표는 여러 페이지에 걸쳐 이어질 수 있다. 세그먼트가 페이지 범위를 기록하더라도 잘린 표의 열 이름이 앞 페이지에만 있으면 해당 구간만으로 답을 확정하기 어렵다. 검색 API가 반환한 근거 후보와 최종 인용의 검증은 다른 단계다.

### 비디오는 보이는 것과 들리는 것을 따로 생각해야 한다

관리형 비디오 수집은 영상을 일정 시간 창으로 나누고 각 구간을 검색 가능하게 만든다. 공식 글은 10–20초의 짧은 창이 특정 장면의 정확한 시각을 찾는 데, 최대 80초의 긴 창이 주제 검색에 유리할 수 있다고 설명하며 기본 30초를 제시한다. 짧으면 문맥이 잘리고, 길면 찾은 구간의 위치가 흐려진다. 동영상에서는 화면과 음성이 서로 다른 증거가 된다. 공식 예시에서 `audio_mode`를 켜면 첫 번째 오디오 트랙을 화면과 함께 임베딩해 화자가 말한 내용을 찾을 수 있고, 끄면 기본적으로 화면 프레임만 검색한다. 화면에 연사가 보이는 장면에서 특정 발언을 찾으려면 오디오 사용 여부가 검색 성패를 바꿀 수 있다.

이 사실로부터 ‘자막이 필요 없다’는 말이 모든 접근성·감사 요구를 대체한다고 결론낼 수는 없다. 음성 검색이 가능하더라도 실제 답변의 인용문을 검수할 때는 녹음 품질, 다중 화자, 언어, 잘린 구간을 봐야 한다. 설명하는 장면이 화면 밖에서 일어나거나 영상에 무음 구간이 많으면 영상 검색 결과의 의미도 달라진다. 구간의 시작·종료 시각을 보존하고 사용자에게 원본으로 이동하는 경로를 제공해야 사후 검증이 가능하다.

### 프리뷰를 운영 설계에 반영하는 방법

[Google 공식 문서](https://docs.cloud.google.com/gemini-enterprise-agent-platform/build/vector-search-2/query-search/search-data-stores)는 해당 기능을 **Pre-GA 공개 프리뷰**로 표시한다. 블로그 기준 제공 리전은 `us-east4`와 `europe-west4`, 데이터 스토어와 검색 API는 REST `v1beta`로 설명되어 있다. 문서 페이지의 예시와 버전 표기가 변경될 수 있으므로 구현 직전 현재 API 문서를 재확인해야 한다. 공식 글은 수집 자체의 별도 요금이 공개 프리뷰 기간에는 없지만 GA부터 청구 예정이며, 기반 Collection은 표준 Agent Retrieval 요금 대상이라고 말한다. ‘무료’라고 간단히 표현하면 잘못이다.

권한도 점검 대상이다. 공식 안내는 Agent Retrieval 서비스 에이전트에 파일을 읽을 수 있는 역할을 부여하도록 설명한다. 파일을 업로드한 계정의 권한과 서비스 에이전트 권한은 다르다. 백업 버킷과 생산 버킷을 혼동하면 서비스가 불필요한 파일까지 읽을 수 있다. 삭제 시에는 데이터 스토어만 지워 기반 Collection이 남는 경우를 경고한다. 실험에서 과금과 데이터 잔존을 관리하려면 **생성·재가져오기·삭제·권한 회수**를 하나의 수명주기로 다뤄야 한다.

### NVIDIA 모델과 Google 서비스의 관계

두 발표는 직접 결합 상품이 아니다. NVIDIA Parse는 페이지 이미지에서 구조를 추출하는 모델 및 레시피다. Google의 관리형 수집은 파일을 검색 가능한 데이터 객체로 바꾸는 서비스다. Google 서비스가 내부적으로 Nemotron을 사용한다는 발표는 없다. 두 방법을 비교하려면 ‘파서를 직접 소유해 도메인 특화할 것인가’와 ‘수집을 관리형 서비스에 맡길 것인가’라는 아키텍처 선택으로 다뤄야 한다. 직접 파서는 추출 형식·모델·배포 위치를 더 세밀히 통제할 수 있지만 렌더링, 인덱싱, 운영을 직접 맡아야 한다. 관리형 수집은 배관을 줄이지만 제공 리전·프리뷰 조건·서비스가 제공하는 분할 방식을 따라야 한다.

## Top News 3 — Hugging Face, 여러 에이전트가 ‘정말 함께 일했는가’를 측정하다

[Hugging Face의 11월 26일 기술 글](https://huggingface.co/blog/training-swarms)은 에이전트를 여럿 띄우는 것과 실제 협업의 효과를 구분한다. 네 명의 논리적 에이전트가 각각 1–99의 정수 하나만 알고 있으며, 팀 중 적어도 한 명이 네 숫자의 정렬된 전체 목록을 제출하면 성공이다. 개별 에이전트는 다른 세 숫자를 처음부터 볼 수 없으므로 이 과제는 **정보를 서로 주고받는 행위**가 필요하다. 네 개의 서로 다른 모델을 학습한 것도 아니다. 각자 별도 문맥을 가진 네 에이전트가 하나의 Qwen3-0.6B 정책을 공유한다. 이 설계는 ‘에이전트 수를 늘렸더니 답이 좋아졌다’는 단순 관찰보다 통신 자체를 보기 쉽다.

### 재시도와 협업의 차이

같은 문제를 네 번 풀고 그중 하나를 고르는 방법도 단일 시도보다 성공 확률을 높일 수 있다. 그러나 검증기가 정답을 고를 수 있어야 하고, 계산량도 늘어난다. 따라서 다중 에이전트 실험에는 같은 토큰 예산에서 독립 실행과 통신 팀을 비교하는 기준이 필요하다. Hugging Face 글도 이를 원칙으로 내세우되, 이번 숫자 정렬 과제는 정보가 분산돼 있어 단독 에이전트가 원천적으로 완전한 답을 알 수 없다는 한계를 분명히 말한다. 이번 실험은 ‘같은 예산으로 일반 문제에서 다중 에이전트가 이겼다’는 증명이 아니라 **협업 학습의 전제인 정보 전달을 익힐 수 있는가**를 보는 실험이다.

팀은 직접 메시지와 브로드캐스트를 보내고 받은 메시지를 읽을 수 있다. 공유 보상은 성공에 따라 주어지고 생성 토큰이 많을수록 일부 감소한다. 공식 글의 예시는 팀 허용량 36,864토큰, 보상식 `성공 × (1 − 0.25 × min(1, 팀 생성 토큰 / 36,864))`이다. 메시지를 많이 보내면 별도로 상을 받는 구조가 아니다. 정답을 맞히되 토큰을 아끼는 방향으로 압력을 준다. 각 문제에는 여덟 개 독립 팀 시도를 모아 집단 안의 상대적 보상으로 정책을 업데이트한다. 한 팀에서 한 에이전트의 답이 틀려도 팀 전체가 성공했다면 그 에이전트도 팀의 이점을 공유한다. 이는 협력적 신용 할당의 장점이자, 어떤 행동이 실제로 기여했는지 모호하게 만드는 한계다.

### 공개된 숫자를 정확히 읽기

공식 글은 원래 실험의 학습 초반 다섯 업데이트와 후반 다섯 업데이트를 비교해 팀 성공률이 **6.56%에서 82.34%**, 팀당 생성 토큰 평균이 **12,826.9에서 8,026.0**으로 바뀌었다고 한다. 생성 토큰 감소는 약 37.4%다. 같은 기간 브로드캐스트 평균은 2.38에서 5.73으로 늘었다. 소통이 늘면서 토큰은 줄어든 것이다. 다만 메시지 수만으로 효율을 판단하면 안 된다. 모델의 추론, 도구 호출, 메시지 본문 모두 생성 토큰에 들어간다. 훈련된 체크포인트 75의 보류 집합에서는 32문제 중 26문제, 즉 81.25%를 풀었다. 이 보류 집합의 토큰 효율 측정은 보존하지 않았다고 글이 스스로 밝힌다. 따라서 훈련 구간의 37.4% 절감을 보류 집합 일반화 결과로 바꾸어 말하면 안 된다.

‘훈련 전 팀을 여덟 번 시도한 최고 결과’와 ‘훈련 후 팀을 한 번 시도한 결과’도 제시된다. 각각 37.5%와 82.3%, 문제당 대략 10만 3,000토큰과 8,000토큰이라고 한다. 흥미로운 비교지만 글은 둘 다 훈련 문제에 기반하고, 초기 다섯 업데이트에는 이미 약간 학습된 정책이 포함되며, 직접적인 단일 에이전트 비교가 아니라는 점을 단다. 논문이 보고한 200업데이트 후 93.2%도 이번 75업데이트 실험과 조건을 구분해야 한다. 같은 ‘성공률’이라는 단어 뒤에 **훈련/보류 집합, 업데이트 수, 시도 수**가 다르다.

### 제품팀에 어떤 의미가 있나

실무에서 에이전트를 분리할 이유는 ‘여럿이면 똑똑해진다’는 막연한 기대가 아니라 **정보·권한·전문성·시간을 분리할 필요**다. 예를 들어 문서 검색 에이전트는 출처 위치를 확인하고, 추출 검증 에이전트는 표 수치와 축 단위를 점검하며, 답변 에이전트는 근거를 문장에 연결할 수 있다. 하지만 세 역할이 같은 잘못된 파싱 결과만 본다면 역할 분리는 독립 검증이 아니다. 중복 추론 비용과 통신 오버헤드가 늘 뿐이다. 반대로 각 역할이 다른 증거를 실제로 접하고, 서로의 결론을 반증할 수 있다면 단일 긴 프롬프트보다 유의미할 수 있다. 그 여부는 과제별 측정으로 판단해야 한다.

실험 설계를 옮길 때는 최소 세 비교가 필요하다. 하나는 **동일 토큰 예산의 단일 에이전트**, 하나는 **여러 독립 시도의 best-of-N**, 하나는 **정보를 공유하는 팀**이다. 가능하면 모델, 도구, 문서 집합, 기회 횟수, 검증기를 같게 한다. ‘팀이 이겼다’는 관찰이 단순히 토큰을 네 배 쓴 덕분인지, 선택기가 정답을 알아서 골라준 덕분인지, 서로 다른 증거를 모은 덕분인지 나누어야 한다. 실패 시에도 누가 어떤 근거를 사용했는지 추적해야 같은 오류를 고칠 수 있다.

## Top News 4 — ggml-org, AMD에서 llama.cpp의 입력·출력 속도를 따로 보는 공개 대시보드

[ggml-org의 11월 26일 발표](https://huggingface.co/blog/ggml-org/llamacpp-amd-bench)는 AMD Ryzen·Radeon 하드웨어에서 llama.cpp 빌드, 모델, 양자화에 따른 로컬 추론 성능을 살피는 [벤치마크 대시보드](https://ggml-org-llamacpp-amd-bench.static.hf.space/index.html)를 소개한다. 현재 공식 글이 열거한 하드웨어 선택지는 Radeon 8060S(gfx1151)와 Radeon AI Pro R9700S(gfx1201)이다. 사용자는 구성별 비교, 빌드 이력, 문맥 길이 증가에 따른 생성 처리량을 볼 수 있고 공개 워크플로와 원시 결과 데이터로 측정 경로를 따라갈 수 있다. 이 투명성이 핵심이다. 벤치마크가 ‘어떤 모델이 최고’라는 순위표로 끝나지 않고 **빌드가 바뀌면서 성능이 왜 달라졌는지** 조사할 여지를 준다.

두 기본 시험은 모두 토큰/초이지만 서로 다른 작업이다. `PP512`는 시작 문맥 깊이 0에서 512개 입력 토큰을 처리하고 출력을 생성하지 않는다. `TG128`은 기존 문맥 없이 128개 토큰을 생성한다. 첫 항목은 긴 프롬프트를 넣을 때의 전처리 성능에, 둘째는 답변 생성의 처리량에 가까운 참고값이다. 실제 챗봇에서는 입력 처리와 출력 생성이 연속해서 발생하고, 이전 대화가 캐시에 남을 수도 있다. 그래서 컨텍스트 스케일링 탭이 중요하다. 문맥이 길어질수록 생성 속도가 어떻게 변하는지 봐야 긴 문서 질의와 코딩 세션의 체감 지연을 이해할 수 있다.

공식 글에 따르면 워크플로는 공개된 설치용 사전 빌드 바이너리를 사용하고 주간 일정으로 표준 `llama-bench`를 실행한다. Flash Attention을 켜고 끈 조건, 구성당 10회 반복, Q4_K_M·Q8_0·BF16·F16 등 여러 양자화가 포함된다. 모델 집합은 바뀔 수 있다. 공개된 [gfx1151 워크플로](https://github.com/ggml-org/llama-install.sh/blob/master/.github/workflows/bench-gfx1151.yml), [gfx1201 워크플로](https://github.com/ggml-org/llama-install.sh/blob/master/.github/workflows/bench-gfx1201.yml), [결과 버킷](https://huggingface.co/buckets/ggml-org/install.sh-benches-data)을 함께 제공한다. 원하는 구성의 값이 이상하다면 그래프 이미지만 보지 말고 빌드 ID와 JSONL의 원시 측정치를 확인할 수 있다.

로컬 AI 제품팀의 선택에는 최소 네 축이 있다. 첫째, **품질**: 더 낮은 정밀도에서 업무상의 오류가 늘지 않는가. 둘째, **입력 지연**: 긴 문서를 읽을 때 얼마나 기다리는가. 셋째, **출력 지연**: 모델이 답을 이어 쓰는 속도와 첫 토큰까지 시간이 어떤가. 넷째, **메모리·동시성**: 한 장치에서 여러 사용자를 감당할 수 있는가. 대시보드는 주로 처리량 참고값을 제공하고 품질과 서비스 전체 지연을 직접 측정하지 않는다. ‘토큰/초가 높다’는 이유만으로 특정 양자화를 택하면 숫자 표의 작은 오류가 더 비싼 결과를 만들 수 있다. 로컬 구동을 고르는 팀은 대시보드를 후보 좁히기에 쓰고, 자사 워크로드에서 품질과 p50·p95 지연을 다시 측정해야 한다.

## 개발자에게 의미 — 네 발표를 하나의 실험 계획으로 바꾸기

이 절은 네 공급자가 공동으로 제안한 아키텍처가 아니라 **공개 자료를 바탕으로 한 편집자의 실무 제안**이다. 예시 업무는 ‘여러 해의 감사 보고서와 회의 영상에서 특정 수치의 근거를 찾아 요약하는 서비스’다. 먼저 평가 집합을 만든다. 단순 문단 20건, 다단 표 20건, 차트 20건, 각주·페이지 간 연결 20건, 영상 장면·발언 20건처럼 오류 유형이 다르게 드러나는 사례를 준비한다. 숫자는 권장 표본 크기가 아니라 설계 설명을 위한 예시다. 실제 표본은 실패 위험과 고객 문서 분포에 맞춰 정한다. 정답에는 문장뿐 아니라 **파일 ID, 페이지/시간 구간, 셀·행·열 또는 차트 축 정보**를 기록한다.

다음으로 문서 추출을 평가한다. 원본 PDF와 이미지에서 페이지를 렌더링할 때 해상도·회전·색상 처리를 기록하고, 한 페이지를 한 요청으로 보낸다면 페이지 간 이어지는 표를 별도 조립한다. NVIDIA 같은 자체 파서는 텍스트 정확도 외에 행·열 헤더 연결, 수식·단위, 차트 계열, 위치 좌표, 출력 완료를 본다. 관리형 수집을 택하면 검색 결과가 원문 페이지와 실제로 대응하는지, 편집한 파일을 다시 가져왔을 때 이전 구간이 남지 않는지 확인한다. 한 방식이 구조 추출에서 앞서도 다른 방식이 운영 비용에서 앞설 수 있다. 같은 파일 집합과 질의 집합에서 비교해야 한다.

검색 평가는 질문을 의도별로 나눈다. 정확한 키워드가 있는 질의, 뜻만 비슷한 질의, 숫자와 연도를 정확히 찾아야 하는 질의, 여러 페이지를 결합해야 하는 질의, 음성에만 있는 영상 정보 질의가 필요하다. 상위 `k`개에 정답 구간이 포함되는 **recall@k**와 불필요한 결과가 너무 많은지 보는 정밀도, 답변이 실제 원문 위치를 인용했는지 보는 인용 일치율을 따로 측정한다. 재정렬을 켜면 상위 결과가 좋아질 수 있지만 지연·비용도 바뀐다. 문서에는 재정렬을 지원하더라도 Google 글은 VIDEO 데이터 스토어에 `reranking_spec`이 지원되지 않는다고 명시한다. 동일 기능이 모든 자료형에 있다고 가정하지 않는다.

에이전트 구성 평가는 비싸고 복잡하므로 마지막에 한다. 단일 에이전트가 검색과 답을 모두 수행하는 기준선을 먼저 만든다. 그 뒤 별도 검증 에이전트가 원문 표 수치와 인용 위치를 독립 확인하는 방식, 정보가 다른 도구에 분산된 협업 방식, 같은 예산으로 단일 에이전트가 더 오래 추론하는 방식을 비교한다. 에이전트 팀의 메시지 수나 직책 수 자체를 성과로 삼지 않는다. 최종 정확도, 잘못된 인용 비율, 사람이 고치는 시간, 토큰과 GPU 사용량, 위험한 행동의 차단율을 함께 본다. 유리한 한 사례의 데모보다 **실패한 사례를 다시 분류할 수 있는 로그**가 운영 개선에 더 유용하다.

마지막으로 성능을 측정한다. 문서 업로드부터 사용 가능한 검색까지의 수집 지연, 질의 후 첫 결과까지 검색 지연, 첫 토큰까지의 생성 지연, 답변 완료까지의 종단 간 지연을 각각 기록한다. ggml-org 대시보드는 모델·하드웨어 후보를 고르는 참고 자료다. NVIDIA의 페이지/초와 ggml-org의 토큰/초는 서로 다른 작업 단위이므로 직접 나눠 비교할 수 없다. 한 요청이 열 페이지를 포함하고 세 페이지만 추가 정밀 파싱한다면 총 비용은 **페이지별 처리 시간 + 검색·재정렬 + 답변 생성**의 조합으로 계산해야 한다. 평균만으로 피크 시간의 장애를 보지 못하므로 p95와 오류율을 함께 관찰한다.

### 예시: ‘정확한 숫자지만 틀린 답’이 만들어지는 경로

사용자가 ‘2025년 사업부 A의 영업이익은?’이라고 묻는다. 파서는 표의 숫자 `128`을 정확히 읽지만 `2024년` 열에 있던 수치를 `2025년` 열에 연결한다. 검색은 해당 페이지를 찾아준다. 답변 에이전트는 페이지 번호를 달아 `128`이라고 답한다. 사용자는 링크가 붙어 있어 믿기 쉽다. 이 사례에서는 OCR 문자 정확도, 검색 recall@k, 인용 URL 존재 여부가 모두 좋아 보여도 **행·열 관계 복원**과 **답변-근거 일치**가 실패했다. 평가 집합에 구조 관계 질문이 없으면 놓친다. 해결 방법은 단순히 더 큰 답변 모델을 쓰는 게 아니라 원본 이미지와 구조화 결과의 관계를 대조하고, 최종 수치에 단위·연도·항목을 묶어 검증하는 것이다.

다른 사례에서는 영상에서 연사가 ‘계약은 다음 분기부터’라고 말하지만 화면에는 지난 분기의 슬라이드가 남아 있다. 음성 모드를 끈 영상 검색은 화면의 지난 분기와 잘 맞는 장면을 반환할 수 있다. 답변이 이를 근거로 삼으면 발언과 화면이 뒤섞인다. 시간 구간이 같은 자료라도 **검색 신호가 음성인지 영상인지**가 중요하다. 비디오 결과에는 탐색할 수 있는 시각을 붙이고, 발언에 대한 사실 확인은 실제 오디오 또는 검증 가능한 전사를 기준으로 한다. 짧은 클립이 문장의 앞뒤를 자르면 주변 구간까지 재생해 확인한다.

세 번째 사례에서는 문서 검증 에이전트 둘이 같은 검색 결과 스니펫만 읽고 서로 ‘맞다’고 확인한다. 에이전트 수는 늘었지만 증거는 한 개다. 이 경우 독립 검증이라는 이름이 잘못됐다. 두 번째 에이전트가 원본 페이지나 다른 검색 경로를 보도록 설계하고, 첫 에이전트의 답을 반증할 조건을 명시해야 한다. Hugging Face 실험의 핵심은 별도 문맥을 가진 에이전트가 **서로 없는 정보를 실제로 전달**했다는 점이다. 제품에서는 역할 이름만 나누는 것이 아니라 서로 다른 근거를 접하게 해야 한다.

## 운영 포인트 — 배포 전 질문과 실패 대응

### 1. 원본과 파생물의 연결

원본 파일에는 변하지 않는 ID와 버전을 붙인다. 파싱 결과에는 입력 파일 해시, 페이지 번호, 렌더링 설정, 파서 모델·버전, 생성 시각을 붙인다. 검색 구간에는 어떤 파싱 결과에서 나왔는지와 인덱스 버전을 기록한다. 답변에는 사용한 구간 ID와 실제 인용 위치를 저장한다. 이것은 어떤 공급자 문서의 기본 기능을 그대로 나열한 것이 아니라 **감사 가능한 서비스**를 위한 제안이다. 특히 원본이 수정됐을 때 오래된 구간이 검색되는 문제를 찾는 데 필요하다.

### 2. 품질 게이트

평균 점수가 높아도 비용이 큰 오류는 따로 막아야 한다. 금액·용량·날짜·규정 조항·의료 항목 등은 원문과 정규화 결과를 항목별로 대조한다. 표에서는 행 제목, 열 제목, 단위, 각주를 하나의 근거 묶음으로 보존한다. 차트에서는 축의 시작점과 눈금, 범례를 함께 확인한다. 답변 모델이 출처에 없는 계산을 했다면 계산식과 입력 숫자를 표시한다. 검사에 실패하면 확신을 가장한 문장보다 ‘근거 부족’으로 반환하거나 사람 검토로 넘긴다. 이 게이트가 제품 가치를 떨어뜨리는지 여부도 정당한 작업의 완료율로 측정한다.

### 3. 접근권한과 데이터 수명주기

관리형 수집을 쓰면 객체 저장소와 서비스 에이전트의 읽기 권한을 최소 범위로 둔다. 임시 평가 데이터와 생산 데이터를 같은 버킷에 섞지 않는다. 삭제 명령이 데이터 스토어와 기반 Collection 양쪽을 처리했는지 확인한다. 자체 파서를 쓰면 페이지 렌더링 이미지, 임시 크롭, 구조화 JSON, 결과 로그가 새 민감 정보 저장소가 될 수 있다. 모델 추론 로그의 예시 페이지에 이름·계좌번호가 들어가지 않도록 관리해야 한다. ‘모델이 로컬에서 돈다’는 사실만으로 파생 파일의 보안이 해결되지는 않는다.

### 4. 프리뷰와 재현성

Google 기능은 공개 프리뷰이므로 API 버전·리전·요금 조건을 배포 시점에 고정해 확인한다. NVIDIA 모델과 데이터셋은 모델 카드·레시피·코드 커밋을 기록한다. ggml-org 벤치마크는 빌드별 기록이 있으므로 ‘Radeon에서 빠름’ 같은 모호한 문장 대신 해당 빌드·모델·양자화·Flash Attention 설정을 기록한다. Hugging Face의 실험을 재현한다면 훈련 문제 풀과 보류 집합, 업데이트 수, 생성 토큰 정의, GPU 수와 서빙 구현을 함께 기록한다. 실험 결과를 재현할 정보가 없으면 성능 회귀를 판별하기 어렵다.

### 5. 사고가 났을 때의 순서

잘못된 답이 보고되면 첫 질문은 ‘어느 모델이 틀렸는가’가 아니라 **어느 단계에서 처음 사실이 바뀌었는가**다. 원본 페이지가 실제로 무엇을 말하는지 확인한다. 파싱 결과의 구조·숫자·좌표를 본다. 검색에 정답 구간이 포함됐는지 본다. 답변이 검색 근거를 정확히 사용했는지 본다. 각 단계가 정상이었다면 질문이 모호했는지, 계산 규칙이 누락됐는지 확인한다. 오류를 파서·검색·추론·권한·지연으로 분류해야 수정 위치가 보인다. 모든 실패를 프롬프트 수정으로 덮으면 다음 문서에서 같은 오류가 반복된다.

## 적용 우선순위: 누구에게 오늘 뉴스가 중요한가

**문서 RAG를 직접 운영하는 팀**에는 Google의 관리형 수집이 가장 즉각적인 실험 후보이지만, 프리뷰·리전·권한·삭제 방식을 먼저 평가해야 한다. 이미 자체 파서를 쓰고 있는 팀에는 NVIDIA의 합성 데이터와 검증 가능한 보상 레시피가 도메인 특화의 선택지를 제공한다. 두 자료를 동시에 읽으면 ‘파서를 고칠 문제’와 ‘검색 구간을 고칠 문제’를 구분하는 데 도움이 된다. 같은 정답 실패라도 원인은 달라질 수 있다.

**에이전트 워크플로를 구축하는 팀**에는 Hugging Face 글의 실험 설계가 중요하다. 팀이 정보 교환을 통해 푼 과제인지, 추가 시도와 토큰만 쓰고 이긴 과제인지 구별해야 한다. 협업을 도입하기 전에 단일 에이전트와 같은 예산의 기준선을 반드시 남기고, 여러 에이전트가 실제로 서로 다른 근거를 사용했는지 확인한다. 에이전트의 대화가 길어지는 것은 협업의 성과가 아니라 비용일 수도 있다.

**로컬 추론을 검토하는 팀**에는 ggml-org 대시보드가 출발점이다. 하드웨어·빌드·양자화별 처리량을 공개 원시 데이터와 대조할 수 있다. 다만 문서 AI 서비스에서는 파싱 모델과 답변 모델의 GPU 사용이 겹치고, 긴 문맥·동시성·사용자 지연이 중요하다. 입력 512토큰과 생성 128토큰의 기준 시험만 보고 실제 긴 보고서 질의의 처리량을 추정해서는 안 된다.

## 오늘 바로 실행할 수 있는 검증 체크리스트

1. **자료의 신선도:** 발표일과 후속 업데이트일을 구별한다. 모델 카드의 이전 출시 이력을 오늘 새 출시로 쓰지 않는다.
2. **원본 위치:** 정답마다 파일 ID와 페이지 또는 영상 시각을 기록한다. 위치가 없는 답은 별도 범주로 분류한다.
3. **표 구조:** 숫자 문자열뿐 아니라 행·열·단위·각주 연결을 평가한다.
4. **차트 해석:** 표시된 값과 축에서 추정한 값을 구분하고, 추정값이면 허용 오차를 정한다.
5. **출력 완료:** 토큰 상한 도달·반복 출력·형식 오류를 정확도와 별도 지표로 센다.
6. **검색 범위:** 정답 구간이 상위 검색 결과에 포함되는지, 재정렬 여부에 따라 바뀌는지 확인한다.
7. **인용 일치:** 답의 각 주장에 대응하는 원문 구절이 실제 인용 위치에 있는지 검사한다.
8. **영상 신호:** 화면 검색과 음성 검색의 결과를 구분하고 필요한 경우 양쪽을 확인한다.
9. **권한:** 관리형 서비스 에이전트가 요구된 버킷과 객체만 읽는지 확인한다.
10. **비용:** 수집·저장·검색·재정렬·파싱·답변 생성 비용을 별도 항목으로 산출한다.
11. **지연:** 처리량과 첫 응답 시간, p95 완료 시간, 업로드 후 검색 가능 시간을 따로 기록한다.
12. **협업 기준선:** 단일 실행·독립 재시도·정보 공유 팀을 같은 예산에서 비교한다.
13. **배포 제한:** 공개 프리뷰 조건과 지원 리전, 모델·라이브러리 버전, 데이터 사용 조건을 기록한다.
14. **삭제 검증:** 원본, 파생 이미지, 데이터 스토어, 기반 Collection, 임시 로그가 삭제 정책에 따라 사라지는지 확인한다.
15. **오류 분류:** 최종 답의 실패를 추출·검색·근거 사용·추론·지연·권한으로 분리해 다음 실험에 반영한다.

이 체크리스트는 모든 제품에 동일하게 적용하라는 규정이 아니다. 사용자의 업무와 피해 가능성에 따라 게이트의 강도를 정해야 한다. 문서 요약을 참고용으로 보여 주는 서비스와 자동으로 계약 금액을 확정하는 서비스에 같은 오류 허용치를 둘 수 없다. 핵심은 모델의 인상적인 데모와 서비스의 책임 있는 동작을 별도 실험으로 다루는 것이다.

## 실무 설계 노트 — 도입 여부를 결정하는 세 가지 갈림길

이 섹션은 제품의 새 기능을 추가로 발표하는 부분이 아니다. 앞서 확인한 공식 자료를 한 팀의 기술 검토 회의에서 사용할 수 있도록 **결정 질문**으로 바꾼 것이다. 결론을 미리 정하지 않고 요구사항을 먼저 적는 것이 핵심이다.

### 갈림길 A: 추출 모델을 직접 운영할 것인가, 관리형 수집을 쓸 것인가

자체 파서가 유리한 상황은 원본 페이지 이미지와 추출 결과의 연결을 세밀하게 통제해야 하거나, 특정 도메인 자료로 미세조정을 반복해야 하거나, 배포 위치와 결과 형식에 강한 요구가 있을 때다. NVIDIA가 공개한 데이터·레시피는 이런 팀이 실험을 시작할 근거를 제공한다. 그러나 모델만 내려받으면 끝나는 일이 아니다. PDF를 페이지 이미지로 바꾸는 서비스, 실패 페이지의 재시도, 구조화 결과의 버전 관리, 검색 색인 생성, 모델·GPU 업데이트, 보안 패치와 관찰성을 직접 담당한다. 이미 검색 서비스가 갖춰져 있어 파싱 품질만 병목일 때 자체 파서의 투자 효과가 크다.

관리형 수집이 유리한 상황은 파서·청킹·임베딩·색인의 조립 자체가 병목이고, 공개 프리뷰의 리전·기능·지원 조건을 받아들일 수 있을 때다. Google Agent Retrieval은 문서와 영상을 데이터 스토어로 가져오고 출처 위치가 딸린 구간을 반환하는 흐름을 제시한다. 하지만 **관리형**이라는 말은 시스템 책임의 소멸이 아니라 이동을 뜻한다. 서비스 권한, 인덱스 최신성, 검색 품질, 인용 검증, 삭제 확인은 여전히 고객 제품의 책임이다. 제공하지 않는 파싱 규칙이나 도메인 특화 보상이 필요하면 서비스 기본 처리만으로는 부족할 수 있다.

평가표에는 ‘우리 문서에서 정답 구간을 찾는 비율’, ‘틀린 숫자를 조용히 내는 비율’, ‘파일 수정 후 최신 정보가 검색될 때까지 시간’, ‘같은 달의 예상 비용’, ‘데이터 저장 리전’, ‘운영자가 조정 가능한 부분’을 행으로 넣는다. 한쪽은 모델 정확도를, 다른 쪽은 API 편의성을 기준으로 점수를 매기면 공정한 비교가 아니다. 최종 사용자에게 필요한 **정답과 근거를 같은 조건으로 제공하는 전체 파이프라인**을 비교해야 한다. 프리뷰 기능의 가격이나 API 버전은 바뀔 수 있으므로 실험 날짜를 결과에 적는다.

### 갈림길 B: 에이전트를 나눌 것인가, 하나에 더 많은 예산을 줄 것인가

‘문서를 찾는 역할’과 ‘답을 쓰는 역할’을 분리하는 것은 설계상 자연스럽다. 그렇지만 여러 세션을 띄우는 순간 통신 실패, 중복 작업, 타임아웃, 책임 불명확성이 생긴다. Hugging Face 실험처럼 각 구성원에게 서로 없는 정보가 있고 이를 짧은 메시지로 공유해야 할 때 분리는 분명한 목적을 갖는다. 반면 같은 검색 결과를 세 에이전트가 읽고 비슷한 요약을 반환한다면, 독립된 근거가 아니라 동일한 오류의 복제일 수 있다. 팀 설계 전에 정보가 실제로 어디에 분산되어 있는지 지도로 그려야 한다.

세 가지 기준선을 한 세트로 남긴다. 첫째, 단일 에이전트가 주어진 토큰 예산 안에서 검색·검증·답변을 끝내는 경우. 둘째, 같은 예산 안에서 독립 실행을 여러 번 시도하고 검증 가능한 선택 규칙으로 하나를 고르는 경우. 셋째, 역할과 서로 다른 근거를 부여한 에이전트가 메시지를 교환하는 경우다. 각 방식의 성공률을 토큰, 벽시계 시간, 도구 호출 수, 사람의 최종 수정 시간과 함께 비교한다. ‘성공’은 문장 유창성이 아니라 원본에 근거한 정답과 올바른 인용으로 판정한다.

다중 에이전트가 유리하더라도 모든 요청에 사용해야 하는 것은 아니다. 평이한 단일 문단 질문에는 한 에이전트로 충분할 수 있고, 복잡한 표·차트나 상충하는 문서의 수치를 조정해야 할 때만 별도 검증을 켤 수 있다. 라우팅 규칙의 목표는 토큰 절약 자체가 아니라 **위험에 맞는 검증 강도**다. 값이 작은 실험은 자동 응답, 고위험 수치 해석은 근거 확인과 사람 검토라는 경로를 만들 수 있다. 어느 요청을 고위험으로 분류할지 또한 평가 집합으로 검증한다.

### 갈림길 C: 처리량을 최적화할 것인가, 오류 비용을 먼저 줄일 것인가

NVIDIA의 페이지/초와 ggml-org의 토큰/초는 둘 다 유익하지만 사용자가 체감하는 지연의 일부다. 사용자가 100쪽 PDF를 올리면 파일 업로드, 렌더링, 파싱, 색인, 검색 가능 상태가 되기까지의 시간이 먼저 중요하다. 이미 색인이 완성된 보고서에 질문하면 검색, 재정렬, 답변 생성의 시간이 중요하다. 이 두 사용 흐름을 섞어 ‘우리 서비스는 초당 몇 페이지’라고 표현하면 중요한 병목을 숨긴다. 서비스 수준 목표를 **첫 업로드 후 사용 가능 시간**과 **기존 자료에 대한 질의 응답 시간**으로 분리한다.

오류 비용은 더 중요한 구분이다. 내부 초안 검색에서 한 페이지를 놓치면 사람이 다시 찾을 수 있다. 자동으로 고객에게 금액을 통지하거나 계약 조건을 결정한다면 잘못된 숫자 하나가 GPU 비용 절감보다 훨씬 크다. 단일 패스가 빠르더라도 차트·표처럼 위험한 페이지에서는 재처리를 켜는 전략을 검토할 수 있다. 반대로 모든 페이지를 triple-pass로 돌리면 처리량과 비용을 낭비할 수 있다. ‘어떤 페이지를 더 읽을 것인가’의 판정기 역시 잘못된 음성을 줄이면서 누락을 얼마나 남기는지 따로 측정한다.

성능 측정에서는 동일한 원본 집합·동일한 질문·동일한 출력 품질 기준을 유지한다. 모델을 바꾸고 프롬프트도 바꾸고 문서 분할도 바꾼 뒤 지연만 비교하면 어느 변화가 효과를 냈는지 알 수 없다. 먼저 추출 방식과 색인을 고정한 채 추론 하드웨어를 비교하고, 다음에는 하드웨어를 고정한 채 추출·검색 정책을 비교한다. 품질과 속도의 Pareto 경계를 그리면 ‘더 빠르면서 정확한’ 조합과 ‘더 빠르지만 위험한’ 조합이 분리된다. 최종 선택에는 공급자 조건, 리전과 운영 부담까지 포함해야 한다.

## 평가 결과를 읽는 법 — 같은 숫자를 다른 뜻으로 사용하지 않기

오늘 자료의 숫자는 단위부터 다르다. NVIDIA 측정의 ‘페이지/초’는 페이지 이미지 추출 작업의 처리량이다. Google 예시의 ‘검색 0.3–0.5초’는 특정 영상 데이터 스토어에 대한 질의 사례다. Hugging Face의 ‘성공률 82.34%’는 숫자 공유 과제의 훈련 후반 팀 시도에 관한 것이다. ggml-org의 ‘토큰/초’는 정해진 입력·출력 길이의 로컬 추론 벤치마크다. 네 숫자를 하나의 ‘AI가 빨라졌다’ 지표로 묶지 않는다. 모두 중요한데 **서로 다른 질문의 답**이다.

또 하나는 실험 조건의 비대칭이다. NVIDIA의 DFlash2 그래프는 HTTP와 이미지 로딩을 제외한다. Google의 검색 예시에는 수집 작업이 별도로 있다. Hugging Face의 보류 집합 성공률에는 보류 집합 토큰 절약 수치가 함께 보존되지 않았다. ggml-org의 PP512·TG128은 처음 문맥 깊이 0에서 시작한다. 공개 자료가 제외 조건을 설명했으면 독자는 바로 그 제외 조건을 제품 측정에 다시 넣어야 한다. 제공자가 부정확하게 발표했다는 뜻이 아니라, 실험의 목적과 운영 의사결정의 목적이 다르다는 뜻이다.

숫자의 신뢰도도 분리한다. 공개 워크플로와 원시 데이터가 있으면 재실행과 조건 확인이 쉽다. 그러나 같은 하드웨어가 없거나 운영 트래픽이 다르면 재현 가능한 벤치마크라도 내 서비스의 성능을 예측하지 못할 수 있다. 단일 데모에서 나온 성공 사례는 오류 유형을 설명하는 데 유익하지만 전체 실패율을 계산할 수 없다. 반대로 집계 점수는 평균적 흐름을 보여 주지만 드문 치명 오류를 숨길 수 있다. 좋은 도입 결정은 데모, 집계, 실패 사례, 비용 예측을 서로 다른 증거로 취급한다.

마지막으로 공개 프리뷰와 공개 가중치, 공개 벤치마크는 서로 다른 ‘공개’다. 공개 프리뷰는 제품의 제공 단계와 조건을, 공개 모델·데이터는 자료 접근과 사용 조건을, 공개 벤치마크는 실험 절차와 결과의 검증 가능성을 말한다. 어느 하나도 곧바로 생산 환경 보증을 뜻하지 않는다. 기술 발표를 읽을 때 ‘무엇이 공개됐나’ 다음에 ‘무엇을 내가 다시 검증해야 하나’를 반드시 붙이는 이유다.

## 부록 A — 문서 AI 평가표를 실제로 설계한다면

평가표를 만들 때 처음부터 ‘정답률’ 열 하나만 두지 않는다. 답변의 질과 그 답변에 이른 경로를 분리한다. 권장하는 최소 단위는 **원본 파일 한 개에 대한 질문 한 개**다. 이 단위마다 질문 ID, 파일 ID와 버전, 예상 답, 허용되는 동의 표현, 정답 근거 위치, 필요한 계산, 민감도, 검토자를 기록한다. 정답 근거 위치는 한 페이지일 수도, 여러 페이지나 영상 구간일 수도 있다. 여러 근거가 필요하면 모두 기록하고 단일 인용만으로 충분하다고 채점하지 않는다. 데이터셋을 만든 사람이 모델의 예측을 본 뒤 정답을 바꾸면 평가가 흐려진다. 논쟁의 여지가 있는 사례는 검토자가 사전에 합의하거나 별도 ‘모호함’ 범주로 남긴다.

첫 번째 열 묶음은 **원본 해석**이다. 원본의 글자, 표 헤더, 행·열, 단위, 각주, 차트 범례, 이미지 위치가 추출 결과에 보존됐는지 확인한다. 문자 단위 오류율은 유용하지만 충분하지 않다. 재무 표에서 `1,000`의 쉼표 하나가 빠지는 것과 단락의 띄어쓰기 하나가 바뀌는 것은 같은 ‘한 글자 차이’가 아니다. 숫자에는 원문과의 완전 일치, 단위 일치, 기간 일치, 항목 관계 일치를 따로 둔다. 어떤 오류가 최종 답에 영향을 주는지 표시한다. 숫자를 맞혀도 인접 열의 숫자를 가져왔으면 위치 오류로 기록한다. 페이지 렌더링에서 회전이 잘못돼 파서가 읽지 못했다면 모델 오류와 전처리 오류를 구분한다.

두 번째 열 묶음은 **검색**이다. 정답 페이지가 `top_k` 안에 있는지, 검색이 완전히 다른 파일을 가져왔는지, 구간이 정답의 앞부분만 담고 나머지 설명을 잘랐는지 본다. recall@k는 ‘정답 근거가 상위 k개 안에 들어옴’의 비율이다. 검색 결과가 많으면 recall은 올라갈 수 있지만 답변 모델에 불필요한 내용도 증가한다. 따라서 정답 구간이 포함됐는지와 모델이 실제로 읽은 총 토큰·구간 수를 함께 기록한다. 영상은 시각 오차도 필요하다. 공식 결과의 시작·종료 시각 안에 발언이 포함되더라도 앞뒤 5초를 봐야 뜻이 완성되는 경우가 있다. 제품이 사용자에게 보여 주는 클립 범위를 측정 기준에 포함한다.

세 번째 열 묶음은 **답변**이다. 예상 답과 의미가 같은지, 불확실한 값을 확정한 것처럼 썼는지, 계산식이 맞는지, 인용한 구간이 해당 문장을 지지하는지 검토한다. 질문의 답을 할 수 없는 경우를 의도적으로 넣는다. 검색에 근거가 없는데 그럴듯한 답을 내면 심각한 오류다. 반대로 충분한 근거가 있는데도 ‘모르겠다’고만 하면 과도한 회피다. 따라서 ‘정답’, ‘근거 없는 답’, ‘잘못된 인용’, ‘부당한 거절’, ‘정당한 보류’를 별도 범주로 집계한다. 제품의 안전 설계와 사용성 설계는 둘 다 이 분류에 영향을 준다.

네 번째 열 묶음은 **비용·지연·운영**이다. 파싱에 투입한 페이지 수와 추가 패스 수, 색인에 사용한 저장량, 검색 호출 수와 재정렬 여부, 에이전트의 개별 토큰과 메시지 수, 사용자 지연, 사람 검토 시간을 기록한다. 비용 계산에는 요청 한 건의 평균뿐 아니라 문서 한 건을 처음 수집하는 비용과 재수집 비용을 따로 넣는다. 매일 업데이트되는 문서가 많다면 색인 비용이 질의 비용보다 클 수 있다. 반대로 한 번 수집한 오래된 보고서에 질문이 많다면 검색·생성 비용이 중심이 된다. 공개 벤치마크 한 숫자로 이 비율을 추론할 수 없으므로 자사 트래픽의 문서 변경률과 질의 반복률을 측정해야 한다.

### 평가 집합의 누출과 난이도 편향

시연에 쓰인 문서를 그대로 평가에 재사용하면 프롬프트와 분할 규칙을 그 문서에 맞추는 동안 보류 집합이 사라진다. 개발 집합과 최종 검증 집합을 나누고, 최종 집합의 원본 위치·정답·평가 기준을 구현 팀이 정기적으로 열어 보지 않도록 한다. 시간이 지나면 제품이 처리하는 문서 분포도 바뀐다. 신규 고객의 양식, 새 언어, 스캔 방식, 압축 규칙, 영상 촬영 습관이 달라지면 이전 집합의 좋은 점수가 과거의 사실이 된다. 정기적으로 실패 사례를 추가하되, 기존 집합의 점수도 버전별로 남겨 회귀를 볼 수 있게 한다.

난이도는 질문의 길이로 정하지 않는다. ‘2026년 총매출은?’이라는 짧은 질문도 파일 여러 개의 단위가 다른 경우 어렵다. ‘이 페이지의 첫 문단을 요약해 달라’는 긴 질문은 쉬울 수 있다. 난이도를 단일 페이지/복수 페이지, 본문/표/차트/영상, 명시적 값/추론·계산, 원본 품질, 답 불가능 여부의 조합으로 표시한다. 결과를 이 층별로 보면 전체 평균이 좋아져도 가장 중요한 다단 표에서 악화된 사실을 놓치지 않는다. 공급자 발표의 평가 분포와 우리 문서 분포가 다르면 점수의 직접 비교를 피한다.

### 실패 사례의 재현 패킷

오류가 발견됐을 때 재현 가능한 기록은 원본 또는 보안상 허용된 사본, 파일 해시와 버전, 페이지 이미지의 렌더링 설정, 모델·API 버전, 파서 출력, 검색 결과와 순위, 재정렬 점수, 에이전트가 실제로 본 문맥, 최종 답, 지연·비용이다. 민감 데이터를 외부 이슈에 붙이라는 뜻은 아니다. 내부에서 접근이 통제된 기록을 보관하되, 개발자가 같은 입력으로 같은 경로를 조사할 수 있어야 한다. 파서가 숫자를 잘못 읽었는지, 검색이 정답 구간을 놓쳤는지, 답변이 맞는 구간을 오독했는지를 판별하는 데 이 정보가 쓰인다.

같은 질문을 여러 번 실행해 결과가 흔들리는지도 본다. 한 번의 정답이 안정성을 입증하지 않는다. 특히 에이전트가 도구 호출과 메시지 순서를 바꾸는 경우 검색된 근거 자체가 달라질 수 있다. 반복 실행에서는 정답률뿐 아니라 **잘못된 인용의 발생 확률**과 **재현 가능한 실패 유형**을 본다. 모델이 항상 같은 틀린 답을 내는 문제와 가끔 위험한 행동을 하는 문제는 대응 방식이 다르다. 전자는 데이터·추출 규칙의 정정이, 후자는 통제·검증·권한 게이트가 더 중요할 수 있다.

## 부록 B — 가상의 연간 보고서에 적용하는 단계별 설계 검토

이 예시는 특정 제품의 실제 성능 사례가 아니라, 오늘의 소식을 하나의 검토 문서로 묶기 위한 가상 상황이다. 사용자는 세 해의 연간 보고서와 한 시간짜리 발표 영상을 업로드한다. 질문은 ‘2025년 해외 매출이 2024년보다 얼마나 늘었고, 경영진은 그 원인을 어떻게 설명했나?’다. 정답에는 두 연도의 동일 단위 매출값, 증가액 또는 증가율 계산, 발표 영상에서 원인 설명을 한 정확한 시간 구간이 모두 필요하다. 한 페이지의 숫자만 찾으면 완료가 아니다.

**수집 단계:** 먼저 파일의 고유 ID와 해시를 만들고, 보고서가 스캔본인지 텍스트 PDF인지, 통화 단위가 표마다 같은지 확인한다. 스캔본의 표는 페이지 이미지 추출 평가가 중요하다. 텍스트 PDF라고 해서 표의 관계가 보존됐다고 가정하지 않는다. 영상은 발언이 화면에 자막으로 뜨는지, 오디오에서만 나오는지 확인한다. Google Agent Retrieval을 검토한다면 관리형 수집이 보고서와 영상에 대해 각각 어떤 데이터 스토어와 세그먼트를 만드는지 테스트한다. 자체 NVIDIA 파서를 검토한다면 PDF 페이지 렌더링과 구조 추출, 페이지 간 표 연결을 구현 범위에 넣는다.

**검색 단계:** 질문을 숫자 질의와 설명 질의로 나누어 증거를 찾는다. 2024년 보고서와 2025년 보고서의 ‘해외’가 동일한 사업부 정의인지 확인한다. 영업 지역 분류가 바뀌었다면 단순 차감은 무의미할 수 있다. 표에서 가져온 숫자는 표 제목, 기간, 단위, 연결 기준을 함께 저장한다. 영상 검색에서는 ‘매출 증가의 이유’를 말한 구간을 찾고 해당 구간 앞뒤를 재생한다. 화면에 매출 표가 있더라도 음성에서 원인을 설명한 시각이 다를 수 있다. Google의 비디오 예시가 보여 준 것처럼 오디오 모드의 설정 여부가 검색 가능성을 바꾼다.

**해석 단계:** 두 값이 실제로 같은 정의를 가진다면 증가액은 `2025년 값 − 2024년 값`, 증가율은 `증가액 ÷ 2024년 값`으로 계산한다. 분모가 0이거나 기준년도가 재작성됐으면 계산을 멈추고 설명해야 한다. 숫자가 백만 달러와 십억 달러로 섞여 있으면 단위를 먼저 정규화한다. 답변 에이전트가 계산한 값을 별도 검증 단계에서 원본 표와 다시 대조한다. 다중 에이전트를 쓴다면 한 에이전트는 문서 수치를, 다른 에이전트는 영상 발언을, 검증자는 계산과 근거 일치를 확인하게 한다. 각자 같은 요약 스니펫만 읽게 하면 분리의 장점이 사라진다.

**답변 단계:** 최종 문장은 수치와 계산식, 해당 보고서 페이지, 경영진 발언의 영상 시각을 분리해 제시한다. 발언이 실제 증가의 ‘원인’인지 단지 전략 목표를 말한 것인지 구분한다. 만약 영상에 직접적인 원인 설명이 없으면 추측을 출처가 있는 것처럼 꾸미지 않는다. ‘보고서에서 증가액은 계산할 수 있지만, 영상에서 확인 가능한 원인 설명은 찾지 못했다’는 부분 답도 제품에서는 정직한 성공일 수 있다. 완전한 답을 억지로 만드는 것보다 근거의 범위를 정확히 표시하는 편이 낫다.

**운영 단계:** 업로드 후 언제 검색 가능해졌는지, 수치 질문에서 어떤 단계가 지연의 대부분을 차지했는지 기록한다. 보고서의 숫자가 잘못됐다면 NVIDIA 파서 또는 관리형 수집 결과를 대조한다. 영상 근거가 빠졌다면 오디오 모드, 세그먼트 길이, 질의 표현을 조사한다. 계산이 틀렸다면 별도 산술 검증을 강화한다. AMD 기반 로컬 답변 모델을 선택하려면 ggml-org 대시보드에서 후보를 고른 뒤 세 보고서의 실제 검색 구간 길이와 출력 길이로 재측정한다. 하나의 공개 처리량 그래프는 이 전체 경로를 대신하지 않는다.

## 부록 C — 운영 회의에서 자주 나오는 오해 여섯 가지

**‘출처가 표시됐으니 환각이 아니다.’** 출처 위치가 있다는 것과 주장이 그 위치에 실제로 있다는 것은 다르다. 검색 결과의 페이지 표식은 검증을 가능하게 하는 기반이지 검증 자체가 아니다. 표의 잘못된 열을 인용할 수도 있고, 맞는 페이지에서 다른 연도의 수치를 가져올 수도 있다. 인용 일치 평가는 답의 각 주장과 원문의 대응 관계를 보아야 한다.

**‘OCR이 정확하므로 RAG도 정확하다.’** 문자와 구조는 다르다. 표의 모든 숫자를 정확히 읽어도 행·열 관계가 뒤집히면 질문의 답은 틀린다. 거기에 검색이 적절한 구간을 놓치거나 답변이 이미 찾은 근거를 잘못 요약할 수도 있다. 파이프라인의 한 단계가 좋아졌다는 결과는 전체 성능의 필요조건일 수 있지만 충분조건은 아니다.

**‘관리형 서비스가 파이프라인을 없앴다.’** 관리형 수집은 사용자가 직접 작성하던 파싱·분할·임베딩·색인 코드를 줄인다. 데이터 스토어의 접근권한, 원본 업데이트, 수집 완료 확인, 검색 결과 검증, 삭제와 과금은 남는다. 한 API 호출은 검색 인터페이스의 단순화이지 원본을 신뢰할 수 있는 답으로 바꾸는 모든 판단의 자동화가 아니다.

**‘에이전트를 여러 명 띄우면 검증이 독립적이다.’** 같은 파싱 결과와 같은 검색 스니펫을 보는 에이전트들의 동의는 공통 원인 오류를 배제하지 않는다. 독립성을 주장하려면 서로 다른 원본 접근·검증 절차가 있는지 확인한다. Hugging Face 실험에서 협업이 의미 있는 이유는 서로에게 없는 숫자가 실제로 분산돼 있었기 때문이다.

**‘벤치마크 처리량이 높으니 실제 사용자도 빠르다.’** 추론 시험에서 파일 업로드, 이미지 렌더링, 수집, HTTP, 동시 사용자의 대기열은 빠질 수 있다. 지표의 분모가 페이지인지 토큰인지도 다르다. 사용자가 체감하는 경로를 조립해 별도 종단 간 지연을 측정하고, 평균과 p95를 함께 본다.

**‘공개 데이터와 레시피가 있으니 모든 문서에 적응할 수 있다.’** 합성 자료의 규모는 유용하지만 실제 고객 서식의 표, 스캔 품질, 언어, 기호는 다른 분포일 수 있다. 도메인 적응에는 이미지·정답 라벨의 품질과 독립 보류 집합, 검증기가 필요하다. NVIDIA의 치과 양식 사례는 정해진 생성기에서 높은 성공률을 보인 실험이지 임상 문서 일반에 대한 보증이 아니다.
