## 배경: 같은 날의 발표가 보여 주는 네 가지 서로 다른 전환

첫 번째 전환은 **능력 대비 비용**이다. 고성능 모델을 모든 요청에 쓰면 비용이 커지고 대기 시간이 길어진다. 반대로 가장 저렴한 모델만 쓰면 긴 절차의 중간 실패 때문에 재시도, 사람 검토, 복구 시간이 늘 수 있다. Terra 발표가 의미 있는 이유는 100만 토큰 단가라는 구입 가격을 낮춘 데만 있지 않다. 시각 입력을 읽고 컴퓨터를 조작하는 다단계 업무에서 어느 정도 품질을 유지하며 더 빠르게 끝낼 수 있는지를 이야기하기 때문이다. 다만 OpenAI의 벤치마크와 가격표는 업체가 제시한 조건이다. 조직이 다루는 화면, 문서, 언어, 접근 정책이 다르면 각자의 성능 곡선이 달라진다.

두 번째 전환은 **AI가 만든 결과의 지위**다. 코드나 초안에서는 모델 출력이 곧바로 사람이 검토할 작업물이라는 관행이 굳어지고 있다. 수학·과학의 새로운 정리 주장에는 이 관행을 그대로 적용할 수 없다. Lean에서 어떤 명제가 컴파일되는가, 형식화가 자연어 원고의 핵심 주장과 정확히 같은가, 보조 정리가 적합한가, 기존 문헌의 개념을 올바르게 번역했는가, 새 결과의 의미를 전문가가 합의했는가가 별개의 질문이다. OpenAI도 세 분야에 서로 다른 공개 방식을 택했다. 공개 산출물은 중요한 출발점이지만 완결된 사회적 검증이 아니다.

세 번째 전환은 **코드 생성 속도에 맞춘 독립 보안 검토**다. 코딩 에이전트가 만든 변경을 다른 에이전트가 검토하는 구성이 유망하더라도, 두 에이전트가 같은 데이터나 같은 잘못된 가정을 공유하면 오류가 함께 통과할 수 있다. 보안 스캐너의 경고, 에이전트의 추론, 샌드박스 재현, 인간 리뷰, 병합 권한은 단계별로 분리해야 한다. CodeRabbit 사례의 핵심은 ‘모델이 보안을 해결했다’가 아니라 **PR에서 종속성·공유 라이브러리·연결 저장소까지 영향 범위를 넓혀 보고, 확실한 것부터 사람이 조치하도록 연결한다**는 작업 흐름이다.

네 번째 전환은 **사용 패턴을 관찰하는 단위**다. AI 도입 담론은 흔히 사용자 수, 토큰 수, ‘몇 퍼센트의 일자리가 바뀐다’ 같은 거대한 숫자로 옮겨 간다. Signals는 대신 업무 활동이라는 분류 체계를 제공한다. 어떤 활동에서 질문을 하는지, 어떤 활동에서 산출물을 만들도록 요청하는지, 국가별 구성이 어떻게 변하는지 연구할 수 있다. 그러나 메시지 분류는 업무 성과나 자동화된 노동 시간을 직접 측정하지 않는다. 개인용 계정 사용자는 회사의 공식 시스템에서 일하는 모든 직원과 같지 않다. 데이터가 더 세밀해질수록 오히려 일반화의 경계도 세밀하게 써야 한다.

이 네 전환을 한 문장으로 묶으면 다음과 같다. **더 싸고 빠른 모델을 구매하는 것과, 그 모델이 낸 행동·주장·발견을 검증 가능한 사회기술적 절차에 넣는 것은 별개의 일이다.** 오늘의 뉴스는 모델 출시, 실험, 사용 데이터가 각각 그 절차의 다른 층을 보여 준다. 개발자는 입력 토큰 가격보다 작업 완료 정의를, 연구자는 발표의 규모보다 증거의 공개 범위를, 보안팀은 탐지량보다 수정과 재발 방지를, 제품팀은 메시지 점유율보다 사용자의 실제 업무 결과를 먼저 물어야 한다.

## 1. GPT-6.1 Terra — 가격표에서 업무 단위 원가까지

### 출시 사실과 비교 대상의 범위

OpenAI는 Terra를 GPT-5.6 Terra보다 진전된 빠르고 효율적인 모델로 소개한다. 표준 API 가격은 입력·출력·캐시 입력을 별도로 제시한다. 입력 100만 토큰 1달러, 출력 100만 토큰 5달러, 캐시 입력 100만 토큰 0.05달러다. 같은 발표는 GPT-5.6 Terra와 GPT-6.1 Sol의 표준 API 가격보다 50% 낮다고 말한다. 이 ‘50%’는 게시 당시의 표준 단가 비교이며, 모든 고객 계약과 일괄 처리, 저장된 프롬프트 캐시, 별도 도구 비용을 포함한 청구서가 정확히 절반이라는 의미가 아니다. 사용자는 실제 청구 항목과 캐시 적중률을 확인해야 한다.

OpenAI는 ChatGPT Work와 Codex의 Plus·Pro·Enterprise·Edu 사용자에게 Terra가 제공되고, API 개발자는 `gpt-6.1-terra`로 접근할 수 있다고 밝혔다. 플랜의 ‘같은 사용 허용량으로 더 많은 작업’이라는 설명은 API의 달러 단가와 다른 상품 조건이다. 팀이 앱의 백엔드를 API로 운영할 경우, 채팅 제품의 허용량을 서비스 원가 계산에 넣으면 안 된다. 반대로 사람이 Codex에서 일하는 도구와 API 기반 백오피스 자동화를 동일한 가격표로 비교해도 안 된다. 같은 모델 계열을 쓰더라도 제품별 과금·한도·실행 정책이 다르기 때문이다.

시각·컴퓨터 사용은 이번 출시의 중심이다. 공식 글은 기술 도면을 3D 모델로 만들거나 영상 샷을 장면별로 검토해 타임코드 로그를 만드는 전문 작업을 Agents’ Last Exam의 예로 든다. MMMU-Pro에서는 시각 추론을, OSWorld 2.1에서는 데스크톱 앱을 여러 단계로 조작하는 능력을 본다고 설명한다. 이 벤치마크들은 각각 입력과 채점 방식이 다르다. 정적인 이미지의 관계를 맞히는 능력, 실제 GUI에서 클릭·입력·저장을 끝내는 능력, 전문 과제를 독립적으로 완수하는 능력을 한 숫자로 바꿀 수 없다. 도면에서 치수를 읽는 능력과 CAD 도구의 권한·상태를 다루는 능력도 다르다.

공식 비교에 따르면 Agents’ Last Exam의 중간 추론 설정에서 Terra는 GPT-5.6 Terra보다 **15%포인트** 높은 점수를 약 **3분의 1** 비용으로 냈다. 여기서 15%포인트는 상대 15% 향상이 아니다. 예컨대 40%에서 55%라면 15%포인트이자 상대 37.5% 향상이다. 발표 원문에 그 절대 점수 전체가 모두 제시되지 않은 대목은 숫자를 임의로 복원하지 않는다. 또 GPT-6 Astra와 유사한 성능을 토큰당 약 10분의 1 가격으로 낸다는 설명과, Terra가 Astra·Sol보다 작업을 세 배 넘게 빨리 끝낸다는 설명은 각각 업체가 지정한 비교 조건의 결과다. 현장의 네트워크 지연, 도구 실행 속도, 승인 대기 시간까지 포함한 지표가 아니다.

### ‘싼 토큰’과 ‘싼 업무’는 다른 분모다

실무에서 모델 원가는 `입력 토큰 × 입력 단가 + 출력 토큰 × 출력 단가`만으로 끝나지 않는다. 도구 호출이 많은 에이전트에는 스크린샷·문서 업로드, 검색·브라우저·실행 환경, 캐시, 재시도, 컨텍스트 축약, 사람의 확인 시간이 붙는다. 컴퓨터 사용 작업에서 실패한 세션이 동일한 입력을 다시 읽고 화면을 처음부터 조작하면 단가가 낮아도 과제별 비용이 높아질 수 있다. 그러므로 가격 비교의 분모는 ‘요청 1회’보다 **검증된 완료 작업 1건**이 적절하다. 실패의 정의를 너무 관대하게 잡으면 비용도 왜곡된다.

가령 청구서 1,000건을 읽어 ERP에 입력하는 흐름을 시험한다고 하자. 단순 문서 인식에서는 공급자명, 금액, 세금, 계좌, 만기일을 추출하고 필드별 정확도를 본다. 실제 자동 입력에서는 중복 청구서 탐지, 거래처 마스터와의 일치, 승인자 확인, 저장 후 재조회, 수정 가능성을 같이 봐야 한다. 모델이 올바른 금액을 읽었지만 잘못된 거래처 카드에 저장했다면 작업 성공이 아니다. 브라우저가 입력 도중 만료되어 중복 등록을 했다면 재시도는 오히려 손실이다. 이처럼 과제의 최종 상태를 정의하지 않은 채 ‘토큰값 50% 인하’를 자동화 ROI로 바꾸면 숫자가 과도하게 낙관적이 된다.

원가 기록은 최소한 작업 ID, 모델 ID, 추론 설정, 입력·출력·캐시 토큰, 도구 호출 횟수, wall-clock 시간, 완료 여부, 사람 개입 시간, 재시도 횟수를 포함해야 한다. 민감한 원문 내용 자체를 로깅하지 않고도 이 메타데이터는 남길 수 있다. 작업의 난이도별로 나눠 보면 저난도에는 Terra가, 난도가 높은 소수에는 Sol 또는 Astra가 더 적합할 수 있다. OpenAI가 스스로 복잡한 코딩 과제에는 Sol과 Astra가 더 나은 선택이라고 적은 만큼, 모델 라우팅은 ‘모든 일을 최저가 모델로’가 아니라 **언제 승격해야 전체 비용이 줄어드는가**라는 문제다.

캐시 입력 단가는 특히 큰 프롬프트나 반복되는 정책 문서에 매력적이지만, 캐시 할인율을 모든 입력에 곱해서는 안 된다. 실제 적중 여부는 요청 형태, 캐시 정책, 메시지의 안정성에 달린다. 정책이 자주 바뀌거나 사용자별 자료가 앞부분부터 달라지면 할인 적용 비율이 낮아질 수 있다. 반대로 공통 작업 지침과 스키마가 안정적이라면 비용이 더 내려갈 수 있다. 비용 모델에는 ‘모든 입력이 일반 단가’와 ‘측정된 캐시 적중률’의 두 시나리오를 두고 실제 청구 로그로 갱신하는 편이 안전하다.

### 시각 인식에서 실행까지 이어질 때 검증점

컴퓨터 사용 에이전트의 오류는 단일 답변 오류보다 오래 남는다. 화면을 오독한 뒤 버튼을 잘못 누르고, 그 상태에서 다시 스크린샷을 읽으면 오류가 다음 단계의 정상 상태처럼 보일 수 있다. 모델이 ‘저장했습니다’라고 답해도 실제 서버에 반영되지 않았을 수 있고, 반대로 응답이 지연되는 동안 두 번 저장할 수 있다. 따라서 중요한 조작에는 **전후 상태 확인**이 필요하다. 예를 들어 문서 입력이라면 저장 버튼 누름이 아니라 저장된 레코드 ID와 조회 결과를 확인해야 한다. 일정 변경이라면 달력 화면의 표시와 API 응답, 참석자 통지 여부를 구분해야 한다.

평가셋에는 정상 화면만 넣지 않는다. 로그인 세션 만료, 한글·영문 혼합 레이블, 팝업과 모달, 반응형 레이아웃, 느린 로딩, 같은 이름의 두 대상, 접근 권한 거부, 읽기 전용 상태, 임시 저장과 최종 제출의 구분을 넣는다. 모델이 모르는 단계를 임의로 채우지 않고 중단·보고하는지도 점수로 본다. OpenAI는 Terra가 이전 세대보다 범위를 지키고 한계를 설명하는 경향이 높다고 주장하지만, 그 자체 평가가 우리 애플리케이션의 잘못된 제출을 막는다는 증거는 아니다. 앱의 상태 전이와 승인 게이트가 독립적으로 있어야 한다.

실행 권한도 단계별로 나누어야 한다. 읽기와 탐색은 비교적 낮은 위험이지만, 외부로 정보 전송, 금전 이체, 사용자 삭제, 공개 게시, 코드 배포는 영향이 크다. 작업이 최종 상태를 바꿀 때는 모델이 한 번 더 ‘정말 할까요’라고 쓰는 대화형 확인만으로 충분하지 않다. 시스템이 변경 대상·차이·범위를 사람에게 구조적으로 보여 주고, 승인된 경우에만 좁은 범위의 권한으로 실행하도록 설계해야 한다. 사용자의 명시적 승인 없이 외부 행동을 수행해서는 안 되는 작업을 모델이 화면에서 우회해 처리하지 못하게 API 측 권한을 묶는다.

### 사실성·코딩 평가를 읽는 법

공식 글의 내부 ‘오류를 유도하는 프롬프트’ 평가에서는 낮은 추론 설정의 오류율이 GPT-5.6 Terra **53.6%**에서 GPT-6.1 Terra **16.7%**로 내려갔다고 한다. 차이는 **36.9%포인트**다. 최대 추론 설정에서는 18%포인트 하락한 **4.3%**라고 한다. 이 변화는 인상적이지만 내부 평가의 프롬프트 구성과 정답 판정 기준을 알지 못하면 문서 요약, 코드 생성, 의료 정보, 사내 검색의 오류율로 그대로 옮길 수 없다. 모델이 모를 때 모른다고 말하는 능력, 잘못된 출처를 만드는 빈도, 계산·추론 오류는 현장별로 다른 검사가 필요하다.

Terminal-Bench 4.0에서는 최대 추론 설정의 Terra가 **50.3%**, GPT-5.6 Terra의 공개 점수가 **21.5%**로 소개된다. 이 평가는 커맨드라인에서 문제를 해결하는 코딩 에이전트를 대상으로 한다. 이미 있는 도구, 테스트, 컨테이너, 시간 한도, 문제 분포에 결과가 민감하다. 절대 점수가 절반가량이라는 사실은 모든 새로운 리포지토리 문제의 절반을 풀 수 있다는 보증이 아니고, 두 배 넘게 높아졌다는 사실은 코드 리뷰를 없애도 된다는 뜻이 아니다. 원문도 가장 복잡한 코딩 과제에는 Sol·Astra를 권한다. 코드 작성의 결과는 테스트 통과뿐 아니라 변경 범위, 보안, 성능, 유지보수성, 회귀 위험을 평가해야 한다.

Terminal-Bench-Science 0.1에서는 Terra가 최대 추론 설정에서 Sol을 넘고 특정 경쟁 모델과 다섯 점 이내에 들면서 추정 비용은 5분의 1 미만이라고 업체가 설명한다. 연구용 코딩 작업을 잘 수행한다는 결과와 새로운 과학 지식을 독립적으로 검증했다는 것은 다르다. 후자는 아래 과학 발표에서 다시 등장하는 구분이다. 평가상 강점이 특정 워크로드에 존재한다면 그 종류의 작업부터 시험하면 되지만, 벤치마크의 순위를 전체 연구 능력의 서열로 일반화해서는 안 된다.

### 안전 카드: 효율이 높아질수록 통제 비용도 설계해야 한다

Terra 시스템 카드 부록은 생물·화학 분야를 **High** 능력, 사이버보안 분야를 **Critical** 능력으로 취급한다고 적었다. 이 라벨은 OpenAI의 Preparedness Framework에 따른 내부 분류다. 생물·화학 설명에서는 Multimodal Troubleshooting Virology가 지표 임계값을 넘지만, 게시된 네 개의 Critical 능력 결과는 임계값을 넘지 않았다고 한다. 사이버보안 내부 Sandbox Bench는 실제 내부 시스템에서 영감을 얻은 런타임·파일 파서·egress 프록시 문제를 대상으로 한다. Terra는 22개 중 5개, Sol은 9개, Astra는 10개에서 성공했다고 카드에 나온다. 단순 비율로 적으면 각각 약 22.7%, 41.9%, 45.5%다.

이 숫자 역시 안전의 전체 점수는 아니다. 내부 샌드박스의 22개 대상이 조직의 배포 환경이나 공격면과 같지 않고, 모델 단독 응답과 실제 서비스의 감시·정책·격리 조치도 다르다. 시스템 카드 자체가 일부 안전 평가는 전체 프로덕션 안전장치가 없는 모델 응답 기준이라고 밝힌다. 보안팀은 모델 호출 전의 데이터 접근 제어, 도구 권한, 샌드박스 격리, 결과 검토, 로그 감사가 따로 작동하는지 봐야 한다. 상대적으로 저렴한 모델은 더 많은 자동화 시도를 가능하게 하므로, 요청 단위 위험이 낮아 보이더라도 전체 노출량이 늘어날 수 있다. 능력과 접근성을 함께 고려하는 이유다.

### 개발자에게 의미: 모델 라우터의 승격 기준을 미리 정한다

Terra를 첫 시도 모델로 쓰고 실패 시 Sol이나 Astra로 승격하는 전략은 합리적일 수 있다. 그러나 실패 판정이 ‘모델이 실패라고 말했다’ 하나에 의존하면 자신감 있는 오답은 통과하고 정직한 불확실성만 비싼 모델로 넘어간다. 외부의 정답 검사, 타입·스키마 검사, 실행 후 상태 확인, 위험 기반 규칙을 같이 써야 한다. 예를 들어 이미지에서 금액을 읽는 작업은 총액과 항목 합계의 일치, 통화·세율·거래처의 정합성으로 검사할 수 있다. 코드 변경은 목적한 테스트와 주변 회귀 테스트, 정적 분석, 리뷰 기준을 통과해야 완료다.

라우터에는 네 가지 출구가 있어야 한다. 첫째, Terra가 검증 가능한 작업을 완료하면 승인된 범위에서 종료한다. 둘째, 품질은 불확실하지만 수정 가능성이 높으면 같은 모델에 명확한 피드백을 한 번 제공한다. 셋째, 여러 번 재시도하면 오히려 비용·오류가 커질 때 상위 모델로 승격한다. 넷째, 개인정보·금전·보안 권한·불명확한 요구사항처럼 모델 선택으로 해결되지 않는 문제는 인간에게 넘긴다. 이 출구를 구현하지 않으면 ‘저비용 라우팅’은 잘못된 자동화의 반복이 될 수 있다.

모델 버전과 프롬프트를 동시에 바꾸지 않는 것도 중요하다. Terra를 도입하면서 프롬프트, 도구, 권한, 스키마를 모두 바꾸면 개선이나 악화의 원인을 찾기 어렵다. 기준 평가셋을 고정하고, 동일한 과제를 기존 모델과 Terra에 병렬로 돌리며, 오류 유형을 비교한다. 실서비스에서는 작은 트래픽부터 배포하고, 확인된 완료율·재시도율·취소율·사람 검토량·총원가가 기준을 만족하는지 본다. 회귀가 생기면 즉시 이전 라우팅으로 되돌릴 수 있도록 모델 ID와 설정을 배포 구성에 명시한다.

### 운영 포인트: 가격 인하 공지가 배포 계획의 종료가 아니다

운영자는 출시 당일 지역·계정·제품별 접근 가능 여부를 실제로 확인해야 한다. `gpt-6.1-terra` 식별자가 문서에 있어도 해당 계정의 한도와 도구 지원, 이미지 입력 형식, 레이트 리밋, 데이터 처리 계약을 별도로 확인해야 한다. 공식 발표의 성능표가 곧 조직의 가용성 약속은 아니다. 신규 모델을 필수 경로에 넣을 때는 지연 P50·P95·P99, 오류율, 큐 적체, 제한 응답, 캐시 변화와 공급자 장애 시 폴백을 기록한다. 컴퓨터 사용은 모델 응답이 끝나도 브라우저나 앱 작업이 진행 중일 수 있으므로, 전체 작업의 시간 제한과 중단 복구가 중요하다.

마지막으로 리스크 로그는 ‘모델이 잘못했다’는 문장보다 구체적이어야 한다. 어떤 화면 상태에서 어떤 행동이 선택됐고, 어떤 검증이 실패했으며, 실제로 어떤 외부 상태가 바뀌었는지를 구분한다. 민감 정보는 마스킹하고 원자료 보존 기간을 정한다. 도구 호출을 재현할 수 있는 최소 메타데이터와 변경 전후의 안전한 스냅샷이 있으면 장애 원인을 찾기 쉽다. 오늘 가격표의 숫자를 내일의 운영 성과로 확인하려면, 바로 이 관측성이 먼저 필요하다.

## 2. AI 생성 수학·과학 결과 — ‘증명 파일’에서 ‘학계의 이해’까지

### 세 결과를 같은 검증 단계로 묶지 않는다

OpenAI의 10월 26일 연구 발표는 수학, 계산복잡도, 물리학에서 모델이 만든 결과 세 묶음을 소개한다. 회사가 세 결과를 발표하는 방식부터 다르다. 수학 결과는 AI가 쓴 원고와 Lean 형식화 내용을 공개하고 연구자들이 자율적으로 검토하도록 했다. 계산복잡도 결과는 외부 전문가 그룹을 구성하면서 원고와 Lean 파일을 즉시 공개했다. 물리학 결과는 외부 전문가 그룹이 먼저 내용을 이해·정리하고 산출물 공개를 유예하기로 했다. 이 공개 경로의 차이를 무시하고 세 주장을 모두 ‘AI가 풀었다’는 한 문장으로 쓰면 검증의 현재 위치가 사라진다.

OpenAI는 해당 원고를 완결된 논문이라기보다 **원시 연구 데이터**로 읽는 것이 좋다고 밝혔다. 연구 공동체가 그 데이터를 독립적으로 해석하고 설명하는 데 시간이 필요하다는 취지다. 발표에는 투명성, 학술적 공로의 귀속, 외부 그룹의 독립성과 자발성을 네 원칙으로 적었다. 참여 연구자에게 비밀유지계약을 요구하지 않고, 참여 자체가 발견의 원저자라는 뜻도 아니라고 한다. 이 원칙은 바람직한 방향의 약속이지만, 실제 학술적 신뢰는 원고와 코드의 공개, 반례 탐색, 피어 리뷰, 후속 설명, 정정 가능성의 운영을 통해 형성된다.

검증의 층위를 나눠 보자. 첫 층은 파일 접근성이다. 외부인이 원고와 코드, 의존성, 빌드 방법을 볼 수 있는가. 둘째는 기계적 형식 검증이다. 특정 Lean 버전과 라이브러리 조건에서 정리가 컴파일되고 의도하지 않은 공리나 생략이 없는가. 셋째는 의미 대응이다. Lean의 정확한 명제가 자연어 원고가 주장하는 명제와 같은가. 넷째는 수학적 해석이다. 새로운 정리가 이미 알려진 사실을 다른 말로 쓴 것은 아닌가, 가정의 의미가 분야에서 받아들여지는가, 함의가 맞는가. 다섯째는 사회적 검증이다. 다양한 독립 전문가가 정리의 내용을 이해하고 오류·한계·새 아이디어의 위치를 공개적으로 토론하는가. ‘Lean에서 통과했다’는 둘째 층의 중요한 근거일 수 있지만 나머지 층을 대신하지 않는다.

형식화에 대한 경계는 형식 증명을 폄하하기 위한 것이 아니다. Lean은 지정된 논리 체계 안에서 정리와 증명 사이의 기계적 일관성을 강하게 보증할 수 있다. 그러나 사용자가 어떤 정리를 입력했는지, 자연어의 ‘모든 물리 이론’이 형식 명제의 정확한 양화 범위에 포함되는지, 현실 세계의 실험 사실을 설명하는지는 Lean이 자동으로 판단하지 않는다. 모델이 자연어 원고와 코드를 동시에 만들어 서로 유사한 방향으로 보이게 했더라도, 둘의 연결은 연구자가 검사해야 한다. 특히 엄밀한 존재성 정리와 물리적 예측의 실험적 성공은 다른 증거다.

### 수학: 국소 평활화, 카케야, 제한 추측을 어떻게 읽을까

발표의 수학 부분은 조화해석의 **국소 평활화(local smoothing)** 문제를 다룬다. 직관적으로는 파동의 집중이 최악의 한 순간에는 클 수 있어도 시간에 걸쳐 평균하면 더 제어된다는 성질이다. OpenAI는 모델이 모든 차원에서 해당 추측의 증명을 만들었으며, 이로부터 카케야 추측과 Stein의 restriction 추측도 해결된다고 주장한다. 원문은 새로운 보조 편미분방정식이 증명의 핵심이라고 설명한다. 과거의 관련 성과로 2차원 국소 평활화 증명과 3차원 카케야 결과를 언급한다. 기존 연구의 긴 계보를 지워 ‘AI가 처음으로 모든 것을 증명했다’고 쓰지 않는 이유다.

OpenAI가 링크한 [형식화 범위 문서](https://github.com/openai/math/blob/main/lean/docs/079.md)는 적어도 발표 주장을 좀 더 정확히 읽게 한다. 이 문서는 유클리드 반파동의 특정 (L^p) 국소 평활화 추정, Bochner–Riesz 승수 경계, 구면 extension 추정, 카케야 최대 연산자 경계, 유클리드 카케야 집합의 Hausdorff 차원이 전체 차원이라는 비교 명제를 열거한다. 해당 문서가 ‘모든 가능한 카케야 관련 명제’의 무제한 증명을 뜻하지 않는다. 수학적 주장에는 차원, 지수 (p), Sobolev 차수, 임의의 작은 양수 손실 같은 정확한 범위가 붙는다. 대중적 표제와 형식화 범위가 어떻게 맞물리는지 전문가의 해설이 필요한 이유다.

공개 시각도 구분할 필요가 있다. OpenAI는 모델 출력이 10월 18일 생성됐고 다음 날 Lean 형식화가 이뤄졌으며, 전문가와 논의한 후 10월 26일 발표와 함께 자료를 공개했다고 적었다. 따라서 오늘 뉴스의 날짜는 **발표일**이지 문제가 오늘 아침에 처음 풀렸다는 뜻이 아니다. 원고 제목의 날짜나 GitHub 경로의 날짜 역시 검토 완료일과 같지 않다. 공개 리포지토리의 현재 파일을 읽는 독자는 이후 커밋으로 내용이 바뀔 수 있으므로, 검증 보고서에는 커밋 해시와 Lean 의존성 버전을 남겨야 한다.

개발자에게 이 사례가 주는 교훈은 단순한 ‘AI도 수학을 한다’가 아니다. 새 알고리즘, 최적화, 보안 증명, 규제 보고서 등 **정확한 명제가 필요한 작업**에 모델을 쓰려면 사람이 의도한 명제와 실제로 검증된 명제의 대응표가 있어야 한다. 예를 들어 인증 로직의 ‘모든 사용자는 자기 정보만 본다’는 자연어 요구가 코드에서는 ‘로그인한 사용자에게 요청이 성공한다’는 약한 테스트로 바뀌면, 테스트가 통과해도 보안 요구를 증명하지 못한다. AI가 만든 형식 산출물에서는 바로 이 요구–명제의 차이가 핵심 검토 대상이다.

연구팀이 이 결과를 내부에서 검토한다면 첫 보고서에는 적어도 다섯 칸이 필요하다. 주장된 정리의 자연어 버전, Lean의 정확한 정리 선언, 사용된 주요 기존 정리와 공리, 재현한 빌드 환경, 독립 전문가가 아직 판단하지 못한 의미상의 쟁점을 적는다. 공개 원고의 설명을 그대로 복제하는 대신, ‘우리가 독립적으로 확인한 부분’과 ‘발표자의 설명에 의존한 부분’을 나눈다. 엄청난 발견이라는 기대가 클수록 작은 가정이나 범위 제한이 빠지기 쉽다. 판단을 늦추는 것이 무조건 회의적 태도는 아니다. 대단한 주장을 제대로 이해하기 위한 절차다.

### 계산복잡도: ETH 반박 주장의 정확한 대상

ETH(Exponential Time Hypothesis)는 대략적으로 SAT와 같은 문제에 특정 형태의 부분지수 시간 알고리즘이 없으리라는 오랜 추측이다. OpenAI는 모델이 ETH가 거짓임을 보였고, 나중에 Lean에서 형식화했다고 발표한다. 이 문장은 **P=NP를 증명했다**는 뜻도, 실무의 모든 조합 최적화가 내일부터 빠르게 풀린다는 뜻도 아니다. ETH는 P 대 NP와 관련 있지만 같은 명제가 아니다. 부분지수 시간의 이론적 상한은 여전히 매우 큰 문제에서 실용적 계산 시간을 보장하지 않을 수 있고, 상수와 입력 표현, 메모리 요구량이 응용 가능성을 좌우한다.

공식 발표는 이 결과의 이해와 설명을 위해 Russell Impagliazzo, Ramamohan Paturi, Ryan Williams가 이끄는 외부 그룹을 소개한다. Impagliazzo와 Paturi는 원래 ETH를 제안한 연구자들 가운데 두 명이라고 OpenAI가 적는다. 그들이 그룹을 이끈다는 사실은 고도의 검토가 예정돼 있다는 의미가 있지만, 오늘 시점의 독립된 최종 승인 도장은 아니다. 그룹은 공개된 자연어 원고와 형식 산출물을 토대로 가정·구성·기존 하한 결과와의 관계를 검토할 예정이다. 발표 주체의 설명과 외부 전문가의 향후 평가를 시간 순서대로 구분해야 한다.

[ETH 형식화 범위 문서](https://github.com/openai/math/blob/main/lean/docs/378.md)는 표제보다 더 세밀하다. 고정된 (k\ge2)에 대해 표준화된 (k)-CNF 입력의 만족 할당 수를 정확히 세는 결정적 기계의 시간 경계를 서술하고, 원고의 절 수 (m)에 따른 더 날카로운 경계와 선형 절 수의 경우를 구분한다. 문서에는 부분지수 시간과 다항 공간이라는 비교 문구가 있다. 이 정보는 흥미롭지만, 정의가 다른 SAT 인코딩 또는 실무 솔버의 평균 사례에 무조건 같은 속도를 준다고 결론낼 수 없다. 복잡도 정리는 흔히 최악 사례, 점근적 입력 크기, 고정 파라미터 조건에 관한 것이며, 실제 라이브러리 성능은 또 다른 실험 주제다.

이런 결과가 참이고 전문가가 의미를 확인한다면 파장은 클 수 있다. ETH를 가정한 수많은 조건부 하한 논문을 다시 읽어야 하고, 어떤 문제가 불가능에 가까운지에 관한 연구 로드맵이 바뀔 수 있다. 그렇더라도 **조건부 하한이 무효가 되는 것**과 **현장에서 바로 실행 가능한 빠른 알고리즘이 확보되는 것**은 다르다. 발표 원문도 더 빠른 실제 알고리즘을 찾고 이론적 진전을 실용적 개선으로 바꾸려면 추가 연구가 필요하다고 적는다. 보안 제품, 물류 최적화, 데이터베이스 쿼리 엔진이 당장 새 복잡도 정리에 따라 빨라진다는 기사로 바꾸면 안 된다.

개발자와 제품팀은 이 소식을 ‘최적화 문제를 다시 풀어 보자’는 연구 신호로 볼 수 있지만, SLA나 아키텍처를 변경할 근거로 삼기에는 이르다. SAT 솔버를 쓰는 업무라면 먼저 실제 입력 분포, 현재 병목, 근사 허용 여부, 하드웨어 비용, 입력 전처리 효과를 측정한다. 논문의 이론적 시간 복잡도가 검증되더라도 구현·상수·메모리 사용량·입출력 비용이 별도다. 학계의 정밀 검토가 진행되는 동안 제품 로드맵에는 ‘탐색’으로 기록하고 ‘확정된 성능 개선’으로 기록하지 않는 편이 맞다.

### 물리학: 원자료 미공개의 뜻과 엄밀성의 범위

세 번째 묶음은 4차원에서 게이지장과 페르미온을 포함하는 상호작용 양자장론의 엄밀한 존재성 결과다. OpenAI는 양자색역학(QCD)과 표준모형의 한 완성형을 포함하는 이론의 존재성 결과를 주장한다. 일부로 순수 Yang–Mills 이론의 존재성도 포함된다고 설명한다. 이 분야는 수학적으로 매우 정교하다. 물리학의 표준모형이 실험을 잘 설명한다는 사실과, 이를 특정 공리·구성에서 완전히 엄밀한 수학적 객체로 세울 수 있다는 주장은 다르다. 또한 특정 완성형의 존재성과 자연이 실제로 그 완성형을 선택했다는 실험적 주장은 다르다.

OpenAI는 David Gross가 Michael Douglas, Arthur Jaffe, Igor Klebanov, Nikita Nekrasov와 함께 결과를 검토하는 그룹을 이끈다고 밝혔다. 그룹은 모델 산출물을 바로 공개하기보다 직접 정리한 설명을 먼저 쓰기로 했다고 한다. 이는 관심 있는 외부인이 발표 당시 수학·컴퓨터과학 사례와 동일한 방식으로 원문을 재현하기 어렵다는 뜻이다. 공개 유예가 곧 결과가 틀렸다는 증거도 아니고, 유명한 연구자들이 참여한다는 이유로 이미 검증됐다는 증거도 아니다. 현재 확인 가능한 것은 **OpenAI의 주장과 공개 전략**까지다.

공식 글은 순수 Yang–Mills의 존재성이 Clay Mathematics Institute의 밀레니엄 문제 일부와 관련된다고 적는다. 그러나 관련된 문제의 한 구성 요소를 다뤘다는 설명과 **밀레니엄 문제 전체의 공식 해결 인정**은 다른 단계다. 구체적인 명제·가정·질량 간극 등 공식 문제 문구와의 관계는 산출물 공개와 전문가 설명을 기다려야 한다. 섣부른 ‘밀레니엄 문제 해결’ 제목은 과학의 범위와 공개 증거를 동시에 흐린다. 오늘 시점의 표현은 ‘OpenAI가 관련 엄밀한 존재성 결과를 주장했고 외부 그룹이 검토 중’이 가장 정확하다.

과학 발표에서 물리학 결과의 AI 출력은 9월에 만들어졌고, Lean 형식화 완료가 10월 중순이라고 OpenAI는 밝혔다. 발표가 늦어진 이유로 길이와 복잡성을 들었다. 이는 공개 날짜만 보고 생성·검증의 속도를 추정하면 안 된다는 예다. 원자료가 아직 공개되지 않았으므로 우리는 형식화가 어떤 정의와 공리를 채택했는지 직접 확인했다고 쓸 수 없다. 향후 산출물이 공개되면 정리의 정확한 범위, 기존 구성적 양자장론과의 연결, 물리학적 함의, 재현 절차를 별도로 검토해야 한다.

### 학술 공개 프로토콜의 가치와 한계

이번 발표에서 가장 실무적인 지점은 분야별로 **공개 방식 자체를 실험**한다는 것이다. 수학에서는 즉시 공개 후 커뮤니티가 자율 검토한다. 계산복잡도에서는 외부 그룹을 조직하되 원자료를 공개한다. 물리학에서는 외부 그룹이 원자료 공개를 유예하고 정리한다. OpenAI는 어느 방식이 가장 유용한지 아직 모른다고 적는다. 세 방식은 각각 빠른 공개, 집중된 해설, 오해 방지를 다르게 강조한다. 그러나 어떤 선택이든 처음 초대한 연구자가 정보와 해설의 방향을 먼저 갖는 비대칭성이 생길 수 있다는 점을 OpenAI도 인정한다.

연구 도구 개발자에게는 여기서 제품 기능을 생각해 볼 수 있다. AI가 생성한 수학 주장에는 단순 PDF보다 **명제 ID, 의존성 그래프, 소스 커밋, 형식 증명 상태, 알려진 검토 쟁점, 관련 선행 연구, 외부 검토자의 독립성**이 함께 표시되어야 한다. 수정판이 나오면 무엇이 바뀌었는지 추적할 수 있어야 한다. 반례 제안과 정정은 댓글 한 줄로 묻히지 않게 공식 이슈로 연결돼야 한다. 검토자의 공로를 원저자와 별도 표기하는 메타데이터도 중요하다. ‘AI가 썼다’는 기원 정보와 ‘누가 검증했다’는 신뢰 정보는 다른 필드다.

이 프로토콜은 일반 소프트웨어 개발에도 통한다. 에이전트가 만든 PR의 생성 모델, 사용한 도구, 대상 커밋, 실행 테스트, 실패한 테스트, 사람이 검토한 쟁점을 기록하면 나중에 문제를 찾기 쉽다. 그러나 소프트웨어에서는 보통 ‘배포 후 롤백’이 가능하고, 대형 수학 주장에서는 잘못된 제목이 학술 기록과 대중 이해에 오래 남는다. 연구 결과에 더 높은 표현의 신중함을 요구하는 것은 AI에만 적용하는 이중 잣대가 아니다. 모든 중대한 발견 주장에 필요한 일반적인 검증 순서다.

### 개발자에게 의미: 생성·검증·해석을 세 개의 워크플로로 만든다

AI 연구 도구를 만든다면 ‘증명 생성’ 버튼 하나에 세 기능을 숨기지 말아야 한다. 첫째, **생성**은 가설, 보조 정리, 코드, 설명을 제안한다. 둘째, **검증**은 컴파일·실험·대조·독립 재현을 수행한다. 셋째, **해석**은 결과가 어떤 개념과 기존 지식에 맞는지 분야 전문가가 설명한다. 생성에서 높은 점수를 받은 모델이 검증의 모든 역할을 맡으면 자기 산출물에 대한 독립성이 약해진다. 가능하다면 검증 환경은 생성 에이전트의 작업 환경과 분리하고, 사람이 직접 정리 선언과 가정을 읽을 수 있게 한다.

형식 검증 도구가 아니더라도 이 원칙은 쓸 수 있다. 데이터 분석 보고서에서 모델이 ‘매출이 증가했다’고 쓰면, 계산 코드와 원시 데이터 버전, 집계 정의를 따로 실행해 확인한다. 계약서 요약에서 모델이 ‘해지 수수료 없음’이라고 쓰면, 조항 위치와 예외 조건을 사람이 확인한다. 보안 진단에서 모델이 ‘재현됨’이라고 쓰면, 격리된 환경의 실행 기록과 영향을 받은 버전을 분리한다. 중요한 것은 서로 다른 역할의 증거를 한 모델의 유창한 문장 안에 섞지 않는 것이다.

### 운영 포인트: 놀라운 발견을 다루는 뉴스룸·팀의 체크리스트

기사가 큰 과학적 주장을 다룰 때는 날짜, 원 발표 주체, 공개 산출물, 독립 검토 주체, 현재 합의 수준, 미공개 부분을 한꺼번에 적어야 한다. 오늘의 수학·ETH 사례는 공개 원고와 Lean 범위 문서가 있지만, 그 내용의 학계 최종 평가까지 이 기사에서 수행한 것은 아니다. 물리학 사례는 원자료 미공개라는 더 큰 제한이 있다. 이는 출처 링크 수를 늘리는 것으로 해결되지 않는다. **읽을 수 있는 자료와 읽을 수 없는 자료를 구분**해야 한다.

팀 내부 지식베이스에는 기사 제목을 확정 사실로 넣기보다 상태를 둔다. 예를 들어 `발표됨`, `산출물 공개`, `독립 재현`, `전문가 해설`, `동료 심사`, `합의 형성`, `정정`처럼 기록한다. 새로운 검토가 나오면 상태와 요약을 갱신한다. ETH 관련 아키텍처 결정을 당장 하지 않는 것도 이 상태 관리의 결과다. 오히려 진짜 큰 발견이라면 검토 과정을 투명하게 남겨 오래 사용할 수 있는 지식으로 만드는 편이 발표일의 열광보다 가치가 크다.

## 3. CodeRabbit와 GPT-6.1 Sol — 코드 보안의 ‘발견’과 ‘수정’ 사이

### 발표에서 확인되는 사실과 확인되지 않는 수치

OpenAI는 CodeRabbit이 보안 에이전트의 **주 모델**로 GPT-6.1 Sol을 사용한다고 소개했다. ‘주 모델’은 유일한 모델이라는 뜻이 아니다. 원문은 다른 프런티어 모델과 보안 도구도 함께 사용한다고 명시한다. 따라서 특정 보안 발견을 전부 Sol 한 모델의 성과로 귀속하거나, 다른 모델을 썼을 때의 반사실적 차이를 계산할 수 없다. 발표는 PR 검토, 저장소 전반을 훑는 Deep Scan, 연동된 다른 저장소까지 보는 CodeRabbit Secure를 구분한다. 이는 새 모델 출시와 달리 **고객 활용 사례**를 설명하는 글이다.

OpenAI는 CodeRabbit이 수천 저장소와 조직에서 보안 관련 문제를 표시한다고 적는다. 이 표현은 규모에 관한 사업자 측 설명이지 품질의 분모가 아니다. 공개 글에는 검사한 PR 수, 확인된 진짜 취약점 수, 오탐률, 놓친 취약점 수, 심각도 분포, 평균 수정 시간, 비교 대상 스캐너의 설정이 함께 제시되지 않았다. CodeRabbit의 제품 페이지는 도달 가능성, 악용 가능성, 영향 범위를 판단해 노이즈를 줄인다고 설명한다. 그러나 제품 페이지의 설명도 독립 성능 평가와 같지 않다. 오늘 확인되는 것은 **워크플로와 제품 주장**이며, 공개 자료만으로 정량 우열을 매길 수는 없다.

‘AI가 보안 스캐너를 대체한다’고 쓰지 않는 이유는 이 시스템이 애초에 독립적인 기존 검사와 보완 관계로 설명되기 때문이다. 정적 분석기는 특정 언어의 데이터 흐름과 금지 API를 안정적으로 점검할 수 있고, 의존성 스캐너는 알려진 CVE와 버전 관계를 제공한다. 비밀 탐지 도구는 토큰·키 패턴을 빠르게 잡는다. 모델 기반 에이전트는 여러 파일과 서비스의 맥락을 읽고, 왜 변경이 접근 제어나 신뢰 경계를 깨는지 설명하는 데 이점이 있을 수 있다. 각 도구의 장점이 다르므로, 어떤 검사가 어떤 종류의 결함을 찾았는지 태그를 유지해야 한다.

### PR 단위 검사로 놓치기 쉬운 경계

보안 결함은 변경 파일 하나에만 있지 않다. 새 API 라우트는 정상처럼 보여도 다른 패키지의 인증 미들웨어가 특정 경로를 제외하거나, 공유 라이브러리의 직렬화 규칙이 다른 서비스와 다를 수 있다. 설정 파일 한 줄은 배포 환경의 정책을 약화할 수 있고, 프런트엔드의 접근 제한은 서버 권한 검사가 없으면 의미가 없다. OpenAI가 설명한 CodeRabbit 흐름은 이런 교차 파일·교차 구성요소 관계를 보려는 시도다. Deep Scan은 저장소의 넓은 범위를 살피고, CodeRabbit Secure는 연결된 저장소—예를 들어 공통 인증 라이브러리—까지 영향 범위를 확장한다고 한다.

그러나 범위를 넓히면 새로운 문제가 생긴다. 검토 모델에 더 많은 소스 코드와 설정을 제공해야 하고, 관련 없는 레거시 경고도 증가할 수 있다. 연결 저장소의 현재 배포 버전과 기본 브랜치가 다르면 ‘코드상 취약해 보임’이 실제 노출 상태와 다를 수 있다. 반대로 소스 저장소만 보고 운영 환경의 프록시나 IAM 정책을 놓칠 수도 있다. 보안 발견은 **코드 경로, 배포된 버전, 런타임 구성, 외부 도달 가능성**을 함께 확인해야 우선순위를 정할 수 있다. 저장소를 더 많이 읽는 능력이 배포 사실을 자동으로 알려 주지는 않는다.

조직이 평가할 때는 최소 네 유형의 문제를 별도로 만든다. 새로 추가된 명백한 입력 검증 실패, 기존 공통 라이브러리와 충돌하는 변경, 배포 설정에서만 드러나는 권한 문제, 실제로는 보호 장치가 있어 오탐이 되기 쉬운 코드다. 첫 유형만 잘 찾는 모델은 이미 정적 분석기가 담당할 수 있다. 두 번째와 세 번째에서 맥락 이해의 가치가 생기지만 평가가 어렵다. 네 번째는 팀의 신뢰를 지키는 데 중요하다. 경고가 많아도 검토자가 반복적으로 ‘위험 없음’을 누르면 고위험 경고까지 피로 속에 묻힌다.

### 샌드박스 검증: 좋은 신호지만 모든 탐지를 증명하지 않는다

OpenAI의 사례는 사용자가 선택한 발견에 대해 격리된 샌드박스에서 악용 가능성을 확인하려고 시도한다고 설명한다. **사용자가 선택한 발견**과 **시도**라는 단어가 중요하다. 모든 경고를 자동으로 재현한다는 말이 아니다. 재현이 성공하면 특정 조건에서 경로가 실제로 작동함을 강하게 뒷받침할 수 있다. 실패하더라도 취약점이 없다는 결론은 아니다. 테스트 데이터, 설정, 권한, 네트워크, 타이밍이 운영과 달라 재현되지 않을 수 있다. 반대로 샌드박스에서만 가능한 조합을 실제 배포 위험으로 과대평가할 수도 있다.

검증 환경은 생산 데이터와 분리해야 한다. 토큰은 일회성·최소 권한으로 제공하고, 외부 네트워크 접속과 파일 접근을 제한하며, 서비스 모의 객체와 테스트 계정을 사용한다. 파괴적 페이로드가 필요한 경우에는 더 엄격한 승인과 격리가 필요하다. 발표의 ‘생산 시스템에서 테스트하지 않는다’는 설명은 좋은 설계 방향이지만 조직은 자체 연결 설정이 실제로 그런 경계를 보장하는지 확인해야 한다. 자동 생성된 공격 시나리오와 로그는 민감한 내부 경로를 담을 수 있으므로 접근 통제와 보존 기간도 정해야 한다.

발견의 상태를 `가설`, `도달 경로 확인`, `샌드박스 재현`, `운영 영향 추정`, `수정 검토`, `배포 완료`, `재발 방지`로 나누면 팀 간 의사소통이 좋아진다. 샌드박스 재현이 됐어도 운영에 해당 버전이 없으면 노출 우선순위는 달라진다. 운영에 해당 버전이 있지만 재현이 실패했어도 민감 데이터 경로라면 추가 조사를 해야 한다. 모델의 자연어 설명을 상태 필드 대신 쓰면 어느 검증을 실제로 수행했는지 나중에 알기 어렵다. 보안 업무에는 문장력보다 **증거 사슬**이 중요하다.

### 수정 PR이 자동 생성돼도 병합 책임은 남는다

CodeRabbit Secure는 지원하는 문제에 대해 수정 PR 초안을 만들 수 있다고 한다. OpenAI 원문은 사람이 그 PR을 검토하고 승인한다는 점을 분명히 한다. 보안 패치는 결함 하나를 막으면서 호환성, 성능, 정상 사용자의 권한, 로깅, 데이터 마이그레이션을 바꿀 수 있다. 예를 들어 인증 검사를 추가했는데 내부 배치 작업까지 막거나, 예외를 모두 403으로 바꾸면서 문제 감지가 어려워질 수 있다. 사용자가 선택한 발견을 자동으로 고친다는 문구보다 **패치가 어떤 보호 속성을 회복하고 어떤 동작을 변경하는지**가 중요하다.

수정 PR에는 최소한 공격 경로 설명, 변경 전 실패하는 회귀 테스트, 변경 후 통과하는 테스트, 의도한 호환성 범위, 남은 미해결 경로가 있어야 한다. 재현 가능하지만 테스트가 없으면 같은 종류의 버그가 되돌아올 수 있다. 반면 테스트만 고쳐 통과시킨 PR은 실질적 보호 장치를 제공하지 않을 수 있다. 리뷰어는 코드를 쓴 에이전트와 수정 제안 에이전트가 같은 지시·문맥을 공유했는지도 알아야 한다. 두 에이전트가 서로를 ‘독립’ 검토한다고 소개해도 동일한 오해를 반복할 가능성은 남는다. 다른 종류의 검사와 인간의 위협 모델링이 필요하다.

취약점 수정은 배포 완료까지 추적해야 한다. PR이 병합됐어도 패키지 릴리스, 컨테이너 이미지, 배포 파이프라인, 여러 운영 인스턴스에 반영되지 않으면 노출이 남는다. 어제 이 블로그가 다룬 PHP 보안 패치와 연결되는 지점이다. 모델이 결함을 찾는 속도가 빨라진다고 실제 운영 시스템의 수정 속도가 자동으로 빨라지는 것은 아니다. 보안 메트릭도 경고 수만 세지 말고 **진짜 문제 확인까지 걸린 시간, 수정 승인까지 걸린 시간, 운영 반영까지 걸린 시간, 같은 종류 재발률**을 봐야 한다.

### 도입 평가: 일반 소프트웨어 품질 지표와 보안 지표를 함께

파일럿은 이미 정답이 알려진 내부 사례부터 시작할 수 있다. 과거에 수정한 취약 PR과 정상 PR을 섞되, 모델이 학습한 공개 예제만 반복하지 않는다. 팀이 실제로 사용하는 언어, 프레임워크, 마이크로서비스 경계, 인증·인가 구현을 포함한다. 결함이 없는 PR을 충분히 넣어야 오탐률을 추정할 수 있고, 드문 고위험 결함을 의도적으로 넣어야 누락 경향을 볼 수 있다. 취약점 여부를 사람이 사전에 판정하고, 에이전트는 그 정답을 보지 않게 하는 방식이 필요하다. 보안팀 간 의견이 갈리는 사례는 ‘정답 불명’으로 따로 표기한다.

측정 단위는 경고 한 줄이 아니다. 하나의 근본 원인에 여러 경고가 붙으면 경고 수가 늘어도 발견률은 오르지 않는다. 중복 제거 후 **고유한 결함 단위의 재현율**, 심각도별 정확도, 오탐으로 소요된 검토 시간, 수정 제안의 테스트 통과율, 실제 병합률, 패치 후 회귀를 본다. ‘수천 저장소’라는 공급자 규모 표현과는 다른 내부 분모다. 팀이 바쁜 주간에 경고를 감당할 수 있는지도 운영 지표다. 고위험 발견 1건을 빠르게 처리하는 것이 사소한 경고 100건보다 중요할 수 있다.

비교 대상을 정할 때는 기존 정적 분석·의존성 검사·수동 코드 리뷰가 켜진 정상 파이프라인과 비교한다. 검사기를 전부 끈 상태에서 AI만 켜고 좋은 결과가 나왔다고 해도 실제 증분 가치가 아니다. 반대로 AI 도구가 기존 검사 결과를 읽고 설명·우선순위화하는 가치가 있다면 그 기여를 별도 측정한다. CodeRabbit 사례 원문은 기존 스캐너를 보완한다고 적으므로, 실무에서 확인할 질문도 ‘기존 시스템 대비 어떤 취약점이 추가로 발견되거나 더 빨리 해결됐는가’여야 한다.

### 운영 포인트: 권한·비용·비밀의 경계

보안 에이전트는 소스 코드, 설정, 의존성, 이슈 기록을 많이 읽어야 유용하다. 그러므로 도입 계약과 기술 설정에는 코드가 어디로 전송되고 얼마나 보관되는지, 모델 제공자와 제품 제공자 사이의 처리 경로, 연결 저장소의 접근 범위, 비밀이 로그에 나타났을 때의 처리, 삭제·권한 회수 방법이 들어가야 한다. 공개 사례가 제품의 일반적인 데이터 처리 조건을 전부 설명하지 않는다. 실제 조직의 계정·지역·연결 방식에 적용되는 조건을 확인해야 한다. 최소 권한은 모델의 안전 성향이 아니라 저장소 토큰과 앱 설치 권한에서 강제된다.

실패 시 기본 동작도 명확해야 한다. 스캐너가 시간 초과하거나 모델 공급자가 장애를 겪을 때 모든 PR을 무조건 막으면 개발이 멈추고, 모든 PR을 통과시키면 의존한 보안 게이트가 사라진다. 위험도별로 분리할 수 있다. 일반 PR은 기존 검사와 인간 리뷰로 진행하되 고위험 영역은 수동 보안 검토를 요구하고, AI 경고가 없다는 이유만으로 승인을 자동화하지 않는다. 버전 업그레이드나 규칙 변경 후에는 오탐·누락 추세를 다시 본다. 원문은 사람이 최종 출시 결정을 맡는다고 했고, 운영 설계도 그 원칙에 맞아야 한다.

AI 보안의 본질은 ‘문제를 얼마나 많이 말하는가’가 아니라 ‘어떤 근거로 누가 무엇을 바꿨는가’다. 코드 생성 에이전트, 보안 에이전트, 인간 리뷰어의 각 권한과 기록을 분리하면 모델이 바뀌어도 책임 경계가 남는다. CodeRabbit 사례는 이 흐름의 한 구현을 보여 주지만, 우리 저장소와 업무의 품질은 자체 파일럿으로만 확인할 수 있다. 미공개 성능 숫자를 상상해 넣지 않고 검증할 질문을 남기는 편이 실무적으로 유익하다.

## 4. OpenAI Signals — ‘업무 메시지’와 ‘업무 성과’를 분리해서 읽는다

### 무엇을 어떤 범위에서 분류했나

OpenAI는 자사 Signals의 개인용 ChatGPT 사용 데이터를 O*NET의 **Intermediate Work Activities(IWA)** 165개와 연결해 공개했다. IWA는 여러 직업에 공통으로 나타나는 중간 수준의 업무 활동 분류다. 예컨대 자료 준비, 마케팅 콘텐츠 작성, 프로그래밍, 업무 데이터 분석처럼 직함보다 구체적이면서 개별 메시지보다 넓은 단위를 제공한다. 공식 글은 거의 100개국의 업무 관련 사용을 분기 단위로 볼 수 있다고 하며, 새 분석의 기간은 **2025년 1분기부터 2026년 3분기**다. 관련 개인용 데이터 페이지는 더 넓은 표본 기간을 2024년 7월부터 2026년 9월이라고 설명하므로, **사이트 전체의 데이터 범위와 이번 IWA 시계열의 범위를 혼동하지 않아야 한다.**

가장 중요한 표본 경계는 계정 유형이다. 이 분석은 **개인용 ChatGPT Free·Go·Plus·Pro의 메시지**를 대상으로 한다. 공식 설명은 Enterprise 메시지와 Codex 사용을 제외한다고 명시한다. 회사 안에서 팀이 공식 도구로 작성한 코드, 자동 에이전트의 실행 로그, 비공개 기업 워크플로는 이 데이터의 직접 관측 대상이 아니다. 개인이 업무 목적으로 ChatGPT에 질문한 메시지는 포함될 수 있으나, 조직 차원의 조달·배포·감사 정책과 같은 분모가 아니다. ‘거의 100개국’이라는 넓은 지리적 범위도 표본 대표성을 저절로 보증하지 않는다.

자료의 단위는 **메시지**라는 점도 중요하다. 사용자 한 사람이 같은 문제를 열 번 질문하면 메시지 열 건일 수 있지만 업무 열 건을 수행한 것은 아니다. 하나의 메시지에 긴 문서 작성 요청과 여러 작업이 들어 있을 수도 있다. 사용자가 답을 실제로 사용했는지, 시간을 절약했는지, 오류를 고쳤는지, 수입이나 생산성이 늘었는지는 메시지 분류만으로 알 수 없다. 공개 데이터는 사용의 방향을 연구하는 자료이지 업무 성과를 직접 측정한 실험이 아니다. 사용량과 가치의 관계를 볼 때는 이 분모 차이를 계속 기억해야 한다.

OpenAI는 개별 대화를 연구자가 직접 읽지 않는다고 설명한다. 식별 정보를 제거한 뒤 자동 시스템으로 메시지를 분류하고, 작은 집단은 결과를 공개하지 않으며, 통계적 노이즈를 더해 개인정보를 보호한다고 한다. 이 절차는 개인정보 보호에 중요하지만 분석상의 대가도 있다. 자동 분류의 오차, 특정 국가·언어의 표현 차이, 작은 집단의 누락, 노이즈의 영향이 세부 비교에 반영될 수 있다. 우리는 공개 설명만으로 각 IWA의 분류 정확도나 국가별 오차를 모두 확인할 수 없다. 작은 차이를 과도하게 해석하지 말아야 한다.

### 56.0%에서 51.1%로: 무엇이 변했고 무엇은 알 수 없나

공식 글의 눈에 띄는 숫자는 모든 분기에 관측된 **74개국**에서 상위 10개 업무 활동이 차지하는 각 나라의 분류된 업무 메시지 비율 평균이 **2025년 1분기 56.0%**에서 **2026년 3분기 51.1%**로 낮아졌다는 것이다. 차이는 4.9%포인트다. 상대 감소율로 표현하면 약 8.8%지만, 이 숫자를 굳이 강조할 이유는 적다. 중요한 해석은 업무 관련 ChatGPT 사용이 상위 소수 활동에만 덜 집중됐다는 **메시지 구성상의 변화**다. 이는 AI가 더 다양한 활동에 사용되고 있을 가능성을 보여 주지만, 사용 성과가 전반적으로 향상됐다는 증거는 아니다.

‘상위 10개’의 구성은 국가와 분기에 따라 달라질 수 있다. 전체 활동의 절대 메시지 수가 어떻게 변했는지, 표본 사용자 구성이 바뀌었는지, 분류 규칙이 안정적이었는지를 함께 봐야 세부 원인을 말할 수 있다. 집중도 하락은 기존 인기 활동의 감소 때문일 수도 있고, 다른 활동의 성장 때문일 수도 있다. 제품 기능이 새로 늘거나 접근성이 달라져 사용 방식이 변했을 수도 있다. 공식 글도 국가별 차이가 실제 일의 구성 차이 또는 AI 도구 접근 차이를 반영할 수 있다고 신중하게 적는다. 편집자가 단일 인과 원인을 붙이면 데이터 범위를 넘어선다.

특히 74개국은 거의 100개국 전체와 같은 분모가 아니다. 모든 분기에 꾸준히 관측된 국가만 넣어 시간 비교를 했다는 설명이다. 이 설계는 국가 구성의 변동을 줄이지만, 초기 데이터가 부족한 나라의 변화를 담지 못할 수 있다. 한국만의 활동 비율을 이 56.0%·51.1% 평균으로 추정해서는 안 된다. 국가별 데이터에서 다른 추세가 가능하다. 지리적 비교는 접속 가능성, 사용자 구성, 언어, 산업 구조, 요금제 보급, 개인정보·기업 정책 같은 요소의 영향을 받을 수 있다.

### O*NET 연결이 주는 연구 기회와 과도한 해석

O*NET의 장점은 직업별 실제 활동에 대한 별도 자료와 ChatGPT 메시지의 주제를 연결할 수 있다는 것이다. 단순히 ‘기획자는 AI를 많이 쓴다’보다 어떤 업무 활동—정보 수집, 자료 설명, 보고서 작성, 관계자 조율 등—에서 AI에 무엇을 요청하는지 묻기 좋다. OpenAI는 미국 일자리의 업무 활동 분포와 ChatGPT 사용 분포를 나란히 보는 시각화를 제공한다. 그러나 원문은 두 분포가 크게 다르며, 미국 고용 가중 활동의 약 **43%**가 개별 공개 범주 밖의 `Other IWAs`에 들어간다고 설명한다. 여기에는 물품 이동, 차량 운행, 의료 기록 유지처럼 원래 표본에서 충분히 일관되게 나타나지 않은 활동이 포함된다.

이 43%는 AI가 그 업무를 절대로 도울 수 없다는 뜻도, 그 업무를 이미 자동화했다는 뜻도 아니다. **ChatGPT 개인용 메시지로 포착되는 활동과 노동시장 전체 활동의 관측 범위가 다르다**는 신호다. 실제 직업은 화면 밖의 물리적 작업, 협업, 책임, 규제 절차를 포함한다. 화면에 텍스트로 나타나는 부분만 세면 직업의 일부가 잘릴 수 있다. 반대로 하나의 기획 업무가 ChatGPT에서 여러 문서·코드·분석 메시지로 쪼개져 과대표집될 수 있다. O*NET 연결은 비교의 출발점이지 직접적인 자동화율 계산 공식이 아니다.

연구자가 데이터를 쓴다면 세 질문을 구분하면 좋다. 첫째, **관측된 사용:** 어떤 종류의 메시지가 언제 어느 나라에서 늘었는가. 둘째, **가능한 메커니즘:** 접근성, 제품 기능, 직무 구성, 언어, 요금제가 그 변화를 설명하는가. 셋째, **결과:** 실제 품질·시간·임금·고용·고객 만족이 변했는가. 공개 Signals는 첫 질문에 직접 도움을 주고 두 번째의 가설을 만들 수 있다. 세 번째에는 별도 설문, 실험, 기업 운영 데이터 또는 노동시장 통계가 필요하다. 한 데이터셋이 모든 질문에 답한다고 홍보하면 분석의 신뢰가 떨어진다.

### 제품 개발자가 이 데이터로 할 수 있는 일

제품팀은 ‘사람들이 많이 쓰는 활동’ 목록을 곧바로 기능 우선순위로 옮기기보다, 자신의 사용자 집단에서 반복되는 **구체적인 실패와 완료 상태**를 찾는 데 참고할 수 있다. 예를 들어 글쓰기 메시지가 많다는 사실만으로 새 에디터를 만들어야 하는 것은 아니다. 사람들이 기존 도구에서 초안 작성, 사실 확인, 이해관계자 승인, 버전 관리 중 어디서 막히는지 알아야 한다. 프로그래밍 메시지가 늘어도 회사의 주요 비용이 코드 작성 시간인지, 리뷰·테스트·배포 대기인지 확인해야 한다. Signals는 탐색 가설을 만드는 지도이지 개별 제품의 사용성 조사 결과가 아니다.

165개 IWA 분류를 내부 고객 조사에 그대로 쓰는 것도 신중해야 한다. 이 분류는 여러 직종의 업무를 공통 언어로 묶는 데 유리하지만, 고객의 실제 업무를 결정하는 승인 단계, 민감 정보, 특정 규제, 타 시스템과의 연결은 별도 필드가 필요하다. 좋은 발견 인터뷰는 ‘어떤 AI 도구를 원하십니까’보다 ‘지난주 어떤 업무에서 어떤 자료를 받아 어떤 결정을 누구에게 전달했고 무엇을 다시 수정했습니까’를 묻는다. 활동 이름은 그 대답을 정리하는 데 도움이 되지만, 업무 흐름의 대체물이 아니다.

또 개인용 메시지 사용은 회사의 공식 구매 의사와 다르다. 조직은 보안·법무·운영 조건이 맞지 않으면 직원들이 개인적으로 자주 하는 활동을 기업 서비스로 도입하지 않을 수 있다. 반대로 개인용 데이터에는 거의 나타나지 않는 반복적인 백오피스 작업이 API·배치 자동화에 더 큰 경제적 가치를 가질 수도 있다. B2B 제품 로드맵은 내부 파일럿의 품질과 운영 비용, 구매자·사용자·정보보호 담당자의 요구를 같이 봐야 한다. 공개 개인용 데이터는 이 질문을 대신해 주지 않는다.

### 데이터 거버넌스: 표본·분류·업데이트를 함께 보존한다

Signals 자료를 보고서에 재사용한다면 숫자 하나만 캡처하지 않는다. 자료 버전, 조회일, 기간, 국가 필터, 모집단, 메시지 분류 범주, 노이즈·억제 정책, 인용 형식을 기록한다. OpenAI의 다운로드·방법 페이지는 Signals v3.0이라는 인용 정보를 제공하고 CC BY 4.0 라이선스를 명시한다. 라이선스의 출처 표시 요구를 지키는 동시에, 표나 차트가 새 버전에서 달라질 수 있다는 점을 독자에게 알려야 한다. ‘2026년 10월 27일 확인’이라는 발행 기준도 그 맥락이다.

데이터를 조직의 자체 로그와 연결할 때는 개인정보 위험이 커진다. 공개 집계의 활동 분류를 사내 사용자별 업무 성과 평가로 바로 쓰면 원래의 공개 목적과 다른 감시가 될 수 있다. 개인 메시지의 분류 정확도와 개인의 능력·노력을 동일시해서도 안 된다. 필요한 것은 실제 제품의 사용 개선을 위한 집계 분석인지, 특정 직원의 행동 추적인지 목적을 구분하고 권한·보존 기간을 정하는 일이다. OpenAI가 공개 데이터에서 작은 그룹을 억제하고 노이즈를 더하는 이유 역시 개별 대화의 식별 가능성을 줄이기 위해서다. 조직이 더 상세한 원자료를 가진다고 같은 보호 의무가 없어지는 것은 아니다.

### 운영 포인트: 지표의 분모를 잃지 않는다

활동별 사용량을 KPI로 삼는다면 메시지 수, 활성 사용자 수, 고유 작업 수, 성공한 작업 수를 따로 보고해야 한다. 사용자가 같은 질문을 여러 번 반복하는 것은 열성 사용일 수도 있지만 답변 품질 문제일 수도 있다. 총 메시지가 늘어도 완료율이 낮아지면 제품 경험은 악화됐을 수 있다. 업무 활동의 ‘다양화’도 새로운 활동의 만족도가 낮다면 성공이라고 할 수 없다. 공개 Signals가 보여 주는 집계 구성 변화와 우리 제품의 결과 지표는 서로 보완적인 층이다.

오늘 공개된 숫자로 만들 수 있는 가장 정직한 운영 질문은 ‘우리 사용자가 AI를 어떤 활동에 가져오고, 그 활동에서 무엇을 완료했다고 확인할 수 있는가’다. 활동별로 오류와 사람 재작업, 민감 자료 처리, 과제별 비용을 측정하면 제품 개선 방향이 잡힌다. 오히려 거대한 ‘AI 사용률’ 하나보다 이 세밀한 질문이 개발 우선순위에 도움이 된다. Signals의 관찰은 사용자 행동을 더 잘 묻기 위한 시작점으로 활용하고, 노동시장 전체의 결론은 다른 근거와 함께 검토해야 한다.

## 다섯 발표를 한꺼번에 읽는 개발자 실행안

### 1단계: 발표의 종류와 증거의 종류를 표기한다

오늘의 다섯 항목은 동일한 ‘뉴스’이지만 증거가 다르다. Terra의 가격·API 식별자는 공급자가 게시한 현재 상품 조건이다. Terra의 성능 숫자는 공급자의 특정 평가 결과다. 시스템 카드의 High·Critical은 공급자의 위험 분류다. 과학의 원고와 Lean 파일은 검토할 수 있는 연구 산출물이다. CodeRabbit 사례는 고객·공급자 측의 업무 구현 설명이다. Signals는 표본과 분류를 거친 집계 관찰이다. 이들을 같은 확신 등급으로 쓰면 의사결정자가 ‘어느 숫자를 계약 조건으로, 어느 숫자를 실험 가설로 써야 하는지’ 알 수 없다.

팀의 조사 문서에 `발표 사실`, `제공자의 주장`, `공개 산출물로 재현한 사실`, `외부 독립 검토`, `우리 조직에서 측정한 결과`를 별도 열로 두자. 예를 들어 `gpt-6.1-terra`라는 API 식별자와 가격은 공식 발표에서 확인했다. 특정 한국어 ERP 화면의 자동 입력 성공률은 아직 확인하지 않았다. ETH 자연어 원고와 형식화 범위는 공개됐지만 이 글에서 증명 내용을 독립 검증하지 않았다. CodeRabbit의 제품 흐름은 공식 사례로 확인했지만 오탐률 숫자는 공개되지 않았다. 이처럼 확인된 부분과 미확인 부분을 함께 적으면 경영진 보고에서도 지나친 확신을 피할 수 있다.

공식 발표의 문장을 그대로 옮길 때는 주어도 유지한다. ‘OpenAI는 50.3%를 보고했다’와 ‘Terra는 우리 업무의 절반을 해결한다’는 완전히 다른 문장이다. ‘OpenAI는 ETH 반박을 주장하고 Lean 산출물을 공개했다’와 ‘학계가 ETH 반박을 확정했다’도 다르다. 기술 담당자가 이 차이를 지켜야 구매·투자·연구 방향의 결정을 왜곡하지 않는다. 공식 출처를 썼다는 사실만으로 출처가 평가한 범위를 넘어서는 독립적 사실이 생기지는 않는다.

### 2단계: 모델 실험의 단위를 사용자 업무로 만든다

Terra 파일럿에서 먼저 할 일은 테스트 프롬프트를 수백 개 모으는 것이 아니라 **업무 완료 판정**을 쓰는 것이다. 예를 들어 기술 도면에서 목록을 만든다면 치수·기호·단위의 정확도가 중요하다. 실제 CAD 변환까지 한다면 파일을 열 수 있는지, 구조가 편집 가능한지, 원본과 비교했을 때 누락이 없는지 봐야 한다. 청구서 처리라면 인식 정확도에 중복 등록 방지와 승인 상태를 더한다. 회의 문서 작성이라면 좋은 문장보다 참석자·결정·담당자·기한의 근거가 중요할 수 있다. 모델 성능의 단위는 사용자가 기다리는 최종 상태에 맞춰야 한다.

난도별 표본을 만든다. 쉬운 예는 비용 비교에는 좋지만 실패 경계를 찾지 못한다. 복잡한 화면, 부정확한 스캔, 두 후보가 모두 그럴듯한 입력, 파일이 잠긴 경우, 저장 후 서버 오류가 나는 경우를 포함한다. 기대 동작에는 정답뿐 아니라 중단·추가 질문·수동 이관도 허용한다. ‘무조건 자동 완료’만 성공으로 취급하면 모델이 불확실성을 숨기도록 잘못 보상할 수 있다. 안전하게 중단한 사례와 근거 없이 진행한 사례를 구분해야 한다.

측정은 품질·시간·비용을 동시에 한다. 성공률이 조금 높아도 P95 지연과 사람 검토 시간이 크게 늘면 사용자 경험은 악화할 수 있다. 반대로 단가가 절반이어도 성공률이 내려가 재시도·수정이 늘면 총비용은 증가한다. 일반 입력과 캐시 입력의 비중을 구분하고, 상위 모델로 승격한 비율을 기록한다. 간단한 비교식은 `총비용 / 검증된 완료 작업 수`이며, 분자에는 API 청구뿐 아니라 재시도와 필수 검토 시간을 포함한다. 업무 중요도가 높은 경우에는 실패의 예상 손실도 따로 추정한다.

### 3단계: 에이전트 행동과 보안 검토를 서로 다른 권한으로 둔다

컴퓨터 사용과 코드 보안은 모두 ‘에이전트가 행동한다’는 표현으로 묶이지만 권한 모델이 다르다. 화면을 읽는 권한, 임시 초안을 만드는 권한, 외부 상태를 바꾸는 권한, 비밀에 접근하는 권한, 보안 테스트를 실행하는 권한, 코드를 병합하는 권한을 하나의 토큰에 담지 않는다. Terra 기반 자동화는 사용자의 승인 범위 안에서 도구를 다루고, CodeRabbit 기반 검토는 발견·샌드박스 검증·수정 PR 초안까지만 맡길 수 있다. 사람에게 넘기는 시점을 기술적으로 정의해야 안전성이 대화상의 예절에만 의존하지 않는다.

감사 기록도 업무별로 나눈다. 코드 보안 발견에는 어떤 커밋과 파일, 경로, 스캐너 결과, 재현 조건을 봤는지가 필요하다. 화면 조작에는 어떤 상태에서 어떤 버튼을 누르고 어떤 결과를 확인했는지가 필요하다. 모두 원문 전체를 무기한 보관할 필요는 없으며, 오히려 비밀과 개인정보가 쌓일 수 있다. 최소한의 재현 가능한 메타데이터를 정하고 목적별 보존 기간을 둔다. 설명 가능한 오류 기록은 공급자 모델을 바꾸더라도 같은 검증 절차를 유지하게 해 준다.

### 4단계: 연구 결과는 빌드 가능성과 의미 검토를 따로 추적한다

수학·계산복잡도 결과를 기술 블로그나 내부 세미나에서 다룰 경우, 공개 리포지토리의 특정 커밋을 고정하고 Lean 환경을 재현한다. 그다음 어떤 명제가 어떤 기존 정리를 호출하는지 정리한다. 그러나 컴파일 성공 화면을 보여 준 뒤 ‘따라서 전체 과학적 의미가 확인됐다’고 발표하지 않는다. 자연어 원고와 형식 명제의 대응, 분야의 선행 연구, 전문가의 해설이 이어져야 한다. 물리학 결과처럼 원자료가 아직 공개되지 않은 경우에는 재현 불가 상태를 명확히 표기하고 발표자의 요약 외에는 독립 확인할 수 없다고 말한다.

AI가 만든 연구의 공로도 무시할 수 없다. 새 아이디어를 이해하기 위해 노력한 외부 연구자, 기존 정리의 원저자, 정리의 약점을 발견한 검토자, 형식화 시스템을 구축한 개발자가 서로 다른 기여를 한다. OpenAI는 외부 그룹이 이해와 해설에 대한 인정을 받아야 하며, 자사는 모델 발견에 대한 학술 공로를 요구하지 않는다고 썼다. 공개 라이선스, 인용, 수정 이력, 검토자의 독립성을 기록하면 연구 공동체가 검증 결과를 공정하게 사용할 수 있다. 이는 과학뿐 아니라 오픈소스의 AI 생성 패치에도 적용할 수 있는 원칙이다.

### 5단계: 사용 데이터를 ‘자동화율’로 번역하지 않는다

Signals의 IWA는 제품 수요를 탐색할 때 매력적이다. 하지만 메시지에서 활동을 분류한 비율을 업무 시간의 비율, 일자리의 대체율, 기업의 구매 의사로 바꾸는 단계에는 추가 근거가 필요하다. 활동별로 얼마나 많은 사람이 접근할 수 있는지, 한 사람이 몇 개의 메시지를 남기는지, 메시지가 실제 결과로 이어졌는지, 기업 정책 때문에 특정 활동은 공식 도구에서만 이뤄지는지 조사해야 한다. 특히 Codex와 Enterprise가 빠져 있으므로 개발팀과 대기업의 사용 패턴을 직접 추론할 수 없다.

실무의 좋은 연결 방식은 공개 자료로 가설을 만들고 내부 조사로 확인하는 것이다. ‘업무 활동이 다양해졌다’는 발표를 보고 고객 인터뷰에서 새로운 활동이 등장하는지 살핀다. 자사 로그에서는 개인정보 보호를 유지하면서 작업 완료율과 수정률을 본다. 기업의 구매자는 감사·접근통제·비용 한도를 확인한다. 세 종류의 자료가 같은 방향을 가리킬 때 제품 확장을 결정한다. 어느 한 자료에서만 큰 숫자가 나왔다는 이유로 범용 자동화를 선언하지 않는다.

## 오늘의 운영 체크포인트

- **모델 도입:** `gpt-6.1-terra`의 실제 계정 접근, 기능·도구 지원, 레이트 리밋, 데이터 처리 조건, 청구 로그를 확인한다. 표준 가격과 조직 계약 가격을 분리한다.
- **업무 측정:** 요청 성공이 아니라 검증된 최종 상태를 성공으로 정의한다. 재시도·사람 개입·상위 모델 승격까지 총비용에 포함한다.
- **컴퓨터 사용:** 읽기·초안·제출·외부 전송의 권한을 나누고, 중요한 작업에는 변경 전후 상태를 확인한다. 세션 만료와 중복 제출을 별도 실패 유형으로 본다.
- **안전성:** 시스템 카드의 위험 분류를 참고하되, 실제 격리·도구 권한·로그·승인과 동일시하지 않는다. 내부 벤치마크 수치를 자신의 공격면으로 외삽하지 않는다.
- **코드 보안:** PR 경고의 근거와 배포 버전을 연결한다. 샌드박스 재현, 수정 PR, 인간 승인, 운영 반영을 서로 다른 상태로 관리한다.
- **연구 검증:** 공개 원고·Lean 파일·빌드 환경·명제 범위·독립 해설의 상태를 표시한다. 물리학 산출물은 현재 공개 유예라는 사실을 숨기지 않는다.
- **데이터 분석:** Signals의 모집단은 개인용 ChatGPT 메시지임을 적는다. 74개국 시계열 비교와 거의 100개국의 지리적 범위를 다른 분모로 취급한다.
- **배포 후 관측:** 새 모델이나 보안 도구를 한 번에 전면 도입하지 않는다. 작은 범위에서 오류 유형, 사람 검토량, 비용, 롤백 조건을 확인한다.

## 맺음말

오늘의 발표는 AI의 경계가 넓어지는 모습을 서로 다른 각도에서 보여 준다. Terra는 더 저렴한 시각·컴퓨터 사용과 코딩 능력을 제시한다. CodeRabbit 사례는 그 능력을 코드 보안 검토에 배치하는 방식이다. Signals는 개인이 AI를 어떤 업무 활동에 가져오는지 측정할 틀을 준다. 수학·과학 발표는 모델이 생성한 고난도 결과를 공동체가 어떻게 검증할 것인가라는 더 어려운 질문을 던진다. 네 갈래를 한 가지 낙관론이나 비관론으로 묶을 필요는 없다.

개발과 운영의 공통 기준은 단순하다. **누가 무엇을 주장했는지, 공개 증거가 어디까지인지, 실제 업무에서 어떤 최종 상태를 확인했는지**를 나누어 기록한다. 가격은 청구서와 완료 작업으로, 모델 능력은 우리 평가셋과 안전 경계로, 보안 발견은 재현과 배포로, 과학 주장은 형식화와 독립적 해석으로, 사용 데이터는 표본과 실제 성과로 검증한다. 그 과정을 통과할 때 오늘의 인상적인 발표가 내일도 쓸 수 있는 지식이 된다.
