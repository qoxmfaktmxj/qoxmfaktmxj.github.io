## 배경 — ‘더 강한 모델’보다 더 넓은 시스템 경계

모델 성능 발표만 따라가면 이번 네 건이 서로 무관해 보인다. PHP 보안 사고는 전통적인 웹 운영 문제이고, Git 저장소의 잠금 범위는 분산시스템 문제이며, 클라우드 모델 공급은 구매 문제, 이용 정책은 법무 문제로 분류하기 쉽다. 그러나 AI 에이전트가 실제 제품과 개발 흐름에 들어오면 네 범주가 한 업무 경로에서 만난다. 에이전트가 코드 변경을 만들고 Git에 푸시하고, 배포 파이프라인이 웹 서버를 갱신하며, 모델 호출은 조직의 데이터 경계와 제공사의 정책 안에서 실행된다. 코드 제안의 품질이 좋아도 취약한 런타임이 남아 있으면 서비스가 안전하지 않고, 푸시가 성공해도 기본 브랜치 병합이 막히면 개발 속도는 오르지 않으며, 모델 제공 경로가 다양해져도 감사와 정책 적용이 불명확하면 운영 승인에 걸린다.

이 때문에 오늘의 뉴스는 **능력**, **가용성**, **안전성**, **책임**을 분리해서 읽어야 한다. PHP 버전 검사 도구는 위험 신호를 찾는 능력이다. 패치가 모든 실제 워커에 반영됐는지는 배포 상태다. GitHub의 참조별 동시성 설계는 저장소의 특정 쓰기 패턴 처리 능력이다. 조직의 자체 CI와 리뷰 큐가 빨라졌다는 증거는 아니다. 클라우드 모델 정식 발표는 접근 경로가 생긴다는 뜻이다. 원하는 지역에서 특정 데이터 보관 옵션으로 호출 가능한지는 별도 확인이 필요하다. 정책 문구가 명확해졌다는 사실은 어떤 앱의 중개성 여부가 자동 판정된다는 뜻이 아니다.

발표 수치를 자신의 서비스 수치로 가져오지 않는 것도 중요하다. GitHub의 3~4배는 현실적인 내부 트래픽으로 실시한 특정 아키텍처 시험 결과다. Google Cloud의 ‘단일 플랫폼’은 사용자의 IAM, 청구, 로그가 실제로 어떤 제품 경로를 거치는지 살펴야 의미가 있다. OpenAI의 취약점 탐지·조정 발표는 협업에 대한 자체 설명이며 개별 PHP 운영자의 노출 범위를 알려주지 않는다. 다음 절은 각 발표의 사실, 개발자에게 필요한 판단, 운영 시 검증 항목을 분리한다.

## 1. PHP 긴급 패치 — AI가 결함을 찾아도 배포 완료까지는 운영자의 일

### 무엇이 공개됐고 누가 영향받는가

PHP 공식 보안 공지는 CVE-2026-109618을 메모리 부족 처리 중 내부 요청 데이터가 부분 초기화 상태로 남고 정리 코드가 이를 유효한 데이터처럼 다룰 수 있는 결함으로 설명한다. CVE-2026-109619는 요청 소유 내부 상태가 해제된 메모리 이후에도 남아 다음 요청에서 재사용될 수 있는 결함이다. PHP 프로젝트는 둘 다 인증되지 않은 원격 코드 실행으로 이어질 수 있다고 밝히고, PHP-FPM, Apache `mod_php`, `php-cgi`, FrankenPHP, LiteSpeed를 포함해 **웹 요청을 받는 PHP 설치**를 경고한다. 특히 `mod_php`에서는 애플리케이션 코드가 실행되기 전 요청으로 공격이 시연됐다고 설명한다. 이 설명은 일반적인 WordPress 플러그인 하나의 결함이 아니라 런타임 계층의 문제라는 점을 보여준다.

공식 수정 버전은 PHP 8.2.35, 8.3.36, 8.4.27, 8.5.12다. 오래된 8.1 이하 버전은 PHP 프로젝트의 일반 지원 범위 밖이다. 일부 배포판·LTS 공급자가 백포트한 수정 패키지를 줄 수 있으므로 `php -v` 출력 숫자만으로 취약·안전을 판정해서도 안 된다. 반대로 신규 버전의 컨테이너 이미지를 받았다는 사실만으로 실행 중인 워커 전체가 교체됐다고 결론 내릴 수도 없다. 이미지 태그가 고정됐거나 롤링 배포 일부가 남아 있다면 서비스는 이전 바이너리를 계속 쓸 수 있다.

10월 23일의 추가 공지는 매우 구체적이다. `session.serialize_handler`를 설정에서 `php_binary` 또는 `php_serialize`로 두었다가 애플리케이션 실행 중 `ini_set()`으로 `php`로 바꾸고 `session_start()`를 호출하며, 세션 업로드 진행 기능까지 켜져 있는 드문 조합에서 남은 원격 코드 실행 경로를 막기 위해 `session.upload_progress.enabled=0`을 다음 정규 버그 수정 릴리스 전까지 권고했다. 이미 21일 공지의 완화책으로 이를 적용했다면 유지하라고 한다. **설정 조합이 드물다는 문장을 근거로 전체 업데이트를 미루면 안 된다.** 21일의 두 취약점에 대한 공식 권고는 여전히 패치 버전 적용이다.

### 개발자에게 의미: 감지, 수정, 확인의 세 단계를 섞지 않는다

OpenAI가 공개한 `php2shell-checker`는 외부 URL의 `X-Powered-By`·`Server` 헤더 또는 로컬 설치 정보에 근거한 **버전 경고 도구**다. 외부 모드는 먼저 `HEAD`를 보내고 405·501일 때만 `GET`을 시도한다. 리다이렉트나 응답 본문은 조사하지 않으며 익스플로잇 요청을 보내지 않는다. 헤더가 없거나 해석할 수 없으면 `UNKNOWN`, 광고된 버전이 공식 수정 릴리스 이상이면 `OK`, 영향 범위이면 `POTENTIALLY VULNERABLE`을 준다. `UNKNOWN`은 안전이 아니다. `OK`도 광고된 문자열에 대한 판단일 뿐 백엔드 워커, 로드밸런서 뒤의 다른 인스턴스, 실제 패치 수준을 증명하지 않는다. 배포판의 백포트가 있으면 구 버전 문자열만 보고 불필요하게 위험으로 분류할 수 있다. 이 도구는 **자산 발견의 보조 수단**으로 써야 한다.

실무의 첫 단계는 외부에서 보이는 사이트 이름이 아니라 실행 환경의 목록을 만드는 것이다. VM 패키지, FPM 풀, 컨테이너 이미지, CI 작업용 PHP, 관리형 호스팅, 플러그인 테스트 환경을 분리한다. 각 서비스의 런타임 버전과 패키지 공급자, 노출 경로, 업데이트 책임자를 함께 기록한다. 두 번째는 PHP 프로젝트 또는 공급자의 패치 아티팩트를 식별하고 스테이징에서 애플리케이션 호환성을 확인한 뒤 배포하는 것이다. 세 번째는 패치된 패키지나 이미지가 실제 모든 워커에서 돌아가는지 확인하는 것이다. 성공 기준을 ‘배포 파이프라인 종료’가 아니라 **실행 중인 워커의 빌드·재시작 확인**으로 둔다.

공식 공지는 즉시 업데이트가 어렵다면 일부 공격 경로의 노출을 줄이는 설정을 제시하지만 ‘완전한 안전’이라고 하지 않는다. 예를 들어 업로드 진행 기능 비활성화와 워커 재시작이 한 경로를 막을 수 있어도 다른 변형 가능성이 남는다. 메모리 제한 조정 역시 예상하지 못한 자원 소모라는 가용성 비용을 만들 수 있다. 따라서 완화책은 별도 변경 기록과 만료일을 가진 임시 조치로 취급하고, 보안 릴리스 배포를 뒤로 미루는 근거로 삼지 않는다.

### 운영 포인트: AI 발견의 속도와 패치 공급망의 속도는 다르다

OpenAI는 자사 프로그램에서 GPT-5.6 Sol을 사용한 연구자가 결함을 찾았고 Wiz도 독립적으로 같은 취약점들을 발견·보고했으며, PHP 유지보수자가 수정과 릴리스를 주도했다고 설명한다. OpenAI가 제시한 다섯 단계는 상류 프로젝트의 검증·수정, 영향을 받는 조직의 준비 시간, 정부·기반시설 파트너와의 조정, 배포판·호스팅 사업자의 업데이트 준비, 공개 후 사용자 검증이다. 이는 모델이 취약점을 찾아냈다는 이야기보다 **발견부터 실제 패치 적용까지의 공급망**이 길다는 점을 드러낸다.

운영팀은 사고 대응 표에 ‘최초 발표 시각’만 적지 말고, 공급자별 수정 패키지 확보 시각, 배포 시작·종료, 워커 재기동, 서비스 테스트, 로그 검토 결과를 남겨야 한다. 공개 이후에는 알려진 취약 버전 스캔이 증가할 수 있으므로 외부 노출 서비스부터 우선순위를 매긴다. 다만 공격 징후가 없다는 것은 침해가 없었다는 확정이 아니다. 고위험 서비스에서 기존 워커의 이상 종료, 예상치 못한 프로세스, 웹 서버·애플리케이션 로그 변화를 별도로 조사한다. 새로운 수정 버전이 나온 뒤 기존 임시 완화책을 해제할 때도 한꺼번에 원복하지 않고 구성 이유와 부작용을 검토한다.

## 2. GitHub의 Git 아키텍처 — 브랜치가 다르면 왜 함께 기다려야 했나

### 저장소 단위 잠금이 에이전트 쓰기에서 병목이 되는 이유

GitHub의 10월 21일 기술 글은 데이터센터에서 Azure로 저장소를 옮기는 이행 상태를 공개한다. 전체 저장소의 99.99999%가 두 환경에 함께 복제돼 있고, 일반적으로 한 저장소는 다섯 복제본을 가지며 두 복제본이 Azure에 있다는 설명이다. Azure가 Git 트래픽 약 절반을 처리하지만, 가장 바쁜 소수 저장소는 약 25ms의 지역 간 왕복 지연 때문에 이동이 어렵다고 한다. 숫자 99.99999%는 ‘모든 저장소가 신형 아키텍처로 이전됐다’는 뜻이 아니다. 이 글의 핵심은 **남은 초고부하 저장소를 옮기기 위한 과도기 설계**다.

기존 구조에서는 쓰기를 커밋할 때 복제본 과반의 동의가 필요하다. 그러나 실제로는 건강한 모든 복제본의 응답을 타임아웃까지 기다렸다고 GitHub는 설명한다. 느린 원격 복제본 하나가 매 쓰기 지연에 영향을 주고, 저장소 전체 잠금이 커밋 시점까지 유지되면 서로 다른 브랜치에 대한 푸시도 한 줄로 선다. 에이전트 A가 `feature/a`를 갱신하고 에이전트 B가 `feature/b`를 갱신하는 것은 일반적으로 서로 순서가 필요 없는 작업인데도, 저장소 전체 잠금은 이를 불필요하게 직렬화한다. 요청이 늘면 대기열 길이가 늘고 각 요청은 이전 요청의 지역 간 지연까지 간접적으로 부담한다.

Git의 일관성 요구를 더 좁게 보면 핵심은 **각 참조의 순서**다. 동일한 `main` 참조를 갱신하는 두 푸시는 정확한 순서와 충돌 처리가 필요하다. 반면 다른 브랜치의 ref 변경은 대부분 독립적이다. GitHub는 쿼럼의 직렬화 범위를 저장소 전체에서 ref별로 줄이겠다고 설명한다. 내부의 현실적인 트래픽 시험에서 서로 다른 ref의 쓰기 처리량이 3~4배 높아졌다는 자체 결과를 제시한다. 이 수치를 모든 저장소의 `git push`가 4배 빨라진다고 옮기면 안 된다. 같은 `main`으로 몰리는 병합이나 리뷰 승인, CI 큐, 네트워크 왕복 자체는 여전히 제한이 될 수 있다.

### 객체 저장소와 가상 복제본: 읽기를 쓰기 쿼럼에서 떼어낸다

GitHub는 대부분의 저장소에서 읽기와 쓰기의 비가 약 100:1에서 1,000:1이라고 설명한다. 현재는 읽기·쓰기가 같은 영속 복제본을 사용해 캐시 메모리와 압축·정리 작업의 자원을 나눠 쓴다. 계획한 다음 단계는 Azure Blob Storage를 내구성의 원천으로 두고, 이를 쿼럼의 특별한 멤버처럼 표현하는 **가상 쓰기 복제본**을 도입하는 것이다. 이 복제본은 읽기를 제공하지 않고 쓰기 스트림을 객체 저장소에 내구적으로 저장한다. GitHub의 설계 설명에 따르면 저장소가 쓰기를 승인하는 시점에는 객체 저장소에 영속화돼 있어야 한다. 독립 ref의 트랜잭션을 한 번의 객체 저장소 I/O 묶음으로 처리할 수 있다는 점도 강조한다.

이후 가상 읽기 복제본은 쿼럼에 들어가지 않고 객체 저장소에서 캐시를 데워 읽기 트래픽을 받을 수 있다. 읽기 수요에 맞춰 늘리고 줄이는 계산 계층과, 참조 순서를 보장하는 쓰기 계층을 구분할 수 있다. 그러나 기술 글은 초기 가상 읽기 복제본이 백그라운드 동기화를 하므로 **모든 종류의 읽기 요청에 즉시 적합하지 않다**고 명시한다. 모든 읽기를 제공하려면 요청 경로에서 변경된 ref와 데이터만 보충하는 후속 작업이 필요하다. 즉 목표 아키텍처와 현재 구축 상태를 한 문장으로 합쳐 ‘GitHub 읽기는 모두 객체 저장소에서 즉시 일관되게 제공된다’고 쓰면 틀린다.

### 개발자에게 의미: 에이전트 병렬화의 단위를 작업 종류와 맞춘다

여러 에이전트가 한 저장소에서 작업한다면 서로 다른 브랜치로 초안을 제출하게 하는 것은 저장소의 쓰기 경합을 줄일 수 있다. 그러나 이것은 저장소 서버의 한 층만 해결한다. 변경이 한 기본 브랜치로 합쳐질 때는 코드 충돌, 브랜치 보호, 필수 리뷰, 동일 테스트 자원의 대기가 여전히 생긴다. 특히 많은 에이전트가 같은 설정 파일이나 의존성 잠금 파일을 자주 수정한다면 ref는 달라도 나중의 머지 비용이 커진다. 에이전트 수를 늘리기 전에 **동시 푸시 처리량, PR 리뷰 대기, 머지 큐, CI 시작·종료, 재기반·충돌 비율**을 구분해 측정해야 한다.

GitHub가 공개한 3~4배 시험은 GitHub의 스토리지 설계에 대한 결과다. 자체 GitLab, Gitea, 사내 Git 서버에 ‘ref별 직렬화’만 붙이면 같은 수치를 얻을 것이라는 근거가 아니다. 객체 저장, 복제, 라우팅, 캐시 일관성, 가비지 컬렉션까지 같이 설계해야 한다. 다만 설계 원칙은 재사용 가능하다. **무엇이 정말 전역 순서를 요구하는지 먼저 묻고, 나머지 병렬 작업을 그 순서의 잠금 밖으로 뺀다.** 에이전트가 만든 수많은 독립 변경을 하나의 전역 큐에 묶으면 모델 호출을 늘려도 전체 처리량이 늘지 않는다.

### 운영 포인트: 새로운 용량은 새로운 일관성 검증이 필요하다

저장소 서버를 운영하는 조직은 ref별 쓰기에서 같은 ref의 경쟁, 강제 푸시, 삭제와 재생성, 중간 장애, 복제본 지연을 시험해야 한다. 독립 ref의 성공률만 보고 일관성을 증명할 수 없다. 객체 저장소가 영속 원천이 되면 그 쓰기의 확인 시점과 계산 노드 장애 뒤 복구 순서가 중요해진다. 읽기 캐시의 오래된 ref가 푸시 직후 API나 CI에 보이면 사용자 입장에서는 Git이 거짓말을 하는 것과 같다. 현재 GitHub 글도 가상 읽기 복제본의 초기 백그라운드 조정에는 한계가 있다고 인정한다. 자체 운영자의 테스트 계획에는 ‘성공한 푸시 직후 같은 ref를 다시 읽는 경로’가 반드시 들어가야 한다.

팀에서 지금 당장 적용할 수 있는 것은 성능 수치의 복제가 아니라 병목 지도다. 저장소 서버의 지연, 작업별 브랜치 갱신 속도, 기본 브랜치의 머지 큐, CI 가동률을 각각 그래프로 보고 가장 긴 대기 구간을 찾는다. 서버가 푸시를 4배 많이 받아도 테스트가 느리면 배포 빈도는 그대로다. 반대로 저장소 서버가 병목이 아닌데 에이전트 수만 늘리면 리뷰 업무와 보안 검토의 부하가 늘 수 있다. GitHub가 설계에서 인간의 리뷰와 브랜치 보호를 유지한다고 강조한 이유도 여기에 있다.

## 3. Google Cloud의 OpenAI 모델 — ‘선택권’의 실제 단위를 확인한다

### 발표의 현재형과 미래형을 분리하기

Google Cloud의 공식 글은 GPT-6 Astra, GPT-6.1 Sol, GPT-6 Luna를 Model Garden에서 선택된 기업 고객에게 **비공개 프리뷰**로 순차 제공한다고 밝힌다. OpenAI의 공식 글은 일반 제공을 향후 몇 주에 계획한다고 설명한다. 두 원문을 같이 읽어야 ‘출시’라는 홍보 표현과 현재의 접근 가능 범위를 구분할 수 있다. 지원 지역, API 형태, 할당량, 모델별 기능, 버전 고정, 가격을 모든 고객에게 동일하게 공개한 일반 제공 발표는 아니다. 마찬가지로 Google Antigravity와 기업용 Gemini 제품 안에서의 사용은 ‘곧 제공’될 기능으로 서술돼 있다.

Google Cloud는 자사 플랫폼에서 폐쇄형 주요 모델 세 계열을 선택할 수 있고 200개 이상의 모델을 한 플랫폼에서 다룰 수 있다고 강조한다. 이 숫자만으로 어떤 팀이 원하는 모델이 원하는 지역·요금제로 즉시 사용 가능한지 알 수 없다. Model Garden의 카탈로그 수와 조직의 실제 승인된 모델 수는 다르다. 평가할 때는 동일한 작업·입력 분포에 대해 각 모델의 성공률과 지연, 비용을 직접 비교해야 한다. 모델 이름을 ‘상위/하위’로 붙이기보다 업무별 오류 비용과 툴 사용 패턴에 맞춰 라우팅 기준을 정한다.

청구 측면에서는 Google Cloud Marketplace 거래, 한 청구서, 기존 클라우드 사용 약정의 차감, Flexible Savings Plans 적용을 설명한다. 이것은 구매·예산 관리의 실익이 될 수 있다. 그러나 한 청구서가 원가의 단순함을 보장하지는 않는다. 토큰 단가, 캐시 과금, 도구 실행, 네트워크 이동, 로그 보관, 서드파티 서비스 결합 비용을 실제 계약서와 사용량으로 계산해야 한다. 자체 엔드포인트와 클라우드 경유 엔드포인트를 비교할 때 단순한 모델 단가뿐 아니라 기존 GCP 약정과 지원·운영 비용까지 같이 계산한다.

### 데이터 경계와 거버넌스: 발표 문구를 검증 가능한 질문으로 바꾸기

Google Cloud는 고객의 프롬프트·문맥·출력이 지정한 데이터 경계 내에 남고 기초 모델 훈련에 쓰이지 않는다고 설명하며, 전용 인프라와 격리 게이트웨이, 인증 ID, VPC Service Controls, 감사 로그를 강조한다. 동시에 **Zero Data Retention 옵션과 Confidential Compute는 ‘coming soon’**으로 적는다. 따라서 현재 프리뷰에서 이미 모든 고객이 ZDR 또는 기밀 컴퓨팅을 쓸 수 있다는 표현은 잘못이다. 의료·금융·인사 자료 같은 민감 정보를 넣기 전에는 현재 계약과 실제 서비스 문서에서 보관·삭제·운영자 접근·지원 인력 경계가 무엇인지 확인해야 한다.

‘데이터가 클라우드 안에 남는다’는 말도 네트워크만의 문제가 아니다. 모델 호출 전 RAG 검색이 다른 인덱스를 거치고, 에이전트가 외부 SaaS 도구를 호출하고, 로그·트레이스에 원문 프롬프트가 남으면 전체 업무의 데이터 경계는 그 모든 시스템을 포함한다. 동일한 IAM 주체로 호출했다고 해서 플러그인의 접근 권한까지 자동으로 제한되지는 않는다. 프로젝트별 서비스 계정, 모델 호출 권한, 도구 권한, 인덱스 권한, 로그 열람 권한을 분리한다. 감사 로그에는 모델 이름만이 아니라 실제 요청의 주체, 리전, 데이터 분류, 도구 호출, 차단 사유를 연결할 수 있어야 한다. 민감한 본문은 불필요하게 로그에 복제하지 않는다.

### 개발자에게 의미: 모델 교체 가능성의 한계도 함께 설계한다

모델을 ‘동적으로 바꿀 수 있다’는 플랫폼의 설명을 애플리케이션의 무비용 교체로 해석하면 안 된다. 같은 프롬프트라도 모델마다 함수 호출 형식, 구조화 출력 준수율, 긴 문맥에서의 오류, 안전 정책 거절, 지연 분포가 달라질 수 있다. 모델별 어댑터와 공통 평가셋을 갖추고, 응답 스키마 검증과 실패 재시도 범위를 분리한다. 에이전트에서는 한 단계의 도구 호출 실패가 다음 열 단계에 전파될 수 있으므로 단일 질의 정답률보다 **완료율, 재시도 횟수, 도구 오류, 비용/완료 과제**를 봐야 한다.

프리뷰를 시험한다면 프로덕션 전체를 이동하기 전에 데이터가 비식별화된 대표 과제로 시작한다. 동일한 작업을 기존 경로와 Google Cloud 경유 경로에 보내 출력 품질, 첫 토큰까지의 시간, 전체 완료 시간, 비용, 로그·추적 가능성을 비교한다. 장애 때 기존 모델이나 다른 경로로 폴백하려면 공급자마다 다른 오류 코드와 할당량 정책을 다뤄야 한다. 프리뷰의 서비스 수준과 향후 일반 제공의 서비스 수준은 다를 수 있으므로 가용성 가정도 분리한다.

### 운영 포인트: 공급 경로가 늘수록 계약·정책·감사의 책임이 늘어난다

Google Cloud를 통하면 조직의 구매와 IAM 체계에 통합할 가능성이 생긴다. 그러나 사고 조사 때는 어느 기업이 어떤 로그를 보유하고, 지원 요청에 누가 접근하고, 정책 위반은 어느 경로에서 차단되는지 알아야 한다. OpenAI는 Microsoft가 여전히 주요 클라우드 파트너라고 적었다. 이는 이번 발표가 단일 공급자 독점이나 즉각적인 전체 인프라 이전을 뜻하지 않는다는 맥락이다. 멀티클라우드 모델 접근은 선택권을 늘리지만, 운영자는 공급 경로별 **모델 버전·정책 버전·비용·장애·데이터 처리 계약**을 관리해야 한다.

## 4. OpenAI 이용 정책 — 모델 라우터와 일반 앱의 경계

### 11월 20일 발효 예정인 조항을 지금 읽는 이유

OpenAI는 10월 21일 글에서 서비스 제공 경로가 늘어도 비슷한 안전 기준이 적용돼야 한다고 설명했다. 파트너가 모델에 접근을 제공할 때 안전 장치 유지, 위반 조사, 적절한 조치와 집행 협조를 요구하는 정책이라고 한다. 수정된 이용 정책은 **2026년 11월 20일 발효 예정**이라고 표시된다. 오늘 시점에 이미 모든 조항이 발효됐다고 쓰면 틀리고, 아직 미래이므로 무시해도 된다고 판단하는 것도 실무상 위험하다. 새 서비스를 출시하거나 판매 계약을 맺는 일정이라면 사전에 제품 유형을 분류할 시간이 필요하다.

정책 원문은 제3자가 OpenAI 모델을 **직접 이용하게 하는 모델 접근 중개 플랫폼 또는 기타 서비스**를 운영할 경우 사전 검토·승인을 요구한다고 한다. 모델 라우터, AI 게이트웨이를 예시로 든다. 한편 애플리케이션이 모델을 통합해 자사 기능을 제공한다는 이유만으로 이 요건이 적용되는 것은 아니라고 분명히 적는다. 예를 들어 사용자가 인사시스템에서 휴가 규정을 검색·요약하는 기능과, 고객이 범용 API 키처럼 모델 호출을 임의로 만들어 쓰는 서비스는 경계가 다를 수 있다. 실제 분류는 UI 문구 하나가 아니라 고객이 모델에 어느 정도 직접 접근하는지, 프롬프트와 도구를 누가 통제하는지, 재판매 구조가 무엇인지 살펴야 한다.

### 개발자에게 의미: 정책을 배포 가능한 기술 요구로 바꾸기

중개 경로에 해당할 가능성이 있는 서비스는 모델을 호출하는 API만 구현해서는 충분하지 않다. 고객·최종 사용자 식별과 권한, 남용 조사에 필요한 로그, 계정 도용·유출 키의 분리 대응, 위험한 작업의 승인·차단, 이의 제기 경로를 제품 구조에 넣어야 한다. OpenAI 글은 최종 사용자를 식별하되 신원을 OpenAI에 직접 알려주지 않으려는 SafetyIDs를 고객과 함께 도입 중이라고 설명한다. 아직 발표 단계인 이 기능을 현재 모든 API에서 사용 가능하다고 가정하지 않는다. 조직이 구현할 수 있는 것은 우선 내부적으로 추적 가능한 사용자·조직 식별자를 일관되게 전달하고, 실제 제공 규격이 공개되면 프라이버시 설계와 맞춰 반영하는 것이다.

정책을 이유로 모든 사용자 프롬프트 원문을 무제한 저장하는 것도 잘못된 해결책이다. 사고 대응에 필요한 최소 이벤트, 정책 결정 결과, 요청 식별자, 시각, 모델·라우팅 경로를 우선 기록하고 민감 본문은 별도 보존 기준에 따른다. 모델 제공 경로가 직접 API와 파트너 클라우드로 나뉠 때 같은 고객의 집행 상태가 서로 불일치하지 않는지 확인해야 한다. 자체 라우터에서 우회 경로가 열리면 안전 정책과 고객 계약 모두 의도와 달라질 수 있다. 단, 발표사의 정책 목적 설명과 특정 고객에게 적용되는 실제 계약은 다를 수 있으므로 상용 배포 판단은 현재 계약·정책 전문을 함께 확인한다.

### 운영 포인트: 모델 선택권과 일관된 통제는 함께 설계한다

OpenAI는 직접 제공, 호스팅 파트너, 리셀러 간에 일관된 안전 기준을 목표로 한다고 밝혔다. 이것이 모든 제공 경로의 성능, 지연, 데이터 보관, 법적 역할이 같다는 뜻은 아니다. 정책 집행이 여러 사업자에 걸치면 의심 사건의 탐지부터 조사·정지·복구까지 담당과 시간을 합의해야 한다. 한 곳에서 차단된 키가 다른 경로에서 그대로 작동한다면 정책은 이름만 동일하다. 반대로 오탐으로 전체 기업 계정이 중지되면 정상 사용자까지 피해를 본다. 사용자 단위의 최소 권한, 분리 가능한 키, 이의 제기·재개 절차가 중요하다.

새 정책은 ‘모델 접근 중개’에 대한 사전 승인뿐 아니라 민감한 고위험 행위의 인간 검토, 다른 모델을 대체하기 위한 훈련 데이터 생성 제한 등 여러 조항을 담는다. 이 글은 모든 조항의 법률적 해설이 아니라 **AI 제품 설계자가 당장 확인해야 할 제공 경로와 책임 경계**에 초점을 맞춘다. 개인용 앱이 모델 API를 쓰는 것과 범용 모델 이용 권한을 고객에게 판매하는 것을 구분하고, 정식 이용 전에는 최신 정책과 계약 조건을 다시 읽는 것이 실무적으로 정확하다.

## 다섯 가지 실행 질문 — 오늘의 발표를 팀의 점검 항목으로 바꾸기

1. **보안:** 우리 서비스의 PHP는 무엇이 실제로 실행 중인가? 이미지 저장소의 태그나 CI 성공 기록이 아닌, 각 워커의 바이너리·공급자 패치 기록·재시작 시각을 확인했는가? 외부 헤더에 버전이 없어서 `UNKNOWN`이 나온 서비스는 별도 자산 조사로 연결됐는가?
2. **개발 흐름:** 병렬 에이전트가 서로 다른 ref를 갱신하는 작업과 같은 `main` ref를 갱신하는 작업을 구분했는가? 푸시 처리량이 아니라 PR 대기·리뷰·머지·CI까지 포함한 완료 시간을 보고 있는가?
3. **모델 공급:** Google Cloud의 현재 프리뷰에서 실제 사용할 수 있는 모델·리전·할당량·기능·요금은 무엇인가? ‘향후 제공’으로 표시된 ZDR, Confidential Compute, 제품 통합을 현재 운영 요건에 이미 포함시키지 않았는가?
4. **데이터와 감사:** 프롬프트, 검색 문맥, 출력, 에이전트 도구의 데이터가 각각 어디에 저장되고 누가 볼 수 있는가? 한 청구서로 묶인다고 감사와 사고 대응의 단일 책임자가 자동으로 생기는 것은 아니다.
5. **정책:** 우리 제품은 특정 업무 기능에 모델을 내장하는 앱인가, 아니면 고객이 범용 모델 접근을 직접 얻는 중개 서비스인가? 11월 20일 발효 전 검토가 필요한 경로를 목록으로 만들었는가?

## 용어와 숫자를 잘못 읽지 않기

- **`99.99999%`는 새 Git 아키텍처의 전체 배포율이 아니다.** GitHub 글은 대부분 저장소의 두 환경 복제 상태를 말한다. 남은 고부하 저장소와 후속 가상 복제본 설계는 별개다.
- **`3~4배`는 내부 시험의 서로 다른 ref 쓰기 처리량이다.** 모든 사용자의 푸시 지연이나 기본 브랜치 병합량의 보증값이 아니다.
- **`OK`는 PHP 서비스 전체의 보안 감사 통과가 아니다.** 공개 검사기는 광고된 버전 문자열만 검사하고, 백포트와 로드밸런서 뒤의 다른 인스턴스를 증명하지 못한다.
- **‘출시’와 ‘일반 제공’은 다르다.** Google Cloud의 모델은 선택 고객 대상 비공개 프리뷰로 설명되고, OpenAI 원문은 일반 제공을 향후 계획으로 쓴다.
- **‘coming soon’은 현재 기능이 아니다.** 데이터 보관 옵션과 Confidential Compute, 다른 Google 제품 통합은 실제 제공 시점을 확인해야 한다.
- **중개 플랫폼과 모델을 사용하는 앱은 같은 범주가 아니다.** OpenAI 정책은 직접 모델 접근을 제공하는 서비스에 사전 검토·승인을 요구하면서 일반적인 앱 통합과 구별한다.
