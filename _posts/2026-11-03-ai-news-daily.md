## 배경: 에이전트의 성패는 모델 한 번의 답변 밖에서 결정된다

RAG 서비스는 흔히 모델과 벡터 데이터베이스를 연결하면 완성된다고 생각한다. 그러나 사용자가 보는 답변의 품질은 검색 이전 단계부터 결정된다. 웹 페이지에서 메뉴와 광고가 본문에 섞이면 검색 결과가 오염된다. 수정된 정책이 오래된 문서와 함께 남아 있으면 더 높은 유사도를 가진 낡은 문장이 인용될 수 있다. 출처 URL과 수집 시각이 없으면 운영자는 답변의 근거를 역추적하기 어렵다. 인덱싱 여부와 **현재 유효한 내용인지**는 다른 질문이다. 첫 번째 AWS 글은 바로 그 데이터 준비와 삭제·동기화의 문제를 다룬다.

에이전트 비용 역시 한 번의 모델 호출 단가로 비교하면 틀린다. 쇼핑 에이전트는 검색, 후보 열람, 조건 검증, 최종 추천을 반복한다. 각 단계가 모델 호출과 도구 사용을 낳는다. 작은 모델에 최종 답변 문장만 학습시키면 말투는 따라 할 수 있지만 어느 도구를 언제 호출할지는 충분히 배울 수 없다. 두 번째 글은 여러 단계의 **궤적**을 학습 데이터로 다룬다. 다만 궤적을 흉내 내는 것과 실제 문제를 푸는 것은 다르므로 보지 않은 문제에서 도구 루프 전체를 평가한다.

멀티모달 검색은 문서에 없는 정보를 마법처럼 복원하지 않는다. 물리 부품의 사진이 비슷해도 전압·토크·온도 범위가 맞지 않으면 대체품이 아니다. 반대로 수치상 비슷해도 장착 구멍과 커넥터가 다르면 통합 비용이 커진다. 세 번째 글은 문서와 그림을 찾는 **확률적 검색**, 수치를 비교하는 **결정적 규칙**, 최종 결정을 내리는 **인간 검토**를 나눠 놓는다. 이 경계가 없으면 높은 코사인 유사도를 승인 근거로 오해하기 쉽다.

장애 대응에서는 읽고 판단할 수 있는 맥락을 빨리 모으는 것이 중요하다. 경고 하나에 로그, 자원 상태, 코드 변경, 서비스 담당자를 연결하는 일은 당직자의 시간을 상당히 쓴다. 네 번째 글의 성과는 모델이 배포를 자동 수정했다는 것이 아니다. **조사와 요약**을 자동화해 사람이 더 빨리 조치 판단을 시작하게 했다는 점이다. 응답 시간이 빨라져도 잘못된 원인 추정이나 과도한 자동 조치가 생기면 신뢰는 무너진다.

## 1. 웹 RAG: 크롤러 선택보다 먼저 원천의 책임을 정한다

### 관리형 Web Crawler를 먼저 검토하는 이유

AWS 글은 공개 웹 페이지를 Bedrock Managed Knowledge Bases에 연결할 때 관리형 Web Crawler를 출발점으로 제시한다. 시드 URL 또는 사이트맵을 주고 범위·속도를 설정하면 수집기가 페이지를 읽는다. JavaScript로 늦게 나타나는 콘텐츠를 기다리는 기능과 일정 동기화가 제공되며, 첫 전체 수집 뒤에는 추가·수정·삭제된 내용을 반영한다는 설명이다. 이 경로는 별도 브라우저 실행 환경, 크롤링 코드, 배치 스케줄러를 직접 소유하지 않는 편익이 있다. **커스텀 크롤러를 쓸 수 있다는 이유만으로 쓰는 것이 최선은 아니다.** [원문](https://aws.amazon.com/blogs/machine-learning/prepare-web-content-for-amazon-bedrock-knowledge-bases-with-crawl4ai/)

그러나 관리형 기본 경로만으로는 특정 페이지의 본문 영역만 뽑거나, 메뉴·바닥글을 특수 규칙으로 제거하거나, 조직이 요구하는 메타데이터를 붙이는 일이 충분하지 않을 수 있다. 이때 Crawl4AI를 **준비 단계**로 사용한다. 샘플은 허용된 공개 사이트를 제한된 깊이·페이지 수로 돌고, Markdown 문서와 같은 위치의 `.metadata.json` sidecar를 S3에 업로드한 다음 Knowledge Bases 수집 작업을 시작한다. 수집 뒤의 파싱·청크화·임베딩·인덱싱·검색은 Knowledge Bases의 역할이다. Crawl4AI를 벡터 검색 엔진 또는 실시간 웹 검색으로 소개하는 것은 역할을 혼동한 것이다.

실무에서 선택 질문은 세 개다. 첫째, 페이지에 접근할 권한이 있는가. 둘째, 관리형 연결기가 필요한 내용을 충분히 읽고 업데이트하는가. 셋째, 커스텀 추출·메타데이터가 실제 답변 품질을 올리는가. 세 질문에 앞서 크롤러 도구를 결정하면 구현은 빨라도 운영 책임은 불명확해진다. 예를 들어 공개 정책 안내 사이트는 관리형 연결기만으로 충분할 수 있다. 동일한 사이트가 탐색 메뉴와 이전 버전 PDF를 많이 노출한다면 선택적 추출과 유효기간 메타데이터가 필요할 수 있다. 차이는 사이트 이름이 아니라 **문서 품질과 변경 양상**에서 나온다.

### 샘플의 경로: 제한된 수집에서 검색까지

원문의 예제는 EventBridge 일정이 ECS Fargate 작업을 시작하는 형태다. 작업은 허용된 시드에서 페이지를 탐색하고, Markdown과 메타데이터를 만든다. 다음으로 S3 버킷에 두 파일을 함께 올리고, Knowledge Bases의 ingestion job을 시작한다. 사용자는 이후 Retrieve 또는 생성 응답 API로 검색한다. 이 단계별 분리는 관측에도 도움이 된다. **수집 실패, 변환 실패, 업로드 실패, 인덱스 반영 실패, 검색 실패**를 같은 ‘RAG 오류’로 뭉치면 어디서 답변이 낡았는지 알 수 없다.

샘플은 탐색 깊이와 페이지 상한, URL 패턴, 호스트·경로 범위를 지정한다. 최종 URL이 리디렉션으로 다른 호스트를 가리킬 수 있으므로 요청 URL뿐 아니라 **실제 도착한 URL의 범위를 다시 확인**한다. 동일 페이지의 표준 URL을 중복 제거하는 로직도 있다. 이는 수집량과 비용을 줄이는 것 이상이다. 같은 문서의 중복 청크가 검색 상위권을 점유하면 답변이 특정 출처에 과하게 끌릴 수 있다. 중복 제거 규칙을 바꿨다면 검색 결과 분포도 다시 보아야 한다.

본문 추출은 휴리스틱이다. 메뉴와 광고를 줄이는 필터가 정책의 중요한 각주까지 버릴 수 있다. CSS 선택자를 고정하면 사이트 개편 뒤 본문이 비어 있을 수 있다. 그래서 샘플을 생산 환경에 복사할 때는 성공한 페이지 수만 보지 말고 **대표 페이지의 최종 Markdown**을 사람이 검토해야 한다. HTML 원본이 200 응답이었다는 사실은 중요한 표와 업데이트 날짜가 추출됐다는 뜻이 아니다. 추출 후 본문 길이가 갑자기 짧아진 페이지, 제목은 있지만 핵심 표가 없는 페이지, 문자 인코딩이 깨진 페이지를 별도 품질 실패로 분류한다.

### 메타데이터 sidecar와 출처의 수명

원문의 S3 경로 규칙은 중요하다. `page.md`의 sidecar는 동일 위치의 `page.md.metadata.json`이다. 예제는 출처 URL, 크롤링 시각, 콘텐츠 분류 같은 값을 구조화된 `metadataAttributes`에 넣는다. 메타데이터는 그럴듯한 장식이 아니다. 검색 시 웹 자료만 거르거나 최근 수집된 자료를 선택하고, 생성 답변에 **원본 URL을 보여 주는** 데 사용된다. sidecar 최대 크기는 원문 기준 10KB다. 필드를 무한히 추가하는 대신 어떤 필드가 검색 필터와 감사에 실제로 필요한지 정해야 한다.

출처 URL도 불변의 진실은 아니다. 페이지가 수정되면 같은 URL이 다른 내용을 가리킨다. 수집 시각과 원본의 발효일을 구분해야 한다. 특히 규정·정책은 ‘어제 수집한 1년 전 규정’이 오늘도 유효하다는 뜻이 아니다. 원문이 제시한 `crawled_at_epoch`는 **언제 가져왔는지**를 설명하지만 **언제부터 유효한지**는 설명하지 않는다. 실무 제안은 별도의 `effective_from`, `effective_to`, `document_version`, `owner`를 소스에서 신뢰성 있게 얻을 수 있을 때만 추가하는 것이다. 모델이 빈 값을 추정해 채우게 해서는 안 된다.

### 삭제와 동기화는 별도의 운영 기능이다

커스텀 파이프라인의 업로드는 **가산적**이다. 어떤 URL이 다음 크롤에서 보이지 않는다고 S3의 이전 문서와 sidecar가 자동 삭제되는 것은 아니다. 원문은 낡은 자료를 제거하려면 S3의 해당 문서와 sidecar를 지운 뒤 수집을 다시 실행해야 한다고 명시한다. 삭제 보호 임계치를 설정했다면 많은 삭제가 발생한 동기화는 삭제 단계를 건너뛸 수도 있다. 따라서 ‘이번 수집에 안 나왔다’와 ‘사용자 검색에서 사라졌다’는 구별해야 한다. 중요한 정책 페이지가 없어지거나 이동했을 때 오래된 청크가 계속 답변 근거가 되는 것이 가장 위험한 실패 중 하나다.

운영팀은 URL별 상태를 `발견 → 추출 → 업로드 → 인덱스 반영 → 검색 가능 → 폐기`로 관리하는 편이 좋다. 재시도나 사이트 장애로 일시적으로 안 보인 URL을 곧바로 삭제하는 것도 위험하다. 반대로 수개월간 없는 페이지를 무기한 남기는 것도 위험하다. 문서 소유자와 원천별 보존 규칙, 삭제 유예기간, 수동 검토 예외를 정해야 한다. 삭제를 시작할 때는 sidecar와 문서가 함께 제거되는지, 인덱스가 실제로 정리되는지 검색으로 확인한다. 이 작업은 파일 동기화가 아니라 **지식의 유효성 관리**다.

### 검색 품질을 생성 답변과 분리해서 측정한다

원문은 생성 단계를 붙이기 전에 대표 질문을 `Retrieve`로 검사하라고 권한다. 올바른 페이지가 상위에 없는 문제는 더 긴 프롬프트로 근본 해결되지 않는다. 검색 후보의 적합도, 정답 페이지의 포함률, 최신 문서 우선도, 출처 URL의 정확성, 인용 구간의 충분성을 분리해 측정한다. 원문에 나온 관리형 Knowledge Bases의 기본 청크는 300토큰·20% 겹침이며, 다른 청크 전략도 선택할 수 있다. 청크 전략은 데이터 소스를 만들 때 정하고 나중에 바꾸려면 새 데이터 소스를 만드는 경로가 필요하므로 예제를 적용하기 전에 실제 문서로 비교해야 한다.

긴 정책 문서라면 작은 청크가 조항의 예외를 분리할 수 있고, 큰 청크가 엉뚱한 장을 함께 가져올 수 있다. 표의 행 제목이 다른 청크로 갈라지면 숫자만 인용될 수 있다. 동일 문서 여러 버전이 검색에 섞이면 고품질 임베딩만으로 해결되지 않는다. 따라서 RAG 평가는 모델 답변의 자연스러움보다 **검색 후보와 인용의 사실성**에서 시작한다. 답변 오류가 생겼을 때 ‘검색 결과는 맞았는데 요약을 잘못했는지’, ‘처음부터 틀린 문서를 가져왔는지’를 분리해야 개선 비용을 줄인다.

### 개발자에게 의미: 수집기는 데이터 제품이다

크롤러를 한 번 실행하는 데모에서는 URL 몇 개가 읽히면 충분해 보인다. 운영에서는 원천 목록, 수집 허용, 실패율, 변경 탐지, 데이터 유효기간, 삭제, 저작권과 접근 권한, 인용 UI까지 소유해야 한다. 특히 공개 페이지가 아닌 로그인 자료는 예제의 범위 밖이다. 원문은 이 샘플이 인증 세션을 구현하지 않는다고 설명하고, 로그인이 필요한 자료에는 관리형 Web Crawler의 인증 옵션부터 검토하라고 한다. 인증을 추가하려면 세션 처리와 비밀 관리 및 보안 검토가 필요하다. ‘크롤러가 JavaScript를 읽을 수 있다’는 사실과 ‘어떤 페이지든 읽어도 된다’는 주장은 전혀 다르다.

인사시스템을 예로 들면 공지와 규정의 공개 버전을 검색에 넣는 것은 가능해도 직원별 급여 명세를 공개 웹 크롤링 경로에 섞어서는 안 된다. 자료 범주에 따라 저장소와 권한, 검색 필터를 나눠야 한다. 사용자가 묻는 질문에 직원 개인의 내용을 인용하지 않도록 검색 시점에도 권한을 확인해야 한다. `content_category=web` 같은 메타데이터는 편리한 필터일 뿐, 사용자별 접근 제어 자체는 아니다. 출처 URL이 내부 링크를 드러내는지도 점검한다.

## 2. 에이전트 증류: 최종 답이 아니라 행동의 단위를 학습한다

### 왜 단순 프롬프트 압축으로는 부족한가

AWS의 SeqKD 글은 쇼핑 보조 에이전트를 예로 든다. ‘20달러 미만의 검은 가방을 높은 평점의 상점에서 찾아 달라’는 요청은 조건을 읽고, 카탈로그를 검색하고, 후보를 확인하고, 조건을 다시 비교한 뒤 추천해야 한다. 한 번의 자연어 답변과 달리 각 단계는 **다음 도구 호출을 결정하는 상태**다. 교사 모델을 작은 모델로 바꾸면 답변 문체는 비슷해도 검색을 너무 빨리 끝내거나, 가격 조건을 무시하거나, 같은 검색을 반복할 수 있다. 이 문제를 해결하려면 작업의 완료 여부뿐 아니라 그에 이르는 궤적을 관찰해야 한다. [원문](https://aws.amazon.com/blogs/machine-learning/build-efficient-agents-with-knowledge-distillation-on-amazon-sagemaker-ai/)

SeqKD는 교사 모델이 만든 텍스트 시퀀스를 학생의 지도 미세조정 데이터로 사용한다. 교사의 내부 가중치나 로그 확률을 얻지 않아도 되므로 API를 통해 쓰는 모델에도 적용할 수 있다. 원문 샘플은 Bedrock의 GLM-5.3을 교사로, Qwen3.5-4B를 학생으로 사용한다. 중요한 점은 모델 이름 자체가 아니라 **성공 궤적의 선정 기준과 평가 분리**다. 교사의 출력이 틀렸는데도 학습하면 학생은 그 오류를 체계적으로 재현할 수 있다. 교사가 한 번 성공한 궤적만 남기면 성공하기 쉬운 문제에 치우칠 수도 있다.

### 학습 데이터의 단위는 문제다

원문에서 ShoppingBench는 합성 쇼핑 문제 750개를 제공하고, 상품·상점·쿠폰 의도별로 250개다. 예제는 426개를 학습 문제로, 324개를 보류 평가 문제로 나눈다. 교사는 각 학습 문제에서 복수의 궤적을 생성하며, 벤치마크의 채점기가 모든 제약을 만족한 실행을 선택한다. 여기서 단순히 대화 한 줄을 학습과 검증으로 나누면 누수가 생긴다. 한 문제에서 파생된 여러 단계와 여러 실행이 서로 거의 같은 맥락을 공유하기 때문이다. **문제 단위 분리**가 필요한 이유다.

각 성공 궤적에는 사용자 요청, 모델의 중간 판단, 도구 호출, 도구가 반환한 관찰, 최종 종료가 포함된다. 원문은 이를 단계별 학습 예제로 인코딩한다. 그런데 매 단계의 대화 이력이 길어지면 이전 검색 결과가 반복되어 토큰이 급증한다. 샘플은 도구 관찰에서 다음 결정에 필요한 상품 ID·가격·평점·조건 관련 필드만 남기고, 긴 목록을 제한하는 방식을 제안한다. 여기서 압축은 데이터 손실이다. 필요 없는 홍보 문구를 버리는 것은 좋지만, 반품 조건이나 배송 제한처럼 사용자 제약과 연결되는 필드를 버리면 학생은 그 조건을 학습할 수 없다.

학습 길이 제한은 성능 문제이기도 하지만 의미 문제이기도 하다. 토큰 초과가 뒷부분을 잘라 버리면 정답을 결정한 마지막 관찰이 사라질 수 있다. 긴 궤적을 무조건 버리면 어려운 문제만 학습에서 빠진다. 따라서 어떤 궤적이 탈락하는지 의도별로 보고, 잘라낸 관찰이 정답 조건과 관련이 있는지 표본 검토해야 한다. 길이 제한을 넘긴 비율, 예제당 도구 단계 수, 성공 궤적 채택률은 모델 훈련 전의 **데이터 품질 지표**다.

### 학습 성공과 제품 성공은 다른 평가다

원문은 먼저 한 단계씩 교사의 도구 행동을 얼마나 재현하는지 저비용 사전 검사를 하고, 학생이 기본 모델보다 나아졌을 때 전체 도구 루프 평가로 넘어간다. 이 순서는 비용과 원인 분석에 합리적이다. 그러나 한 단계의 정답률이 높아도 여러 단계가 연결되면 작은 실수가 누적된다. 첫 검색에서 잘못된 카테고리를 고르면 뒤의 후보 비교가 아무리 정확해도 최종 추천은 틀릴 수 있다. 그래서 보류된 ShoppingBench 문제에서 실제 검색 서버와 모델 엔드포인트를 이용해 **끝까지 작업을 완수했는지** 확인한다.

원문의 ASR(Absolute Success Rate)은 추천 상품이 문제에 명시된 모든 제약을 만족하는 비율이다. 샘플 결과에서 증류 학생은 학습 전 기본 모델보다 평균 약 24포인트 높은 성과를 보였고, 교사의 판단과 도구 호출 이유를 포함한 학습은 도구 호출만 학습한 경우보다 평균 약 13포인트 높았다. 이는 **원문의 단일 실행과 특정 벤치마크**에 대한 수치다. 독립적인 쇼핑몰, 최신 상품, 한국어 문의, 개인정보 제약에서 같은 차이를 보장하지 않는다. 채점기가 어떤 제약을 검사했는지, 누락된 실행은 어떻게 처리했는지, 보류 문제 수는 얼마인지 함께 제시해야 한다.

실제 서비스에서 평가는 도구 호출 타당성뿐 아니라 결과의 유효성을 본다. 예를 들어 검색 도구를 불렀더라도 배송 국가 필터가 틀렸다면 사용자는 상품을 살 수 없다. 사용자가 원한 가격은 할인 적용 전인지 후인지, 재고 정보는 어느 시점 기준인지, 상점 평점은 누구의 데이터인지 구분해야 한다. 학습 데이터가 합성이고 채점기가 정답을 알 때는 자동 채점이 가능하지만 실서비스에서는 사람이 만든 경계 사례와 데이터 스냅샷, 결제 직전의 실시간 확인이 필요하다.

### ‘작은 모델이라 싸다’는 결론에는 사용량이 빠져 있다

큰 API 모델은 대체로 토큰 사용량에 따라 과금되고, 직접 띄운 학생 모델은 엔드포인트가 켜져 있는 시간에도 비용이 발생한다. 작은 모델이 요청마다 빠르더라도 트래픽이 적으면 고정 인프라 비용이 더 클 수 있다. 반대로 요청이 많고 충분히 배치·동시 처리할 수 있으면 비용 구조가 유리해질 수 있다. 원문은 이 사례의 단일 작업당 비용이나 지연 수치를 공개하지 않았다. 그러므로 ‘증류로 비용 80% 절감’ 같은 숫자를 이 글에서 만들지 않는다. 팀은 **작업 완료당 비용**, **제약을 모두 충족한 작업당 비용**, **p95 지연**, **GPU 활용률**, **실패 재시도 비용**으로 비교해야 한다.

원문의 학생 모델은 LoRA 어댑터로 제공하며, 기저 모델과 어댑터를 같은 실시간 엔드포인트의 별도 추론 구성요소로 운영한다. 이를 통해 기본 모델과 증류 모델을 같은 루프에서 비교할 수 있다. 단, 모델은 도구 호출을 ‘실행’하지 않는다. 모델이 출력한 도구 호출을 애플리케이션의 결정적 하네스가 파싱하고 실행한 뒤 결과를 다시 전달한다. 도구 권한·인수 검증·타임아웃·중복 호출 방지는 여전히 애플리케이션의 책임이다. 훈련 성공이 이 보안 경계를 대신하지 않는다.

### 인사시스템에 적용할 경우의 경계

예를 들어 ‘이 직원의 잔여 연차를 확인하고 다음 주 휴가를 신청해 줘’라는 에이전트를 만든다고 하자. 학습용 성공 궤적은 연차 조회, 날짜 겹침 확인, 정책 확인, 신청 초안 작성까지 포함할 수 있다. 그러나 교사가 만든 궤적에 실제 직원 정보가 들어갔다면 학습 데이터 보존과 접근 통제를 먼저 검토해야 한다. 실제 개인정보를 모델 행동 예제로 무심코 복제하는 것은 비용 최적화가 아니다. 가능한 범위에서 합성·비식별 사례를 쓰고, 정책 개정 전후의 사례를 분리한다.

제품 평가에서는 ‘도구를 바르게 골랐다’만으로 성공이 아니다. 잔여일수 부족, 휴일 계산, 승인권자 부재, 대리 신청, 신청 취소, 중복 클릭, 경계 날짜, 조직 이동 등에서 시스템의 원장과 일치해야 한다. 교사 모델이 그럴듯한 문장으로 잘못된 정책 해석을 했는데 채점기가 놓쳤다면 학생은 그 실수를 더 빠르게 반복할 수 있다. 위험한 업무에서는 모델이 자주 사용하는 경로일수록 **결정적 정책 함수와 서버 승인**을 강화해야 한다.

## 3. 멀티모달 검색: 이미지는 후보를 찾고, 규칙은 적합성을 판정한다

### 가상 부품 예제가 보여 주는 분업

AWS의 엔지니어링 보조 글은 위성 반작용 휠 같은 부품의 수명·대체 가능성을 찾는 예제를 설명한다. 샘플 데이터는 가상의 제조사 제품 7개이며, 정형 사양 JSON과 인터페이스 문서, 사진, 성능 차트가 함께 있다. 질문에 따라 Catalog, Evaluation, Knowledge 전문가 에이전트가 필요한 도구만 사용하고, 여러 전문가가 참여했을 때 감독 에이전트가 결과를 종합한다. 이는 한 모델에게 모든 도구와 문서를 무제한 주는 것보다 역할이 분명하다. 그렇지만 전문 에이전트 이름이 있다고 그 자체로 품질이 보증되지는 않는다. [원문](https://aws.amazon.com/blogs/machine-learning/agentic-engineering-intelligence-with-amazon-nova-multimodal-embeddings-and-amazon-bedrock-agentcore/)

이 예제에서 Nova Multimodal Embeddings는 문서·도면·사진을 공통 검색 공간에 배치한다. 사용자가 ‘특정 토크 곡선’이라고 묻거나 차트 이미지를 올리면 관련 원본을 찾을 수 있다. 다만 **텍스트·문서 검색과 이미지 입력 검색은 서로 다른 경로**다. 글은 관리형 Knowledge Bases의 검색 API가 이미지 입력을 받지 않아, 이미지로 찾는 경우 S3 Vectors 인덱스를 직접 조회한다고 설명한다. 하나의 멀티모달 모델을 썼다고 모든 API가 모든 입력을 동일하게 받는다고 가정하면 구현에서 막힌다. 입력 유형별 경로와 결과의 출처를 UI에서 다시 합쳐야 한다.

사진 유사도는 코사인 점수로 후보 비교를 돕고, 모델은 장착 패턴·커넥터·외형의 눈에 띄는 차이를 설명한다. 그러나 사양 적합성은 별도 Python 코드가 공차와 요구 조건을 비교한다. 이미지가 비슷해도 전기적 인터페이스가 다르면 허용될 수 없다. 사양이 맞아도 인증 상태가 다르면 승인할 수 없다. 원문에서 모델은 대체를 승인하지 않고 근거와 플래그를 정리한다. 최종 엔지니어링 검토의 책임은 인간에게 남긴다. 안전이 중요한 분야에서 이 구분은 단순한 면책 문구가 아니라 시스템 구조다.

### 원천 필드와 추론값을 섞지 않는다

샘플은 제조사 이름을 파일명·사진·모델의 추측에서 가져오지 않도록 하고, 구조화된 `vendor` 필드를 기준으로 삼는다. 파일 이름에 특정 공급사가 연상되어도 실제 데이터의 소유자를 다르게 기록할 수 있기 때문이다. 실무에서는 **각 필드의 진실 원천(source of truth)**을 정하는 일이 검색 모델 선택만큼 중요하다. 사진에서 모델이 읽은 토크 수치, PDF의 OCR로 뽑은 수치, ERP의 검증된 사양 필드가 다르면 무엇을 우선할지 정해야 한다. 어느 하나를 자동으로 덮어쓰면 감사 때 데이터가 어떻게 바뀌었는지 복원할 수 없다.

구조화 필드도 항상 최신이라고 보장되지는 않는다. 구매 시스템이 오래된 규격을 담고 있고 새 인증 문서가 뒤늦게 올라올 수 있다. 따라서 사양 비교 결과에는 값뿐 아니라 원천 문서, 버전, 수집 시각, 적용 여부를 붙여야 한다. 모델이 출처가 다른 숫자를 하나의 표로 합칠 때는 서로 모순되는 값이 있다는 사실을 숨기지 않아야 한다. ‘가장 그럴듯한 하나’만 선택하는 요약은 엔지니어링 리뷰에 위험하다. 모순은 오히려 검토해야 할 **발견 항목**이다.

### 평가와 감사 기록의 차이

원문의 샘플은 36개의 큐레이션된 질문을 여섯 범주로 나눠 오프라인 검증하고, AgentCore Evaluations를 이용한 온라인 trace 평가도 설명한다. 네 개의 안전 관련 질문은 모델이 대체를 추천하거나 승인하지 않는지 확인한다. 평가에 ‘정답 부품을 찾았는가’만 넣지 않고 ‘거부해야 할 때 거부했는가’를 넣은 점이 중요하다. 다만 36개 샘플은 실제 산업 부품의 조합 공간을 대표한다고 볼 수 없으며, 온라인 LLM 판정 점수도 형식적 승인 요건을 대체하지 않는다.

감사 기록은 평가 점수와 다르다. 평가 점수는 모델 행동의 품질을 추정하는 지표지만, 감사 기록은 어떤 원본과 도구 결과로 어떤 판단을 했는지 재현하기 위한 증거다. 원문 예제는 모델이 ‘기록해야지’라고 기억하는 데 맡기지 않고, 오케스트레이션 코드가 도구 호출 이력을 읽어 기록한다. 이것이 중요한 이유는 모델의 문장이 `승인하지 않겠습니다`라고 말해도 로그 저장이 누락될 수 있기 때문이다. 비즈니스 필수 조건은 프롬프트보다 코드와 데이터베이스 제약에 둔다.

### 개발자에게 의미: 도구 권한을 역할별로 자른다

Catalog 전문가는 후보 탐색 도구를, Evaluation 전문가는 정형 비교 도구를, Knowledge 전문가는 문서 검색 도구를 사용한다. 같은 모델 계열을 쓰더라도 **도구 집합을 다르게 주는 것**이 역할 분리의 실질이다. 한 전문가가 불필요하게 데이터 수정이나 승인 도구를 호출할 수 없다면 오류의 폭도 좁아진다. 최종 감독 에이전트는 여러 결과를 종합할 수 있지만 새로운 사실을 만들어낼 권한은 없다. 충돌하면 원문과 사양 비교를 다시 보여 주고 사람에게 넘겨야 한다.

인사시스템에서는 이 분업이 `규정 검색`, `잔여량 계산`, `신청 가능 여부 검사`, `승인`으로 대응된다. 규정 검색은 관련 조항을 찾아도 직원 개인의 남은 휴가를 결정하지 못한다. 잔여량은 근태 원장과 정책 코드가 계산해야 한다. 신청 가능 여부는 사용자 권한, 날짜, 조직 규칙을 서버에서 검사한다. 승인은 별도의 권한자 행위다. 모델에게 한꺼번에 허용하면 ‘근거를 설명하는 역할’과 ‘상태를 바꾸는 역할’이 섞인다. 원문의 부품 교체 예제처럼 **모델은 근거를 조립하고 결정은 명시된 담당자에게 남긴다**는 원칙이 적합하다.

## 4. Circle K: 장애 대응 자동화의 초점은 수리보다 초동 맥락이다

### 수치의 의미부터 정확히 읽는다

AWS와 Circle K의 공동 사례에 따르면 기존 수동 장애 초동 분류는 45~60분이 걸렸다. 운영 시스템 도입 후 내부 지표의 평균 분류 시간은 15분 미만으로 줄었고, 글은 이를 67~75% 감소로 표현한다. 일부 단순 사고의 요약은 5~8분, 복잡한 다중 서비스 사고도 15분 이내로 보고한다. 회사는 2026년 4월 AgentCore 버전을 배포했다고 설명한다. 이 수치는 **고객의 자체 측정**이며 외부 재현 실험이나 모든 장애 유형의 평균 수리 시간(MTTR)으로 읽어서는 안 된다. 특히 분류가 빨라진 것과 장애가 해결된 것은 별개다. [원문](https://aws.amazon.com/blogs/machine-learning/how-circle-k-accelerated-devops-incident-triage-to-under-15-minutes-with-amazon-bedrock/)

기존 구조에서는 Grafana 알림이 SNS와 SQS를 거쳐 Lambda로 전달된다. Bedrock Flows의 두 전문 에이전트가 AWS 자원 상태와 OpenSearch 로그·trace를 병렬 조사한다. 이후 GitHub를 탐색하는 에이전트가 앞의 결과를 받아 관련 저장소와 최근 코드를 좁혀 본다. 마지막 모델 호출은 세 결과를 probable root cause, 근거, 영향 서비스와 담당자, 권장 조치로 정리한다. Lambda가 구조화된 요약을 Slack 채널로 보낸다. 당직자는 원시 경고를 보고 여러 도구를 다시 열기 전에 맥락이 정리된 메시지를 받을 수 있다.

예시 장애는 HTTP 5xx 비율이 3분 연속 5%를 넘는 경고다. 자원 상태에서 데이터베이스 연결 풀이 소진되고 ECS 태스크가 다시 시작되는 것이 보인다. 로그에는 PostgreSQL 연결 거절이 나타난다. 코드 탐색에서 요청마다 새 연결을 여는 패턴을 찾는다. 모델은 마케팅 캠페인과 시간 상관관계를 엮어 원인 후보를 설명한다. 이 흐름은 **탐지→증거 수집→가설→권장 조치**다. 가설을 확정 사실로 표시하거나 모델이 곧바로 DB 설정을 변경하는 단계가 아니다. 원문 메시지의 근거는 당직자가 실제 로그와 변경 이력을 다시 열어볼 수 있어야 가치가 있다.

### Flows에서 AgentCore로 옮긴 이유

원문은 초기 Flows 구성이 수개월 동안 잘 작동했으나 서비스와 데이터가 늘면서 일부 조사가 단일 Flow 노드의 실행 범위를 넘었다고 설명한다. 먼저 로그 필터와 컨텍스트 길이, 서비스별 Flow 분할을 조정했다. 이후 컨테이너화한 조사 로직을 AgentCore Runtime의 하나의 세션으로 옮겼다. AgentCore는 더 긴 세션을 지원하지만, 실제 사례에서는 Lambda의 최대 실행 시간 안에 결과를 반환하도록 설계한다. **최대 8시간 세션을 지원한다**는 플랫폼 성능과 **사고 요약을 15분 내 전달한다**는 이 사례의 서비스 목표를 혼동해서는 안 된다.

이전에는 병렬 전문가 셋을 Flow 노드로 구성했지만 AgentCore 버전에서는 한 런타임 세션의 에이전트가 같은 조사를 수행한다. Gateway는 OpenSearch, Knowledge Bases, GitHub 등 데이터 소스 접근을 도구로 중개한다. OpenTelemetry 기반 trace로 어떤 단계가 느렸는지 보고, 프롬프트와 도구 정의를 바꿀 때 병목을 찾는다. 운영 기술의 전환보다 중요한 것은 **분석 로직과 오케스트레이션을 분리해 놓아 이식할 수 있었다**는 점이다. 처음부터 특정 워크플로 제품의 노드 속에 진단 지식을 묻어두었다면 재작성 비용이 컸을 것이다.

### 운영 포인트: 요약의 정확도를 따로 계측한다

‘15분 미만’은 분류 속도 지표다. 실제 현장에서는 두 종류의 오류가 중요하다. 첫째, **오탐 근본 원인**이다. 증거가 충분하지 않은데 한 원인을 확정적으로 말하면 당직자는 잘못된 서비스에 손댄다. 둘째, **빠진 중대한 근거**다. 예를 들어 직전 배포나 외부 공급자 장애가 누락되면 모델이 로그의 일부 현상만 설명한다. 속도와 별도로 근거 링크의 열람 가능성, 상위 가설의 적중률, 조치 권고의 재검토율, 당직자의 수동 조사 시간, 잘못된 변경으로 인한 2차 장애를 살펴야 한다.

알림 폭주 때에는 한 사고에서 수십 건의 경고가 나올 수 있다. 각각 독립적으로 모델 조사를 시작하면 중복 조회와 비용이 커진다. 사건 식별, 중복 접기, 경고 묶기, 일정 시간 내의 새 단서 추가, 종료 기준을 설계해야 한다. 서로 다른 사건을 과하게 합치면 진단이 흐려지고, 같은 사건을 과하게 나누면 당직자에게 여러 상충된 요약이 간다. 원문의 아키텍처를 그대로 따라 하기 전에 **우리 조직의 알림 단위가 사고 단위와 얼마나 다른지** 알아야 한다.

운영 로그와 코드에는 민감한 값이 섞일 수 있다. 원문은 Bedrock의 데이터 처리 특성이 Circle K의 보안 요구에 부합했다고 설명하지만, 그것만으로 모든 원시 로그를 모델에 보내도 된다는 뜻은 아니다. 업무 환경에서는 비밀 값과 개인정보의 로그 유입을 줄이고, 도구별 계정 접근을 최소화하며, 추론 입력을 남길 때 보존 기간과 열람 권한을 관리해야 한다. 모델이 작성한 Slack 요약에도 접속 토큰이나 고객 정보가 그대로 실리지 않도록 출력 검사가 필요하다. 예제는 사고 맥락을 보여 주지만 각 조직의 정보 분류 정책까지 대신해 주지 않는다.

## 개발자에게 의미: 네 발표를 한 제품에 적용한다면

인사시스템이 공개 법령과 회사 규정으로 질문에 답하고, 서류 사진을 이해하며, 반복 문의를 처리하고, 운영 장애를 감시한다고 가정해 보자. 이 경우 첫 단계는 최신 모델 선택이 아니다. **정보의 출처와 확정 권한**을 표로 만드는 것이다. 법령의 공개 문서는 신뢰 가능한 원문 URL과 시행일을 가진다. 회사 규정은 조직별 버전과 내부 접근 권한을 가진다. 직원별 연차 잔여량은 문서가 아니라 트랜잭션 데이터다. 서류 사진의 추출값은 미검증 입력이다. 운영 로그는 제품 진단 데이터다. 서로 다른 원천을 한 벡터 인덱스로 섞으면 검색은 편해 보여도 권한과 최신성의 경계가 무너질 수 있다.

그다음은 **행동의 위험도**다. 규정 조항을 찾는 행동, 직원의 현재 잔여량을 조회하는 행동, 휴가 초안을 만드는 행동, 신청을 확정하는 행동, 관리자가 승인하는 행동은 서로 다른 도구와 권한을 가져야 한다. 증류 학생 모델이 도구 호출을 더 잘 배운다 해도 서버 검증은 사라지지 않는다. 규정 검색의 자신감이 높아도 결재 상태를 변경할 수 없다. 멀티모달 문서 검색이 사진에서 날짜를 읽어도 원본과 대조하기 전에는 확정 기록으로 쓰지 않는다. 장애 분석 에이전트가 배포 오류를 추정해도 배포 롤백은 운영자의 승인 규칙을 따른다.

**평가 데이터도 층별로 나눈다.** RAG에는 조항을 찾는 질문과 폐기된 규정을 찾아서는 안 되는 질문이 필요하다. 도구 에이전트에는 정상 신청, 거절, 중복 클릭, 타인 정보 조회 같은 경계 사례가 필요하다. 서류 이미지에는 흐림·잘림·중복 페이지·개인정보가 가린 경우가 필요하다. 운영 에이전트에는 원인이 여러 개일 수 있는 경고와 로그 미수집 사례가 필요하다. 네 유형을 하나의 ‘AI 정확도 90%’로 합치면 개선할 곳이 보이지 않는다. 정확도 지표가 같은 단위를 세는지부터 확인해야 한다.

### 1주 차: 원천·권한 지도를 만든다

공개 자료, 사내 문서, 직원별 데이터, 운영 로그를 분리한다. 각 원천에 소유자와 변경 시각, 보존 기간, 삭제 방식, 접근 정책을 적는다. 웹 자료는 관리형 크롤러로 충분한지 대표 URL 다섯 개를 확인한다. Markdown을 직접 준비해야 한다면 본문 누락과 URL 범위 이탈을 검사한다. 이 단계의 산출물은 화려한 데모가 아니라 **어떤 자료가 어디에서 어떻게 들어왔는지** 설명할 수 있는 지도다. 출처를 밝힐 수 없는 문장은 아직 사용자 답변으로 내보내지 않는다.

### 2주 차: 행동 계약과 평가 세트를 만든다

에이전트가 호출할 도구의 인수·반환값·권한·타임아웃·재시도 규칙을 문서화한다. 성공 궤적을 수집하더라도 실패 궤적을 버리지 않고 평가 사례로 보존한다. 문제 단위로 학습과 평가를 나누고, 정책이 개정됐을 때 이전 정답이 계속 옳은지 재검토한다. 작은 모델의 품질을 볼 때 기본 모델과 교사뿐 아니라 기존 운영 방식도 비교한다. ‘교사와 비슷하다’는 사실이 사용자 문제 해결의 기준을 충족한다는 뜻은 아니다. 검증 기준을 만족하지 못하면 기존 모델 또는 사람 처리 경로로 되돌릴 수 있어야 한다.

### 3주 차: 검색·이미지·정형 계산의 모순을 점검한다

같은 사안을 설명하는 문서와 정형 필드가 다를 때 UI가 무엇을 보여 줄지 결정한다. 모델이 그 차이를 매끄러운 한 문장으로 지우지 못하게 한다. 직원의 연차 계산은 서버 정책 함수와 원장이 기준이고, 규정 문서 인용은 해설 근거다. 이미지 OCR이 읽은 날짜는 사용자 확인을 거친 임시 값이다. 각 값에 출처와 검증 상태를 붙여야 ‘AI가 말했다’는 불명확한 책임 표현을 줄일 수 있다. 확정 값과 제안 값을 같은 시각 디자인으로 표시하지 않는다.

### 4주 차: 운영자가 사건을 재구성할 수 있게 한다

요청 ID로 사용자 질문, 검색된 문서 버전, 사용한 도구, 정책 검사 결과, 최종 변경 이력을 연결한다. 장애 대응에서도 경고 ID와 조사 trace, 근거 로그, 권장 조치, 실제 운영자 조치를 연결한다. 개인정보를 무제한 남기라는 뜻이 아니다. 접근 통제와 보존 기간을 갖춘 **최소한의 재현 가능한 증거**가 필요하다는 뜻이다. 모델의 최종 문장만 저장하면 왜 그런 판단을 했는지 알 수 없고, 반대로 원시 로그를 과도하게 저장하면 다른 위험이 생긴다.

## 운영 포인트: 배포 전·후에 묻는 질문

| 분야 | 배포 전 질문 | 배포 후 관찰 | 조치 기준의 예 |
| --- | --- | --- | --- |
| 웹 수집 | 허용된 URL만 읽는가? | 범위 이탈, 빈 Markdown, 크롤 실패 | 범위 이탈은 수집 중단 후 원인 확인 |
| 지식 유효성 | 폐기 문서가 삭제되는가? | 오래된 문서의 검색 노출 | 중요한 정책의 구버전 인용 시 답변 차단 |
| 증류 | 학습·평가 문제가 겹치지 않는가? | 제약 충족률, 단계 수, 반복 검색 | 핵심 사례 퇴행 시 이전 모델로 전환 |
| 도구 실행 | 모델이 호출할 수 있는 권한이 제한되는가? | 잘못된 인수, 무단 호출 시도 | 권한 오류를 모델 재시도로 우회하지 않음 |
| 멀티모달 | 사진·도면의 출처가 연결되는가? | 이미지 후보와 정형 사양의 충돌 | 충돌은 사람 검토로 이관 |
| 사고 분석 | 근거와 원인 후보를 구분하는가? | 오탐, 조사 지연, 운영자 수용률 | 고위험 조치는 자동 실행 금지 |

이 표는 네 공식 글의 공통 메시지를 실무 점검표로 번역한 것이다. 구체적인 차단 임계값은 조직의 업무 위험과 오류 비용을 바탕으로 정해야 한다. 예컨대 검색 상위 결과 한 건이 틀렸을 때도 사용자에게 피해가 큰 법적 안내와, 틀려도 쉽게 다시 탐색할 수 있는 일반 개발 문서 검색은 같은 기준을 적용할 이유가 없다. 위험도에 따라 검토 깊이를 조정하되, **근거 없는 자동 확정**은 피한다.

### 실패 상황을 네 가지로 분리한다

**원천 자료 실패:** 새 페이지가 수집되지 않거나 오래된 문서가 삭제되지 않았다면 모델 온도를 조정하지 않는다. URL 범위, 추출 결과, sidecar, 수집 작업, 검색 결과를 순서대로 확인한다. 사용자에게는 ‘현재 자료 확인 중’ 같은 유효성 상태를 알리고, 오래된 답변을 확정적으로 반복하지 않는다. 주요 문서의 버전이 바뀌었을 때 검색 인덱스 갱신이 완료되기 전의 공백도 운영 시나리오로 다룬다.

**모델 행동 실패:** 학생 모델이 도구를 잘못 고르거나 같은 검색을 반복한다면 먼저 실패한 문제의 궤적을 본다. 학습 데이터의 성공 판정이 올바른지, 긴 관찰이 잘려 필요한 조건이 빠졌는지, 도구 출력 형식이 학습 시점과 달라졌는지 확인한다. 학습 데이터를 더 늘리기 전에 학생 모델의 용량이 문제 난이도를 감당하는지도 본다. 출력 형식만 정돈됐고 과제 완수율은 오르지 않았다면 더 많은 형식 예제를 넣는 것은 해법이 아닐 수 있다.

**근거 충돌 실패:** 멀티모달 검색이 찾은 사진과 사양서, ERP의 정형 값이 충돌한다면 한 값을 임의 선택하지 않는다. 출처, 버전, 기준 시각을 나란히 보여 주고 정해진 소유자에게 검토를 요청한다. 이미지 유사도는 탐색 순서를 정할 수 있지만 부품 적합성이나 인사 승인 권한의 최종 판정이 아니다. 모델의 설명이 매끄러울수록 숨겨진 충돌을 리뷰 화면에 명시하는 장치가 필요하다.

**운영 판단 실패:** 장애 요약에 근거가 없거나 잘못된 확신이 반복되면 전달 지연을 줄이는 실험보다 먼저 출처 표기와 신뢰도 표현을 고친다. 경고에서 실제 원인까지의 연결을 검증 가능한 로그 링크로 제공한다. 가설을 여러 개로 유지할 수 있게 하고, 조사 실패 또는 자료 부족을 정상 상태로 처리한다. ‘원인을 찾지 못함’은 실패를 숨기는 문장보다 안전한 결과일 수 있다.

## 수치와 주장에 대한 해석 주의

- **45~60분→15분 미만**은 Circle K의 장애 **초동 분류** 시간이며, 전체 장애 복구 시간의 개선률이 아니다. 제품과 조직의 운영 방식이 다르면 성과도 달라진다.
- **증류 학생의 점수 상승**은 ShoppingBench의 보류 문제와 원문이 사용한 모델·데이터·도구 루프에 대한 결과다. 학습되지 않은 산업 도메인에서 같은 정확도를 기대할 수 없다.
- **멀티모달 유사도**는 후보를 찾기 위한 신호다. 물리·법률·인사상 적합성의 확정 근거가 아니다. 결정적 검사와 사람 검토가 따로 필요하다.
- **300토큰·20% 겹침**은 원문이 설명한 관리형 지식베이스의 기본 청크 설정이지 모든 문서에 적합한 최적값이 아니다. 표와 예외 조항이 있는 문서는 실제 질문으로 비교해야 한다.
- **실시간 웹과 배치 수집**은 다르다. 수집 완료 시각과 문서 자체의 발효일도 다르다. 최신성 요구가 높은 문의라면 검색 시점의 원천 확인이 필요할 수 있다.

## 결론: 빠른 답변보다 추적 가능한 결정

오늘 새벽 공개된 네 AWS 글은 AI 에이전트를 운영할 때 모델의 크기보다 **근거의 수명, 행동의 평가, 판정의 책임, 현장 조사의 맥락**이 중요함을 보여 준다. 웹 자료는 가져온 뒤 언제 사라지는지까지 관리해야 한다. 작은 모델은 그럴듯한 문장보다 실제 도구 루프의 성공으로 평가해야 한다. 멀티모달 검색은 후보를 넓히되 결정적 사양 검사와 사람의 승인 자리를 빼앗지 않는다. 장애 대응 자동화는 조사를 앞당길 수 있지만 복구의 판단과 사후 책임을 흐리지 않는다. 네 층을 연결하는 공통 조건은 **어떤 원천에서 어떤 행동을 거쳐 어떤 결과가 확정됐는지 재구성할 수 있는 제품 설계**다.

## 심층 실무 노트: 네 흐름이 만나는 지점

### 1) 출처의 체인과 실행의 체인을 함께 남긴다

오늘 네 사례를 따로 도입하면 각 팀은 자신의 로그가 충분하다고 생각하기 쉽다. RAG 팀은 문서 URL을 남기고, 모델 팀은 학습 실행 ID를 남기고, 에이전트 팀은 도구 호출을 남기고, 운영팀은 경고 ID를 남긴다. 그러나 사용자의 실제 문제는 이 네 체인을 가로지른다. 예컨대 AI가 오래된 휴가 규정에 근거해 신청 가능하다고 답했고, 사용자가 신청 버튼을 눌렀는데 서버가 거절했으며, 당직자는 오류 경고만 받았다고 하자. 문서와 에이전트 실행과 업무 요청과 운영 사건을 연결할 수 없으면 각각은 정상처럼 보인다. 결국 같은 오류가 재발한다.

연결은 모든 원시 내용을 한곳에 복사하라는 뜻이 아니다. 이벤트마다 안정적인 식별자를 남기고, 권한 있는 운영자가 필요한 범위에서 증거를 조합할 수 있게 한다. 문서에는 원천 ID와 버전, 검색 결과에는 청크 ID와 인용 URL, 도구 호출에는 요청 ID와 검증 결과, 업무 변경에는 서버 트랜잭션 ID, 경고에는 사건 ID를 둔다. 각 단계의 데이터 보존 기간은 다르게 설정할 수 있다. 개인정보를 포함한 도구 결과는 짧게 보존하거나 마스킹하되, 잘못된 판단의 원인이 된 문서 버전과 도구 종류는 재현 가능해야 한다. **추적성은 데이터 최대 보관이 아니라 결론의 근거를 다시 찾을 수 있는 최소 구조**다.

이 연결이 없는 시스템은 장애 후 회의에서 모델을 탓하기 쉽다. 실제 원인은 웹 페이지의 CSS 변경으로 본문 추출이 빈 문서가 된 것일 수도 있다. 또는 검색은 맞았지만 학생 모델이 도구 결과를 읽기 전에 답을 끝냈을 수도 있다. 사진 검색은 후보를 올바르게 찾았지만 뒤의 정형 사양 검사가 이전 버전 파일을 읽었을 수도 있다. 장애 분석 에이전트가 정확한 로그를 찾았는데 Slack 요약의 절단 때문에 근거가 빠졌을 수도 있다. ‘AI가 틀렸다’는 통합 분류는 개선점을 숨긴다. 데이터, 검색, 행동, 판정, 전달을 분리하면 각 담당자가 고칠 수 있다.

### 2) ‘최신’이라는 단어를 다섯 가지 시계로 분해한다

웹 기반 지식 서비스의 최신성은 하나의 시각이 아니다. **원천 게시 시각**은 작성자가 글을 공개한 때다. **시행 시각**은 정책이 적용되는 때다. **크롤 시각**은 시스템이 읽은 때다. **인덱스 반영 시각**은 검색 가능해진 때다. **사용자 질문 시각**은 답변이 필요했던 때다. 이 순서는 항상 일정하지 않다. 미래에 시행될 정책이 오늘 게시될 수 있고, 어제 시행된 정책을 오늘 밤에야 수집할 수 있다. 페이지는 재수집됐지만 인덱싱 오류 때문에 오래된 청크가 남을 수 있다.

사용자에게 ‘최신 정책 기준’이라고 말하려면 무엇을 기준으로 최신이라 하는지 먼저 정의해야 한다. 대부분의 제품에서는 현재 시행 중인 버전을 찾고, 검색 인덱스가 그 버전을 반영했음을 확인해야 한다. 자료가 끊겼을 때는 과거 답변을 그대로 보여 주기보다 확인 불가 상태를 알리는 편이 낫다. 반대로 과거 특정 시점의 신청을 감사하는 화면이라면 당시 시행된 규정이 필요하다. 같은 질문 문장이라도 `오늘 신청 가능한가`와 `지난달 신청이 왜 거절됐는가`는 다른 버전을 검색해야 한다. RAG 메타데이터 설계는 검색 정확도뿐 아니라 시간에 따른 업무 의미를 표현해야 한다.

Circle K 사례에도 여러 시계가 있다. 경고가 발생한 때, 로그가 수집된 때, 모델이 조회한 때, 코드가 배포된 때, 담당자가 메시지를 읽은 때다. 사건의 선후관계가 잘못되면 모델이 ‘직전 배포가 원인’이라고 말하지만 실제로 배포는 오류 뒤였을 수 있다. 모든 시스템의 시계를 동기화하고 시간대를 명시하는 일은 멀티 에이전트 설계보다 덜 화려하지만 중요하다. 오늘 뉴스에서도 UTC 게시 시각을 KST로 환산하지 않으면 어제 뉴스와 오늘 뉴스를 혼동한다. 시간의 분모를 고정하는 것이 해석의 출발점이다.

### 3) 경로별 실패를 사용자에게 다른 문장으로 보여 준다

검색에서 문서가 없을 때와 정책상 답할 수 없을 때를 같은 ‘죄송합니다’로 처리하면 사용자가 재시도할 이유를 알 수 없다. **원천 미수집**이면 자료 동기화 상태와 공식 원문을 안내할 수 있다. **권한 부족**이면 문서가 있다는 사실조차 드러내지 않으면서 적절한 접근 요청 경로를 보여 줄 수 있다. **검색 결과 충돌**이면 어느 문서끼리 충돌하는지 권한 범위에서 설명하고 담당자 확인을 요청할 수 있다. **모델 도구 실패**면 사용자가 이미 입력한 값은 보존하되 확정하지 않는다. **업무 규칙 거절**이면 서버가 계산한 사유와 이의 제기 절차를 보여 준다.

운영자에게는 더 세밀한 상태가 필요하다. ‘AI 오류’라는 단일 지표 대신 `source_unavailable`, `content_extraction_failed`, `ingestion_pending`, `retrieval_low_confidence`, `tool_argument_invalid`, `policy_denied`, `human_review_required`처럼 단계별 코드가 유용하다. 사용자에게 내부 코드를 그대로 보여 줄 필요는 없지만, 운영 지표와 사용자 문구가 같은 상태 모델을 공유하면 설명이 일관된다. 상태 모델은 모델이 자유롭게 생성한 단어가 아니라 서버가 관리해야 한다. 모델은 상황을 요약할 수 있어도 최종 업무 상태를 만들어내서는 안 된다.

### 4) RAG 평가표를 답변 평가와 분리한다

한 번의 최종 답변 평가에서 ‘정답’만 보면 검색 경로의 개선이 어렵다. 적어도 네 묶음의 질문을 만든다. **정확한 문서 발견**: 권한 있는 최신 원문이 상위 결과에 있는가. **불필요한 문서 배제**: 오래된 버전, 다른 부서 정책, 메뉴·광고 청크가 상위에 섞이지 않는가. **인용의 충실성**: 답변의 핵심 주장마다 정확한 문단이 뒷받침되는가. **답변의 업무 적합성**: 사용자가 다음에 해야 할 행동과 예외 조건을 이해할 수 있는가. 이 네 가지가 모두 통과해야 실무적 정답이다.

예를 들어 ‘퇴직 전 미사용 휴가 정산’ 질문에 맞는 규정이 5위에 있고 1위는 오래된 규정이라면 모델이 우연히 5위를 읽어 정확히 답하더라도 검색 품질은 위험하다. 다음 질문에서는 1위만 읽을 수 있다. 반대로 정확한 규정이 1위여도 모델이 예외 조항을 빼면 요약 품질 실패다. 인용 URL은 맞지만 구체적인 조항이 다른 청크에 있으면 인용 충실성 실패다. 따라서 문서 수정, 청크 설정 변경, 재수집, 임베딩 교체가 있을 때는 검색 평가를 먼저 돌리고 생성 평가를 다음에 돌린다. 이전 결과와 비교할 때 질문 집합과 문서 버전도 기록한다.

평가 세트는 쉬운 질문만 쌓으면 안 된다. 제목이 비슷한 두 규정, 서로 다른 시행일, 삭제됐지만 검색에 남은 페이지, HTML 표의 머리글이 누락된 페이지, URL 리디렉션, 같은 내용을 여러 도메인에 복제한 페이지가 필요하다. 이런 사례는 크롤러와 인덱스 운영의 실패를 드러낸다. 원문 AWS 글이 `Retrieve`부터 보라고 권하는 이유는 생성 답변에 가려진 검색 실패를 먼저 분리하기 위해서다. 정답이 없는 질문에 억지로 답하지 않는지도 별도 평가 항목으로 둔다. 출처가 없는 완성된 문장은 정답처럼 보이지만 재검증하기 어렵다.

### 5) 증류 데이터에서 성공만 남길 때의 편향을 점검한다

성공 궤적만 학습시키는 것은 잘못된 행동을 가르치지 않는 장점이 있다. 그러나 채점기가 해결할 수 있는 문제만 선별하는 효과도 있다. 교사가 자주 실패하는 어려운 상황, 카탈로그에 정보가 부족한 상황, 사용자의 조건이 모호한 상황은 학습 데이터에서 사라질 수 있다. 실제 제품에서는 그런 상황이 오히려 사람에게 이관해야 하는 중요한 경계다. 따라서 성공 학습 데이터와 별도로 **실패 평가 데이터**를 보존해야 한다. 어떤 이유로 탈락했는지도 기록한다. 교사가 제약을 위반했는지, 도구가 실패했는지, 평가기가 판정할 수 없었는지에 따라 대응이 다르다.

원문 샘플의 ShoppingBench는 정답을 기계적으로 검사할 수 있어 성공 판정이 명확하다. 업무 시스템은 그렇지 않을 때가 많다. ‘추천이 도움이 되었는가’는 사용자의 반품, 다음 행동, 장기 만족도와 연결되고, HR 문의의 ‘정확한 답’은 법·취업규칙·개별 계약 조건에 따라 달라진다. 평가기가 놓치는 조건이 있다면 성공 궤적도 실제로는 실패다. 작은 학생이 큰 교사의 추론 형식을 잘 배워도 사실 검증이 없는 조건에서는 오류를 재생산할 수 있다. 학습 목표와 업무 성공 기준을 문서로 연결해야 한다.

학생 모델을 제품에 넣을 때는 모델 교체 외의 변수도 고정한다. 도구 API가 변경되고 검색 데이터가 갱신되고 프롬프트가 수정된 상태에서 학생과 교사를 비교하면 어느 변화가 성과를 만들었는지 모른다. 동일한 질문 집합, 동일한 데이터 스냅샷, 동일한 도구 제한, 비슷한 동시 요청 조건을 사용한다. 이후 실제 사용자 트래픽의 소규모 단계적 배포에서 예상과 다른 오류를 본다. 최종 선택 기준은 벤치마크 평균뿐 아니라 위험 사례의 미통과 건수, 운영 지연, 응답 품질, 사용자 완수율이다. 평균이 높아도 무단 조회 한 건은 배포를 막을 수 있다.

### 6) 비용은 ‘성공한 작업 한 건’으로 계산한다

모델 호출 비용만 비교하면 에이전트 루프의 경제성이 왜곡된다. 각 작업의 총비용에는 교사 데이터 생성, 학습 작업, GPU 엔드포인트의 대기 시간, 검색 서버, 벡터 인덱스, 도구 API, 재시도, 사람이 수동으로 고친 시간까지 들어간다. 어떤 비용은 선투자이고 어떤 비용은 요청량에 따라 증가한다. 교사 모델은 호출량이 적을 때 고정 인프라를 갖추지 않아도 된다. 학생 모델은 충분한 부하에서 단가가 낮을 수 있지만 사용량이 적은 밤에도 엔드포인트가 켜져 있으면 비용이 발생한다. 원문이 단일 작업당 비용 숫자를 내지 않은 이유가 여기 있다.

비교식은 복잡할 필요가 없다. 월 총비용을 월간 **성공한 작업 건수**로 나누고, 오류 수정 비용을 별도 표시한다. 실패한 작업도 비용에 포함한다. 자동 답변이 1만 건이지만 2천 건이 사람에게 재처리된다면 자동 처리당 비용보다 재처리를 포함한 성공당 비용이 더 중요하다. 지연도 평균만 보지 않는다. 길고 복잡한 요청이 p95를 높이는지, 타임아웃 때문에 사용자가 재시도해 비용을 두 번 내는지 본다. 학생 모델이 빠른 대신 같은 결과에 도달하려고 더 많은 도구 단계를 쓰면 기대한 절감이 사라질 수 있다.

학습 비용은 실험 실패까지 포함한다. 데이터가 잘못 분할되어 결과를 다시 내거나, 도구 관찰을 과하게 잘라 모델을 다시 훈련하면 초기 예상보다 비용이 커진다. 반대로 성공 궤적 데이터셋이 여러 학생 모델을 비교하는 데 재사용된다면 선투자 가치가 높아질 수 있다. 모델 운영비 절감이 목표라면 연구 실험과 서비스 운영의 비용 계정을 분리해 측정한다. 사용자에게 지연이 중요한 업무인지, 모델 비용이 월 예산의 큰 비중인지에 따라 증류의 우선순위도 달라진다. 작은 모델 도입은 목표가 아니라 가설이다.

### 7) 이미지 검색의 확신도와 사양 검사의 확실성을 분리한다

코사인 유사도는 두 이미지 임베딩이 가까운 정도다. 사진의 각도와 조명, 배경, 해상도, 잘림 방식에 영향을 받는다. ‘0.92라서 대체품으로 안전하다’는 해석은 잘못이다. 그 점수는 후보를 먼저 볼 순서를 정하는 데 쓸 수 있어도 물리적 호환성의 승인 기준으로 바로 쓰면 안 된다. 부품 예제는 이를 정형 스펙 비교와 엔지니어 리뷰로 분리한다. HR의 문서 사진에서도 도장 모양이 비슷하다는 사실과 실제 발급기관이 맞는지는 다른 문제다. 사진 검색 결과는 원본 문서 확인과 독립된 검증이 필요하다.

결정적 검사도 입력이 틀리면 틀린 결론을 낸다. 사양 JSON의 전압 필드가 옛 제품 값을 담고 있다면 Python 비교는 매번 같은 잘못된 판정을 재현할 것이다. ‘결정적’은 **동일 입력에 동일 결과**라는 의미이지 입력의 진실성을 자동 보증하지 않는다. 따라서 원문의 구조는 확률적 검색을 코드 검사로 보완하면서도, 코드 검사에 들어가는 정형 값의 출처와 버전을 함께 확인해야 완성된다. 엔지니어가 최종 결정을 하려면 검색 결과뿐 아니라 검사에 사용된 실제 값과 공차 규칙도 볼 수 있어야 한다.

모순이 있을 때 시스템은 어떤 종류인지 분류할 수 있다. 이미지와 정형 값이 충돌하는지, 서로 다른 버전의 문서가 충돌하는지, 같은 버전의 문서와 ERP 값이 충돌하는지, 모델의 해설만 원문과 충돌하는지다. 충돌 유형별 소유자가 다르다. 이미지 분류 문제는 검색팀, 사양 데이터 문제는 마스터 데이터 담당자, 규칙 문제는 도메인 전문가, 요약 문제는 에이전트팀이 맡을 수 있다. 사람이 승인한다는 말을 남발하기보다 **어떤 사람이 무엇을 보고 어떤 기록을 남겨야 하는지** 정의하는 것이 운영 가능한 설계다.

### 8) 장애 요약에서 사실·가설·권고를 다른 칸에 둔다

장애 조사 에이전트의 메시지를 자유로운 문단 하나로 만들면 당직자가 검증된 사실과 모델 추정을 구별하기 어렵다. 구조화된 양식은 최소한 **관측 사실**, **원인 가설**, **반증 가능한 대안**, **추가 확인**, **권장 조치**, **조치 위험도**를 나눌 수 있다. 예컨대 ‘5xx 증가’와 ‘DB 연결 거절 로그’는 관측이다. ‘마케팅 캠페인이 부하를 늘렸다’는 시간 상관관계가 있는 가설이다. ‘RDS Proxy 도입’은 장기 개선 권고이며, 실시간 사고의 즉각적인 완화책과는 다르다. 모델이 세 종류를 같은 확신 문장으로 합치지 않게 한다.

근거 링크를 붙이는 것만으로 충분하지 않다. 링크를 열 수 있는 권한이 당직자에게 있는지, 사건 시점으로 필터가 고정됐는지, 로그가 보존 기간 안에 있는지 확인해야 한다. 링크가 사라진 뒤에도 사건의 핵심 지표와 조치 기록을 감사 가능한 범위에서 남긴다. 반대로 원시 로그를 Slack에 길게 복사하면 민감 정보가 더 넓게 퍼질 수 있다. 요약에는 최소한의 증거와 안전한 탐색 링크를 제공하는 편이 낫다. 보안 경계는 입력과 출력 양쪽에 있다.

운영 시간 지표도 구분한다. `탐지까지`, `조사 시작까지`, `첫 유효한 가설까지`, `완화 시작까지`, `서비스 회복까지`, `근본 원인 확인까지`는 서로 다른 단계다. Circle K의 수치는 초동 분류의 개선이다. 모델이 첫 유효 가설을 빨리 제공해도 사람의 승인이나 실제 수정에 시간이 걸릴 수 있다. 반대로 자동화가 잘못된 원인을 빨리 제시하면 회복까지는 더 느려질 수 있다. 운영 대시보드는 빠른 결과를 보여 주는 숫자 하나보다 사용자 영향과 잘못된 조치의 빈도를 함께 보여 줘야 한다.

### 9) 도구 루프와 장애 대응에 같은 중단 조건을 둔다

쇼핑 에이전트가 같은 검색을 계속 반복하는 것과 장애 조사 에이전트가 계속 로그를 읽는 것은 형태가 비슷하다. 어느 쪽도 ‘더 생각하면 더 좋은 답이 나온다’고 무한정 실행할 수 없다. 최대 단계 수, 토큰·시간 예산, 동일 도구 재호출 제한, 새로운 증거가 늘지 않는 상태의 종료 조건을 정의해야 한다. 중단할 때는 무조건 실패라고만 하지 않고 확보한 사실과 아직 모르는 사실을 분리해 반환한다. 사람에게 넘길 때는 이미 확인한 범위를 함께 보내 반복 조사를 줄인다.

중단 조건은 도메인에 따라 다르다. 상품 추천은 조건을 만족하는 후보가 없으면 ‘찾지 못함’으로 끝낼 수 있다. 인사 승인 요청은 규정 충돌이 있으면 반드시 검토로 이관해야 한다. 장애 조사에서는 중요한 고객 영향이 커지는 동안 완벽한 원인을 찾겠다고 기다리지 말고 현재 유효한 증거와 안전한 완화 선택지를 당직자에게 전달해야 한다. 도구 루프의 품질은 정답률뿐 아니라 **적절한 시점에 멈추는 능력**이다. 원문 증류 글의 단계 수와 Circle K 사례의 분류 시간은 이 문제를 서로 다른 각도에서 보여 준다.

### 10) 운영 도입을 위한 최소 산출물

첫 번째 산출물은 **원천 등록부**다. 자료의 URL 또는 저장소, 소유자, 접근 권한, 게시·시행·수집·반영 시각, 삭제 절차를 포함한다. 이 문서가 없으면 RAG 결과가 틀릴 때 누구에게 물어야 할지 모른다. 두 번째는 **도구 계약서**다. 도구별 입력 스키마, 허용 주체, 부작용, 멱등성, 실패 코드, 로그 정책을 적는다. 모델이 어떤 도구를 호출할 수 있는지와 서버가 실제로 허용하는 권한을 구별한다. 세 번째는 **평가 세트**다. 성공 예제뿐 아니라 권한 거절, 오래된 출처, 검색 충돌, 이미지 오인식, 도구 타임아웃, 잘못된 원인 추정도 포함한다.

네 번째는 **운영 사건 양식**이다. 사실, 가설, 근거 링크, 영향 범위, 담당자, 다음 확인, 조치 결과를 기록한다. 다섯 번째는 **전환과 복귀 기준**이다. 학생 모델의 품질이 하락했을 때 이전 모델로 어떻게 돌아갈지, 검색 인덱스가 낡았을 때 답변을 제한할지, 사고 분석 에이전트가 오탐을 반복할 때 자동 전달을 중지할지 정한다. 여섯 번째는 **비용·지연·품질 대시보드**다. 모델 호출 수만이 아니라 성공한 업무, 사람 재처리, 문서 최신성, 도구 실패, 운영 사고의 실제 회복 시간까지 묶는다. 이 산출물들은 특정 클라우드 제품에 종속되지 않는다.

## 마무리: 오늘의 네 공식 글을 읽는 순서

처음부터 네 기술을 한 번에 도입할 필요는 없다. 이미 RAG를 운영한다면 AWS의 Crawl4AI 글에서 **수집 자료의 삭제와 인용 검증**을 먼저 점검한다. 도구를 많이 호출하는 에이전트의 비용이 고민이면 증류 글에서 **문제 단위 평가와 성공당 비용**을 읽는다. 사진·도면을 검색한다면 엔지니어링 사례에서 **검색 유사도와 정형 판정의 역할 분리**를 참고한다. 장애 대응이 느리다면 Circle K 사례에서 **반복적인 맥락 수집의 자동화**를 확인한다. 네 글을 관통하는 실행 원칙은 동일하다. 원천을 확인하고, 행동을 추적하고, 확정 권한을 분리하고, 사용자 또는 운영자가 실제로 겪는 결과를 측정한다.

## 설계 예제 A: 규정 검색 서비스의 수집 계약을 처음부터 끝까지 적는다

### 원천을 등록할 때

회사 규정 검색 서비스를 맡았다고 해 보자. 운영자는 먼저 크롤러를 설치하지 않고 **원천 목록**을 만든다. 공개 법령 사이트의 문서, 회사 내부 취업규칙, 직원 포털의 도움말은 서로 접근 방법과 권한이 다르다. 공개 법령에는 원문 URL과 시행일을 필수로 적고, 사내 규정에는 문서 소유 부서·승인 버전·적용 조직을 추가한다. 직원 포털 도움말은 실제 법적 근거가 아니라 사용 절차 설명일 수 있으므로 검색 결과에서 별도 범주로 보여 준다. 서로 다른 문서의 의미를 같은 ‘지식’으로 합치지 않는 것이 첫 단계다.

원천 등록부에는 수집 허용 범위도 적는다. 공개 웹이라고 해서 사이트 전체를 무제한 탐색할 필요는 없다. 법령 본문 경로만 허용하고 검색 페이지, 댓글, 개인화 영역, PDF 미리보기의 중복 경로는 제외할 수 있다. AWS 샘플이 URL 범위와 리디렉션 후 도착 URL을 확인하는 이유가 여기에 있다. 리디렉션으로 인증 페이지나 다른 도메인에 이동했는데 요청 URL만 검사하면 의도치 않은 자료를 가져올 수 있다. 크롤 성공률보다 **허용 범위 준수율**이 먼저다.

문서 소유자가 갱신 주기를 모른다고 한다면 수집기는 그 불확실성을 숨기지 않아야 한다. 매일 크롤해도 원문이 갱신되지 않으면 정책의 실질 유효성은 확인할 수 없다. 사이트의 게시일이 빠졌다면 수집 시각만으로 ‘오늘 정책’이라고 표현하지 않는다. 원문에서 발효일을 파싱하는 규칙을 만들 수 있어도 그 파싱이 검증됐는지 표본 검사를 한다. 데이터가 부족한 상태를 빈 값으로 표현하는 편이 임의의 날짜를 채워 넣는 것보다 낫다. 나중에 사용자가 답변을 문제 삼았을 때 기록의 공백이 드러나면 바로 수정할 수 있지만, 잘못된 확정 값은 사고 원인을 숨긴다.

### 추출 품질의 수용 기준을 정할 때

크롤러가 HTML을 Markdown으로 바꾸면 최소한 제목, 절 번호, 표의 행과 열, 각주, 개정일, 첨부 링크가 살아 있는지 확인한다. 무작위로 다섯 페이지만 보는 대신 문서 유형을 나눠 표본을 고른다. 짧은 공지, 긴 규정, 표 중심 문서, 자바스크립트로 본문을 그리는 페이지, 수정 이력이 많은 문서, PDF 링크 중심 페이지가 모두 필요하다. 한 유형이 실패하면 그 유형의 수집을 보류한다. 전체 95% 성공이라는 숫자보다 중요한 조항 하나가 누락된 것이 더 심각할 수 있다.

본문 필터가 내비게이션을 제거하는 것은 좋은 일이지만 예외 조항이 접힌 영역에 있을 수 있다. 원본 HTML에서 본문 텍스트의 길이와 추출 결과의 길이를 비교하는 자동 규칙은 이상을 찾는 출발점이다. 하지만 길이가 비슷해도 표가 평탄화되면서 열 의미가 바뀔 수 있다. 예를 들어 ‘근속 1년 미만’과 ‘1년 이상’의 휴가 일수가 표에서 서로 뒤바뀌면 글자 수는 거의 같다. 중요한 표는 구조 비교나 대표 질의 평가가 필요하다. 추출 도구의 업데이트가 이 변환을 바꿀 수 있으므로 버전을 고정하고 변경 전후의 차이를 기록한다.

추출된 Markdown의 제목이 페이지 제목과 일치하는지도 본다. 하나의 HTML 페이지에 여러 규정이 붙어 있으면 하나의 거대한 문서로 인덱싱하기보다 규정 단위로 나누는 편이 검색에 유리할 수 있다. 반대로 조항을 너무 작게 잘라 정의와 예외가 분리되면 오답이 늘어난다. 청크 전략을 결정하기 전에 문서 단위부터 정해야 한다. AWS 원문이 기본 청크 설정을 설명하지만, 실제 최적값은 문서 구조와 질문 유형에 달려 있다. 청크 크기 하나를 바꿔 해결할 문제인지 원천 분할부터 다시 해야 할 문제인지 구별한다.

### 동기화와 삭제를 테스트할 때

새 규정이 게시되었을 때 수집·인덱싱이 얼마나 걸리는지 측정한다. 이 시간을 **최신성 지연**으로 기록한다. 그러나 지연이 짧아도 이전 규정이 검색에서 제거되지 않으면 두 버전이 공존한다. 따라서 변경 테스트는 신규 문서가 나타났는지뿐 아니라 폐기 문서가 사라졌는지를 함께 확인한다. 커스텀 S3 경로라면 파일과 sidecar를 함께 삭제한 다음 수집을 다시 돌려야 한다. 원문에서 설명한 삭제 보호가 동작했다면 인덱스에 남아 있는지 별도 확인한다. 삭제 요청 성공 응답만으로 검색 결과 삭제를 추정하지 않는다.

삭제 정책은 일시적 오류와 실제 폐기를 구분해야 한다. 사이트가 잠깐 503을 반환하면 크롤러는 페이지를 놓칠 수 있다. 이때 무조건 S3 문서를 삭제하면 사용자 답변에 공백이 생긴다. 반대로 404가 수일간 지속되고 공식 목록에서도 빠졌다면 폐기 검토를 시작할 수 있다. 리디렉션으로 새 URL에 이동했다면 옛 URL 문서를 단순 삭제하기보다 새 문서와 버전 관계를 연결한다. 법령처럼 과거 시점 조회가 필요한 자료는 완전 삭제 대신 역사 인덱스로 이동할 수도 있다. 이 선택은 법적 보존 요구와 제품의 질문 유형에 따라 다르며, 크롤러의 기본 동작에 맡길 결정이 아니다.

수집이 끝난 후에는 실제 질문 세트를 돌린다. ‘올해 적용되는 규정’, ‘작년 당시 규정’, ‘해당 조직의 예외’, ‘존재하지 않는 조항’을 분리한다. 검색 결과가 한 문서에 과도하게 몰리면 중복 청크 여부를 확인한다. 본문이 맞아도 인용 URL이 홈페이지로만 돌아가면 검증 경험이 나쁘다. 사용자가 클릭하면 정확한 조항으로 갈 수 있는지, 내부 문서라면 권한이 없는 사람에게 URL을 노출하지 않는지 확인한다. 원문 인용은 답변의 부속물이 아니라 신뢰 계약이다.

### 운영 장애를 재현할 때

문서가 잘못 인용된 사고를 조사하는 절차를 실제로 연습한다. 사고 시점의 사용자 질문, 검색 인덱스 버전, 상위 검색 결과, 모델 입력에 들어간 문맥, 최종 답변, 당시 원천 문서를 차례로 확인한다. 검색은 옳았는데 답변이 틀렸다면 요약 문제다. 검색 결과부터 틀렸다면 문서 추출·메타데이터·청크·랭킹으로 더 내려간다. 원천 문서가 잘못됐다면 문서 소유자에게 수정 요청을 해야 한다. 모델 프롬프트를 바꾸는 일은 마지막이 될 수 있다. 이 절차를 갖추면 문제를 만든 계층과 고칠 계층이 같아진다.

## 설계 예제 B: 증류한 에이전트를 배포 가능한 기능으로 만드는 심사

### 문제 집합을 설계할 때

학생 모델의 훈련용 예제를 모으기 전에 성공의 정의를 정한다. 쇼핑이라면 가격, 평점, 재고, 배송 국가, 쿠폰 적용 조건 중 무엇을 반드시 만족해야 하는지 명시한다. 인사시스템이라면 직원 권한, 정책 버전, 신청 날짜, 잔여량, 승인 상태를 구분한다. 단순히 사람이 최종 문장을 보고 ‘괜찮아 보인다’고 판단하면 성공한 도구 궤적을 선별할 수 없다. 가능하면 결정적 채점기와 도메인 전문가 검토를 결합한다. 자동 채점이 가능한 부분은 고정하고, 모호한 부분은 별도 라벨로 남긴다.

문제 집합은 정상 요청의 빈도만 반영하면 안 된다. 사용자가 조건을 일부 빠뜨린 요청, 서로 모순된 조건, 자료가 없는 요청, 권한이 없는 요청, 도구가 느리거나 실패하는 요청을 포함한다. 이런 사례에서 바람직한 행동은 정답 상품을 찾는 것이 아니라 질문을 되묻거나 안전하게 중단하거나 사람에게 넘기는 것일 수 있다. 성공 궤적의 정의도 그에 따라 달라진다. ‘항상 답하기’가 목표이면 모델이 모르는 것을 인정하지 못하게 된다. 평가 세트는 자주 일어나는 사례와 피해가 큰 사례의 균형을 맞춘다.

교사 모델이 같은 문제를 두 번 풀었다면 두 궤적을 모두 독립된 문제로 취급하지 않는다. 원문처럼 문제 단위로 학습과 보류 평가를 나눈다. 유사한 문장으로 바꾼 문제도 정답 조건이 같다면 데이터 누수를 일으킬 수 있다. 특히 상품 카탈로그나 정책 문서가 학습과 평가에서 같을 때 학생이 특정 상품 ID를 기억했을 수 있다. 모델의 일반화 능력을 보려면 새 상품, 다른 정책 버전, 드문 도구 오류를 포함한 별도 평가가 필요하다. 벤치마크 점수와 제품 내 실전 점수를 구분해 보고한다.

### 궤적을 선별할 때

성공 판정만으로 학습 데이터가 안전하다는 뜻은 아니다. 교사가 검색 결과를 많이 읽고 우연히 정답을 찾았다면 비효율적인 행동을 학생에게 가르칠 수 있다. 같은 검색을 여러 번 반복한 뒤 성공했다면 정답이라는 이유만으로 모범 궤적으로 삼을지 검토해야 한다. 반대로 빨리 답했지만 근거를 확인하지 않았다면 잠재적 위험이 있다. 데이터 선별 기준에 정답 제약 충족 외에도 도구 사용 횟수, 불필요한 권한 요청, 근거 확인 여부, 중간 단계의 허위 주장을 넣을 수 있다. 다만 지나치게 완벽한 궤적만 남기면 실제 현장의 다양한 상황을 학습하지 못한다.

도구 관찰을 압축할 때는 정보 선택의 기준이 필요하다. 가격과 평점은 쇼핑 제약에 중요하지만 상품 목록의 광고 문구는 덜 중요할 수 있다. 그러나 반품 불가 조건이 사용자에게 중요한 경우 그 문구를 버리면 안 된다. HR에서는 신청 날짜와 잔여량뿐 아니라 적용 정책 버전이 결정에 필요하다. 압축 규칙은 모델 팀만 정하지 말고 도메인 담당자가 검토한다. 토큰 비용 절감이 업무 의미를 없애는지 테스트한다. 압축 전후에 같은 채점 결과가 나오는지 일부 문제를 비교하면 손실의 영향을 파악할 수 있다.

학습 데이터를 저장할 때는 교사 호출이 어떤 모델 버전과 도구 스키마에서 이뤄졌는지 기록한다. 도구 결과 포맷이 바뀌면 옛 궤적의 행동이 현재 서비스에서 더는 유효하지 않을 수 있다. 정책이 바뀌면 과거의 ‘성공’이 오늘의 실패가 될 수 있다. 데이터셋은 영구 정답 모음이 아니라 특정 시점의 행동 샘플이다. 시간이 지나면 폐기하거나 다시 채점해야 한다. 특히 개인정보가 섞일 수 있는 환경에서는 학습 데이터의 생성과 보존에 업무 데이터보다 엄격한 통제가 필요할 수 있다.

### 평가를 두 단계로 진행할 때

사전 평가는 학생 모델이 교사와 같은 맥락에서 다음 도구 행동을 합리적으로 고르는지 본다. 이 단계는 전체 환경을 띄우지 않아도 되므로 여러 실험을 싸게 비교할 수 있다. 다만 다음 행동 하나만 맞히는 모델이 전체 문제를 풀지는 못한다. 도구 관찰을 읽고 다음 계획을 세우며, 조건을 다시 확인하고, 끝날 때를 아는 능력은 긴 루프에서 드러난다. 그래서 본 평가는 실제 도구와 동일한 제한을 건 하네스로 실행한다. 결과는 의도별 성공률과 실패 유형으로 나눠 본다.

기본 모델보다 좋아졌다는 것만으로 배포하지 않는다. 교사 모델과 비교하고, 현재 서비스 모델과 비교하고, 위험 사례의 절대 기준을 확인한다. 예를 들어 전체 성공률이 크게 올라가도 타인 정보 조회를 막지 못하면 서비스에 넣을 수 없다. 벤치마크 평균은 마케팅 숫자가 되기 쉽지만 운영 결정을 위해서는 **가장 나쁜 실패의 종류**가 더 중요할 때가 많다. 원문이 사용한 보류 문제 324개도 특정 벤치마크의 분포를 나타낸다. 실제 서비스의 드문 오류까지 모두 포함한다고 주장하지 않는다.

### 점진적으로 전환할 때

학생 모델을 바로 기본 경로로 바꾸기보다 읽기 전용·낮은 위험의 요청에서 먼저 시험한다. 교사와 학생의 결과를 조용히 비교하는 그림자 평가를 하거나 제한된 사용자 집단에서 단계적으로 적용한다. 도구 호출 횟수, 타임아웃, 사용자 수정률, 성공당 비용을 함께 본다. 모델이 도구를 올바르게 불러도 사용자가 결과를 이해하지 못해 다음 단계에서 이탈하면 제품 가치는 낮다. 에러가 늘면 이전 모델로 되돌리는 기준을 사전에 정한다. 한 단계의 점수보다 실제 사용자 흐름의 완수율이 출시 판단에 가깝다.

전환 중에 모델뿐 아니라 시스템 프롬프트, 검색 인덱스, 도구 정의를 한꺼번에 바꾸면 결과 해석이 어려워진다. 변수 하나씩 변경하고, 변경 이유와 기대 효과를 기록한다. 성능 향상 원인을 확신할 수 없는 경우에는 단정하지 않는다. 새 학생 모델이 더 빨랐지만 캐시 적중률도 높아졌다면 어느 요소가 지연을 줄였는지 구분해야 한다. 비용도 같은 기간의 요청량과 요청 길이를 맞춰 비교한다. 판단이 어려울수록 문서화된 실험 설계가 필요하다.

## 설계 예제 C: 멀티모달 증거를 검토 화면에 올리는 방식

### 후보와 판정을 분리한 화면

엔지니어링 부품 검토 화면을 만든다면 검색 결과는 ‘후보’ 열에, 규칙 검사 결과는 ‘사양 적합성’ 열에, 최종 검토 상태는 ‘결정’ 열에 둔다. 사진 유사도가 높은 부품이 첫 번째에 나오더라도 정형 사양의 필수 요건 하나가 실패하면 그 실패를 상단에 표시한다. 모델의 서술은 이미지에서 관찰되는 차이를 설명하는 보조 정보다. 코사인 점수 하나로 녹색 체크를 표시하지 않는다. 사용자가 이미지를 확대하고 원본 사양 문서를 열 수 있어야 한다. 점수에 대한 설명은 모델의 문장보다 **비교 대상과 사용된 이미지 버전**이 먼저다.

한 후보에 여러 출처가 있을 수 있다. 제품 카탈로그의 정형 값, 공급자 PDF, 내부 승인된 사양, 현장 사진이 서로 다르면 화면은 최신 값 하나로 나머지를 덮어쓰지 않는다. 확정값이 어느 시스템에서 관리되는지 표시하고 충돌 내역을 검토 항목으로 올린다. 시스템은 원문 링크와 각 문서의 개정 번호, 읽힌 페이지를 보여 준다. 시각 자료가 동일한 이미지의 다른 해상도인지 다른 제품 버전인지도 구별한다. 검색 모델은 유사한 것을 모아 줄 수 있지만 문서의 법적·기술적 효력을 결정할 수 없다.

### 승인 흐름에 남겨야 할 것

검토자는 추천 목록을 받아도 자동으로 승인하지 않는다. 요구 조건과 실제 사양의 비교표, 예외를 허용한 근거, 추가 시험의 필요성, 승인자와 날짜를 남긴다. 원문 예제의 감사 기록 아이디어는 이런 흐름에 적합하다. 단, 로그가 있다는 이유만으로 감사에 충분한 것은 아니다. 어떤 규칙 버전이 쓰였는지, 입력 필드의 출처가 무엇인지, 사람이 무엇을 확인했는지 보존해야 한다. 모델이 작성한 설명을 그대로 승인 기록으로 삼으면 모델의 추론 오류가 검토자의 결정처럼 보일 수 있다. 사람은 단순한 마지막 버튼이 아니라 검토 가능한 정보를 가진 책임 주체여야 한다.

자동화를 확대하고 싶다면 위험이 낮은 단계부터 시작한다. 문서 후보 찾기, 중복 이미지 묶기, 누락된 필드 표시, 상충된 숫자 강조는 검토자를 도울 수 있다. 대체품 추천과 승인, 안전 검증 면제는 훨씬 강한 검증을 요구한다. 업무를 단계별로 나누면 모델이 잘하는 탐색과 요약을 활용하면서도 결정 경계를 지킬 수 있다. 같은 원칙은 인사시스템에서도 통한다. 정책 문서를 찾고 신청서의 빈칸을 표시하는 자동화는 비교적 낮은 위험이다. 급여 지급이나 인사 평가 확정은 다른 권한과 검토가 필요하다.

### 오답을 발견한 뒤 모델을 바꿀지 데이터를 바꿀지

이미지 검색이 잘못된 부품을 상위에 올렸다면 사진의 촬영 조건, 인덱스에 들어간 이미지 종류, 라벨과 원본 연결, 임베딩 모델을 차례로 본다. 사양 판정이 틀렸다면 정형 필드와 공차 규칙, 단위 변환, 버전 선택을 본다. 설명이 틀렸다면 모델 입력의 근거와 프롬프트, 요약 규칙을 본다. 승인 사고라면 도구 권한과 서버 상태 전이를 본다. 실패 계층을 구별하지 않고 모델만 교체하면 원인을 유지한 채 이름만 바꾸는 셈이다. 원문의 예제가 확률적 검색과 코드 판정을 나눠 놓은 까닭을 운영 절차에도 반영한다.

## 설계 예제 D: 장애 초동 분석을 안전하게 좁혀 시작한다

### 첫 자동화 범위를 선택할 때

Circle K 사례를 보고 곧바로 모든 서비스의 장애를 에이전트가 조사하게 할 필요는 없다. 반복적인 경고가 많고 로그·서비스 문서·담당자가 비교적 잘 정리된 한 서비스에서 시작한다. 경고 하나가 들어오면 사람이 평소 확인하는 순서를 기록한다. 예컨대 최근 배포, 서비스 건강 상태, 주요 오류 로그, 의존 DB 상태, 고객 영향 범위다. 각 단계에서 읽기 전용 도구로 얻을 수 있는 자료만 연결한다. 자동 수정 도구는 초기에 주지 않아도 된다. 목적은 ‘장애를 스스로 고친다’가 아니라 **당직자가 맥락을 모으는 시간을 줄인다**다.

도구 호출은 최소 권한으로 설계한다. 코드 검색이 필요하다고 모든 저장소와 브랜치를 읽게 하지 않는다. 경고가 식별한 서비스의 저장소로 범위를 좁힌다. 여러 계정의 로그를 조회해야 한다면 계정별 읽기 권한과 요청 기록을 둔다. 검색 도구의 응답에는 시스템 전체 비밀 값이 섞일 수 있으므로 전처리에서 마스킹한다. 원문에서 OpenSearch 탐색을 별도 에이전트로 둔 이유 중 하나는 로그량이 크기 때문이다. 많은 로그를 모두 모델 컨텍스트에 넣는 대신 시간 범위, 요청 ID, 에러 패턴으로 줄여야 비용과 오류를 함께 줄인다.

### 요약 양식을 정할 때

첫 버전의 요약은 화려한 장문보다 당직자가 2분 안에 확인할 수 있는 필드가 중요하다. 사건 ID, 영향 서비스, 첫 발생 시각, 현재 고객 영향, 관측 사실 세 개, 가장 가능성 높은 원인 두 개, 원인별 근거와 반증, 추가 확인 한 개, 안전한 완화 선택지, 담당자와 링크를 제공한다. 모든 필드를 모델이 추정하게 하면 틀린 정보를 확정해 보일 위험이 있다. 사건 ID와 시각, 서비스 소유자는 시스템에서 주고, 모델은 근거에 기반한 가설과 설명을 작성한다. 정보가 없으면 빈칸 또는 ‘확인되지 않음’으로 남긴다.

메시지가 Slack에 도착했다는 것은 조치가 완료됐다는 뜻이 아니다. 당직자가 메시지를 열었는지, 근거 링크를 확인했는지, 어떤 조치를 택했는지, 결과가 어땠는지 연결해야 한다. 여러 명이 동시에 대응하는 경우 사건의 현재 담당자와 인수인계 상태도 중요하다. 자동 요약은 기존 사고 관리 체계에 붙어야 한다. 별도 채팅 메시지만 남기면 사건이 종료된 후 학습할 자료를 찾기 어렵다. 메시지를 운영 사건의 기록과 연결하고, 잘못된 가설이 있었다면 평가 사례로 되돌린다.

### 성과를 측정할 때

도입 전후의 시간만 비교하지 않는다. 대상 서비스의 장애 빈도와 난이도가 달라졌을 수 있다. 야간 당직자의 숙련도와 알림 품질도 변한다. 가능한 범위에서 유사한 사건 유형을 비교하고, 중대한 사고와 단순 재시작을 나눠 본다. 초동 분류 시간이 줄었더라도 복구 시간이 그대로라면 조사 이후의 승인·배포 과정이 병목일 수 있다. 반대로 복구 시간이 줄었지만 오탐 조치가 늘었다면 장기 안정성이 나빠질 수 있다. 고객 영향 시간, 잘못된 롤백, 중복 경고 수, 당직자의 실제 수동 조회 시간을 함께 본다.

Circle K의 내부 지표는 실무적 가능성을 보여 주지만 우리 조직의 예측값은 아니다. 원문은 고객 환경의 규모, AWS 중심의 자료 접근, 기존 로그·문서 구조, 팀의 반복 개선이라는 맥락을 함께 제시한다. 로그가 전혀 정리되지 않은 팀이 같은 에이전트를 붙인다고 15분이 나오지는 않는다. 자동 조사에 앞서 서비스 소유자, 배포 이력, 런북, 관측 데이터가 정확해야 한다. 좋은 에이전트는 없는 운영 질서를 만들어내기보다 존재하는 질서를 빠르게 연결한다.

### 잘못된 권고가 나왔을 때

근본 원인 가설이 틀렸다면 어떤 근거가 잘못됐는지 확인한다. 원시 로그가 실제 사건과 무관했는지, 최근 배포의 시간대가 잘못 해석됐는지, 지식베이스의 서비스 문서가 낡았는지, 모델이 약한 상관관계를 과도하게 확신했는지 구별한다. 수정은 해당 계층에서 한다. 사건 종료 뒤에는 모델 메시지를 사람의 최종 사후 분석과 비교한다. 같은 패턴의 오답이 반복되면 그 사건 유형을 자동 요약 범위에서 제외할 수 있다. 안전한 운영 자동화는 기능을 늘리는 경로뿐 아니라 범위를 줄이는 경로도 갖는다.

## 상세 운영 매트릭스: 제품 단계별 판단 기준

### 기획 단계 — 무엇을 자동화하지 않을 것인가

AI 기능을 기획할 때 ‘무엇을 할 수 있는가’ 목록만 만들면 성공 조건이 흐려진다. 사용자의 질문에 답하는 기능인지, 후보를 찾아 주는 기능인지, 업무를 확정하는 기능인지 분리한다. 오늘 공식 글의 네 사례는 모두 자동화 범위에 한계를 둔다. 웹 수집 예제는 허용된 공개 페이지의 배치 수집이며, 실시간 무제한 탐색이 아니다. 증류 예제는 특정 쇼핑 벤치마크의 제약 충족 행동을 다루며, 모든 에이전트 업무의 비용 최적화가 아니다. 부품 예제는 후보 탐색과 문서 초안이며 최종 대체 승인 아니다. Circle K 사례는 초동 분류이며 완전 자동 복구가 아니다. 이 제한을 제품 요구사항의 첫 줄에 적어야 한다.

자동화하지 않을 항목은 위험도와 검증 가능성으로 고른다. 잘못된 제안이 사용자의 추가 확인으로 쉽게 수정되면 자동화 범위를 넓힐 수 있다. 잘못된 확정이 금전·인사·안전·법적 결과를 만들면 권한과 사람 검토를 분리해야 한다. 모델이 매우 자신 있어도 승인 권한을 갖지 않게 설계할 수 있다. 반대로 모든 결과를 사람에게 넘기면 사용자가 기대한 효율이 사라진다. 읽기 전용 자료 탐색, 후보 정리, 근거 제시, 서식 채우기처럼 낮은 위험의 단계를 먼저 자동화하고, 결과 확정은 기존 트랜잭션 시스템의 검증을 통과시킨다. 제품 가치와 통제는 대립하지 않는다.

기획 문서에는 사용자에게 보이는 상태를 적는다. ‘답변’, ‘근거 불충분’, ‘동기화 대기’, ‘검토 필요’, ‘제출됨’, ‘승인됨’은 모두 다르다. AI가 만든 초안을 승인된 결과처럼 보이게 하면 기술적으로 권한이 분리돼 있어도 사용자 경험은 혼란스럽다. 특히 에이전트가 그럴듯한 자연어 문장을 생성하면 서버의 실제 상태보다 문장이 강하게 인식될 수 있다. 확정 상태는 서버에서 받은 구조화된 코드와 시각으로 표시하고 모델 문장은 해설로 둔다. 장애 분석에서도 ‘원인 후보’와 ‘확인된 원인’을 디자인과 용어로 구분한다.

### 데이터 단계 — 자료를 찾는 것과 사용할 권한은 다르다

크롤러와 벡터 검색은 자료가 어디 있는지 찾아 준다. 사용할 권한은 별개의 검사다. 공개 페이지를 수집하는 예제에서는 사이트의 허용 범위와 robots 지침을 확인한다. 내부 문서라면 소유자와 접근 권한을 확인한다. 직원별 데이터는 검색 후보가 됐다는 이유로 답변에 포함하면 안 된다. 사용자 세션과 대상 객체의 관계를 서버가 검사해야 한다. 인덱스에 메타데이터를 넣어 필터링하더라도 그 필터가 최신 권한과 항상 일치하는지 점검한다. 인덱스가 지연되는 동안 조직 이동이나 퇴사자의 권한이 바뀌었을 수 있다.

자료의 민감도도 나눈다. 공개 자료는 인용 URL을 화면에 보여 줄 수 있다. 사내 자료는 권한 있는 사용자에게만 링크를 제공한다. 직원 개인 정보는 원문을 통째로 모델에 전달하기보다 서버 함수가 필요한 값만 계산해 반환할 수 있다. 운영 로그에는 IP 주소나 고객 식별자가 섞일 수 있어 모델에 넣기 전에 최소화한다. 모든 정보를 하나의 프롬프트에 넣으면 모델이 일을 잘할 것 같지만, 실제로는 누출과 혼동의 범위를 넓힌다. 필요한 도구가 필요한 데이터만 받아야 한다. 원문의 역할별 도구 제한과 크롤 범위 제한은 같은 원칙의 서로 다른 표현이다.

데이터를 가공할 때 변환 기록을 남긴다. 원본 HTML, 추출 Markdown, 청크, 임베딩 인덱스, 검색 결과는 각각 다른 산출물이다. 문장이 답변에 들어가기까지 어떤 변환을 거쳤는지 알아야 누락과 왜곡을 찾는다. 원문이 출처 URL을 sidecar에 넣는 것은 출발점이다. 실무에서는 변환기 버전과 추출 실패 유형도 유용하다. 모든 단계의 전체 내용을 영구 보관할 필요는 없지만 중요한 문서의 원본 또는 원본 버전에 다시 접근할 수 있어야 한다. 변환 결과만 남기면 잘못된 표를 복구하기 어렵다.

### 모델 단계 — 도구 사용을 예측하는 모델과 도구를 실행하는 서버

증류한 학생 모델은 다음 도구 호출 문자열을 생성할 수 있다. 그러나 실제 도구 실행은 서버가 한다. 모델이 허용되지 않은 함수를 출력하면 서버는 거부한다. 함수 이름이 맞아도 인수의 타입과 범위가 틀리면 거부한다. 리소스 ID가 다른 사용자 소유라면 세션 권한을 검사한다. 동일 요청이 재시도되면 멱등성 키로 중복 실행을 막는다. 도구가 느리면 시간 초과와 재시도 한도를 적용한다. 이 규칙은 모델 크기에 관계없이 같다. 작은 모델의 품질을 높이는 프로젝트가 서버 권한 경계를 약화시키는 이유가 되어서는 안 된다.

모델 변경은 데이터 변경과 분리한다. 새 학생 모델의 성능을 보려면 동일한 도구와 자료에서 비교한다. 동시에 검색 랭킹을 바꾸면 응답이 좋아진 이유를 모른다. 모델의 출력 형식을 바꾸는 경우에는 파서와 검증기도 함께 버전 관리한다. 교사 궤적이 이전 형식의 도구 호출을 학습했다면 새 형식에서 실패할 수 있다. ‘모델이 도구 호출을 잘 못한다’는 결과가 학습 능력 부족이 아니라 스키마 변경일 수 있다. 비교를 위한 고정 환경과 실제 서비스의 빠른 변화 사이에는 주기적인 재평가가 필요하다.

모델의 자기평가를 성능 지표로 쓰지 않는다. ‘확신도 0.95’ 같은 출력은 실제 제약 충족을 보증하지 않는다. 쇼핑에서는 벤치마크 채점기가 상품 조건을 확인한다. 부품에서는 Python 규칙이 정형 값을 비교한다. 인사시스템에서는 정책 함수가 잔여량과 권한을 계산한다. 장애 대응에서는 사람이 사후 원인을 확인한다. 모델의 문장 품질과 작업 품질을 구분하는 검증 기준이 있어야 한다. 유창성은 사용자 경험의 요소지만 사실성의 대체물이 아니다.

### 평가 단계 — 평균을 세분화해 잘못된 승격을 막는다

평가 점수는 위험도가 다른 질문을 한 숫자로 합치면 왜곡된다. 낮은 위험의 일반 문의가 95% 맞고 높은 위험의 급여 문의가 60% 맞아도 전체 평균이 좋아 보일 수 있다. 사용자 수와 피해 규모를 고려해 필수 통과 범주를 정한다. 정상 요청, 경계 요청, 권한 오류, 최신성 오류, 도구 장애, 모호한 입력, 사람 이관을 따로 본다. 점수가 높아도 특정 필수 범주의 오류가 하나라도 있으면 기능을 제한할 수 있다. 이는 모델이 나쁘다는 평가가 아니라 제품의 위험 허용도를 명시하는 결정이다.

증류 모델의 품질은 `최종 답변`, `각 도구 호출`, `불필요한 호출 수`, `전체 완수`, `중단 또는 이관의 적절성`을 함께 본다. RAG는 `정답 문서 포함`, `낡은 문서 배제`, `인용 일치`, `답변의 제한 표현`을 본다. 멀티모달 검색은 `정답 후보 발견`, `이미지·문서 연결`, `정형 사양 충돌 탐지`, `승인 거부`를 본다. 장애 분석은 `첫 유효 가설까지 시간`, `근거 정확성`, `당직자의 확인`, `오탐 조치`를 본다. 이 지표들은 서로 다른 단위이므로 하나의 AI 점수로 더하지 않는다. 대신 제품 목표별로 어떤 지표가 선행 신호이고 어떤 지표가 최종 결과인지 연결한다.

평가 세트를 만들 때 정답을 미래에 그대로 유지할 수 있는지 확인한다. 쇼핑 상품의 가격과 재고는 변한다. 법과 회사 규정은 개정된다. 부품의 인증 상태는 바뀐다. 장애의 원인은 사후 조사에서 새로 밝혀진다. 정답을 고정 데이터 스냅샷에 묶거나, 정답 판정 함수를 버전 관리해야 한다. 그렇지 않으면 모델이 개선됐는데 평가가 떨어지거나, 모델이 퇴행했는데 평가가 올라갈 수 있다. 점수의 날짜와 데이터 버전 없이는 추세 해석이 어렵다. 오늘 뉴스의 게시 날짜와 분석 기준 시간을 분리한 이유도 같은 종류의 혼동을 피하기 위해서다.

### 배포 단계 — 성능 승격은 롤백 가능한 계약으로 만든다

새 모델 또는 새 검색 파이프라인을 배포할 때 ‘성공하면 계속 사용’이라는 막연한 기준 대신 승격 조건을 적는다. 핵심 질문의 정답률이 기준보다 낮아지지 않아야 하고, 권한·안전 범주의 실패가 없어야 하며, p95 지연과 성공당 비용이 예산 안에 있어야 한다. 자료 수집 파이프라인이라면 최신성 지연과 삭제 반영 시간이 허용 범위여야 한다. 사고 분석이라면 첫 요약 시간뿐 아니라 잘못된 근거 링크와 오탐 권고가 낮아야 한다. 일부 지표는 출시 전 평가할 수 있고 일부는 제한된 실트래픽에서만 볼 수 있다. 그래서 단계별 배포와 되돌리기 경로가 필요하다.

되돌리기는 모델만 이전 버전으로 바꾸는 것을 뜻하지 않는다. 새 청크 전략으로 만든 인덱스가 틀렸다면 이전 인덱스를 보존하고 검색 경로를 전환해야 한다. 새로운 도구 스키마가 문제라면 서버와 모델의 호환성을 고려해야 한다. 부품 판정 규칙이 잘못 바뀌었다면 영향을 받은 검토 기록을 식별해야 한다. 장애 요약의 형식이 잘못돼 당직자가 중요한 필드를 못 봤다면 메시지 양식을 복구해야 한다. 어느 층의 변경인지 구별할 수 있도록 버전을 따로 관리한다. 통합 배포의 편리함 때문에 원인 추적과 복귀가 어려워지지 않게 한다.

### 운영 단계 — 평시와 사고 중의 진실 기준을 다르게 둔다

평시에는 충분한 평가와 샘플 검토를 거쳐 모델과 자료를 개선할 수 있다. 실제 사고 중에는 사용 가능한 근거가 제한되고 시간이 중요하다. Circle K 사례처럼 초동 분석은 ‘현재까지의 관측’을 빨리 정리하는 일이다. 완전한 원인 분석은 사고가 끝난 뒤 더 많은 로그와 전문가 검토로 이뤄질 수 있다. 당직 메시지는 잠정적이라는 표시를 유지하고, 새 증거가 나오면 갱신돼야 한다. 첫 요약이 사후 보고서의 최종 진실로 굳어지면 잘못된 원인이 조직의 기억이 된다.

RAG에서도 평시와 긴급 상황이 다르다. 일반 규정 문의에는 인덱스된 문서가 충분할 수 있다. 오늘 아침 공지된 긴급 정책 변경은 아직 수집되지 않았을 수 있다. 이런 경우 답변의 최신성 요구를 감지해 공식 원문을 직접 확인하게 하거나 담당자에게 넘겨야 한다. 모든 질문에 동일한 검색 경로를 쓰는 편리함보다 질문의 시간 민감도를 판단하는 것이 중요하다. 사용자가 즉시 업무를 확정하려 한다면 조회 시점의 원장과 규정 버전을 서버에서 다시 검사한다. 검색 인덱스는 안내에 유용하지만 거래의 최종 기준은 아닐 수 있다.

## 숫자를 실제 제품 지표로 번역하는 연습

### 예제 1: 검색 인덱스에 1만 문서가 있다

문서 수가 많다고 답변 품질이 좋은 것은 아니다. 같은 규정의 버전이 다섯 개 들어 있으면 문서 수는 늘고 검색 충돌도 늘 수 있다. 메뉴와 광고를 수집하면 청크 수는 늘어도 관련성은 떨어진다. 문서 수 대신 고유한 유효 원천의 비율, 최근 갱신 시점, 폐기 반영률, 대표 질문의 정답 문서 포함률을 본다. 검색된 문서가 사용자에게 인용 가능한지도 확인한다. 원문 URL이 비공개 내부 저장소로만 이어지면 답변을 검증할 수 있는 사용자가 제한된다. 인덱스 규모는 비용 예측에는 유용하지만 사용자 가치의 직접 지표가 아니다.

문서 수가 증가할 때 검색의 분모도 바뀐다. 초기 100개 문서에서 상위 5개에 정답이 들어간 비율과 1만 개 문서에서의 같은 비율은 난이도가 다르다. 수집 범위를 넓혔다면 기존 질문에서 관련 없는 문서가 새로 상위에 올라오는지 확인한다. 확장을 ‘더 많은 지식’이라고만 보면 퇴행을 놓친다. 문서 버전, 조직 범위, 언어, 유형별로 검색 결과를 나눠 본다. 같은 질문을 새 인덱스와 이전 인덱스에 실행해 어떤 문서가 밀렸는지 비교하면 변화의 원인을 찾기 쉽다.

### 예제 2: 학생 모델이 기본 모델보다 24포인트 높다

원문의 벤치마크 수치는 좋은 신호지만 제품에서는 절대 성공률과 실패 유형이 중요하다. 기본 모델이 아주 낮은 점수였다면 24포인트 향상 후에도 서비스 기준에 못 미칠 수 있다. 평균 향상은 특정 의도에서의 하락을 감출 수 있다. 또한 학습용 교사와 평가 문제의 종류가 비슷하면 새로운 도메인에 대한 일반화는 별도 검사해야 한다. 성능 결과를 소개할 때 모델 크기, 평가 문제 수, 성공 정의, 단일 실행 여부를 함께 표시한다. 숫자를 팀의 비용 절감률이나 매출 증가율로 바로 연결하지 않는다.

제품팀이 실제로 궁금한 것은 사용자가 조건을 모두 만족한 결과를 얻고 후속 행동을 완료했는가다. 쇼핑이라면 추천을 클릭하고 구매할 수 있었는지, HR이라면 신청이 적법하게 접수됐는지, 운영이라면 당직자가 유효한 근거를 보고 조치를 시작했는지다. 벤치마크 성공률과 사용자 과제 완료율 사이에는 UI, 데이터 신선도, 권한, 재고, 네트워크, 조직 절차가 놓여 있다. 모델 실험의 인과 효과를 보려면 그 중 무엇을 고정했고 무엇이 바뀌었는지 적어야 한다. 한 점수로 전체 제품 성공을 선언하지 않는다.

### 예제 3: 사진 유사도 0.95가 나온다

0.95가 어느 임베딩 모델과 전처리, 어떤 사진 쌍에서 나왔는지 모르면 해석할 수 없다. 사진이 같은 제품의 다른 각도라면 높은 점수가 자연스럽다. 서로 다른 부품이 동일한 외형의 케이스를 쓰더라도 점수가 높을 수 있다. 장착 위치가 몇 밀리미터 다른 것은 사진에 드러나지 않을 수 있다. 점수는 후보 탐색 우선순위의 신호다. 실제 적합성은 정형 사양, 원문 도면, 인증 상태, 사람 검토를 거친다. 유사도 임계값을 바꾸기 전에 오탐과 누락이 어떤 업무 비용을 만드는지 평가한다.

임계값을 너무 높이면 안전하게 사용할 수 있는 후보를 놓칠 수 있다. 너무 낮추면 검토자가 수많은 엉뚱한 후보를 보게 된다. 이 균형은 사용자가 ‘비슷한 사진’을 원하는지 ‘교체 가능한 부품’을 원하는지에 따라 달라진다. 전자는 시각 검색의 문제이고 후자는 엔지니어링 판단의 문제다. 같은 검색 UI에서 두 목적을 혼합하면 높은 점수가 안전성을 뜻하는 것처럼 보인다. 용어를 ‘시각적 유사 후보’로 정확히 표시하고, 정형 판정과 승인 상태를 다른 칸에 둔다.

### 예제 4: 장애 분류가 15분 아래로 내려갔다

초동 분류 지연이 줄면 당직자가 조치를 시작하는 시간이 앞당겨질 수 있다. 그러나 실제 고객 영향 시간이 줄었는지는 별도로 측정한다. 장애의 종류가 쉬워졌거나 경고 체계가 바뀌었을 수 있다. 자동 요약을 받았어도 당직자가 근거를 다시 확인하느라 비슷한 시간을 썼을 수도 있다. 반대로 요약이 정확해 재조사를 줄였다면 시간이 절약된다. 내부 지표와 함께 당직자의 실제 업무 시간, 원인 가설의 적중률, 후속 수정까지의 시간, 잘못된 조치 발생률을 본다. Circle K의 수치는 실무 사례의 결과이지 범용 서비스 수준 계약이 아니다.

운영팀이 숫자만 목표로 삼으면 요약을 너무 일찍 보내 지연이 줄어든 것처럼 보일 수 있다. 중요한 것은 **유효한 초동 정보**가 언제 도착했는가다. 근거가 빠진 즉시 메시지는 당직자에게 다시 조사할 일을 남긴다. 반대로 완벽한 분석을 기다리느라 30분 늦게 보내는 것도 좋지 않다. 사건의 심각도에 따라 첫 짧은 사실 요약과 후속 가설 업데이트를 나누는 방식이 유용할 수 있다. 그때 메시지 버전을 명시해 이전 가설이 정정됐다는 사실을 보여 줘야 한다.

## 현장 질문 12개: 발표를 도입 결정으로 바꾸는 문답

### Q1. 관리형 Web Crawler와 Crawl4AI 중 어느 쪽부터 시작해야 하나?

먼저 수집하려는 페이지의 유형과 필요한 메타데이터를 확인한다. AWS 원문은 관리형 Web Crawler가 범위와 속도, JavaScript 로딩과 정기 동기화를 처리할 수 있다면 그 경로를 시작점으로 제시한다. 별도 크롤러를 운영하면 브라우저 환경, 스케줄, 재시도, URL 범위, 출력 검증을 모두 팀이 소유해야 한다. 단순 공개 문서 검색이면 그 비용을 지불할 이유가 적을 수 있다. 반면 본문만 선택적으로 추출해야 하거나 문서마다 커스텀 분류·출처·수집 시각을 붙여야 한다면 Crawl4AI를 준비 계층으로 쓸 수 있다. 중요한 것은 어느 도구가 더 최신인가가 아니라 **우리 원천의 실패 모드를 누가 책임질 수 있는가**다.

판단 실험은 작게 시작한다. 서로 다른 구조의 대표 URL을 고르고 두 경로에서 나온 검색 결과를 비교한다. Markdown의 표·각주 보존, 검색 정답 페이지 포함률, 동기화 지연, 삭제 반영, 운영 비용을 기록한다. 커스텀 경로가 품질을 크게 올리지 않는다면 관리형이 운영상 유리할 수 있다. 반대로 관리형이 꼭 필요한 특정 요소를 놓친다면 그 유형에만 커스텀 추출을 적용하는 혼합 구성이 가능하다. 한 사이트 안에서도 문서 유형별 경로를 다르게 할 수 있다. 도구의 이름보다 질문별 답변 품질과 유지보수 부담을 기준으로 결정한다.

### Q2. 수집된 페이지를 삭제했는데 왜 오래된 답이 계속 나오는가?

파일 저장소의 삭제와 검색 인덱스의 삭제가 같은 순간에 끝나는 것은 아니다. AWS 예제의 커스텀 업로드는 가산적이라 페이지가 다음 크롤에서 빠져도 S3의 옛 문서가 남는다. 문서와 sidecar를 함께 삭제하고 새로운 ingestion job을 실행해야 한다. 삭제 보호 설정이 있으면 대량 삭제가 건너뛰어질 수 있다. 또 같은 내용이 다른 URL이나 중복 문서에 남아 있을 수 있다. 그러므로 원본 URL 하나를 지웠다는 사실만으로 사용자의 검색에서 사라졌다고 결론 내리면 안 된다. 실제 질문으로 검색 결과를 확인해야 한다.

조사 순서는 유용하다. 먼저 S3에 문서와 sidecar가 남았는지 본다. 다음으로 수집 작업의 상태와 삭제 보호 경고를 본다. 이어 검색 API의 상위 결과에 같은 문서의 다른 버전이나 복사본이 있는지 확인한다. 마지막으로 생성 모델이 검색 결과 밖의 오래된 문장을 어디에서 가져왔는지 본다. 캐시가 있다면 캐시 무효화도 점검한다. 문제를 해결한 뒤에는 삭제 요청부터 검색에서 사라질 때까지의 시간을 기록한다. 정책·가격·권한 문서처럼 유효기간이 중요한 자료에는 이 지연이 제품 수준의 지표다.

### Q3. 수집 시각이 최신이면 문서도 최신이라고 할 수 있나?

아니다. 오늘 가져온 페이지가 몇 년 전 규정을 그대로 담을 수 있다. 수집 시각은 **우리 시스템이 원문을 읽은 때**이고, 시행일은 **업무에 적용되는 때**다. 게시일은 저자가 공개한 때이며, 검색 인덱스 반영 시각은 또 다르다. 다섯 시각을 하나의 ‘최신’으로 묶지 않는다. 원문에서 시행일을 제공한다면 구조화해 기록하고, 제공하지 않는다면 추정하지 않는다. 사용자에게 답할 때 현재 적용 여부가 불확실하면 그 사실을 밝히거나 원문 확인 경로로 안내한다.

과거 사건을 분석할 때는 더 복잡하다. 현재 최신 규정이 아니라 사건 당시 적용된 규정을 찾아야 한다. 버전 이력을 완전히 삭제하면 과거 판단의 재현성이 사라진다. 반대로 과거 문서를 현재 답변 인덱스에 그대로 남기면 잘못 인용될 수 있다. 현재용 검색과 감사용 역사 검색의 목적을 분리한다. 오늘의 AWS 수집 글은 삭제 절차를 설명하지만 법적 보존 정책까지 자동 결정하지는 않는다. 문서 소유 부서와 제품팀이 자료의 수명을 정해야 한다.

### Q4. 성공 궤적만 학습시키면 학생 모델의 실패가 줄지 않나?

잘못된 행동을 모범 답안으로 주지 않는 장점은 있다. 하지만 성공을 판정하는 채점기가 놓치는 제약이 있다면 잘못된 궤적도 통과한다. 교사가 자주 실패하는 어려운 문제는 학습에서 빠져 학생이 그 상황을 거의 보지 못할 수 있다. 성공 궤적을 모으는 과정에서 문제별 성공률과 탈락 이유를 기록해야 한다. 도구 장애, 정보 부족, 모호한 사용자 조건, 권한 거절은 단순한 실패가 아니라 별도 처리 방식을 배워야 할 상황이다. ‘항상 정답을 만들어 낸 궤적’만 남기면 모르는 것을 인정하는 행동을 배우기 어렵다.

훈련과 평가의 역할도 분리한다. 학생에게 가르칠 성공 궤적은 엄격하게 선별하되, 교사가 실패한 문제와 안전상 중요한 경계는 보류 평가 세트에 남긴다. 학생이 교사의 잘못을 그대로 따라 하는지, 어려운 상황에서 중단할 줄 아는지 본다. 원문의 ShoppingBench는 모든 상품 조건을 만족했는지 검사하는 채점기가 있어 선별을 자동화할 수 있었다. 일반 업무에서는 그만큼 명확한 채점기를 만들기 어려울 수 있다. 그래서 사람의 검토와 서버의 결정적 업무 규칙을 함께 써야 한다.

### Q5. 도구 호출을 더 잘하는 학생 모델이면 서버 권한 검사를 줄여도 되나?

아니다. 모델의 행동 품질은 통계적으로 평가되고, 서버 권한은 각 요청에서 확정적으로 검사해야 한다. 학생 모델이 대부분 올바른 도구를 선택해도 공격적 입력이나 데이터 오류에서 잘못된 대상 ID를 낼 수 있다. 서버는 사용자 세션, 객체 소유권, 도구 인수, 현재 상태, 중복 요청 여부를 확인해야 한다. 모델이 호출하지 않아야 할 도구를 출력하는 경우에는 실행하지 않고 오류 상태를 반환한다. 모델이 ‘승인됨’이라고 말해도 서버가 승인 트랜잭션을 완료하지 않았다면 실제 상태는 승인되지 않은 것이다.

증류와 권한 검사는 서로 다른 문제를 푼다. 증류는 더 작은 모델로 유용한 행동을 재현하려는 시도다. 권한 검사는 부적절한 행동이 시스템 효과를 내지 못하게 한다. 작은 모델이 효과적인 에이전트가 되면 오히려 더 많은 업무 경로를 자동으로 시도할 수 있으므로 서버 경계가 중요해진다. 도구별 허용 목록과 멱등성, 감사 로그를 고정한 뒤 모델을 비교해야 공정한 성능 측정도 가능하다. 모델마다 다른 권한을 주고 결과를 비교하면 모델의 능력과 시스템의 허용 범위를 혼동한다.

### Q6. 작은 모델의 품질이 교사와 비슷하면 비용 절감은 확정인가?

아니다. 품질과 비용은 다른 측정이다. API 교사는 사용량에 따라 과금되고, 직접 호스팅한 학생은 엔드포인트의 가동 시간과 인스턴스 크기에 따라 비용이 생긴다. 요청이 적은 서비스에서는 학생 엔드포인트의 대기 비용이 더 클 수 있다. 동시 요청이 많으면 학생이 유리해질 수 있지만 지연과 GPU 용량을 맞추기 위해 규모를 늘려야 할 수도 있다. 학습 데이터 생성과 재학습, 모델 평가, 도구와 검색 인프라의 비용도 포함한다. 원문은 단일 작업당 비용을 공개하지 않았다. 그 부재를 다른 자료의 일반 할인율로 채우면 잘못된 투자 판단을 한다.

비교에는 같은 문제 집합과 같은 성공 기준을 사용한다. 월간 총비용을 처리 건수가 아니라 성공 건수로 나누고, 사람이 다시 처리한 비용을 별도로 본다. 학생이 싼 호출을 여러 번 해 결국 더 비싼 도구 루프를 만든다면 단일 호출 단가는 의미가 줄어든다. 반대로 학생이 응답을 조금 느리게 하더라도 정확한 검색과 종료 판단으로 전체 작업 시간을 줄일 수 있다. 비용, 지연, 품질의 균형을 제품별로 평가한다. ‘작은 모델은 무조건 싸다’는 기술 명제가 아니라 워크로드에 따라 확인할 가설이다.

### Q7. 이미지 검색에서 관련 사진을 찾았다면 사양서 확인을 생략할 수 있나?

생략할 수 없다. 외형 유사도는 모델이 학습한 시각 특징의 가까움이다. 같은 케이스에 다른 내부 부품이 들어갈 수도 있고, 사진 각도가 달라 실제로 같은 부품이 멀게 보일 수도 있다. 엔지니어링 적합성에는 전압, 토크, 질량, 장착 규격, 인터페이스, 인증, 수명 같은 조건이 있다. 원문 예제는 이미지 검색과 설명을 보조 근거로 사용하고, 정형 사양의 통과·플래그는 Python 규칙으로 계산한다. 승인 결정은 엔지니어가 한다. 이미지 유사도와 최종 적합성을 같은 색의 배지로 표시하지 않는 것이 좋다.

이미지 검색의 가치가 낮다는 뜻은 아니다. 문서 제목을 모를 때 차트 이미지로 관련 사양서를 찾거나, 누락된 사진을 통해 후보를 좁히는 데 강점이 있다. 시각 후보를 찾은 뒤 원문 도면의 세부 값과 현재 승인 상태를 확인하면 검색의 이점과 안전한 판정을 함께 얻는다. 사진의 출처와 촬영 시각이 불분명하면 검색 결과에 그 불확실성을 표시한다. 모델이 분석한 외형 차이를 수치 검증과 별도로 제시하면 엔지니어가 놓친 문제를 빨리 발견할 수도 있다. 역할을 정확히 정하는 것이 멀티모달 기능의 가치다.

### Q8. 결정적 규칙으로 판정했다면 사람 검토는 형식적인가?

결정적 규칙은 입력과 규칙이 맞는 범위에서 같은 결과를 낸다. 입력 값이 틀렸거나 필수 조건이 빠졌다면 일관되게 잘못된 결과를 낸다. 예를 들어 전압은 맞지만 장착 환경의 진동 요구가 규칙에 없으면 ‘통과’는 전체 적합성의 증명이 아니다. 사람 검토는 누락된 조건, 원문과 정형 데이터의 불일치, 현장 맥락을 확인할 수 있다. 다만 사람 검토를 막연한 마지막 버튼으로 만들면 실제로 아무도 근거를 읽지 않는다. 검토해야 할 위험, 충돌, 예외, 사용된 규칙 버전을 화면에 명시해야 한다.

반대로 모든 사소한 후보 검색을 사람에게 넘길 필요도 없다. 기계가 잘할 수 있는 범위는 넓다. 후보를 모으고, 비교표를 만들고, 수치 차이를 계산하고, 필수 정보가 없음을 표시하고, 감사 기록을 준비할 수 있다. 인간은 모델이 만든 긴 글을 처음부터 읽는 대신 미해결 충돌과 승인 조건에 집중한다. AWS의 엔지니어링 예제는 이런 분업을 보여 준다. 최종 승인이라는 단어를 프롬프트에만 쓰는 것이 아니라 도구 권한, 기록, 화면 상태, 승인자 역할에 반영해야 한다.

### Q9. 사고 분석에서 모델이 근본 원인을 제시하면 바로 복구를 자동화해야 하나?

초동 분류와 실제 복구는 위험도가 다르다. Circle K 글은 자동 조사와 요약을 보여 주지만 모든 권고를 자동 실행하는 아키텍처로 소개하지 않는다. 모델의 원인 가설은 로그와 코드의 시간 상관관계를 바탕으로 할 수 있고, 동일 증상이 다른 원인에서도 나타날 수 있다. 복구 조치가 트래픽 차단이나 데이터 변경, 롤백을 수반한다면 더 강한 확인이 필요하다. 처음에는 읽기 전용 조사와 당직자의 확인을 목표로 삼고, 반복적으로 검증된 낮은 위험의 조치에만 별도의 자동화 정책을 고려한다.

자동 복구를 검토할 때는 조치가 되돌릴 수 있는지, 잘못 실행했을 때 고객 피해가 무엇인지, 시스템이 현재 상태를 확실히 아는지, 한 번만 실행됨을 보장하는지 묻는다. 모델의 문장을 실행 명령으로 바로 연결하지 않는다. 운영자 승인, 정책 엔진, 변경 요청, 사후 검증이 필요할 수 있다. 장애 중에는 시간이 촉박하므로 승인 절차도 실용적이어야 한다. 그러나 속도 지표만 보고 위험한 자동화를 밀어붙이면 한 번의 오판이 기존 수작업보다 큰 사고를 만들 수 있다.

### Q10. 장애 요약이 빠른데 당직자가 계속 원시 로그를 다시 읽는 이유는?

요약의 근거가 부족하거나 링크가 열리지 않거나, 모델의 확신 표현이 실제 증거보다 강하면 당직자는 다시 조사한다. 특정 로그 라인과 시간 범위, 서비스 상태, 관련 코드 변경, 런북을 볼 수 있어야 요약을 신뢰할 수 있다. 너무 긴 메시지도 문제다. 중요한 사실과 가설이 여러 문단에 흩어져 있으면 다시 정리하는 시간이 든다. 구조화된 양식과 읽기 가능한 근거 링크를 제공하고, 새 증거가 들어오면 무엇이 달라졌는지 표시한다. 당직자에게는 ‘모델이 몇 초 만에 답했다’보다 **다음 안전한 행동을 결정할 만큼 충분한 맥락**이 중요하다.

운영팀은 요약의 유용성을 직접 물어야 한다. 당직자가 어떤 필드를 실제로 사용했고 어떤 필드는 틀렸거나 불필요했는지 확인한다. 요약을 받은 뒤 첫 유효 조치까지의 시간, 잘못된 원인 때문에 돌아간 조사 단계, 사건 종료 후 정정된 가설의 비율을 기록한다. 이런 피드백은 모델 프롬프트뿐 아니라 데이터 소스와 도구의 범위를 바꿀 근거가 된다. 예를 들어 담당자 정보가 자주 틀리면 모델 언어가 아니라 서비스 소유자 등록부를 고쳐야 한다. 사용자 행동을 보면 문제 계층이 드러난다.

### Q11. 네 공식 글 중 한 가지부터 적용한다면 무엇을 우선해야 하나?

현재 제품의 병목에서 시작한다. RAG 답변이 틀리고 근거가 낡았다면 웹 수집과 삭제·인용 검증을 먼저 개선한다. 에이전트 호출 비용이 큰데 작업이 안정적으로 정의돼 있다면 증류 실험이 가치 있다. 사진이나 PDF의 그림을 찾는 일이 많은데 사람의 판정 근거가 부족하다면 멀티모달 검색과 결정적 비교를 시도한다. 당직자가 반복적으로 로그와 코드를 모으느라 시간을 쓴다면 장애 초동 맥락 수집을 자동화한다. 네 기술은 도입 순서가 정해진 패키지가 아니다. 하나를 잘 운영하기 위한 자료와 지표가 없으면 나머지를 한꺼번에 붙여도 신뢰는 높아지지 않는다.

우선순위를 정할 때 구현 난이도만 보지 않는다. 예상 사용자 가치, 위험, 필요한 원천 품질, 검증 가능한 정답, 운영 인력을 함께 본다. 예를 들어 규정 검색의 문서 버전이 엉망인데 작은 모델로 비용만 줄이는 프로젝트는 성공 가능성이 낮다. 반대로 자료는 잘 정리돼 있지만 반복적인 문의량이 커서 모델 비용이 병목이라면 증류가 적합할 수 있다. 발표 글을 기술 목록으로 읽지 않고 **우리 제품의 가장 비싼 실패를 고치는 후보**로 읽으면 과도한 도입을 피할 수 있다.

### Q12. 공식 블로그 사례를 제품 기획서에 어떻게 인용해야 하나?

발표의 종류와 증거 수준을 표시한다. Circle K 수치는 고객 내부 지표에 기초한 운영 사례다. 증류 결과는 특정 벤치마크와 단일 실행의 실험 결과다. Crawl4AI 글은 참조 아키텍처와 구현 안내다. 멀티모달 부품 글은 가상 데이터의 샘플 구현이다. 이 네 가지를 모두 ‘AWS가 성능을 보증했다’로 묶으면 안 된다. 기획서에는 원문 링크, 발행 시각, 적용 환경, 샘플 규모, 원문이 명시한 한계를 함께 적는다. 그 다음 우리 환경에서 검증할 가설을 별도 문장으로 적는다.

예를 들어 ‘Circle K는 초동 분류를 15분 미만으로 줄였다. 우리 팀은 반복 경고 세 종류에서 현재 40분인 맥락 수집 시간을 20분 아래로 낮출 수 있는지 시험한다’처럼 적는다. 후반 문장은 **우리의 목표**이지 사례의 보증이 아니다. ‘ShoppingBench에서 학생 모델의 점수가 올랐다. 우리 고객 문의 데이터에서도 오류 없이 비용이 줄지 시험한다’도 마찬가지다. 출처가 검증된 사실과 아직 검증되지 않은 제품 가설을 한 문장에서 섞지 않으면 의사결정자가 투자의 근거를 정확히 이해할 수 있다.

## 바로 사용할 수 있는 검토 양식

### 웹 문서 수집 변경 기록

수집 경로를 바꿀 때는 `변경 목적`, `대상 URL 패턴`, `제외 URL 패턴`, `사용 권한 근거`, `추출 도구 버전`, `원본 문서 표본`, `추출 Markdown 표본`, `검색 평가 결과`, `삭제 테스트 결과`, `복귀 방법`을 기록한다. 변경 목적이 ‘더 많은 페이지 수집’이라면 어떤 질문이 기존에 답을 못 했는지 적는다. URL 패턴은 요청 주소뿐 아니라 리디렉션 후 주소까지 검사한다. 권한 근거는 공개 페이지 여부와 사이트별 크롤 제한을 포함한다. Markdown 표본에는 제목과 표, 각주가 보존됐는지 표시한다. 검색 평가에는 관련 없는 문서가 상위에 끼어드는지 포함한다. 삭제 테스트를 빠뜨리면 새 자료가 추가되는 데모는 성공해도 오래된 규정을 제거하지 못하는 제품이 된다.

변경 기록에 결과 숫자만 적지 말고 실패 사례 링크를 남긴다. 동일한 HTML 구조의 페이지 열 개가 성공했다는 사실보다 구조가 다른 한 페이지의 실패가 더 많은 정보를 준다. `0건 실패`라는 문구는 어떤 범위에서 검사했는지 없으면 의미가 없다. 예를 들어 100개 URL 가운데 20개만 자바스크립트 기반이라면 전체 성공률 90%가 실제로는 자바스크립트 페이지의 절반 실패를 숨길 수 있다. 원천 유형별로 분모를 나눠 보고하고, 특히 업무에 중요한 문서는 별도 필수 통과 목록으로 둔다. 샘플이 아닌 실제 페이지의 변경을 감지할 방법도 적는다.

### 증류 실험 결과 기록

증류 실험 기록에는 `교사 모델과 버전`, `학생 기본 모델`, `훈련 문제 수`, `성공 궤적 채택률`, `문제 단위 분할 방식`, `도구 스키마 버전`, `학습 데이터 길이 제한`, `잘린 궤적 비율`, `사전 평가`, `전체 루프 평가`, `의도별 실패`, `배포 비용 예상`, `복귀 기준`을 넣는다. 모델 이름만 바꾸고 나머지를 빼면 다른 팀이 실험을 재현하기 어렵다. 특히 한 문제의 여러 궤적을 학습과 평가에 나눠 넣지 않았는지 확인한다. 원문에서 문제 단위 분할을 강조한 이유다. 채점기의 성공 정의도 기록해야 나중에 정책 또는 카탈로그가 변했을 때 같은 점수를 비교할 수 있다.

실험 결론은 ‘좋다/나쁘다’ 두 칸이 아니라 **어떤 업무 범위에서 쓸 수 있는가**를 답해야 한다. 학생 모델이 간단한 상품 검색에서 교사와 비슷하지만 복잡한 쿠폰 조건에서 자주 실패한다면, 간단한 검색에만 배포하는 선택이 가능하다. HR 문의에서도 규정 검색 설명은 처리하되 실제 신청 확정은 기존 서버 폼으로 돌릴 수 있다. 모델 전환을 전체 제품에 일괄 적용할 필요가 없다. 부분 배포가 가능한 구조를 갖추면 실험 결과의 좋은 부분을 활용하고 위험한 부분을 제한할 수 있다. 실패 범주가 명확해야 이런 결정을 내릴 수 있다.

### 멀티모달 후보 검토 기록

후보 검토 기록에는 `사용자 질문 또는 업로드 이미지`, `검색된 문서·사진의 원본`, `정형 사양 입력`, `적용된 공차 규칙`, `규칙 버전`, `통과·플래그 이유`, `모순된 출처`, `추가 검토자`, `최종 결정`을 분리한다. 모델이 작성한 자연어 요약은 별도 첨부로 둔다. 최종 결정에는 승인자가 확인한 조건과 승인하지 않은 조건을 표시한다. 이미지는 후보 발견에 쓰였는지 실제 치수 판독에 쓰였는지도 적는다. 같은 ‘AI 이미지 분석’이라는 표현 아래 서로 다른 증거 수준이 숨어 있기 때문이다. 모델이 특정 값을 사진에서 읽었다면 원문 도면이나 공급자 자료로 검증하기 전에는 임시 값으로 둔다.

검토 기록이 길어져 엔지니어가 읽지 않는다면 핵심 충돌을 맨 위에 둔다. 필수 사양의 불일치, 원천 버전 충돌, 불명확한 인증 상태, 승인되지 않은 대체 제안은 먼저 보여 준다. 나머지 검색 후보는 접어 둘 수 있다. 모든 데이터를 한 화면에 쏟는 것보다 **결정에 영향을 주는 근거를 우선순위화**하는 것이 중요하다. 모델은 요약을 도울 수 있지만 위험의 우선순위는 업무 규칙과 전문가의 기준을 따라야 한다. 검토자가 한 번의 클릭으로 근거 원본에 도달하지 못하면 자동화가 만든 편의가 오히려 확인 부담을 늘린다.

### 장애 조사 기록

사고 기록에는 `경고 발생 시각`, `조사 시작 시각`, `첫 요약 전달 시각`, `확인된 사실`, `원인 가설`, `가설별 근거와 반증`, `영향 서비스와 고객`, `조치 담당자`, `실제 조치와 결과`, `사후 확정 원인`을 분리한다. 첫 요약과 사후 확정 원인을 같은 필드에 덮어쓰지 않는다. 초동 가설이 틀렸어도 그때 어떤 근거가 있었는지 알 수 있어야 평가에 쓸 수 있다. 사용자 영향의 시작과 끝을 따로 기록해야 초동 분류 개선이 실제 복구에도 이어졌는지 확인할 수 있다. 5분 만에 요약을 보냈지만 고객 영향이 계속됐다면 개선의 다음 단계는 조사 자동화가 아니라 승인·수정 경로일 수 있다.

사건 종료 후에는 AI가 찾은 근거 중 실제로 유용했던 것과 오해를 부른 것을 표시한다. 로그가 틀린 서비스에서 왔다면 범위 지정 문제다. 코드는 맞았지만 배포 버전이 달랐다면 버전 연결 문제다. 서비스 문서의 담당자가 틀렸다면 지식베이스 관리 문제다. 모델이 정황을 확정 원인처럼 표현했다면 요약 문제다. 이 분류를 하지 않으면 사고 하나를 모델 프롬프트에 수십 줄 추가하는 방식으로 대응하기 쉽다. 프롬프트가 길어져도 데이터 원천이 틀린 문제는 남는다. 운영 개선은 정확한 실패 계층을 겨냥해야 한다.

## 의사결정용 비교표: 네 사례의 범위와 한계

| 항목 | 공식 글에서 확인한 범위 | 생산 환경에서 추가할 검증 |
| --- | --- | --- |
| 웹 수집 | 공개 웹의 제한된 배치 수집과 Markdown·sidecar 준비 | 허용 URL, 문서 시행일, 삭제 반영, 권한, 인용 품질 |
| SeqKD | ShoppingBench 성공 궤적을 통한 작은 모델의 도구 행동 학습 | 업무별 보류 평가, 실패 사례, 성공당 비용, 개인정보 처리 |
| 멀티모달 엔지니어링 | 가상 부품 자료에서 문서·사진 검색과 결정적 사양 비교 | 실제 원천 데이터 품질, 인증 상태, 사람 승인 기록 |
| Circle K | 고객 내부 지표에 기반한 초동 분류 시간 개선 | 우리 사건 유형, 오탐, 실제 고객 영향 시간, 복구 절차 |

이 표를 제품 제안서에 넣을 때 오른쪽 열을 비워 둔 채 출시 일정을 확정하지 않는다. 예컨대 공개 웹 수집은 기술적으로 쉬워 보여도 업무에 맞는 시행일 관리가 어려울 수 있다. 증류는 모델 학습 파이프라인보다 성공을 판정할 평가 세트가 더 큰 과제일 수 있다. 멀티모달 검색은 임베딩 API 연결보다 정형 사양 원장의 품질이 중요할 수 있다. 사고 분석은 에이전트 프레임워크보다 서비스 소유자와 로그 체계의 정리가 우선일 수 있다. 원문이 보여 준 가능성을 우리 환경에서 성립시키는 조건을 먼저 확인해야 한다.

### 의사결정이 어려울 때의 중단 기준

새 기능의 효과가 불확실하면 제한된 실험으로 범위를 좁힌다. 관리형 크롤러와 커스텀 크롤러의 답변 품질 차이가 작다면 운영 부담이 낮은 경로를 택할 수 있다. 학생 모델의 성공률은 높지만 위험 사례에서 거절을 못 한다면 배포 범위를 줄이거나 보류한다. 이미지 유사 후보는 잘 찾지만 정형 데이터가 자주 틀리면 자동 판정을 확대하지 않는다. 사고 요약은 빠르지만 당직자가 신뢰하지 않으면 근거 품질과 메시지 구조를 고친다. ‘파일럿을 계속한다’는 말도 조건이 없다면 종료가 없는 사업이 된다. 다음 실험의 질문, 기간, 필수 통과 기준을 정한다.

중단은 실패의 낙인이 아니다. 도구에 맞지 않는 문제를 일찍 발견하면 비용을 아낀다. 실시간 웹 확인이 필요한 질문을 하루 한 번의 배치 인덱스로 해결하려 한다면 기술 경로를 바꿔야 한다. 학생 모델의 용량이 업무의 긴 꼬리 문제를 감당하지 못하면 더 큰 학생이나 교사 유지가 나을 수 있다. 사진으로 식별하기 어려운 부품은 정형 검색과 전문가 문서가 우선이다. 원시 로그가 부족한 서비스는 에이전트보다 관측 체계를 먼저 개선해야 한다. 기술 발표를 도입 명령으로 읽지 않는 것이 실무적 판단이다.

## 마지막 확인: 오늘 기사에서 검증한 것과 제안한 것

공식 원문과 RSS에서 확인한 사실은 네 글의 발행 시각과 URL, 각 예제의 구성, 원문이 밝힌 수치와 범위다. 예를 들어 AWS의 Crawl4AI 글은 커스텀 파이프라인이 삭제를 자동 처리하지 않는다는 점을 설명한다. 증류 글은 보류된 ShoppingBench 문제와 학생·교사 비교를 제시한다. 부품 글은 가상 데이터와 인간 검토를 전제한다. Circle K 글은 고객 내부의 초동 분류 지표를 보고한다. 이들은 확인 가능한 발표 내용이다. 서로 다른 글의 숫자를 한 제품의 예상 성과로 합산하지 않는다.

이 글에서 제시한 문서 등록부, 상태 코드, 제품 화면 분리, 단계별 배포, 실패 대응, HR 적용 예시는 **필자의 실무 설계 제안**이다. AWS가 모든 표와 절차를 제품 기능으로 제공한다고 주장하지 않는다. 어떤 제안이 실제로 필요한지는 조직의 자료, 권한, 위험, 운영 체계를 보고 정해야 한다. 공식 발표의 사실과 적용 제안을 나누면 독자가 원문을 다시 확인할 수 있고, 제품팀은 검증할 가설을 명확하게 만들 수 있다. 오늘의 결론은 모델을 덜 믿으라는 단순한 경고가 아니라 **모델이 유용하게 일할 수 있도록 출처·권한·평가·책임을 함께 설계하자**는 실무 원칙이다.

## 별첨: 변경이 생겼을 때 다시 확인할 열 가지 신호

첫째, **원천 페이지 구조가 바뀌었다면** 수집 성공 상태만 믿지 않는다. 200 응답이어도 본문 선택자가 빗나가면 메뉴만 남거나 표가 빠질 수 있다. 대표 문서의 Markdown을 이전 버전과 비교하고, 제목·절 번호·표의 의미가 유지됐는지 본다. 본문 길이가 갑자기 짧아진 URL은 검색 결과에서 일시 제외할지 검토한다. 잘못 수집된 내용을 모델이 매끄럽게 보충하도록 두면 문제를 발견하기 더 어려워진다.

둘째, **문서가 폐기되거나 이동했다면** 새 URL의 수집과 옛 URL의 검색 제거를 각각 확인한다. 같은 내용이 다른 주소에 중복 인덱싱되면 검색 상위 결과가 한 출처로 쏠릴 수 있다. 삭제 보호 설정, sidecar 잔존, 수집 작업 상태를 함께 확인한다. 과거 감사에 필요한 문서는 현재 답변용 인덱스와 분리해 보존할 수 있다. ‘삭제’가 파일을 없애는 일인지 현재 답변에서 제외하는 일인지 목적을 먼저 정한다.

셋째, **도구 응답 스키마가 바뀌었다면** 증류 학생의 출력 형식과 하네스의 파서를 같이 시험한다. 모델이 학습한 도구 결과의 필드 이름이 바뀌면 추론 능력 문제가 아닌 호환성 문제가 생긴다. 도구 호출의 성공률과 작업 완수율이 동시에 떨어졌는지 확인하고, 구버전과 신버전을 명시한다. 모든 실패를 프롬프트 수정으로 해결하려 하지 않는다. 파서가 거부한 인수와 서버가 권한 때문에 거부한 인수는 다른 실패다.

넷째, **사용자 요청 유형이 달라졌다면** 기존 벤치마크의 대표성을 다시 본다. 쇼핑 문제에서 새로운 배송 국가가 늘거나 HR에서 새로운 근무 형태가 도입되면 과거 성공률은 충분하지 않다. 모델이 잘 처리하던 범위를 유지하되 새로운 범주를 별도로 평가한다. 실패를 학습 데이터에 넣을지, 결정적 규칙을 추가할지, 사람 검토로 둘지 업무 위험에 따라 결정한다. 데이터가 늘었다는 이유로 무조건 재학습하는 것은 비용과 회귀 위험을 늘릴 수 있다.

다섯째, **모델 공급이나 엔드포인트 구성이 바뀌었다면** 호출 단가만 보지 않는다. 학생 모델의 GPU 활용률, 동시성, 추론 지연, 도구 반복 횟수, 종료 실패를 함께 본다. 비용이 낮아져도 사용자가 결과를 받기 전에 떠나면 성공당 비용은 올라간다. 반대로 월간 요청량이 낮으면 켜진 엔드포인트의 대기 비용이 더 커질 수 있다. 비교 기간의 사용량과 질문 길이를 맞추고, 정확히 같은 성공 기준으로 평가한다.

여섯째, **새 이미지 유형이 들어왔다면** 검색 품질을 다시 점검한다. 제품 사진으로 만든 인덱스가 스캔한 도면이나 현장 사진에도 잘 작동한다고 가정할 수 없다. 사진의 해상도와 배경, 각도, 절단, 문서의 작은 글자가 결과에 영향을 준다. 시각 검색이 후보를 찾지 못하는 것과 정형 사양 검사에서 탈락하는 것을 분리한다. 사용자에게는 ‘검색 결과 없음’과 ‘적합한 후보 없음’을 다르게 설명한다. 전자는 검색 한계이고 후자는 업무 판정이다.

일곱째, **정형 사양이나 정책 코드가 바뀌었다면** 모델 평가만으로 끝내지 않는다. 결정적 계산의 입력, 단위, 공차, 적용 범위가 맞는지 별도 테스트한다. 모델이 정답처럼 설명하더라도 서버 판정이 다르면 실제 업무는 서버 상태를 따른다. 반대로 서버 규칙이 틀렸다면 모델이 올바른 문서를 인용해도 사용자가 거절될 수 있다. 두 층의 불일치를 오류로 기록하고 소유자를 분명히 한다. 신뢰의 기준은 한쪽을 무조건 우선하는 것이 아니라 업무별 진실 원천을 사전에 정하는 것이다.

여덟째, **장애 경고의 빈도나 형태가 바뀌었다면** 조사 에이전트의 사건 묶기 방식을 확인한다. 경고마다 독립 실행하면 비용과 중복 메시지가 늘고, 모든 경고를 한 사건으로 묶으면 다른 원인이 섞일 수 있다. 사건 ID, 서비스, 시간 범위, 고객 영향의 중첩을 기준으로 묶되 당직자가 분리하거나 합칠 수 있어야 한다. 초동 요약이 새 경고를 반영해 갱신됐으면 무엇이 새 사실이고 무엇이 철회된 가설인지 표시한다.

아홉째, **운영자가 요약을 사용하지 않는다면** 모델의 문장을 더 길게 쓰기 전에 근거와 양식을 확인한다. 필요한 로그 링크가 없거나, 담당자가 틀리거나, 실제 조치와 무관한 내용을 길게 설명하면 당직자는 다시 수작업을 한다. 유용한 요약은 정보량보다 결정을 돕는 구조가 중요하다. 사실, 가설, 다음 확인, 조치 위험도를 짧고 구분된 필드로 제공한다. 당직자의 피드백을 자료 소유자와 도구 담당자에게 연결한다.

열째, **지표가 좋아졌다면** 어떤 실패가 아직 남았는지 본다. 평균 검색 적합도는 오래된 정책 한 건의 인용을 숨길 수 있고, 평균 에이전트 성공률은 무단 조회 한 건을 숨길 수 있다. 평균 분류 시간은 중요한 고객 사고 한 건의 지연을 숨길 수 있다. 개선은 분명히 기록하되 핵심 위험 범주의 절대 실패 수를 별도 표시한다. 제품의 성공을 모델 활동량이 아니라 실제 사용자 문제 해결과 운영 사고 감소로 판단한다.

이 열 가지 신호의 공통점은 **변경된 층에서 검증한다**는 것이다. 원천이 변했으면 수집과 검색을, 도구가 변했으면 실행 계약을, 모델이 변했으면 행동을, 규칙이 변했으면 결정적 판정을, 운영 경고가 변했으면 사건 연결을 다시 본다. 하나의 대형 ‘AI 점수’로 모든 층을 대체할 수 없다. 오늘 네 공식 글이 유용한 이유는 각각 다른 층의 운영 문제를 구체적으로 보여 주기 때문이다. 네 발표의 수치와 사례는 출발점이고, 실제 제품의 신뢰는 출처가 맞고 행동이 제한되며 결과를 되돌아볼 수 있는 설계에서 완성된다.

## 최종 체크: 오늘의 발표를 내일의 운영으로 잇는 질문

내일 이 글을 다시 볼 때 가장 먼저 확인할 것은 새 모델의 이름이 아니다. 우리 서비스의 한 답변이 어떤 원문에서 나왔는지 찾을 수 있는가. 그 원문이 현재 적용되는 버전인지 설명할 수 있는가. 검색에 없는 사실을 모델이 보충했을 때 감지할 수 있는가. 도구 호출이 실제 권한을 넘으려 했을 때 서버가 막는가. 사용자가 결과를 보고 업무를 끝냈는지 알 수 있는가. 장애가 났을 때 첫 가설과 최종 원인을 구분해 기록하는가. 이 질문에 답할 수 있어야 발표의 기술을 제품 가치로 바꿀 수 있다.

특히 AI 기능의 소유자가 여러 팀으로 나뉘는 조직에서는 문서 소유자, 검색 담당자, 모델 담당자, 업무 API 담당자, 운영 당직자의 책임 경계를 짧게 적어 두는 것이 유용하다. 정답이 틀렸을 때 누구나 프롬프트만 고치려고 하면 실제 원인인 오래된 문서나 잘못된 정형 필드가 남는다. 반대로 모델 행동이 문제인데 크롤러만 다시 돌려도 해결되지 않는다. 각 계층의 실패 신호와 담당자를 연결하면 사고 대응 속도가 빨라진다. 오늘 네 공식 글의 기술적 세부사항은 서로 다르지만 모두 이 경계의 중요성을 드러낸다.

제품팀은 다음 작은 실험을 고를 수 있다. 최근 사용자 질문 열 개에서 인용이 실제 최신 원문으로 연결되는지 확인한다. 에이전트가 실패한 요청 다섯 개의 도구 궤적을 읽고, 모델 오류와 도구 계약 오류를 나눈다. 이미지 검색 결과 다섯 개에서 원본 사양과 정형 값의 충돌을 표시한다. 지난 사고 세 건에서 첫 요약이 실제 당직자의 다음 행동에 도움이 됐는지 확인한다. 이 작은 검토의 결과가 충분히 좋지 않다면 기능을 늘리기 전에 해당 층을 고친다. 충분히 좋다면 실험 범위를 한 단계 넓힌다. 발표를 복사하는 것보다 검증 가능한 한 걸음이 지속적인 개선에 가깝다.
