# 오늘의 AI Daily News

## 발행 기준과 한눈에 보는 결론

이 글은 **2026년 10월 21일 오전 11시 30분 KST**에 확인한 공개 공식 발표와 프로젝트 원문을 토대로 썼다. 검색 API에 필요한 키가 없어 `web_search`는 실패했다. 따라서 OpenAI 뉴스와 Hugging Face 블로그의 공식 목록에서 10월 20일 항목을 확인하고, 각 발표 원문과 공개 저장소를 직접 열었다. 검색 실패는 뉴스가 없다는 뜻이 아니다. 확인되지 않은 제3자 기사나 추정 날짜를 근거로 보충하지 않았다. 본문에서 ‘발표했다’는 제공자의 주장, ‘확인했다’는 공개 페이지에서 직접 읽은 내용, ‘제안한다’는 편집자의 실행 방안을 구분한다.

오늘의 핵심은 여섯 가지다. OpenAI는 Orchestra Bio 인수를 발표하며 연구 모델과 신약개발 프로그램의 업무 조정을 연결하겠다는 방향을 제시했다. Hugging Face는 Google의 **TorchTPU**가 TPU를 PyTorch의 네이티브 장치로 다루는 길을 열었다고 설명했다. 같은 팀의 **PyTorch 2.15 MPS** 기술 글은 Mac의 로컬 모델 실행에서 FP8, MoE 디코딩, 비디오 메모리와 정확도 개선 사례를 공개했다. Ai2는 최종 선택만이 아니라 **설득에 흔들리는 정도와 설명의 차이**를 측정하는 FairStress를 발표했다. 여기에 IBM Research의 지침 학습형 고객지원 에이전트와 NVIDIA의 연구용 생성형 수술 시뮬레이터도 함께 살핀다. 여섯 소식은 제품 전략, 장치 이식성, 성능·정합성, 의사결정 평가, 에이전트 절차, 물리적 상호작용 생성의 서로 다른 층위에 있다. 하나의 성능 순위로 합치지 않는다.

개발자 관점의 공통 결론은 명확하다. 프레임워크 API가 같아지는 일은 포팅을 시작하기 쉽게 하지만, 모델 출력이 정확하고 비용 효율적이라는 증거를 대신하지 않는다. 평가 데이터가 커지는 일은 모델을 비교할 기회를 늘리지만, 특정 조직의 인사·금융·의료 의사결정에 자동으로 적합하다는 뜻이 아니다. 바이오 워크플로에서 에이전트가 다음 작업을 제안하는 일도 과학자와 프로그램 책임자의 승인, 출처와 상태 추적을 생략하라는 뜻이 아니다. 네 발표를 제품에 연결할 때는 **업무 계약, 재현 가능한 실험, 사람이 승인할 경계**를 먼저 정의해야 한다.

## 배경: AI 도입의 네 개 층위를 한 지표로 압축하지 않는다

새 발표를 실무 계획으로 바꿀 때 흔히 ‘지원 여부’ 하나로 평가한다. 오늘은 그 표현이 특히 위험하다. TPU가 PyTorch 장치로 보인다는 것은 해당 백엔드가 모델의 모든 연산을 빠르게 실행한다는 뜻이 아니다. Mac에서 특정 MoE 모델의 디코딩이 6배 이상 빨라졌다는 것은 다른 모델의 첫 토큰 지연이나 품질이 그대로라는 뜻이 아니다. 공정성 벤치마크의 대규모 항목 수는 조직의 실제 지원자나 환자에게 적절한 의사결정 기준이 완성됐다는 뜻이 아니다. 바이오 에이전트가 프로젝트 일정의 의존관계를 찾는다는 설명은 연구·제조·임상의 규제 책임을 자동 위임할 수 있다는 뜻이 아니다.

네 소식을 읽는 순서는 기술 계층을 따라가면 쉽다. **장치 계층**에서 TorchTPU와 MPS 개선은 모델이 실행될 컴퓨팅 경로를 바꾼다. **모델 행동 계층**에서 FairStress는 같은 모델이 입력 표현과 압박에 따라 어떻게 선택을 바꾸는지 드러낸다. **업무 계층**에서 Orchestra와 Rosalind의 결합은 여러 사람과 시스템이 이어지는 과정을 에이전트가 어떻게 추적할지 질문한다. 제품 팀이 다루는 것은 세 층을 동시에 통과한 결과다. 장치가 빨라졌어도 행동이 맞지 않으면 쓰지 못하고, 행동이 좋아도 업무의 승인·감사 경로가 없으면 배포할 수 없다.

따라서 아래의 기술 설명에는 발표자가 측정한 범위를 먼저 적고, 이어서 자체 검증 설계를 제안한다. 예시 체크리스트와 게이트는 **편집자의 실무 제안**이지 발표 회사들이 제공하거나 보증하는 기능이 아니다. 측정되지 않은 값을 수치처럼 쓰지 않는다. 특히 제3자의 임상적 사용 승인, 규제 적합성, 대규모 비용 우위는 오늘 확인한 원문에서 증명되지 않았다.

## 1. OpenAI × Orchestra Bio: 모델의 답을 신약개발의 다음 행동으로 연결한다는 구상

### 무엇을 발표했는가

OpenAI는 Orchestra Bio를 인수했다고 공식적으로 알렸다. Orchestra는 과학자·프로그램 리더·AI 에이전트가 신약개발 프로그램을 함께 진행하도록 돕는 플랫폼으로 설명된다. Rosalind는 생명과학 연구용 모델과 도구의 이름이다. GPT-Rosalind는 생물학·화학 질문을 추론하도록 설계된 모델, Rosalind Workbench는 도구·데이터와 연결해 결과 분석과 실험 계획을 돕는 공간이다. 인수 발표의 초점은 새로운 기초 모델의 벤치마크가 아니라, 연구 결과가 다음 시험·결정·일정으로 이어지는 **업무의 연결성**이다.

공식 글은 미국에서 표적 발견부터 규제 승인까지 신약개발이 평균 약 10~15년 걸린다고 설명한다. 이 숫자를 인수에 따른 예상 단축 기간으로 읽으면 안 된다. 복잡성을 설명하는 배경 숫자이지 이번 결합의 효과 측정값은 아니다. 내부 부서와 외부 파트너 사이의 여러 시스템이 분리돼 있고, 한 공정의 지연이 다른 공정에 영향을 주는 상황을 해결 대상으로 제시한다. 제조 배치 실패가 임상시험 개시에 영향을 미치는 예시는 에이전트가 파급 일정과 선택지를 정리해 사람에게 제공하는 사용 시나리오다.

Rosalind 소개 페이지는 연구 워크플로에 대해 입력 확인, 분석 계획 승인, 실행 중 추적, QC 지표와 저장 산출물 검토라는 단계를 제시한다. 이 구성이 중요한 이유는 모델이 ‘좋아 보이는 실험’ 한 줄을 제안하는 것과 검토 가능한 연구 업무를 수행하는 것의 차이를 보여 주기 때문이다. 실험 결과가 어떤 파일·시료·분석 버전에서 왔는지 기록되지 않으면 다음 단계의 제안도 감사하기 어렵다. 반대로 사람의 승인 지점을 갖춘 워크플로는 도구가 늘어날수록 상태와 책임을 분명하게 만든다.

### 인수의 의미를 제품 로드맵과 구분한다

인수는 조직과 기술의 결합에 관한 사건이다. 공식 문구는 향후 에이전트 개발 목표를 말하지만, 오늘 즉시 모든 Rosalind 고객에게 Orchestra 기능이 제공된다는 출시는 발표하지 않았다. 기존 Orchestra 고객의 데이터 이동, 계약 변경, 통합 UI, API 일정도 이 글에서 확인되지 않는다. 제품 팀이 이 뉴스를 보고 조달이나 데이터 설계를 바꾸려면 현재 계약·문서와 공개된 기능 목록을 별도 확인해야 한다.

또한 공식 글의 파트너 사례는 제품 효과의 범위를 가르는 데 중요하다. Novo Nordisk와의 협력은 R&D와 상업 실행의 속도를 높이려는 목표, Moderna 사례는 복잡한 데이터의 통찰을 실험 워크플로로 전환할 잠재력으로 소개된다. 회사가 소개한 협력과 잠재력을 외부 독립 검증의 임상 성과처럼 취급하지 않는다. 연구용 도구의 가치는 환자 치료 효과가 아니라 **반복 가능한 연구 의사결정 과정**에서 먼저 평가할 수 있다.

### 바이오 에이전트의 최소 데이터 모델

업무 조정 에이전트가 유용하려면 문서 검색만으로는 부족하다. 예를 들어 `study_id`, `sample_id`, `assay_version`, `planned_date`, `actual_date`, `owner`, `dependency`, `decision_status` 같은 식별자와 상태가 맞물려야 한다. 원자료와 요약 사이에는 출처 링크가 있어야 하고, 에이전트가 제안한 변경과 사람이 승인한 변경은 별도의 이벤트여야 한다. 이는 공식 제품의 스키마를 설명하는 것이 아니라, 일반적인 업무 시스템에서 검증 가능한 에이전트를 설계할 때 필요한 **편집자의 최소 예시**다.

제조 배치 실패가 발생했다고 가정해 보자. 에이전트는 관련 임상 일정과 대체 배치의 가능성을 찾아볼 수 있다. 하지만 어떤 배치가 어떤 시험에 쓰일 수 있는지, 품질관리의 실패 원인이 해결됐는지, 참여자에게 영향을 주는 조치인지에 따라 필요한 검토자가 달라진다. ‘일정 자동 변경’으로 바로 이어지지 않도록 `영향 분석 → 근거 묶음 → 시나리오 비교 → 책임자 승인 → 변경 기록`을 분리해야 한다. 모델의 자유형 자연어 답변을 바로 원장이나 실험 상태로 쓰면 재현성과 책임 소재가 약해진다.

운영적으로는 두 가지 상반된 실패를 피해야 한다. 첫째, 도구가 없을 때의 과장이다. 에이전트가 접근하지 못한 연구 기록까지 고려한 듯 답하면 잘못된 완전성이 생긴다. 둘째, 도구가 있을 때의 과도한 자신감이다. 연결된 시스템이 많아도 최신성, 권한, 단위, 시료 정체성이 맞는지는 별도 문제다. 결과 화면에는 사용한 데이터의 시점·출처와 빠진 시스템을 함께 보여 주는 편이 안전하다. ‘모든 정보를 봤다’는 표현보다 ‘이 세 시스템의 특정 버전을 참조했다’는 표현이 검토 가능하다.

### 개발자에게 의미

바이오를 다루지 않는 팀에도 이 발표는 참고가 된다. 엔터프라이즈 에이전트의 경쟁 지점이 자연어 답변의 유창함에서 **여러 시스템의 상태·의존관계·승인 기록을 얼마나 일관되게 유지하는가**로 이동하고 있음을 보여 준다. 인사시스템, 회계, 제조, 고객지원도 업무가 하나의 프롬프트로 끝나지 않는다. 제안이 어느 데이터에서 왔고 누가 승인했으며 어떤 후속 변경이 일어났는지 추적해야 한다. 다만 인수 발표만으로 해당 역량의 성능 수준을 일반화하지 않는다.

## 2. TorchTPU: PyTorch의 같은 코드가 더 많은 장치를 만날 때

### 기존 경로의 불편함과 새 인터페이스

Hugging Face의 공식 글은 TPU에서 PyTorch를 쓰려면 종전에 PyTorch/XLA의 `torch_xla` 또는 JAX 경로를 익히는 일이 많았다고 설명한다. XLA의 지연 실행에서는 Python 코드 한 줄이 실행될 때 실제 장치 계산이 완료되지 않을 수 있고, 작은 변경이 그래프 재컴파일을 일으켜 디버깅과 성능 예측이 어려워질 수 있다. Optimum TPU는 Hugging Face 모델의 TPU 학습·추론 경로를 제공했지만, TorchTPU에서는 Transformers와 Diffusers가 네이티브 백엔드 위에서 작동하므로 **그 두 라이브러리를 TPU에서 실행하는 데 Optimum TPU가 필수는 아니라고** 글이 설명한다. 기존 사용자의 모든 워크로드에서 마이그레이션이 필요하거나 권장된다는 뜻은 아니다.

TorchTPU는 PyTorch에 TPU 백엔드를 추가한다. 공개 저장소는 ATen 커널, XLA 계산용 컴파일 캐시, 데이터·텐서 병렬 예시, `torch.compile()` 통합, 디버깅·벤치마킹 유틸리티를 설명한다. Hugging Face 글은 TPU VM에서의 설치와 `device_map="tpu"`로 모델을 로드하는 Transformers 예시, `pipe.to("tpu")`로 Diffusers 파이프라인을 이동하는 예시를 제공한다. eager 모드는 개발과 디버깅의 접근성을 높이고, compiled 모드는 그래프 재사용을 활용하는 최적화 경로로 소개된다.

여기서 ‘네이티브’는 **사용자 API와 통합 경로**에 관한 설명이다. 컴파일이 없어진다거나 XLA 기술 요소를 전혀 쓰지 않는다는 뜻으로 단순화하면 안 된다. 공개 저장소 자체가 XLA 계산의 캐시를 적고, Hugging Face 글도 compiled 실행의 첫 호출과 재사용을 구분한다. 장치 API의 자연스러움과 하위 런타임의 성격을 별도 층위로 읽어야 한다.

### 버전과 환경의 경계

공개 저장소는 Python 3.11 이상 지원과 공개 패키지 `torch_tpu` 0.2.0 설치 안내를 제공한다. 설치 예시의 CPU PyTorch 인덱스 지정은 TPU VM에 필요 없는 큰 CUDA 빌드를 받지 않기 위한 설명이다. 이 예시를 로컬 CPU나 GPU에서 TPU 실행이 가능해졌다는 뜻으로 읽으면 안 된다. 실제 TPU 장치가 붙은 적절한 VM과 드라이버·런타임 환경이 있어야 한다. 저장소의 README는 Google Cloud TPU v6e 인스턴스를 간단한 시작 환경으로 언급한다.

재현 실험에서는 `python --version`, PyTorch 버전, `torch_tpu` 패키지 버전, TPU 유형과 토폴로지, 드라이버 이미지, Transformers·Diffusers 버전을 한 묶음으로 잠가야 한다. `pip install`이 끝났다는 사실만으로 목표 모델을 로드했다고 보고하지 않는다. 같은 코드를 다른 환경에서 돌렸을 때 발생하는 불일치를 줄이려면 설치 명령보다 **검증 당시의 전체 의존성 명세**가 중요하다.

### 글의 성능 수치를 해석하는 법

Hugging Face는 Pallas 기반 ragged-dot 커널을 Mixture-of-Experts 모델에 붙인 사례에서, batch 64와 TPU v6e-8의 디코딩 처리량이 기본 구현 대비 Qwen3-30B-A3B는 21.5배, Gemma 4 26B-A4B는 12.8배 높았다고 적었다. 이 수치의 분모는 **동일 장치에서의 기본 구현**이며 GPU와의 가격·성능 비교가 아니다. 배치가 크면 효과가 크다는 설명도 함께 붙는다. 낮은 동시성의 대화형 서비스에 배치 64의 배율을 그대로 적용할 수 없다. 총 처리량이 올라도 첫 토큰 지연이나 요청별 p95는 달라질 수 있다.

Diffusers 사례의 Cloud TPU v6e-4에서는 특정 이미지·비디오 모델, bf16, batch 1, 텐서 병렬 4칩 설정이 제시된다. 1024×1024 이미지 생성의 한 예시는 compiled 3.5초, eager 8.0초로 적혔다. 이 역시 특정 프롬프트·단계 수·파이프라인의 예시다. 모델 로딩, 첫 그래프 컴파일, 장시간 서비스의 요청 분포를 모두 포함한 종단간 지표로 취급하지 않는다. 워크로드가 이미지 크기마다 달라진다면 동일 크기의 그래프를 재사용한다는 가정도 약해진다.

### 테스트 통과율은 지원률과 다르다

Hugging Face는 TPU에서 실행되는 Transformers 테스트의 96.5%가 통과하고, 보고한 34개 이슈 중 19개가 수정됐다고 밝혔다. TPU 결과를 공개 대시보드에 표시하는 nightly CI는 **작업 중**이라고 적었다. 96.5%는 ‘모든 Transformers 기능 중 96.5%가 지원된다’거나 ‘서비스 요청의 96.5%가 성공한다’는 뜻이 아니다. 해당 테스트 집합과 당시 실행 환경의 결과다. 테스트가 없는 모델·정밀도·동적 형태의 조합은 분모에 없다.

공개 글의 긍정적인 대목은 실패를 작은 재현 스크립트와 이슈로 바꾸겠다는 점이다. 플랫폼 팀의 파일럿도 이 습관을 따를 수 있다. 단지 ‘TPU에서 안 됨’이라고 남기지 말고 최소 모델, 입력 형태, 버전, 연산과 로그를 좁혀야 한다. 문제가 PyTorch 백엔드의 커널인지 Transformers의 캐시 처리인지, 장치 메모리인지 분류되면 우회 방법과 업스트림 수정 가능성이 보인다. 네이티브화는 개발자에게 디버깅 경로를 열어 주는 일이기도 하다.

### 자체 검증의 순서

파일럿 1단계는 목표 모델 하나를 고르고 입력의 정상·경계·예외 분포를 문서화하는 것이다. 2단계는 CPU나 기존 GPU 경로와 출력의 허용 오차를 정의해 정합성을 비교한다. 3단계는 eager로 기능 경계를 확인하고, compiled에서 첫 호출과 재사용 호출을 나눠 측정한다. 4단계는 요청 길이·이미지 크기·배치·동시성을 바꿔 지연과 처리량의 곡선을 얻는다. 5단계는 실패했을 때 기존 경로로 되돌리는 비용과 시간을 측정한다. 이 다섯 단계는 일반적인 검증 설계 제안이다. 특정 패키지의 공식 인증 절차는 아니다.

전환 판단의 분모를 ‘한 번 성공한 실행’에서 ‘품질 목표를 만족한 완료 요청’으로 바꾸는 게 중요하다. 장치 시간 가격이 낮아도 그래프 캐시가 흔들리거나 메모리 부족으로 재시도가 많다면 완료 요청당 비용이 오를 수 있다. 반대로 API가 익숙해 팀의 유지보수 부담을 줄인다면 단순 장치 가격 비교보다 실제 이익이 클 수 있다. 이 결정에는 팀의 부하와 운영 데이터가 필요하며 오늘 공식 글만으로 결론을 내릴 수 없다.

## 3. MPS in PyTorch 2.15: 성능 향상과 ‘조용한 오염’ 수정의 차이

### 공식 글에서 확인한 주요 변화

Hugging Face의 PyTorch 팀은 Mac용 MPS 백엔드에서 FP8, MoE 모델 디코딩, 행렬 연산, 오디오·비디오·학습 커널, Python에서의 MPS 스트림 및 이벤트 타이밍을 다룬다고 설명했다. 이전에는 지원되지 않는 연산과 성능 절벽, 예상 밖의 메모리 증가가 실사용 모델의 장애가 됐고, 이를 실제 Hugging Face 모델로 찾아 PyTorch에 기여한다는 배경을 제시한다. MPSGraph 대신 전용 Metal 커널을 쓰는 경우가 늘어났다는 설명도 있다. 다만 한 번의 릴리스가 MPS의 모든 연산 공백을 없애지는 않는다.

FP8 `float8_e4m3fn`은 BF16 대비 같은 개수의 가중치를 저장하는 공간이 절반이라는 설명과 함께 소개된다. `F.scaled_mm` 등 지원 연산에서 GPU 상의 계산 경로가 제공된다는 뜻이다. 메모리가 절반이라는 말은 모델 전체 RAM이 정확히 절반이 된다는 뜻이 아니다. 활성값·KV 캐시·스케일·메타데이터·임시 버퍼는 별도로 남는다. FP8로 바꾸면 결과 품질, 범위 초과, 스케일 정책을 검증해야 한다. 저장 형식의 이득과 실제 작업 집합의 피크 메모리 감소를 구분한다.

MoE 디코딩 수치는 M3 Ultra, `torch.compile`, 특정 모델에서의 비교다. Qwen3.6-35B-A3B는 9.4에서 61.3 tokens/s, LFM2.5-8B-A1B는 23.6에서 123.6 tokens/s라는 사례가 제시된다. 그룹 matmul의 전용 디코딩 경로, GPU-CPU 동기화 감소, top-k 라우팅 개선이 원인으로 설명된다. 이 메커니즘을 모르면 ‘PyTorch를 올리면 모든 로컬 LLM이 6배 빨라진다’는 과장으로 번지기 쉽다. MoE의 활성 전문가 수, 배치와 메모리 배치, 컴파일 사용 여부가 다른 모델은 같은 증가율을 기대할 수 없다.

### 정확도 이슈는 속도보다 우선한다

Qwen-Image-2.1 VAE 인코더의 기존 MPS 경로에서는 이미지 편집이 조용히 오염되는 사례가 있었다고 글은 설명한다. 오류가 발생해 작업이 멈추면 탐지할 수 있지만, 결과 이미지는 생성됐는데 내용이 잘못되면 사용자가 모델 품질 문제로 오해할 수 있다. 패딩 변경 후 encode-decode 왕복이 CPU 기준과 비교해 PSNR 10.06dB에서 29.95dB로 개선됐다는 수치는 **특정 왕복 정합성 시험**을 가리킨다. 일반적인 생성 미학 점수나 모든 영상 작업의 품질 지표가 아니다.

이 사례는 로컬 모델 운영의 중요한 원칙을 보여 준다. 장치별 회귀 시험은 처리 속도만 재면 안 된다. 이미지 입력을 그대로 인코딩·디코딩한 결과의 기준 영상 차이, 비디오 프레임의 시간적 일관성, 모델의 숫자 범위, 토큰 출력의 허용 오차를 모니터링해야 한다. 그래픽 결과가 시각적으로 그럴듯해도 업무에 필요한 세부 정보가 빠질 수 있다. 이미지 편집에서는 원래 유지돼야 할 텍스트·얼굴·도형이 바뀌는 문제를 대표 입력으로 넣는 편이 좋다.

Wan2.2 tiled VAE의 드라이버 피크 메모리가 270GiB에서 약 8GiB로 줄었다는 공식 사례도 같은 맥락이다. 전자의 값이 일반 Mac에 설치된 물리 메모리 크기를 뜻하는 것은 아니다. 글은 드라이버 메모리의 피크를 말한다. 값이 극적으로 줄었다고 해서 모든 비디오 생성 파이프라인이 8GiB 장치에서 원활히 실행된다는 뜻으로 옮기지 않는다. 재현하려면 특정 모델·타일 설정·프레임 수·해상도와 측정 수단을 맞춰야 한다.

### 업그레이드 결정과 운영 게이트

공식 글의 명시된 요구사항은 macOS 15 이상과 Python 3.11 이상이다. 글은 2.15의 릴리스 후보를 시험해 보라고 권한다. 따라서 안정 버전의 보급 상태와 별개로, 현재 단계에서의 시험 결과로 읽어야 한다. 기존 Mac 앱이나 개발자의 노트북이 둘 다 만족하는지 먼저 확인해야 한다. 특히 Python 런타임 업그레이드는 바이너리 확장과 패키지 호환에 영향을 줄 수 있다. 성능 향상만 보고 생산 환경의 버전을 즉시 올리기보다, 잠긴 의존성으로 격리된 실행 환경을 준비해 목표 모델을 확인한다. 오픈소스 프레임워크 릴리스의 존재와 우리 애플리케이션의 사용 준비 상태는 다르다.

검증에는 세 종류의 비교가 필요하다. **정합성**: CPU 또는 기존 안정 경로를 기준으로 허용 가능한 수치·영상 차이를 확인한다. **지연**: warm-up, 컴파일, 첫 토큰, 지속 디코딩을 나눈다. **자원**: 모델 로드, 실행 중 피크, 장시간 반복 후 누수를 확인한다. 개선이 두 축에 나타나도 세 번째 축이 악화될 수 있다. 예컨대 속도는 좋아졌지만 입력 크기가 바뀔 때마다 컴파일이 반복되면 인터랙티브 앱의 사용성은 떨어질 수 있다.

## 4. FairStress: ‘정답을 골랐다’ 이후에도 공정성 시험은 끝나지 않는다

### 벤치마크가 측정하려는 질문

Ai2의 문제 제기는 단순하다. 두 후보의 이력 중 A가 더 강하다고 명확히 주어진 경우, 모델이 A를 선택했다고 해서 평가가 끝나는가? 같은 증거와 자격을 유지하고 인구통계적 표현만 바꾼 다음, ‘상급자가 B를 선호한다’는 같은 유형의 주장으로 압박하면 선택이 한쪽 구성에서 더 쉽게 뒤집힐 수 있다. 최종 선택만 한 번 관찰하는 시험은 그 취약성을 놓친다. FairStress는 정답 선택, 정체성 표지, 설득형 접두문의 영향을 짝지어 비교한다.

공식 글은 300개 시나리오가 채용, 의료, 대출, 교육, 주거, 형사사법 등 29개 영역에 걸쳐 있다고 설명한다. 일부는 명확한 강자, 일부는 비교가 애매한 두 후보를 제시한다. 인구통계 정보는 없음, 이름, 간접 암시, 명시적 라벨 등으로 표현하고, 설득 문구는 권위·사회적 합의·새 증거 주장·법적 우려·역사적 불이익 등을 활용한다. 같은 유형의 문구가 A 또는 B를 옹호하게 쌍을 만든다. 이 조합이 전체 1,300만 건 이상으로 확장되며, FairStress-Core는 항목반응이론으로 선택한 약 5만 건이다. 큰 전체 집합과 빠른 부분집합의 점수를 같은 조건인 것처럼 비교하지 않아야 한다.

연구팀의 ‘대칭적 공정성’은 **같은 근거라면 정체성에 관계없이 같은 기준을 적용하고, 잘 뒷받침된 결정은 같은 유형의 압박에 비슷하게 버텨야 한다**는 정의다. 이 정의에는 명시적 가치 선택이 있다. 예컨대 역사적 차별의 시정이나 대표성 목표를 결정의 정당한 요소로 보는 형평성 접근은 다른 결론을 낼 수 있다고 연구팀도 인정한다. 따라서 조직이 이 벤치마크를 가져올 때는 법·정책·도메인 전문가와 먼저 ‘허용되는 근거’가 무엇인지 정해야 한다. 벤치마크 점수를 정책의 대체물로 만들지 않는다.

### 발표 수치의 범위와 읽는 법

15개 모델에 대한 전체 평가에서, 연구팀은 정체성이 간접 암시될 때 올바른 결정을 포기하는 격차 평균이 6.9%포인트, 명시적 라벨일 때 9.3%포인트였다고 적었다. FairStress-Core의 특정 프런티어 모델·모드에서는 양쪽 자격이 비슷한 모호한 문제에서 소수자 코드 후보를 60~65% 고른 사례를 제시한다. 매칭된 설득형 접두문에 따른 방향별 전환 차이는 연구팀의 12개 모델·모드 실행에서 8.8~42.4%포인트였다. 이 숫자는 **해당 평가 조건의 그룹별 행동 차이**를 기술할 뿐 개별 사람에 대한 모델 의도나 모든 응용에서의 방향을 증명하지 않는다.

설명에도 차이가 보고됐다. 공개 글에 따르면 11개 오픈웨이트 모델에서 명시적 정체성 라벨이 있는 경우 소수자 코드 후보를 선택한 설명은 ‘회복력’, ‘다양성’, ‘장벽’ 같은 표현을 더 자주 쓰고, 다수자 코드 후보를 선택한 설명은 ‘증거’, ‘기준’, ‘상세함’ 같은 절차적 단어가 더 많았다. 올바른 후보를 골랐어도 그 사람의 자격을 설명하는 방식에 차이가 생길 수 있다는 뜻이다. 다만 빈도 비교만으로 차별의 동기나 실제 조직의 피해 규모를 단정할 수 없다. 설명의 내용, 과제 문맥, 정답의 근거와 함께 봐야 한다.

내부 활성 분석은 더 좁은 범위다. Gemma-3-12B-it과 Qwen2.5-7B-Instruct의 일부 비교에서 활성값으로 인구통계적 선택 방향을 약 73% 정확도로 예측했고, 같은 활성의 텍스트 설명은 57~59%로 50% 우연 기준보다 조금 높았다고 연구팀이 썼다. 이름을 제거하면 활성 기반 예측력이 약 18%포인트 감소했다는 후속 시험도 있다. 이는 모든 모델의 숨겨진 ‘의도’를 판독했다는 뜻이 아니다. 두 모델과 몇 가지 대비에서 관찰한 신호이며, 내부 표현과 언어적 설명의 차이를 탐구한 제한적 결과다.

### 평가 방법이 결론의 방향을 바꿀 수 있다

연구팀은 기존 BBQ 평가와 FairStress가 서로 다른 방향을 보이는 이유를 살폈다. 고정 답안의 확률을 비교하는 방식과 사용자가 질문해 모델이 직접 답을 생성하는 방식은 실제 동작이 다르다. 동일한 BBQ 문항과 모델 가중치를 두고 채팅 템플릿, 질문 형식, 고정 선택지 점수 또는 생성 답변을 달리한 다섯 설정에서 일부 모델의 관측된 편향 방향이 바뀌었다고 보고한다. 이 대목은 벤치마크가 틀렸다는 단정이 아니라 **측정 프로토콜이 무엇인지 적지 않은 단일 점수의 위험**을 보여 준다.

서비스 팀은 자신들의 UI와 사용자의 실제 프롬프트를 포함해 시험해야 한다. 관리자 화면에서 두 지원자를 비교하는 방식과, HR 담당자가 자연어로 후보 평가 이유를 묻는 방식은 같은 모델을 써도 다른 평가 환경이다. 사내 룰이 시스템 프롬프트에 들어가고, PDF의 후보 정보가 검색 증강으로 들어오는 경우도 별개다. FairStress가 알려 준 차원을 참고하되, 실제 결정을 대신 수행하기 전에는 프로덕션 흐름과 일치하는 생성 방식으로 정합성과 설명을 검증해야 한다.

### 개선 기법의 비용을 함께 본다

Ai2는 자기비판, 활성 스티어링, 학습된 편집 등 아홉 개 개입을 시험했고 대부분이 비대칭을 안정적으로 줄이지 못했다고 설명한다. 한 활성 스티어링 방법은 명확한 결정에서 Qwen2.5-7B-Instruct의 정확도를 98%에서 47%로 떨어뜨렸다. 공정성 격차가 한 지표에서 줄었다고 해도 정답을 거의 절반 잃는다면 실무 적용은 어렵다. 반사실적 사고 과정을 통해 후보의 인구통계 정체성을 서로 바꿔 다시 생각하게 하는 방식은 세 모델 계열에서 올바른 결정을 포기하는 격차를 줄이면서 정확도를 대체로 유지했지만, 애매한 사례의 비대칭을 모두 없애지는 못했다.

따라서 자체 개선 실험의 결과표에는 적어도 네 열이 필요하다. **정확한 선택률, 그룹별 차이, 설득에 따른 전환률, 설명의 근거 충실도**다. 하나가 좋아지고 다른 하나가 크게 나빠지는 방법을 ‘공정성 개선’ 한 문장으로 배포하면 안 된다. 모호한 사례에는 정답이 없을 수 있으므로, 조직의 정식 의사결정 정책과 사람 검토 경로를 따로 정의한다. 모델이 불확실하다고 답하는 선택지도 평가에서 빠져서는 안 된다.

### 인사·대출·의료에 적용할 때의 경계

고위험 의사결정에서 모델을 쓰려는 팀은 공개 벤치마크를 사전 위험 탐지 도구로 사용하고, 실제 결정을 자동화하는 근거로 전용하지 않아야 한다. 채용에서는 자격 요건의 출처와 가중치가 공고·조직 정책과 일치하는지 확인해야 한다. 대출에서는 법률상 금지된 입력과 허용되는 입력, 누락 자료 처리 절차를 문서화해야 한다. 의료에서는 우선순위 기준을 임상 전문가가 정의해야 한다. FairStress가 29개 도메인을 포괄한다고 해서 어느 도메인의 규정과 실무를 대신하는 것은 아니다.

각 조직의 테스트 자료를 만들 때에는 실제 개인 데이터를 무심코 평가 서비스에 업로드하지 않는 것이 기본이다. 합성·비식별 사례에서도 자격 근거, 정체성 단서, 압박 문구가 교차하는 구조를 만들어야 한다. 반사실 쌍을 만들 때는 인구통계적 표현 외의 정보가 바뀌지 않았는지 검사한다. 이름 교체가 문화·언어·경력의 암시까지 바꾸면 원래 의도한 ‘정체성만 달라진 시험’이 아니다. 설득 문구도 같은 길이와 권위 수준으로 짝을 맞춰야 비교가 의미 있다.

## 5. 네 발표를 함께 읽는 개발자 가이드

### 장치 포팅과 업무 승인에는 같은 ‘중간 상태’ 문제가 있다

TorchTPU와 MPS는 모델 계산이 어느 장치에서 실행되는지를 바꾼다. 에이전트 플랫폼은 계산 결과가 어떤 다음 작업으로 바뀌는지를 다룬다. 둘 사이에는 중간 상태가 있다. 장치의 경우 모델 로드 성공, 연산 지원, 출력 정합성, 지속 부하에서의 성능을 차례로 확인해야 한다. 에이전트의 경우 정보 검색 성공, 근거의 정확성, 제안의 타당성, 사람 승인 후의 상태 변경을 차례로 확인해야 한다. 첫 계단을 밟았다고 마지막 계단에 도착한 것은 아니다.

FairStress는 이 중간 상태의 행동 측면을 비춘다. ‘A를 선택했다’는 한 번의 출력과 ‘같은 근거에서 A를 계속 지지한다’는 강건성은 다르다. 같은 식으로 TPU에서 같은 모델의 출력이 한 입력에서는 맞더라도 긴 문맥·새 이미지 크기·분산 실행에서 같을지는 별도 검증이다. 결과의 신뢰성을 높이려면 성공을 단일 불리언이 아니라 **상황별 불변조건의 집합**으로 정의해야 한다.

### 네 소식의 성숙도를 구별한다

OpenAI 인수 발표는 **기업의 전략·통합 방향**이다. TorchTPU 저장소는 **실제 공개 패키지와 코드**가 있는 개발 경로다. MPS 글은 **특정 버전의 기술 변경과 측정 사례**다. FairStress는 **공개 평가 자료·코드·연구 결과**다. 이 성숙도가 서로 다른 발표를 같은 구매 체크리스트에 넣으면 오류가 생긴다. 인수에는 로드맵과 계약 질문을, 공개 백엔드에는 설치와 호환성 질문을, 릴리스에는 회귀 질문을, 벤치마크에는 평가 설계와 정책 질문을 해야 한다.

제품 발표를 보는 담당자는 ‘언제 내 계정에서 쓸 수 있는가’를 물어야 한다. 인프라 담당자는 ‘내 모델과 입력이 이 버전에서 실행되는가’를 물어야 한다. 품질 담당자는 ‘출력과 실패가 현재 경로와 얼마나 다른가’를 물어야 한다. 정책 담당자는 ‘결정의 근거와 책임이 누구에게 있는가’를 물어야 한다. 네 질문 중 하나만 답한 팀은 전체 시스템을 검증한 팀이 아니다.

### 숫자 비교의 분모를 적는다

오늘 본 큰 숫자들은 서로 비교할 수 없다. TorchTPU 커널의 21.5배는 특정 TPU의 기본 구현 대비 **처리량 배율**이다. MPS의 61.3 tokens/s는 특정 Mac과 MoE 모델의 **디코딩 속도**다. 96.5%는 실행된 Transformers **테스트의 통과율**이다. FairStress의 9.3%포인트는 명시적 인구통계 표지 조건에서 관찰한 **결정 전환의 그룹 간 격차**다. 신약개발 10~15년은 인수 효과가 아니라 **일반적인 기간 배경**이다. 분모가 다른 수치를 한 장의 ‘AI 진전 그래프’로 놓는 순간 기술 의사결정은 흐려진다.

측정 보고서에는 수치 옆에 최소한 `대상 모델 / 하드웨어 / 소프트웨어 버전 / 데이터셋 / 실행 조건 / 비교 기준 / 측정 시각`을 붙여야 한다. 정답이 있는 평가라면 정답 정의와 제외 조건도 적는다. 비용이라면 클라우드 장치 시간뿐 아니라 실패 재시도, 대기, 운영 시간을 분리한다. 이 형식은 화려하지 않지만 나중에 새 릴리스나 새로운 모델이 나왔을 때 같은 질문을 다시 할 수 있게 한다.

## 개발자에게 의미: 이번 주 실행 가능한 네 가지 작은 실험

### 실험 A — TPU의 ‘로드 가능’과 ‘서비스 가능’을 분리

목표 체크포인트 하나를 골라 공개 TorchTPU 버전과 적절한 TPU VM에서 로드한다. 가장 짧은 정상 입력, 일반 입력, 긴 입력, 형태가 바뀌는 입력을 준비한다. eager에서 출력과 오류를 확보한 뒤 compiled 경로에서 첫 요청·반복 요청·형태 변경 요청을 따로 측정한다. 성공 보고서에는 정확도 또는 허용 오차, 첫 토큰 지연, 지속 처리량, 메모리, 실패 원인을 기재한다. 이 결과가 ‘서비스 가능’이라고 판단되려면 재시도와 대체 경로가 정의돼야 한다. 실제 파일럿을 해보지 않은 상태에서 공식 블로그의 배율을 비용 계획에 넣지 않는다.

### 실험 B — Mac 업그레이드의 정합성 회귀

macOS와 Python 요구사항을 만족하는 별도 환경에서 PyTorch 2.14와 2.15를 비교한다. 목표 모델이 MoE라면 두 버전의 같은 가중치·컴파일 설정에서 출력 토큰과 디코딩 속도를 기록한다. 이미지 편집이라면 원본을 보존해야 하는 대표 입력과 왕복 인코드·디코드 입력을 포함한다. 비디오라면 한 번의 성공뿐 아니라 반복 생성의 피크 메모리와 장시간 안정성을 본다. 어떤 수치가 공식 블로그와 다르면 실패로 단정하기 전에 하드웨어·모델·설정·데이터 크기의 차이를 확인한다.

### 실험 C — 의사결정 모델의 반사실 쌍

실제 개인 정보가 없는 작은 합성 사례에서 자격 근거는 고정하고 인구통계 표지만 바꾼다. 기본 선택을 기록한 뒤 같은 유형·길이의 설득 문구를 양쪽에 붙인다. 정답이 명확한 사례와 모호한 사례를 분리한다. 선택이 뒤집혔다면 어느 조건에서, 설명은 무엇을 근거로 들었는지 함께 기록한다. FairStress의 전체 결과를 조직의 정답으로 가져오지 말고, 평가 차원을 설계하는 참고로 쓴다. 개선 프롬프트를 추가한 뒤에는 대칭성만이 아니라 원래 정확도도 다시 재야 한다.

### 실험 D — 에이전트의 상태 변경 전 검토 화면

연구·인사·제조 등 실제 워크플로 하나를 골라 에이전트가 제안만 하도록 연결한다. 제안에는 참조한 문서와 데이터 버전, 추론이 아닌 확정 사실, 누락 데이터, 예상되는 후속 의존 작업을 적게 한다. 상태 변경 버튼은 검토자만 누르게 하고, 변경 전후 상태와 승인자를 이벤트로 남긴다. 기초 모델의 지식이 더 최신인지를 묻기 전에 업무 시스템의 출처와 최신성 검증을 갖춘다. OpenAI의 인수 발표가 이러한 설계를 공식적으로 보장하지는 않지만, 발표가 겨냥한 ‘복잡한 작업 조정’에 필요한 검증 단위는 이렇게 만들 수 있다.

## 운영 포인트 — 채택 전 책임자가 확인할 것

**릴리스·버전 관리.** TorchTPU는 패키지·PyTorch·TPU 런타임을 함께 잠근다. MPS는 macOS·Python·PyTorch 버전을 함께 잠근다. 버전 하나만 적은 성능 수치는 재현하기 어렵다. 패키지의 새 릴리스가 나오면 설치 가능 여부와 사용 중인 API의 변경을 먼저 확인하고, 기존 결과를 자동으로 최신 결과로 취급하지 않는다.

**관측 가능성.** 장치 백엔드에는 컴파일 횟수·캐시 적중·OOM·CPU 폴백·p50/p95 지연을 기록한다. 모델 판단에는 입력 버전·정책 버전·결정·설명·사람의 재검토 결과를 기록한다. 에이전트에는 읽기 도구 호출, 제안, 승인, 실제 변경을 구분한다. 로그는 민감 정보를 최소화하면서도 장애 재현에 충분해야 한다. ‘성공 응답 200’만으로 품질을 감시할 수 없다.

**실패의 종류.** TPU에서 실행 실패는 연산 지원, 버전 불일치, 메모리, 분산 통신 등으로 나뉜다. MPS에서는 느린 실행뿐 아니라 조용한 출력 오염을 고려한다. FairStress식 결정 평가에서는 정답을 틀리는 것과 같은 정답을 불균형하게 포기하는 것을 구분한다. 에이전트에서는 근거가 틀린 제안과 올바른 제안을 잘못된 권한으로 실행한 오류를 구분한다. 분류가 정확할수록 수정 담당자도 선명해진다.

**되돌리기.** 하드웨어 경로 변경은 이전 장치의 이미지와 모델 버전을 유지해 롤백 시간을 재야 한다. 에이전트의 외부 상태 변경은 가능하면 승인과 실행을 분리하고, 되돌릴 수 없는 단계에는 명시적인 사람 검토를 둔다. 평가 모델이나 프롬프트를 바꾸는 경우 기존 정책 버전을 기록해 어떤 결정이 어느 버전에서 나왔는지 추적한다. 기술적으로 되돌릴 수 있는 것과 이미 사람이 영향을 받은 결정을 원상복구하는 것은 다르다.

**비용.** 장치의 시간당 가격이나 단일 요청의 API 호출료는 총비용의 일부다. 품질 회귀로 인한 수동 재작업, 컴파일·warm-up, 유휴 자원, 실패 요청의 재시도, 검토 담당자의 시간을 포함해 완료 작업당 비용을 계산한다. 장치가 더 빨라졌다는 공개 배율을 우리 팀의 총소유비용 절감으로 바로 바꾸지 않는다. 마찬가지로 업무 조정 에이전트의 시간 절감도 승인·감사·오류 수습의 시간을 제외하고 계산하면 편향된다.

## 과장하기 쉬운 표현을 정확히 고치기

- **“TPU에서 PyTorch가 그대로 돌아간다.”** → TorchTPU는 네이티브 장치 API를 제공한다. 실제 모델·연산·버전·입력 형태는 자체 검증이 필요하다.
- **“TPU가 GPU보다 21.5배 빠르다.”** → 공식 수치는 배치 64의 특정 Pallas 커널과 같은 TPU의 기본 구현을 비교한 디코딩 처리량이다. GPU와의 비교가 아니다.
- **“Mac 로컬 LLM이 모두 6배 빨라졌다.”** → M3 Ultra, `torch.compile`, 제시된 MoE 모델의 사례에서 2.14 대비 5~6.5배 향상이 보고됐다.
- **“PyTorch 2.15면 모든 이미지 편집 문제가 해결된다.”** → 글은 Qwen-Image-2.1 VAE의 특정 MPS 패딩 오류 수정과 왕복 PSNR 개선을 보여 준다. 다른 모델은 시험해야 한다.
- **“공정성 벤치마크에서 높은 점수면 채용 자동화가 가능하다.”** → 평가 정의, 실제 정책, 법적 요건, 업무 데이터, 사람 검토를 별도로 결정해야 한다.
- **“OpenAI 인수로 신약 승인 기간이 줄었다.”** → 공식 글은 인수와 향후 에이전트 목표를 발표했다. 승인 기간 단축의 측정 결과를 발표하지 않았다.
- **“큰 테스트 집합이면 사각지대가 없다.”** → FairStress의 1,300만 항목도 특정 설계의 변형이다. 실제 조직의 권한·정책·언어·데이터 흐름을 모두 대표하지 않는다.

## 오늘의 판단: 어디까지 알 수 있고 무엇이 남았는가

확인된 것은 각 회사·연구팀의 공개 발표와 공개 저장소에 적힌 기능·수치·범위다. TorchTPU의 공개 패키지와 저장소 안내, MPS 2.15의 특정 모델 측정, FairStress의 설계와 결과, Orchestra 인수의 방향은 출처를 따라 재확인할 수 있다. 그러나 독자의 모델이 TPU에서 안정적으로 실행되는지, 특정 Mac에서 업그레이드의 순이익이 있는지, 인사시스템의 의사결정이 공정한지, 바이오 에이전트가 실제 프로그램 일정을 얼마나 개선하는지는 오늘 확인한 원문만으로 알 수 없다.

그 차이를 채우는 산출물은 거창한 전면 도입 선언이 아니다. TPU에서는 **버전이 고정된 재현 스크립트와 품질·지연 곡선**, Mac에서는 **실사용 모델의 정합성·피크 메모리 회귀표**, 결정 모델에서는 **정책 담당자가 승인한 반사실 쌍과 오류 분류표**, 에이전트에서는 **근거·제안·승인·실행의 분리된 감사 기록**이 먼저다. 이 네 가지가 있으면 다음 발표가 나왔을 때 같은 기준으로 비교할 수 있다. 공개 뉴스의 가치는 곧바로 출시하라는 신호가 아니라, 검증 가능한 다음 질문을 더 정확하게 만드는 데 있다.

## 심층 분석 A — 네이티브 백엔드의 ‘같은 코드’는 어떤 동일성을 보장하는가

### API 동일성과 출력 동일성

TorchTPU가 TPU를 PyTorch 장치로 표시하고 MPS가 PyTorch의 Mac 가속 경로를 개선한다는 말은 개발자가 같은 모델 정의를 사용할 여지를 넓힌다는 뜻이다. 그러나 모델 정의가 같아도 계산 정밀도, 커널 구현, 연산 순서, 메모리 배치, 난수 처리와 컴파일 최적화는 장치마다 달라질 수 있다. 따라서 ‘같은 코드가 실행된다’는 말은 적어도 네 단계로 분해해야 한다. 첫째는 Python 코드가 오류 없이 실행되는가, 둘째는 모델의 수치 결과가 허용 범위에 있는가, 셋째는 생성물의 업무적 품질이 같은가, 넷째는 운영 목표의 지연·비용·복구가 맞는가다. 앞의 하나가 뒤의 세 가지를 함의하지 않는다.

예를 들어 이미지 편집 앱을 생각해 보자. 파이프라인이 MPS 장치로 올라가고 `images[0]` 객체를 돌려주면 기능 스모크 테스트는 통과한다. 그러나 공식 MPS 글이 설명한 VAE 오염처럼 encode-decode 경로가 입력의 세부 구조를 잃었다면 사용자는 ‘동작은 하지만 잘못된 편집’을 받는다. TPU의 경우에도 모델이 토큰을 출력하는 것과 목표 언어·길이·도메인에서 기존 경로와 비슷한 답을 내는 것은 다르다. 비결정적 생성 모델의 출력을 바이트 단위로 비교할 수 없으므로, 태스크별로 적절한 비교 방식을 정해야 한다. 분류기는 레이블과 확률 분포, 임베딩은 근접성·다운스트림 검색 결과, 이미지 생성은 구조 보존과 안전 필터, 언어 생성은 정답이 있는 질문과 실사용 평가 샘플을 함께 본다.

장치별 수치 차이를 모두 오류로 분류해서도 안 된다. 부동소수점 계산에서는 연산 순서와 정밀도에 따라 작은 오차가 생길 수 있다. 중요한 것은 오차의 크기가 업무 기준을 깨는지다. 일반적인 텍스트 초안 작성과 의약품 용량 계산의 허용 오차는 같을 수 없다. 허용 범위는 모델 개발팀만 정하지 말고 결과를 소비하는 업무 담당자와 합의해야 한다. 성능 실험에서 ‘동일한 품질’이라고 쓰려면 그 품질의 판정 방법과 샘플 집합을 남긴다. 그래야 빠른 장치가 품질을 낮춰서 얻은 이익인지 판단할 수 있다.

### eager와 compile을 나누어 측정하는 이유

Hugging Face의 TorchTPU 글은 eager에서 시작하고 필요한 경우 `torch.compile`을 사용하라고 안내한다. Diffusers 예시도 eager 이동과 compiled 변형을 나란히 보여 준다. 이 구조는 개발 초기와 장기 실행의 목적이 다르기 때문이다. eager는 연산별 실패 위치를 좁혀 기능을 확인하기 쉽다. compiled는 반복되는 모양과 그래프의 재사용으로 빠른 경로를 노린다. 첫 호출에 컴파일 비용이 들어가는 경우, 짧게 한 번 실행하고 종료하는 작업은 compiled 지연이 더 클 수도 있다. 장시간 반복 서비스에서는 이후 호출의 이득이 초기 비용을 상쇄할 수 있다. 어느 쪽이 유리한지는 입력 크기 분포와 캐시 재사용률이 결정한다.

그래서 성능표를 만들 때 `설치 → 모델 로드 → 첫 추론 → 반복 추론 → 입력 모양 변경 → 프로세스 재시작`을 분리한다. 설치와 모델 로드는 사용자가 매 요청마다 경험하지 않을 수도 있지만, autoscaling이나 장애 복구에서는 다시 겪는다. 입력 모양 변경은 이미지 해상도와 텍스트 길이가 다양할 때 중요하다. 프로세스 재시작은 캐시가 유지되는지, 어떤 산출물이 재사용 가능한지 보게 한다. 공식 예시 하나의 3.5초와 8.0초를 비교하는 데서 그치지 않고, 우리 서비스의 요청 분포에서 총 지연을 계산한다.

측정값도 중앙값만으로 충분하지 않다. 첫 요청이 느리고 이후가 매우 빠른 경로라면 평균이 사용자의 체감을 숨길 수 있다. p95와 최댓값을 함께 기록하고, 컴파일 도중 다른 요청이 대기하는지 확인한다. 높은 처리량의 배치 서버에서는 분당 완료 요청 수가 중요한 반면, 실시간 보조 도구는 첫 결과 도착 시간이 더 중요할 수 있다. 공식 블로그의 수치는 어떤 질문을 시작할지 알려 주지만 목표 서비스의 SLA를 대신 정해주지는 않는다.

### 지원 행렬을 만드는 방법

‘TorchTPU 지원’이라는 하나의 칸 대신 행렬을 쓴다. 행은 목표 모델과 버전, 열은 실행 모드·정밀도·입력 형태·병렬 방식으로 둔다. 각 칸에는 `미시험`, `로드 성공`, `정합성 통과`, `성능 측정 완료`, `운영 승인` 같은 상태를 표시한다. 어느 팀이 미시험을 실패로, 어느 팀이 로드 성공을 운영 승인으로 해석하면 같은 자료로 다른 결정을 내린다. 상태의 정의와 담당자를 문서화하는 것이 행렬의 핵심이다.

Mac 앱도 같은 행렬을 만들 수 있다. Intel Mac인지 Apple Silicon인지, macOS와 Python 버전이 무엇인지, MPS를 사용할 때 CPU 폴백이 발생하는지, `torch.compile`을 쓰는지를 적는다. PyTorch 2.15 글에 있는 FP8과 새 Metal 커널의 혜택은 모든 장치·연산 조합에 균일하지 않다. 제품에서 사용하지 않는 기능의 개선이 릴리스 노트에 많아도 우리 앱의 변경 우선순위를 올릴 이유는 적다. 반대로 이번 글의 Qwen-Image-2.1 VAE처럼 실제 오류를 겪던 경로라면 버전 업그레이드의 우선순위가 높아질 수 있다.

### 비용의 비교 단위

가속기 비교를 ‘초당 토큰’ 한 줄로 끝내지 않는다. 대화형 모델은 입력 토큰 수, 출력 토큰 수, 동시성, 배치 방법, 캐시 재사용, 품질 게이트를 고정해야 한다. 텍스트 생성에서 같은 초당 토큰 수라도 첫 토큰이 너무 늦거나 결과가 목표 품질에 미달하면 사용자 가치가 낮다. 이미지 모델은 생성 단계 수, 해상도, 재시도 비율이 비용에 영향을 준다. 학습 작업은 스텝 처리량뿐 아니라 검증 점수에 도달하는 총 시간과 실패 재시작까지 포함해야 한다.

일반적인 내부 비용표에는 장치 임대료, 실행 중 사용률, 모델 로드·컴파일 시간, 저장소와 전송, 엔지니어 유지보수, 장애 대응 시간을 분리할 수 있다. 그런 다음 **품질을 통과한 완료 작업 한 건당 비용**을 계산한다. 공식 TorchTPU 글의 커널 배율은 이 분수의 한 요소일 뿐이다. MPS의 로컬 실행에는 클라우드 청구서가 없더라도 사용자 장치의 배터리·메모리 경쟁·설치 복잡성이 비용이 된다. 의사결정자는 돈뿐 아니라 사용자가 기다리는 시간과 실패 비용을 함께 본다.

## 심층 분석 B — FairStress를 실무 평가 하네스로 옮길 때

### 데이터 세트의 단위를 먼저 정의한다

FairStress의 기본 단위는 두 후보 사이의 결정 시나리오다. 현실의 인사·대출·의료 업무에서는 후보의 적합성을 설명하는 근거가 구조화되지 않은 문서, 표, 면담 기록, 시스템 상태에 나뉘어 있을 수 있다. 자체 평가를 설계한다면 단순히 이름만 바꾸는 반사실 쌍보다 먼저 **결정에 허용되는 근거**를 명시한다. 자격증이 필수인지 우대인지, 부채비율 계산에 누락 자료를 어떻게 취급하는지, 환자 우선순위를 누가 승인한 기준으로 정하는지가 그것이다. 기준이 불분명하면 모델의 선택이 맞는지 판정할 수 없다.

정답이 명확한 사례와 애매한 사례를 섞어 하나의 정확도로 발표하면 문제가 생긴다. 명확한 사례는 더 강한 후보를 골랐는지 확인할 수 있다. 애매한 사례에서는 둘 중 어느 선택이든 타당할 수 있고, 중요한 것은 근거를 정직하게 설명하고 보류 또는 추가 정보 요청을 할 수 있는지다. FairStress가 두 유형을 나누는 이유도 여기에 있다. 실무 하네스는 `정답이 있는 선택`, `동률·모호함`, `자료 부족`, `권한 없는 요청`을 구분해야 한다. 자료 부족을 임의 선택으로 채우는 모델은 평균 선택률이 그럴듯해도 운영상 위험하다.

테스트 데이터의 균형은 표면적 인원수만 맞추면 되는 일이 아니다. 자격의 강도, 결격 사유, 문서 길이, 표현 방식이 그룹별로 고르게 분포해야 한다. 인구통계적 표현을 바꾸는 과정에서 직장명·지역·언어 능력처럼 결과에 합법적으로 영향을 줄 수 있는 요소도 함께 바뀌었다면 순수한 대비가 아니다. 반사실 쌍마다 변경된 필드를 기계적으로 비교하고, 의도적으로 남긴 차이는 이유를 적는다. 외부의 실제 사람 데이터를 사용한다면 데이터 권한과 보존 기간이 평가 설계의 일부여야 한다.

### 설득형 접두문은 실제 공격 표면을 닮아야 한다

FairStress가 시험하는 압박은 단순한 ‘다시 생각해’가 아니다. 상급자 권고, 새 증거 주장, 법적 우려, 사회적 합의 같은 서로 다른 형태가 있다. 실제 서비스에서도 채용 담당자가 ‘팀장이 이미 정했다’고 적거나, 고객이 ‘법적 문제를 피하려면 다른 결과를 내야 한다’고 적을 수 있다. 모델이 이런 문구를 새로운 사실로 받아들여 기존 근거를 버리면 의사결정 경계가 약해진다. 반대로 진짜 새 증거가 들어왔는데도 절대 바꾸지 않는 모델도 유용하지 않다. 따라서 설득에 대한 강건성은 모든 변경을 거부하는 능력이 아니라 **새 정보의 검증과 권한 판단을 유지하는 능력**이다.

내부 테스트에는 문구별 예상 행동을 적는다. 근거가 없는 ‘고위층이 B를 선호한다’는 주장에는 기존 기준을 유지하거나 권한 확인을 요청할 수 있다. 검증 가능한 새로운 자격증이 추가됐다면 정보 출처를 확인한 뒤 선택을 바꿀 수 있다. 법적 우려를 제기하는 문구라면 독단적 결정보다 정책 담당자에게 넘기는 편이 맞을 수 있다. 이 셋을 모두 ‘선택이 뒤집혔다’라는 한 개의 실패로 묶으면 모델의 올바른 업데이트와 부당한 압박 수용을 구분하지 못한다. FairStress의 대칭성 지표를 참고하되 제품의 행동 분류표를 더 세밀하게 만든다.

### 설명의 품질을 별도로 채점한다

모델이 자격상 강한 후보를 고른 뒤에도 설명에서 그 후보의 실제 실적 대신 추상적 정체성 이야기를 강조할 수 있다. Ai2 글은 이런 차이를 관찰했다고 보고한다. 자체 평가에서는 설명의 단어만 세는 방식에 머무르지 말고 근거가 원자료의 어느 필드와 대응하는지 확인한다. 예를 들어 채용 평가라면 필수 경력, 프로젝트 결과, 면접에서 확인한 역량과 부족한 자료를 구분한다. 차별적 표현이 없더라도 잘못된 실적을 지어냈다면 설명은 불합격이다. 근거가 맞아도 원래 기준에 없는 속성을 들었다면 왜 등장했는지 검토해야 한다.

설명 점수와 선택 점수는 별개다. 올바른 후보를 잘못된 이유로 고른 모델은 다음 사례에서 취약하다. 잘못된 후보를 그럴듯한 이유로 설명하는 모델도 위험하다. 두 점수를 하나로 평균 내면 서로 상쇄되어 문제를 숨긴다. 리더십 보고에는 ‘선택 정확’, ‘근거 충실’, ‘불확실성 표시’, ‘설득에 대한 대칭적 안정성’을 별도 열로 제시한다. 표본이 적으면 숫자 뒤의 사례를 함께 읽는다. 작은 격차를 확정적인 구조적 현상으로 단정하지 않는 신중함도 필요하다.

### 프롬프트 수정이 해결책인지 확인한다

공정성 문제를 발견하면 ‘공정하게 판단하라’는 시스템 프롬프트를 추가하고 싶어지기 쉽다. 하지만 연구팀이 비교한 여러 개입에서 일부는 대칭성을 개선하는 대신 정확도를 크게 떨어뜨렸다. 자체 수정도 원본 모델, 수정 모델, 동일한 시험 집합으로 나란히 비교해야 한다. 어떤 조합에서는 과도한 보정이 생기고 다른 조합에서는 여전히 불균형할 수 있다. 모델이 모든 민감 사례를 거절하는 방식으로 표면 점수를 올리는지도 확인한다. 거절이 정당한 업무 경계인 경우와 실무자가 필요로 하는 지원을 제공하지 못하는 경우를 구분한다.

프롬프트는 모델 가중치가 같아도 행동을 바꾼다. Ai2의 BBQ 비교에서 채팅 템플릿과 답변 생성 방식의 차이가 관측 방향에 영향을 준 점을 주목해야 한다. 운영 앱의 시스템 프롬프트, 검색 문서, 입력 폼, 재시도 로직이 평가 환경과 다르면 공개 벤치마크 점수는 참고자료다. 실제 출시 후보의 정확한 프롬프트·모델 버전·온도·후처리로 평가를 다시 돌려야 한다. 사후에 프롬프트가 바뀌면 결정의 기준이 달라질 수 있으므로 변경 기록과 재평가 게이트를 묶는다.

### 사람의 검토를 형식적 버튼으로 만들지 않는다

‘사람이 마지막에 승인한다’는 문구만으로 안전해지지 않는다. 검토자가 모델의 결론과 같은 말로 채워진 화면만 본다면 실질적인 독립 검토가 어렵다. 화면에는 원자료의 핵심 근거, 모델이 고려하지 못한 자료, 정책 기준, 반대 근거를 확인할 수 있어야 한다. 사람이 모델 의견을 반려하거나 추가 자료를 요구하기 쉬워야 한다. 승인율이 99%라고 해서 모델이 매우 정확하다는 결론을 내리지 않는다. 검토가 무의미하게 설계됐을 가능성도 있다.

업무 현장에서는 의사결정의 주인이 누구인지 명확해야 한다. 모델은 정보를 정리하고 후보별 근거를 대조할 수 있지만, 법적·윤리적 책임이 수반되는 결정의 기준은 조직과 담당자가 정한다. 특히 FairStress가 채택한 대칭적 공정성은 하나의 평가 관점이다. 조직의 합법적 형평성 정책이나 의료 우선순위 규칙과 충돌하는 경우에는 벤치마크 점수를 목표로 삼기 전에 정책 전문가가 판단해야 한다. 공정성은 수학적 점수 하나가 아니라 무엇을 공정한 결정의 조건으로 볼지에 대한 명시적 합의가 필요하다.

## 심층 분석 C — 과학·업무 에이전트가 ‘제안’에서 ‘실행’으로 넘어가는 문턱

### 연결된 시스템이 많아질수록 출처는 더 중요해진다

Rosalind와 Orchestra의 결합 목표는 연구 모델의 답을 신약개발 프로그램의 복잡한 일정·의존관계에 연결하는 것이다. 시스템을 여럿 연결하면 에이전트가 더 많은 사실을 볼 수 있는 동시에, 서로 다른 시점과 의미의 자료를 한 답변에 섞을 위험도 커진다. 같은 시료 ID가 여러 실험실에서 다른 표현으로 기록되거나, 계획 날짜와 확정 날짜가 다른 시스템에 남을 수 있다. 에이전트가 현재 상태를 요약할 때에는 어느 원장·문서·버전에서 가져왔는지 함께 보여야 한다. 자연어 요약이 깔끔하다는 이유로 모순된 시스템 상태를 지워서는 안 된다.

특히 과학 연구의 근거는 결과와 해석을 분리해야 한다. 측정값이 있다는 사실과 그 값이 특정 가설을 지지한다는 해석은 다르다. 실험이 실패했다는 사실과 제조 배치를 폐기해야 한다는 정책 결정도 다르다. 에이전트의 자료 구조와 UI가 `관측`, `모델 추론`, `사람의 판단`, `승인된 실행`을 각각 표시하면 검토자가 어디를 반박해야 하는지 알 수 있다. 하나의 ‘AI가 분석했다’ 칸에 모든 층위를 담으면 잘못된 자동화가 일어나기 쉽다.

업무 조정용 에이전트는 일정 변경의 파급을 계산할 수 있다. 하지만 의존관계가 누락돼 있으면 파급 분석도 불완전하다. ‘영향 없음’이라는 결론을 내리기 전에 어떤 데이터 소스와 의존관계를 확인했는지 보여야 한다. 검색 범위 밖의 시스템이 있다면 ‘확인하지 못함’으로 표시한다. 이것이 인간 담당자의 업무를 늘리는 듯 보여도 장기적으로는 잘못된 완전성에 따른 재작업을 줄인다. OpenAI 발표에는 이러한 구체 UI의 구현 보증이 없으므로, 이는 발표를 읽은 독자가 자체 제품에서 고려할 운영 설계다.

### 상태 변경 권한을 분리한다

에이전트가 일정 변경안을 만들고 변경 버튼까지 직접 누를 수 있다면 편리하다. 그러나 외부 파트너, 시험 일정, 샘플 이동, 규제 기록에 영향이 갈 수 있는 업무에서는 준비와 실행을 분리하는 편이 맞다. 준비 단계에서 에이전트는 변경 대상, 예상 영향, 전제 조건, 대안, 증거 링크를 제시한다. 승인 단계에서 권한 있는 사람이 전체 영향을 확인한다. 실행 단계에서는 승인된 정확한 변경만 적용하고, 이후 상태를 다시 읽어 기대와 일치하는지 검사한다. 자연어 승인 한 줄을 범위가 무제한인 도구 권한으로 바꾸지 않는다.

실패해도 안전하게 복구할 수 있는 작업과 되돌릴 수 없는 작업을 나누는 것도 중요하다. 임시 알림 초안 작성은 쉽게 취소할 수 있다. 이미 외부에 발송한 시험 지시나 물리적 시료 이동은 되돌리기 어렵다. 신약개발에서는 후자의 비용이 크므로 승인 문턱이 높아야 한다. 같은 원리는 일반 인사시스템의 급여 확정, 대출 실행, 주문 발주에도 적용된다. 업종이 달라도 ‘분석은 자동화할 수 있으나 외부 상태 변경에는 별도 검증이 필요하다’는 구조가 유효하다.

### 에이전트 평가의 정답을 만든다

모델의 자연어 답변만 읽고 ‘유용했다’고 평가하면 업무 조정 성능을 과대평가할 수 있다. 평가 사례에는 사건의 초기 상태와 올바른 후속 조치를 명시한다. 제조 배치 실패 예시라면 영향을 받는 시험, 필수 승인자, 일정의 선후관계, 잘못 건드리면 안 되는 무관한 프로그램을 포함한다. 에이전트가 관련된 두 일정을 찾고 하나를 놓쳤다면 실패다. 관련 없는 일정을 변경해도 실패다. 변경하지 않고 누락 정보 때문에 책임자에게 질문하는 것이 정답일 수도 있다.

이런 평가에서 ‘정답’을 만들려면 업무 담당자의 시간이 든다. 그러나 그 시간이 아깝다고 공개 모델 벤치마크를 대신 쓰면 제품의 핵심 위험이 남는다. 공개 생명과학 질문의 정확도는 사내 데이터 권한과 최신성, 승인 체계에 대한 지표가 아니다. 에이전트의 시험은 과학 지식 질문과 별개로 **도구 사용·상태 이해·정확한 변경 범위·사람에게 넘기는 판단**을 평가해야 한다. 이 역시 OpenAI의 인수 효과를 평가했다는 주장이 아니라, 복잡한 업무 조정이라는 발표 목표를 실무에서 검증하는 방법이다.

## 심층 분석 D — 팀별 의사결정 메모 예시

### 플랫폼 팀: TorchTPU 파일럿 요청서를 읽을 때

요청서에 ‘PyTorch 코드 변경이 적다’만 적혀 있으면 부족하다. 모델 ID, 체크포인트 리비전, 현재 GPU 또는 CPU 기준 경로, 예상 입력 분포, 품질 게이트, TPU VM 유형, 성능 목표가 있어야 한다. 새 백엔드를 시험하는 목적도 분명히 한다. 인프라 비용 절감인지, 공급망 다변화인지, 이미 보유한 TPU 자원의 활용인지에 따라 성공 기준이 달라진다. 파일럿 기간과 실패 시 기존 경로로 돌아가는 절차를 정한다. 재현 로그를 남기지 않은 한 번의 데모는 구매 결정을 뒷받침하지 못한다.

플랫폼 담당자는 공식 저장소에 이슈나 제한 사항이 공개되어 있는지도 확인한다. 96.5% 통과율이라는 숫자만 인용하지 않고, 남은 실패가 우리 모델의 핵심 연산에 해당하는지 살핀다. 이슈 34개 중 19개가 수정됐다는 사실은 활발한 개발을 뜻할 수 있지만, 우리 문제가 해결됐다는 뜻은 아니다. 이슈를 재현하는 최소 스크립트가 있다면 팀 자체 결과와 비교한다. 백엔드가 빨리 발전하는 시기에는 버전 고정과 작은 자동 회귀가 특히 가치가 높다.

### 모바일·데스크톱 팀: Mac의 2.15 업그레이드를 결정할 때

로컬 AI 앱은 서버와 달리 사용자의 하드웨어 분포를 통제하기 어렵다. 최소 macOS 버전과 Python 기반 런타임 배포 방식을 먼저 확인한다. 일부 사용자만 macOS 15 이상이라면 모든 사람에게 같은 경로를 제공할 수 없다. 새 MPS 경로가 없는 환경의 대체 동작을 준비한다. 모델 파일의 크기와 앱 설치 크기, 초기 다운로드 시간도 품질의 일부다. FP8이 가중치 저장 공간에 주는 이점이 앱 전체 설치 크기와 실행 메모리에 얼마나 나타나는지 별도로 측정한다.

속도 개선을 홍보하기 전에는 실제 사용자의 입력 패턴을 확인한다. 짧은 프롬프트와 긴 프롬프트, 한 번의 생성과 여러 번 이어지는 편집은 다른 워크로드다. 공식 글의 M3 Ultra 결과가 M 시리즈 전체에 적용된다고 쓰면 안 된다. 특정 모델의 정확도 문제가 수정됐다면 속도 수치보다 해당 버그의 재현과 해결을 우선 검증한다. 앱 사용자는 숫자 배율보다 자신이 저장한 사진·문서가 손상되지 않는지를 더 크게 체감한다.

### 제품·정책 팀: 의사결정 보조 모델을 승인할 때

FairStress를 적용할지는 ‘우리 모델이 공정한가’라는 추상 질문 대신 ‘어떤 기준의 일관성을 어떤 업무에서 요구하는가’로 결정한다. 채용 앱에서 모델이 지원자를 순위화하는 것과 면접 질문 초안을 추천하는 것은 영향력이 다르다. 전자는 자격 기준과 그룹별 오류, 사람 검토를 엄격히 다뤄야 한다. 후자도 특정 후보에게 다른 수준의 난이도나 설명을 제공한다면 기회의 차이가 생길 수 있다. 기능마다 영향 범위와 검토 수준을 기록한다.

공개 FairStress 점수를 제품의 합격·불합격 기준으로 가져오지 않는다. 회사 정책과 지역별 법률, 사용자에게 제공하는 설명을 반영한 자체 사례가 필요하다. 실무 결과를 해석할 때는 그룹별 표본 수와 불확실성을 함께 제시한다. 소수의 사례에서 5%포인트 차이가 나왔다고 확정적 결론을 내리지 않는다. 반대로 통계적 유의성이 없다는 이유로 심각한 개별 오류를 무시해서도 안 된다. 수치와 오류 사례를 같이 읽는 운영 습관이 중요하다.

### 업무 시스템 팀: 바이오 에이전트 뉴스를 자사 도메인에 적용할 때

Orchestra 인수 소식에서 일반 업무팀이 배울 점은 특정 생명과학 지식이 아니라 작업 간 의존관계의 중요성이다. 인사시스템에서 한 직원의 부서 변경은 결재선, 근태 정책, 급여 원가부서, 접근권한에 영향을 줄 수 있다. 에이전트가 부서 변경 요청을 이해했다고 해도 영향을 받는 객체를 모두 찾았는지, 누가 승인해야 하는지, 변경 일자가 어느 시스템의 기준인지 확인해야 한다. 이 구조는 제조 배치 실패가 임상 일정에 미치는 영향을 찾는 공식 예시와 비슷한 문제 형식이다. 다만 기능이 실제 제품에 구현돼 있다는 뜻은 아니다.

업무 시스템은 먼저 영향 그래프를 기록 가능한 형태로 갖춰야 한다. 에이전트가 생성한 자연어 설명에만 의존하지 말고, 어떤 엔터티와 의존관계가 조회됐는지 구조화된 목록을 남긴다. 변경을 적용하면 원래 요청과 달라진 값이 없는지 사후 검증한다. 수정 기록을 사람의 검토와 연결한다. 이 기초가 있어야 더 강한 모델로 바꾸거나 새로운 도구를 연결해도 기존 승인 절차를 유지할 수 있다.

## FAQ — 오늘 발표를 제품 회의에 가져갈 때의 질문

### 1. TorchTPU가 있으면 기존 `torch_xla` 프로젝트를 바로 폐기해야 하나?

아니다. Hugging Face 글은 새로운 네이티브 경로에서 Transformers·Diffusers에 Optimum TPU가 더 이상 필수는 아니라고 설명한다. 그렇다고 기존 프로젝트의 모든 동작과 비용이 새 경로에서 더 좋다고 증명한 것은 아니다. 현재 코드의 연산, 분산 구성, 운영 중인 모델을 같은 테스트로 비교하고, 새 경로의 이득이 명확한 부분부터 전환하면 된다. 이미 안정적으로 실행되는 경로는 실패 시 대체 수단이 될 수 있다.

### 2. `device_map="tpu"`로 로드되면 운영 승인할 수 있나?

로드는 가장 앞의 검증 단계다. 대표 입력의 결과와 예외, 동적 길이, compiled 경로의 warm-up과 재컴파일, 장시간의 메모리·통신 오류, 재시도와 롤백까지 보아야 한다. 공개 예시는 시작 코드를 제공할 뿐 우리 서비스의 SLA를 보증하지 않는다. 로드 성공은 지원 행렬에서 ‘로드 성공’ 칸에만 적고, 정합성·성능·운영 상태를 비워 둔다.

### 3. 공식 커널 배율을 예산 절감률로 써도 되나?

안 된다. 21.5배와 12.8배는 특정 TPU와 batch 64에서 기본 구현 대비 커널을 붙였을 때의 디코딩 처리량이다. 장치 간 가격, 다른 배치, 첫 토큰 지연, 품질, 유휴 자원은 포함하지 않는다. 예산에는 같은 서비스 요구사항을 만족하는 두 구성의 완료 요청당 총비용을 계산해 넣는다. 벤치마크 수치는 실험의 우선순위를 정하는 데 쓴다.

### 4. Mac에서 FP8이면 모델 메모리가 정확히 절반인가?

글이 말하는 절반은 BF16과 비교한 `float8_e4m3fn` 값의 저장 크기다. 모델 전체에는 활성값, KV 캐시, 스케일·메타데이터, 실행 버퍼, 앱의 다른 메모리가 함께 있다. FP8을 사용할 수 있는 연산과 대상 모델도 확인해야 한다. 추론 품질이 유지되는지도 직접 평가한다. 전체 앱의 메모리 사용량은 실제 장치에서 재야 한다.

### 5. MPS 글의 Qwen-Image-2.1 수치가 이미지 생성 품질 점수인가?

아니다. 공식 글에서 인용한 10.06dB와 29.95dB는 VAE encode-decode 왕복이 CPU 기준 영상과 얼마나 비슷한지를 측정한 PSNR이다. 패딩 문제로 이미지 편집이 오염되던 특정 경로를 보여 준다. 생성된 이미지의 미적 만족도나 모든 프롬프트에서의 정합성을 뜻하지 않는다. 제품 테스트에는 실제 편집 작업의 결과를 별도 포함해야 한다.

### 6. Wan2.2의 8GiB면 8GiB Mac에서 영상 생성이 보장되나?

아니다. 공식 글은 특정 tiled VAE 디코드의 피크 드라이버 메모리 예시를 제시한다. 모델의 다른 부분, 입력과 출력 프레임, 시스템 메모리, 동시 실행 앱은 포함되지 않을 수 있다. 필요한 전체 워크로드의 피크와 시간, 오류율을 실제 목표 기기에서 측정해야 한다. 이 수치를 전체 비디오 생성 파이프라인의 최소 요구사항으로 바꾸면 안 된다.

### 7. FairStress의 1,300만 항목이면 자체 평가가 필요 없나?

필요하다. 큰 항목 수는 연구 설계의 조합 규모다. 조직의 정책, 문서 형식, 입력 언어, 모델에 부여한 권한, 실제 사람 검토 절차를 모두 대표하지는 않는다. 공개 자료는 어떤 종류의 비대칭을 찾아야 하는지 알려 주는 출발점이다. 출시에 쓰는 정확한 프롬프트와 업무 기준으로 자체 사례를 평가해야 한다. 개인정보 사용과 보존도 조직의 책임이다.

### 8. 모델이 소수자 코드 후보를 더 많이 선택하면 곧 공정성이 높아진 것인가?

그 자체로는 아니다. 명확한 근거가 어느 쪽을 지지하는지, 모호한 경우 조직 정책이 무엇인지, 설명이 실제 자격을 충실히 반영하는지 함께 보아야 한다. Ai2는 특정 비교에서 과도한 보정 가능성을 보고했지만, 대칭적 공정성만이 유일한 정당한 정의라고 주장하지 않는다. 선택 비율 하나로 정당성을 판정하면 실제 강점이나 불이익 정책을 지워 버릴 수 있다.

### 9. 반사실 프롬프트를 추가하면 문제를 해결할 수 있나?

연구팀의 특정 실험에서 정체성을 바꿔 재고하게 하는 방식은 올바른 결정을 포기하는 격차를 줄이는 데 상대적으로 효과적이었다. 그러나 모호한 사례의 비대칭을 모두 제거하지 않았고, 다른 모델·정책·도메인에 그대로 적용된다는 보장은 없다. 배포 후보에서 원래 정확도, 거절률, 설명의 충실도와 추가 지연을 함께 평가해야 한다. 절차를 하나 추가했다는 사실을 결과 개선의 증거로 삼지 않는다.

### 10. 인수 발표로 Rosalind의 새 에이전트를 오늘 구매할 수 있나?

공식 인수 글은 결합의 방향을 제시하지만 특정 통합 기능의 일반 출시일이나 계약 조건을 말하지 않는다. 구매 가능 기능과 가격, 데이터 처리 범위는 현재 제품 문서와 공급자의 계약 자료를 확인해야 한다. 발표의 비전은 파일럿 요구사항을 만드는 근거가 될 수 있지만, 제공 중인 API의 목록으로 간주할 수 없다.

### 11. 바이오 도메인이 아닌데 인수 소식이 왜 중요한가?

여러 시스템의 상태와 사람의 결정을 연결하는 문제는 일반 기업 앱에도 있다. 부서 이동, 결재선 변경, 고객 불만 처리, 제조 일정 조정처럼 한 사건이 여러 업무에 파급될 때 에이전트가 유용해질 수 있다. 그러나 유용함은 모델의 말솜씨가 아니라 의존관계의 누락 없는 파악, 근거의 출처, 승인된 변경만 실행하는 능력으로 검증해야 한다. 발표의 생명과학 사례를 다른 도메인의 검증된 성능으로 옮기지는 않는다.

### 12. 오늘 무엇부터 해 보면 좋은가?

이미 TPU 자원이 있으면 목표 모델 한 개의 eager 로드·정합성을 확인한다. Mac 모델 앱을 운영하면 2.15의 요구사항과 현재 사용자 하드웨어 분포를 비교한다. 의사결정 보조 모델이 있으면 합성 반사실 쌍 몇 개와 설득형 입력을 작성한다. 에이전트가 외부 상태를 바꾼다면 제안·승인·실행 로그가 분리돼 있는지 확인한다. 하루 안에 네 기술을 모두 도입하는 게 목적이 아니라, 현재 제품에서 가장 큰 미검증 경계를 찾는 것이 목적이다.

## 부록 — 최소 재현 보고서의 형식

성능이나 품질 결과를 공유할 때 첫 줄에 ‘무엇을 비교했는가’를 적는다. 예: `TorchTPU 0.2.0의 특정 모델 추론 vs 기존 장치 경로`, `PyTorch 2.15 MPS의 이미지 편집 왕복 vs 2.14`, `제품 프롬프트 A와 B의 반사실 결정 비교`다. 이어서 모델 ID·리비전, 데이터 출처와 샘플 수, 하드웨어, 운영체제·런타임·패키지 버전, warm-up 방식, 실패 처리, 비교 기준을 적는다. 숫자는 그 뒤에 놓는다. 앞부분이 비어 있으면 다른 팀이 점수를 재현할 수 없다.

정합성 결과에는 단순 성공률 외에 실패 사례를 분류한다. 장치 비교에서는 로드 오류, unsupported op, 수치 차이, 출력 품질 차이, 지연 위반, 메모리 오류를 나눈다. 공정성 평가에서는 잘못된 선택, 설득으로 부당하게 뒤집힘, 새 증거를 정당하게 반영함, 설명의 사실 오류, 정책 밖 답변을 나눈다. 에이전트에서는 근거 누락, 의존관계 누락, 승인 전 실행, 승인 후 상태 불일치를 나눈다. 분류 체계가 있어야 ‘점수 향상’이 실제로 어떤 결함을 줄였는지 볼 수 있다.

결론에는 통과·보류·실패를 분명히 적되, 모르는 것도 남긴다. ‘특정 입력 집합에서 정합성 통과, 긴 입력과 분산 실행은 미시험’ 같은 결론은 과장이 없고 다음 행동이 명확하다. ‘AI가 빨라졌으니 도입’보다 검토 가능하다. 외부 발표의 수치를 인용할 때에는 발표자의 주장과 내부 재현을 분리한다. 시간이 지나 새 릴리스가 나오면 같은 문서 형식으로 다시 측정할 수 있고, 이전 결과를 이유 없이 덮어쓰지 않는다.

마지막으로 각 실험의 비용과 종료 기준을 정한다. 하루짜리 포팅 스파이크의 목적은 모든 운영 위험을 해결하는 게 아니라 목표 모델이 실행 가능한지 판별하는 것이다. 공정성 평가의 첫 주 목적은 조직의 정책 정의와 가장 중요한 반사실 쌍을 만드는 것일 수 있다. 에이전트 파일럿의 첫 단계는 승인 전 상태 변경을 막고 근거를 남기는 것일 수 있다. 검증 가능한 작은 결과가 쌓이면 뉴스의 약속을 제품의 실제 역량으로 바꿀 수 있다. 이 과정을 거치지 않은 채 발표의 수치만 빌려오는 것은 빠른 의사결정처럼 보이지만, 나중에 가장 비싼 질문을 운영 현장으로 미룬다.

## 실무 부록 1 — 발표를 검증 가능한 릴리스 게이트로 바꾸는 방법

### 게이트의 목적과 측정 대상

새 기술을 채택하는 팀은 대개 ‘데모 통과’라는 말을 쓴다. 그러나 무엇이 통과인지 정의하지 않으면 같은 결과를 각 부서가 다르게 읽는다. 플랫폼 팀은 모델이 실행되면 통과라고 생각하고, 제품 팀은 사용자가 원하는 결과를 얻어야 통과라고 생각하며, 운영 팀은 장애 뒤에도 복구돼야 통과라고 생각한다. 이 셋은 모두 필요한 조건이다. 그래서 오늘 뉴스에 대한 공통 게이트를 **기능, 정합성, 성능, 관측, 복구, 권한**의 여섯 층으로 분리한다. 각 층은 누가 승인하는지와 미시험 상태를 포함해야 한다. 이 틀은 특정 공급자의 공식 인증 기준이 아니라 자체 배포 판단을 위한 제안이다.

기능 게이트는 목표 사례의 코드와 모델이 원하는 경로에서 실행되는지 본다. TPU라면 특정 체크포인트가 로드되는가, MPS라면 앱의 특정 기능이 수행되는가, FairStress식 평가라면 시험 입력과 답변이 실제 제품 흐름에서 생성되는가, 업무 에이전트라면 필요한 시스템만 읽는가가 질문이다. 기능 테스트가 되지 않으면 그다음 수치는 의미가 없다. 다만 기능 테스트를 통과했다고 다른 게이트를 자동으로 통과 처리하면 안 된다. 여섯 칸의 상태를 독립적으로 관리한다.

정합성 게이트는 결과가 업무상 허용 범위에 있는지 본다. 분류와 점수의 비교에는 수치 오차가 필요할 수 있고, 이미지 편집에는 보존해야 할 요소가 필요하며, 채용·대출 보조에는 결정 근거와 정책의 일치가 필요하다. 에이전트는 제안한 작업이 실제 근거의 범위를 넘지 않는지를 봐야 한다. 성능 게이트는 대기 시간, 처리량, 메모리, 비용을 다루지만 품질을 낮춰 얻은 속도는 별도 실패로 둔다. 어느 한 축만 좋아도 출시할 수 있다는 식의 평균 점수는 피한다.

관측 게이트는 장애가 발생했을 때 원인을 추적할 수 있는가다. 백엔드에서는 입력 크기와 컴파일 여부, 앱에서는 모델·패키지 버전, 평가에서는 정책·프롬프트 버전, 에이전트에서는 도구 호출과 승인 기록이 필요하다. 복구 게이트는 실패 후 원래 경로로 돌아가거나 작업을 중지할 수 있는지 확인한다. 권한 게이트는 외부 상태 변경이 누구의 결정으로 이뤄지는지 본다. TPU/MPS처럼 주로 내부 실행 경로인 경우에는 배포 권한이 핵심이고, 에이전트의 일정 변경이나 고위험 의사결정에서는 업무 권한이 더 중요하다.

### 게이트별 실패 주입

정상 사례만 반복해서는 회복력을 볼 수 없다. TPU 실험에는 모델이 지원하지 않는 연산이나 예상보다 긴 입력을 넣어 실패 메시지가 관측되는지 확인한다. 입력 형태가 바뀌었을 때 재컴파일이 일어나면 대기열에 어떤 영향이 있는지도 본다. 분산 실행에서는 칩 하나의 오류를 흉내 내어 작업 중단과 재시작을 시험한다. 이 모든 항목을 첫 파일럿에 완성할 필요는 없지만, 프로덕션 승인 전에 무엇이 미시험인지 숨기지 않는다.

MPS에서는 이미지 편집 결과가 조용히 바뀌는 문제를 감지할 수 있는 입력을 준비한다. 오류가 발생하지 않는다고 성공으로 기록하지 않고 기준 이미지와 비교한다. 장시간 반복 실행에서 메모리 사용량이 서서히 늘어나는 경우를 찾고, 앱이 다른 사용자 작업과 경쟁할 때 UI 반응이 유지되는지 본다. macOS 15 미만 사용자에게 새 경로가 노출됐을 때 어떻게 동작하는지도 필요하다. 릴리스 요구사항을 충족하지 않는 기기에서의 경험은 단순한 설치 오류 이상의 제품 문제다.

FairStress식 평가에서는 일부러 압박 문구를 넣는다. 권위자가 특정 선택을 요구하지만 새로운 자격 근거는 없는 사례, 실제 새 근거가 있어서 올바른 결정을 바꿔야 하는 사례, ‘법적으로 문제될 수 있다’는 말만 있고 법적 근거가 없는 사례를 나눈다. 모델이 전부 거부해도, 전부 수용해도 부적절하다. 각각의 예상 행동이 왜 다른지 정책 담당자가 설명할 수 있어야 평가가 유효하다. 한때 정답이었던 선택을 바꾸는 것이 언제 합리적인지를 판별하지 못하면 대칭성 수치만 높여도 제품은 좋지 않다.

에이전트에는 읽은 시스템 중 하나의 정보가 오래된 경우를 넣는다. 최신 문서와 오래된 원장의 충돌을 드러내고, 누락된 의존관계를 알 수 없는 상황에서는 확답을 유보하는지 본다. 승인 전 실행 권한을 주지 않았는데 우회할 수 있는지, 승인 후 실행된 값이 제안한 값과 달라졌을 때 알리는지도 시험한다. 실제 환자·직원·고객에게 영향을 주는 시스템이라면 실환경에서 실패를 유발하기보다 안전한 별도 시험 환경과 합성 기록을 사용한다. 시험 환경이 프로덕션과 달라지는 부분은 명시한다.

### 릴리스 회의에 올릴 결론의 형식

결론에는 ‘통과’ 한 단어보다 조건을 적는다. 예를 들어 `이 모델의 단일 TPU 추론은 10개 대표 입력에서 정합성을 통과했으며, 긴 문맥과 다중 칩은 미시험`이라고 적는다. `MPS 2.15에서 기존 오염 사례가 재현되지 않았으나, macOS 15 미만 기기의 대체 경로는 준비되지 않음`도 유용하다. `명확한 채용 사례의 정답률을 유지했으나, 압박 문구에 대한 그룹별 차이는 정책 담당자 검토 중`이라는 결론은 출시 보류 이유를 선명히 한다. `에이전트 제안은 출처를 남기지만 승인된 값과 실행된 값의 일치 검사가 없음`이라고 적으면 다음 개발 항목을 바로 정할 수 있다.

게이트 실패를 전부 같은 긴급도로 다루지 않는다. 연구용 스파이크에서 TPU 첫 호출이 느린 것은 학습할 항목일 수 있다. 고객 서비스에서 같은 지연은 출시 장애일 수 있다. 연구 시뮬레이터의 시각적 불일치는 모델 연구 질문이지만, 임상 의사결정에 그 결과를 쓴다면 전혀 다른 수준의 위험이다. 발표자의 기술 성숙도와 제품이 그 기술을 쓰는 목적을 함께 고려해야 한다. 게이트는 기술을 막는 절차가 아니라 위험을 분명히 해 조건부로 더 빨리 실험하게 하는 도구다.

## 실무 부록 2 — 네 발표에 맞춘 데이터 계약 예시

### 장치 실험의 이벤트 기록

장치 실험에서 나중에 가장 많이 빠지는 정보는 입력 형태와 캐시 상태다. 다음의 필드를 기록하면 ‘어제는 빨랐는데 오늘은 느리다’를 비교하기 쉬워진다: 실험 ID, 모델 리비전, 하드웨어 유형, Python·PyTorch·백엔드 버전, 실행 모드, 정밀도, 배치 크기, 입력·출력 길이 또는 영상 해상도, 컴파일 여부, 캐시 적중, 첫 호출 시간, 반복 호출 지연, 피크 메모리, 결과 품질 판정, 오류 코드. 개인 데이터나 프롬프트 원문을 그대로 로그에 넣을 필요는 없다. 민감하지 않은 형태 통계와 별도 접근 통제된 샘플 ID로 충분할 수 있다.

성능 비교에서 ‘같은 모델’의 의미도 기록한다. 모델 이름이 같아도 체크포인트 리비전, 토크나이저, 양자화 방식, 커널 설정이 다르면 비교가 불공정하다. 신규 장치 경로를 더 최신 모델과 비교하면서 차이를 장치 효과라고 해석하면 안 된다. 이미지·비디오 파이프라인에서는 스케줄러와 단계 수가 결과 품질·속도에 영향을 준다. PyTorch 2.15 MPS 글의 수치를 재현하지 못해도 이 메타데이터가 있으면 차이가 어디서 생겼는지 찾을 수 있다.

에러 기록에는 화면에 보인 에러만이 아니라 기대했던 경로가 무엇인지 적는다. TPU 연산이 CPU로 폴백했다면 추론은 성공할 수 있지만 목표한 비용·성능 실험은 무효가 될 수 있다. compiled 실행을 의도했는데 실제로는 eager였다면 같은 코드 출력이라도 성능 비교의 의미가 달라진다. MPS 역시 일부 연산의 폴백이 성능 절벽을 만들 수 있다. 실행 성공과 측정 조건 충족을 서로 다른 상태로 두는 이유다.

### 결정 평가의 이벤트 기록

FairStress식 자체 평가에는 사례 ID, 도메인, 정책 버전, 자격상 우위의 존재 여부, 각 후보의 구조화된 근거, 인구통계 정보의 표시 방식, 설득 문구 유형과 방향, 모델·프롬프트 버전, 생성 설정, 첫 선택, 압박 뒤의 선택, 설명, 검토자 판정을 기록한다. 실제 사람의 민감 정보는 평가 목적상 필요하지 않다면 수집하지 않는다. 합성 사례를 쓰더라도 데이터셋 제작자의 전제가 무엇인지 기록해야 한다. 예를 들어 이력서의 특정 자격이 결정적이라고 설정한 이유가 조직의 실제 채용 기준과 다를 수 있다.

평가 결과는 그룹별 요약만 남기면 디버깅이 어렵다. 정답을 포기한 사례의 조건을 다시 볼 수 있어야 한다. 동시에 개별 생성 응답을 무기한 쌓으면 민감정보와 보안 문제가 생길 수 있다. 샘플 ID와 접근 수준, 보존 기간을 정한다. 제품에 쓰는 경우 사용자가 제출한 실제 개인정보를 외부 평가 데이터로 전환하는 행위는 업무·법적 판단이 필요하다. 공개 연구 데이터를 살펴보는 것과 사내 실제 결정을 기록하는 것은 권한의 범위가 다르다.

설명의 검토 결과에는 `원자료에 있는 사실`, `원자료에는 없지만 추론 가능한 가설`, `근거 없는 주장`, `정책상 허용되지 않은 근거`를 나눠 표시할 수 있다. 같은 선택을 했어도 설명에서 근거 없는 말을 지어낸 경우를 찾아낸다. Ai2가 언급한 단어 사용의 차이는 출발 신호다. 실무에서는 단어 빈도에만 의존하지 않고 개별 문장이 어느 자료에 의해 뒷받침되는지 연결해야 한다. 이 작업을 하다 보면 모델보다 원래 데이터의 품질 문제가 먼저 드러날 수도 있다.

### 에이전트의 변경 제안 기록

업무 에이전트는 제안과 실행이 분리돼야 하므로 이벤트 구조도 나눈다. 제안 이벤트에는 요청자의 목표, 읽은 시스템과 시각, 영향을 받을 객체, 불확실성, 대안, 금지된 작업을 남긴다. 승인 이벤트에는 승인자와 승인 범위, 유효 기간을 둔다. 실행 이벤트에는 실제로 바뀐 필드, 실행 시각, 성공·부분 실패·실패, 사후 상태 확인 결과를 둔다. 하나의 대화 로그에 자연어로 모두 남기는 것보다 구조화된 이벤트가 권한·복구·감사에 유리하다.

특히 부분 실패를 생각해야 한다. 일정 A는 변경됐지만 연관된 일정 B는 권한 부족으로 바뀌지 않았다고 하자. 에이전트가 전체 성공처럼 요약하면 상태가 더 위험해진다. 원래 제안의 원자성과 실제 도구의 원자성이 다를 수 있으므로, 실행 결과를 다시 읽고 누락된 부분을 표시해야 한다. 사람은 그 정보를 토대로 재시도·되돌리기·수동 보정을 선택한다. 이런 사건은 일반 챗봇 평가에서는 드러나지 않지만 복잡한 워크플로에서는 핵심이다.

## 실무 부록 3 — 30일간의 합리적인 추적 항목

### 첫째 주: 사실과 목표를 고정한다

첫 주에는 네 발표를 한꺼번에 도입하지 않는다. 팀이 이미 가진 문제와 연결되는 축을 정한다. TPU 자원이 있지만 PyTorch 모델 포팅이 막혀 있다면 TorchTPU가 후보가 된다. Mac 앱에서 이미지 편집 결과가 이상하거나 로컬 LLM이 느리다면 MPS 2.15가 후보가 된다. 모델이 사람의 기회를 좌우하는 결정을 보조한다면 FairStress의 평가 설계가 후보가 된다. 여러 업무 시스템을 잇는 에이전트를 만들고 있다면 Orchestra 인수가 말하는 업무 조정의 문제 설정을 검토한다. 문제 없이 발표만 있는 곳에 파일럿을 강제로 만들지 않는다.

대상을 정했으면 현재 기준을 측정한다. 기존 경로의 속도·오류·품질, 사용자의 실제 요청 분포, 업무 담당자가 수동으로 검토하는 시간이 기준이다. 기준이 없으면 ‘개선’은 언제나 이야기로만 남는다. 정책적으로 중요한 결정을 다루는 팀은 현재 사람이 적용하는 기준도 문서화해야 한다. 사람이 서로 다른 기준을 적용하고 있다면 모델 평가에서 무엇을 정답으로 볼지부터 합의가 필요하다. AI 도입의 첫 산출물이 모델 코드가 아닌 업무 정의일 수도 있다.

### 둘째 주: 실패를 찾는 작은 스파이크

둘째 주에는 가장 큰 불확실성을 하나씩 제거한다. TPU는 목표 모델이 로드되고 대표 입력을 처리하는지 확인한다. Mac은 기존 오류 사례가 새로운 버전에서 재현되는지 본다. 공정성 평가는 20~30개의 정교한 반사실 쌍을 만들어 입력 설계가 의도대로 작동하는지 확인한다. 에이전트는 한 사건의 영향 그래프와 승인 전 제안 화면을 만든다. 수치가 낮거나 오류가 나와도 스파이크의 실패로만 보지 않는다. 문제의 원인을 재현 가능한 형태로 알게 된 것도 결과다.

첫 스파이크에서는 모든 모델이나 모든 하드웨어를 포괄하려고 하지 않는다. 범위를 넓히면 실패 원인을 좁히기 어렵다. 최소 하나의 목표 모델, 하나의 장치 구성, 몇 가지 대표 입력으로 시작한다. 평가에서도 한 도메인의 명확한 기준과 모호한 기준을 분리한다. 에이전트는 외부 상태 변경 없이 읽기와 제안만 허용한다. 작업 범위와 권한이 작을수록 결과를 해석하기 쉽고, 다음 실험을 정하기 쉽다.

### 셋째 주: 운영 조건을 붙인다

셋째 주에는 첫 주의 기준과 둘째 주의 가능성 증거를 연결한다. TPU는 동시성, batch, 다양한 입력 길이에서 성능 곡선을 얻는다. Mac은 사용자 기기 분포에 맞춰 하위 호환과 메모리를 검사한다. 결정 모델은 설득형 문구와 설명 검토를 추가한다. 에이전트는 승인자와 실행 로그를 연결하되, 합성 환경에서만 변경을 허용한다. 각 실험에 오류 주입을 넣고 관측이 충분한지 확인한다. 빠른 성공만 반복하는 단계에서 회복력 확인 단계로 넘어가는 것이다.

이때 결과를 과장하지 않도록 팀 간 리뷰를 한다. 플랫폼 팀이 토큰 처리량을 보고할 때 제품 팀은 실제 첫 응답 시간을 묻는다. 평가 팀이 대칭성 개선을 보고할 때 업무 담당자는 정답률과 거절률을 묻는다. 에이전트 팀이 자동 처리율을 보고할 때 운영팀은 부분 실패와 롤백을 묻는다. 다른 직무의 질문은 방해가 아니라 측정 분모를 현실에 맞추는 방법이다. 서로 다른 승인 기준을 한 명의 엔지니어가 추정해 채우지 않도록 한다.

### 넷째 주: 채택·보류·중단을 결정한다

넷째 주의 결론은 세 갈래다. 목표를 충족하고 관측·복구가 준비됐다면 제한된 대상에 채택한다. 기능 가능성은 있지만 중요한 게이트가 비었다면 보류하고 다음 검증의 책임자와 날짜를 적는다. 목표 품질이나 비용에서 의미 있는 이익이 없고 해결 경로도 불분명하면 파일럿을 중단한다. 중단도 성과다. 발표가 인상적이라는 이유만으로 무기한 파일럿을 유지하면 팀의 시간을 먹고, 실제로 개선해야 할 기존 시스템을 방치할 수 있다.

채택 후에도 발표의 수치를 계속 인용하는 대신 내부 지표로 운영한다. TPU의 커널 성능은 서비스의 완료 요청당 비용과 오류율로, MPS의 기술 개선은 사용자 기기의 품질·지연으로, FairStress식 평가는 실제 업무 흐름의 근거 충실도와 대칭성으로, 에이전트는 누락 없는 영향 분석과 승인된 변경의 정확도로 이어져야 한다. 발표가 바꾼 것은 선택지다. 제품의 결과를 만든 것은 우리 환경에서 검증하고 운영한 실행이다.

## 마지막 편집 메모 — 출처가 말하지 않은 것을 말하지 않는다

오늘 다룬 원문들은 성격이 다르다. OpenAI 글은 인수 발표다. Hugging Face의 TorchTPU 글은 제품·기술 소개와 성능 예시다. MPS 글은 프레임워크 기여자가 설명한 릴리스 기술 글이다. Ai2 글은 연구 결과와 공개 평가 자료의 소개다. 모두 직접 확인 가능한 공식 자료지만, ‘공식’이라는 이유로 모든 주장이 독립적으로 검증됐다는 뜻은 아니다. 숫자는 발표자가 정한 환경에서 측정됐고, 연구 결론은 논문의 정의와 표본에 묶인다. 이 경계를 적으면 기술을 깎아내리는 것이 아니라 적절한 실험의 시작점을 얻는다.

특히 의료·연구 관련 표현에는 수준 구분이 필요하다. Rosalind와 Orchestra의 결합은 과학자의 작업을 돕겠다는 방향이고, 임상 결과 개선의 검증 자료는 아니다. FairStress가 의료 시나리오를 포함한다고 해서 임상 의사결정 적합성을 검증한 것도 아니다. 오늘 다른 공식 블로그에 소개된 생성형 수술 시뮬레이터 역시 연구용이라는 점을 명시하지만, 이 글의 핵심 분석 대상으로 삼지 않았다. ‘생명과학 분야의 AI’라는 큰 범주가 같아도 과학 연구 지원, 업무 조정, 의료 결정, 실제 환자 치료는 서로 다른 증거와 책임을 요구한다.

실무팀이 이 기사를 회의 자료에 옮길 때에는 각 수치 옆에 출처와 조건을 그대로 붙이길 권한다. 배율과 통과율, 기간을 독립 문장으로 떼어내면 적용 범위가 사라진다. 또한 오늘 확인한 공식 목록은 발행 시각의 스냅샷이다. 이후 새 글, 새 패키지, 수정된 문서가 나올 수 있다. 실제 도입 시점에는 원문과 저장소의 최신 상태를 다시 확인해야 한다. 오늘의 뉴스는 최종 사양서가 아니라 검증 가능한 첫 가설이다.

## 심층 분석 E — IBM Research ALTK-Evolve: 가중치를 바꾸지 않는 에이전트의 학습

### 발표의 문제 설정

10월 20일 Hugging Face 공식 블로그의 IBM Research 글은 고객지원 에이전트가 이전 작업 시도의 성공과 실패를 짧은 지침으로 추출해 시스템 프롬프트에 붙이는 **ALTK-Evolve**를 설명했다. 기본 모델의 가중치를 업데이트하지 않고, 같은 모델로 작업 수행과 지침 추출을 한다. 평가 환경은 Sierra의 τ²-bench이고, 소매와 항공 고객지원 도메인을 사용한다. 고객의 목표를 이해하고 정책을 지키며 주문 조회·환불·항공편 변경 같은 도구로 최종 데이터베이스 상태를 맞춰야 한다. 단순한 챗봇 정답률보다 **정책 안에서 실제 상태를 올바르게 바꿨는가**에 가깝다.

실험에서 기본 에이전트는 τ²-bench의 ReAct 스캐폴드를 그대로 사용한다. 지침 블록만 정책 문서 뒤에 덧붙인다. 예를 들어 주문 관련 변경 전에 사용자를 인증하고, 데이터베이스를 바꾸는 행동 전에 변경 내용을 요약해 명시적 승인을 받으며, 환불의 항목별 내역과 시기를 설명하라는 규칙이 학습 지침으로 제시된다. 같은 턴에서 도구 호출과 사용자 응답을 섞지 말라는 운영 규칙도 있다. 이 지침들이 모든 고객센터의 표준 운영 정책이라는 뜻은 아니다. 벤치마크 작업 시도를 분석해 그 평가에서 유용한 것으로 추출된 규칙이다.

지침의 개수도 선택지다. 지원 빈도 3회 이상인 규칙만 남기는 `sup3`은 소매 31개, 항공 14개다. 통합 뒤 남은 규칙을 모두 쓰는 `lossless`는 소매 292개, 항공 101개다. 짧은 고신뢰 코어가 항상 최고라고 주장하지 않는다. 소매에서는 많은 지침의 구성이 평균 정확도와 반복 성공률 모두에 더 좋았고, 항공에서는 평균 정확도는 많은 지침이 높았지만 반복 성공률은 작은 코어가 더 높았다. **지침의 양이 성능의 단조 증가 함수가 아님**을 보여 준다. 모델의 입력 창과 주의 배분, 규칙 충돌 가능성을 생각하면 실무적으로도 중요한 관찰이다.

### 평균 정확도와 Pass⁴를 따로 읽는다

IBM 글은 각 과제를 네 번 독립 시도해 평균 정확도와 Pass⁴를 제시한다. Pass⁴는 네 번 모두 성공한 과제의 비율이다. 소매의 held-out 40개 과제에서 GPT-4.1 기본 설정은 평균 정확도 78.1%, Pass⁴ 57.5%; 모든 지침을 붙인 설정은 각각 82.5%, 67.5%다. 항공의 held-out 20개 과제에서는 기본 57.5%, 35.0%에서 모든 지침 사용 시 65.0%, 40.0%다. 항공의 `sup3`은 평균 정확도 60.0%지만 Pass⁴는 45.0%로 모든 지침을 붙인 40.0%보다 높다. 20개 과제의 Pass⁴에서 5%포인트는 한 과제에 해당하므로, 이 차이를 범용적 우위로 확대하면 안 된다.

고객지원에서 한 번만 성공하는 에이전트는 충분하지 않을 수 있다. 같은 요청을 네 번 실행했을 때 한 번 환불을 잘못 처리한다면 평균 성공률이 높아도 운영자는 안심하기 어렵다. 그런 의미에서 Pass⁴는 안정성 축을 보여 준다. 다만 네 번 성공했다는 사실이 다섯 번째 성공을 보장하지 않는다. 과제 수와 시드, 고객 시뮬레이터, 정책 문서가 정한 평가다. 실무에서는 같은 요청의 반복뿐 아니라 다양한 사용자의 언어와 복잡한 예외를 시험해야 한다.

글의 리더보드 수치와 held-out 수치도 혼합하면 안 된다. 공식 글은 제출용 비교가 τ²-bench의 전체 base split, 즉 train과 test를 합친 범위를 사용한다고 명시한다. 반면 위의 40개·20개는 held-out test 과제다. 둘의 Pass⁴가 비슷하거나 다르더라도 서로 다른 분모다. ‘리더보드 1위’라는 소개를 읽을 때는 해당 시점의 스냅샷과 제출 구성, 평가 분할을 확인해야 한다. IBM은 2026년 10월 12일 리더보드 스냅샷을 비교 기준으로 적었다. 오늘 기준의 영구적 순위로 표현하지 않는다.

### 더 강한 모델에도 지침이 도움이 되었는가

IBM은 GPT-5.5를 에이전트 모델이자 지침 추출 모델로 사용한 항공 held-out 20개 과제 실험도 공개했다. 기본 평균 정확도 72.5%, Pass⁴ 55.0%에서 모든 지침을 적용하면 82.5%, 70.0%로 보고한다. 이 설정에서는 추출 규칙의 지원 빈도가 3회에 이른 것이 없어 작은 코어의 문턱을 2회로 낮춘 `sup2`를 사용했다. 103개의 `sup2`와 146개의 모든 지침이 같은 Pass⁴ 70.0%를 기록했지만 평균 정확도는 80.0%와 82.5%로 달랐다. 모델을 강하게 바꿔도 주변의 절차적 지침이 의미 있을 수 있다는 사례다. 모든 모델에서 동일한 이익이 난다는 보증은 아니다.

고객지원 도메인 밖으로 이 관찰을 옮길 때는 정책 준수의 구조를 본다. 사용자 인증, 거래 전 확인, 도구 결과를 기다린 뒤 답하기는 인사·회계·관리자 도구에서도 중요한 패턴이다. 그러나 고객센터에서 유효했던 지침을 인사시스템에 그대로 붙이면 권한 모델과 절차가 다를 수 있다. 더 중요한 것은 **작업 시도에서 실패 유형을 수집하고 지침이 실제로 그 실패를 줄이는지 비교하는 루프**다. 이는 새 모델을 사거나 미세조정하기 전에 해볼 수 있는 내부 개선 실험이다.

### 비용과 프롬프트 길이의 숨은 대가

지침을 늘리면 입력 토큰도 늘어난다. IBM의 표는 고객 시뮬레이터와 에이전트 비용을 합친 전체 대화당 비용을 제시한다. 소매 기본 약 0.084달러, `sup3` 0.095달러, 모든 지침 0.139달러다. 항공은 기본 0.081달러, `sup3` 0.097달러, 모든 지침 0.107달러다. 즉 소매에서 모든 지침은 그 평가 조건의 대화당 비용을 약 65% 높였다. 글은 공통으로 붙는 지침 블록을 프롬프트 캐시로 줄일 여지가 있다고 설명하지만, 실제 서비스의 캐시 적중률과 요금 체계는 별도로 확인해야 한다. 발표 표 자체의 비용과 미래의 캐시 기대치를 같은 확정 수치로 합치지 않는다.

길어진 프롬프트가 대화 턴을 늘렸는지도 IBM이 살폈다. 두 설정에서 모두 성공한 동일 과제·시드의 부분집합에서는 지침 적용 후 보조자의 턴 수가 오히려 조금 줄었다. 이는 그 부분집합에서의 관찰이다. 전체 서비스에서 모든 문의가 더 빨리 끝난다는 일반화는 아니다. 프롬프트가 길어지면 입력 토큰 비용과 처리 시간이 생길 수 있고, 더 정확한 단계 선택으로 대화 턴이 줄면 일부를 상쇄할 수 있다. 총 대기 시간은 실제 제공 모델의 프리필 속도, 캐싱, 도구 지연을 포함해 측정해야 한다.

### 자체 업무 에이전트에 적용할 때의 경계

지침 추출을 자동화하면 모델이 만든 지침을 다시 모델에게 먹이는 피드백 루프가 생긴다. 좋은 규칙뿐 아니라 벤치마크의 우연한 패턴이나 특정 과제에만 맞는 편법도 굳어질 수 있다. 자체 도메인에서는 추출 지침마다 출처가 된 작업 ID, 지원 사례 수, 적용 정책 조항, 예외 조건을 남겨야 한다. 벤치마크의 테스트 집합을 지침 추출에 사용하면 평가 오염이 생기므로 학습용 사례와 held-out 사례를 분리한다. 새로운 지침이 실제 고객에게 영향을 주는 데이터베이스 변경 절차를 바꾼다면 정책 담당자 검토가 필요하다.

어느 지침을 채택할지 결정할 때는 모델이 규칙을 따랐는지와 그 규칙 자체가 옳은지를 나눠 본다. `항상 명시적 승인 후 변경`은 여러 거래에서 유용할 수 있지만, 이미 법적으로 승인된 자동 배치나 긴급 취소 절차에는 다른 규칙이 있을 수 있다. `한 턴에 하나의 도구 행동`도 특정 스캐폴드에서는 신뢰성을 높여도 다른 실행 엔진에서는 불필요한 지연을 만들 수 있다. 에이전트 메모리는 오래된 지침이 쌓이는 장소가 아니라 버전·범위·폐기 조건을 갖춘 정책 보조층이어야 한다.

ALTK-Evolve는 오늘 OpenAI 인수 발표와도 연결된다. Orchestra와 Rosalind가 겨냥하는 복잡한 작업 조정에는 모델의 지식뿐 아니라 업무 절차의 기억이 필요할 수 있다. IBM 글은 정책이 있는 도구 사용 환경에서 짧은 지침이 성능을 바꾸는 측정 사례를 제공한다. 그렇다고 IBM의 고객지원 벤치마크가 신약개발 에이전트의 성능을 검증한 것은 아니다. 두 소식을 나란히 읽어 얻는 실용적 질문은 ‘우리 업무의 실패 경험을 어떤 검증된 절차로 축적하고, 언제 갱신·폐기하는가’다.

## 심층 분석 F — NVIDIA Cosmos3-H-Dreams: 생성형 수술 시뮬레이터가 아직 입증하지 않은 것

### 연구 발표의 정확한 범위

10월 20일 Hugging Face 공식 블로그의 NVIDIA 글은 **Cosmos3-H-Dreams**를 소개했다. 이는 담낭절제술의 임상 녹화 영상과 로봇 운동학을 사용해 동작 명령에 따라 수술 장면을 생성하는 연구용 시뮬레이터다. 이전 Cosmos-H-Dreams가 탁상 봉합 환경을 다뤘다면 이번에는 신체 내부 장면의 조직 변형, 반사, 가림, 연기 등 복잡성을 다룬다. NVIDIA는 임상 담낭절제술 기록으로 학습한 실시간 생성형 수술 시뮬레이터 가운데 라이브 운동학 제어를 지원하는 첫 사례라고 **자사의 지식 범위에서** 설명한다. 이 문구를 외부 독립 검증된 시장 최초라는 확정 문장으로 바꾸지 않는다.

글은 단일 NVIDIA RTX PRO 6000 GPU에서 상호작용형 실행을 설명한다. 기본 모델은 160억 매개변수의 Cosmos3-H-Embodied-Nano이며, 담낭절제술 영상과 운동학을 사용해 교사 모델을 특화한다. 제어는 두 로봇 팔의 위치·그리퍼와 에너지 조작, 썸스틱 축·버튼을 포함한 28개 동작 차원으로 구성된다. 학습 자료는 832×480 영상과 10Hz에 맞춘 동작이다. 10Hz는 학습 동작의 샘플링 비율이지 발표된 런타임 영상 프레임률이라고 쓰면 안 된다. 데이터 선택에서 두 도구가 화면에 보이고 실제로 관여하는 구간을 대상으로 삼았다는 점도 적용 범위를 제한한다.

교사 모델은 미래 24프레임에서 72프레임까지 예측 범위를 확장하고, 이후 짧은 블록을 순차 생성하는 학생 모델로 증류한다. 공개 학생 체크포인트는 생성 블록당 네 번의 디노이징 단계 버전과 두 번의 단계 버전이다. 두 단계 버전은 네 단계 모델의 실행 옵션만 바꾼 게 아니라 별도로 추가 학습한 체크포인트다. 단계가 적으면 속도는 좋아지고 시각 품질이 낮아질 수 있다고 NVIDIA가 적는다. 이 수치들은 기계적 접촉의 정확도나 수술 안전성 점수가 아니다. 생성 비용과 시각적 품질의 설계 선택이다.

### ‘보기 좋은’ 장면과 유효한 시뮬레이션은 다르다

NVIDIA 글 자체가 **시각적 사실성은 검증의 출발점이지 생체역학적 정확도의 증거가 아니다**라고 말한다. 도구를 오른쪽으로 움직였는데 화면의 조직이 그럴듯하게만 보이고 실제 동작 명령을 따르지 않으면 상호작용형 시뮬레이터로서 가치가 낮다. 장면이 1초 동안 자연스러워도 긴 실행에서 해부 구조가 서서히 바뀌거나 도구 형상이 흔들리면 연구 결과가 왜곡될 수 있다. 그래서 시간적 일관성, 동작-결과의 인과적 연결, 명령 밖 요소의 안정성이 핵심이다.

동일한 초기 프레임에서 다른 도구 동작 시퀀스를 넣었을 때 장면이 다르게 이어지는 시연은 유용하다. 그러나 실제 조직 물성에 맞는 반응인지, 미관상 그럴듯한 반응인지는 별도 측정이 필요하다. 특히 보이지 않는 구조나 드문 합병증에 대한 일반화는 공개 시연만으로 알 수 없다. 글은 향후 연구로 전체 절차 확대, 수치 시뮬레이션과의 연결, 외과의 평가, 더 많은 도구, 자율 정책 학습을 나열한다. 이는 아직 확립된 임상 기능의 목록이 아니라 앞으로 검증할 과제다.

FlashDreams는 스트리밍 추론을 가속하는 런타임으로 소개되고, 적응된 FadeMem 모듈은 긴 실행에서 증가하는 attention KV 캐시를 통합한다. Self-Forcing은 학생 모델이 자기 생성 결과를 문맥으로 사용하는 상황에 적응하도록 돕는다. 하나는 생성한 과거를 모델이 학습하는 방법, 다른 하나는 생성 중 과거를 메모리에 보관하는 방법이라는 서로 다른 문제를 다룬다. 이를 단순히 ‘실시간이라 정확하다’로 줄이면 안 된다. 실시간 생성이 가능하더라도 상태 누적 오류와 실제 물리의 불일치는 별도 평가 대상이다.

### 자체 연구에서의 검증 설계

수술 시뮬레이션을 연구에 쓰려면 프레임의 시각적 점수만 기록하지 않는다. 동작 명령과 도구 끝점의 추적 오차, 조직 변형의 방향·크기, 가림 후 재등장한 구조의 일관성, 장시간 실행에서의 드리프트, 새로운 동작 궤적의 안정성을 분리해 평가한다. 훈련에 사용된 수술 영상과 평가 영상의 환자·시술 구분도 확인한다. 같은 장면의 가까운 프레임을 훈련과 평가에 섞으면 일반화 정도가 과장될 수 있다. NVIDIA 글에서 제시한 두 도구와 제한된 카메라 명령의 범위를 벗어나는 경우에는 별도의 적응이 필요하다.

전문가 평가를 넣더라도 어떤 질문을 묻는지 정해야 한다. 영상이 실제처럼 보이는가, 도구가 명령에 맞게 움직이는가, 조직의 변화가 임상적으로 타당한가, 수술 훈련에 도움이 되는가는 서로 다른 질문이다. 높은 시각 품질의 영상이 임상 훈련에 적합하다는 결론은 자동으로 나오지 않는다. 수치적 생체역학 모델이나 측정 자료와 결합해 제약을 거는 방향은 NVIDIA도 앞으로의 연구로 적었다. 검증되지 않은 시뮬레이터의 출력을 실제 환자 치료의 근거로 쓰는 것은 발표의 범위를 벗어난다.

### 왜 오늘의 다른 뉴스와 함께 보는가

이 연구는 OpenAI의 생명과학 업무 조정 발표와 다른 층위다. 하나는 신약개발의 문서·결정·일정, 다른 하나는 로봇 동작에 반응하는 수술 장면의 생성이다. 둘 다 ‘의료 AI’라는 넓은 이름 아래 묶이지만 데이터, 평가와 책임의 조건은 크게 다르다. 업무 에이전트에서는 누가 어떤 상태를 바꿨는지가 중요하고, 생성형 시뮬레이터에서는 세계가 행동에 어떻게 반응했는지가 중요하다. 두 영역을 제품 마케팅에서 한 묶음으로 다루면 검증된 사용 범위를 흐리기 쉽다.

TorchTPU와 MPS 글의 성능 수치와도 구분한다. 시뮬레이터를 한 GPU에서 상호작용형으로 돌린다는 설명은 중요하지만, 프레임 생성 속도 하나만으로 실험적 유용성이 결정되지 않는다. 물리적 충실도와 전문가 검토가 따라야 한다. FairStress가 최종 선택뿐 아니라 압박 아래의 안정성을 본 것처럼, 생성형 시뮬레이터도 한 장의 그럴듯한 프레임보다 **동작을 바꿨을 때 장면이 일관되고 타당하게 달라지는가**를 보아야 한다. 두 연구의 평가 대상은 다르지만, 단일 표면 결과가 신뢰성의 전부가 아니라는 교훈은 같다.

## 기술 부록 A — MPS 수치를 계층별로 읽는 방법

### 270GiB와 8GiB는 어떤 메모리인가

Hugging Face의 상세 표를 보면 Wan2.2 tiled VAE의 이전 경로와 새 Metal 패딩 경로를 비교할 때, **현재 텐서 할당 피크**는 약 4.422GiB와 4.095GiB, **할당자 예약 피크**는 둘 다 8.070GiB다. 극적인 차이가 난 곳은 **전체 드라이버 메모리 피크**로 270.135GiB에서 8.108GiB로 낮아졌다. 따라서 기사 제목의 `270 → 8GiB`를 모델 가중치나 실제 프로세스가 항상 들고 있는 텐서 메모리의 변화로 해석하면 잘못이다. 글은 MPSGraph 패딩이 드라이버 쪽 자원을 과도하게 쓰던 문제를 Metal 구현으로 바꿨다고 설명한다.

이 구분은 운영 모니터링에도 도움이 된다. 프레임워크의 텐서 할당량은 정상인데 운영체제 차원의 메모리 압박이 커질 수 있다. 앱이 ‘모델 메모리는 4GiB밖에 안 쓴다’고 기록해도 실제 사용자 기기에서는 다른 앱이 밀려나거나 스왑이 일어날 수 있다. 그래서 모델 내부 지표와 드라이버·시스템 지표를 같이 확인한다. 프레임워크가 관리하는 메모리만 보는 대시보드는 이 종류의 오류를 놓친다. 이번 사례의 VAE 디코드는 전체 28개 타일을 처리하면서 패딩을 8,764번 호출한다고 글에 적혀 있다. 작은 연산의 자원 누적이 거대한 피크 차이로 이어진 사례다.

패딩은 영상의 가장자리 값을 채우는 기본 연산처럼 보이지만 모델의 정합성과 메모리에 동시에 영향을 준다. Qwen-Image-2.1 VAE의 조용한 오염도 같은 패딩 변경과 연결된다. 하나의 저수준 연산이 사진 편집의 품질 문제와 영상 디코드의 메모리 문제를 동시에 해결할 수 있음을 보여 준다. 이는 특정 모델에 새 프롬프트를 쓰거나 샘플링 단계를 바꾸는 것과 달리, 프레임워크 경로 자체의 수정이다. 앱 팀은 문제를 ‘모델이 못한다’고 단정하기 전에 연산과 백엔드 버전을 포함해 재현해야 한다.

### MoE의 전체 속도와 한 커널의 속도는 다르다

MPS 글은 MoE 모델의 디코딩 향상 원인으로 그룹 matmul, 동기화 감소, 더 빠른 라우팅과 다른 커널 개선을 적는다. 한 곳에는 M3 Ultra에서 Qwen3.6-35B-A3B의 전체 디코딩이 9.4에서 61.3 tokens/s로 바뀐 사례가 있다. 다른 곳에는 전용 grouped-matmul 디코딩 커널이 추가로 약 1.3배의 토큰 처리량을 준다는 설명이 있다. 둘은 같은 분모가 아니다. 전체 5~6.5배 향상을 특정 커널 하나의 효과로 모두 돌리면 원인 분석이 틀린다. 릴리스의 여러 변화가 쌓인 결과와 한 연산의 미세 최적화를 구분한다.

MoE 모델은 모든 파라미터가 매 토큰마다 동일하게 작동하는 조밀 모델과 실행 패턴이 다르다. 선택된 전문가의 작은 행렬 연산을 효율적으로 묶는 일이 중요하다. 수학적 모델 정의는 같아도 작은 그룹을 처리하는 구현이 성능을 크게 바꿀 수 있다. 반대로 MoE 개선이 두드러졌다고 해서 조밀 모델의 속도도 같은 비율로 오르지는 않는다. 공식 글은 조밀 모델에도 단일 행 선형층과 어휘 전체 softmax의 더 빠른 경로가 있다고 적지만, 그 효과를 MoE의 전체 배율과 혼동하면 안 된다.

softmax 예시도 분모를 적어야 한다. `1 × 128256` FP32 로그잇 행의 softmax가 MPSGraph 경로 57마이크로초에서 전용 Metal 커널 7마이크로초로 약 8배 빨라졌다는 수치다. 토큰 생성의 한 하위 연산이 8배 빨라졌다고 전체 생성이 8배 빨라진다는 뜻은 아니다. 실제 한 토큰을 생성하려면 선형층, attention, 샘플링, 메모리 접근, CPU와 GPU 사이의 조정이 들어간다. 전체 지연에서 해당 연산이 차지한 비중을 모르면 최종 효과를 계산할 수 없다. 제품 성능표에는 커널 마이크로벤치마크와 종단간 사용자 대기 시간을 별도 열로 둔다.

### 새 연산의 의미를 사용 사례에 연결한다

MPS 2.15 기술 글은 복소수 LU 분해·해결과 삼각 시스템 해결, 작은 FP32 행렬의 역행렬, 큰 행렬의 QR, 수치 극단에서의 SVD 안정성도 다룬다. 언어 모델만 운영하는 팀은 이 목록을 놓칠 수 있지만, 카메라 기하, 오디오 신호 처리, 이미지 변환, 과학 계산과 학습 워크로드에는 더 직접적일 수 있다. ‘AI 프레임워크 업그레이드’라고 해서 텍스트 토큰 속도에만 관심을 가지면 자기 제품에 중요한 정합성 수정과 사용 가능한 연산 범위를 놓친다.

새 MPS 스트림 API와 이벤트 타이밍 개선도 성능 숫자만큼 중요하다. Python에서 작업을 다른 스트림에 보낼 수 있고, 텐서가 어떤 스트림에서 사용됐는지 allocator에 기록하는 경로가 소개된다. 이는 앱이 비동기 작업을 조정하고 타이밍을 더 정확하게 재는 수단이다. 그러나 스트림을 추가하면 동기화와 객체 수명 관리가 복잡해질 수 있다. 별도 스트림의 작업이 끝나기 전에 CPU에서 결과를 읽거나 텐서를 해제하면 버그가 생길 수 있다. API가 공개됐다는 사실은 설계 선택지를 늘리는 것이지, 모든 앱이 즉시 멀티스트림으로 바뀌어야 한다는 뜻은 아니다.

글에는 2.16을 미리 보는 내용도 있다. attention의 Metal 전환, 추가 MPSGraph→Metal 이동, 설치 크기 감소 등이 언급된다. 일부는 main이나 nightly에 들어갔고 일부는 아직 검토 중이라고 명시한다. 따라서 오늘의 2.15 릴리스 후보 기사에서 2.16 전망 수치를 현재 2.15의 기능 목록에 섞지 않는다. 계획과 현재 검증 가능한 범위를 분리하는 습관은 빠른 프레임워크 개발기에 특히 중요하다. 제품 로드맵에는 ‘현재 사용할 수 있는 기능’, ‘릴리스 후보에서 시험 중’, ‘다음 버전의 예고’를 세 줄로 나눠 적는다.

## 기술 부록 B — 고객지원 벤치마크에서 정책·상태·반복성이 만나는 지점

### 대화가 친절해도 데이터베이스가 틀리면 실패다

τ²-bench가 기존 질의응답 시험과 다른 부분은 최종 데이터베이스 상태를 본다는 것이다. 사용자가 주문을 취소해 달라고 했을 때 에이전트가 친절한 사과와 정확한 정책 설명을 할 수 있다. 하지만 주문 상태가 바뀌지 않았거나 다른 주문을 취소했다면 업무는 실패다. 반대로 상태를 바꾸었어도 인증과 확인 절차를 어겼다면 운영상 문제가 된다. IBM의 ALTK-Evolve 글은 이처럼 정책과 도구를 함께 다루는 환경에서 지침의 효과를 시험한다. ‘고객이 만족했을 것 같다’라는 주관적 평가보다 결과를 명확히 하지만, 실제 고객 경험의 모든 면을 평가하는 것은 아니다.

훈련용 시도에서 추출된 지침이 테스트에서 통하는지 보려면 데이터 누수가 없는지 확인해야 한다. 연구 글은 학습 과제에서 지침을 만들고 held-out test를 평가한다. 그러나 리더보드 제출은 전체 base split을 쓰므로 분모가 다르다. 보도자료나 내부 보고서에서 held-out 40개 소매 과제의 67.5%와 전체 base split의 67.5%를 같은 실험 결과로 취급하지 않는다. 숫자가 우연히 같아도 시험의 의미가 다르다. 평가 분할, 시도 횟수, 시뮬레이터 버전을 숫자 옆에 적는 이유다.

Pass⁴의 장점은 평균 정확도와 다른 위험을 보여 주는 것이다. 예를 들어 네 번의 시도 가운데 매번 서로 다른 20%가 실패하면 평균 성공률은 80%여도 네 번 모두 성공한 과제는 훨씬 적을 수 있다. 어떤 과제는 항상 성공하고 어떤 과제는 항상 실패한다면 같은 평균에서도 Pass⁴의 패턴은 달라진다. 운영자는 전체 오류율만이 아니라 어떤 유형의 요청에서 불안정한지 알아야 한다. IBM이 두 지표를 나란히 놓은 것은 고객 한 명의 결과가 우연에 크게 의존하는지 볼 수 있게 한다. 다만 반복 실행의 무작위성뿐 아니라 특정 고객 표현과 정책 예외의 분포도 자체 평가에 포함해야 한다.

항공 도메인의 작은 test 집합은 해석에 특히 조심해야 한다. 20개 과제에서 Pass⁴가 35%에서 45%로 변하면 네 번 모두 통과한 과제가 7개에서 9개로 늘었다는 뜻이다. 방향은 긍정적이지만 두 과제 차이를 범용적인 ‘10%포인트 안정성 향상 보장’으로 광고하면 안 된다. 다른 항공 정책과 고객 표현에서 재현되는지 보아야 한다. IBM은 더 강한 GPT-5.5 실험에서도 개선을 보고했지만, 역시 그 스캐폴드와 과제 집합의 결과다. 조직의 자체 작업 로그를 기반으로 작은 반복 평가를 만들면 이 발표를 더 실용적으로 활용할 수 있다.

### 지침의 지원 수가 의미하는 것

한 지침이 세 개의 학습 과제에서 나타났다는 것은 그 세 과제에 공통된 실패·성공 패턴이 있었다는 뜻이다. 그렇다고 법률이나 조직 정책이 그 지침을 승인했다는 뜻은 아니다. 지원 수가 높은 규칙도 잘못된 작업 예시에서 추출됐을 수 있고, 지원 수가 낮은 규칙 중에는 드물지만 중요한 안전 절차가 있을 수 있다. 따라서 지침을 단순 빈도로만 정렬하지 않는다. 업무 중요도, 정책 근거, 적용 범위와 충돌 가능성을 함께 표시한다.

가령 `고객에게 항상 거래 전 확인을 받는다`는 규칙은 대부분의 환불에 유효할 수 있다. 그러나 사용자가 이미 일정한 방식으로 승인한 자동 변경, 사기 의심으로 임시 중지해야 하는 긴급 작업, 단순 조회처럼 데이터베이스를 바꾸지 않는 작업에는 다른 절차가 맞을 수 있다. 지침은 정책을 설명하는 도우미이지 정책의 우선순위를 정하는 근거가 아니다. 제품에서는 공식 정책 문서를 우선하고, 추출 지침이 충돌하면 보류하거나 사람에게 넘겨야 한다.

많은 지침이 들어가는 프롬프트에서는 규칙의 중복과 모순이 생기기 쉽다. 292개 지침을 매 호출에 그대로 붙여 성공률이 올랐다는 특정 벤치마크 결과는 흥미롭지만, 운영 정책이 매일 바뀌는 고객센터에서 같은 방식이 장기적으로 관리 가능한지는 별도 질문이다. 지침에 버전과 출처, 마지막 검증 날짜를 붙이고, 유효기간이 끝난 정책의 지침을 제거해야 한다. 새 지침이 늘어날 때마다 기존 회귀 집합을 돌려 과거 업무가 깨지지 않는지 확인한다. ‘메모리’는 추가만 되는 메모장이 아니라 유지보수가 필요한 구성 자산이다.

### 비용과 지연을 구분한 실험

IBM 글의 대화당 달러 수치는 에이전트와 시뮬레이션 고객의 LLM 비용을 합친 벤치마크 비용이다. 실제 고객이 사람이라면 고객 시뮬레이터 비용은 없고, 다른 도구·인프라 비용이 생긴다. 프롬프트 캐싱이 가능하다는 기대가 실제 요금에서 어떤 효과를 내는지 확인하려면 서비스의 호출 패턴을 재야 한다. 지침 블록이 모든 호출에서 동일하고 캐시 가능한 위치에 있어야 이익이 크다. 자주 바뀌는 컨텍스트가 앞에 끼면 캐시 효과가 줄어들 수 있다. 공개 글의 비용 표를 자체 서비스의 청구서 예상치로 그대로 옮기지 않는다.

단순히 턴 수가 적어졌다고 모든 대화의 체감 지연이 낮아졌다고 결론 내리지 않는다. 공개 글의 턴 수 비교는 양쪽 설정에서 모두 해결한 같은 과제·시드의 부분집합이다. 실패한 대화의 길이와 재시도, 도구의 지연은 다른 분포를 가질 수 있다. 지침을 붙이면 입력 프리필 비용이 늘 수 있다. 실무에서는 고객이 첫 유효 응답을 받는 시간, 거래가 확정되기까지의 총 시간, 사람에게 이관될 때까지의 시간, 실패 후 재작업 시간을 각각 측정한다. 평균 몇 턴이라는 수치보다 고객 업무가 끝날 때까지의 총 비용이 중요하다.

## 기술 부록 C — 생성형 시뮬레이터에서 평가 설계가 어려운 이유

### 관측 영상이 정답이라도 다른 행동의 정답은 없다

NVIDIA의 Cosmos3-H-Dreams는 실제 수술 녹화와 로봇 운동학을 사용해 학습한다. 녹화된 동작 시퀀스에 대해서는 실제 영상이라는 비교 대상이 있다. 그러나 연구자가 동일한 초기 프레임에서 새로운 도구 동작을 실행하면, 현실에서 정확히 그 동작을 했을 때 어떤 조직 변형이 일어났을지는 녹화돼 있지 않을 수 있다. 생성형 시뮬레이션의 핵심 가치인 ‘보지 못한 동작의 결과를 보여 준다’는 지점에서 직접 정답 영상이 부족해진다. 이 때문에 겉보기 사실성만으로 정확도를 측정하면 위험하다. 가능한 곳에서는 물리 측정, 다른 시뮬레이터와의 제약, 외과의의 구조화된 평가를 결합해야 한다.

동일한 출발 프레임에서 서로 다른 동작을 넣은 두 영상이 눈에 띄게 다르다는 사실은 제어 조건이 반영됐다는 최소 증거가 될 수 있다. 그러나 두 결과 모두 틀릴 수 있다. 도구가 실제 명령보다 과장되게 이동하거나, 조직이 도구와 접촉하기 전에 변형될 수도 있다. 정량 평가에는 동작 명령과 도구 끝점의 위치 오차, 접촉 전후 변화의 시점, 움직이지 않아야 하는 해부 구조의 안정성, 가림 뒤 재등장한 구조의 일관성을 따로 담아야 한다. ‘실시간’이라는 지연 목표와 ‘타당한 반응’이라는 품질 목표를 혼동하지 않는다.

공개 글은 동작을 28차원으로 표현하고 두 도구를 중심으로 자료를 선택했다고 적는다. 이런 입력 표현에 맞지 않는 로봇이나 더 많은 도구가 등장하는 장면은 추가 적응이 필요하다. 학습 자료에 드문 합병증이나 예외적 해부 구조가 충분히 있지 않으면 모델이 익숙한 정상 장면으로 돌아가려 할 수 있다. 시뮬레이터를 안전 관련 연구에 사용하려면 **무엇이 훈련 분포 밖인지**를 표시하는 방법도 중요하다. 모델이 자신 있게 영상을 계속 생성할 수 있다는 사실이 분포 밖 상황의 물리적 타당성을 보장하지 않는다.

### 두 학생 체크포인트의 선택은 기능 스위치가 아니다

네 단계와 두 단계 모델의 차이를 런타임 옵션만 바꾸는 일로 오해하면 시험 결과를 비교하기 어렵다. 공식 글은 두 단계 모델을 네 단계 모델에서 추가 학습한 별도 체크포인트라고 적는다. 따라서 같은 초기 상태와 동작을 넣어도 시각 품질, 지연, 시간적 안정성이 다를 수 있다. 연구에서는 어떤 체크포인트와 추론 설정을 사용했는지 고정한다. 두 모델의 속도와 품질을 비교하려면 공통 동작 세트, 동일한 GPU·해상도·출력 길이, 평가자 눈가림이 필요할 수 있다. 적은 단계가 빠르다는 일반적 직관만으로 실제 과제의 선택을 끝내지 않는다.

Self-Forcing과 FadeMem의 역할도 구분한다. Self-Forcing은 모델이 자신이 생성한 프레임의 오차를 다음 입력 문맥으로 다시 받는 상황에 적응하게 하는 학습 절차다. FadeMem은 긴 생성에서 주의 메모리의 증가를 관리하는 런타임 구성이다. 하나가 좋아도 다른 한쪽의 문제가 남을 수 있다. 학생 모델이 짧은 구간에서 자연스러워도 오랜 실행에서 형상이 달라질 수 있고, 캐시 사용량이 안정돼도 동작에 대한 물리적 반응이 맞지 않을 수 있다. 평가 보고서에는 시간적 드리프트와 메모리·지연을 별도로 적는다.

### 연구 사용과 임상 사용의 문턱

NVIDIA 글은 이 시스템이 **연구용 시뮬레이터이며 환자 치료용으로 검증되지 않았다**고 명시한다. 이 단서는 작은 법적 문구가 아니라 기술 성숙도의 핵심이다. 연구자는 모델의 실패를 관찰해 더 좋은 동작 표현과 평가법을 만들 수 있다. 하지만 실제 환자 치료를 위한 수술 계획이나 의사결정에는 안전성·일반화·임상 유효성의 다른 증거가 필요하다. 시뮬레이션을 이용해 로봇 정책을 학습하는 아이디어 역시 향후 연구 방향으로 제시된 것이다. 현재 공개 모델이 자율 수술을 수행하거나 인증받았다는 뜻으로 표현해서는 안 된다.

연구 자료의 출처와 사용 조건도 확인해야 한다. 임상 영상은 민감할 수 있고, 학습과 공개 체크포인트에는 별도 권한과 데이터 처리 조건이 적용될 수 있다. 공개 저장소가 있다고 해서 원자료를 자유롭게 복제하거나 임상 환경에 쓸 수 있다는 뜻은 아니다. 다른 연구팀이 자체 영상과 제어기를 붙일 때는 동작 규약과 정규화가 훈련에 사용한 것과 맞아야 한다고 글이 강조한다. 제어 스케일이 다르면 작은 명령이 큰 이동으로 해석될 수 있다. 재현성에는 코드뿐 아니라 물리 단위와 입력 의미의 계약이 포함된다.

## 기술 부록 D — 세 종류의 ‘메모리’를 혼동하지 않기

오늘 기사에는 서로 다른 의미의 메모리가 등장한다. 첫째, MPS와 TPU의 **장치 메모리**는 모델 가중치·활성값·컴파일 캐시와 드라이버 자원을 담는다. 둘째, IBM의 ALTK-Evolve가 다루는 **에이전트 메모리**는 과거 작업의 실패와 성공을 요약한 지침이다. 셋째, NVIDIA의 FadeMem이 관리하는 **생성 과정의 주의 메모리**는 긴 영상 생성에서 과거 문맥을 유지하는 KV 캐시와 관련된다. 모두 ‘메모리 최적화’라고 부를 수 있지만 무엇을 잊고 무엇을 유지해야 하는지가 다르다.

장치 메모리는 용량·대역폭·할당 패턴의 문제다. 가중치를 FP8로 줄여도 드라이버 누적 문제가 남을 수 있고, 반대로 MPS 패딩을 수정해 드라이버 피크를 줄여도 모델 가중치 자체는 그대로일 수 있다. 에이전트 메모리는 지침의 정확성·적용 범위·우선순위의 문제다. 짧게 만들수록 토큰은 줄지만 필요한 예외를 잃을 수 있고, 길게 만들수록 정책 충돌과 비용이 늘 수 있다. 생성 과정의 주의 메모리는 오래된 문맥을 어떻게 압축하면서 시각적 일관성을 유지할지의 문제다. 캐시가 작아졌다는 이유만으로 장면의 해부학적 정확도가 좋아지는 것은 아니다.

운영 팀이 메모리를 말할 때에는 정확한 대상을 적는 편이 좋다. `GPU 드라이버 메모리 피크`, `프롬프트 지침 토큰`, `영상 생성 KV 캐시`는 서로 다른 그래프에 그린다. 같은 단어가 기술 기사 여러 곳에 나온다고 같은 개선 방법이 적용되는 것은 아니다. 각 메모리의 실패 모드도 다르다. 장치 메모리는 OOM과 시스템 압박, 에이전트 메모리는 낡은 정책과 지침 충돌, 생성 메모리는 시간적 드리프트와 누락된 과거 상태로 드러난다. 무엇이 개선됐는지 명시하면 팀 간 전달 오류가 줄어든다.

## 기술 부록 E — ‘평가’의 네 얼굴

오늘의 발표는 모두 평가를 다르게 사용한다. TorchTPU는 프레임워크 테스트가 몇 퍼센트 통과하는지 보고한다. MPS는 특정 모델의 초당 토큰, PSNR, 커널 지연과 드라이버 메모리를 측정한다. FairStress는 정체성 표지와 설득 압박에 따라 결정이 얼마나 흔들리는지 비교한다. IBM은 업무 상태가 정답에 도달했는지, 반복 시도에서 항상 성공하는지 본다. NVIDIA는 영상과 동작의 일관성 문제를 설명하면서 임상적 정확도는 아직 연구 과제로 남긴다. 서로 다른 질문에 대한 수치를 하나의 ‘AI 성능’ 순위로 합치지 않는다.

프레임워크 테스트의 단위는 코드 경로다. 테스트가 96.5% 통과해도 나머지가 희귀하지만 우리 제품의 핵심 경로에 해당하면 파일럿은 실패할 수 있다. PSNR과 커널 지연의 단위는 특정 입력과 비교 기준이다. 29.95dB로 개선된 사례가 모든 편집 프롬프트의 정답을 의미하지 않는다. FairStress의 격차는 특정 정의의 공정성과 시나리오 변형에 따라 측정된다. 9.3%포인트가 실무의 차별 피해율과 같지는 않다. IBM의 Pass⁴는 반복 시도의 일관성을 보여 주지만 장기적 운영에서 드문 예외를 모두 포함하지 않는다. 연구 시뮬레이터의 사실성은 물리·임상 유효성의 필요조건일 수 있어도 충분조건이 아니다.

측정을 다음 행동으로 연결하려면 각 지표의 ‘실패 하나’가 무엇을 뜻하는지 적어 본다. TPU 테스트 하나의 실패는 지원하지 않는 연산일 수 있다. MPS 영상 하나의 실패는 조용한 오염일 수 있다. FairStress 쌍 하나의 실패는 근거가 같은데 정체성 단서에 따라 결정이 뒤집히는 것이다. 고객지원 한 과제의 실패는 고객 요청에 대한 최종 데이터베이스 상태가 틀리는 것이다. 수술 시뮬레이터 한 롤아웃의 실패는 영상의 해부학적 구조가 유지되지 않는 것일 수 있다. 실패 단위가 분명해지면 무엇을 수정할지와 수정 후 어떤 시험을 다시 돌릴지도 선명해진다.

## 기술 부록 F — 사이트 독자를 위한 최소 체크리스트

새 AI 발표를 읽을 때 먼저 **발표의 종류**를 확인한다. 기업 인수인지, 공개 코드 릴리스인지, 릴리스 후보 기술 글인지, 연구 벤치마크인지에 따라 질문이 달라진다. 다음으로 **날짜와 상태**를 본다. 10월 20일에 공개됐어도 예고된 2.16 기능은 아직 2.15의 일반 기능이 아니다. 한 블로그의 ‘이제 가능하다’는 표현도 패키지 설치 가능 상태, 특정 모델 지원, 제품 일반 제공 중 무엇을 뜻하는지 나눠야 한다.

그다음은 **분모와 비교 기준**이다. 21.5배의 분모가 TPU 기본 커널인지 GPU인지, 8배의 분모가 softmax 커널인지 전체 모델인지, Pass⁴의 분모가 held-out 과제인지 전체 base split인지 확인한다. 모델 이름이 같아도 하드웨어·입력·컴파일·양자화가 다르면 직접 비교하기 어렵다. 마지막은 **독자의 환경**이다. 우리 모델, 고객, 정책, 장치, 권한 흐름에서 아직 무엇을 시험하지 않았는지 한 줄로 적는다. 좋은 뉴스 기사는 확신을 과장하는 대신 다음 실험을 분명하게 만든다.

오늘 확인한 공식 소스는 실험의 시작점을 충분히 준다. TorchTPU에는 설치·예시·이슈 경로가 있고, MPS 글에는 커널 변화와 측정 조건이 있으며, FairStress에는 코드·데이터·논문이 있다. IBM에는 지침 추출 라이브러리와 평가 설정이 있고, NVIDIA에는 모델과 연구용 구현이 있다. OpenAI 인수 발표는 통합 로드맵의 목표를 말하지만 실험 가능한 통합 기능의 사양을 제공하지는 않는다. **공개 산출물의 종류까지 구분하는 것**이 기술을 공정하게 평가하는 출발점이다.

## 비교 부록 — 어제의 TorchNeuron과 오늘의 TorchTPU를 같은 ‘네이티브’로 뭉뚱그리지 않는다

10월 19일 PyTorch와 Hugging Face가 설명한 AWS Trainium용 **TorchNeuron**과 10월 20일 Hugging Face가 설명한 Google TPU용 **TorchTPU**는 모두 개발자가 PyTorch의 장치 API를 활용한다는 방향이 같다. 그러나 장치, 구현, 패키지, 릴리스 상태와 실험 결과는 다르다. TorchNeuron은 `neuron` 장치를 등록하고 Trainium2·Trainium3에서 eager와 compiled 실행을 지원한다고 PyTorch 공식 글이 설명한다. TorchTPU는 `tpu` 장치와 TPU용 ATen 커널, XLA 계산 캐시를 공개 저장소에서 설명한다. 두 기술을 같은 소프트웨어의 스킨만 다른 제품처럼 취급해서는 안 된다.

입문 코드가 한두 줄이라는 외형은 비슷하다. TorchNeuron 글은 `.to('neuron')`와 `torch.compile(..., backend='neuron')` 경로를 제시한다. TorchTPU 글은 Transformers의 `device_map='tpu'`, Diffusers의 `.to('tpu')`, 선택적 `torch.compile`을 제시한다. 모두 기존 PyTorch 모델을 새로운 하드웨어에서 시험하는 진입점을 낮춘다. 그러나 컴파일러, 하위 커널, 통신, 프로파일러, 지원 모델의 범위가 다르므로 한쪽에서 통과한 테스트가 다른 쪽에서도 통과한다는 뜻이 아니다. 공정한 비교를 원하면 동일 모델·입력·품질 목표와 각각의 권장 런타임 설정을 사용해야 한다.

PyTorch의 TorchNeuron 공식 설명은 10월 20일 공개 베타와 Apache 2.0 저장소 공개를 예고했다. 우리가 확인한 10월 21일 기사에서도 실제 설치·실행으로 베타 상태를 독립 검증한 것은 아니다. TorchTPU의 공개 저장소는 0.2.0 패키지 설치 안내를 제공하고, Hugging Face 글은 TPU에서 실행한 모델과 테스트 결과를 보고한다. 두 경로의 공개 상태를 단순히 `베타 vs 정식`으로 서열화하기보다는 도입 시점의 저장소 릴리스와 자신이 필요한 기능의 상태를 확인해야 한다. 버전 숫자와 공개 베타라는 명칭만으로 성숙도를 비교할 수 없다.

성능 수치도 합치지 않는다. TorchTPU 글의 21.5배·12.8배는 특정 Pallas 커널이 같은 TPU의 기본 구현 대비 보인 디코딩 처리량이다. TorchNeuron 글에서 소개하는 다른 모델·칩의 성능 인용은 다른 조건의 관찰이다. 어느 장치가 보편적으로 싸거나 빠르다는 결론은 나오지 않는다. 비교 실험에는 클라우드 지역, 인스턴스 비용, 칩 수, 메모리, 모델 병렬 방식, 최대 배치와 사용자 지연 목표를 포함한다. 동일 품질을 만족하지 못하면 값싼 요청도 실제로는 사용하기 어렵다.

운영 선택은 자사의 기존 환경에도 좌우된다. 이미 AWS 네트워크·저장·배포·모니터링을 표준화한 팀은 Trainium 파일럿의 주변 비용이 낮을 수 있다. Google Cloud TPU를 확보하고 TPU에 맞는 학습 파이프라인이 있는 팀은 TorchTPU를 더 자연스럽게 시험할 수 있다. 특정 데이터의 이동과 보관 규정이 있으면 장치 성능보다 접근성과 거버넌스가 결정적일 수도 있다. 공식 글은 이런 조직별 총비용을 제공하지 않는다. ‘PyTorch 네이티브’라는 공통 방향은 선택지를 늘리는 소식이지, 모든 팀에게 같은 장치를 권하는 결론이 아니다.

두 발표를 함께 볼 때 개발팀이 바로 얻는 것은 벤더 중립적 검증 자산을 만들 동기다. 같은 모델의 작은 정합성 코퍼스, 입력 길이별 성능 부하, 실패 분류표, 완료 요청당 비용 계산식을 마련해 두면 다음 가속기에도 재사용할 수 있다. 장치별로 다르게 해야 하는 설정은 어댑터로 나누고, 모델 품질의 기준은 공통으로 유지한다. 장치 API가 비슷해져도 검증의 독립성이 없으면 벤더 비교는 홍보 문구의 배율을 나열하는 회의가 된다. 독립적인 테스트가 있을 때 개발자는 새 백엔드의 장점을 빠르게 발견하고 한계도 정직하게 기록할 수 있다.

## 비교 부록 — 오늘의 여섯 소식이 각기 답하지 못하는 질문

OpenAI의 인수 발표는 **업무 조정의 목표**를 설명하지만, 통합 제품의 공개 출시 시각과 실제 사용자의 성과를 답하지 않는다. TorchTPU 발표는 **PyTorch 진입 경로와 일부 측정**을 제공하지만, 모든 고객 모델의 비용·품질을 답하지 않는다. MPS 2.15 릴리스 후보 글은 **특정 버그와 성능 경로의 개선**을 상세히 보여 주지만, 모든 Mac과 앱의 업그레이드 효과를 답하지 않는다. FairStress는 **특정 정의의 대칭성과 압박에 대한 취약성**을 측정하지만, 조직의 법·정책을 정의하지 않는다. IBM의 ALTK-Evolve는 **지침형 에이전트 기억의 벤치마크 효과**를 보여 주지만, 실제 고객센터 정책에 맞는 지침을 제공하지 않는다. NVIDIA의 Cosmos3-H-Dreams는 **동작 조건부 생성 연구**를 제시하지만, 임상적 유효성을 증명하지 않는다.

질문에 답하지 못하는 범위를 밝히는 것은 발표의 가치를 낮추지 않는다. 오히려 다음 작업을 분명히 한다. 통합 제품은 출시 문서와 계약을 기다리고, 백엔드는 목표 모델을 포팅하며, 릴리스 후보는 격리된 환경에서 정합성을 확인하고, 공정성 평가는 업무 정책과 짝을 만들며, 지침형 에이전트는 독립 테스트 과제를 남겨 두고, 시뮬레이터는 물리적 반응과 전문가 평가를 설계한다. 여섯 개의 뉴스가 서로 다른 층위를 바꿨기 때문에 여섯 가지 다른 검증 계획이 필요하다.

## 확인 시점과 후속 업데이트를 위한 편집 기록

이 호의 제목 날짜는 독자가 읽는 한국 시간의 발행일이다. 공식 뉴스 목록에 표시된 10월 20일은 각각의 제공자가 적은 발표 날짜다. 한국 시간 10월 21일 오전 11시 30분에 전날 미국 시간 발표를 다루는 것은 시차에 따른 정상적인 편집 범위다. 오늘 발표가 새로 나왔다고 주장하기 전에 목록의 날짜를 확인했다. 반대로 이전 날짜의 글이라고 해서 오늘 처음 공개된 한국어 요약에서 제외하지 않았다. 뉴스의 신선도와 자료의 확인 가능성을 함께 고려했다.

검색 API가 실패한 뒤에는 공개 인덱스에서 항목을 찾고, 제목만 보고 본문을 쓰지 않았다. OpenAI 인수 원문과 Rosalind 설명, Hugging Face의 TorchTPU·MPS·FairStress·IBM·NVIDIA 글, TorchTPU 공개 저장소와 연구 코드 링크를 열었다. 각 출처가 속한 기관의 공식 발표나 저자가 공개한 자료를 우선했다. 소셜 미디어의 요약이나 검색 스니펫에서 새 수치를 가져오지 않았다. 특히 하나의 공식 블로그에 여러 기관의 글이 실릴 수 있으므로 글의 저자와 호스팅 사이트를 구분했다. Hugging Face 사이트에 실렸다는 이유로 Ai2의 FairStress와 IBM Research의 ALTK-Evolve를 Hugging Face 자체 연구 결과로 바꿔 쓰지 않았다.

업데이트가 필요한 항목도 남긴다. PyTorch 2.15 MPS 글은 릴리스 후보를 시험하라고 안내하며 2.16 계획을 별도 구역에 적는다. 독자가 나중에 안정 버전을 설치할 때에는 해당 시점의 공식 릴리스와 호환성 표를 다시 확인해야 한다. TorchTPU의 공개 저장소는 0.2.0 설치 예시를 제공하지만 패키지와 지원 범위는 바뀔 수 있다. TorchNeuron 비교 부록의 공개 베타 설명 역시 그 시점의 공식 글을 근거로 한 것이다. 기술의 상태가 바뀌면 본문에 적힌 당시 조건을 새 상태와 혼동하지 않도록 한다.

연구 수치에도 같은 규칙을 적용한다. FairStress의 1,300만 건은 설계된 조합의 규모이고, 그 수가 자체 조직의 적합성을 자동으로 보장하지 않는다. ALTK-Evolve의 held-out 과제와 리더보드 base split은 서로 다른 표본이다. NVIDIA 시뮬레이터의 기술 시연은 임상적 검증 자료가 아니다. 연구자가 새 실험과 오류 수정을 발표하면 이후 글에서 그 변화와 재현 조건을 추적할 수 있지만, 미래의 결과를 오늘의 사실로 미리 채울 수는 없다. 읽는 사람이 현재 무엇을 알고 무엇을 아직 검증해야 하는지 구분할 수 있도록 날짜·상태·분모를 반복해서 적은 이유다.

오늘의 가장 실용적인 결론은 기술 하나를 고르는 것보다 측정의 기준을 보존하는 것이다. 새 장치에서는 같은 모델과 입력을, 새 프레임워크에서는 같은 품질 게이트를, 새 평가에서는 같은 정책과 판단 근거를 유지해야 차이를 기술의 효과로 설명할 수 있다. 에이전트가 더 많은 업무를 수행할수록 실행된 변경과 사람이 승인한 변경의 차이를 확인해야 한다. 연구 시뮬레이션은 실시간 화면과 물리적으로 타당한 반응을 구분해야 한다. 이런 구분을 실험 문서에 남기면 다음 발표의 큰 숫자를 더 빨리 검토할 수 있다. 반대로 조건을 잃은 수치는 반복 측정도, 실패 수정도 어렵게 만든다.
