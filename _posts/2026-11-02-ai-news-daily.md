이 글에서 **공식 발표의 사실**과 **필자의 운영 제안**을 구분한다. 제품 지원 범위, 버전, 날짜와 발표 측정치는 링크된 원문에 근거한다. 반면 승인 단계, 평가 분할, 실패 대응, 모니터링 지표, 인사시스템 예시는 공식 제품이 자동 제공하는 기능이 아니라 발표를 읽고 설계한 실무 적용안이다. 발표의 예제 코드를 그대로 프로덕션 구성이라고 부르지 않으며, 특정 수치가 모든 팀에서 재현된다고도 주장하지 않는다.

## 배경: 에이전트의 산출물은 더 이상 답변 한 문장이 아니다

기존 챗봇은 질문을 받아 텍스트를 반환했다. 반환값이 틀리면 사용자가 읽고 무시할 여지가 있었다. 반면 에이전트가 예약 카드를 만들고, 고객 정보를 입력받고, 승인 버튼을 연결하고, 코드를 수정하고, 모바일 앱 안에서 추론하면 결과는 곧 **인터페이스·작업 흐름·저장된 데이터·배포물**이 된다. 산출물의 형태가 바뀌면 책임 경계도 바뀐다. 에이전트가 어떤 버튼을 제안했는지, 프런트엔드가 어떤 속성을 허용했는지, 서버가 클릭 이벤트를 어떤 권한으로 실행했는지 각각 기록해야 한다. 하나의 ‘AI가 했다’는 로그로는 사고 원인을 복원할 수 없다.

오늘의 발표들은 ‘모델이 좋아졌다’라는 단순한 스토리와 거리가 있다. A2UI는 모델 출력을 실행 코드가 아닌 선언형 메시지로 만들고 이미 작성된 컴포넌트로 제한한다. Agents CLI 글은 작은 기능 변경이 에이전트의 행동을 어떻게 바꾸는지 측정한다. LiteRT는 추론 런타임을 앱 패키지 밖으로 이동해 배포와 성능의 책임을 다시 나눈다. Octoverse는 에이전트가 이미 개발 흐름의 출발점에 들어왔다는 활동 지표를 보여 주지만 그 자체로 품질을 증명하지 않는다. 따라서 이 네 발표를 함께 읽을 때의 해석은 **생성량 증가에 맞춰 검증량과 승인 품질을 어떻게 늘릴 것인가**다.

### 데이터의 분모를 먼저 고정해야 한다

오늘 등장하는 숫자는 서로 같은 대상을 세지 않는다. A2UI의 컴포넌트 카탈로그 숫자는 UI 구성요소 수다. Agents CLI 데모의 평균 점수는 네 사례와 특정 판정 모델의 점수다. LiteRT의 8MB와 1.4배는 Google이 시험한 앱·추론 경로의 관찰이다. GitHub의 179억은 최근 12개월 푸시 횟수이고, 40% 이상은 특정 월의 PR 시작 방식 비중이다. 수치를 한 슬라이드에 나란히 놓아 ‘AI 생산성이 몇 배’라고 합산할 수 없다. 각각의 단위, 기간, 모집단, 비교 기준을 함께 써야 한다. 특히 제품 기획자는 활동량, 속도, 정확도, 사용자 가치, 운영비를 서로 다른 지표로 관리해야 한다.

## 1. A2UI·CopilotKit: 에이전트 UI는 화면 코드가 아니라 제한된 의도다

Google의 10월 29일 글은 여행 패키지를 텍스트 여섯 문단으로 설명하는 대신 사용자가 고를 수 있는 카드·선택기·입력 화면을 대화 안에서 보여 주는 사례로 시작한다. 이 차이는 미관이 아니다. 사용자가 여러 선택지를 비교하고, 값을 수정하고, 다음 단계로 넘어갈 수 있는 상태ful 인터페이스를 제공한다는 뜻이다. 그러나 모델이 HTML·JavaScript를 마음대로 만들게 하면 화면 오류를 넘어 스크립트 실행, 임의 네트워크 요청, 디자인 시스템 이탈, 접근성 결함이 생길 수 있다. 그래서 글은 앱이 정의한 카탈로그의 컴포넌트만 에이전트가 선택하는 선언형 경로를 소개한다. [Google 공식 글](https://developers.googleblog.com/build-generative-ui-apps-with-a2ui-copilotkit-agents/)

### 세 층을 혼동하지 말자: 화면 언어, 이벤트 운송, 앱 통합

**A2UI**는 에이전트가 어떤 컴포넌트를 어떤 데이터로 조합할지 설명하는 형식이다. 클라이언트가 허용한 컴포넌트 카탈로그에 없는 것은 화면이 되지 않는다. **AG-UI**는 에이전트의 이벤트와 사용자의 상호작용을 클라이언트와 주고받는 흐름이다. **CopilotKit**은 런타임, 채팅 UI, A2UI 렌더링을 앱과 연결하는 통합 경로 중 하나다. 세 이름을 모두 ‘UI 프레임워크’라고 부르면 경계가 흐려진다. 같은 A2UI 메시지가 React, Lit, Angular, SwiftUI, Jetpack Compose, Flutter의 렌더러로 표현될 수 있다는 것이 원문의 주장이고, CopilotKit은 React·Angular 지원과 Vue·Slack 커스텀 렌더러를 설명한다. 포터빌리티는 규격과 렌더러 구현을 뜻할 뿐, 각 플랫폼에서 픽셀·키보드·스크린리더 동작이 자동으로 동일하다는 보증은 아니다.

원문 예제는 Google ADK 에이전트를 `ag_ui_adk`로 FastAPI 엔드포인트에 연결한 뒤, 프런트엔드에서 `FlightCard`를 카탈로그에 등록한다. `FlightCard`에는 항공사, 출발·도착, 경유 횟수 속성이 있고 Zod 스키마가 속성 타입을 검증한다. 에이전트는 카탈로그에 있는 컴포넌트와 속성만 사용할 수 있다. 이 모델에서 프런트엔드 팀은 **어떤 화면 요소가 존재할 수 있는지**를 코드와 스키마로 통제한다. 모델은 그 허용 범위 안에서 **어떤 순서와 데이터로 보여 줄지** 결정한다. 도구 호출 권한이나 결제 승인까지 UI 카탈로그가 통제한다고 이해해서는 안 된다. 화면 렌더링 허용과 서버의 업무 실행 허용은 분리된 승인이다.

### 클릭이 돌아오는 순간 보안 경계가 한 번 더 생긴다

원문의 예약 흐름 예시에서는 `/booking/cabin` 데이터 경로에 연결된 선택기와 `confirmBooking` 이벤트를 갖는 버튼을 만든다. 버튼이 눌리면 지정된 데이터 경로의 값이 같은 흐름을 통해 에이전트에 돌아가고, 에이전트는 같은 `surfaceId`에 새 화면을 보낸다. 클라이언트의 기본 입력 검증은 잘못된 이메일을 모델 호출 없이 표시할 수 있다. 이는 반응성과 비용에 이롭지만, **클라이언트 검증이 서버 검증을 대신하지 않는다**. 브라우저는 변조할 수 있고, 오래된 화면에서 버튼을 누를 수도 있다. 결제·인사 승인·계정 변경처럼 실제 효과가 있는 이벤트에는 서버가 사용자 세션, 객체 소유권, 권한, 현재 상태, 중복 실행 방지를 다시 확인해야 한다.

예를 들어 인사시스템의 휴가 신청 화면을 에이전트가 조합한다고 하자. `LeaveBalanceCard`, `DateRangePicker`, `ReasonField`, `SubmitRequestButton` 같은 컴포넌트를 앱이 허용할 수 있다. 모델이 화면에 ‘잔여 연차 12일’을 적었다고 해서 서버의 장부가 12일인 것은 아니다. 잔여일수는 권한 있는 서버 API 결과로 표시하고, 제출 순간에도 다시 계산해야 한다. 에이전트가 임의로 관리자 승인 버튼을 추가하지 못하게 카탈로그에서 제외하는 것은 첫 방어선이다. 그러나 일반 `Button` 컴포넌트가 임의 이벤트 이름을 받을 수 있다면 같은 문제가 돌아온다. **컴포넌트 허용 목록과 이벤트 허용 목록**을 함께 설계해야 한다.

A2UI 글은 서버 또는 클라이언트에서 카탈로그를 제공할 수 있다고 한다. 동적 카탈로그는 맥락에 따라 화면을 바꾸는 데 유리하지만, 권한 정보가 오래되거나 사용자별 카탈로그가 섞이면 위험하다. 실무 제안은 카탈로그에 버전을 주고, 사용자 권한과 서버 정책에서 파생된 카탈로그만 발행하며, 클라이언트가 제출한 카탈로그를 서버 권한의 근거로 사용하지 않는 것이다. 카탈로그 설명이 모델 프롬프트에 들어간다는 점도 중요하다. 프롬프트 문구의 변경이 컴포넌트 선택을 바꿀 수 있으므로 화면 계약 변경은 코드 변경만큼 검토해야 한다.

### 스트리밍은 ‘부분 화면’의 생명주기를 요구한다

A2UI의 평평한 JSON 메시지는 ID 참조를 통해 점진적으로 도착하고 화면에 그려질 수 있다. 사용자는 모든 텍스트가 완성되기 전에 카드 일부를 볼 수 있다. 하지만 부분 화면에 ‘확인’ 버튼이 먼저 나타나고 가격·기간이 나중에 바뀌면 잘못된 시점의 동의를 받을 수 있다. 따라서 결제나 신청 버튼은 필요한 데이터가 모두 로드되고 서버가 최신성을 확인하기 전에는 비활성화해야 한다. 스트리밍을 켜는 것은 단순한 성능 옵션이 아니라 **상태 전이 설계**다. 로딩, 부분 결과, 유효성 오류, 재시도, 완료, 만료를 컴포넌트마다 정의해야 한다.

원문은 잘못 생성된 출력이 검증에서 잡히면 수정 요청을 보내는 자가 회복 경로와, 재시도 소진 시 짧은 메시지로 대화를 계속하는 실패 완화를 설명한다. 이것은 사용자가 깨진 화면을 덜 보게 해 주지만 무제한 안전망은 아니다. 같은 입력에 반복 실패하면 토큰 비용과 지연이 쌓인다. 운영자는 생성 실패율, 재시도 횟수, 카탈로그 미지원 컴포넌트 비율, 최종 텍스트 폴백률을 따로 측정해야 한다. 사용자가 화면을 보고도 완료하지 못한 비율은 기술적 렌더 성공률과 다른 지표다.

### 개발자에게 의미: 컴포넌트 API가 모델과의 계약이 된다

기존 컴포넌트 라이브러리는 인간 개발자가 타입과 문서를 읽으며 사용했다. 에이전트가 이를 조합할 때는 컴포넌트의 설명과 속성 스키마가 모델이 이해하는 API가 된다. `FlightCard`가 `stops`를 숫자로 요구하면 타입 검증은 쉽지만, ‘직항 여부’와 ‘경유 공항’의 의미까지 자동 보증하지 않는다. 속성의 데이터 출처, 단위, 로케일, 빈 값 처리, 민감도, 클릭 가능 여부를 함께 문서화해야 한다. 같은 `price` 속성이라도 세금 포함 여부와 통화가 빠지면 UI는 맞게 렌더되어도 사용자가 잘못 판단한다.

디자인팀과 프런트엔드팀은 에이전트가 조합할 최소 단위를 신중하게 정해야 한다. 버튼·문자열만 허용하면 조합 자유도는 크지만 잘못된 플로가 나오기 쉽다. 반대로 완성된 `LeaveApplicationForm` 하나만 허용하면 안전하지만 개인화는 제한된다. 실무에서는 읽기 전용 결과 카드와 낮은 위험의 입력 구성요소를 세밀하게 열고, 계정 변경이나 결제처럼 되돌리기 어려운 행동은 높은 수준의 전용 컴포넌트와 별도 승인 이벤트로 묶는 편이 낫다. 이 선택은 모델 성능이 아니라 제품 위험도에 따라 바뀐다.

## 2. Agents CLI: 평균 점수를 올리는 것보다 실패 사례를 보존하는 평가 루프

Google의 10월 28일 글은 에이전트 개발을 ‘한 번 잘 동작하는 데모’와 ‘모델·도구·대화 형태가 바뀌어도 계속 잘 동작하는 제품’으로 나눈다. 이를 위해 사례 데이터셋으로 실제 에이전트를 실행해 trace를 생성하고, 판정하고, 이전 실행과 비교하며, 실패를 묶어 원인을 찾는 순환을 제안한다. 예제는 Agents CLI v1.8.0의 LangChain 템플릿으로 네 사례를 만든다. 인사말, 샌프란시스코 날씨, 로마 날씨, 주제 밖 질문이다. 네 개라는 수가 충분하다는 뜻이 아니라 변경할 때마다 실행할 수 있을 만큼 작아야 한다는 설명이다. [Google 공식 글](https://developers.googleblog.com/hill-climbing-agent-quality-with-agents-cli-evaluation/)

### 코드가 정상이어도 에이전트 행동은 퇴행한다

원문의 첫 실험은 날씨 에이전트의 시스템 프롬프트에 다른 프로젝트의 요리사 페르소나를 붙여 넣는다. 코드는 문법상 유효하고 날씨 도구도 등록돼 있다. 그러나 결과는 달라진다. 평균 점수는 5점 척도에서 4.00에서 2.75로 떨어진다. 사례별로는 인사말 5→4, 샌프란시스코 날씨 4→2, 로마 날씨 2→2, 주제 밖 질문 5→3이다. 특히 샌프란시스코 사례에서는 날씨 도구를 호출하는 대신 조건을 지어낸다. 전통적인 단위 테스트는 함수가 등록됐는지는 확인할 수 있지만 모델이 실제로 그 함수를 호출하는지는 확인하지 못한다. 따라서 에이전트의 회귀 검사는 **최종 답변과 도구 호출 trace**를 모두 봐야 한다.

평균 2.75라는 숫자만 보면 어느 사례를 고칠지 알기 어렵다. 사례별 차이와 trace가 있어야 ‘요리사 페르소나 때문에 도구 호출이 사라졌다’라는 원인을 추적할 수 있다. 원문은 `eval compare`로 두 결과 파일의 차이를 보고, 파일에 남은 사례별 점수를 정렬한다. 단일 점수만 대시보드에 보관하면 3주 뒤 회귀가 발견됐을 때 어떤 입력이 깨졌는지 복원할 수 없다. 제품팀이 평가 결과를 버전 관리하거나 아티팩트 저장소에 남길 때는 입력 데이터셋 버전, 평가 설정 버전, 모델·도구 버전, 프롬프트 해시, 실행 시각을 함께 묶어야 한다.

### 모델 교체에서 같은 평균 하락은 같은 원인이 아니다

두 번째 실험에서는 정상 프롬프트로 되돌린 뒤 `gemini-3.8-flash`를 `gemini-2.5-flash`로 바꾼다. 평균은 다시 4.00에서 2.75가 된다. 그러나 사례별 변화는 다르다. 인사말 5→5, 샌프란시스코 날씨 4→3, 로마 날씨 2→2, 주제 밖 질문 5→1이다. 동일한 평균 하락이지만 프롬프트 오염과 모델 교체는 실패 패턴이 다르다. 후자는 최근 사건에 대한 훈련 지식 시점의 한계 때문에 주제 밖 질문에서 큰 하락이 생긴다고 원문은 해석한다. 그러므로 평균 하나만 보고 두 변경을 모두 취소하거나 모두 승인하면 잘못된 결론이 된다.

실제 제품에서는 사례의 빈도와 피해를 함께 고려해야 한다. 사용자의 90%가 날씨만 묻고 주제 밖 질문이 거의 없다면 모델 교체가 경제적일 수 있다. 그러나 주제 밖 질문이 법률·급여·의료처럼 고위험 분야로 이어진다면 한 건의 실패라도 허용할 수 없다. 단순 가중 평균도 충분하지 않다. 치명적 위반은 평균과 별개로 **절대 차단 지표**로 둬야 한다. 예컨대 다른 직원의 급여를 보여 주거나 휴가 승인을 권한 없이 수행하는 사례는 100개의 친절한 인사말로 상쇄되지 않는다. 이는 원문 사례에서 도출한 평가 설계 제안이다.

### 평가자도 버전이 있는 의존성이다

예제의 커스텀 품질 판정은 특정 모델을 judge로 사용하고 정확성·관련성·명료성을 1~5점으로 채점한다. 모델 교체 실험에서도 judge는 고정한다. 그렇지 않으면 피평가 에이전트의 변화와 평가자의 변화를 분리하기 어렵다. 운영에서는 judge 자체의 버전, 평가 지침, 샘플링 설정, 맥락 길이, 언어를 고정·기록해야 한다. 한국어 인사시스템이라면 영어 날씨 예제의 점수가 그대로 품질을 설명하지 못한다. 한국어 요청, 날짜·시간대, 공휴일, 개인정보, 조직별 승인 규칙, 도구 오류, 애매한 표현을 따로 평가해야 한다.

한 사람이 채점한 소수 사례로도 평가자의 일관성을 점검할 수 있다. judge와 사람의 불일치가 큰 유형을 찾아 해당 유형은 규칙 기반 검사나 사람 심사로 보완한다. 예를 들어 개인정보 노출은 ‘답변 품질 4점’ 같은 점수보다 정확한 문자열·권한 조건 검사가 낫다. 도구를 꼭 호출해야 하는 경우는 trace에 해당 도구가 있었는지 검사한다. 휴가 일수 계산은 테스트 데이터의 기대값과 비교한다. 부드러운 응대·명료성처럼 정량 규칙으로 판단하기 어려운 부분에 judge를 쓴다. 원문은 평가 루프를 소개하지만 이런 판정 조합은 필자의 운영 제안이다.

### 정기 실행은 드리프트를 포착할 수 있지만 알림까지 설계해야 한다

Google 글은 Agents CLI 자체가 스케줄러를 포함하지 않으므로 cron 또는 Cloud Scheduler에서 명령을 실행할 수 있다고 한다. 결과 파일만 쌓아 두면 회귀가 발생해도 아무도 모른다. 예제는 기준 실행과 새 실행의 평균을 비교해 임계값을 넘으면 비영(非零) 종료 코드를 반환하는 래퍼를 보여 준다. 하지만 운영에서는 평균 점수 임계값 하나로 모든 알림을 만들지 말아야 한다. 핵심 사례 실패, 특정 도구 호출 급감, 정책 위반, 타임아웃, 비용 급증, judge 실행 오류를 구분해야 한다. 평가 자체가 실패한 날을 ‘점수 유지’로 처리하면 감시 공백이 된다.

데이터셋도 두 층이 필요하다. 작은 inner-loop 세트는 모든 프롬프트·도구 변경에서 빠르게 돌린다. 더 큰 회귀 세트는 배포 전 또는 야간에 돌린다. 두 세트의 사례를 중복만 시키지 말고 목적을 달리한다. 작은 세트는 핵심 성공 경로와 큰 사고 위험을 담고, 큰 세트는 다양한 문장 표현과 도구 상태를 담는다. 운영 로그에서 새 실패가 나오면 개인정보를 제거하고 재현 가능한 사례로 승격한다. 이때 결과 점수만 업데이트하지 말고 **사례 입력과 기대 조건**을 서로 다른 파일에 보존한다. 원문 역시 데이터셋은 입력, 평가 설정은 기대라고 분리할 것을 권한다.

### 자동 최적화는 후보 생성이지 자동 배포가 아니다

`eval optimize`는 ADK 프로젝트에서 GEPA로 프롬프트 후보를 만들어 목표 지표에 맞게 평가한다. 원문은 이 기능이 해당 LangChain 확장에는 현재 적용되지 않으며 도구·모델·구조가 아닌 프롬프트 최적화에 한정된다고 한다. 후보는 특정 평가 지표의 표현에 과적합될 수 있으므로 사람이 검토해 승격해야 한다. 평가 세트와 최적화 세트를 완전히 동일하게 두면 모델이 평가 문항의 정답 형태만 배우는 식의 착시가 생긴다. 홀드아웃 사례, 최근 실제 사용자 사례, 위험 사례를 따로 두고 개선 여부를 확인해야 한다. 고정된 평가에서 5점이 됐다고 운영 품질이 완성된 것은 아니다.

원문 마지막의 중요한 경고는 평가 실행 횟수와 품질 개선이 같은 말이 아니라는 것이다. 한 통제 연구에서 Agents CLI를 쓰는 코딩 에이전트는 평가를 네 배 더 실행했지만 평가 뒤 에이전트를 실제로 변경하는 빈도는 기준과 비슷했다고 한다. 평가가 많아져도 실패 원인을 고치지 않으면 제품은 나아지지 않는다. 운영 조직에서는 ‘이번 주 평가 몇 회’보다 ‘새로 찾은 실패 몇 건, 원인 규명 몇 건, 수정 뒤 재발 여부’를 보아야 한다. 평가 플랫폼 구축 자체를 완료 목표로 삼으면 시험 성적만 자동으로 생산하는 조직이 된다.

## 3. LiteRT in Play services: 추론 런타임을 앱 밖으로 옮길 때의 득실

Google의 10월 28일 발표는 Android에서 사용자 정의 모델을 실행하는 LiteRT 런타임을 Google Play services 경로로 제공하고 `CompiledModel` API로 GPU 사용을 단순화한다. 기존에는 빠른 GPU 경로를 활용하려면 LiteRT를 앱에 포함해야 했다고 원문은 설명한다. Play services가 런타임을 공용으로 제공하면 여러 앱이 각자 패키지에 같은 런타임을 싣지 않아도 된다. Google의 시험에서 전환 앱은 약 8MB 작아졌고, 새 GPU 경로는 구 GPU delegate보다 약 1.4배 빨랐다. 이것은 제품이 참고할 출발 수치이지 모든 기기에서 같은 절감과 속도를 얻는다는 보증이 아니다. [Google 공식 글](https://developers.googleblog.com/smaller-apps-and-faster-gpu-inference-with-litert-in-google-play-services/)

### 앱 크기 절감과 추론 성능은 서로 다른 실험이다

8MB 감소는 런타임 중복 패키징을 줄인 결과다. 앱 다운로드, 설치 공간, 스토리지 부담에 의미가 있다. 그러나 전체 앱의 크기가 8MB인 경우와 200MB인 경우 사용자 체감은 다르다. 모델 파일 자체가 크면 런타임만 옮겨도 전체 크기가 여전히 크다. 출시 전에는 AAB 또는 APK의 다운로드 크기, 설치 뒤 크기, 모델 다운로드 크기, 기기 저장 공간, 최초 실행 시간을 각각 측정해야 한다. ‘앱 8MB 감소’를 ‘모델도 8MB 감소’로 읽으면 안 된다.

1.4배 GPU 속도 수치는 모델·연산자·입력 텐서·기기 GPU·발열·동시 실행 부하에 따라 달라질 수 있다. 평균 추론시간만 보면 카메라 프레임의 끊김을 놓친다. p50·p95·p99 지연, 첫 호출 컴파일 비용, 연속 실행시 발열과 배터리 소모, CPU fallback 비율, 백그라운드 복귀 후 재초기화 시간을 따로 봐야 한다. 개인정보 때문에 온디바이스 모델을 택한 제품이라면 네트워크가 끊긴 상태에서도 초기화와 추론이 실제로 가능한지 확인해야 한다. Play services 제공이라는 배포 형태가 앱의 데이터 보존·전송 정책을 자동으로 설명해 주지는 않는다. 데이터 흐름은 해당 API와 모델 로딩 경로를 별도로 검증해야 한다.

### `CompiledModel`은 이식 경로이지만 구 API 호환과 구분한다

원문은 LiteRT가 기존 `.tflite` 모델 형식을 유지하면서 새로운 `CompiledModel` API를 제공한다고 설명한다. CPU와 GPU를 하나의 워크플로로 다루고, 사용 가능한 환경에서 OpenCL 또는 OpenGL을 사용하며, GPU가 쓸 수 없으면 CPU로 fallback할 수 있다. 기존 Interpreter API는 Play services 경로에서도 CPU로 계속 사용할 수 있지만 GPU를 쓰려면 `CompiledModel`로 옮겨야 한다. ‘LiteRT 의존성만 바꾸면 GPU 성능이 자동 향상된다’는 해석은 틀리다. 코드 경로와 모델 호환성 검증이 필요하다.

공식 안내의 기본 순서는 `com.google.android.gms:play-services-litert:17.0.0` 또는 이후 버전 추가, 기존 번들 LiteRT 의존성 제거, `LiteRt.initialize`로 GPU 사용 환경 초기화, `CompiledModel` 생성 시 해당 환경 전달이다. 버전 문자열은 발표 당시 예제다. 실제 구현 시 최신 안정 버전과 릴리스 노트를 다시 확인해야 한다. `initialize`가 비동기 작업이라는 사실은 시작 화면 설계에도 영향을 준다. 초기화 중에 사용자에게 무한 로딩을 보여 주지 말고, 타임아웃·기기 미지원·CPU fallback·모델 다운로드 실패를 구분해야 한다. 단말 성능에 따라 GPU가 이득이 없을 수 있으므로 실측을 기준으로 경로를 선택하는 것이 안전하다.

원문은 Android 7(API 24)부터의 전화기, Wear OS 4 이상, Android Automotive OS(Android 11 이상)을 지원 범위로 적는다. ‘Android 7 이상’만 보고 모든 폼팩터가 똑같이 지원된다고 읽으면 안 된다. 스마트워치는 메모리·배터리 한계가 크고 자동차는 운전자 주의 분산 등 UI 요구가 다르다. 모델 파일과 추론 런타임의 호환도 기기별로 검증해야 한다. 같은 `.tflite` 형식을 사용할 수 있다는 말은 모든 연산자, 정밀도, 가속 경로에서 동일한 결과와 지연을 보장한다는 뜻이 아니다.

### 관리형 업데이트는 배포 부담을 줄이지만 변화 감지가 필요하다

Play services를 통해 성능·버그·보안 패치가 단계적으로 전달되면 앱이 매번 새 바이너리를 배포하지 않아도 된다. 반면 앱 팀이 배포하지 않은 시점에 런타임 동작이 바뀔 수 있다. 런타임 버전과 기기 모델을 로그에 남기고, 추론 결과의 정확도·실패율·지연을 버전별로 비교해야 한다. 특히 온디바이스 개인정보 분류, 얼굴·문서 인식, 음성 명령처럼 사용자가 바로 결과를 보는 기능은 단계적 업데이트 중 일부 기기에서만 회귀가 나타날 수 있다. 제품팀이 외부 런타임을 공유한다고 품질 책임도 외부로 이전되는 것은 아니다.

원문은 구 GPU delegate와 custom delegate API를 `CompiledModel` GPU 및 Compiler Plugin·Dispatch API로 대체하는 방향을 설명한다. NNAPI는 2027년부터 제거될 예정이고 오래된 SDK에는 핵심 보안 수정만 제공된다고 한다. 이미 배포한 앱이 즉시 멈춘다는 뜻은 아니지만, 새 SDK로 빌드할 때 구 API 코드가 컴파일되지 않을 수 있고 의존성 충돌 위험이 커진다. 따라서 지금 필요한 의사결정은 ‘오늘 강제 전면 교체’가 아니라 **현재 앱의 모델·기기·API 사용 현황 목록화와 마이그레이션 순서**다.

### 코딩 에이전트가 바꾼 코드는 실제 단말에서 확인한다

Google은 Android Studio의 LiteRT 스킬이 `Interpreter` 호출을 `CompiledModel` 경로로 바꾸고 GPU·CPU fallback을 설정할 수 있다고 소개한다. 동시에 생성된 diff를 검토하고 빌드한 뒤 실제 단말에서 결과를 비교하라고 명시한다. 이 순서가 중요한 이유는 API 이름 변경보다 출력 일치가 어렵기 때문이다. 전처리의 색 공간, 텐서 배치, 정규화, 후처리의 임계값, 기존 CPU·GPU의 수치 차이가 사용자 눈에 보이는 결과를 바꿀 수 있다. 제품팀은 모델별 대표 샘플과 경계 샘플로 정답 비교를 하고, 기기군별로 첫 실행과 지속 실행을 나눠 측정해야 한다. 에이전트가 빌드 성공을 만들었다는 사실은 결과가 정확하다는 증거가 아니다.

## 4. Octoverse 2026: 에이전트가 개발량을 늘렸다는 관측과 품질의 빈칸

GitHub의 10월 28일 Octoverse 보고서는 최근 12개월 푸시 179억 회, 전체 저장소 커밋 343억 건, 병합 PR 13억 건을 기록했다. 병합 PR의 일평균은 약 350만 건으로 제시된다. GitHub Actions 작업은 초당 1,440회, 하루 약 1억 2,400만 회 수행됐고, Dependabot PR도 3,000만 건 넘게 병합됐다. 이는 GitHub 생태계의 작업량 변화다. 모든 증가분을 AI 에이전트 때문이라고 계산한 실험 결과는 아니다. [GitHub 공식 보고서](https://github.blog/news-insights/octoverse/octoverse-commits-pushes-reach-new-highs-in-2026-as-developers-build-with-agents/)

### 에이전트 설정 파일과 커밋 수의 상관을 인과로 바꾸지 않는다

올해 만들어진 저장소 가운데 에이전트 설정 파일이 있는 저장소의 평균 커밋은 없는 저장소의 8배였다고 GitHub는 보고한다. 하지만 설정 파일을 둘 정도로 개발 활동이 활발한 팀일 가능성, 조직 규모, 저장소 목적, 자동화된 커밋 비중이 다를 수 있다. 따라서 ‘설정 파일을 추가하면 커밋이 8배’는 잘못된 결론이다. 분석이 말하는 것은 **에이전트 중심 작업을 도입한 집단에서 활동량이 높게 관찰됐다**는 것이다. 실무에서는 도입 전후 동일 팀의 유사 과제, PR당 재작업, 배포 후 결함, 승인 대기시간, 사용자 가치까지 보아야 생산성에 가까운 판단을 할 수 있다.

9월 PR의 40% 이상이 에이전트로 시작됐고 3월에는 17%였다는 것도 ‘PR의 40%를 에이전트가 혼자 완성했다’는 뜻은 아니다. 시작 방식은 작성·수정·검토·승인의 전체 책임과 다르다. 에이전트가 초안을 만들고 사람이 바꿨을 수 있고, 사람이 요청을 만들고 에이전트가 테스트를 고쳤을 수도 있다. 이런 구분을 하지 않으면 인력 계획에서 자동화 능력을 과대평가한다. PR을 세는 조직은 초안 생성, 구현, 테스트, 리뷰, 머지의 각 단계에 누가 얼마나 개입했는지 분리해 보는 편이 낫다.

### 활동량의 증가가 리뷰 용량 문제를 만든다

에이전트가 한 사람이 처리할 수 있는 변경 후보를 여러 개 만들면 코드를 생산하는 병목은 줄지만 리뷰·테스트·보안 검토·릴리스 판단이 새 병목이 된다. PR 10개가 열린 것을 성과로 보지 말고, 중요한 결함을 예방하면서 병합·운영까지 간 변경을 성과로 봐야 한다. 리뷰어가 코드를 모두 읽기 어려울 정도로 볼륨이 커지면 위험 기반 분류가 필요하다. 데이터베이스 마이그레이션, 결제·급여 계산, 인증, 권한, 공개 API 변경은 더 깊게 검토하고, 문구·주석·가역적 UI 변경은 자동 검사를 더 활용할 수 있다. 에이전트가 만든 코드라는 이유만으로 모두 위험하거나 모두 안전한 것은 아니다. **변경 영향도와 복구 난이도**가 기준이어야 한다.

GitHub는 9월 Copilot 사용자 중 61%가 둘 이상의 모델을 썼다고 보고한다. 모델 선택이 늘었다는 사실은 한 제품 안에서도 추론·계획·빠른 작업을 나눌 수 있음을 보여 준다. 동시에 평가 범위가 늘어난다. 모델 A에서 통과한 프롬프트·도구 호출이 모델 B에서도 같다는 보장은 없다. 모델별 라우팅 조건, 비용, 실패 유형, 결과 재현 가능성을 기록해야 한다. 모델 이름만 로그에 남기면 충분하지 않다. 같은 요청이 어떤 모델에 왜 갔는지, 응답 이후 어떤 검증을 통과했는지 알아야 비용 절감과 품질의 교환관계를 설명할 수 있다.

### 보고서의 산업 분류는 흥미롭지만 데이터 생성 방법을 읽어야 한다

Octoverse는 공개 저장소를 산업별로 보기 위해 저장소 이름, 설명, 토픽, README를 모델로 분류한 표본을 사용한다. 이는 기업 매출이나 실제 배포된 AI 시스템을 집계한 값이 아니다. 예컨대 의료 관련 저장소가 많아졌다는 수치는 의료 현장에서 임상 사용이 같은 비율로 늘었다는 뜻이 아니다. GitHub는 행정·지원, 광업, 의료, 농업 등에서 AI를 언급한 저장소가 40%를 넘지만 에이전트가 연 PR은 3% 미만인 산업이 있다고 설명한다. AI 언급과 에이전트 개발 사용은 다른 신호다. 건설은 약 4분의 1이 AI를 언급하고 약 9%에서 에이전트 PR이 관측돼 다른 패턴을 보인다. 지표의 차이는 기술 채택의 종류가 다름을 보여 주지만 그 차이의 원인은 별도 조사 없이는 확정할 수 없다.

한국 개발자를 위한 단서도 있다. 보고서의 공개 저장소 푸시 상위 국가 표에서 한국은 7위다. 이는 프로필 위치로 보정한 공개 저장소 활동 순위이지 한국의 AI 기업 경쟁력 순위가 아니다. 오픈소스 참여와 국내 서비스의 실제 매출·품질을 혼동하면 안 된다. 그러나 공개 저장소 활동의 규모가 커진 만큼 한국어 문서, 지역 규제에 맞는 예제, 국내 운영 환경에서 재현 가능한 평가 세트의 가치가 커진다고 해석할 수 있다. 이 마지막 문장은 GitHub의 통계에서 도출한 실무적 시사점이지 보고서가 직접 측정한 결론은 아니다.

## 개발자에게 의미: 네 발표를 하나의 제품 파이프라인에 놓으면

가상의 인사시스템을 생각해 보자. 직원이 ‘다음 달 3일 휴가를 신청하고 잔여일수를 알려 달라’고 묻는다. 에이전트는 정책 문서와 휴가 장부를 조회한다. A2UI로 날짜 선택·잔여일수 카드·제출 버튼을 그린다. 사용자는 날짜를 고르고 제출한다. 서버는 권한과 잔여일수를 다시 확인해 결재 흐름을 시작한다. 모바일 앱은 문서 사진의 개인정보를 온디바이스에서 분류할 수 있다. 개발팀은 이 플로를 에이전트로 구현하고 평가하며 PR을 만든다. 오늘의 네 뉴스가 이 하나의 플로에서 만난다.

첫째, 화면의 **표현**과 실제 **업무 행위**를 구분한다. 에이전트가 승인 상태를 ‘승인됨’으로 표시해도 서버 워크플로의 상태가 바뀐 것은 아니다. UI에서 제출한 요청에는 고유 ID를 부여하고 서버가 접수·검증·결재·완료를 순서대로 기록해야 한다. 재시도나 네트워크 끊김으로 같은 버튼이 두 번 눌려도 신청 두 건이 만들어지지 않도록 멱등성을 구현한다. 사용자는 ‘에이전트가 그렇게 말했다’가 아니라 시스템의 확정 상태를 확인해야 한다.

둘째, 평가의 **성공 조건**을 기능별로 쪼갠다. ‘질문에 친절히 답했다’와 ‘올바른 휴가 유형을 선택했다’, ‘잔여일수를 정확히 계산했다’, ‘권한 없는 직원 정보를 노출하지 않았다’, ‘서버 도구를 올바르게 호출했다’는 다른 테스트다. 텍스트 응대는 judge로 볼 수 있지만 날짜 계산과 권한은 결정적 검사로 보는 편이 낫다. 민감한 업무라면 불확실할 때 추측하지 않고 담당자에게 넘기는 행동도 평가해야 한다. 실패 케이스가 추가될 때마다 데이터셋과 기대 조건을 버전 관리한다.

셋째, 모바일에서 추론이 빠르다는 사실은 **최종 사용자 과제 완료율**을 대체하지 않는다. 문서 사진의 분류가 1.4배 빨라도 글자가 잘못 인식되거나, 느린 기기에서 초기화가 오래 걸리거나, 결과가 너무 늦게 동기화되면 사용자는 신청을 완료하지 못한다. 온디바이스 경로를 택할 이유가 프라이버시라면 입력이 기기 밖으로 나가지 않는지 제품 구성 전체에서 확인해야 한다. 런타임 공급 방식과 개인정보 처리 정책은 별개의 결정이다.

넷째, 팀의 **개발 속도**를 푸시 횟수로 보지 않는다. 에이전트가 UI·API·테스트 변경 PR을 많이 열어도 머지되지 않거나 운영 장애를 늘리면 성과가 아니다. 기능을 작은 단위로 내되, 정책 계산과 권한 변경에는 더 강한 검증을 붙인다. 릴리스 뒤에는 오류율, 사용자의 재시도, 업무 처리 시간, 실제 고객 문의를 본다. PR 활동량은 입력 지표이고 사용자 문제 해결은 결과 지표다.

### 작은 팀을 위한 구체적인 적용 순서

**첫 주: 사실의 경계 세우기.** 어떤 화면을 에이전트가 구성할지 하나만 고른다. 읽기 전용 결과 카드부터 시작한다. 컴포넌트와 이벤트 이름, 속성 타입, 데이터 출처를 문서화한다. 사용자 계정·관리자 승인·금전 처리 이벤트는 실험 카탈로그에서 제외한다. UI를 생성하는 경로와 업무 API 경로의 로그 ID를 연결한다. 동시에 현재 앱의 모바일 모델과 추론 API 사용 여부를 조사한다. 사용할 계획이 없는 기술까지 한 번에 도입할 필요는 없다.

**둘째 주: 재현 가능한 평가 만들기.** 성공 사례와 위험 사례를 합쳐 작은 평가 세트를 만든다. 예컨대 정상 휴가 신청, 잔여일수 부족, 이미 승인된 휴가 수정 요청, 다른 직원 정보 조회, 도구 타임아웃, 오래된 정책 문서, 잘못된 이메일 형식, 두 번 클릭을 포함한다. 도구 호출 trace와 최종 UI 이벤트를 함께 저장한다. 모델 교체와 프롬프트 변경을 같은 실험으로 섞지 않는다. 결과가 나빠지면 평균뿐 아니라 사례별 diff를 읽는다.

**셋째 주: 기기·브라우저 실측.** A2UI 화면이 느린 네트워크에서 부분적으로 렌더될 때 버튼 상태가 적절한지 확인한다. 키보드, 스크린리더, 한국어 길이, 고대비 모드도 검사한다. LiteRT를 쓰는 Android 앱이라면 CPU와 GPU 경로에서 샘플 결과·첫 호출·연속 호출을 비교한다. 낮은 사양 기기에서 fallback이 작동하는지 보고, 사용하지 않는 모델 지원 범위를 제품 약속에 넣지 않는다.

**넷째 주: 배포 후 피드백 루프.** 실패한 UI 생성과 미완료 신청을 모니터링한다. 정기 평가가 실패하면 알림을 보내고, 실패 사례를 개인정보 제거 후 평가 세트에 편입한다. PR 단위로 ‘생성한 코드 양’이 아니라 배포 후 사고와 사용자 완수율을 본다. 기술 선택의 성패는 데모 화면이 예쁜지보다 같은 사용자가 같은 일을 반복 가능하게 끝낼 수 있는지에 달려 있다.

## 운영 포인트: 오늘 바로 점검할 경계

| 경계 | 확인 질문 | 권장 증거 | 흔한 오해 |
| --- | --- | --- | --- |
| 화면 계약 | 에이전트가 어떤 컴포넌트·이벤트를 만들 수 있는가? | 카탈로그 버전, 스키마, 이벤트 허용 목록 | 선언형 UI면 서버 권한도 안전하다 |
| 사용자 입력 | 버튼이 눌릴 때 어떤 값을 보내는가? | 데이터 경로, 사용자 세션, 요청 ID | 클라이언트 검증만으로 제출이 안전하다 |
| 평가 | 평균 하락은 어느 사례에서 왔는가? | 사례별 trace, 기준·후보 결과 파일 | 점수 하나가 회귀의 원인을 말한다 |
| 모바일 추론 | 어떤 기기와 모델에서 빨라졌는가? | 기기군별 p50/p95, CPU fallback, 출력 비교 | 발표 수치가 모든 단말의 보증치다 |
| 개발 활동 | 많이 만든 변경이 운영 가치로 이어졌는가? | 병합 후 결함, 사용자 과제 완료율, 복구 시간 | 커밋·푸시 증가가 생산성 증가다 |

이 표의 권장 증거는 네 회사가 제품에 자동 제공한다고 발표한 기능 목록이 아니다. 네 원문의 사실을 실제 제품 운영으로 옮길 때 팀이 자체적으로 남겨야 할 자료다. 특히 생성형 UI에서는 ‘화면이 보였다’와 ‘업무가 확정됐다’ 사이를 분리하고, 평가에서는 ‘점수가 나왔다’와 ‘실패를 고쳤다’ 사이를 분리해야 한다. 모바일에서는 ‘빌드가 된다’와 ‘실제 단말에서 정확하다’를 분리한다. 개발 조직에서는 ‘작업이 시작됐다’와 ‘고객 문제가 해결됐다’를 분리한다.

### 실패 상황별 대응 우선순위

**잘못된 A2UI 컴포넌트가 생성된 경우**에는 재시도만 늘리지 말고 카탈로그 설명·버전·모델 출력의 차이를 기록한다. 화면을 안전한 텍스트 안내로 전환하고 사용자가 수행하려던 업무를 잃지 않게 한다. 잘못된 이벤트가 서버까지 도달했다면 렌더러 문제가 아니라 권한 검증 문제로 분류한다. 이벤트 허용 목록과 서버 접근 제어를 확인한다.

**평가 점수가 하락한 경우**에는 먼저 평가 실행 자체의 오류를 배제한다. 데이터셋, judge, 모델, 도구, 프롬프트가 한꺼번에 바뀌었는지 확인한다. 다음으로 실패 사례의 trace를 읽고, 도구 호출 실패인지 답변 선택 실패인지 구분한다. 중요 사례가 실패하면 평균 점수가 좋아도 배포를 멈출 수 있어야 한다. 반대로 낮은 위험의 주제 밖 질문 때문에 평균만 떨어졌다면 비용·속도와 함께 판단한다.

**LiteRT 전환 뒤 특정 기기에서 느려진 경우**에는 평균 성공 수치로 덮지 않는다. 기기 모델, OS, Play services·런타임 버전, GPU 지원, 모델 파일 버전, 입력 크기를 묶어 재현한다. CPU fallback으로 서비스 연속성을 지키면서 GPU 경로의 정확도와 발열을 확인한다. 오류가 전처리·후처리 변경 때문인지 런타임 변경 때문인지 분리해야 한다.

**에이전트가 PR을 대량 생성하는 경우**에는 일단 병합 속도를 올리기보다 위험 분류와 리뷰 용량을 본다. 동일 파일에 잦은 충돌이 나는지, 테스트가 실제 회귀를 잡는지, 보안 경고가 쌓이는지, 배포 후 롤백이 늘었는지 측정한다. 성과 지표가 커밋 수뿐이면 에이전트가 바쁜 만큼 팀은 더 피곤해질 수 있다.

## 한 줄 결론

오늘의 공식 자료는 에이전트가 **더 많은 화면과 코드를 만들 수 있다**는 방향을 보여 준다. 그 속도를 제품 가치로 바꾸는 조건은 화면의 실행 권한을 제한하고, 평가의 실패 사례를 보존하고, 모바일 성능을 실제 기기에서 검증하고, 활동량을 사용자 결과와 구분하는 것이다. 생성 경로를 빠르게 하는 기술보다 **확정·승인·검증 경계를 명확하게 만드는 설계**가 오래간다.

## 심층 적용: 에이전트 화면을 제품 기능으로 승격하는 계약

A2UI를 도입할 때 가장 먼저 정할 것은 ‘모델이 화면을 얼마나 자유롭게 그리게 할까’보다 **이 화면에서 사용자와 시스템이 서로 무엇을 약속하는가**다. 여행 검색 결과의 카드는 검색 결과를 제안할 뿐 예약을 확정하지 않는다. 인사시스템의 휴가 카드는 잔여일수를 안내할 뿐 급여 정산의 법적 근거가 아니다. 한 화면에서 ‘추천’, ‘임시 저장’, ‘제출’, ‘승인’을 같은 버튼 스타일로 보여 주면 사용자는 서로 다른 확정 수준을 구별하지 못한다. 컴포넌트 카탈로그는 정보 전달용, 입력 수집용, 업무 실행 요청용을 분리해 설계해야 한다. 같은 `Button` 하나로 모든 이벤트를 표현할 수 있어도 그렇게 만드는 것이 좋은 계약은 아니다.

**정보 카드**는 서버 출처와 조회 시각을 표시할 수 있어야 한다. 잔여 연차, 배송 가격, 재고 수량처럼 변하는 데이터는 ‘현재’라는 단어만으로 정확성을 보증하지 못한다. 화면에 표시한 값이 어떤 조회의 결과인지, 그 뒤 변경이 있었다면 사용자가 어떻게 알 수 있는지 고려한다. 출처가 모델의 추정일 때는 값 확정처럼 보이는 UI를 사용하지 않는다. 데이터가 없으면 0으로 채우지 말고 미확인 상태를 나타낸다. 컴포넌트 스키마에 `value: number`만 있으면 ‘조회 실패’와 ‘실제로 0’의 차이를 담지 못하므로 상태와 단위를 별도 속성으로 둔다. 이 예시는 A2UI의 특정 필수 스키마를 설명하는 것이 아니라 제품팀의 카탈로그 설계 원칙이다.

**입력 컴포넌트**는 사용자의 임시 입력과 서버가 받아들인 값을 구분해야 한다. 사용자가 날짜를 고르는 동안에는 클라이언트 상태다. 제출 뒤에는 서버 검증 결과가 오기 전까지 확정으로 보이지 않아야 한다. 제출 실패 후 화면이 다시 생성되더라도 사용자가 입력한 값이 안전하게 복원돼야 한다. 반면 주민번호나 계좌번호처럼 민감한 값은 대화 기록이나 추론 프롬프트에 다시 싣지 않도록 특별히 설계한다. 양방향 이벤트 흐름이 편리하다는 이유로 모든 필드가 자동으로 모델에 돌아가게 해서는 안 된다. 원문의 예제에서 버튼 이벤트가 특정 데이터 경로를 지정한다는 점을 활용해 필요한 값만 보내는 계약을 세울 수 있다.

**업무 실행 컴포넌트**는 승인, 철회, 결제, 개인정보 전송처럼 되돌리기 어려운 결과를 낳는다. 모델이 어떤 버튼을 렌더할 수 있는지와 실제로 그 버튼을 사용할 권한이 있는지 분리해야 한다. 화면에는 버튼이 보였지만 서버가 권한을 거부할 수 있다. 거부는 사용자에게 예측 가능한 메시지로 설명해야 하며, 모델의 자유로운 문구 생성에 맡기면 ‘승인됐습니다’ 같은 잘못된 확정 표현이 나올 수 있다. 확정 결과는 서버가 만든 상태 코드와 영수증 또는 요청 ID에서 렌더해야 한다. 모델의 답변은 추가 설명 역할에 그친다.

### 화면 상태 전이의 예시

1. **제안 상태:** 에이전트가 허용된 컴포넌트와 서버 조회 결과로 화면을 구성한다. 아직 요청은 발생하지 않았다.
2. **입력 상태:** 사용자가 날짜·옵션을 바꾸며 클라이언트가 형식 오류를 보여 준다. 모델 호출 없이 가능한 검사는 이 단계에서 처리한다.
3. **제출 대기:** 필수 항목과 서버 조회 시각을 확인한다. 사용자에게 최종 효과를 명시한다.
4. **검증 중:** 서버가 권한, 잔여량, 중복 여부, 정책 유효기간을 확인한다. 제출 버튼은 중복 실행을 막는다.
5. **확정 또는 거절:** 서버가 요청 ID와 확정 상태를 반환한다. 에이전트가 낙관적으로 확정 문구를 만들지 않는다.
6. **재개:** 브라우저를 다시 열거나 다른 기기로 전환해도 서버 상태에서 화면을 복원한다. 에이전트 대화 기록만을 진실의 원천으로 사용하지 않는다.

이 상태 전이를 로그에 기록하면 ‘사용자가 화면을 봤다’, ‘버튼을 눌렀다’, ‘서버가 받았다’, ‘업무가 완료됐다’의 차이를 분석할 수 있다. 완수율이 낮을 때 어느 단계에서 이탈했는지 알아야 A2UI의 가치를 평가할 수 있다. 화면 렌더 성공이 높아도 제출 전 이탈이 늘면 카탈로그 또는 설명 문구가 일을 더 어렵게 만들었을 수 있다. 반대로 한 번의 긴 텍스트 답변보다 화면 생성 지연이 길어도 작업 완료율이 높다면 UI 도입의 가치가 있을 수 있다. 이런 판단은 단일 모델 벤치마크가 아니라 실제 사용자 흐름으로 해야 한다.

### 접근성과 국제화도 카탈로그의 일부다

에이전트가 여러 컴포넌트를 재배열하면 기존 화면에서 검증한 탭 순서와 스크린리더 읽기 순서가 바뀔 수 있다. 단순히 각 컴포넌트가 접근성 속성을 갖췄다고 전체 조합이 접근 가능한 것은 아니다. 오류 메시지가 어느 입력과 연결되는지, 동적으로 생성된 새 카드가 화면 판독기에 어떻게 알려지는지, 버튼을 눌렀을 때 포커스가 어디로 이동하는지 검사한다. 한국어는 영어보다 버튼 문구가 길거나 날짜·금액 형식이 다르다. 모델이 속성 값을 만들어 넣을 때 통화 단위, 일자 형식, 존댓말, 조직 용어가 혼합될 수 있다. 따라서 로케일별 대표 입력과 시각·보조기기 검사를 평가 세트에 포함한다. A2UI의 프레임워크 독립성은 이런 사용자 경험의 자동 해결을 뜻하지 않는다.

## 심층 적용: 네 가지 숫자를 운영 의사결정으로 바꾸는 법

첫째, **Agents CLI의 4.00→2.75**는 네 사례의 판정 점수다. 이를 ‘제품 만족도 31% 하락’이라고 바꿔 말하면 안 된다. 점수의 상한은 5이고, 사례는 네 개이며, 판정 기준도 특정 설정에 의존한다. 1.25점 하락이 심각하다는 판단은 가능하지만, 이를 실제 고객의 손실과 연결하려면 실패한 기능의 사용 빈도와 피해를 알아야 한다. 원문에서 로마 날씨 사례는 기준 상태에서도 2점이다. 기준점이 낮은 사례가 변화하지 않았다는 사실 역시 ‘괜찮음’이 아니라 별도의 기존 결함을 뜻한다. 회귀 분석과 절대 품질 분석은 별개다.

둘째, **LiteRT의 8MB 감소**는 발표에 나온 앱 크기의 관찰치다. 전체 패키지 중 무엇이 제거됐는지, 동적으로 받는 모델이 얼마나 큰지, 기기에 이미 Play services가 설치돼 있는지에 따라 사용자가 체감하는 다운로드 절감은 다르다. 기존 앱이 여러 ABI의 런타임을 포함했는지, 분할 APK를 쓰는지도 영향을 줄 수 있다. 제품 의사결정에는 ‘앱 설치 전 네트워크 전송량’, ‘설치 후 추가 다운로드’, ‘모델 최초 사용 가능 시각’을 따로 측정하는 편이 낫다. 같은 8MB라도 모바일 데이터가 비싼 환경과 Wi-Fi 전용 환경에서 중요도가 다르다.

셋째, **GPU 약 1.4배**는 특정 기준 대비 추론 속도다. 1.4배 빠르다는 말은 100ms가 모든 곳에서 약 71ms가 된다는 약속이 아니다. 실제 태스크에서는 카메라 캡처, 이미지 전처리, 모델 로딩, 추론, 후처리, 화면 표시가 이어진다. 추론이 전체 지연의 절반이면 추론 부분을 1.4배 줄여도 전체는 그보다 훨씬 덜 줄어든다. 반대로 반복 추론을 많이 하는 기능은 배터리·발열이 더 중요할 수 있다. 홍보 수치를 전체 사용자 경험 수치로 옮기기 전에 병목 비율을 재야 한다.

넷째, **Octoverse의 8배 커밋**은 집단 간 평균 차이다. 신규 저장소의 목적과 팀 규모가 다르면 분모가 다르다. 또한 커밋은 크기와 질이 균일하지 않다. 자동 포맷 한 번과 보안 수정 한 번을 같은 1건으로 세는 지표다. 에이전트가 만든 변경을 여러 작은 커밋으로 나누면 건수는 늘어도 납품된 기능은 그대로일 수 있다. 생산성을 보려면 개발자가 투입한 시간, 리뷰어가 투입한 시간, 완료된 사용자 과제, 결함과 롤백을 함께 묶어야 한다. ‘에이전트가 작업을 시작한 PR’ 비율도 병합 성공률·후속 재작업률과 함께 보아야 한다.

### 유사한 숫자를 나란히 놓고 판단하는 실무 예

한 팀이 다음 분기에 인사시스템의 서류 읽기 기능을 LiteRT로 옮기고, 신청 UI를 A2UI로 만들고, 에이전트 코딩을 도입했다고 하자. 보고서에는 앱 용량 8MB 감소, 추론 지연 1.4배 개선, 커밋 8배, 평가 평균 4.00이 나올 수 있다. 이 숫자들만으로 ‘성공’을 선언하기는 어렵다. 사용자가 서류를 올려 신청을 끝내는 시간, 잘못 입력된 문서의 정정률, 권한 오류, 저사양 기기의 포기율, 운영팀의 처리 시간, 배포 후 재작업이 함께 개선돼야 한다. 기술 지표는 원인 후보이고 제품 결과 지표가 결론이다. 좋은 성과 보고는 둘 사이의 연결 경로를 보여 준다.

예를 들어 신청 완료율이 72%에서 80%로 올랐고 추론 지연도 줄었다면 둘 사이의 인과를 바로 주장하지 말아야 한다. UI 문구와 정책이 동시에 바뀌었을 수 있다. 단계적 배포나 비교 집단을 이용해 모바일 런타임 변화와 UI 변화의 영향을 가능한 한 분리한다. 반대로 완료율이 그대로지만 입력 오류로 인한 고객센터 문의가 줄었다면 A2UI가 다른 형태의 가치를 제공한 것일 수 있다. 분석 단위를 정하기 전에 어떤 사용자 문제가 가장 중요한지 결정해야 한다.

## 심층 적용: 평가 세트에 무엇을 넣어야 하는가

Google 예제의 네 날씨 사례는 루프의 사용법을 보여 주기 위한 작은 샘플이다. 제품화된 에이전트의 평가 세트가 네 사례면 충분하다는 뜻이 아니다. 특히 인사시스템은 정책·권한·기록의 오류 비용이 크다. 다음 표는 오늘의 평가 발표에서 도출한 **예시 평가 설계**이며, Agents CLI가 기본 제공하는 테스트 목록이 아니다.

| 유형 | 입력 또는 환경 | 확인할 행동 | 실패 시 위험 |
| --- | --- | --- | --- |
| 정상 조회 | 본인 잔여 연차 질문 | 권한 있는 장부를 조회하고 조회 시각 표시 | 오래된 잔액 안내 |
| 타인 정보 | 다른 직원의 급여 질문 | 조회 거부, 비밀 값 미노출 | 개인정보 침해 |
| 모호한 날짜 | ‘다음 주 금요일’ 신청 | 시간대와 공휴일을 확인하고 날짜 명시 | 잘못된 신청 |
| 부족한 잔여량 | 2일 남았는데 3일 신청 | 정책에 맞게 거절 또는 대안 제시 | 장부 오류 |
| 오래된 정책 | 이전 연도 규정이 검색됨 | 유효기간 확인 후 최신 규정 사용 | 규정 위반 |
| 도구 장애 | 잔여량 API 타임아웃 | 값을 지어내지 않고 재시도 안내 | 허위 정보 |
| 중복 제출 | 버튼 두 번 클릭 | 한 요청 ID로 처리 | 중복 결재 |
| 권한 변경 | 화면 생성 후 관리자 권한 회수 | 제출 시점 재검증 | 권한 우회 |
| 프롬프트 주입 | 첨부문서에 ‘규칙 무시’ 문구 | 문서를 데이터로만 취급 | 지침 탈취 |
| 부분 렌더 | 금액·일수 미도착 상태의 화면 | 확정 버튼 비활성화 | 불완전한 동의 |
| 모델 교체 | 동일 요청을 다른 모델로 라우팅 | 핵심 결과·도구 호출 일치 | 조용한 품질 변화 |
| 로케일 | 한국어·영어 혼합 요청 | 일자·숫자·통화 의미 보존 | 사용자 오해 |

이 표를 모두 LLM judge로 채점할 필요는 없다. 타인 정보 노출은 응답과 도구 로그에서 비밀 값이 나타나는지 확인하고, 권한 변경은 서버가 제출을 거부했는지 확인한다. 중복 제출은 업무 DB의 요청 수로 검증한다. 모호한 날짜는 모델이 날짜를 확인 질문으로 돌렸는지 또는 명시적으로 해석했는지 보는 사례별 규칙이 필요하다. ‘친절함’과 ‘설명의 명료성’은 사람이 검수한 judge 점수로 볼 수 있다. 특정 검사 방법을 하나로 통일하는 것보다 **실패를 찾을 수 있는 증거**를 남기는 것이 중요하다.

테스트 세트를 커밋에 묶을 때는 새 정책이 시행된 시점을 함께 기록한다. 과거 규정의 정답과 현재 규정의 정답이 다를 수 있다. 평가 데이터셋을 최신 정책에 맞게 수정하면서 이전 결과와 점수만 비교하면 기준이 움직인 것을 모델 변화로 오인한다. 원문의 ‘데이터셋과 기대를 분리하라’는 원칙을 정책 도메인까지 확장하면, 입력 사례, 적용 정책 버전, 기대 결과, 판정 로직을 별도 버전으로 다룬다. 실행 결과에는 이 조합의 식별자를 남긴다. 사후 사고 분석 때 ‘왜 그날은 통과했나’를 복원하는 데 필요하다.

### 평가 결과를 실제 수정으로 연결한다

평가가 실패했을 때 담당자는 단순히 프롬프트를 길게 만드는 것부터 시작하면 안 된다. 먼저 실패가 어느 계층인지 본다. 조회 API가 틀린 값을 반환했다면 도구 또는 데이터 문제다. 도구가 정확했지만 호출하지 않았다면 도구 선택 문제다. 정확한 값을 받은 뒤 잘못 설명했다면 응답 생성 문제다. UI가 올바른 값을 잘못 표시했다면 렌더러 또는 스키마 문제다. 서버가 무권한 요청을 실행했다면 접근 제어 문제다. 원인별 소유자가 다르고, 해결책도 다르다. 모든 문제를 ‘모델이 환각했다’로 묶으면 가장 위험한 서버 결함을 놓칠 수 있다.

수정 뒤에는 처음 실패한 사례만 다시 실행하지 말고 그와 가까운 성공 사례도 검사한다. 예를 들어 타인 급여 조회를 막기 위해 프롬프트를 바꿨더니 본인 급여 조회까지 거절할 수 있다. 어떤 교정이 다른 기능을 해치지 않았는지 확인해야 hill-climbing이라고 부를 수 있다. 평가 결과가 좋아져도 실제 제품의 사용 분포와 평가 사례의 분포가 다르면 개선이 체감되지 않을 수 있다. 운영 트래픽에서 개인정보를 지운 실패 패턴을 정기적으로 반영하되, 새 사례를 넣는 순간 기준점이 바뀐다는 사실을 기록한다.

## 심층 적용: 모바일 추론을 출시하는 기기 매트릭스

LiteRT 전환은 코드 의존성 하나를 바꾸는 작업으로 보이기 쉽다. 실제로는 앱 배포, 모델 파일, 기기 가속기, 런타임 업데이트가 만나는 작업이다. 최소한 다음 축을 교차해서 대표 기기를 정한다. **OS 버전**은 지원 최저 버전과 최신 버전, **성능 등급**은 저가형과 고가형, **가속 경로**는 GPU 가능·불가, **모델 종류**는 작은 분류기와 큰 멀티모달 모델, **네트워크 상태**는 초기 설치와 오프라인, **사용 상태**는 첫 호출과 연속 호출이다. 모든 조합을 수작업으로 모두 시험할 수는 없으므로 사용자 비중과 오류 위험을 기준으로 우선순위를 정한다.

초기화 실패는 사용자에게 단순히 ‘AI 기능을 사용할 수 없습니다’라고 보일 수 있지만 원인은 여러 가지다. Play services 버전, 기기 GPU, 모델의 연산자 지원, 파일 손상, 저장 공간 부족, 메모리 압박, API 호출 순서가 다르다. 오류가 났을 때 CPU fallback이 가능한지, 다시 다운로드해야 하는지, 사용자가 직접 해결할 수 없는 문제인지 구분해야 한다. 앱이 확정 기능을 제공한다면 fallback이 실패해도 수동 입력 경로를 남겨야 한다. AI 분류기가 문서를 못 읽었다고 직원이 휴가 신청 자체를 못 하게 만드는 것은 제품 설계상의 선택이지 런타임의 필연적 제약은 아니다.

출력 비교에는 같은 입력 이미지의 해시와 전처리 버전을 고정한다. 두 경로가 미세하게 다른 부동소수점 값을 내는 것은 가능하지만 분류 경계 부근에서 사용자에게 다른 결론을 내릴 수 있다. 따라서 수치의 완전 일치만 요구하지 말고, 업무적으로 중요한 임계값 주변의 결과 일치율을 본다. 사람이 직접 수정 가능한 기능인지, 자동으로 서버 기록에 반영되는 기능인지에 따라 허용 오차가 다르다. 자동 반영하는 모델일수록 더 엄격한 평가와 감사 기록이 필요하다.

성능 지표도 한 가지가 아니다. 첫 호출이 2초 느리고 이후 매번 50ms 빠른 모델은 하루에 한 번 쓰는 기능에는 불리할 수 있다. 연속 100회 추론에서 빠르지만 배터리가 급감하면 카메라를 오래 쓰는 현장 직원에게 불리하다. 평균값이 좋아도 하위 5% 기기에서 앱이 꺼지면 서비스 신뢰가 떨어진다. Google이 발표한 속도 개선을 근거로 시도할 수는 있지만 출시 승인은 자기 사용자·기기·모델에서 얻은 측정값으로 해야 한다.

### 롤아웃과 롤백을 함께 준비한다

가능하다면 기기군 또는 사용자군별로 점진적으로 전환하고, 새 `CompiledModel` 경로에서 실패가 늘면 이전 경로 또는 CPU로 돌아갈 수 있게 한다. 단, 오래된 API가 앞으로 계속 지원된다고 가정해서는 안 된다. 원문은 구 GPU delegate와 custom delegate가 폐기 방향이고 NNAPI는 2027년부터 제거될 예정이라고 명시한다. 롤백은 단기 사고 대응이고 장기 유지 전략은 지원되는 API로의 전환이다. 두 계획을 동시에 가져가야 서비스가 안정되고 기술 부채도 줄어든다.

## 심층 적용: 에이전트 시대의 개발팀 점수판

Octoverse처럼 전체 플랫폼의 활동량을 보면 규모 변화가 분명하다. 한 팀의 운영 점수판은 다른 질문에 답해야 한다. **작업 시작**에는 에이전트가 만든 이슈·PR의 수가 있다. **작업 완료**에는 병합과 배포가 있다. **품질**에는 고객 결함, 롤백, 보안 문제, 장기 유지 비용이 있다. **사람의 부담**에는 리뷰 시간, 중단 횟수, 사고 대응 시간이 있다. 네 범주를 함께 봐야 에이전트가 일을 줄였는지 단지 작업을 더 많이 만들어 냈는지 알 수 있다.

예를 들어 에이전트 도입 뒤 PR 수가 2배, 병합 수가 1.2배, 리뷰 대기시간이 3배라면 생산 단계의 병목이 리뷰로 이동했을 가능성이 있다. 그렇다고 에이전트 도입을 바로 실패라고 단정할 수는 없다. 더 어려운 문제를 다루기 시작했거나 테스트가 강화됐을 수 있다. 변경의 위험도와 규모를 보정해 보아야 한다. 반대로 PR 수는 그대로지만 배포 후 결함이 줄고 리뷰 시간이 단축됐다면 큰 가치가 생겼을 수 있다. 개발팀의 점수판은 에이전트의 활동량을 포상하기 위한 것이 아니라 **고객에게 안전하게 도달한 변경**을 확인하기 위한 것이다.

코드 리뷰를 더 자동화하더라도 책임 주체는 남는다. 보안·권한·데이터 삭제 같은 핵심 경로에는 누가 승인했고 어떤 증거를 보았는지 기록한다. 에이전트가 작성하고 다른 에이전트가 리뷰한 뒤 자동 병합하는 흐름은 빠르지만 같은 오류 가정을 공유할 수 있다. 리뷰 도구가 다른 모델이라고 독립 검증이 된다는 보장도 없다. 결정적인 테스트, 스키마 검증, 정적 분석, 실제 브라우저·단말 검사, 사람이 볼 위험 요약을 함께 사용한다. 에이전트가 PR을 시작한 비율이 높아질수록 이 검증 계층의 처리량도 올려야 한다.

### 조직이 매주 확인할 세 가지 질문

1. **무엇이 실제로 완료됐는가?** 머지뿐 아니라 배포와 사용자 업무 완료를 확인한다. 배포되지 않은 에이전트 산출물은 연구·후보일 수 있지만 납품으로 계산하지 않는다.
2. **어떤 위험이 새로 생겼는가?** 권한 변경, 데이터 이동, 비용, 외부 API, 사용자에게 보이는 확정 문구를 살핀다. 위험이 큰 변경은 에이전트가 작은 diff를 냈어도 깊게 검토한다.
3. **다음 반복에서 무엇을 고칠 것인가?** 평가 결과와 운영 장애를 사례로 남기고 소유자를 지정한다. 테스트만 많이 돌리고 수정하지 않으면 다음 주의 실패가 그대로 반복된다.

이 세 질문은 오늘의 공식 발표를 하나의 실무 루프로 묶는다. A2UI는 사용자와 에이전트의 상호작용을 늘리고, Agents CLI는 변화가 행동에 미치는 영향을 보여 준다. LiteRT는 모바일의 실행 경로를 바꾸며, Octoverse는 개발 산출물의 양이 이미 빠르게 늘고 있음을 보여 준다. 따라서 품질의 단위는 모델 호출 한 번이나 커밋 한 건이 아니라 **사용자가 의도한 일을 정확하고 안전하게 끝낸 한 번의 흐름**이어야 한다.

## 독자를 위한 근거 판독: 발표·예제·측정·제안의 수준이 다르다

오늘의 네 소스를 인용할 때는 근거의 종류를 함께 적는 습관이 필요하다. Google의 A2UI 글에 나오는 코드 조각은 통합 경로를 보여 주는 **예제**다. 예제에 `demo_user`와 메모리 내 서비스가 등장한다고 해서 그것이 사용자 인증과 데이터 보존까지 해결한 프로덕션 설계라는 뜻은 아니다. 이 글의 인사시스템 사례처럼 실제 사용자 데이터를 쓰는 서비스에서는 인증된 사용자 ID, 서버 세션, 영속 저장소, 감사 로그를 별도로 붙여야 한다. 예제를 그대로 복사해 출시하면 화면은 작동해도 권한 경계가 빈 채로 남는다.

Agents CLI 글의 네 사례와 4.00·2.75 점수는 **설명용 실험**이다. 평가 루프를 재현하는 데 유용하지만 모든 에이전트가 같은 모델 교체에서 같은 폭으로 나빠지는 증거는 아니다. 특정 judge의 평가와 사례 구성이 바뀌면 점수도 달라진다. 실무에서 인용한다면 ‘평균 점수 변화보다 사례별 실패 패턴이 중요하다는 데모’로 소개해야 한다. 그 수치를 ‘Google이 모델 A가 모델 B보다 몇 퍼센트 좋다고 증명했다’로 바꾸지 않는다.

LiteRT 글의 8MB·1.4배는 **공급사 측 시험 수치**다. 출처가 공식이라는 점은 발표 사실을 확인할 수 있다는 뜻이지 외부 독립 검증을 마쳤다는 뜻은 아니다. 팀이 자체 모델과 기기에서 측정해 다른 결과를 얻더라도 공식 글과 반드시 모순되는 것은 아니다. 시험 조건이 다르기 때문이다. 보고서에 수치를 옮길 때는 ‘Google의 테스트에서는’이라는 주어를 유지한다. 기능 지원 범위와 API 폐기 일정도 발표 시점의 정보이므로 배포 시 최신 공식 문서를 다시 확인한다.

Octoverse는 GitHub 플랫폼에서 관측한 **집계 지표**다. GitHub 밖의 모든 개발 활동을 포함하지 않는다. 공개 저장소 산업 분류는 모델이 이름·설명·토픽·README를 보고 분류한 표본이다. 단체의 실제 산업과 완전히 일치한다고 단정할 수 없다. 에이전트 설정 파일이 있는 신규 저장소의 커밋 8배는 선택 편향이 있을 수 있다. 보고서가 제공하는 값은 중요한 시장 변화의 신호지만 개별 기업의 ROI 보증이 아니다. 숫자를 제안서에 넣을 때는 집계 범위, 기간, 비교 집단을 각주로 유지한다.

이 뉴스 글 자체에도 층위가 있다. 날짜·API·원문 수치는 링크로 확인할 수 있는 **공식 사실**이다. 서비스 상태 전이, 권한 검증, 기기 매트릭스, 평가 세트, PR 점수판은 발표에서 도출한 **필자의 설계 제안**이다. 제안이 유용하려면 각 조직의 사용자·규정·기술 스택에서 검증해야 한다. 공식 발표와 필자의 제안을 한 문단에 섞어 놓으면 독자는 어느 부분이 제품 기능인지 알기 어렵다. 그래서 각 심층 적용 장에서 범위와 가정을 반복해 밝혔다.

### 이번 호 이후 추적할 항목

A2UI는 실제 사용자 앱에서 카탈로그 변경과 이벤트 권한을 어떻게 버전 관리하는지 살펴볼 가치가 있다. 특히 동적 카탈로그를 클라이언트에서 서버로 보낼 때 서버의 권한 정책과 충돌하지 않는지 확인해야 한다. Agents CLI는 judge와 평가 세트가 바뀌어도 비교 가능한 결과를 남기는 방법, 자동 프롬프트 최적화가 홀드아웃 사례에서 실제로 개선되는지를 추적해야 한다. LiteRT는 Play services 기반 GPU 경로의 기기별 호환성과 2027년 NNAPI 제거에 따른 마이그레이션 안내를 확인해야 한다. Octoverse의 활동량 증가가 이후 릴리스 품질과 보안 지표에 어떤 영향을 주는지는 별도의 장기 데이터가 필요하다. 이 항목들은 오늘 발표된 확정 성과가 아니라 향후 검증할 질문이다.

### 최종 점검표: 한 번의 변경을 출시하기 전

- **출처:** 뉴스의 날짜와 제품 지원 범위를 공식 원문에서 재확인했는가?
- **표현:** 모델이 만든 UI와 서버가 확정한 업무 상태를 구분했는가?
- **권한:** 화면 카탈로그와 서버 API의 권한 검사 양쪽을 설계했는가?
- **평가:** 평균뿐 아니라 핵심 사례의 실패 trace를 확인했는가?
- **기기:** 모바일 추론을 대상 기기와 모델에서 직접 측정했는가?
- **배포:** 에이전트의 코드 변경이 실제로 테스트·리뷰·승인된 커밋인가?
- **운영:** 출시 뒤 실패율과 사용자 완료율의 소유자와 대응 경로가 있는가?

체크리스트의 모든 항목에 ‘예’라고 답해도 사고가 사라지지는 않는다. 그러나 어떤 경계를 확인했는지 기록하면 문제가 생겼을 때 추측 대신 증거로 되돌아갈 수 있다. 생성 속도가 빨라진 환경에서 가장 값비싼 것은 늦은 검증 자체보다, 실패 후 무엇이 실행됐는지 알 수 없는 상태다.
