# AI Daily News | 2026년 11월 26일

**확인 시점: 2026년 11월 26일 11:30 KST.** 오늘의 새 소식은 모델의 놀라운 시연보다 모델을 **반복해서 믿고, 운영비를 배분하고, 입력·출력 데이터를 통제하는 방법**에 가깝다. Google DeepMind는 일상적인 기초 질문을 작은 변형에도 안정적으로 맞히는지 평가하는 Humanity’s First Exam(HFE)을 공개했다. GitHub는 Copilot 코드 리뷰의 비용 부담 주체를 명시적으로 설정하지 않은 조직에 대해 12월 30일부터 기본값을 바꾼다고 예고했다. AWS는 Amazon Bedrock의 Trusted Access API와 Anthropic 모델용 Enterprise Frontier Safeguards(EFS)·Enterprise Data Controls(EDC)를 발표했다. HFE는 11월 25일 KST에, GitHub 공지는 11월 26일 KST 아침에 확인 가능한 신규 발표다. AWS 건은 11월 24일 발표된 운영상 중요한 후속 분석 대상이다.

이 세 뉴스는 서로 다른 층위의 질문을 던진다. **HFE는 ‘답을 반복해서 맞히는가’**, **GitHub 공지는 ‘AI 리뷰의 사용 비용을 누가 부담하는가’**, **AWS 발표는 ‘안전 검토를 위해 남기는 모델 대화 자료를 어디에 두고 누가 관리하는가’**를 묻는다. 시험 성적, 비용 정책, 데이터 보관 방식을 한 가지 ‘AI 성능’ 지표로 합쳐서는 안 된다. 오늘 글은 공식 발표와 문서를 바탕으로 확정된 내용, 시행 예정인 내용, 운영팀이 별도로 검증해야 할 가정을 분리한다.

**핵심 판독:** Google이 말하는 544개 문항과 20개 기초 능력은 일반적 지능 전체를 대표하는 표본이라는 뜻이 아니다. GitHub의 기본값 변경은 모든 Copilot 리뷰가 무조건 조직에 청구된다는 뜻이 아니다. AWS의 EFS는 ‘데이터를 아무 곳에도 남기지 않는다’는 뜻이 아니다. 세 발표 모두 짧은 제목만 읽으면 정반대의 운영 결론에 도달할 수 있다.

## 배경 — 추론 능력이 올라가도 운영 신뢰성은 별도 축이다

지난 몇 년간 AI 제품의 발표는 종종 더 높은 벤치마크 점수, 더 어려운 코딩 문제, 더 긴 컨텍스트를 중심으로 구성됐다. 하지만 기업용 애플리케이션이 실제로 받는 질문은 매번 수학 올림피아드 문제처럼 어렵지 않다. 사용자가 사진 속 표지판의 글자를 읽어 달라고 하거나, 문서의 특정 페이지에서 날짜를 찾아 달라고 하거나, 이미 알려진 내부 절차를 변형된 표현으로 다시 묻는 일이 많다. 이때 중요한 것은 한 번의 최고 성적보다 **비슷한 요청 1,000건 중 얼마나 자주 같은 품질을 내는가**다.

신뢰성은 모델 자체의 정답률만이 아니다. 답이 틀릴 때 사람이 발견할 수 있는가, 여러 번 재시도하면 비용이 얼마나 늘어나는가, 안전 검토와 감사에 필요한 기록은 어디에 쌓이는가, AI가 수행한 코드 리뷰의 청구 항목을 어느 팀이 책임지는가가 모두 제품 신뢰성의 일부다. 모델이 하나의 작업을 잘한다는 실험과 그 모델을 실제 업무 흐름에 넣는 결정은 분리해야 한다.

오늘의 세 공식 발표는 이 분리를 구체적으로 보여 준다. HFE는 ‘쉬운 문제도 변형하면 흔들릴 수 있다’는 평가 설계를 제안한다. GitHub는 자동화가 워크플로에 더 깊이 들어올수록 **비용의 기본값**이 제품 기능만큼 중요해진다는 사실을 보여 준다. Bedrock은 안전 정책 때문에 보관이 필요한 고성능 모델에서 **어디에, 어떤 키로, 누가 검토할 기록을 남길지**를 배포 아키텍처로 만들고 있다. 이 셋을 묶는 공통어는 ‘AI의 통제 가능성’이지만, 통제의 대상은 각각 결과, 비용, 데이터로 다르다.

### 무엇이 오늘 새롭고 무엇이 아닌가

Google의 HFE 발표는 Google 공식 RSS에 11월 24일 19:30 UTC, 곧 11월 25일 04:30 KST로 표시된다. GitHub의 청구 기본값 공지는 공식 Changelog RSS에 11월 25일 22:18 UTC, 곧 11월 26일 07:18 KST로 표시된다. AWS Bedrock 글의 RSS 게시 시각은 11월 24일 05:01 UTC다. 따라서 오늘의 가장 신선한 실무 변경은 GitHub의 과금 공지이고, HFE는 전날 새벽부터 읽을 수 있었던 평가 발표다. AWS 내용은 바로 오늘 처음 발표된 것처럼 포장하지 않고, 두 소식에 연결되는 중요한 운영 기준으로 다룬다.

OpenAI 공식 뉴스 인덱스에서 가장 최근에 표시된 것은 11월 24일 과학 발표 두 건으로, 11월 25일자 이 사이트 글에서 이미 상세히 다뤘다. 오늘 새 OpenAI 모델이 출시됐다고 주장하지 않는다. Google·GitHub·AWS의 공식 인덱스 및 원문을 확인했고, `web_search`는 이 실행 환경의 API 키 부재로 동작하지 않아 기사 출처로 사용하지 않았다. 검색 실패가 곧 신규 발표 부재를 증명하는 것은 아니다. 이 글은 **확인한 공식 자료의 범위** 안에서만 판단한다.

## Top News 1 — Humanity’s First Exam: ‘한 번 할 수 있다’와 ‘매번 할 수 있다’의 차이

[Google DeepMind의 HFE 소개](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/humanitys-first-exam/)는 기존 모델 평가가 수학·코딩·과학처럼 분야별 높은 능력의 상한을 주로 측정해 왔다고 지적한다. 새 평가는 정반대 방향의 질문을 던진다. 비교적 직관적인 일상 문제를 한 번 풀 수 있느냐가 아니라, **표현이나 시각 요소가 조금 달라져도 일관되게 해결하느냐**다. Google이 공개한 규모는 텍스트와 이미지 프롬프트 544개, 기초 능력 20개다. 공개 리더보드와 [기술 보고서](https://storage.googleapis.com/deepmind-media/papers/hfe_tech_paper.pdf)를 연결하고, 12월 15일까지 커뮤니티가 현재 모델이 틀리는 일상 질문을 제출하도록 [Kaggle 이벤트](https://www.kaggle.com/benchmarks/deepmind/hfe)를 열었다.

공식 소개의 예시는 네온사인에 쓰인 각 단어의 세 번째 글자 색깔을 순서대로 말하라는 이미지 질문이다. 정답은 `green; yellow; white; blue; blue`로 제시됐다. 문제 자체는 고급 수학이 아니다. 하지만 글자를 정확히 식별하고, ‘단어별 세 번째’라는 지시를 유지하고, 색을 해당 글자와 정확히 연결하고, 순서를 보존하며, 출력 형식을 맞혀야 한다. 어느 단계 하나가 흔들리면 설명은 그럴듯해도 최종 답이 틀릴 수 있다. **개별 단계가 쉬운 것과 결합된 작업이 안정적인 것은 다르다.**

HFE의 의의는 모델 순위를 하나 더 만드는 데만 있지 않다. 제품 개발자가 자신이 쓰는 모델을 평가할 때 ‘어려운 과제 1개 성공’과 ‘쉬운 과제 100회 중 99회 성공’을 다른 차트에 올려야 한다는 신호다. 예를 들어 고객지원 앱이 결제일을 찾는 작업에서 한 번 멋진 설명을 만들더라도, 날짜의 월·일을 가끔 뒤집으면 운영에서 곧바로 문제가 된다. 의료·금융·행정에서 실패 한 번의 비용이 크다면 평균 정답률과 최악 구간을 함께 봐야 한다.

### 기초 문항 544개를 읽는 올바른 방법

숫자 544는 이번 공개 세트의 크기다. 기업 업무 전체, 모든 언어, 모든 사용자 집단, 모든 입력 품질을 포괄한다는 뜻이 아니다. 능력 20개 또한 제품 요구사항 목록이 아니다. 공식 글은 지난 6개월 동안 프런티어 모델이 HFE에서 상당한 진전을 이뤘다고 말하지만, 소개문만으로 개별 모델의 모든 세부 점수나 통계적 유의성을 확정하지 않는다. 리더보드는 현재 관찰된 결과를 볼 곳이고, 기술 보고서는 평가 구성과 제한을 확인할 곳이다. 오늘 글은 원문의 짧은 소개에 없는 수치나 승자를 꾸며 넣지 않는다.

벤치마크를 운영에 연결하려면 먼저 **측정 단위**를 결정해야 한다. 개별 문항 하나를 맞혔는지, 유사 변형 묶음을 전부 맞혔는지, 동일 입력을 여러 번 돌려 같은 답을 냈는지, 정답을 못 찾았을 때 자신 있게 틀렸는지, 모른다고 정확히 말했는지의 점수는 다르다. ‘일상적 질문의 신뢰성’을 목표로 한다면 평균 정확도만으로는 같은 묶음 안에서의 취약성을 감추기 쉽다.

가령 A 모델이 동일한 종류의 요청 10개 중 9개를 맞힌다고 하자. 평균은 90%지만, 10개가 모두 같은 업무 흐름의 필수 단계라면 그 흐름을 끝까지 오류 없이 통과할 확률은 독립이라는 매우 단순화된 가정 아래 약 35%다. 이 수치는 HFE의 실측값이 아니라 **반복 결합의 위험을 설명하는 가상 계산**이다. 실제 실패는 독립적이지 않을 수 있다. 특정 이미지 배경이나 언어 표현에 실패가 몰리면 더 나빠질 수도 있다. 그러므로 ‘쉬운 문항의 높은 평균’과 ‘실서비스의 긴 작업 흐름’ 사이에 곧바로 등호를 놓지 말아야 한다.

### 작은 변형을 왜 별도로 측정하나

프롬프트 변형은 단순한 말장난이 아니다. 사용자는 `요약해줘`, `핵심 세 줄`, `중요한 점만`처럼 같은 의도를 여러 방식으로 표현한다. 화면 캡처는 해상도·테마·압축·다크 모드·언어 설정에 따라 달라진다. 문서 표는 같은 내용을 다른 페이지 레이아웃으로 표시한다. 특정 정답을 기억하거나 특정 이미지 스타일에 적응한 모델이 실제 환경에서도 같은 추론을 하는지는 별도 질문이다. 변형 평가가 필요한 이유다.

단, 변형을 마구 늘리면 또 다른 문제가 생긴다. 원래 문제와 변형 문제의 난도가 실제로 같은가? 이미지에서 글자가 작아진 것이 ‘사소한’ 차이인가, 불가능에 가까운 차이인가? 애초에 정답이 하나로 고정되는가? 여러 문화권에서 ‘상식’이라고 부르는 정보가 같은가? HFE가 일상 신뢰성의 중요한 측면을 드러내더라도, 개별 제품은 자신의 사용자·언어·자료 조건에 맞춘 별도 평가 세트를 만들어야 한다.

### 리더보드를 제품 선택에 활용할 때

리더보드의 장점은 모델별 비교를 한눈에 볼 수 있다는 것이다. 위험은 점수 한 줄이 내부 업무의 성패와 같다고 믿는 것이다. HFE에는 이미지와 텍스트가 포함되지만, 실제 서비스는 긴 대화 맥락, 도구 호출, 문서 권한, API 실패, 지연시간, 재시도 비용이 얽힌다. 실서비스에서 쓰는 시스템 프롬프트와 도구 구성, 출력 스키마가 벤치마크와 다르면 순위도 바뀔 수 있다. HFE 점수는 **평가해야 할 질문을 알려주는 신호**이지, 구매 승인서가 아니다.

개발팀은 공개 리더보드를 본 뒤 다음 네 가지를 내부에서 따로 시험할 수 있다. 첫째, 자주 발생하는 사용자 질문을 실제 로그에서 개인정보를 제거한 형태로 추출한다. 둘째, 의미가 같은 문장 변형과 이미지 품질 변형을 만든다. 셋째, 모델과 프롬프트 버전을 고정한 뒤 반복 실행해 ‘항상 맞음’, ‘가끔 맞음’, ‘항상 틀림’을 나눈다. 넷째, 틀렸을 때 피해가 큰 유형에는 인간 검토나 결정론적 검증을 붙인다. 이것은 HFE가 제공하는 기능이라고 주장하는 것이 아니라, 발표 취지를 제품 평가로 옮긴 편집상의 제안이다.

### 평가 세트에 반드시 남길 메타데이터

정답 문자열만 저장하면 왜 틀렸는지 분석하기 어렵다. 문항에는 입력 종류(텍스트/이미지), 요구한 세부 동작(식별·계산·순서·형식), 정답 채점 방식, 난도에 영향을 주는 품질 정보, 언어, 변형 묶음 ID, 정답의 출처를 붙여 두는 편이 좋다. 실행 결과에는 모델명과 버전, 호출 시점, 시스템 프롬프트, 온도 등 생성 설정, 도구 사용 여부, 원본 응답, 최종 채점 결과, 실패 유형을 남긴다. 데이터가 민감하다면 이 모든 필드를 그대로 보관하라는 뜻이 아니다. 재현성과 개인정보 최소화 사이의 내부 정책을 먼저 정해야 한다.

특히 *실패 유형*을 나누는 것이 중요하다. 이미지 속 글자를 잘못 읽은 경우와 글자는 맞게 읽었으나 세 번째 글자 위치를 잘못 셈한 경우는 개선 방법이 다르다. 출력 형식만 틀린 경우에는 검증기나 스키마 강제의 효과가 클 수 있다. 모델의 시각 인식이 흔들리는 경우에는 더 좋은 이미지, 다른 입력 경로, 사람 확인이 필요할 수 있다. 전체 점수보다 실패의 구조가 엔지니어링 결정을 이끈다.

### 왜 ‘기본값’이 운영 뉴스인가

AI 기능의 과금 변경에서 가장 큰 리스크는 단가보다 **설정의 빈칸**인 경우가 많다. 팀은 어떤 정책을 명시적으로 선택한 적이 없을 수 있다. 화면에는 지금까지 `Default (Member)`라고 보이므로 ‘Member를 선택했다’고 생각할 수도 있다. 그러나 기본 표시와 저장된 명시적 선택은 다르다. GitHub 공지는 변경 전까지 미설정 항목에 안내를 보여 주며, 계속 구성원의 entitlement를 쓰려면 Copilot 정책 설정에서 `Member`를 직접 선택하라고 한다. 엔터프라이즈가 이 설정을 관리한다면 엔터프라이즈 소유자가 그 결정을 해야 한다.

이 소식이 개발자에게 중요한 이유는 코드 리뷰 자동화의 사용량이 개인 활동처럼 보여도 비용 책임은 저장소의 조직에 귀속될 수 있기 때문이다. 특히 많은 저장소에서 자동 리뷰를 켜고, 새 push마다 다시 리뷰를 요청하거나, 여러 팀이 한 조직의 저장소를 함께 쓰는 곳에서는 비용 배부 기준이 실제 워크플로와 어긋날 수 있다. GitHub 문서는 사용자 설정, 저장소 ruleset, 조직 ruleset의 자동 리뷰 조건이 독립적으로 적용될 수 있다고 설명한다. 여러 조건이 맞더라도 하나의 리뷰만 게시된다고 하지만, 어떤 정책이 리뷰를 유발하는지 관리자는 알아야 한다. 비용·사용량의 원인을 이해하려면 ‘누가 버튼을 눌렀는가’뿐 아니라 ‘어떤 규칙이 자동 요청했는가’를 기록해야 한다.

## Top News 3 — Bedrock Trusted Access: 모델 안전 검토의 저장 위치를 선택하다

[AWS 공식 블로그](https://aws.amazon.com/blogs/machine-learning/introducing-the-amazon-bedrock-trusted-access-api-with-anthropics-enterprise-frontier-safeguards-and-enterprise-data-controls/)는 Trusted Access Program API를 일반 제공한다고 발표했다. 이 API는 모델 제공업체의 프로그램을 발견하고, 자격 상태를 확인하고, 가입하는 절차를 한곳으로 묶는다. 첫 제공 항목은 Anthropic과 함께 만든 EFS 및 EDC이며 **공개 프리뷰**다. 여기서 가장 중요한 시제 구분은 **API의 일반 제공과 개별 프로그램의 프리뷰는 다르다**는 것이다.

고성능 모델의 일부 사용에서는 오용 탐지와 정책 준수를 위해 프롬프트와 응답 기록을 일정 기간 보존해야 한다. 모델 제공자나 클라우드 공급자가 해당 기록을 검토하는 방식이 고객의 데이터 통제 요구와 충돌할 수 있다. EFS와 EDC는 이 긴장 관계를 각각 다른 저장·암호화 방식으로 풀려는 선택지다. 둘 다 자동 안전 모니터링이 위험을 감지하면 고객이 사례를 검토하는 흐름이지만, 기록이 놓이는 장소와 키 소유자가 다르다.

### EFS와 EDC의 실제 차이

EFS에서는 유지되는 입력·출력 데이터가 고객 AWS 계정의 S3 버킷에 저장되고 고객의 AWS KMS 키로 암호화된다. AWS 블로그에 따르면 Amazon Bedrock은 해당 유지 데이터의 사본을 자체 저장소에 보관하지 않으며, 사람 검토는 고객팀이 담당한다. 자동 안전 모니터링은 AWS 운영 환경에서 수행된다. 위험 신호가 있으면 사례 파일을 고객 버킷에 만들고, 고객은 관련 기록을 살펴본 뒤 응답을 작성한다. EFS는 *보관이 없다는 뜻*이 아니다. **보관 위치와 키·사례 검토권이 고객 쪽이라는 뜻**이다.

EDC는 유지 데이터를 Amazon 관리 저장소에 AWS 관리 키로 암호화해 저장한다. 자체 버킷·키 구성이 필요 없고, 고객팀이 플래그된 사례를 검토한다. AWS 문서는 EDC의 Amazon 관리 저장소 기록은 최대 30일 후 삭제되는 형태를 설명한다. 반면 EFS는 고객 버킷의 수명주기 규칙이 적용되며 최소 보관기간 등 문서상 조건을 따라야 한다. 고객에게 운영 편의가 중요한지, 저장 위치와 키 관리가 중요한지에 따라 선택이 달라진다. 둘 중 하나를 ‘더 안전하다’고 일반화할 수 없다. 요구사항과 실제 구성 오류 가능성을 함께 봐야 한다.

| 쟁점 | EFS | EDC | 선택 시 질문 |
| --- | --- | --- | --- |
| 기록 위치 | 고객 AWS 계정의 S3 버킷 | Amazon 관리 저장소 | 사내 정책은 데이터 위치를 어떻게 규정하는가. |
| 암호화 키 | 고객 KMS 키 | AWS 관리 키 | 키 정책·회전·감사 책임을 감당할 팀이 있는가. |
| 검토 | 자동 모니터링 후 고객이 사례 검토·응답 | 고객이 플래그된 사례 검토 | 누가 어떤 시간 안에 사례를 처리하는가. |
| 운영 부담 | 버킷, 키, 정책, 지역별 구성, 수명주기 필요 | 저장소 인프라 운영이 상대적으로 단순 | 단순성보다 통제권이 우선인가. |
| 가시성 | 고객 계정의 CloudTrail에서 키 사용 및 설정한 S3 데이터 이벤트 등을 확인 가능 | 고객 계정에서 AWS 관리 저장소 내부 접근 가시성은 다름 | 감사에 필요한 증거는 어느 계정에서 수집할 수 있는가. |
| 상태 | Anthropic 모델 관련 첫 제공 항목은 공개 프리뷰 | 동일 | 프리뷰 변경 가능성과 시험 트래픽 원칙을 수용할 수 있는가. |

AWS 문서는 대상 모델의 범위를 Claude Fable, Claude Mythos, Cyber Verification Program(CVP)을 통한 Claude Opus 5.5 및 Sonnet 5.5로 설명한다. 이는 **모든 Bedrock 모델의 모든 호출**이 EFS·EDC 대상이라는 뜻이 아니다. 계정의 자격, 가입 범위, 사용 리전, 대상 모델, 데이터 보관 모드를 확인해야 한다. 문서는 프리뷰에 먼저 시험 계정과 시험 트래픽을 사용하고, PII·PHI 같은 규제 데이터를 넣지 말라고 명시한다. 이 내용은 기능을 평가할 때의 실질적 운영 경계다.

### ‘제로 데이터 보관’과의 관계는 특히 조심해야 한다

AWS 문서는 공개 프리뷰에 가입하는 계정 또는 프로젝트의 기존 zero data retention(ZDR) 예외가 꺼지고, EFS 또는 EDC 방식으로 내용이 유지된다고 알린다. 다른 계정의 ZDR은 유지될 수 있다. 또한 자격을 갖춘 고객은 현재 Claude Fable 모델과 기존 CVP 모델에 대해 내부 사용용 임시 ZDR 예외를 적어도 2027년 6월 30일까지 이용할 수 있다고 설명한다. 이는 날짜가 오면 무조건 모든 계정이 자동 이전한다는 뜻은 아니다. 각 고객의 자격·구성·AWS의 후속 안내가 중요하다.

프라이버시 담당자가 ‘보관하지 않는 모델’을 요구한다면 EFS를 그냥 ZDR의 다른 이름으로 승인해서는 안 된다. 반대로 안전팀이 사고 조사와 오용 검토의 증거를 요구한다면 ZDR만으로 모든 목적을 해결할 수 있다고도 말할 수 없다. 둘 사이의 균형은 **어떤 자료를 얼마 동안, 누구의 계정에서, 어떤 접근 경로로 유지할지**라는 명시적인 설계 결정이다.

### 프로그램 API와 저장 설정은 다른 계층

Trusted Access API는 제공 항목을 조회하고 자격·가입 상태를 관리하는 공통 문이다. 실제 저장소의 버킷·키 정책, 데이터 보관 모드, 지역별 설정은 별도 구성이다. `eligible` 상태가 나왔다고 모델 호출의 모든 데이터 흐름이 원하는 위치로 자동 이동하는 것이 아니다. AWS 문서는 EFS-only 계정에서 고객 버킷 구성이 완료되지 않으면 대상 모델 호출이 거부될 수 있다고 설명한다. 프리뷰 계정의 자동 ZDR 전환과 저장 목적지 준비를 원자적인 하나의 단계로 생각하면 운영 사고가 날 수 있다.

또 하나의 범위는 지역이다. 문서는 저장 설정을 호출하는 리전마다 준비하도록 안내한다. 교차 리전 추론을 쓰더라도 EFS의 유지 기록은 호출의 소스 리전에 설정된 버킷으로 간다고 설명한다. ‘미국 리전에 버킷 하나 만들었으니 모든 리전 호출이 그곳에 기록된다’는 가정은 위험하다. 지역별 호출 목록, 소스 리전, 적용되는 계정·프로젝트 설정의 우선순위를 표로 확인해야 한다. 이 검사는 데이터 상주 요구뿐 아니라 사고 조사 시 기록 누락을 막기 위한 것이다.

### 사례(case) 검토는 사람의 업무다

자동 모니터링이 위험을 발견하면 사례가 생기고, 고객이 이를 읽고 `violation` 또는 `no_violation` 같은 응답을 남기는 흐름이 AWS 문서에 설명돼 있다. 자동 분류는 최종 판정이 아니다. 사례를 처리할 사람, 기한, 재검토 기준, 기록 보존을 정하지 않으면 저장 위치를 고객 계정으로 옮긴 의미가 줄어든다. 반대로 모든 원문 기록을 지나치게 넓은 운영팀에 열어두면 최소 권한의 원칙에 어긋날 수 있다. 데이터 통제는 물리적 저장 위치만이 아니라 **누가 어떤 근거로 열람하고 판단하는가**까지 포함한다.

AWS 문서에는 EFS에서 `transcripts/`와 `review-cases/`, `review-responses/` 같은 경로가 설명돼 있다. 운영팀은 실제 문서 버전에 맞춰 파일 구조와 알림·응답 절차를 검토해야 한다. 오늘 글이 S3 객체를 직접 읽거나 테스트 계정을 만들었다는 뜻은 아니다. 공식 자료에 기재된 운영 모델을 분석한 것이다. 프리뷰 구현 상세는 바뀔 수 있으므로 적용 직전 문서를 다시 확인해야 한다.

### 비용과 장애를 같은 표에 놓기

AWS 문서는 EFS·EDC 자체의 별도 요금이나 모델 가격·속도 제한 변경은 없다고 설명하면서, EFS의 표준 S3·KMS 비용과 조건에 따라 데이터 전송 비용이 발생할 수 있다고 안내한다. 이것은 ‘무료 운영’을 의미하지 않는다. 저장소, 키, 감사 로그, 사례 검토 인력, 자동화 개발에 비용이 든다. 특히 고객 키나 버킷에 대한 Bedrock 접근을 제거하면 대상 모델 서비스에 영향이 생길 수 있다는 설명이 있다. 키 삭제나 정책 변경을 단순 정리 작업으로 취급하지 말아야 한다.

GitHub 과금 공지와 비교하면 흥미로운 공통점이 드러난다. 기능의 정가가 변하지 않아도 **누가 비용을 부담하는지**와 **어디에 비용이 쌓이는지**가 달라진다. GitHub는 AI 리뷰 비용의 청구 주체, AWS는 데이터 보관과 검토의 운영 비용·책임 주체가 핵심이다. 둘 다 제품 구매 계약보다 실제 설정과 기본값이 중요하다.

## 개발자에게 의미 — 평가, 청구, 데이터 흐름을 하나의 릴리스 점검으로

개발자는 종종 모델 선택을 ‘성능이 좋은가, API가 빠른가, 가격이 싼가’ 세 항목으로 요약한다. 오늘 뉴스는 그 표에 빠진 열을 보여 준다. **동일 유형의 일상 작업에서 실패가 얼마나 들쭉날쭉한지**, **자동화가 누구의 예산으로 실행되는지**, **모델이 남기는 안전 기록을 어느 계정이 관리하는지**가 필요하다. 세 열은 서로 상쇄되지 않는다. HFE 점수가 높아도 민감한 기록을 잘못 보관하면 출시할 수 없고, 강한 데이터 통제를 구현해도 자동 리뷰 비용을 예측하지 못하면 확대하기 어렵다.

예를 들어 사내 문서 Q&A 에이전트가 매일 수천 건의 질문에 답한다고 하자. 제품팀은 정답률 95%를 자랑할 수 있다. 하지만 ‘퇴직금 지급일’처럼 오류 한 건이 사람에게 직접 영향을 주는 질문에서는 5% 실패가 허용되지 않을 수 있다. 프롬프트 한 줄을 바꾸면 갑자기 오답률이 높아진다면 평균 정답률은 신뢰를 설명하지 못한다. 모델을 교체하거나 새 버전을 배포할 때에는 HFE의 문제의식처럼 **작은 변형에서의 일관성**을 확인하고, 실패 비용에 따라 사람이 확인하도록 설계해야 한다.

그 에이전트의 코드가 여러 저장소에서 자주 수정되고 Copilot 리뷰가 자동 요청된다면, 팀은 코드 리뷰 자체의 품질과 비용을 살펴야 한다. 리뷰가 테스트가 놓친 결함을 얼마나 잡았는지, 반대로 근거 없는 수정 요청 때문에 작업 시간이 늘었는지 확인한다. 동시에 새해 예산에 자동 리뷰의 청구 주체를 반영한다. ‘개발자가 사용하니 개발자 개인 비용’ 또는 ‘조직 저장소이니 무조건 조직 비용’이라는 직감보다 정책 화면의 실제 상태를 먼저 본다.

만약 그 에이전트가 Bedrock의 대상 Anthropic 모델을 쓴다면 모델 요청·응답의 안전 검토 기록은 또 다른 설계 대상이다. 데이터 보관이 가능한 자료인지, 고객 버킷에 둘지 AWS 관리 저장소에 둘지, 사례 검토 인력이 있는지, 어떤 리전에 호출하는지 확인한다. 이 단계는 모델 성능 실험과 분리할 수 있지만, **정식 출시 승인에서는 함께 보아야 한다**. 기술적 실패, 비용의 예산 초과, 기록의 부적절한 저장은 사용자에게 모두 서비스 실패로 보이기 때문이다.

### 팀별 ‘관찰 가능한 사실’ 목록

| 팀 | 오늘의 질문 | 최소한 남길 증거 |
| --- | --- | --- |
| 모델·평가 | 쉬운 요청의 변형과 반복에서 얼마나 자주 실패하나 | 버전 고정된 평가 세트, 변형 묶음별 결과, 실패 유형 |
| 프런트엔드·제품 | 사용자가 오답을 눈치채고 정정할 수 있나 | 원문 출처 표시, 확신이 낮은 결과의 확인 흐름, 사용자 수정 기록 |

이 표는 벤더가 통합 대시보드를 제공한다는 뜻이 아니다. 서로 다른 공식 발표를 **한 릴리스 검토 회의에서 읽기 위한 편집자의 구조**다. 각 팀이 자신의 증거만 들고 오면 전체 서비스의 오류 경로를 놓치기 쉽다. 서로 다른 지표를 한 장에 모으되, 이를 하나의 ‘AI 점수’로 합치지는 않는다.

## 운영 포인트 — 이번 주와 12월의 실질적 체크포인트

### 이번 주: AI 평가를 ‘평균’에서 ‘최악 구간’까지 넓힌다

HFE를 그대로 복제할 필요는 없다. 먼저 실제 제품에서 실패했을 때 가장 곤란한 작업 10개를 정한다. 작업마다 대표 입력 하나와 의미가 같은 변형 입력을 여러 개 만든다. 텍스트라면 어순·표현·언어·불필요한 주변 문장을 바꾸고, 이미지라면 밝기·잘림·압축·배경과 글꼴을 바꾼다. 정답이 변하지 않아야 하는 변형과 정답이 달라져야 하는 변형을 구분한다. 앞의 경우 일관성, 뒤의 경우 민감도를 볼 수 있다.

결과는 전체 평균뿐 아니라 작업별·변형 묶음별로 요약한다. `정답 1회 / 10회`와 `정답 9회 / 10회`의 차이를 알기 쉽도록 표시한다. 똑같은 입력을 반복했을 때 흔들리는지, 표현을 바꿀 때 흔들리는지도 분리한다. 제품팀은 사용자에게 보여 주는 UI에서 어떤 결과를 자동 확정하고 어떤 결과를 검토하도록 할지 이 자료로 결정한다. 이 과정에 사용한 실제 고객 자료는 권한과 개인정보 정책에 맞게 처리한다.

### 12월 30일 전: Copilot 정책의 ‘빈칸’을 없앤다

모든 조직이 `Member`를 선택해야 하는 것은 아니다. 예를 들어 코드 리뷰가 조직의 필수 보안·품질 체계라면 조직이 비용을 부담하는 편이 더 자연스러울 수 있다. 반대로 리뷰 요청이 개인 사용량 한도 안에서 자율적으로 이뤄지고 별도 조직 예산이 없다면 `Member`가 맞을 수 있다. 중요한 것은 공지 이후에도 과거의 기본값이 유지될 거라고 생각하며 **설정을 비워두는 실수**를 피하는 것이다. 저장된 선택과 기본 표시를 구별하고 담당자가 정책을 명시적으로 정해야 한다.

정책 변경은 기술팀 혼자 승인하기 어렵다. 저장소 소유 조직이 청구되므로 재무 담당자와 예산 책임자가 알아야 한다. 엔터프라이즈에서 중앙 관리 중이면 엔터프라이즈 소유자가 설정 주체다. 리뷰 자동화 범위를 정하는 저장소·조직 ruleset 소유자와 과금 정책 소유자가 다르면, 서로의 변경을 알 수 있도록 기록을 남겨야 한다. 12월 30일이 오기 전 정책의 기준선과 설정자·설정 시각을 적어두면 이후 청구 차이를 설명하기 쉽다.

### Bedrock 프리뷰: 시험 계정에서 데이터 흐름부터 검증한다

EFS/EDC는 프리뷰이므로 AWS 문서의 권고대로 시험 계정에서 시험 트래픽으로 시작한다. 대상 모델과 가입 범위를 확인한 뒤, EFS라면 각 호출 리전의 버킷·키와 정책을 준비한다. EDC라면 Amazon 관리 저장소가 내부 요구사항에 맞는지 확인한다. 기존 ZDR 예외가 프리뷰 가입 범위에서 꺼진다는 점을 관계자에게 미리 알린다. 그 뒤 실제 시험 호출에서 기록과 CloudTrail 가시성, 사례 발생 시 처리 경로를 검증한다. 단순히 API의 `eligible` 응답이나 IAM 권한 부여만 보고 데이터 보관 설계가 끝났다고 판단하지 않는다.

이 준비에는 실패 시나리오도 포함해야 한다. 키가 비활성화되거나 버킷 정책이 바뀌면 호출에 어떤 영향이 생기는가? 지역별 구성 하나가 누락되면 기록은 어디로 가는가? 사례 검토자가 휴가 중이면 누가 대체하는가? 보관기간이 끝난 뒤 법무·감사 대응에 필요한 최소 기록은 무엇인가? 실제 정식 도입에 앞서 이 질문에 답해야 한다. 모델 제공자의 새 기능을 시험하는 단계와 민감한 운영 자료를 흘려보내는 단계를 같은 날 처리하지 않는 편이 안전하다.

## 심층 분석 — 세 소식을 연결하는 ‘통제면’ 설계

오늘의 발표를 더 깊게 보면 AI 제품에는 적어도 세 개의 통제면이 필요하다. 첫째는 **결과 통제면**이다. 모델이 언제 답을 내고 언제 인간·기계 검증으로 넘길지 정한다. HFE는 이 통제면을 설계할 때 단순 정답률 대신 일관성 자료가 필요하다는 점을 상기시킨다. 둘째는 **비용 통제면**이다. 어떤 자동화가 실행됐고 비용이 어느 예산으로 귀속되는지 정한다. GitHub 공지는 미설정 기본값이 비용 통제면의 일부라는 사실을 보여 준다. 셋째는 **데이터 통제면**이다. 입력·출력·안전 검토 기록이 어디에 남고 누가 열람하는지 정한다. AWS의 EFS/EDC는 이것을 클라우드 배포 옵션으로 구현한다.

세 통제면은 서로 연결돼 있지만, 한 컨트롤로 묶어서는 안 된다. 예를 들어 정확도 문제를 해결하려고 같은 요청을 세 번 반복하면 결과 통제면은 좋아질 수 있어도 비용 통제면은 악화된다. 오답을 조사하려고 모든 모델 대화를 영구 보관하면 사후 분석은 쉬워질 수 있지만 데이터 통제면의 부담이 커진다. 비용을 아끼려고 모든 자동 리뷰를 끄면 실질적인 결함 발견 능력이 떨어질 수 있다. 정책 결정에는 **교환관계가 있다**. 좋은 아키텍처는 각각을 따로 측정하고, 변화가 다른 면에 미치는 영향을 기록한다.

### 사례 1: 반복 추론으로 신뢰성을 올릴 때

사용자 질문의 답을 모델 한 번이 아니라 여러 번 생성해 합의하는 방식을 생각해 보자. 특정 문제에는 도움이 될 수 있다. 하지만 서로 같은 잘못된 전제에 의존하면 세 번 모두 틀릴 수 있다. 모델 호출량이 늘어 비용과 지연도 커진다. 민감한 내용이 각 호출과 기록에 반복되면 보관 대상도 늘 수 있다. 따라서 ‘반복하면 믿을 수 있다’가 아니라, 실제 변형 평가에서 얼마나 개선됐고 비용·데이터 요구가 얼마나 늘었는지 함께 측정해야 한다. HFE의 문제의식을 적용할 때도 이 점이 핵심이다.

### 사례 2: 자동 코드 리뷰를 조직 단위로 넓힐 때

개발팀이 모든 PR에 Copilot 리뷰를 붙이면 사람이 놓치는 문제를 더 빨리 볼 수 있다. 한편 사소한 스타일 제안과 중복 경고가 늘어날 수 있다. GitHub의 과금 기본값이 조직 쪽으로 바뀌는 조건이라면 이 사용량은 조직의 비용으로 잡힌다. 좋은 운영은 ‘모든 PR’이라는 설정 하나로 끝나지 않는다. 어떤 저장소·브랜치·변경 규모에서 자동 요청할지, 새 push에도 재검토할지, 인간 리뷰어가 AI 의견을 어떻게 검증할지, 사용량과 결함 탐지 효과를 어떻게 결합해 볼지 정해야 한다. 이 판단은 GitHub가 공지한 청구 정책과 별개의 내부 제품 정책이다.

### 사례 3: 안전 검토 기록의 소유권을 바꿀 때

Bedrock의 EFS를 선택하면 고객의 저장 통제력이 높아진다. 동시에 버킷·키·정책·수명주기·사례 처리 운영을 고객이 맡는다. EDC를 선택하면 기반 저장소 구성 부담이 적지만, AWS 관리 저장소라는 점이 데이터 상주·감사 요구에 맞는지 검토해야 한다. 어느 선택이든 ‘모델 호출이 성공한다’만 확인해서는 부족하다. 안전 검토가 작동하는지, 사례가 관계자에게 전달되는지, 사람이 실제로 응답할 수 있는지 검증해야 한다. 특히 프리뷰에서는 기능·문서가 바뀔 수 있어 변경 관리가 필요하다.

### 의사결정 기록에 남길 일곱 문장

1. 우리가 자동화하려는 업무와 실패했을 때의 영향은 무엇인가.
2. 어떤 공개 벤치마크와 어떤 내부 평가가 그 업무에 관련되는가.
3. 일상 작업의 변형·반복에 대한 최소 허용 신뢰성은 얼마인가.
4. 기능을 호출하는 권한과 사용량·비용의 책임자는 누구인가.
5. 입력·출력·감사 자료가 남는 장소와 기간, 접근 권한은 무엇인가.
6. 벤더 기본값이 바뀌면 어떤 정책이 자동으로 달라지는가.
7. 한 달 뒤 어떤 측정 결과가 나오면 현재 결정을 되돌릴 것인가.

이 문장들은 어떤 벤더가 제공하는 공식 양식이 아니다. 모델 도입 회의를 발표 자료의 낙관적 숫자에서 벗어나게 만드는 최소 질문이다. 오늘의 세 공식 자료는 각각 다른 문장을 채우는 근거가 된다.

## 실무 가이드 A — ‘일상 신뢰성’을 평가 가능한 요구사항으로 바꾸기

HFE가 던진 질문을 실무에 가져오려면 먼저 무엇을 ‘같은 일’이라고 부를지 정해야 한다. 한 사용자가 사내 규정에서 휴가 일수를 묻는 상황을 예로 들자. ‘올해 며칠 쉴 수 있나요’와 ‘연차 발생 일수 알려줘’는 대체로 같은 의도지만, 입사일·직종·사용한 휴가가 다르면 정답도 달라진다. 평가를 만들 때 입력의 표현만 바꾸고 사실 조건을 고정한 세트와, 사실 조건을 조금 바꿔 정답이 달라져야 하는 세트를 나누지 않으면 신뢰성을 잘못 측정한다. 전자는 불필요한 민감도를 찾고, 후자는 필요한 민감도를 찾는다.

첫 세트의 좋은 모델은 동의어, 어순, 문장 길이가 달라져도 같은 근거를 찾아 같은 결론을 내린다. 둘째 세트의 좋은 모델은 조건이 달라진 만큼만 답을 바꾸고, 판단에 필요한 정보가 부족하면 추가 정보를 요청한다. 두 작업을 모두 ‘일관성’이라는 한 숫자로 묶으면 위험하다. 사용자가 입사일을 바꿨는데도 똑같은 연차 일수를 내는 모델은 표면적으로는 일관되지만 실제로는 둔감한 것이다. HFE가 말하는 작은 변형을 실무에 적용할 때 **변형에 불변이어야 하는 속성과 반응해야 하는 속성**을 별도 주석으로 붙여야 한다.

평가 문항을 만드는 책임도 분리한다. 제품팀은 사용자가 자주 묻는 질문과 실패했을 때의 영향을 정한다. 도메인 담당자는 정답과 허용 가능한 예외를 확정한다. 평가 담당자는 문항을 과하게 튜닝하지 않도록 보류 세트를 관리한다. 개발팀은 모델과 프롬프트를 바꾸되 평가 정답을 무단으로 바꾸지 않는다. 이 역할 분리가 없으면 배포 직전 점수를 좋게 만들려고 어려운 문항을 버리거나 정답을 모델 출력에 맞춰 수정하는 유혹이 생긴다. 신뢰성을 측정하려던 평가가 신뢰성을 숨기게 되는 것이다.

### 1단계: 실패 비용을 세 구간으로 나눈다

모든 틀린 답에 같은 대응을 붙이면 비용이 지나치게 크거나 위험이 남는다. 첫 구간은 오답이 쉽게 발견되고 영향이 작은 업무다. 예를 들어 마케팅 초안의 비핵심 표현은 사용자가 고치기 쉽다. 두 번째 구간은 오답이 후속 업무에 전달되지만 사람이 확인할 수 있는 업무다. 코드 리뷰의 제안, 내부 문서의 요약, 데이터 분류가 여기에 들어갈 수 있다. 세 번째 구간은 오답이 권리·돈·보안·건강에 영향을 주거나 원상복구가 어려운 업무다. 같은 95% 정확도라도 세 번째 구간에서는 자동 확정의 근거로 부족할 수 있다.

구간은 모델이 아니라 **업무 결과의 영향**으로 정해야 한다. 같은 모델이 작성한 문구도 초안으로 보여 주는 것과 고객에게 발송하는 것은 위험이 다르다. 같은 이미지 판독도 사진의 분위기를 묘사하는 것과 계좌번호를 읽어 송금하는 것은 다르다. 그러므로 HFE 같은 공개 벤치마크는 모델의 기본 행동에 대한 힌트를 줄 수 있어도, 어떤 업무를 자동화할지 결정하는 위험 분류를 대신하지 않는다.

### 2단계: 변형 묶음을 만든다

문항 하나에 변형을 무작정 열 개 붙이는 것보다, 변형의 목적을 명시하는 편이 낫다. 표현 변형은 의미가 같은 질문을 다른 문장으로 쓴다. 순서 변형은 같은 사실을 다른 순서로 제시한다. 잡음 변형은 무관한 문장을 넣고 모델이 핵심 조건을 잃는지 본다. 멀티모달 변형은 캡처의 크기·명암·압축률을 조정한다. 경계 변형은 정답을 구별하는 값 하나만 바꾼다. 형식 변형은 같은 내용을 JSON, 표, 문장으로 요구한다. 한 묶음에 여러 요인을 한꺼번에 바꾸면 실패 원인을 알기 어렵다. 처음에는 요인 하나씩 바꾸고, 기본 행동을 이해한 다음 복합 변형을 추가한다.

평가 데이터에 날짜·통화·언어가 들어가면 기준 시점과 지역을 고정해야 한다. ‘오늘’이나 ‘최근’이 포함된 문항은 실행일에 따라 정답이 변한다. 한국어와 영어를 섞은 업무에서 언어별 정확도 차이를 확인해야 한다. 실제 사용자 문장을 사용할 때는 동의와 내부 정책에 맞춰 비식별화한다. 평가 세트에 개인정보를 그대로 복사해 넣는 것은 나중에 모델 로그·외부 도구·리포트로 확산되는 위험을 만든다. 신뢰성 시험의 데이터 흐름 자체도 데이터 통제면의 일부다.

### 3단계: 결과를 평균 외에 네 방식으로 본다

첫째는 **문항별 정확도**다. 가장 기본이지만 반복 실패가 특정 유형에 집중되는지 알 수 없다. 둘째는 **묶음 완전 성공률**이다. 같은 원문의 모든 변형을 맞힌 비율을 본다. 셋째는 **실패의 심각도**다. 단순 형식 오류와 잘못된 금액·사람·정책 안내를 구분한다. 넷째는 **오답 발견 가능성**이다. 모델이 원문 근거를 보여 주는가, 검증기가 오류를 잡을 수 있는가, 사용자가 쉽게 교정할 수 있는가를 본다. 모델의 점수가 같더라도 오류가 눈에 잘 띄는 제품과 조용히 누적되는 제품의 위험은 다르다.

정확도가 95%라고 할 때 분모도 써야 한다. 전체 실행 횟수 중 95%인지, 문항 중 95%인지, 사용자 세션 중 95%인지에 따라 의미가 다르다. 어떤 문항은 여러 번 반복했고 다른 문항은 한 번만 실행했다면 단순 실행 평균이 특정 문항에 쏠릴 수 있다. 모델 A가 쉬운 질문에서 좋은 대신 위험도가 높은 질문에서 나쁘다면 전체 평균이 더 높아도 도입하지 않을 수 있다. **모델 선택은 사용 빈도와 실패 비용을 함께 고려한 업무 가중치**에 달려 있다. 이 가중치는 제품팀의 결정으로 공개·검토 가능해야 한다.

### 4단계: 오답을 고치는 순서를 정한다

평가가 실패를 드러내면 곧바로 프롬프트를 길게 추가하는 방식은 지속되기 어렵다. 먼저 입력 정보가 충분한지 본다. 정답이 문서에 없거나 도구가 권한 때문에 못 읽었다면 모델을 바꾸어도 해결되지 않는다. 둘째, 오류가 결정론적으로 잡히는지 본다. 날짜 형식, 수치 합계, JSON 구조는 프로그램 검증을 붙일 수 있다. 셋째, 모델의 추론·시각 인식이 흔들리는지 본다. 이때 모델·해상도·도구·프롬프트 대안을 비교한다. 넷째, 높은 위험의 결과를 사람이 검토해야 하는지 결정한다. 마지막으로 동일 실패가 다시 발생하지 않도록 평가 문항과 모니터링 지표에 남긴다.

프롬프트 수정 하나가 문제 유형 A를 고쳐도 유형 B를 악화시킬 수 있다. 그래서 수정 전후에는 전체 평가 묶음을 다시 돌려야 한다. 이때 이미 개발자가 반복해서 본 문항뿐 아니라 보류해 둔 문항을 함께 본다. HFE의 공개 데이터셋도 시간이 지날수록 최적화 대상이 될 수 있다. 자체 평가에서는 개발·검증·보류 데이터를 분리하는 기본적인 실험 규율이 여전히 필요하다.

## 실무 가이드 B — 코드 리뷰 자동화의 단위 경제학

GitHub의 공지를 비용 문제로만 보면 ‘누가 결제하나’에서 멈춘다. 그러나 조직이 실제로 판단할 것은 리뷰 한 건의 **순가치**다. AI가 발견한 문제 중 사람이 확인해 수정한 비율, 이후 장애나 보안 결함을 줄였는지, 사람 리뷰어의 시간을 절약했는지, 반대로 중복·오탐 처리로 시간을 더 쓰게 했는지를 기록해야 한다. AI 리뷰는 인간 리뷰와 정적 분석을 완전히 대체하는 것이 아니라 한 추가 채널이다. 비용이 조직에 청구되든 구성원에게 귀속되든 품질 판단은 필요하다.

간단한 내부 원장에는 네 종류의 이벤트를 나눠 적을 수 있다. 첫째, 리뷰가 **요청**됐는가. 둘째, 실제로 리뷰가 **게시**됐는가. 셋째, 개발자가 제안을 **확인·수정·기각**했는가. 넷째, 결함이 후속 테스트나 운영에서 **발견**됐는가. 요청 건수만 보면 GitHub ruleset이나 자동 옵션의 효과는 보이지만, 유용한 검토였는지 알 수 없다. 수정 건수만 보면 원래도 고쳤을 문제인지 구분하기 어렵다. 비용과 가치를 비교하려면 분모와 사건 순서가 필요하다.

비용 귀속의 관점에서는 개인 계정, 저장소 소유 조직, 엔터프라이즈 정책이라는 세 층위를 구별한다. 저장소는 A 조직 소유인데 코드를 바꾼 개발자는 B 조직에 속할 수 있다. 단일 회사 안에서도 중앙 플랫폼 조직이 저장소를 소유하고 여러 제품팀이 기여할 수 있다. GitHub 공지의 기본값은 **저장소 소유 조직**을 가리킨다. 내부 비용 배부를 기여자 소속 팀으로 하고 싶다면 그것은 GitHub 기본 청구 외에 조직이 별도로 설계할 회계 규칙이다. 공지 자체가 부서별 비용 자동 배부를 제공한다고 해석해서는 안 된다.

### 과금 설정 변경을 검토하는 예시 회의

첫 질문은 ‘현재 정책에 명시적 값이 저장돼 있나’다. 값이 저장돼 있으면 이번 공지의 기본값 변경이 그 선택을 덮어쓰지 않는다. 둘째 질문은 ‘우리 조직은 리뷰를 필수 품질 게이트로 보는가, 개인 생산성 도구로 보는가’다. 필수 게이트라면 비용을 조직이 감당하고 사용 기준을 정하는 것이 논리적일 수 있다. 개인 도구라면 구성원 entitlement를 유지할 수 있다. 셋째는 ‘자동 리뷰가 어디서 발생하는가’다. 개인 설정과 저장소·조직 ruleset이 다르게 켜져 있다면 관리자가 사용량을 잘못 예상할 수 있다. 넷째는 ‘AI Credits 유료 사용과 billing lock 등 예외 조건이 있는가’다. 이 조건에 따라 미설정 계정의 전환 결과가 달라진다.

회의의 결과는 선택값 한 글자보다 근거가 중요하다. `Member`를 선택했다면 구성원별 사용 한도와 비용 경험을 어떻게 안내할지 적는다. `Organization`을 선택했다면 어떤 저장소에 자동 리뷰를 허용하고 비용 경보를 어떻게 받을지 적는다. 자동 리뷰를 운영하지 않기로 했다면 코드 품질을 다른 경로에서 어떻게 확보할지 적는다. 날짜를 12월 30일 이전으로 명시하고, 이후 GitHub 청구 정보와 정책 화면을 비교하는 검증 일정을 잡는다. 이것이 **기본값의 우연을 조직의 의도로 바꾸는 작업**이다.

### ‘리뷰가 하나만 게시된다’의 함정

GitHub 문서는 여러 자동 요청 원인이 겹쳐도 Copilot이 한 개의 리뷰를 게시한다고 설명한다. 이 설명은 중복 요청이 무조건 중복 게시물을 만든다고 걱정할 필요가 없다는 뜻이다. 그러나 규칙이 여럿 적용되는 상태를 그냥 방치해도 된다는 뜻은 아니다. 어느 ruleset이 리뷰를 요구하는지 모르면 나중에 리뷰 범위를 줄이거나 늘릴 때 예상치 못한 저장소가 영향을 받는다. 또한 새 push에 대한 재리뷰 설정이나 초안 PR 리뷰 설정이 어디에서 켜졌는지도 별도로 봐야 한다. 리뷰 게시 개수와 자동화 정책의 복잡도는 다른 지표다.

자동 리뷰의 품질을 측정할 때는 AI가 지적한 수보다 *실제로 유의미한 수정으로 이어진 지적*을 세는 편이 낫다. 그러나 이 역시 편향이 있다. 개발자가 지적을 무시했지만 실제로는 맞는 경우도 있고, 맞는 제안이라도 이미 테스트가 잡았을 수 있다. 따라서 샘플 PR을 사람이 재검토해 ‘유효한 발견’, ‘기존 도구와 중복’, ‘근거 부족’, ‘문맥 오해’를 나누면 유용하다. 특정 언어나 저장소 구조에서 오탐이 몰리면 정책을 전체적으로 끄기 전에 그 범위를 조정할 수 있다.

### 월별 운영 지표의 예

정량 지표는 많을수록 좋지 않다. **자동 리뷰를 게시한 PR 수**, **사람이 실제로 검토한 AI 지적 수**, **수정으로 이어진 유효 지적 수**, **오탐에 쓴 사람 시간의 표본 추정**, **조직 청구 비용**, **실제 장애·보안 결함의 사후 발견 수** 정도부터 시작한다. 지표 옆에는 자동 리뷰가 켜진 저장소 범위와 ruleset 버전을 적는다. 범위가 늘어나면 비용과 발견 수가 함께 늘 수 있으므로 단순 전월 대비로 품질이 좋아졌다고 판단하지 않는다.

공식 과금 공지는 가격표나 무상 한도를 자세히 설명하지 않는다. 따라서 조직별 예상 금액은 실제 계약과 사용량을 확인해야 한다. 오늘 글의 원장 설계는 비용을 특정 수치로 예측하려는 것이 아니라, 기본값 변경을 **비용 원인의 관측 가능성**으로 연결하려는 제안이다. 사용량을 전혀 관찰하지 않은 채 12월 말부터 청구 주체만 바꾸면 가격 논쟁이 생산성 논쟁을 덮을 수 있다.

## 실무 가이드 C — 안전 데이터 보관을 아키텍처 결정으로 기록하기

Bedrock의 EFS·EDC 선택은 클라우드 콘솔의 체크박스 하나로 끝나지 않는다. 모델 호출의 **소스 리전**, 가입 범위인 **조직·계정·프로젝트**, 적용되는 **모델 목록**, 저장 목적지, 키 소유자, 사고 대응팀이 모두 결정에 들어간다. 프리뷰를 시험할 때는 이 다섯 항목을 한 장의 그림이나 표로 적어야 한다. 누가 모델을 호출하는지 모른 채 저장 버킷만 만들면 한 리전에서는 기록이 고객 계정에 남고 다른 리전은 기대와 다르게 동작할 수 있다.

AWS 문서에 따르면 EFS에서 고객 계정 버킷을 쓰려면 S3 버킷과 KMS 키가 호출 리전에 맞게 준비되고 정책이 서비스 접근을 허용해야 한다. 이 제약은 보안을 강화하는 동시에 새로운 실패 모드를 만든다. 키 정책을 바꾸거나 키를 비활성화하면 데이터 해독뿐 아니라 대상 모델 제공에도 영향이 생길 수 있다. 고객 키가 있으면 통제권이 높아진다는 말의 반대면은 고객이 키 운영을 잘못하면 서비스가 중단될 수 있다는 뜻이다. 키를 ‘보안팀만 관리하는 독립 자산’이 아니라 **모델 서비스의 운영 의존성**으로 다뤄야 한다.

버킷의 수명주기 정책도 설계 항목이다. 보관기간을 너무 짧게 잡으면 사례 조사 전에 기록이 없어질 수 있고, 필요 이상으로 길게 잡으면 개인정보·규제 위험과 저장 비용이 커진다. 공식 문서가 요구하는 최소 보관 조건을 먼저 확인하고, 회사의 데이터 분류 기준과 조사 기간을 조화시켜야 한다. 데이터가 S3에 있다고 해서 자동으로 적절히 삭제되는 것은 아니다. 삭제 정책, 버전 관리, 백업, 접근 로그, 복제 여부가 함께 맞아야 한다. 공지의 ‘고객 버킷’이라는 한 단어 뒤에 실제 운영 책임이 많이 숨어 있다.

### 사전 시험에서 남길 관찰 자료

테스트 호출의 시간과 소스 리전, 대상 모델 ID, 계정·프로젝트 식별자, 적용한 저장 설정의 버전, CloudTrail 이벤트, S3 객체 생성 여부, 데이터 삭제 예정일을 남긴다. 이때 시험 프롬프트는 합성 자료를 사용한다. 실제 주민번호·고객 상담 내용·의료 기록을 ‘정상 동작 확인’이라는 이유로 보내지 않는다. AWS 문서가 프리뷰에서 시험 트래픽만 사용하고 PII·PHI를 보내지 말라고 권고하는 이유는 기능을 검증하는 도중 데이터 정책을 앞질러 가면 되돌리기 어렵기 때문이다.

사례 처리 테스트는 조심해서 설계한다. 실제 악용 입력을 만들 필요 없이, 문서가 제공하는 절차와 샘플 케이스 처리 방법을 관계자와 확인한다. 알림이 어느 팀으로 가는지, 사례 파일을 누가 읽을 수 있는지, 응답은 어떤 권한으로 작성하는지, 휴일이나 담당자 부재 시 경로가 있는지 살펴본다. 공식 문서에는 EFS의 사례가 고객 버킷에 도착하고 응답을 남기는 구조가 설명돼 있으나, 개별 조직의 인력·근무 체계까지 제공하지 않는다. 사람 검토의 책임을 넘겨받는다는 것은 담당자를 이름으로 정하는 일이다.

### EDC가 더 단순하지만 질문이 사라지는 것은 아니다

EDC는 고객 버킷·키를 직접 구성하지 않아 초기 설정이 가벼울 수 있다. 그렇다고 데이터 통제 책임이 전부 사라지는 것은 아니다. 어떤 계정이 프리뷰에 가입했는지, 대상 모델 호출의 자료가 Amazon 관리 저장소에 유지되는지, 보관기간과 지역 조건이 사내 규정에 맞는지 살펴야 한다. 고객팀이 사례를 검토해야 한다는 점도 같다. 특히 고객 계정의 CloudTrail에 고객 키·버킷 접근이 나타나는 EFS와, AWS 관리 저장소 내부 흐름을 고객 계정에서 같은 방식으로 보지 못하는 EDC는 감사 방식이 다르다. 감사 담당자의 요구 증거가 무엇인지 먼저 정해야 한다.

### 임시 ZDR 예외를 그대로 둬도 되는가

ZDR은 입력·출력을 보관하지 않는다는 점에서 민감한 자료 보호에 직관적으로 유리해 보인다. 하지만 대상 모델의 안전 정책과 고객의 사용 자격, 내부 사용 조건, 임시 예외의 기간이 함께 붙는다. AWS 문서는 자격을 갖춘 고객에게 기존 예외를 적어도 2027년 6월 30일까지 제공한다고 적었다. 이는 장기 설계를 아무것도 하지 않아도 된다는 면허가 아니다. 향후 조건 변화에 대비해 현재 어떤 계정이 어떤 예외를 쓰는지 기록해야 한다. EFS/EDC 프리뷰 가입 시 해당 계정·프로젝트에서 ZDR이 꺼질 수 있으므로, 두 상태 사이의 전환을 데이터 처리 변경으로 승인받아야 한다.

데이터 보관을 논의할 때는 ‘우리의 프롬프트는 민감하지 않다’는 단순화도 피한다. 평범해 보이는 요청에도 고객 이름, 내부 코드, 저장소 경로, 재무 수치, 보안 사고 설명이 섞일 수 있다. 사용자 입력뿐 아니라 모델 출력이 기밀을 재구성할 수도 있다. 따라서 EFS 버킷의 접근권한과 EDC 채택 여부는 모델에 무엇을 입력하는지에 대한 제품 정책과 연결돼야 한다. 가장 엄격한 통제 방식을 선택했다고 해서 애플리케이션의 데이터 최소화가 불필요해지는 것은 아니다.

## 비교 실험 — 세 벤더 발표를 같은 기준으로 읽는 법

오늘의 뉴스는 각 회사가 다른 문제를 푼다. 그래서 ‘Google이 평가, GitHub가 비용, AWS가 보안에서 앞섰다’처럼 우열을 매길 수 없다. 대신 발표문을 읽을 때 공통 질문을 적용하면 과장을 줄일 수 있다. **누가 발표했는가?** HFE의 성과 설명은 평가를 만든 Google의 글이다. GitHub 청구 동작은 정책 소유자인 GitHub의 공지다. Bedrock 저장·안전 검토 방식은 서비스 제공자인 AWS의 문서다. 각 회사가 자기 시스템의 기능과 일정에 대해 1차 출처라는 점은 강점이지만, 독립적 효과 검증을 대신하지 않는다.

**무엇이 현재 동작하고 무엇이 예정인가?** HFE의 벤치마크·Kaggle 경로는 공개돼 있다. GitHub 기본값의 전환일은 미래인 12월 30일이다. Bedrock의 공통 API는 일반 제공이고 EFS·EDC는 공개 프리뷰다. 이 차이를 기사 제목에서 보존해야 한다. ‘출시’, ‘공개’, ‘예고’, ‘프리뷰’는 같은 동사가 아니다. 뉴스 독자는 시제 하나로 오늘 무엇을 시험하고 무엇을 준비할지 결정한다.

**어떤 분모와 범위가 있는가?** HFE의 544문항은 일상 문제 전체가 아니다. GitHub 변경의 대상은 유료 라이선스 구성원의 코드 리뷰 중 과금 설정이 저장되지 않은 경우다. EFS·EDC는 대상 Anthropic 모델과 자격을 얻은 계정·프로젝트의 특정 흐름이다. 숫자나 기능명만 따면 발표가 모든 사용자와 모든 모델에 적용되는 것처럼 보인다. 범위가 빠진 요약은 운영에서 가장 위험한 요약이다.

**누가 다음 검증을 해야 하는가?** HFE 점수가 실제 한국어 업무에 유효한지는 제품팀이 내부 평가로 확인한다. GitHub 과금 설정이 예상 계정으로 청구되는지는 조직 관리자와 재무팀이 12월 이후 확인한다. Bedrock 데이터가 원하는 저장 목적지에 남고 사례 검토가 운영되는지는 플랫폼·보안팀이 시험 계정에서 확인한다. 공식 발표의 사실과 고객 환경에서의 작동은 서로 다른 관찰 단계다. 어느 회사의 공식 글도 독자의 내부 환경에 대해 자동으로 증명하지 않는다.

### 편집자를 위한 제목 점검

‘Google이 AI 신뢰성을 해결했다’는 제목은 HFE가 **측정 도구**라는 사실을 지운다. ‘GitHub가 모든 Copilot 리뷰를 조직에 청구한다’는 제목은 미설정·유료 라이선스·Business/Enterprise·예외 조건을 지운다. ‘AWS가 Claude 입력을 보관하지 않는다’는 제목은 EFS·EDC의 유지 데이터 흐름을 거꾸로 설명한다. 정확한 제목은 길더라도 범위를 남긴다. 이 글의 제목에 ‘쉬운 질문의 신뢰성, 코드 리뷰 비용, 모델 데이터 통제’라고 쓴 이유가 여기에 있다. 세 회사의 브랜드를 나열하는 것보다 독자가 무엇을 확인해야 하는지 드러내는 편이 유용하다.

## 팀 회의에 가져갈 질문 30개

아래 질문들은 세 발표의 핵심 주장과 그 바깥에 남은 결정을 구분하기 위한 것이다. 답은 벤더 페이지에 모두 있지 않다. 특히 ‘우리 팀’에 관한 답은 내부 로그·정책·계약을 확인해야 한다.

1. 우리가 자동화하려는 가장 흔한 일상 작업은 정확히 무엇인가?
2. 그 작업에서 답이 틀렸을 때 누가 피해를 보고, 얼마나 빨리 발견할 수 있는가?
3. 한 번의 정답과 반복적인 정답을 다른 지표로 기록하고 있는가?
4. 문장 표현이 바뀌어도 답이 같아야 하는 경우와, 조건이 바뀌면 달라져야 하는 경우를 구분했는가?
5. 이미지 입력의 압축·해상도·밝기가 실제 사용 환경을 대표하는가?
6. 평가 문항의 정답은 누가 언제 어떤 근거로 승인했는가?
7. 공개 벤치마크의 데이터가 모델 학습이나 프롬프트 조정에 노출됐을 가능성을 고려했는가?
8. 한국어 사용자의 질문과 영어 공개 벤치마크 사이의 간극을 별도로 측정했는가?
9. 전체 평균이 좋은 모델이 가장 위험한 작업에서도 좋은가?
10. 틀린 답을 검증기·인간·사용자 중 누가 발견할 수 있는가?
11. 모델을 여러 번 호출해 신뢰성을 높였다면 비용·지연·기록량도 함께 측정했는가?
12. 자동 코드 리뷰는 개인 설정, 저장소 ruleset, 조직 ruleset 중 어디에서 요청되는가?
13. 유료 Copilot 라이선스 구성원의 리뷰 과금 설정이 명시적으로 저장돼 있는가?
14. 정책 화면의 `Default (Member)`를 명시적으로 선택한 `Member`로 혼동하고 있지 않은가?
15. 저장소 소유 조직과 PR 작성자의 예산 조직이 다를 때 내부 비용 배분 기준은 무엇인가?
16. AI Credits 유료 사용, billing lock, 청구 고객 상태의 예외를 확인했는가?
17. 코드 리뷰 사용량이 늘었을 때 실제 유효 지적이 같은 비율로 늘었는가?
18. 오탐 처리에 든 사람의 시간을 비용 비교에 포함했는가?
19. 12월 30일 이후 청구 정보를 누가, 언제, 어떤 기준선과 비교할 것인가?
20. Bedrock에서 EFS·EDC가 적용되는 대상 모델과 계정·프로젝트를 정확히 알고 있는가?
21. 공통 Trusted Access API의 GA와 EFS·EDC의 프리뷰 상태를 구분했는가?
22. 프리뷰 시험에 실제 고객의 민감 데이터를 사용하지 않는가?
23. 프리뷰 가입이 기존 ZDR 예외를 바꾸는 범위를 이해했는가?
24. 각 호출 리전의 저장 구성과 소스 리전을 표로 확인했는가?
25. EFS를 선택했다면 S3·KMS 접근을 끊었을 때 서비스에 미칠 영향을 시험했는가?
26. 유지 기록의 수명주기와 사고 조사 기간이 서로 충돌하지 않는가?
27. 사례 파일이 생겼을 때 사람 검토·응답의 담당자와 대체 인력이 있는가?
28. EDC를 선택했다면 AWS 관리 저장소의 감사·보관 증거가 내부 요구를 충족하는가?
29. 제품의 모델 성능, 비용 정책, 데이터 처리 정책 중 하나가 바뀌면 나머지 둘을 다시 검토하는가?
30. 지금의 결정을 바꿀 만큼 중요한 다음 관측값은 무엇인가?

목록이 길어 보여도 실제 회의에서는 해당 서비스에 관련되는 질문만 골라 쓰면 된다. HFE를 읽은 평가팀에는 1~11번, Copilot 관리 담당자에는 12~19번, Bedrock 플랫폼팀에는 20~28번이 우선이다. 29~30번은 세 팀을 다시 한 테이블에 앉히는 질문이다. 평가가 좋아졌다고 비용과 데이터 통제의 검토가 면제되지 않고, 저장소 통제를 잘했다고 모델의 오답이 사라지지 않는다는 것을 확인하려는 구조다.

## 상황별 의사결정 연습 — 같은 뉴스가 다른 팀에는 다르게 작동한다

아래 사례는 벤더가 발표한 실제 고객 사례가 아니라, 공식 발표의 조건을 제품·운영 의사결정에 대입해 보는 **가상 시나리오**다. 목적은 발표에 없는 제품 기능을 주장하는 것이 아니라, 독자가 자기 팀의 질문을 발견하도록 돕는 것이다. 사용량이나 비용 수치는 임의로 만들지 않았다. 조건이 달라지면 결론도 달라지므로 각 사례의 판단을 그대로 복사하지 말아야 한다.

### 상황 1 — 학교 행정 챗봇의 쉬운 질문

학생이 ‘성적 정정 신청은 언제까지인가요’라고 묻는다. 모델은 첫 시험에서 공식 공지의 날짜를 정확히 찾았다. 이때 HFE식 질문은 ‘한 번 맞혔는가’가 아니라, 공지 제목을 달리 부르거나 ‘마감일’, ‘끝나는 날’, ‘마지막 제출일’로 바꿔 물어도 동일한 근거를 찾는가다. 더 어려운 변형은 학기와 학과가 달라졌을 때 날짜를 구분하는 것이다. 행정 챗봇이 옛 학기의 날짜를 자신 있게 알려 주면 학생이 권리를 잃을 수 있다. 따라서 자동 답변에 공지 원문과 학기·기준 시점을 붙이고, 최신 공지를 찾지 못한 경우 담당 부서로 넘기는 방식이 필요하다. 이 예시의 교훈은 고급 추론이 아니라 **평범한 날짜 하나의 일관성**이 사용자 신뢰를 좌우한다는 점이다.

### 상황 2 — 사진 속 표를 읽는 현장 앱

현장 직원이 장비의 작은 라벨을 촬영해 앱에 넣는다. 깨끗한 샘플 사진에서는 모델이 제품 번호를 맞힌다. 그러나 조명이 반사되고 라벨 모서리가 잘린 사진에서는 숫자 `8`을 `3`으로 읽을 수 있다. 이때 HFE의 네온사인 예시와 같은 다단계 작업이 일어난다. 시각 요소를 식별하고, 해당 위치를 선택하고, 순서를 유지하고, 출력 형식을 맞춘다. 앱이 시리얼 번호를 즉시 데이터베이스에 확정 저장한다면 작은 인식 오류가 재고·보증 기록으로 퍼진다. 같은 AI 모델을 써도 UI에서 읽은 번호를 확대해서 보여 주고 직원이 확인하도록 하면 실패의 영향이 줄어든다. 모델 평가와 사용자 인터페이스 설계가 분리될 수 없는 이유다.

### 상황 3 — 한국어 고객지원에서 영어 벤치마크를 쓸 때

제품팀이 공개 리더보드 상위 모델을 골랐다고 하자. 고객은 ‘해지’, ‘탈퇴’, ‘계약 종료’를 섞어 쓰고, 구독 유형에 따라 다른 절차가 적용된다. 공개 벤치마크의 영어 기초 문항 성적이 높더라도 이 한국어 업무의 안전성을 직접 보장하지 않는다. 내부 평가에서는 실제 사용자의 표현을 개인정보를 제거해 분류하고, 같은 의도의 말 바꾸기와 다른 의도의 유사 표현을 나눠야 한다. ‘해지 예약’과 ‘즉시 해지’는 비슷해 보여도 결과가 다를 수 있다. 질문을 묶어서 평균을 내기 전에 **업무적으로 같아야 할 답과 달라야 할 답**을 명확히 표시한다. 이것이 HFE의 일상 신뢰성 문제의식을 현지 언어와 서비스 정책으로 번역하는 방법이다.

### 상황 4 — 외부 자료가 바뀌는 뉴스 요약기

매일 아침 공식 발표를 요약하는 에이전트는 어제의 정답을 오늘 그대로 반복하면 틀릴 수 있다. 검색 페이지의 순서, 기사 업데이트 시각, 문서의 범위가 바뀐다. 평가 세트에서 `오늘의 최근 발표`를 고정된 정답으로 저장하면 시간이 지날수록 시험 자체가 잘못된다. 이 경우 모델의 일관성 평가는 출처 URL과 확인 시각을 함께 기록해야 한다. 같은 공식 자료를 같은 시각의 스냅샷으로 주었을 때 요약이 안정적인지와, 새로운 자료가 들어왔을 때 내용을 올바르게 갱신하는지를 분리한다. HFE처럼 작은 변형을 살피되 **시간에 따른 사실 변화**는 변형이 아니라 정답 변경으로 취급해야 한다. 오늘 글이 게시 시각과 확인 시점을 맨 앞에 적은 이유도 같다.

### 상황 5 — 코드 리뷰가 필수 품질 게이트인 조직

조직이 모든 중요 저장소의 PR에 Copilot 리뷰를 자동 요청하기로 했다면 이는 개인 개발자의 취향이 아니라 공통 품질 체계다. 그 경우 조직 과금은 논리적인 선택일 수 있다. 하지만 과금 정책과 품질 정책은 함께 설계해야 한다. 사소한 문서 변경에도 자동 리뷰를 요구할지, 새 push마다 재검토할지, AI 의견을 인간 리뷰 승인으로 착각하지 않도록 어떤 표시를 둘지 정해야 한다. 12월 30일의 GitHub 변경은 미설정 기본값의 비용 귀속만 바꾸므로, 조직이 자동 리뷰를 품질 게이트로 삼을지 여부를 대신 결정하지 않는다. 결정 뒤에는 실제 유효 지적과 사람이 들인 시간을 추적한다. 비용이 조직으로 옮겨졌다는 사실만으로 리뷰의 가치가 높아지는 것은 아니다.

### 상황 6 — 개인별 entitlement를 유지하려는 분산 팀

개발자가 필요할 때만 Copilot 리뷰를 요청하고, 중앙 조직이 자동 리뷰를 강제하지 않는 팀은 구성원별 entitlement를 유지하려 할 수 있다. 이때 관리자는 현재 화면에 `Default (Member)`라고 보인다는 이유만으로 안심하면 안 된다. GitHub 공지의 대상은 **선택이 저장되지 않은 상태**다. 12월 30일 뒤에도 같은 동작을 원한다면 정책에서 `Member`를 명시적으로 선택해야 한다. 팀에 여러 엔터프라이즈·조직이 있다면 관리 주체가 누구인지 확인한다. 저장소 소유 조직이 달라지는 프로젝트 이동도 비용 경로를 바꿀 수 있으므로 예산 책임자와 공유한다. 핵심은 ‘개인을 선택하라’가 아니라 **지속하고 싶은 동작을 명시적 정책으로 남기라**는 것이다.

### 상황 7 — 비용 관리자가 AI Credits를 막아 놓은 계정

한 조직이 AI Credits 유료 사용을 활성화하지 않았거나 billing lock이 있다면 GitHub 공지의 기본값 전환은 그 조직에서 예고된 일반 경로와 달라질 수 있다. 공지는 이런 조건이나 청구 가능한 고객이 없는 경우 `Member`로 설정한다고 설명한다. 따라서 중앙 관리자는 모든 조직에 ‘반드시 새해부터 조직 과금이 시작된다’고 알리면 안 된다. 조직별 현재 설정과 과금 가능 조건을 확인하고, 예외를 문서화한다. 다만 예외에 기대어 영구 정책을 비워두는 것도 바람직하지 않다. 나중에 AI Credits 유료 사용을 켜거나 billing lock을 해제하면 그때의 설정과 공지를 다시 봐야 한다. **예외 조건은 의도를 표현하는 정책의 대체물이 아니다.**

### 상황 8 — 한 저장소에 여러 팀이 기여할 때

중앙 플랫폼팀이 소유한 저장소에 제품 A·B팀의 PR이 함께 들어온다고 하자. GitHub 공지의 조직 청구 기본값은 저장소 소유 조직을 중심으로 설명된다. 실제 코드를 작성한 팀과 청구 받는 조직이 다를 수 있다. 중앙 플랫폼팀은 비용 원장에 PR 작성팀, 저장소, 자동 리뷰 설정, 유효 지적을 함께 기록하고 내부 비용 배부 원칙을 정해야 한다. 그렇지 않으면 리뷰 사용량이 늘 때 ‘누가 이 비용을 만들었나’라는 논쟁이 제품 품질을 개선할 기회를 밀어낸다. GitHub가 내부 부서 간 정산을 자동으로 해 준다고 가정해서는 안 된다. 정책의 외부 청구 주체와 회사 내부 관리회계의 귀속 주체를 구별한다.

### 상황 9 — 민감도가 높은 문서를 Bedrock에 넣는 팀

보안팀이 ‘프롬프트를 저장하지 않는 모델만 사용 가능’이라고 정해 놓았다면 EFS를 이름만 보고 승인하면 안 된다. EFS는 고객 버킷에 데이터를 **유지**한다. 키와 버킷을 고객이 통제하는 것은 중요한 차이지만 ‘무보관’과는 다르다. 기존 ZDR 예외의 사용 자격, 프리뷰 가입 범위, 해당 모델의 보관 조건을 비교해야 한다. 프리뷰를 시험하는 팀은 실제 민감 문서가 아니라 합성 문서를 사용하고, 데이터 흐름을 먼저 증명한다. 이 상황에서 가장 중요한 결정은 EFS와 EDC 중 어느 쪽이 더 좋은지가 아니라 **제품 요구사항이 보관을 허용하는가**다. 허용하지 않는다면 대상 모델의 도입 방식부터 다시 봐야 한다.

### 상황 10 — 고객 키를 요구하는 규제 산업

한 조직은 생성형 AI 대화 기록이 반드시 자체 계정과 자체 키에 있어야 한다. EFS는 이 요구에 맞을 수 있다. 하지만 ‘고객 키 사용 가능’이라는 한 줄만으로 적합성을 확정하지 않는다. 키를 누가 만들고 회전하는지, 정책 변경을 누가 승인하는지, CloudTrail에서 어떤 이벤트를 볼 수 있는지, 사용 리전마다 저장 설정이 완비됐는지 확인한다. 키 삭제나 버킷 접근 제한이 모델 호출을 멈출 수 있다면 비상 복구 절차도 필요하다. 자체 키는 통제권과 함께 장애 책임을 가져온다. 이 조직은 EFS를 시험 계정에 구성한 뒤 데이터 위치뿐 아니라 **운영상 복구 가능성**을 확인해야 정식 도입의 근거를 얻는다.

### 상황 11 — 저장소 운영을 줄이고 싶은 작은 플랫폼팀

다른 조직은 자체 S3·KMS 정책을 운영할 인력이 충분하지 않고, AWS 관리 저장소가 내부 규정에 맞는다. EDC가 더 단순한 후보가 될 수 있다. 그래도 프리뷰 상태와 보관기간, 사례 검토 방식, 기존 ZDR 예외의 변화, 대상 모델 범위는 확인해야 한다. ‘버킷이 필요 없다’는 편의가 ‘아무도 기록을 관리할 필요가 없다’는 뜻은 아니다. 안전 사례의 판정 책임은 여전히 고객팀에 있다. 보관 위치를 AWS에 맡긴 대신 어떤 감사 자료를 받고 어떤 내부 접근 통제를 적용할지 정한다. 작은 팀일수록 자동화된 알림과 명확한 사례 담당자가 중요하다. 기술 구성을 간소화하되 운영 책임을 공백으로 남기지 않는 것이 핵심이다.

### 상황 12 — 여러 리전에 모델 호출을 분산할 때

서비스가 지연시간을 줄이려고 여러 리전에서 Bedrock을 호출한다면 데이터 보관 설계도 지역별로 확인해야 한다. AWS 문서는 EFS의 유지 기록이 소스 리전에 설정된 고객 버킷으로 간다고 설명한다. 교차 리전 추론이 실제 처리를 다른 리전으로 보낼 수 있어도 기록의 위치를 추측해서는 안 된다. 특정 리전의 저장 구성이 빠졌을 때 모델 호출이 어떻게 동작하는지 프리뷰 시험으로 확인하고, 예상한 위치에 기록이 생겼는지 검증해야 한다. 리전 목록은 배포 구성·장애 복구 경로와 함께 관리한다. 주 리전만 검증하고 재해 복구 리전에서 처음 민감 데이터를 흘려보내는 식의 도입은 피해야 한다.

### 상황 13 — 고객 대응팀이 안전 사례를 맡게 될 때

EFS나 EDC를 선택하면 자동 안전 모니터링이 만들어 낸 사례를 고객팀이 검토한다. 기존 보안 운영센터가 AI 대화의 문맥을 이해하는지, 개인정보 담당자와 어떻게 협업하는지, 사례에 대한 응답 권한은 누가 갖는지 확인해야 한다. 자동 탐지가 거짓 양성일 수도 있고 실제 정책 위반일 수도 있다. 담당자가 아무 설명 없이 `violation` 또는 `no_violation`을 누르는 절차는 부실하다. 조사 기준, 최소 열람 원칙, 2차 검토 조건을 정해야 한다. 이 인력·절차 비용은 AWS의 기능 가격과 별개로 운영에 든다. ‘고객이 사례를 검토한다’는 발표 문장은 고객 조직에 업무가 생긴다는 뜻이기도 하다.

### 상황 14 — 한달 뒤 모델 버전을 바꿀 때

오늘 HFE에 높은 점수를 받은 모델이 다음 버전에서 모든 업무를 똑같이 수행한다고 보장할 수 없다. 모델 공급자의 업데이트, 시스템 프롬프트 수정, 도구 응답 형식 변경이 일상 질문의 신뢰성을 바꿀 수 있다. 배포 전에 고정된 평가 세트로 회귀 시험을 하고, 특히 이전에 실패했던 변형 묶음이 개선됐는지 본다. 새 버전의 토큰 사용량과 지연, 민감한 기록 보관 방식도 다시 확인한다. 모델 성능의 회귀 시험을 백엔드 API의 회귀 시험처럼 취급하되, 확률적 응답 특성에 맞춰 반복과 오류 유형을 기록한다. **기능은 비슷해 보여도 비용과 데이터 흐름이 달라질 수 있다.**

### 상황 15 — 이 사이트와 같은 뉴스 자동화

매일 AI 뉴스 글을 만드는 자동화는 공개 웹의 변화에 좌우된다. `web_search`가 실패했다고 해서 일을 멈추면 공식 RSS와 뉴스 인덱스에 새 소식이 있어도 놓친다. 반대로 검색 결과 하나만 보고 날짜·내용을 확정하면 시간대와 수정된 원문 때문에 잘못된 글을 낼 수 있다. 그래서 공식 인덱스와 RSS로 게시 시각을 확인하고, 원문을 열어 적용 범위·시제·제한 사항을 읽는다. 오늘 GitHub 과금 공지는 11월 25일 UTC 늦은 시간에 나왔지만 한국 시각으로는 11월 26일 아침이다. 시간대를 명시하지 않으면 ‘어제 뉴스’와 ‘오늘 새 뉴스’의 경계가 흐려진다. 출처 확인 과정을 공개하는 것이 자동화 글의 신뢰성을 높인다.

## 작동 가능한 최소 점검표 — 세 소식을 30분 회의로 압축한다면

첫 10분은 **평가**다. 제품팀은 사용자 영향이 큰 작업 세 가지를 고르고, 각 작업의 의미 보존 변형과 조건 변경 변형을 한 개씩 보여 준다. 평가 담당자는 모델이 각 변형에서 어떤 근거로 답했고 실패가 어디서 생겼는지 설명한다. 이 시간에 공개 리더보드 순위를 논쟁하기보다 우리 제품의 실제 입력을 본다. 공개 HFE는 문제의식을 제공할 뿐 고객 서비스의 합격선을 정해 주지 않는다. 회의의 산출물은 새 모델 도입 여부가 아니라 다음 배포에서 반드시 통과할 변형 평가 묶음이다.

다음 10분은 **비용**이다. Copilot 관리자는 조직의 코드 리뷰 과금 선택이 저장된 값인지, 기본 표시인지 보여 준다. 자동 리뷰를 일으키는 사용자·저장소·조직 정책을 구분한다. 재무 담당자는 `Member`와 `Organization` 중 어떤 귀속이 내부 원칙에 맞는지 말한다. GitHub 공지는 12월 30일부터의 기본값 변경이므로 지금 필요한 것은 급한 지출 계산보다 의도적인 정책 결정이다. 회의의 산출물은 선택값, 결정권자, 변경 전후 검증일이다.

마지막 10분은 **데이터**다. 플랫폼팀은 Bedrock에서 대상 모델을 호출하는 계정·프로젝트·리전을 표로 제시한다. 보안팀은 EFS, EDC, 현재 ZDR 중 어떤 방식이 데이터 분류 기준에 맞는지 확인한다. 프리뷰 시험에 실제 규제 자료를 쓰지 않겠다는 원칙과 사례 검토 담당자를 정한다. API의 GA와 프로그램의 프리뷰를 구분한다. 회의의 산출물은 기능 도입 승인이 아니라 시험 범위와 데이터 흐름 검증 계획이다. 세 안건 중 하나라도 증거가 부족하면 결과를 ‘미결정’으로 남기는 편이 추측으로 채우는 것보다 낫다.

이 회의는 모든 팀이 위 세 제품을 실제로 쓴다는 전제를 요구하지 않는다. 어떤 팀은 HFE만 관련되고, 어떤 팀은 Copilot 정책만 관련될 수 있다. 중요한 습관은 AI 도입을 모델 품질이라는 단일 차원에 가두지 않고, **결과·비용·기록의 책임**을 함께 적는 것이다. 여기에 모두가 동의할 수 있다면 오늘 발표 세 건은 단순 뉴스 소비를 넘어 실제 운영 개선으로 이어진다.

## 용어를 정확히 쓰기 위한 짧은 사전

- **일관성(reliability):** 같은 과제나 작은 변형에서 안정적으로 적절한 답을 내는 성질. 한 번의 최고 성적과 다르다.
- **벤치마크:** 정해진 문항·평가 절차로 모델을 비교하는 도구. 실제 제품의 모든 입력 분포를 대표하는 보증서는 아니다.
- **변형 묶음:** 의미가 같거나 조건 차이가 통제된 여러 입력의 그룹. 무엇이 달라져야 하고 무엇이 유지돼야 하는지 표시해야 한다.
- **entitlement:** 구독 또는 라이선스에 부여된 사용 권리. GitHub 공지에서는 기존의 구성원 Copilot 사용 권리와 조직 과금의 관계를 읽는 핵심 단어다.
- **기본값(default):** 명시적 선택이 저장되지 않았을 때 시스템이 적용하는 동작. 화면에 기본값이 표시되는 것과 사용자가 그 값을 저장한 것은 다르다.
- **저장소 소유 조직:** GitHub 공지에서 기본 조직 청구의 기준이 되는 조직. PR 작성자의 소속과 항상 같지는 않다.
- **GA(일반 제공):** 제품 또는 API가 일반적으로 제공되는 상태. 그 API로 접근하는 모든 개별 프로그램도 GA라는 뜻은 아니다.
- **공개 프리뷰:** 제한과 변경 가능성이 남아 있는 사전 제공 단계. AWS의 EFS·EDC가 여기에 해당한다.
- **ZDR:** 입력·출력의 zero data retention, 즉 해당 방식의 무보관을 가리키는 말. 고객 버킷에 기록을 보관하는 EFS와 다르다.
- **EFS:** 대상 Anthropic 모델의 유지 기록을 고객 계정 S3와 고객 KMS 키로 관리하는 Bedrock 제공 항목.
- **EDC:** 대상 모델의 유지 기록을 Amazon 관리 저장소·관리 키로 처리하는 Bedrock 제공 항목.
- **소스 리전:** 애플리케이션이 모델 호출을 시작한 AWS 리전. EFS 기록 위치를 판단할 때 중요하다.
- **안전 사례(case):** 자동 모니터링이 검토를 요청하기 위해 만든 기록. 탐지 자체가 최종 위반 판정은 아니다.

## 평가 설계 워크시트 — HFE에서 얻는 구체적 방법론

공개 벤치마크의 취지를 말로만 공유하면 다음 주에는 잊힌다. 이를 실제 평가 계획으로 바꾸려면 문항 카드에 최소한 **과제 설명, 입력, 허용되는 정답, 같은 의미의 변형, 정답이 달라지는 경계 변형, 오류 심각도**를 써야 한다. 예를 들어 ‘이미지 속 세 번째 단어의 첫 글자 색을 말하라’는 문항이라면, 이미지 자체, 단어 분리 기준, 색 이름의 허용 범위, 조명 변형을 기록한다. 색을 영어로 답해도 맞는지, `blue`와 `navy`를 같은 것으로 볼지 미리 정한다. 채점 기준을 응답을 본 뒤 바꾸면 모델의 일관성을 측정하는 대신 채점자의 유연성을 측정하게 된다.

문항 카드에는 **실행 환경**도 붙여야 한다. 모델 ID와 제공 날짜, 입력 이미지의 원본 해상도, 전처리 방식, 시스템 프롬프트, 출력 형식 제약, 온도, 반복 횟수, 도구 호출 허용 여부를 기록한다. 모델이 처음에는 파일 전체를 읽다가 나중에는 일부 페이지만 본다면 점수 차이는 모델만의 변화가 아닐 수 있다. Google이 11월 23일 소개한 [Gemini API의 file slicing controls](https://blog.google/innovation-and-ai/technology/developers-tools/file-slicing-controls/)처럼 문서·시트·영상의 일부를 서버에서 선택해 읽는 기능은 입력의 양과 모양을 바꾼다. 오늘의 주 뉴스는 아니지만, 평가 환경에서 **무엇을 모델에 실제로 보여 주었는가**가 결과를 좌우한다는 좋은 예다.

원본 입력의 품질을 고정하는 것만으로는 충분하지 않다. 실제 제품에서 파일을 자르고 축소하는 단계가 있다면 평가에도 같은 단계를 넣어야 한다. 이미지가 모델에 전달되기 전 프런트엔드에서 압축되는지, PDF가 페이지 이미지로 변환되는지, 검색 도구가 긴 문서의 앞부분만 보여 주는지 살펴야 한다. 모델이 틀린 것이 아니라 파이프라인이 필요한 단서를 버렸을 수 있다. 반대로 파이프라인이 정답에 해당하는 텍스트를 우연히 메타데이터로 제공해 모델이 쉽게 맞힐 수도 있다. 벤치마크가 아무리 정교해도 입력 경로가 실제 제품과 다르면 운영 판단에 쓰기 어렵다.

### 채점 기준을 세 층으로 나누기

첫 층은 **내용 정확성**이다. 답의 핵심 사실이 맞는가. 둘째는 **근거 일치성**이다. 맞는 답을 했더라도 엉뚱한 출처를 인용하거나 원문에 없는 이유를 붙였다면 운영상 위험할 수 있다. 셋째는 **형식·행동 준수**다. JSON 스키마, 순서, 단위, 언어, ‘확인 불가일 때는 모른다고 답하기’ 같은 요구를 지켰는가. HFE의 네온사인 예시도 색을 모두 식별했지만 순서를 바꾸거나 세미콜론 형식을 깨면 과제의 요구를 완수한 것이 아니다. 실서비스에서는 세 층이 각기 다른 장애로 이어진다.

내용 정확성을 평가할 때는 ‘정답 문자열과 완전 일치’만 쓰면 동의어를 오답으로 세기 쉽다. 반대로 느슨한 언어 모델 채점만 쓰면 실제로 틀린 숫자나 날짜를 그럴듯한 설명 때문에 맞음으로 분류할 위험이 있다. 날짜·금액·식별자는 결정론적 파서로 확인하고, 의미가 넓은 답은 사람 검토 샘플을 섞는 방식이 유용하다. 평가기가 모델이면 평가기 역시 오류를 낼 수 있으므로 이견 사례를 수집한다. ‘평가 자동화’도 또 하나의 AI 제품이며 품질 관리가 필요하다.

### 문항을 고르는 기준

평가 문항은 ‘기술적으로 재미있는 것’보다 ‘자주 일어나고 실패 비용이 큰 것’에 우선순위를 둔다. 자주 발생하지만 영향이 작은 작업은 표본을 충분히 모아 평균 품질을 본다. 드물지만 영향이 큰 작업은 표본이 적어도 개별 실패를 자세히 검토한다. 실제 사용자 로그에서 문항을 고를 경우 동의와 데이터 보호를 지키고, 특정 시기의 이슈가 과대표집되지 않도록 한다. 가령 연말정산 기간의 질문만 모으면 그 시기에는 유용하지만 연중 고객지원의 대표 세트가 되지 않는다. 사용자 분포가 바뀔 때 평가 문항도 주기적으로 갱신해야 한다.

‘쉬운 질문’이라는 이름에도 주의를 기울인다. 숙련된 사람이 한눈에 답을 안다고 해서 모든 사용자에게 쉬운 것은 아니다. 이미지에 색각 차이와 화면 설정의 영향이 있을 수 있고, 문화·언어마다 기초 상식이 다를 수 있다. 문항이 애매해 여러 답이 가능한데 모델이 한 답을 냈다고 오답으로 처리하면 평가의 신뢰성이 떨어진다. HFE가 평가하려는 것은 일상적 능력의 안정성이지, 평가자의 암묵적 가정에 맞추는 능력만은 아닐 것이다. 내부 평가에서는 정답 논쟁이 발생한 문항을 별도 검토하고, 애매성이 해소될 때까지 주요 합격선에서 제외하거나 다중 정답으로 관리한다.

### 결과 보고서의 예시 구조

보고서 첫 장에는 평가 버전과 실행 날짜, 모델·프롬프트 버전, 문항·변형 묶음 수, 전체 정답률, 묶음 완전 성공률, 고위험 오류 수를 적는다. 다음 장에는 실패 유형별 대표 사례를 넣는다. 예를 들어 시각 요소 오독, 조건 누락, 시간대 해석 실패, 형식 위반, 근거 없는 확신을 구분한다. 마지막 장에는 ‘어떤 수정이 어떤 실패를 줄였고 다른 유형에 어떤 회귀를 만들었는가’를 적는다. 실제 수치가 없다면 빈칸으로 남긴다. 공개 HFE 수치를 우리 서비스의 수치인 것처럼 가져오는 것보다 정직한 보고서다.

모델이 개선됐다는 보고에는 **측정 불확실성**도 남겨야 한다. 문항이 20개인데 18개에서 19개로 늘었다면 퍼센트상 개선은 보이지만 우연과 문항 선택의 영향을 무시하기 어렵다. 문항 수와 반복 횟수, 실패가 특정 묶음에 몰렸는지를 함께 보아야 한다. 서로 다른 모델을 비교할 때 동일한 문항과 입력 파이프라인, 도구 사용 조건을 맞추지 않으면 비교 자체가 흐려진다. 공개 리더보드의 숫자도 평가 구성과 실행 조건을 읽은 뒤 해석해야 한다.

## Copilot 정책 감사 카드 — ‘설정의 부재’를 식별하기

GitHub의 변경을 준비할 때 가장 먼저 할 일은 조직 목록을 만드는 것이다. 한 엔터프라이즈 안에 여러 조직이 있고, 각 조직이 서로 다른 저장소와 정책을 가질 수 있다. 각 조직에 대해 Copilot Business·Enterprise 사용 여부, 중앙 엔터프라이즈의 설정 관리 여부, 코드 리뷰의 유료 라이선스 구성원 과금 설정, 비라이선스 구성원의 별도 설정, AI Credits 유료 사용 상태, billing lock, 자동 리뷰 ruleset을 기록한다. 이 카드의 목적은 모든 정보를 한 사람에게 공개하는 것이 아니라 **변경의 적용 조건을 빠짐없이 확인하는 것**이다. 민감한 청구 정보에 대한 접근 권한은 최소화해야 한다.

감사 결과를 세 색으로 나누면 이해하기 쉽다. **녹색**은 명시적 설정이 저장돼 있고 비용 담당자가 결과를 이해하는 경우다. **노란색**은 미설정이지만 담당자가 확인 중이거나, 계정 예외 조건 때문에 당장 전환은 없더라도 정책 의도가 기록되지 않은 경우다. **빨간색**은 미설정인데 자동 리뷰가 넓게 켜져 있고, 조직 청구 가능 조건이 충족되며, 비용 담당자가 바뀐 기본값을 모르는 경우다. 이것은 GitHub 공식 상태 분류가 아닌 운영 편의상의 분류다. 실제 GitHub UI의 라벨과 혼동하지 말아야 한다.

설정이 미비하다고 무조건 `Member`로 바꾸지 않는다. 코드 리뷰를 조직이 의무화했는데 개인 entitlement에 떠넘기면 사용 권한과 비용의 책임이 불일치할 수 있다. 반대로 조직 예산이 없는데 기본값만 받아들이면 예측하지 못한 청구가 생길 수 있다. 관리자는 조직의 정책 목적을 먼저 묻는다. ‘이 리뷰는 누가 이득을 얻는가’, ‘누가 요청하는가’, ‘개인이 요청하지 않아도 ruleset으로 수행되는가’, ‘사용량을 어느 단위로 통제할 수 있는가’가 결정의 근거다. 이 질문에 답한 후 값을 명시적으로 저장한다.

정책 감사 카드는 날짜가 지난 뒤에도 유용하다. 12월 30일을 지나 실제 청구 데이터를 볼 때 당시 어떤 조직이 `Member`, `Organization`, 미설정이었는지 비교할 수 있다. GitHub 공지가 예외 계정은 `Member`로 설정한다고 했으므로, 공지의 조건과 계정의 실제 상태를 대조할 수 있다. 기대와 다르면 GitHub 공식 문서를 다시 보고 지원 경로를 확인한다. 변경 이전의 설정 상태를 기록하지 않으면 사후에 비용 증가가 이번 공지 때문인지, 자동 리뷰 범위 변경 때문인지, 사용량 증가 때문인지 구별하기 어렵다.

### 정책 소유권의 세 가지 사례

작은 조직에서는 개발 리더가 Copilot 설정과 예산을 함께 관리할 수 있다. 이 경우 결정이 빠르지만 검토자 한 명의 가정을 놓치기 쉽다. 중간 규모에서는 플랫폼팀이 ruleset을 관리하고 재무팀이 청구를 본다. 서로의 변경을 알리는 절차가 없으면 규칙 확대와 비용 증가가 다른 회의에서 일어난다. 큰 엔터프라이즈에서는 중앙 소유자가 정책값을 정하고 개별 조직은 저장소 자동 리뷰 범위만 조정할 수 있다. 개별 조직 관리자에게 ‘지금 바꾸라’고 해도 권한이 없을 수 있다. 공지가 엔터프라이즈 소유자의 역할을 언급한 이유를 조직 구조에 맞게 읽어야 한다.

각 사례에서 권장되는 문서 한 줄은 비슷하다. **‘우리는 유료 라이선스 구성원의 Copilot 코드 리뷰를 어느 예산으로 처리하며, 그 선택을 누가 어느 정책 계층에 저장했다.’** 이 문장이 완성되면 12월 30일의 기본값 변경은 적어도 우연한 정책 변경이 되지 않는다. 문장이 완성되지 않는다면 설정 화면의 현재 표시가 아무리 정상으로 보여도 미결정 상태가 남는다. 공지는 UI의 문구보다 저장된 선택과 적용 계층을 보라고 요구한다.

## Bedrock 데이터 흐름 카드 — 저장, 감시, 사람 검토의 경계

EFS/EDC의 데이터 흐름을 그릴 때는 세 화살표를 구분한다. 첫째는 **추론 호출**이다. 애플리케이션이 Bedrock Runtime에 프롬프트를 보내고 모델 응답을 받는다. 둘째는 **유지 기록의 저장**이다. 선택한 프로그램과 구성에 따라 EFS의 고객 버킷 또는 EDC의 Amazon 관리 저장소에 입력·출력이 유지된다. 셋째는 **안전 검토**다. 자동 모니터링이 위험을 찾고 사례가 만들어지면 고객팀이 검토한다. 세 화살표가 모두 같은 계정과 같은 리전에서 끝난다고 추측해서는 안 된다. AWS 문서가 소스 리전과 검토 위치, 고객 버킷의 역할을 따로 설명하는 이유다.

이 카드에는 **프리뷰 가입 전과 후**를 나란히 그려야 한다. 가입 전에는 적격 고객에게 임시 ZDR 예외가 적용될 수 있다. 가입 후 대상 계정 또는 프로젝트에서는 ZDR이 꺼지고 EFS·EDC의 유지 방식으로 바뀔 수 있다. 이 변화는 모델 품질과 별개로 데이터 처리 방식의 실질적 변경이다. 따라서 제품팀이 ‘같은 Claude 모델이니 데이터 정책도 같다’고 말하면 안 된다. 모델명은 같아도 프로그램 가입 상태와 보관 모드에 따라 기록의 위치와 존재 여부가 달라질 수 있다.

**EFS 카드를 채울 때**는 소스 리전별 S3 버킷 이름과 KMS 키 ARN, 버킷·키 정책 버전, 접근 권한자, 수명주기 규칙, CloudTrail 설정, 사례 응답 담당자를 적는다. 키와 버킷의 세부 식별자를 공개 문서나 뉴스 기사에 쓰라는 뜻이 아니다. 내부 제한된 설계 문서에만 남긴다. 데이터가 고객 계정에 있다는 장점은 그 계정을 보호하고 감사할 능력이 있을 때 실현된다. 버킷이 잘못 공개되거나 키 권한이 과도하면 선택의 목적이 퇴색한다. 프리뷰 시험에서 정책을 확인할 때 최소 권한과 접근 기록을 함께 본다.

**EDC 카드를 채울 때**는 Amazon 관리 저장소를 허용하는 법무·보안 근거, 공개 문서가 설명한 보관기간, 사례 검토 절차, 고객 계정에서 볼 수 있는 감사 증거의 범위를 적는다. 자체 S3 운영이 없다는 장점은 실제로 작지만, 자료의 위치와 열람 구조를 확인하는 책임은 그대로 남는다. 어느 옵션이 더 쉬운지는 팀의 기존 역량에 달려 있다. S3·KMS 운영에 익숙한 팀에게는 EFS가 자연스러울 수 있고, 데이터 위치 요건이 허용하는 작은 팀에는 EDC가 관리 부담을 줄일 수 있다. 그러나 프리뷰가 바뀌기 전후의 문서 버전은 모두 기록해야 한다.

### 실패를 설계 문서에 미리 적는 이유

프로덕션 장애는 대개 정상 흐름을 문서화했는데도 일어난다. 모델 호출 자체는 성공했지만 기록이 예상 버킷에 보이지 않을 수 있다. 버킷이 정상인데 키 정책 변경으로 새 기록이 쌓이지 않을 수 있다. 리전 하나만 구성해 장애 복구 경로에서 거절이 생길 수 있다. 사례 알림이 오지만 담당자가 권한이 없어 관련 자료를 읽지 못할 수 있다. 프리뷰의 구현이나 문서가 바뀌어 자동화가 깨질 수도 있다. 각 실패를 ‘어떤 신호로 알아차리고, 누가 복구하며, 어떤 데이터가 영향을 받는가’로 적어 두면 기능 시험이 운영 시험으로 바뀐다.

실패 모드의 심각도는 조직의 사용 목적에 따라 다르다. 내부 실험용 모델 호출이라면 몇 시간의 중단을 허용할 수 있지만, 고객에게 실시간 답변하는 서비스라면 장애 복구 경로가 필요하다. 보안 사고 분석이 중요한 업무라면 기록 누락이 모델 응답 중단보다 더 심각할 수 있다. 무조건 모든 기록을 가장 오래 보관하는 해결책은 개인정보와 비용의 부담을 키운다. **보관의 완전성, 최소화, 서비스 가용성** 사이에서 어떤 우선순위를 선택했는지 설계 문서에 남겨야 한다.

## 오늘 발표에 대한 짧은 Q&A

**Q. HFE가 공개됐으니 우리 서비스의 모델도 믿어도 되나?** 아니다. HFE는 일상적 질문의 반복 신뢰성을 평가하는 공개 도구다. 544개 문항과 20개 능력은 유용한 신호지만 우리 서비스의 언어·자료·실패 비용을 대체하지 않는다. 내부 변형 평가와 운영 관찰이 필요하다.

**Q. 544개라는 숫자는 왜 중요한가?** 평가가 어떤 크기의 공개 세트를 다루는지 알려 준다. 그러나 숫자가 크다고 해서 입력 분포가 우리 사용자와 같다는 뜻은 아니다. 반대로 숫자가 제한적이라고 해서 평가가 쓸모없다는 뜻도 아니다. 문항 구조와 실패 유형을 읽는 것이 중요하다.

**Q. Kaggle 이벤트 마감일이 지나면 HFE가 끝나나?** 공식 글에서 12월 15일은 커뮤니티 제출 이벤트의 마감이다. 벤치마크의 연구 가치나 제품 평가의 필요가 그날 사라진다는 의미는 아니다.

**Q. 12월 30일에 Copilot 코드 리뷰 기능 자체가 달라지나?** 이번 GitHub 공지가 직접 다룬 것은 **미설정 과금 선택의 기본값**이다. 리뷰 성능이나 가격 단가가 바뀐다는 주장은 이 공지에서 확인되지 않는다.

**Q. 이미 `Member`를 선택했는데 다시 선택해야 하나?** 공지는 이미 저장한 `Member` 또는 `Organization` 선택은 유지된다고 한다. 다만 화면의 `Default (Member)`가 명시적 `Member` 선택과 같은 상태인지 확인해야 한다.

**Q. 라이선스가 없는 구성원도 이번 변경 대상인가?** 공지는 유료 라이선스가 있는 구성원에 대한 미설정 기본값을 설명하고, 라이선스가 없는 구성원의 별도 설정은 바뀌지 않는다고 명시한다.

**Q. 저장소를 소유한 조직이 청구받는다는 건 개발자 소속팀도 같아야 한다는 뜻인가?** 아니다. 저장소 소유 조직과 기여자의 내부 소속은 다를 수 있다. 내부 비용 배분은 회사가 별도로 결정해야 한다.

**Q. AWS Trusted Access API가 GA라면 EFS도 GA인가?** 아니다. 공식 글은 공통 API의 일반 제공과 첫 EFS·EDC 프로그램의 공개 프리뷰를 구분한다.

**Q. EFS는 zero data retention인가?** 아니다. EFS는 고객 계정 버킷에 유지 기록을 저장하고 고객 KMS 키로 암호화하는 방식이다. ZDR과 데이터 처리 특성이 다르다.

**Q. EDC는 AWS가 모든 사례를 대신 판정한다는 뜻인가?** 아니다. 자동 안전 모니터링 이후 플래그된 사례를 고객팀이 검토한다는 구조가 공식 자료에 설명돼 있다. 세부 제공 방식은 프리뷰 문서를 확인해야 한다.

**Q. EFS를 켜면 모든 모델 호출이 고객 버킷에 저장되나?** 아니다. 대상 Anthropic 모델과 가입 범위, 리전·설정이 맞는 호출을 봐야 한다. 모든 Bedrock 모델의 모든 입력에 자동 적용된다고 일반화할 수 없다.

**Q. 오늘 바로 무엇을 결정해야 하나?** 모델 평가는 자사 업무의 변형 세트를 만들고, Copilot은 12월 30일 전 미설정 정책의 책임자를 지정하며, Bedrock은 프리뷰 시험 범위와 데이터 보관 요구를 문서화한다. 서로 다른 팀의 결정이지만 모두 공식 발표의 범위와 한계를 보존하는 데서 시작한다.

## 릴리스 게이트 제안 — 세 통제면을 실제 승인 조건으로

평가·비용·데이터를 릴리스 검토에 올릴 때는 추상적인 ‘문제없음’ 대신 관찰 가능한 승인 조건이 필요하다. 평가 게이트는 해당 제품의 고위험 작업 묶음에 대해 정해진 변형 시험을 통과했는지 본다. 실패가 남았다면 오류를 자동으로 감지하고 사람에게 넘기는 경로가 실제로 작동하는지 확인한다. 비용 게이트는 AI 기능이 어떤 설정에서 호출되고 청구 주체가 누구인지 명시한다. 데이터 게이트는 입력·출력과 안전 검토 기록이 정해진 위치와 기간에 보관되며 접근권한이 승인됐는지 본다. 세 게이트는 하나가 다른 하나를 대신할 수 없다.

가령 모델의 HFE 점수가 높더라도 우리 제품의 한국어 개인정보 처리 안내에서 틀리면 평가 게이트를 통과하지 못한다. AI 코드 리뷰가 유용하더라도 미설정 과금 정책으로 예산 담당자가 모르는 조직 청구가 생긴다면 비용 게이트를 통과했다고 보기 어렵다. EFS 버킷이 준비됐더라도 재해 복구 리전의 저장 설정이 빠졌다면 데이터 게이트는 미완성이다. 모든 위험을 제로로 만들자는 뜻이 아니다. **남은 위험과 책임자가 명시된 상태에서 출시 결정을 하자**는 뜻이다. 각 팀은 합격 기준을 업무 영향에 맞춰 정하고, 벤더의 마케팅 문구를 그대로 기준으로 복사하지 않아야 한다.

릴리스 게이트를 너무 무겁게 만들지 않으려면 변경 유형에 따라 검사 범위를 조정할 수 있다. 문구 하나 바꾼 내부 초안 기능은 소규모 평가로 충분할 수 있다. 모델 버전·입력 파이프라인·자동 리뷰 ruleset·Bedrock 저장 설정을 바꾸는 변경은 해당 통제면의 회귀 검사를 요구한다. 이 판단의 출발점은 변경이 사용자 결과, 비용, 보관 데이터 중 무엇에 영향을 주는지 표시하는 것이다. 영향이 없다면 근거를 적고 검사를 생략할 수 있다. 영향이 있는데 아무도 확인하지 않았다면 일정이 급해도 그 사실을 승인 기록에 남겨야 한다.

출시 후에는 **기대와 실제의 차이**를 일정 기간 추적한다. HFE식 반복 평가에서 잘하던 모델이 실제 문의에서 특정 언어·이미지 품질에 약한지 확인한다. Copilot 정책이 의도한 청구 계정에 반영됐는지 12월 30일 이후 첫 청구 자료를 본다. Bedrock 프리뷰의 실제 기록이 예상 리전과 저장 목적지에 남고, 사례 검토가 사람이 처리할 수 있는 분량과 형식인지 본다. 제품 문서와 실제 동작이 다르면 문서를 고치거나 설정을 되돌린다. 벤더 발표를 읽는 것과 운영 증거를 확인하는 것 사이의 차이를 마지막까지 남기는 절차다.

마지막으로 세 통제면의 변경 기록을 같은 릴리스 식별자에 연결하면 사고 분석이 쉬워진다. 어느 날 모델의 답이 흔들렸다면 그날 프롬프트나 입력 절단 방식이 바뀌었는지 확인한다. 코드 리뷰 비용이 늘었다면 과금 정책 변경, 자동 리뷰 범위 확대, PR 증가 중 무엇이 원인인지 분리한다. 데이터 보관량이 늘었다면 가입 범위·모델·리전·보관기간의 변경을 확인한다. 원인을 설명할 수 있으면 수정을 선택할 수 있다. 원인을 설명할 수 없다면 ‘AI라서 예측할 수 없다’는 말이 운영의 빈칸을 가릴 뿐이다.

### 이 기사 자체에도 같은 원칙을 적용한다

오늘 글이 길다고 해서 모든 문장이 같은 증거 수준을 갖는 것은 아니다. GitHub의 적용일과 예외 조건, Google HFE의 문항 규모, AWS의 프리뷰 상태처럼 공식 원문에서 바로 확인 가능한 사실이 있다. 그 사실을 바탕으로 제안한 평가 워크시트, 비용 감사 카드, 릴리스 게이트는 **편집자의 운영 해석**이다. 가상 상황은 실제 벤더 고객의 성과가 아니다. 독자가 제품 도입 회의에서 문장을 재사용할 때도 이 세 층위를 구분해야 한다. 공식 발표의 기능 목록에 이 글의 체크리스트를 끼워 넣으면 출처가 제공하지 않은 약속을 만든다.

같은 이유로 이 글은 확인되지 않은 시장 점유율, 모델별 HFE 점수, Copilot 리뷰 한 건의 가격, EFS·EDC 프리뷰의 모든 지역별 이용 가능 여부를 숫자로 제시하지 않는다. 그런 수치가 필요하다면 각각 공식 리더보드, 계약·청구 화면, 현재 AWS 문서를 시점과 계정 조건에 맞춰 다시 확인해야 한다. **확인할 수 없어서 비워 둔 값**과 **값이 존재하지 않는 것**은 다르다. 하루 뉴스의 역할은 미래의 모든 운영 결과를 예언하는 것이 아니라, 오늘 검증 가능한 사실과 내일 확인해야 할 항목을 구획하는 것이다.

독자가 오늘 세 문장만 기억한다면 다음이면 충분하다. 첫째, 쉬운 질문이라도 여러 변형에서 늘 맞히는지 봐야 한다. 둘째, Copilot 코드 리뷰의 미설정 과금 선택은 12월 30일을 앞두고 의도적으로 결정해야 한다. 셋째, Bedrock의 데이터 통제 옵션은 ‘무보관’이라는 광고 문구가 아니라 실제 저장 위치와 사람 검토 절차로 읽어야 한다. 이 세 문장은 서로 다른 발표를 하나의 불분명한 AI 낙관론으로 합치지 않으면서, 각 팀이 다음 행동을 정할 수 있게 한다.

4. [HFE Kaggle 벤치마크](https://www.kaggle.com/benchmarks/deepmind/hfe) 및 [리더보드](https://www.kaggle.com/benchmarks/deepmind/hfe/leaderboard) — 공식 글에서 연결한 평가·제출 경로다.

**자료 한계:** `web_search`는 이 실행에서 검색 API 키가 없어 오류가 났다. 위 공식 인덱스·RSS·원문을 `web_fetch`로 확인했고, RSS의 게시 시각은 해당 사이트가 표시한 값이다. Google HFE의 공개 글은 평가 취지를 설명하지만, 이 글은 기술 보고서의 전체 방법론이나 Kaggle 순위를 재분석했다고 주장하지 않는다. GitHub 변경은 **미래의 정책 기본값**이며 오늘 이미 모든 조직에서 적용된 완료 상태가 아니다. AWS의 API 일반 제공과 EFS/EDC 공개 프리뷰를 혼동하지 않는다. 운영 체크리스트·가상 시나리오·의사결정 표는 공식 제품 기능이 아니라 공개 자료에 근거한 편집상의 분석이다.

## 마무리 — ‘할 수 있다’에서 ‘맡길 수 있다’로

AI를 실무에 넣을 때 가장 큰 질문은 점점 ‘멋진 답을 한 번 만들 수 있는가’에서 ‘반복되는 쉬운 일을 안정적으로 맡길 수 있는가’로 이동한다. HFE는 그 신뢰성의 한 단면을 평가하려 하고, GitHub는 자동화가 늘면서 비용의 기본값이 조직 운영 결정이 된다는 점을 보여 주며, AWS는 안전 검토용 기록이 모델의 주변 기능이 아니라 배포 아키텍처의 일부라는 사실을 드러낸다.

오늘 당장 할 수 있는 일은 분명하다. 모델 평가에서는 평균뿐 아니라 변형 묶음의 실패를 본다. Copilot 코드 리뷰를 쓰는 조직은 12월 30일 전에 **설정되지 않은 청구 선택**을 찾아 의도적으로 결정한다. Bedrock의 대상 Anthropic 모델을 검토하는 팀은 EFS·EDC·기존 ZDR을 같은 말로 부르지 말고, 계정·리전·버킷·키·사례 검토 인력을 명시한다. 세 발표의 공통 교훈은 모델의 능력을 과소평가하라는 것이 아니다. **능력이 실제 서비스의 책임으로 전환되는 지점을 정확히 보라**는 것이다.
