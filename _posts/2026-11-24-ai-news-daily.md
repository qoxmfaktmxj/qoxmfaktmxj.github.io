# AI Daily News | 2026년 11월 24일

**확인 시점: 2026년 11월 24일 11:30 KST.** 오늘의 핵심은 11월 23일 OpenAI와 Cisco가 발표한 오픈소스 Linux 보안 런타임 **Shirudo**다. 취약점 패치를 준비·검증하는 동안 서비스 재시작 없이 특정 공격 경로를 차단하는 작은 보호 프로그램, 이른바 *shield/upatch*를 배포하고 그 상태를 서명과 TPM 증거로 확인하려는 프로젝트다. OpenAI는 Codex가 생성한 방패가 통제된 실험에서 실행 중인 Elasticsearch의 Java4Shell 악용 시도를 막았다고 설명한다. 그러나 이것은 **사례 실험**이지 다양한 운영 환경에서 검증된 범용 치료제라는 발표가 아니다. 프로젝트 저장소는 스스로를 **pre-release**로 명시하고, 실제 운영에는 수정된 커널과 TPM 2.0 등 특별한 전제 조건이 필요하다고 밝힌다.

오늘 함께 확인한 GitHub의 11월 23일 발표 두 건은 AI를 둘러싼 다른 층위의 운영 문제를 보여 준다. 새 **issue status와 repository board 공개 미리보기**는 사람과 에이전트가 같은 업무 상태를 읽고 변경할 수 있게 한다. **AI usage report를 포함한 사용량 보고서의 `user_id` 열 추가 예고**는 에이전트·봇 비용과 감사를 사용자 이름이 아니라 안정적인 식별자에 연결하게 한다. 각각 커널 런타임 보안과 이슈 협업, 비용 보고에 관한 별도 소식이다. 이를 하나의 제품 출시로 묶어 설명하지 않는다. 공통 질문은 따로 있다. **AI가 일을 빠르게 만들수록 어떤 변경은 누가 승인하고, 어느 상태를 신뢰하며, 나중에 무엇으로 검증할 것인가?**

이번 글은 공식 발표의 문장을 그대로 옮기는 데 그치지 않는다. Shirudo의 공식 저장소, 시작 안내, 작동 원리, 위협 모델, 시스템 요구사항을 대조해 **발표가 입증한 것과 아직 입증하지 않은 것**을 분리한다. 이어 GitHub의 공식 변경 기록에서 운영 자동화가 실제로 받는 영향을 따진다. 아래의 설계 예시와 체크리스트는 원문이 제공하는 제품 기능이라는 주장이 아니라, 그 사실을 바탕으로 편집자가 제안하는 적용·검증 절차다.

## 배경 — 패치와 방패 사이의 위험 시간

취약점이 알려진 순간부터 영구 패치가 운영에 반영될 때까지는 위험한 간격이 생긴다. 수정 소스가 공개돼도 서비스마다 배포판과 플러그인, 데이터 스키마, 성능 특성이 달라 즉시 재시작하기 어렵다. 패치 후의 회귀가 취약점보다 더 큰 장애를 만들 수도 있다. 반대로 패치를 기다린다는 이유로 아무 통제도 하지 않으면 공격 경로가 열린 채로 남는다. 많은 팀이 이 기간에 웹 애플리케이션 방화벽 규칙, 네트워크 격리, 기능 비활성화, 접근 제한, 임시 코드 수정 등을 쓴다. 어느 방법도 무조건 최선이 아니다. 차단 범위가 넓으면 정상 요청도 막고, 좁으면 변형 공격을 놓친다.

Shirudo가 파고드는 지점은 **작동 중인 시스템에 좁은 방어 논리를 배치하는 것**이다. 공개 발표는 취약한 동작과 정상 동작이 같은 Linux 기능을 사용할 수 있다고 짚는다. 호출 자체를 전면 차단하면 서비스는 안전해지는 대신 멈출 수 있다. 좁은 방패는 입력·문맥·호출 경로를 살펴 문제가 되는 행위를 선택적으로 거부하려 한다. 여기서 ‘좁다’는 좋은 속성이지만 동시에 어려운 속성이다. 좁은 규칙에는 빈틈이 남기 쉽고, 입력 해석이 다르면 공격을 놓칠 수 있다. 새로운 규칙이 실제 악용을 막는지와 평소 요청을 허용하는지는 별개 평가 항목이다.

또 하나의 배경은 AI 코딩 에이전트다. 에이전트는 취약점 설명과 코드 차이를 읽고 방어 후보를 더 빠르게 작성할 수 있다. 하지만 속도는 검증을 생략할 이유가 아니다. 보안 패치는 일반 기능 변경보다 공격자가 의도적으로 우회 방법을 찾는다는 점에서 더 높은 기준이 필요하다. AI가 만들어 낸 조각이 ‘컴파일된다’는 사실은 기능을 보증하지 않고, 한 악용 스크립트를 막았다는 사실은 공격 계열 전체를 막았다는 뜻이 아니다. **AI는 초안을 만드는 과정에 들어갈 수 있지만, 적용 권한과 수용 기준까지 자동으로 가져가지는 않는다.**

### 왜 커널 수준인가

공식 설명에 따르면 Shirudo는 Linux의 eBPF를 이용한다. eBPF 프로그램은 정해진 지점에서 커널과 시스템 이벤트를 관찰하거나 정책을 적용할 수 있다. 이 방식은 애플리케이션 소스 자체를 다시 빌드하지 않고도 실행 중인 호스트의 특정 경로에 방어를 끼워 넣을 여지를 준다. 이때 커널에서 실행한다는 사실은 분명한 장단점이 있다. 전면 프록시를 거치지 않고 가까운 지점에서 판단할 수 있지만, 잘못된 훅 선택·성능 비용·커널 호환성 문제가 서비스 전체에 영향을 미친다. 따라서 ‘재시작이 필요 없다’는 장점만 읽고 ‘가벼운 플러그인’처럼 생각하면 안 된다.

프로젝트의 공식 저장소와 문서는 **BPF upatch와 Java upatch**를 구분한다. BPF upatch는 커널 훅 등에 붙는다. Java upatch는 JVM 애플리케이션 코드를 보호하는 방식으로 설명된다. 공개 저장소의 설명에 따르면 Java 에이전트는 구성된 JVM의 시작 시 로드되므로, 모든 유형의 방패가 아무 준비 없이 무조건 현재 프로세스에 즉시 적용된다고 일반화할 수 없다. OpenAI 발표의 Java4Shell 예시는 실행 중인 Elasticsearch에 붙인 방패 사례로 설명되지만, 이를 전체 Java upatch 방식의 모든 배포 조건으로 확대하지 않는다. 개별 방패의 attach 위치와 로딩 절차를 확인해야 한다.

### ‘서명’이 의미하는 것과 의미하지 않는 것

서명은 **누가 이 산출물을 승인된 키로 만들었는지**, 전달 중 바이트가 바뀌지 않았는지를 검증하는 데 도움을 준다. 저장소 문서는 사용자가 임의의 eBPF를 적재하지 못하도록 초기화 이후 서명된 로더로 경로를 제한하는 구조를 설명한다. 반면 서명 자체는 로직의 옳음을 증명하지 않는다. 운영자가 실수로 잘못된 방패에 서명하면 신뢰된 경로를 통해 잘못된 정책이 설치될 수 있다. 공급망 보안과 동작 정확성은 결합되지만 동일하지 않다. 키 보관·서명 절차·코드 검토·회귀 테스트가 각각 필요한 이유다.

이 구분은 제품의 안전 홍보를 읽을 때도 중요하다. **커널 eBPF 검증기**는 프로그램이 특정 안전 규칙을 만족하는지 검사한다. **서명 확인**은 발행 권한과 무결성을 다룬다. **TPM 측정**은 적재 상태에 대한 사후 증거를 다룬다. 이 중 어느 하나도 특정 취약점이 모든 조건에서 차단되며 정상 트래픽이 전혀 손상되지 않았다는 기능 명제를 직접 증명하지 않는다. 기능 검증은 실제 공격·정상 부하·우회 변형을 포함한 별도 실험이다.

## Top News 1 — OpenAI·Cisco, Shirudo 공개: AI 생성 방패를 검증 가능한 운영 변경으로 만들려는 시도

[OpenAI의 11월 23일 발표](https://openai.com/index/introducing-shirudo/)는 Shirudo를 패치를 준비하는 동안 Linux 시스템을 보호할 오픈소스 런타임이라고 소개한다. 핵심은 운영자가 시험할 수 있는 임시 방패를 만들고, 정상 요청 영향이 허용 가능한지 본 뒤 승인하면 실행 중인 서비스에 적용하는 흐름이다. 발표는 네 가지 역량을 열거한다. **실시간 보호**, **에이전트를 활용한 빠른 방어 개발**, **서명과 커널 검사에 기초한 신뢰 가능한 배포**, **TPM을 이용한 하드웨어 기반 상태 검증**이다. 네 가지가 각각 무엇을 보장하는지 분리해서 읽어야 한다.

첫째, 실시간 보호는 보호 논리를 대상 시스템의 실행 중 경로에 붙인다는 뜻이다. 영구 패치 전까지 시간을 벌 수 있다. 그렇다고 원래 취약한 코드가 수정되는 것은 아니다. 방패가 빠지거나, 취약점 경로가 다른 형태로 호출되거나, 예외 경로가 남으면 문제가 돌아올 수 있다. 방패의 존재 기간과 영구 패치 계획을 함께 관리해야 한다. 임시 통제가 조직의 ‘패치를 더 미루어도 된다’는 근거가 되면 본래 목적이 뒤집힌다.

둘째, AI 에이전트의 빠른 개발은 후보를 만드는 시간을 줄이는 가능성이다. 발표의 Java4Shell 시험은 그 가능성을 보여 준다. 그러나 OpenAI가 공개한 설명에서 확인되는 것은 **통제된 테스트에서 하나의 악용 시도가 막혔고 서비스가 계속 실행됐다**는 범위다. 실험의 상세 부하, 공격 변형의 전체 목록, 장기 운영 데이터가 이 발표만으로 제공된다고 쓰지 않는다. ‘Codex가 보안 패치를 자동 적용한다’, ‘모든 Java4Shell 공격을 차단했다’, ‘재시작 없는 패치가 영구 패치를 대체한다’는 제목은 자료의 범위를 넘는다.

셋째, 신뢰 가능한 배포는 파일 하나를 다운로드해서 `root`로 실행하는 단순 설치보다 더 긴 경로다. Shirudo 문서의 [작동 원리](https://docs.shirudo.dev/start/how-it-works.html)를 따라가면 운영 호스트가 BPF 소스를 빌드하고 서명한다. OCI 저장소가 패키지를 보관·전달할 수 있지만 대상은 서명과 다이제스트를 확인한다. 대상의 커널은 서명된 로더를 확인한 뒤 eBPF 검증기를 실행하고, Shirudo는 프로그램을 지정된 위치에 부착한다. 아카이브와 TPM 측정까지 성공했는지 기록한다. 외부 저장소를 맹신하지 않도록 설계했다는 설명이다. 다만 이 흐름의 첫 부분인 **운영 호스트와 서명 키가 신뢰된다**는 전제를 놓치면 전체 체인이 안전하다는 결론은 성립하지 않는다.

넷째, 하드웨어 기반 검증은 대상이 ‘저는 보호 중입니다’라고 출력하는 상태 보고보다 더 강한 증거를 제공하려 한다. 공식 문서는 대상 TPM이 서명한 인용값과 측정 레지스터, 이벤트 로그를 운영자가 기대한 상태와 비교하는 절차를 설명한다. 읽을 때 주의할 점은 **증거의 무결성**과 **기대한 정책의 적절성**이 다르다는 것이다. TPM이 방패 A가 로드됐음을 보여 주어도 방패 A가 적절한 취약점 경로를 막는지는 기능 시험의 문제다. 운영자가 다른 방패 B를 기대했다면 ‘정상적으로 서명된 A’라도 배포 편차다.

### 실제 공개 저장소가 덧붙이는 중요한 단서

[공식 GitHub 저장소](https://github.com/shirudo-dev/shirudo)는 Shirudo를 **pre-release**라고 명시한다. 운영 대상에는 signed-loader ABI와 Shirudo 커널 패치가 반영된 Linux 커널, TPM 2.0이 필요하다고 설명한다. 이 문구 하나가 보도 자료를 실무에 번역할 때의 기준이다. 현재 일반적인 Linux 호스트에 표준 패키지 하나만 설치하면 동일한 방어 모델을 얻는다고 가정할 수 없다. 저장소는 x86-64에서 CI의 모든 테스트 계층, arm64에서 호스트 테스트, arm64의 로컬 테스트 VM을 언급하며 riscv64 대상 검증은 대기 중이라고 적는다. 이 역시 ‘모든 아키텍처에서 운영 준비 완료’와는 다르다.

저장소는 boot-time enforcement, signed/sealed BPF, TPM measurement, pull-based delivery, 관측 기능, 정책 적용, SBOM 등을 기술한다. 이 항목들은 제품 방향을 판단하는 데 유용하지만 각각 사용 가능한 범위와 전제가 다르다. 실제 도입 검토라면 README의 기능 목록보다 [시스템 요구사항](https://docs.shirudo.dev/operate/plan/system-requirements.html), [위협 모델](https://docs.shirudo.dev/security/threat-model.html), [배포 체크리스트](https://docs.shirudo.dev/operate/deploy/deployment-checklist.html)를 먼저 읽어야 한다. 특히 위협 모델은 커널과 부팅 체인, TPM, 운영 호스트, 서명 키에 대한 가정을 나열한다. 일반적인 제품 소개보다 불편하지만, 통제의 경계를 이해하는 데 더 중요하다.

### 방패의 생애주기: 초안부터 제거까지

1. **취약 경로 특정:** 어떤 입력·상태·호출이 악용을 가능하게 하는지 재현한다. 단순히 CVE 이름만 적어서는 방패의 attach 위치와 거부 조건을 설계할 수 없다.
2. **후보 작성:** 사람이든 에이전트든 작은 방어 로직을 제안한다. 이 단계의 결과물은 서명 전 코드이지 승인된 운영 정책이 아니다.
3. **정상 부하와 악용 부하 시험:** 공격 재현이 막히는지, 정상 요청이 실패하지 않는지, 지연과 자원 사용이 허용 가능한지 본다. 세 검증은 서로 대체하지 않는다.
4. **서명과 패키징:** 운영자 키로 승인된 upatch를 서명한다. 저장소 문서상 BPF 로더와 데이터에 대한 서명, 불러올 위치의 메타데이터, 배포를 위한 패키지·인덱스 절차가 있다.
5. **대상에서 확인·적재:** 대상은 서명과 정책 경로를 검사하고 지정된 훅에 방패를 붙인다. 실패한 대상이 몇 개인지와 실제로 보호 중인 대상이 몇 개인지는 배포 요청 건수와 달라야 한다.
6. **측정과 독립 검증:** TPM에 적재 상태의 변경을 기록하고 운영자가 기대하는 상태와 비교한다. 단순 대시보드의 녹색 불빛보다 강한 증거가 목표다.
7. **관측·되돌리기:** 오탐이나 성능 문제가 나오면 승인된 unload 경로를 사용한다. 제거 역시 어떤 보호가 빠졌는지 측정·기록해야 한다.
8. **영구 패치와 종료:** 정식 수정본을 배포하고 취약점 재현이 막히는지 다시 확인한 뒤 임시 방패의 필요성을 종료한다. 임시 정책이 오래 쌓이면 중복·충돌·운영 복잡성이 증가한다.

이 순서는 공식 문서의 build/sign, package/publish, pull, load, measure, attest, export, unload 흐름을 실무 용어로 해석한 것이다. 실제 명령과 환경 조건은 문서를 따라야 한다. 여기서 ‘AI 생성’은 두 번째 단계에만 들어간다. 네 번째 단계의 서명 키나 여섯 번째 단계의 기대 상태를 모델이 임의로 변경할 권한으로 확대하지 않는 것이 설계상의 핵심이다.

### 통제된 Java4Shell 사례를 어떻게 읽어야 하나

OpenAI는 Codex 생성 방패가 Java의 Base64 디코더에 입력 검사를 더해, 실행 중인 Elasticsearch 프로세스에 부착된 상태에서 악성 입력을 거부했고 서비스는 계속 실행됐다고 설명한다. 이는 **특정 입력 조건의 악용 시도 차단과 서비스 생존**을 보여 주는 데 의미가 있다. 그러나 실제 현장에서 결정해야 할 질문은 더 많다. 어떤 입력 인코딩과 우회 변형이 있는가? 어떤 Elasticsearch·JVM 조합에 같은 방패가 붙는가? 공격과 정상 데이터가 동일한 Base64 경로를 공유하는가? 초기화가 늦어 공격 창이 남는가? 이미 공격당한 호스트에도 의미가 있는가? 방패가 오탐을 내면 어느 기능이 손상되는가? 이 질문들은 발표가 틀렸다는 반론이 아니라 **발표의 증거를 운영 승인 조건으로 바꿀 때 필요한 추가 검증**이다.

서비스 무중단은 특히 좁게 해석해야 한다. 발표의 특정 실험에서 재시작이 필요하지 않았다는 사실과 모든 배포 환경에서 무중단 적용이 보장된다는 주장은 다르다. 커널 요구사항을 맞추기 위한 최초 배포에는 부팅 체인 변경이 필요할 수 있다. 방패를 적용하는 데 재시작이 없더라도 사전 인프라 준비가 무중단이라고 보장되는 것은 아니다. 이 구분을 하지 않으면 ‘zero downtime’이라는 말이 지나치게 많은 단계에 걸쳐 사용된다.

## 깊게 보기 — Shirudo가 보호하는 경계와 남겨 두는 위험

보안 제품의 기능 목록만 보면 ‘서명·TPM·eBPF’가 충분한 것처럼 들린다. 그러나 [공식 위협 모델](https://docs.shirudo.dev/security/threat-model.html)은 보호 목표뿐 아니라 그 목표가 의존하는 가정과 미해결 위협을 함께 적는다. 그 문서가 특히 명확하게 구분하는 것은 **커널이 직접 강제하는 것**, **userspace에서 점검하는 것**, **운영자가 증거를 검증해야 탐지되는 것**이다. 세 가지는 같은 강도의 통제가 아니다. 예를 들어 TPM 증거가 있어도 운영자가 기대값을 계산하고 비교하지 않으면 해당 증거만으로 ‘승인된 방패만 돌고 있다’는 결론을 얻기 어렵다.

문서는 G1~G8 보호 목표, A1~A15 가정, T1~T15 대응 위협, R1~R23 잔여 위험, U1~U20 미해결 위협을 식별자로 관리한다. 숫자의 존재 자체가 품질 보증은 아니지만, 어떤 주장이 무엇을 전제로 하는지 검토 가능하게 만든다. 무엇보다 목표 항목의 끝에서 **upatch의 정확성을 보증하는 목표는 없다**고 분명히 적는다. 프로젝트가 방패의 *출처*를 보증하려는 것과 방패의 *내용*을 보증하는 것은 다른 문제라는 뜻이다. AI 생성 코드를 사용하는 경우 이 차이는 더욱 크다.

### 경계 1: 커널을 신뢰한다는 전제

위협 모델은 커널의 eBPF 검증기와 JIT, 키링·암호화 코드, dm-verity, TPM 드라이버가 명세대로 작동한다고 가정한다. 운영자는 이 가정을 완전히 시험할 수 없다. 또한 signed-loader ABI와 필요한 LSM 훅이 있는 특별한 커널이 필요하다. 문서는 관련 기능이 일반 upstream 커널에 아직 없다고 설명하고, 프로젝트의 테스트 커널 빌드가 이를 포함한다고 적는다. 따라서 ‘Linux에서 동작’이라는 상위 표현을 현재의 보편적 배포 호환성으로 오해하면 안 된다. 기존 커널 공급업체의 업데이트 체계와 장기 지원 정책, 자체 커널을 사용하는 부담을 함께 판단해야 한다.

보안 도구가 커널에 가까울수록 지켜야 할 영역과 깨질 수 있는 영역이 함께 커진다. 새 커널을 들이는 것이 기존 커널의 취약점 패치 주기보다 느리거나, 관측 도구와 충돌하거나, 장애 복구를 더 어렵게 만든다면 단일 CVE 대응 이익만으로 도입을 정당화하기 어렵다. 반대로 동일한 커널 이미지를 통제할 수 있고 높은 가용성을 요구하는 좁은 대상군에서는 실험 가치가 있다. **어떤 자산에서 언제 사용할지**를 먼저 정하지 않고 전체 서버를 일괄 적용 대상으로 삼는 것은 좋지 않은 초기 선택이다.

### 경계 2: 부팅 체인이 초기 통제의 출발점

공식 작동 원리는 운영 대상의 initrd 단계에서 Shirudo가 시작되고, 신뢰된 이미지와 인증서를 등록·봉인한 뒤 BPF LSM을 부착한다고 설명한다. ‘초기화 이후’에는 사용자가 임의의 BPF 프로그램을 적재하지 못하게 제한한다는 구조다. 그 말은 거꾸로 **초기화 이전의 부팅 신뢰**가 중요하다는 뜻이다. 위협 모델은 Secure Boot, 서명·측정된 UKI, 특정 PCR 측정, 인증된 커널 명령줄 등 외부 전제를 적는다. 테스트 VM의 빠른 시작 문서도 QEMU가 커널·initrd를 직접 시작하기 때문에 실제 운영 부팅과 측정 방식이 다른 부분을 명시한다.

실무에서 이를 확인할 때는 ‘프로세스가 떠 있다’와 ‘필요한 부팅 보증이 있다’를 분리해야 한다. 보호 데몬이 동작해도 누군가 수정된 initrd로 부팅하여 가드를 붙이지 않았다면 보안 모델은 무너질 수 있다. 반대로 부팅은 정상이지만 서명 키가 유출됐다면 악의적 방패가 정상 경로로 들어올 수 있다. 부팅과 키 보관은 제품 코드 리뷰 밖에서 운영팀이 통제해야 할 부분이다.

### 경계 3: 서명 키와 운영 호스트

Shirudo 문서는 운영 호스트의 서명 키와 빌드 도구를 신뢰한다고 가정한다. 이는 일반적인 공급망 문제와 연결된다. 에이전트에게 후보 코드를 작성하게 할 수는 있지만, 서명 키가 있는 호스트까지 에이전트의 무제한 실행 환경으로 만들면 검토 단계가 의미를 잃는다. 적어도 후보 코드가 코드 리뷰와 독립 테스트를 거쳐 승인된 아티팩트로 고정된 뒤, 별도 권한의 서명 작업을 수행하는 구조가 필요하다. 누가 생성했는지가 아니라 **어떤 바이트를 어떤 승인으로 서명했는지**를 기록해야 한다.

서명 키가 영구적으로 안전하다고 가정해서도 안 된다. 키 회전, 인증서 취소, 긴급 차단, 서명 정책 변경은 평상시 배포보다 더 복잡하다. 공식 문서는 봉인된 키링과 서명된 config의 체계를 설명하지만, 조직의 키 분리와 사고 대응 절차는 조직 스스로 설계해야 한다. 사고가 발생했을 때 모든 대상에 새로운 신뢰 정보를 안전하게 공급할 수 없다면 일상적인 ‘서명 확인’도 신뢰 기반을 잃는다.

### 경계 4: TPM 증거가 증명하는 범위

공식 빠른 시작은 테스트 VM에서 방패를 로드하고, 운영 호스트에서 새 nonce를 만들어 TPM 인용 증거를 요청하며, 기대한 측정 레지스터 값과 비교하는 흐름을 제공한다. nonce는 과거 증거를 재사용하는 일을 막는 데 중요하다. 측정된 상태와 운영자가 예상한 상태를 맞춰 보는 것이지 단순히 서명된 JSON을 저장하는 데서 끝나지 않는다. 대상의 일반 상태 출력과 TPM 증거를 구별해야 한다. 위협 모델은 텔레메트리 자체의 출처 보증에도 한계가 있음을 명시한다.

그러나 TPM 증거도 ‘현재 프로세스의 모든 메모리와 애플리케이션 의미가 안전하다’는 만능 증명은 아니다. 증거에는 기대 상태 정의, 대상 식별, 부팅 체인의 신뢰, 사용한 attestation key의 고정, 시각과 신선도 정책이 필요하다. 예를 들어 운영자가 자신의 기대 목록을 잘못 구성해 승인되지 않은 방패를 기대 목록에 넣었다면 비교가 통과해도 조직 정책 위반일 수 있다. 반대로 승인된 방패가 로드됐지만 아직 적용되지 않는 훅에 붙었다면 측정과 기능 검증 결과가 달라질 수 있다.

### 경계 5: ‘검증 가능한 로딩’과 ‘실제 차단’

하나의 방패에 대해 최소한 네 종류의 질문을 던질 수 있다. **출처:** 누가 승인하고 서명했는가. **설치:** 대상에 기대한 버전이 로드됐는가. **적용:** 원하는 호출 지점에서 평가되는가. **효과:** 악용을 막으면서 정상 요청을 허용하는가. Shirudo는 앞의 두 종류와 일부 적용 상태를 더 강하게 다루려 한다. 마지막 효과는 취약점별 시험과 운영 관측에 의존한다. 이 네 항목 중 하나를 다른 항목의 대리 지표로 쓰면 안 된다.

예를 들어 CI에서 실험 공격 하나가 실패한 것을 보고 곧바로 전체 대상에 서명하면 변형 공격에 대한 적용 범위가 불분명하다. 반대로 TPM 인용이 맞다는 사실만 보고 무해성 검증을 생략하면 정상 사용자 요청이 막힐 수 있다. 부하 테스트에서 지연이 작게 나왔어도 특정 오류 경로에서만 막대한 비용이 든다면 실제 장애 시에 보안 도구가 장애를 증폭할 수 있다. **보안 성공과 서비스 성공을 동일한 테스트 케이스로 측정하지 않는 것**이 중요하다.

### 경계 6: 제거도 승인된 변경이다

방패를 올리는 것보다 내리는 것이 쉬워 보이지만, 제거는 다시 취약 경로를 여는 행위일 수 있다. 공식 문서는 unload directive도 서명되고, 현재 로드된 payload digest와 맞는지 확인하며, 제거 상태도 측정하는 흐름을 설명한다. 실무에서 올바른 질문은 ‘원복할 수 있나’에서 멈추지 않는다. 원복이 필요한 상태를 누가 판단하는가, 공격이 진행 중이라면 다른 격리 통제는 준비됐는가, 여러 방패가 같은 훅에 붙어 있을 때 의존성은 무엇인가, 영구 패치 후 제거 시점을 어떻게 잡는가. 제거 경로가 기술적으로 있어도 운영 절차가 없으면 ‘롤백 가능’은 공허하다.

### 경계 7: 실험 환경과 운영 환경의 차이

[빠른 시작 문서](https://docs.shirudo.dev/start/quickstart.html)는 로컬 VM, 소프트웨어 TPM, 프로젝트가 제공하는 테스트 커널, 운영 호스트와 대상을 분리한 실습을 설명한다. 재현 가능성을 높인 좋은 안내지만 **실습에 성공하는 것과 운영 준비가 되는 것은 다르다.** 실제 운영에서는 물리적 TPM 또는 믿을 수 있는 가상 TPM, 측정 부팅, 호스트별 키와 인증서 관리, 손실·복구 절차, 네트워크·레지스트리 가용성, 장기 커널 업데이트가 개입한다. 실습을 도입 승인으로 오인하지 않고, 실습에서 무엇이 대체됐는지 목록으로 남기는 편이 안전하다.

## 개발자에게 의미 — ‘AI가 만든 코드’가 아니라 ‘증거가 붙은 변경’을 배포한다

Shirudo 소식의 개발자적 의미는 특정 eBPF 프로젝트 채택 여부보다 더 넓다. 기존의 AI 코딩 경험은 주로 사람이 PR을 읽고 테스트를 돌리는 과정을 강조했다. 커널 수준 임시 방패는 그 과정을 **시간 압박이 있는 보안 사고**와 연결한다. 공격이 공개된 순간 몇 시간 안에 방어 후보를 만들고 싶을 수 있다. 동시에 잘못된 방패는 정상 서비스 거부나 잘못된 안도감을 만들 수 있다. 속도와 검증의 긴장은 일반 기능 PR보다 훨씬 크다.

### 생성 단계를 분리해 평가하기

‘AI가 취약점을 막는다’라는 문장을 여러 작업으로 쪼개면 설계가 선명해진다. (1) 취약점 설명과 패치 diff를 읽고 영향을 받는 경로를 찾아낸다. (2) 방어 지점을 제안한다. (3) 최소 거부 조건을 코딩한다. (4) 정상·악용 테스트를 작성한다. (5) 우회 입력을 탐색한다. (6) 성능을 측정한다. (7) 리뷰 자료를 작성한다. (8) 승인된 바이트를 서명한다. (9) 제한된 대상에 배포한다. (10) 기대 상태를 검증한다. 에이전트가 잘할 수 있는 일과 사람·별도 권한 체계가 맡아야 할 일을 각 단계마다 다르게 설정해야 한다. 특히 8~10단계를 이전 단계와 동일한 에이전트 권한으로 자동 연결하면 단일 오류가 곧바로 전사적 보안 변경이 된다.

모델이 작성한 코드의 설명도 검증 대상이다. 에이전트가 ‘악성 입력만 거부한다’고 써도 실제 조건문이 정상적인 인코딩 조합까지 거부한다면 설명은 틀렸다. 설명과 구현을 서로 다른 증거로 두고, 테스트가 둘을 확인하게 해야 한다. 소스 분석에 대한 자신감과 실제 공격 재현 범위를 분리해 기록하면 나중에 새로운 변형 공격이 나왔을 때 판단을 갱신할 수 있다.

### 패치 diff에서 방패 정책을 추출하는 함정

영구 패치의 diff가 한 줄이라도 방패 정책이 한 줄인 것은 아니다. 소스 패치는 프로그램 내부의 불변식을 복구할 수 있지만, 런타임 방패는 관측 가능한 입력과 훅에 의존한다. 코드 경로가 여러 언어·라이브러리 계층을 지나면 최종적으로 보이는 정보가 너무 적을 수 있다. 문자열을 커널 이벤트에서 검사하려 해도 이미 정규화·디코딩이 끝났거나 반대로 아직 인코딩돼 있다면 기대한 판단과 다른 결과가 나온다. 어떤 계층에서 방어할지 결정할 때 ‘얼마나 일찍’, ‘얼마나 정확히’, ‘얼마나 안전하게 실패하는지’를 비교해야 한다.

또한 방패는 공격자가 읽고 우회할 수 있다고 가정하는 편이 낫다. 오픈소스라는 사실은 방어 논리의 검토를 돕지만 동시에 공격자도 조건을 본다는 의미다. 특정 문자열이나 고정 시그니처만 막는 방패는 우회 난도가 낮을 수 있다. 공개 전후의 우회 탐색은 방어 성숙도의 핵심이고, ‘비밀 규칙이므로 안전하다’는 접근보다 유지 가능하다. AI 에이전트에게 변형 입력을 생성하게 할 수 있으나, 모델이 생각해 낸 목록만으로 포괄성을 주장할 수는 없다.

### 테스트는 합격 점수보다 실패 지도를 만들어야 한다

보안 테스트가 단일 pass/fail로 끝나면 운영자가 배포 범위를 결정하기 어렵다. 최소한 (a) 알려진 악용 재현, (b) 인코딩·길이·경계값 변형, (c) 정상 트래픽의 대표 표본, (d) 예외 및 오류 응답, (e) 고부하와 동시성, (f) 방패 적용·제거 중의 요청, (g) 대상 커널·서비스 버전 차이, (h) 관측·로그의 무결성을 나눠 봐야 한다. 모든 조합을 완벽하게 시험할 수는 없다. 대신 **시험하지 못한 공간을 드러내고 제한된 배포를 선택하는 근거**를 만들어야 한다.

특히 오탐과 미탐의 비용은 비대칭이다. 결제 승인이나 인사시스템의 급여 처리처럼 정상 요청을 막는 비용이 큰 업무에서는 자동 차단의 문턱이 높아야 한다. 공개된 공격 경로가 즉각적인 데이터 유출을 허용하고 영구 패치가 멀다면 더 적극적인 임시 차단을 선택할 수 있다. 같은 방패라도 서비스의 업무 가치와 장애 대응 능력에 따라 승인 결론이 달라지는 것이 정상이다. 제품 문서가 모든 조직의 위험 허용도를 대신 정할 수는 없다.

### 작은 서비스에서도 적용할 수 있는 패턴

Shirudo를 실제 설치하지 않아도 설계 원칙은 쓸 수 있다. 웹 애플리케이션이 새로운 입력 검증 규칙을 긴급 배포한다고 가정하자. 에이전트가 규칙 초안을 만들고 테스트를 제안한다. 사람은 코드·테스트·영향 범위를 검토한다. CI가 악용 재현과 정상 요청을 검증한다. 배포 시스템은 승인된 이미지 다이제스트만 적용한다. 운영 대시보드는 배포 대상별 실제 버전을 보여 준다. 사고 후에는 어느 시각에 어떤 규칙이 어느 호스트에서 켜졌는지 추적한다. 서명된 eBPF나 TPM이 없어도 **초안과 승인, 배포 요청과 실제 상태, 정상성 테스트와 공격 차단 테스트를 분리**하는 원리는 동일하다.

반대로 Shirudo의 고급 기술을 쓴다고 해서 기본 운영이 생략되는 것은 아니다. 패치 일정표, 자산 목록, 취약 버전 식별, 모니터링, 장애 중지 권한이 없다면 서명·측정 체계만 도입해도 의사결정은 약하다. 가장 인상적인 기술적 장치보다, 실제로 해당 취약 버전을 운영하는 서버를 정확히 찾는 일이 먼저일 수도 있다.

## Top News 2 — GitHub 이슈 상태·저장소 보드 공개 미리보기: 에이전트의 ‘진행 중’을 어떻게 믿을 것인가

[GitHub의 11월 23일 공식 변경 기록](https://github.blog/changelog/2026-11-23-issue-statuses-and-repository-boards-are-in-public-preview/)은 기존의 open/closed만으로는 작업의 실제 위치를 설명하기 어렵다는 문제에서 출발한다. 공개 미리보기에서는 이슈에 **Backlog, Todo, In progress, In review, Done, Not planned, Duplicate** 상태를 설정한다. 이 값은 이슈 목록, 이슈 대시보드, 저장소 보드에 나타나고 `status:` 필터로 찾을 수 있다. 저장소의 saved view는 보드 레이아웃을 지원하며 열·swimlane·표시 필드·정렬을 설정할 수 있다. 조직이 더 복잡한 계획 기능을 원하면 GitHub Projects를 쓰라는 안내도 함께 있다.

AI 관련성이 생기는 지점은 상태 변경의 자동화다. 발표에 따르면 이슈에 **draft PR**을 연결하면 In progress가 되고, draft PR을 **Ready for review**로 바꾸거나 open PR을 연결하면 In review가 된다. 담당자를 배정하면 Todo, 에이전트를 배정하면 In progress로 설정된다. GitHub Project의 status 값이 이슈 상태와 일치할 때는 양쪽 변경이 동기화된다. GraphQL, REST API, MCP 서버가 이 상태를 읽고·설정하고·초기값을 선택할 수 있으며 상태 변경을 Copilot automations 트리거로 쓸 수 있다고 설명한다.

이 내용은 단순한 칸반 미관 업데이트가 아니다. 에이전트가 작업을 시작하면 이슈 상태가 달라지고, 다른 에이전트 또는 자동화가 그 상태를 다시 읽는 **공유 상태 기계**가 된다. 그러므로 상태는 실행 권한과 업무 책임을 엮는 신호가 될 수 있다. 예를 들어 In progress인 이슈를 다른 에이전트가 중복 선택하지 않게 할 수 있고, In review에 올라온 PR을 리뷰 큐에 넣을 수 있다. 하지만 정확히 그 이유 때문에 상태가 *사실*인지 *자동화가 추론한 값*인지 표시할 필요가 있다.

### 상태 변경은 품질 판정이 아니다

에이전트 배정이 In progress가 되는 것은 ‘일을 시작할 주체가 지정됐다’는 뜻이지 코드를 실제로 수정했다는 증거가 아니다. PR이 열려 In review가 됐다고 해서 테스트가 통과하거나 리뷰어가 지정됐다는 뜻도 아니다. Done이라는 값을 누가 설정하든 배포·사용자 확인까지 끝났다는 의미로 자동 확장해서는 안 된다. 각 상태의 **진입 조건**과 **완료 조건**을 팀이 정의해야 한다. GitHub가 제공하는 자동화 규칙은 출발점이지 조직 업무 정의의 최종판이 아니다.

초기에 흔한 실패는 서로 다른 상태 표현의 충돌이다. 이슈는 In review인데 PR은 CI 실패로 머물 수 있다. 이슈는 Done인데 연결된 PR은 아직 미병합일 수 있다. 에이전트가 배정되어 In progress가 됐지만 실제 실행은 권한 부족으로 멈췄을 수 있다. 이 상황에서 ‘상태’만 대시보드에 보이면 진행률이 과대평가된다. 최소한 PR 링크, 최신 CI 결과, 승인자, 마지막 활동 시각, 차단 사유를 함께 봐야 한다. 상태 전환 이벤트를 근거와 연결해야 자동화가 오도하지 않는다.

### 에이전트 협업에서 필요한 상태 불변식

다음은 공식 기능 설명이 아니라 실무 설계 제안이다. 첫째, **동일 이슈의 중복 작업 소유자**를 제어한다. In progress가 자동으로 붙더라도 여러 에이전트가 같은 브랜치를 건드리면 충돌할 수 있다. 둘째, **상태와 권한을 분리**한다. In review로 갔다고 자동 merge 권한이 생기지 않는다. 셋째, **재시도와 실패를 구분**한다. 에이전트가 멈췄다면 In progress를 영구 방치하지 말고 차단 사유·재개 조건을 기록한다. 넷째, **API 쓰기 권한의 범위를 제한**한다. MCP 또는 REST를 통해 에이전트가 상태를 바꿀 수 있다면 모든 상태를 임의로 설정해도 되는지 검토한다. 특히 Done, Not planned, Duplicate는 업무를 숨기거나 종료시키는 효과가 있어 사람 검토가 필요한 팀도 있다.

다섯째, **상태 동기화의 순환을 살핀다**. GitHub Project 값과 이슈 상태가 동기화되고, 상태 변경이 다시 Copilot automation을 발동하면 조건을 잘못 구성했을 때 반복 이벤트가 생길 수 있다. 제공 기능이 자동으로 순환을 일으킨다는 뜻은 아니다. 여러 자동화 규칙을 조합하는 팀이 자신의 트리거와 종착 조건을 시험해야 한다는 것이다. 여섯째, **대기 중과 진행 중을 구분**한다. 에이전트가 사용자 승인이나 외부 API 접근을 기다린다면 실제 일을 진행하지 못한다. 상태 한 칸만으로는 이 차이를 담기 어렵다. 이슈 본문이나 필드에 blocker와 owner를 남겨야 한다.

### 작은 팀의 도입 예시

웹앱 팀이 버그 이슈를 만들고 에이전트에게 조사만 맡긴다고 가정하자. 에이전트 배정으로 In progress가 되지만, 팀의 정의에는 ‘조사 중’이라는 하위 의미가 필요하다. 에이전트가 재현 절차와 원인 후보를 이슈에 남기고 PR을 만들면 In review로 넘어간다. 이때 CI 실패가 있다면 리뷰어에게 무조건 보낼 것이 아니라 별도 체크 실패로 보여 준다. 리뷰가 끝난 뒤 병합해도 아직 배포가 끝나지 않았다면 Done을 자동 선언하지 않는 팀이 있을 수 있다. 반대로 코드 병합이 업무 완료 정의인 저장소라면 Done을 사용할 수 있다. 핵심은 도구의 자동 상태가 팀의 종료 정의와 일치하는지 확인하는 것이다.

또 다른 예는 인사시스템의 사용자 권한 버그다. ‘다른 직원의 휴가 정보가 검색된다’는 이슈는 일반 UI 버그와 위험 등급이 다르다. 에이전트가 이슈에 배정돼 In progress가 되더라도 실제 민감 데이터를 에이전트 테스트에 넣을 권한을 준 것은 아니다. 테스트 데이터는 익명·합성 자료로 만들고, 수정 PR은 접근 제어 테스트와 함께 검토한다. 상태 보드의 편리함을 데이터 접근 승인과 혼동하면 안 된다.

### 제품 기능 자체의 경계

GitHub 발표가 보장하는 것은 **공개 미리보기**라는 배포 상태다. 조직별 이용 조건이나 정책, 버전별 동작 차이를 적용 전에 확인해야 한다. 보드가 GitHub Projects와 동일한 모든 기능을 제공한다는 설명도 아니다. 기존 이슈 필드가 이슈 유형에 종속됐던 구조가 바뀌어 Priority 외의 필드를 유형에 관계없이 추가할 수 있게 됐지만, 기본 노출은 여전히 유형에 고정한 필드에 영향을 받는다. 이 부분은 기존 자동화나 UI 운영에 작게 보이지만 영향을 줄 수 있으므로 도입 시 테스트할 만하다.

## Top News 3 — GitHub AI 사용량 보고서에 `user_id`: 에이전트 비용과 감사의 결합 키가 바뀐다

[GitHub의 별도 11월 23일 공지](https://github.blog/changelog/2026-11-23-usage-reports-will-include-a-user-id-column-starting-december-1/)는 **2026년 12월 1일부터** `username` 열이 있는 사용량 보고서에 `user_id` 열을 바로 뒤에 추가한다고 설명한다. 대상은 상세 사용량 보고서, **AI 사용량 보고서**, 프리미엄 요청 사용량 보고서이며 REST API로 내보내는 파일에도 적용된다. 요약 보고서는 변하지 않는다. 적용 범위는 모든 GitHub Enterprise Cloud 계정 유형과 GitHub Team의 독립 조직이다. 오늘 이미 열이 바뀌었다는 뜻이 아니라 **다가오는 스키마 변경 예고**다.

GitHub가 밝힌 실무 이유는 이름보다 안정적인 계정 식별이다. 삭제된 계정은 기존 `username`이 비어 같은 값으로 보일 수 있지만 `user_id`가 있으면 각각 구분할 수 있다. 사용자가 이름을 바꿔도 동일 계정의 사용량을 따라갈 수 있고, 감사 로그 이벤트와 조인할 수 있다. `user_id`는 봇 계정을 포함한 사용량 생성 계정의 ID다. 특정 계정에 연결되지 않은 사용량에서는 비어 있을 수 있다. 이는 모든 행에 반드시 값이 있다는 뜻이 아니므로 ETL에서 null/빈 값을 예외 처리해야 한다.

가장 직접적인 운영 영향은 **위치 기반 CSV 파서**다. `username` 뒤에 새 열이 끼어들면 이후 열의 인덱스가 한 칸씩 밀린다. 예를 들어 세 번째 열을 비용이나 요청 수라고 가정하는 스크립트가 새 파일을 읽으면 완전히 다른 값을 그 필드에 넣을 수 있다. 실패가 눈에 띄면 다행이지만 숫자로 파싱 가능한 엉뚱한 열이라면 조용히 잘못된 보고서를 만들 수 있다. GitHub도 12월 1일 전에 열의 위치가 아닌 **헤더 이름으로 읽도록** 바꾸라고 권고한다.

### AI 비용 보고에서 `user_id`가 특히 중요한 이유

AI 사용량은 사람 사용자뿐 아니라 에이전트·봇 계정에 쌓일 수 있다. 계정 표시 이름은 팀 정책이나 조직 개편에 따라 바뀐다. 팀이 `username`만 기준으로 월간 집계를 하면 같은 계정을 둘로 나누거나 다른 삭제 계정을 하나로 합칠 수 있다. 안정적인 ID로 묶으면 변경 이력과 감사 이벤트를 연결하기 쉬워진다. 그러나 안정적인 ID가 **비용 책임자**와 동일한 것은 아니다. 봇 계정 하나가 여러 제품팀의 작업을 실행한다면 `user_id`만으로 어느 팀 예산인지 알 수 없다. 실행을 발생시킨 저장소·워크플로·작업·승인자 같은 맥락도 필요하다.

또한 `user_id` 도입 뒤 과거 보고서와 새 보고서를 단순 연결할 수 있는지 검토해야 한다. 과거 데이터에 ID가 없으면 이름 변경이나 계정 삭제 이후 과거값을 완벽히 복원하지 못할 수 있다. 현재 사용할 수 있는 사용자 디렉터리와 감사 기록을 이용해 가능한 범위에서 매핑하고, 불확실한 부분을 명시해야 한다. 모든 과거 행을 억지로 하나의 ID에 연결하면 오히려 잘못된 비용 귀속이 된다. 이름과 ID, 당시의 조직 소속, 현재의 조직 소속을 별도 차원으로 보존하는 편이 좋다.

### 행별 반올림의 함정

GitHub는 삭제된 서로 다른 계정의 사용량이 이전에는 빈 이름 때문에 한 행으로 뭉쳤다가 앞으로는 분리될 수 있으며, 금액 계산 방식은 같지만 행별 반올림 때문에 합계의 **마지막 소수점 자리**가 약간 다를 수 있다고 명시한다. 이를 곧바로 청구액 오류나 AI 사용량 급증으로 해석하면 안 된다. 비교할 때는 원본 보고서 종류, 대상 기간, 집계 단위, 반올림 자리, 계정 분리 여부를 맞춰야 한다. 단순히 ‘이번 달 총합이 지난달보다 0.01 다르다’는 알람이 유의미한 비용 이상 신호인지 먼저 검토해야 한다.

## 세 소식을 함께 읽을 때 보이는 연결: 작업 상태, 실행 권한, 비용과 보안의 증거

Shirudo는 보안 변경을 만들고 운영 대상에 실어 보낸 뒤 실제 적용 상태를 증명하는 문제를 다룬다. GitHub 이슈 상태는 누가 어떤 작업을 맡아 어느 단계에 있는지를 공유한다. 사용량 보고의 `user_id`는 그 일을 수행한 계정과 비용·감사를 연결하는 실마리다. 세 제품이 서로 통합됐다는 발표는 없고, 아래는 **서로 다른 공식 소식에서 도출한 운영 프레임**이다.

이 프레임에서 에이전트 실행을 네 가지 레코드로 나눌 수 있다. **의도 레코드**는 이슈와 승인된 작업 범위다. **변경 레코드**는 코드·PR·서명된 아티팩트다. **상태 레코드**는 실제 대상의 배포·적재·관측이다. **비용 레코드**는 계정과 작업의 사용량이다. 좋은 자동화는 레코드 네 개가 같은 내용을 의미하도록 묶되, 어느 하나가 다른 하나를 대신한다고 가정하지 않는다. 이슈가 Done이라고 호스트의 방패가 켜진 것은 아니고, TPM이 방패를 측정했다고 이슈의 요구사항이 모두 충족된 것은 아니다. `user_id`가 있다고 실행의 승인자가 그 계정이라고 단정할 수도 없다.

보안 사고를 예로 들면 이슈에는 영향 자산과 방어 목표가 적힌다. 에이전트가 제안한 방패 PR에는 코드와 테스트 결과가 있다. 운영자가 승인해 서명한 아티팩트의 다이제스트가 배포 기록에 들어간다. 실제 대상은 측정 상태로 보고된다. 비용 보고서에는 에이전트가 사용한 리소스가 집계된다. 이 연결고리를 사람이 감사할 수 있어야 ‘빠른 방어’가 ‘설명 가능한 방어’가 된다. 이 기록을 모두 한 거대한 자동화 봇에 맡기면 봇의 오류·권한 오용이 모든 증거를 동시에 오염시킬 수 있다. 분리된 승인과 독립 검증의 가치가 여기 있다.

### 어떤 자동화를 먼저 해야 하는가

우선 **읽기와 제안**을 자동화한다. 영향을 받는 버전 찾기, 취약점 재현 정보 정리, 테스트 케이스 제안, 관련 이슈 연결, 상태·비용 리포트 생성은 비교적 되돌리기 쉽다. 다음으로 **제한된 범위의 실행**을 자동화한다. 실험 VM이나 소규모 카나리 대상에서 방패가 실제로 붙고 정상 부하가 유지되는지 확인한다. 마지막으로 **전면 적용·제거**를 다룬다. 이때는 대상 목록, 승인자, 배포 창, 중지 조건, 독립 검증자를 명확히 둔다. 에이전트가 제안 단계에서 높은 정확도를 보여도 전면 배포 권한이 자동으로 따라오지는 않는다.

이 순서는 AI 활용을 늦추자는 이야기가 아니다. 위험이 다른 단계에 서로 다른 자동화 속도를 적용하자는 것이다. 사고 초기에 느린 수작업만 고집하면 피해가 커질 수 있다. 반대로 설명 없는 전면 자동화를 허용하면 방어 도구가 새로운 장애원이 된다. 서명된 아티팩트와 상태 증명은 빠른 실행을 더 안전하게 만드는 **근거의 기반**이지, 인간 승인이나 서비스 수준 평가를 지워 버리는 마술이 아니다.

## 운영 포인트 — 긴급 방어를 도입하기 전의 검증 계약

Shirudo 같은 런타임 방어를 평가할 때 일반적인 ‘설치 성공’ 체크리스트는 부족하다. 이 기술은 **악용 가능한 시간**을 줄이기 위해 들어오므로, 실제로 그 시간을 얼마나 줄였는지와 그 대가가 무엇인지 측정해야 한다. 아래 계약은 특정 도구 설치 지침이 아니라, 보안팀·서비스팀·플랫폼팀이 같은 결론을 내리기 위해 합의할 검증 항목이다. 공식 문서가 제공하는 기술적 상태와 조직의 승인 기준을 혼동하지 않도록 구분했다.

### 1. 자산과 취약성의 범위를 먼저 확정

첫 질문은 ‘방패를 설치할 수 있는가’가 아니라 ‘어느 자산이 공격 가능한 상태인가’다. 설치된 패키지 버전만으로는 실제 취약한 코드 경로가 사용되는지 확정할 수 없는 경우가 있다. 반대로 스캐너가 놓친 자체 빌드나 플러그인 경로가 있을 수 있다. 서비스 목록, 외부 노출, 인증 필요 여부, 악용 가능 경로, 데이터 민감도, 장애 비용, 기존 보완 통제를 한 장에 모아야 한다. 이 목록이 없으면 방패 배포 성공률도 분모가 없다. 열 대 중 아홉 대에 적용됐다는 보고는 취약한 대상 열 대가 맞는지부터 확인해야 한다.

업무 시스템에서는 데이터 종류가 위험을 바꾼다. 테스트용 위키와 직원 개인정보를 다루는 인사시스템은 같은 취약한 라이브러리를 써도 사고 비용이 다르다. 외부에서 직접 접근 가능한 공개 API와 사내 VPN 뒤의 관리 기능도 긴급성이 다를 수 있다. 이는 어느 한쪽을 무시하자는 뜻이 아니라 우선순위를 정할 때 **취약점 명칭만이 아니라 도달 가능성과 피해**를 고려하자는 뜻이다. 에이전트가 이 분류 초안을 자동으로 만들 수 있지만 실제 방화벽·인증·네트워크 경로를 확인하지 않은 추정값은 확정된 사실처럼 대시보드에 올리면 안 된다.

### 2. 방패의 명세는 금지 조건과 허용 조건을 함께 작성

‘Java4Shell을 막는다’는 문장은 운영 정책으로 너무 넓다. 어떤 입력의 어느 속성이 거부 대상인지, 정상 입력 중 닮은 꼴이 무엇인지, 이미 디코딩된 데이터와 아직 디코딩되지 않은 데이터가 어떤 경로로 오는지 써야 한다. 악성 입력의 예시뿐 아니라 **허용되어야 하는 정상 요청의 예시**를 먼저 고정해 두면, 급한 방어에서 흔한 전면 차단을 발견하기 쉽다. 취약점마다 가장 나은 임시 방어가 eBPF가 아닐 수도 있다. 애플리케이션 설정 변경, 기능 플래그, 역방향 프록시 규칙, 네트워크 차단이 더 단순하고 안전한 경우도 있다. 후보 방법을 같은 위험 기준으로 비교해야 한다.

방패 명세에는 실패 모드도 필요하다. 구성 파일을 읽지 못하면 방어를 끄는가, 서비스를 중단하는가? 서명 확인이 실패하면 로드를 거부하는가? 일부 호스트에서만 실패하면 전체 배포를 멈추는가? 정상 요청 오탐이 생기면 어떤 지표에서 감지되는가? 잠재적인 공격을 놓치면 후속 탐지 수단은 있는가? 이 질문을 구현 뒤에 던지면 도구가 이미 정해 놓은 기본값이 조직의 위험 정책이 된다.

### 3. 생성된 코드의 독립 검토

AI 생성 방패를 검토할 때는 모델이 쓴 자연어 요약보다 실제 diff를 기준으로 삼는다. 변경 범위가 작은지, 외부에서 입력 가능한 값이 어떤 자료형으로 들어오는지, 경계값과 오류 경로를 정확히 다루는지 본다. 특히 문자열 길이, 인코딩, 널 바이트, 잘린 패킷, 다중 요청 결합, 여러 버전에서 다른 구조체 레이아웃이 생기는지 확인한다. 코드가 훅을 지나면서 과도하게 많은 일을 한다면 성능 비용과 재진입·실패 처리의 복잡성이 커진다. 작은 방패라 해도 커널 실행 경로에 붙는다면 일반 유틸리티 함수보다 더 엄격한 검토가 필요하다.

모델이 만든 테스트도 모델이 만든 코드와 같은 오류를 공유할 수 있다. 둘 다 동일한 잘못된 가정, 예를 들어 악성 입력이 단일 인코딩으로만 온다는 가정을 쓰면 테스트는 통과해도 취약점은 남는다. 리뷰어는 다른 출처의 재현 사례, 패치 설명, 실제 프로토콜 사양을 보고 테스트가 빠뜨린 공간을 찾는다. 가능하다면 공격 재현과 정상 부하 표본을 코드 생성 단계와 별도로 확보한다. ‘코드와 테스트를 한 모델이 같이 만들었다’는 사실을 숨기지 말고 리뷰 자료에 표시한다.

### 4. 서명 전 정책 게이트

서명은 배포 가능한 권위를 부여하는 순간이다. 서명 전에 최소한 빌드 재현성, 정적 검사, 취약점 재현, 정상 요청, 성능, 아키텍처 호환성, 롤백 아티팩트를 확인한다. 각 항목의 기준이 분명해야 ‘시간이 급하니 통과’라는 말이 실제 위험 인수 결정인지 단순한 절차 생략인지 구분된다. 모든 테스트가 불가능한 사건이라면 생략한 항목과 대체 통제, 배포 대상 제한, 재평가 시점을 기록한다. 비상 예외는 **기록된 예외**여야 하고, 나중에 정식 패치로 이어지는 경로가 있어야 한다.

서명 작업은 승인된 소스 커밋과 빌드 산출물 다이제스트를 묶는 것이 좋다. 사람이 PR을 승인했지만 빌드 서버가 다른 커밋의 아티팩트를 서명하면 검토의 의미가 사라진다. 실제 서명 키가 운영 호스트에만 있다는 프로젝트 구조는 이 분리를 도울 수 있으나, 조직이 키 보관과 빌드 입력을 관리하지 않으면 자동으로 보장되지는 않는다. 에이전트에게는 서명 키가 없는 작업 환경을 주는 편이 권한 분리에 맞다.

### 5. 카나리 배포와 중지 조건

첫 적용은 작은 카나리 집합에서 시작한다. 표본은 대표성을 고려해 선택하되 가장 위험한 중요 업무부터 실험 대상으로 삼지 않는다. 운영 흐름상 특정 서비스 버전만 대상이라면 그 버전과 실제 트래픽 특성을 재현해야 한다. 성공 기준은 ‘방패 적재’ 하나가 아니라 (a) 기대 아티팩트가 적재됐고, (b) 악용 재현이 차단되고, (c) 정상 요청 오류율과 지연이 허용 범위에 있고, (d) 관측과 되돌리기가 작동하는 것이다. 네 조건 중 하나라도 빠지면 전면 확대 결정을 보류한다.

중지 조건은 절대값과 변화량을 함께 볼 수 있다. 예를 들어 정상 요청 오류율이 평소보다 급증하거나 인증·결제 같은 핵심 흐름에서 새로운 거부가 발생하면 자동 확대를 멈춘다. 구체적인 숫자는 서비스의 기준선과 사고 위험에 따라 조직이 정해야 한다. 데이터가 충분하지 않은 시점에 외부 글에서 가져온 임의의 ‘1%’를 보편적 문턱으로 적용하면 안 된다. 에이전트가 성능 요약을 작성하더라도 실제 중지 권한은 운영자가 명확히 가져야 한다.

### 6. 대상 상태의 독립 검증

배포 시스템이 ‘전송 성공’을 기록했다는 것은 대상이 방패를 실제로 로드해 계속 실행하고 있음을 뜻하지 않는다. 공식 문서의 TPM 인용 절차는 이 간극을 줄이려는 설계다. 실무 확인에는 대상 식별자, 기대할 방패 이름과 digest, 서명 인증서 집합, 측정 시각, nonce, 검증 결과가 함께 필요하다. 기대 상태를 운영자가 계산해 두지 않으면 서명된 증거를 받아도 무슨 상태가 옳은지 알 수 없다. 또 어떤 대상은 일시적으로 네트워크가 끊겨 증거를 보내지 못할 수 있다. **증거 부재**와 **보호 부재**를 구분하되 어느 쪽도 무시하지 않는다.

가용성 측면에서도 검증을 설계한다. 방패가 적용됐는데 관측 시스템이 끊겼다는 이유로 서비스에 갑자기 잘못된 정책을 적용하면 오히려 장애가 생길 수 있다. 반대로 관측이 없다고 보호 중이라고 가정하면 사고 조사에 빈 공간이 생긴다. 사전에 정한 허용 지연, 마지막 확인 시각, 재검증 주기, 고위험 자산의 격리 기준을 적용해야 한다. 프로젝트의 기술이 어떤 증거를 낼 수 있는지와 조직이 그 증거에 어떤 결정을 연결하는지는 다른 설계 단계다.

### 7. 영구 패치와 방패 종료를 하나의 변경으로 묶지 않기

임시 방패와 영구 패치는 서로 다른 코드 경로를 변경한다. 영구 패치를 배포한 뒤 방패를 즉시 제거하면 실제 패치가 모든 대상에 제대로 반영됐는지 확인할 시간이 부족할 수 있다. 반대로 방패를 무한 유지하면 새 버전에서 불필요한 차단을 하거나 성능 비용을 쌓는다. 합리적인 순서는 패치 배포 → 취약점 재현 및 정상성 재검증 → 대상별 패치 확인 → 방패 제거 승인 → 제거 상태 확인이다. 실제 시점은 서비스 특성에 따라 달라질 수 있다. 중요한 것은 **방패가 놓인 기간**과 **패치가 적용된 기간**을 구분해 기록하는 것이다.

패치가 방패와 상호작용할 가능성도 있다. 새 라이브러리 버전은 입력 경로나 함수 이름을 바꾸어 방패가 더 이상 의도한 곳에 붙지 않게 만들 수 있다. 반대로 새 코드에서 정상적인 입력 패턴이 확장되어 예전 방패가 이를 거부할 수도 있다. 따라서 ‘패치가 있으니 방패는 해롭지 않다’가 아니라 호환성 테스트를 해야 한다. 방패를 늦게 제거할 이유가 있으면 문서화하고 재검토 날짜를 정한다.

### 8. 사고 이후의 학습

사건 종료 뒤에는 방패 생성 속도만 성과로 보고하지 않는다. 최초 탐지부터 영향 자산 확인까지, 후보 작성부터 독립 테스트까지, 승인부터 실제 적용 상태 검증까지, 영구 패치 완료까지의 시간을 각각 측정한다. 어느 단계가 병목이었는지 알면 다음 사건에 필요한 자동화가 보인다. 많은 조직은 코드 생성보다 자산 목록의 불완전함, 테스트 환경 부족, 승인자의 연락 체계 때문에 느리다. AI 도구의 속도가 전체 대응 시간을 줄였는지 확인하려면 단계별 시간이 필요하다.

오탐·미탐·성능 악화도 숨기지 않고 회고한다. 실험 중 발견된 실패는 프로젝트를 부정하는 결과가 아니라 실제 위험을 사전에 발견한 성과일 수 있다. 다만 어떤 실패가 어떤 대상에서 재현됐고, 왜 배포 기준이 바뀌었는지 남겨야 같은 실수를 반복하지 않는다. 공개 위협 모델과 내부 사고 기록을 함께 갱신하면 에이전트가 다음 번에 더 나은 초안을 만들 수 있다. 여기서도 민감한 내부 데이터나 취약점 상세를 외부 모델에 무분별하게 전달하지 않는 경계가 필요하다.

## 시나리오별 의사결정: ‘방패를 쓸 것인가’보다 먼저 결정할 것

### 시나리오 A — 공개 API의 고위험 취약점, 패치 검증은 이틀 뒤

외부 공개 API가 취약한 라이브러리를 사용하고 실제 악용 패턴이 관측된다. 즉시 패치를 배포하면 업무 중단 가능성이 크다. 이때 런타임 방패 후보는 가치가 크다. 하지만 긴급하다는 이유로 넓은 입력 차단을 바로 모든 호스트에 적용해서는 안 된다. 먼저 외부 노출을 임시로 제한할 수 있는지, 특정 기능을 끌 수 있는지, 취약한 호출 경로에 정상 트래픽이 얼마나 많은지 확인한다. 그다음 실험 대상에서 악용 재현과 대표적인 정상 요청을 실행한다. 방패 후보가 공격을 막지만 정상 요청 5%를 거부한다면 단순한 ‘보안 성공’이 아니다. 어떤 고객에게 어떤 장애가 생기는지 보고 격리·우회·추가 수정 중 하나를 선택해야 한다.

이 경우 AI 에이전트는 영향 버전과 패치 diff 요약, 방패 초안, 변형 공격 입력, 정상 요청 테스트를 병렬로 제안할 수 있다. 그러나 급박한 사건일수록 제안의 출처와 검증 결과를 구분해야 한다. 인터넷의 취약점 설명이 불완전하거나 악의적으로 작성됐을 수 있고, 외부 텍스트가 에이전트에게 불필요한 네트워크 요청·키 노출을 지시할 수도 있다. 외부 자료는 데이터로 취급하고 에이전트 실행 권한을 제한한다. 공격자의 콘텐츠가 방어 절차의 지시가 되지 않게 하는 것이 AI 도구를 보안 워크플로에 넣는 최소 조건이다.

### 시나리오 B — 내부 인사시스템, 외부 도달성은 낮지만 데이터 민감도는 높음

직원 정보와 급여 데이터를 다루는 내부 시스템에 취약점이 발견됐다. 외부 인터넷에서 직접 닿지 않더라도 사내 계정 탈취나 다른 서비스 침해를 통한 측면 이동 가능성을 고려해야 한다. 다만 커널 변경을 수반하는 pre-release 런타임을 중요 인사 데이터 호스트에 급히 도입하는 것이 기존 접근 제한·서비스 설정 변경보다 더 안전한지 별도 판단이 필요하다. 제한된 인원에게만 기능을 열고, 취약한 엔드포인트를 일시 중단하고, 정식 패치를 가속하는 편이 위험이 작을 수 있다.

이 시나리오에서 중요한 지표는 방패의 기술적 세련됨이 아니라 데이터 접근 경로와 복구 가능성이다. 정상 업무가 멈추면 급여·휴가 승인 같은 법정·운영 일정이 영향받는다. 반대로 개인정보 노출 위험을 낮게 볼 수 없다. 보안팀과 제품팀이 공동으로 **공격 가능성, 데이터 민감도, 업무 중단 비용, 대체 통제의 적용 시간**을 비교해야 한다. 에이전트가 만든 방패를 쓰든 설정 기반 차단을 쓰든 최종 선택과 근거를 이슈에 남겨야 이후 감사에서 이해할 수 있다.

### 시나리오 C — 엣지 장비와 장기 업데이트 주기

현장 장비나 네트워크 어플라이언스는 영구 패치를 빠르게 적용하기 어렵다. Shirudo 저장소는 긴 업데이트 주기를 가진 임베디드·엣지 장치에 서명된 임시 완화를 제공할 가능성을 언급한다. 여기서는 중앙 데이터센터보다 오히려 배포·상태 확인·키 회수의 어려움이 크다. 장비가 오랫동안 오프라인이면 새로운 방패를 못 받거나, 오래된 방패를 유지할 수 있다. TPM이 있고 부팅 체인을 통제할 수 있는지, 장비 커널을 교체할 수 있는지, 실패 시 현장 출동 없이 복구할 수 있는지부터 확인해야 한다.

또한 장비에서 CPU·메모리 여유가 적다면 eBPF의 평균 오버헤드뿐 아니라 최악 경로를 봐야 한다. 측정과 텔레메트리 전송이 네트워크 제한 환경에서 어떻게 동작하는지도 중요하다. 공급업체의 ‘원격 실시간 보호’라는 문구가 대상 장치의 연결성과 보안 모듈을 자동으로 만들어 주지 않는다. 실제 장비 한 대에서 실습한 뒤 다수 장비의 버전 편차를 조사해야 한다.

### 시나리오 D — 같은 취약점에 여러 임시 통제가 겹침

WAF 규칙, 네트워크 ACL, 애플리케이션 feature flag, Shirudo 방패를 동시에 적용하면 방어 깊이가 생길 수 있지만 오류 원인도 모호해진다. 악용 시도가 실패한 것이 어느 통제 때문인지 확인하지 못하면 방패의 효과를 과대평가할 수 있다. 정상 요청이 실패했을 때도 각 계층의 로그가 다르면 진단이 느리다. 처음부터 모든 통제를 꺼서 공격 시험을 하라는 뜻은 아니다. 안전한 실험 환경에서 각 통제의 기여를 분리하고, 운영에서는 어떤 통제가 필수·보조인지 표시해야 한다.

정식 패치가 적용되면 통제를 하나씩 제거하면서 방어 상태를 다시 확인한다. 예를 들어 WAF 규칙만 남아 패치 검증이 실패했는데도 테스트가 통과했다고 오해할 수 있다. 반대로 방패가 계속 작동해 새 애플리케이션의 정상 기능을 막을 수 있다. 다층 방어를 운영하려면 각 층의 존재 여부와 판정 결과를 관찰할 수 있어야 한다.

### 시나리오 E — 에이전트가 코드뿐 아니라 배포까지 제안함

에이전트가 취약점 분석 뒤 ‘이 방패를 즉시 전체 서비스에 적용하자’고 제안한다. 자연어의 확신과 실제 근거를 분리해야 한다. 제안에는 영향 자산 분모, 실제 테스트한 공격 변형, 정상 요청 표본, 대상별 커널 조건, 예상 롤백 시간, 독립 검증 계획이 있어야 한다. 하나라도 비어 있다면 ‘전체 서비스 적용’은 결론이 아니라 가설이다. 에이전트에게 부족한 근거를 수집하도록 할 수 있지만 자신이 작성한 코드를 자신이 평가하고 자신이 승인하는 한 고리로 만들지 않는다.

이와 연결해 GitHub의 새 이슈 상태를 사용할 수 있다. 에이전트가 배정되면 In progress가 될 수 있지만 그 사실로 배포 권한을 부여하지 않는다. PR이 In review로 갔다면 리뷰 결과와 CI 결과를 확인한다. 실제 배포·TPM 확인은 이슈 상태가 아니라 대상 상태 기록에 넣는다. 비용 보고의 봇 `user_id`는 에이전트 사용량을 추적하는 데 도움이 되지만 누가 위험을 인수했는지까지 알려 주지는 않는다. 승인자는 별도로 기록해야 한다.

### 시나리오 F — 공격이 이미 일어난 뒤 방패를 배포함

방패는 보통 앞으로 들어올 악용을 막기 위한 통제다. 이미 침입한 시스템의 데이터 변조나 백도어를 자동으로 제거하지 않는다. Shirudo의 장기 방향에는 침해 탐지·격리·검증된 상태 복구가 언급되지만, 오늘 공개된 방패 시연을 포렌식 완료나 침해 복구의 증거로 삼으면 안 된다. 사건이 진행 중이라면 공격자의 지속성, 권한 상승, 데이터 접근 흔적을 별도로 조사해야 한다. 방패가 새 악용을 막는 동안에도 이미 악성 프로세스가 남아 있을 수 있다.

이 상황에서는 ‘방패 적재 성공’보다 ‘영향 범위 확인’, ‘비밀키 회전’, ‘깨끗한 이미지에서 재배포’, ‘사후 검증’이 더 중요한 순서가 될 수 있다. TPM이 특정 방패의 로딩 상태를 증명한다고 시스템 전체가 침해되지 않았다는 결론을 내릴 수 없다. 위협 모델의 범위를 정확히 지키는 것이 운영 판단을 보호한다.

## 기술 해설 — 서명된 로더부터 측정값까지, 한 단계씩 검증하기

공식 [작동 원리 문서](https://docs.shirudo.dev/start/how-it-works.html)는 방패 하나가 만들어져 제거되기까지의 경로를 비교적 자세히 공개한다. 이를 운영자 관점으로 다시 읽으면 ‘제품이 제공하는 기술’과 ‘조직이 채워야 할 정책’의 빈칸이 보인다. 아래 설명은 문서를 요약·해석한 것이며 실제 명령의 대체 안내가 아니다. 특히 프로젝트가 pre-release이고 커널 요구사항이 특별하므로 기존 Linux 환경에서 그대로 실행 가능한 일반 운영 절차로 읽으면 안 된다.

### 빌드 단계: 왜 BPF 객체 대신 로더에 서명하는가

보통 산출물에 서명하면 파일 바이트가 그대로 실행된다고 생각한다. 하지만 eBPF 객체는 libbpf가 적재 과정에서 맵 정보, 재배치, 커널 심볼 등을 채우면서 바뀔 수 있다. 공식 문서는 이 때문에 원본 BPF 객체 그대로의 서명만으로 커널이 최종적으로 보는 프로그램을 묶기 어렵다고 설명한다. Shirudo는 작은 `BPF_PROG_TYPE_SYSCALL` **로더 프로그램**과 그 데이터에 서명한다. 로더가 커널 내부에서 필요한 생성·적재 단계를 수행하며, 커널은 서명 확인 뒤 각 upatch 프로그램에 대한 검증도 실행한다. 이 설명은 ‘BPF 프로그램을 서명한다’라는 한 문장의 내부가 생각보다 복잡하다는 것을 보여 준다.

운영자는 여기서 한 가지 질문을 더해야 한다. 서명된 로더가 무엇을 적재하는지 **사람이 검토할 수 있는 형태로 추적**되는가. 공식 문서는 upatch의 이름, attach 메타데이터, payload digest, 패키지와 인증서의 경로를 설명한다. 리뷰 시스템에는 소스 커밋과 컴파일러·커널 BTF 입력, 최종 payload digest, 서명한 키 식별자를 함께 남기는 편이 좋다. 소스 PR 링크만 남기고 산출물 바이트를 잃으면 사고 당시 실행된 것이 검토한 것과 같은지 확인하기 어렵다.

### 패키지·레지스트리 단계: 전달 경로를 신뢰하지 않는 설계

문서는 `.bee` 패키지, OCI 레지스트리, 서명된 패키지 인덱스 또는 upatch tree를 통한 배포 경로를 설명한다. 레지스트리는 바이트를 전달할 수 있지만 그 자체를 신뢰하지 않는다는 것이 설계 취지다. 훼손·재생 공격에 대한 서명 확인의 중요성이 여기서 드러난다. 그러나 레지스트리가 위조는 못 해도 최신 패키지를 주지 않거나 아예 응답하지 않는 문제는 남는다. 공급망에서 **무결성**과 **가용성**은 다른 속성이다. 방패가 필요한 사건에서 저장소가 응답하지 않으면 빠른 완화 전략이 무력화될 수 있으므로 배포 경로의 장애 계획도 필요하다.

서명된 인덱스와 패키지가 있어도 조직이 어떤 인증서를 신뢰할지 관리해야 한다. 잘못된 신뢰 루트가 대상에 남아 있으면 오랫동안 쓸 수 있는 서명이 위험해진다. 반대로 유효한 키를 너무 일찍 제거하면 긴급 방패를 배포하지 못한다. 인증서 회전·취소와 다수 환경의 점진적 갱신은 설계 문서가 제공하는 기본 메커니즘을 넘어 조직의 운영 리듬에 맞춰야 한다. 이 문제는 AI가 코드를 생성하는 속도와 무관하다.

### 대상 로딩 단계: 커널이 허용한 것과 서비스가 사용한 것

공식 설명에서는 대상이 로더 데이터를 맵에 넣고 동결한 뒤 서명을 전달해 커널 적재를 요청한다. BPF LSM은 사용자가 임의 프로그램을 로드하려는 경로를 제한한다. 로더는 내부에서 upatch의 맵과 프로그램을 만들고, Shirudo가 프로그램을 정해진 attach 위치에 붙인다. 이 과정은 임의 BPF 실행을 막기 위한 다층 검사가 있다. 그렇지만 ‘대상에서 로드 성공’은 실제 애플리케이션이 취약 경로를 지날 때 해당 훅을 호출하는지, 훅에서 봐야 할 데이터가 존재하는지까지 자동으로 알려 주지 않는다.

프로젝트 문서의 예시처럼 프로그램이 `do_nanosleep`에 붙어 아무것도 하지 않는 테스트 upatch라면 로딩은 성공해도 보안 효과는 없다. 이는 실패가 아니라 설치 경로를 시험하기 위한 정상 예제다. 따라서 실제 방패 검증에는 로드 목록 외에 **의도한 악용 재현이 차단되는 기능 테스트**가 필요하다. 컨테이너나 여러 프로세스가 같은 호스트를 공유하면 대상 선택도 확인해야 한다. 다른 서비스의 정상 요청을 건드리는 넓은 훅이 아닌지 검토해야 한다.

### 측정 단계: 로딩 실패와 증거 불일치의 처리

문서는 아카이브한 upatch와 측정 레지스터를 연결한다. 적재 또는 측정 중 실패하면 로딩을 되돌리려 하고, 되돌리기마저 실패하면 운영자가 조정해야 할 상태를 보고한다. 이 점은 무조건적인 원자성을 약속하기보다 **부분 실패를 인식**한다는 의미다. 실제 시스템에서는 네트워크 중단, 디스크 오류, 재부팅, 프로세스 종료가 어떤 경계에서든 생길 수 있다. 운영 절차는 ‘성공 또는 실패’ 두 값만 두지 말고 `요청됨`, `서명 확인됨`, `적재됨`, `측정됨`, `독립 검증됨`, `조정 필요`처럼 상태를 세분해야 한다.

왜 `조정 필요`가 중요한가? 측정에 실패한 방패가 실제로 붙어 있거나, 반대로 기대한 방패가 사라졌다면 자동 재시도를 무작정 반복하면 상태가 더 복잡해질 수 있다. 공격을 막는 통제가 불확실한 상태라면 어떤 서비스에 추가 격리나 트래픽 제한이 필요한지 사람이 판단해야 한다. 운영 대시보드가 단순 `Error`로만 보여 주면 보안 위험과 일시적 텔레메트리 오류를 구별하지 못한다.

### 검증 단계: 대상의 자기 보고와 운영자의 기대를 비교

공식 문서는 대상의 `status` 출력과 `attest` 증거를 구분한다. 빠른 시작은 운영 호스트가 새로운 nonce를 만들고, 대상의 TPM 서명을 가진 증거를 받아, 기대한 인증서와 방패 payload로 레지스터를 예측한 뒤 비교한다. 특히 빠른 시작은 예시에서 attestation key 이름을 증거 자체에서 추출하는 것은 **어느 TPM이 서명했는지 입증하지 못한다**고 경고하고, 별도의 등록·고정 절차를 소개한다. 이 문구는 많은 보안 데모에서 빠지는 핵심이다. 서명이 수학적으로 맞아도 그 서명 키가 승인된 대상 장치의 키라는 신원 연결이 없으면 의미가 줄어든다.

검증자는 ‘대상에게 네 기대 상태가 무엇이냐’고 물어 그 답을 기대값으로 써서는 안 된다. 독립적인 배포 계획과 승인된 아티팩트 목록에서 기대값을 계산해야 한다. 대상을 믿지 않기 위해 TPM 증거를 요구하면서 비교 기준을 대상의 자기 주장에 맡기면 신뢰 경계가 다시 사라진다. 운영자의 서명 키와 승인 시스템, 대상의 TPM 및 부팅 체인을 분리하는 이유가 여기에 있다.

### 관측 단계: 로그가 많은 것과 신뢰할 수 있는 것

Shirudo 문서는 상태·맵 데이터의 OpenTelemetry 출력과 keepalive를 설명한다. 이 데이터는 경향, 성능, 오류 분석에 중요하지만 공식 문서는 텔레메트리가 TPM 증거 검증과 동일하지 않다고 명시한다. 일반 로그가 많아도 공격자가 호스트를 장악했다면 일부 기록은 조작되거나 누락될 수 있다. 반대로 TPM 인용만 있으면 어떤 요청이 차단됐는지 운영 세부를 설명하기 어렵다. **운영 관측과 독립 검증은 서로 보완**한다. 두 통로를 합쳐서 ‘몇 초 전에 어떤 대상의 어떤 방패가 기대 상태였고, 그 사이 정상 요청 오류율은 어땠는가’를 볼 수 있어야 한다.

관측 지표를 설계할 때는 오탐, 실제 공격 차단, 적용 대상 수, 아직 확인되지 않은 대상 수, 로딩 실패, 부하와 지연, 서명 검증 실패, 상태 조정 필요를 서로 다른 숫자로 둔다. ‘차단 건수’ 하나는 쉽게 오해된다. 공격자가 같은 요청을 수천 번 반복해도 새로운 방어 성능이 생긴 것은 아니다. 정상 요청을 잘못 막아도 차단 건수는 늘 수 있다. 작은 숫자보다 사건 맥락과 분모가 필요하다.

### 제거 단계: 동작 중 보호를 해제하는 권한

공식 문서는 제거 directive도 서명 경로를 통과하고 payload digest가 맞는지 확인한다고 설명한다. 이는 임의의 사용자가 보호 프로그램을 간단히 떼지 못하게 하려는 구조다. 다만 사고 대응 중에는 정당한 제거도 필요하다. 새 방패가 데이터베이스 연결을 막는다면 운영자는 빠르게 정상화를 해야 할 수 있다. 따라서 **긴급 롤백 권한**은 미리 정의하고 연습해야 한다. 사람 승인이 필요하더라도 호출 가능한 담당자가 24시간 없으면 기술적 unload 기능만으로는 충분하지 않다.

제거 후에는 취약점 위험이 다시 열리는지 확인한다. 다른 방어가 없고 패치도 적용되지 않았다면 차단 장애를 해결하는 대신 보안 위험을 받아들이는 선택이 된다. 그러한 선택이 불가피하다면 범위와 종료 시간을 기록하고, 네트워크 격리나 기능 제한 같은 대체 통제를 동시 적용한다. 롤백은 ‘원래 상태로 돌아가는 안전한 버튼’이 아니라 **위험의 종류를 다시 바꾸는 변경**이다.

## 운영 실험 설계 — 발표의 가치를 실제 환경에서 판별하는 방법

새 보안 런타임을 평가할 때 성공 기준을 제품 설명에서 역으로 만들면 유리한 시험만 선택하기 쉽다. 실험 전에 **어떤 조건에서 채택하지 않을지**까지 적는다. 다음 실험은 Shirudo의 성능을 가정한 결론이 아니라, 저장소가 제시한 기능과 전제를 평가하기 위한 방법론이다. 실제 환경에 설치하거나 공격 코드를 실행하라는 지시가 아니다.

### 실험 1: 호환성 분모 만들기

대상 서버 목록을 커널 계열, 부팅 방식, TPM 유무, 아키텍처, 배포판 업데이트 정책, 워크로드 유형으로 나눈다. 공식 요구사항은 수정된 커널·TPM·부팅 체인을 전제로 한다. 따라서 ‘우리 서버 100대 중 95대에서 운영 가능’이라는 숫자는 설치 스크립트를 돌리기 전에는 추정이다. 먼저 실질적으로 준비된 서버 수, 커널 변경이 필요한 서버 수, 기술적으로 불가능한 서버 수를 구분한다. 가상화 환경에서는 vTPM의 신뢰 모델과 재설정·마이그레이션 조건도 확인한다.

호환성은 한 번만 확인하면 끝나지 않는다. 커널 보안 업데이트나 새 배포판 버전으로 갈 때 signed-loader ABI와 커널 훅이 유지되는지 재검증해야 한다. 특정 테스트 VM에서 잘 돌아갔다는 사실은 다음 달 커널 업데이트의 호환성 보증이 아니다. 평가 일정에 정기 커널 업데이트 경로를 포함해야 운영 도구로서 의미가 있다.

### 실험 2: 기능 효과와 오탐을 별도 분모로 평가

방패 후보에 대해 알려진 악용 재현을 여러 입력 형태로 준비한다. 동시에 정상 요청은 트래픽 표본에서 개인정보를 제거해 대표성을 유지한다. 성공률 분모가 ‘공격 요청 1건’이나 ‘정상 요청 1건’이면 결과는 시연일 뿐이다. 반복 수행해 변동성도 본다. eBPF 방패가 붙기 전·후를 같은 서비스 버전과 부하로 비교하고, 다른 WAF나 ACL이 영향을 주는지 확인한다. 공격 재현이 막히면서 정상 요청도 막힌다면 원인 분석 없이 합격을 주지 않는다.

차단 위치를 확인하는 시험도 필요하다. 방패가 맞는 훅에 붙었어도 일부 서비스 인스턴스만 다른 코드 경로를 쓸 수 있다. 예를 들어 특정 요청은 캐시를 거쳐 취약 라이브러리로 가지 않고, 다른 요청만 해당 경로로 간다. 이 경우 일부 악용 재현이 실패해도 실제 취약 경로에 대한 방어가 입증되지 않는다. 시험은 **취약 경로에 도달한 것이 확인된 요청**을 포함해야 한다.

### 실험 3: 부하와 장애 조건

평균 지연이 작더라도 꼬리 지연이 중요하다. 공격 입력이 쏟아질 때의 CPU·메모리·시스템 호출 비용, 정상 트래픽이 몰릴 때의 p95/p99 지연, 로딩·제거 시의 잠깐의 불안정성을 본다. 너무 낮은 부하에서만 시험하면 장애 시간에 방패가 오히려 병목이 될 수 있다. 로그·맵 export가 끊긴 경우에도 차단 정책이 예상대로 유지되는지 확인한다. 제품이 특정 네트워크 종속성을 가진다면 레지스트리 장애, 텔레메트리 수집기 장애, DNS 장애에서 어떤 기능이 남는지도 분리해 본다.

정상적인 고부하와 공격 부하를 섞어 보는 이유는 공격자 트래픽이 방어 프로그램이 가장 비싼 분기로 들어가도록 유도할 수 있기 때문이다. 특정 긴 문자열이나 특수 인코딩을 처리할 때 비용이 급증한다면 방어가 서비스 거부 증폭기가 될 수 있다. 또한 방패가 한 요청을 거부할 때 애플리케이션이 예외를 어떻게 처리하는지 살펴야 한다. 보안 통제의 거부 결과가 반복 재시도를 일으켜 전체 서비스 부하를 올릴 수도 있다.

### 실험 4: 공급망과 승인 경로

테스트 서명 키는 누구에게 있는지, CI 산출물의 digest가 서명 직전에도 같은지, 승인되지 않은 사람이 새 방패를 배포하려 할 때 어디서 거부되는지 확인한다. 잘못된 서명, 오래된 서명, 취소된 키, 다른 대상용 아티팩트에 대한 부정 테스트가 유용하다. 이 테스트는 제품을 공격하기 위한 과시가 아니라 신뢰 경계의 가정을 확인하는 작업이다. 운영 환경의 키를 실습에 가져오지 않고 별도 테스트 키를 쓰는 것도 중요하다.

도구가 서명을 통과시켰다고 승인 체계가 자동으로 완성되지는 않는다. 어떤 PR 리뷰 결과가 어떤 서명 작업으로 이어졌는지 연결할 수 있어야 한다. 에이전트가 코드 변경과 리뷰 설명을 모두 작성했다면 독립 검토자가 실제 내용을 확인했는지 기록한다. 기록이 없으면 사고 뒤 ‘승인된 변경이었다’는 말을 검증할 방법이 없다.

### 실험 5: 상태 검증과 불일치 처리

대상이 기대 방패를 로드한 뒤 정상 인용이 통과하는지 확인한다. 다음에는 실험 환경에서 기대값이 잘못된 경우, 대상이 방패를 제거한 경우, 다른 payload를 로드한 경우, 증거가 오래된 경우를 시험한다. 어떤 상태에서 대시보드가 경고하고 자동화가 멈추는지 본다. TPM 인용 실패가 발생했을 때 서비스가 즉시 중단되어야 하는지, 격리만 할지, 재검증을 요청할지는 자산 위험에 맞게 정한다. 기술적으로 탐지 가능한 불일치를 실제 운영 결정과 연결하지 않으면 검증 기능은 저장된 로그에 불과하다.

독립 검증자의 신뢰 경로도 본다. 등록하지 않은 TPM의 증거가 실수로 통과하지 않는지, 대상 이름과 키가 뒤바뀌면 탐지되는지 확인한다. 공식 빠른 시작이 예제에서 attestation key를 증거 자체에서 가져오는 한계를 경고하는 이유가 바로 신원 고정의 필요성이다. 운영자는 재부팅, 하드웨어 교체, TPM 초기화 시 기존 신원과 새 신원을 어떻게 연결할지도 절차화해야 한다.

### 실험 6: 복구와 장기 유지

방패가 정상 요청을 막는 상황을 실험 환경에서 만들어, 탐지부터 승인된 unload, 대상 확인, 대체 통제 적용까지 시간을 잰다. 커널 업데이트 뒤 다시 부팅했을 때 이전 방패가 안전하게 복원되는지, 서명 키 회전 뒤 이미 설치한 방패를 어떻게 다루는지도 검토한다. 복구 절차가 전문가 한 명의 암묵지에 의존하면 긴급 사건에 취약하다. 문서화된 지휘 체계와 연락망, 대기 인력, 연습 기록이 필요하다.

장기 유지에서는 운영 비용을 합산해야 한다. 수정된 커널 관리, TPM 및 부팅 체인, 서명 키 운영, 보안 검토, 검증 서버, 텔레메트리, 교육, 사고 훈련의 비용이다. 이 비용이 실제 패치 지연 위험을 얼마나 줄이는지와 비교해야 한다. 모든 서비스에 상시 적용하기보다 패치 창이 긴 고가용성 자산에 한정하는 선택도 가능하다. 실험은 ‘기술이 동작한다’뿐 아니라 **어떤 자산에 투자할 가치가 있는지**를 결론으로 내야 한다.

## 에이전트 운영 설계 — 이슈 상태와 비용 식별자를 실제 통제에 연결하기

GitHub의 두 발표는 Shirudo와 직접적인 제품 통합이 없다. 그럼에도 오늘 같이 다루는 이유는 AI가 코드와 작업을 만드는 조직에서 **상태와 책임의 데이터 모델**이 중요해지기 때문이다. 사람이 읽는 이슈 보드가 편해지는 것과 기계가 그 상태를 써서 다음 행동을 결정하는 것은 위험 수준이 다르다. 아래는 GitHub가 공지한 기능을 전제로 한 응용 설계이며, GitHub가 특정 워크플로를 공식 권장한다고 주장하지 않는다.

### 이슈 상태는 선언이며, 증거는 별도 객체다

이슈 상태를 `In progress`로 바꾸는 API 호출은 간단하다. 그러나 그 상태는 코드가 만들어졌는지, 무엇을 시험했는지, 누구의 승인을 받았는지 직접 담지 않는다. 팀이 상태를 자동화의 입력으로 쓸 때는 상태에 연결할 증거를 명시해야 한다. 예를 들어 `In review`의 증거는 열린 PR과 변경 파일, 통과하거나 실패한 CI 실행, 리뷰어 할당, 위험 등급일 수 있다. `Done`의 증거는 머지 커밋과 배포 버전, 실제 사용자 확인 또는 이슈 정의에 따른 종료 조건일 수 있다. 이 중 무엇이 필요한지는 팀이 정하지만 **상태 한 글자만으로 충분하다고 가정하지 않는 것**이 공통 원칙이다.

AI 에이전트가 이슈를 읽고 새 작업을 고르는 경우 상태가 특히 중요하다. 두 에이전트가 같은 이슈를 동시에 선택하면 중복 노력뿐 아니라 서로 다른 해결책이 경쟁한다. 한 에이전트가 상태를 먼저 바꾸고 실제 작업을 시작하지 못하면 다른 에이전트가 그 이슈를 영구히 건너뛸 수 있다. 그러므로 상태를 일종의 **임대(lease)**처럼 다루는 설계를 고려할 수 있다. 담당자, 시작 시각, 마지막 활동, 만료·재배정 조건을 별도 필드나 댓글에 남긴다. GitHub가 이 임대 기능을 제공한다고 말하는 것은 아니다. 상태만으로는 해결되지 않는 운영 질문을 설명하는 것이다.

### 자동 상태 전환의 관찰 가능성

GitHub 공지의 자동 규칙은 대체로 PR과 담당자 이벤트를 출발점으로 삼는다. 이슈가 In review로 바뀌었을 때 ‘에이전트가 리뷰 요청을 했기 때문인지’, ‘draft PR이 ready로 바뀌었기 때문인지’, ‘다른 사람이 open PR을 연결했기 때문인지’ 알 수 있어야 후속 자동화를 설계하기 쉽다. 같은 상태에도 이유가 다르다. 이벤트를 표준화해 기록하면 리뷰 큐가 실제로 필요한 작업을 더 잘 걸러 낼 수 있다. 예를 들어 ready PR이지만 CI가 실패했다면 코드 리뷰보다 작성자 수정이 먼저일 수 있다. 상태가 같아도 다음 행동은 다르다.

반대로 상태 변경 자체에 과도한 자동 권한을 연결하면 위험하다. `In review`가 되면 자동으로 비밀 저장소 읽기 권한을 주거나, `Done`이 되면 바로 보안 방패를 제거한다면 누군가 이슈 상태만 바꿔 외부 작업을 발동할 수 있다. 상태 이벤트는 **검토 시작 신호**로는 유용하지만, 권한 상승이나 파괴적 변경에는 별도 승인·검증이 필요하다. 특히 GitHub 공지가 GraphQL·REST·MCP로 상태 쓰기를 지원한다고 했으므로 에이전트 토큰의 write 범위를 점검할 이유가 생긴다.

### 보드 도입에서 메트릭이 왜곡되는 방식

새 상태를 도입하면 ‘In progress 항목 수’, ‘In review 체류 시간’, ‘Done 건수’ 같은 지표를 만들기 쉽다. 하지만 자동 전환이 있으면 사람의 실제 작업 시간과 상태 체류 시간이 다를 수 있다. PR을 열어 놓고 여러 날 외부 승인을 기다리는 이슈도 In review로 보일 수 있다. 에이전트에게 일괄 배정했지만 실행을 시작하지 않은 이슈는 In progress로 보일 수 있다. 따라서 생산성 지표에 상태를 사용할 때는 이벤트 시점, 대기 사유, 권한 부족, CI 지연을 분리한다. 지표가 목표가 되면 팀은 상태를 예쁘게 보이게 관리할 유인을 갖는다. 문제는 보드가 아니라 **측정값을 업무 결과와 혼동하는 것**이다.

보안 사고에서도 같은 문제가 있다. 방패 관련 이슈가 Done이라고 해서 모든 호스트에 기대한 방패가 설치된 것은 아니다. 작업 상태와 대상 상태를 별도 표로 보여 주어야 한다. 하나는 사람·에이전트의 워크플로, 다른 하나는 시스템의 실제 상태다. 두 표의 연결 키는 승인된 아티팩트 digest와 배포 대상, 커밋 또는 변경 요청 ID가 되어야 한다. 상태를 하나의 ‘진행률’로 압축할수록 누락된 호스트가 가려질 수 있다.

### `user_id`는 비용 조인의 시작이지 비용 책임의 결론이 아니다

GitHub의 새 열은 이름 변경과 삭제 계정 문제를 줄여 준다. 그러나 비용 책임은 계정 단위와 다를 수 있다. 조직이 하나의 서비스 계정으로 여러 에이전트를 실행한다면 같은 `user_id` 아래에 다양한 제품팀의 작업이 모인다. 봇 계정 사용량을 비용 센터에 배분하려면 저장소, 워크플로 실행, 이슈 또는 작업 ID 같은 메타데이터가 필요하다. 사용자 ID와 사람 직원 ID도 다를 수 있으므로 임의로 동일시하지 않는다. 특히 외주·임시 계정, 삭제된 계정, 자동 생성 계정에서는 소속이 시간이 따라 바뀐다.

안정적인 ID는 감사에도 유용하다. 사고가 발생했을 때 특정 계정의 AI 사용량 변화와 이슈·PR 활동을 같은 기간에 볼 수 있다. 다만 **동시 발생은 인과관계가 아니다.** 사용량이 늘었다고 해당 에이전트가 문제 변경을 만들었다고 단정하지 않는다. 실제 API 호출, PR 커밋, 배포 기록, 승인 기록을 연결해야 한다. 보고서의 ID는 조인을 가능하게 하는 하나의 축이지 행위의 완전한 로그가 아니다.

### 보고서 스키마 변경을 안전하게 배포하는 절차

12월 1일 전에는 현행 포맷과 예고된 포맷을 함께 읽는 파서를 준비할 수 있다. 입력 첫 줄에서 헤더를 확인하고 필드 이름으로 매핑한다. 열이 없으면 과거 파일로 처리하되, 없는 `user_id`를 `username`으로 조용히 대체해 같은 의미라고 표기하지 않는다. 컬럼이 존재하지만 비어 있는 경우와 컬럼 자체가 없는 경우도 구분한다. 새 포맷을 받은 뒤에는 ID가 실제로 봇·삭제 계정을 어떻게 분리하는지 확인하고, 비용 합계 차이가 반올림 때문인지 다른 원인인지 대조한다. 이 회귀 시험은 작은 스크립트라도 가치가 있다. 위치 기반 CSV 파서는 잘못된 열을 정상 값처럼 소비할 위험이 있기 때문이다.

스키마 변경 공지를 보고 AI 사용량 보고서만 고치면 충분하지 않을 수 있다. GitHub는 상세 보고서와 프리미엄 요청 보고서도 해당한다고 했다. 스프레드시트 수식, 데이터 웨어하우스 적재, 월별 알림, 예산 초과 자동화, API 클라이언트가 서로 다른 위치에서 같은 파일을 읽을 수 있다. 소비자를 목록으로 만들고 테스트 샘플을 한 번씩 흘려보내야 한다. 반대로 GitHub가 요약 보고서는 바뀌지 않는다고 명시했으므로 모든 파이프라인을 무조건 변경할 필요도 없다. **영향 범위를 정확히 그리는 것**이 빠른 대응이다.

### 상태·비용·승인을 묶는 최소 이벤트 모델

아래 필드는 오늘 발표에 의해 자동 제공된다고 주장하는 것이 아니라, 조직이 자체 자동화에서 보존할 만한 최소 이벤트 모델의 예시다.

| 이벤트 | 최소 식별자 | 보존할 근거 | 빠지면 생기는 질문 |
| --- | --- | --- | --- |
| 작업 배정 | 이슈 ID, 담당 계정 ID, 시각 | 배정 주체와 작업 범위 | 누가 실제로 시작했는가? |
| PR 생성 | 이슈 ID, PR ID, 커밋 SHA | 변경 파일과 CI 결과 | 무엇이 바뀌었는가? |
| 위험 승인 | 승인자 ID, 아티팩트 digest, 시각 | 테스트·예외·배포 범위 | 무엇을 승인했는가? |
| 방패 서명 | 서명 키 식별자, digest | 승인된 소스·빌드 입력 | 검토한 것과 같은 바이트인가? |
| 대상 적용 | 대상 ID, digest, 시각 | 로드 결과·오류 | 요청만 했는가, 실제 적용했는가? |
| 독립 검증 | 대상 ID, nonce, 기대 상태 | TPM 증거·검증 결과 | 대상의 자기 보고가 아닌가? |
| 비용 집계 | 계정 `user_id`, 기간, 보고서 종류 | 원본 파일·헤더 버전 | 이름이 바뀐 계정은 어떻게 합치는가? |
| 종료 | 영구 패치 버전, 제거 상태 | 재현·정상성 재시험 | 임시 방어를 언제 끝냈는가? |

이 모델은 커널 보안 도구가 없는 일반 웹앱 배포에도 적용할 수 있다. ‘방패 서명’ 대신 컨테이너 이미지 서명이나 릴리스 승인으로 바꾸면 된다. 중요한 것은 **업무 상태의 ID, 실제 산출물의 ID, 대상 상태의 ID, 비용 계정의 ID가 서로 다른 것**을 인정하고 안전하게 연결하는 것이다. 이름이나 이슈 제목 같은 사람이 읽는 값만으로 조인하면 변경·중복·재사용에 취약하다.

## 실무 점검표 — 어느 팀이 무엇을 확인해야 하는가

다음 목록은 모든 항목을 당장 완성해야만 기술을 쓸 수 있다는 뜻이 아니다. **긴급 방어에서 빠지기 쉬운 가정을 드러내는 질문 목록**이다. 조직마다 이미 있는 WAF·패치·배포 체계가 다르므로 항목별 책임자와 우선순위는 달라진다. 확인하지 못한 항목은 ‘아니오’와 구별해 ‘미확인’으로 기록하는 편이 좋다.

### 보안·취약점 담당

1. 취약점 식별자뿐 아니라 실제 영향을 받는 코드 경로를 확인했는가.
2. 대상 서비스와 라이브러리의 정확한 버전 범위를 확보했는가.
3. 외부에서 해당 경로에 도달할 수 있는지 네트워크·인증 관점에서 확인했는가.
4. 알려진 악용 재현과 정상 입력의 경계 사례를 각각 준비했는가.
5. 임시 방어가 막지 못하는 변형 공격을 명시했는가.
6. 공격이 이미 일어난 경우 방패 배포와 포렌식을 별도 작업으로 분리했는가.
7. 방패 제거 시 남을 대체 통제와 영구 패치 일정을 정했는가.
8. 코드 생성에 사용한 외부 자료를 신뢰된 지시가 아닌 데이터로 다뤘는가.
9. 서명 키가 유출되거나 오용될 경우 취소·교체 경로가 있는가.
10. 성공 사례를 공개할 때 실험 조건을 과장하지 않는 검토자가 있는가.

### 서비스·애플리케이션 담당

1. 정상 요청의 대표 표본과 민감 업무 흐름을 식별했는가.
2. 방패가 붙는 훅과 실제 서비스 호출 경로가 만나는지 확인했는가.
3. 거부 시 애플리케이션의 예외 처리와 재시도 동작을 시험했는가.
4. 정상 요청 오탐이 사용자에게 어떤 오류로 보이는지 알고 있는가.
5. 패치 전·후의 지연과 오류율 기준선을 갖고 있는가.
6. 방패 적용·제거 순간의 연결·세션 영향도 확인했는가.
7. 정식 패치가 적용된 뒤 방패의 필요성을 재평가하는 일정이 있는가.
8. 정상 서비스에 문제가 생길 때 보안팀과 누가 최종 중지를 결정하는가.
9. 보안 통제 변경이 고객 데이터 보존·정정 절차에 영향을 주는가.
10. 방패 없이도 할 수 있는 설정·기능 제한 대안을 비교했는가.

### 플랫폼·SRE 담당

1. 대상 커널에 프로젝트가 요구하는 signed-loader ABI와 훅이 있는가.

## 자주 생길 오해 12가지 — 발표 문구를 운영 언어로 번역할 때

**1. ‘패치 없이 보호한다’는 말은 패치가 필요 없다는 뜻인가?** 아니다. Shirudo 발표는 패치 준비 중 생기는 위험 시간을 줄이려는 임시 방어를 다룬다. 영구 패치는 취약 코드를 수정하는 본래 조치다. 임시 방패는 적용 범위·후킹 지점·우회 가능성에 좌우된다. 패치가 가능해진 뒤에도 방패를 무기한 방치하면 새 버전과 충돌할 수 있다. 방패를 도입하는 이슈에는 영구 패치의 책임자와 기한을 같이 적어야 한다.

**2. ‘재시작 없이’라는 말은 인프라 도입 전체가 무중단이라는 뜻인가?** 아니다. 특정 방패 적용이 실행 중 서비스에 가능하다는 것과 프로젝트가 요구하는 커널·부팅 체인·TPM을 기존 환경에 마련하는 것은 다른 작업이다. 저장소가 pre-release와 특별한 커널 요구사항을 명시하므로 최초 도입은 상당한 인프라 변경일 수 있다. 실습에서 재시작 없이 방패를 붙였다는 결과를 전체 도입의 무중단 보증으로 확대하지 않는다.

**3. Codex가 방패를 만들었다면 사람 리뷰가 중복 작업인가?** 아니다. 생성된 코드의 기능 명세, 변형 공격, 정상 트래픽 영향, 성능, 서명 대상 바이트는 독립적인 검토 대상이다. 오히려 AI 덕분에 후보를 빨리 만들 수 있다면 검증에 시간을 더 쓸 여지가 생긴다. 사람이 모든 코드를 수작업으로 작성해야 한다는 주장이 아니라, 생성 속도와 배포 권한의 경계를 분명히 하자는 것이다.

**4. eBPF 검증기를 통과하면 기능이 안전하다는 뜻인가?** 검증기는 커널이 허용하는 프로그램 안전 규칙을 확인한다. 취약점 차단 범위, 오탐, 비즈니스 로직 정합성까지 증명하는 것은 아니다. 잘못된 거부 조건을 가진 프로그램도 기술적으로 유효할 수 있다. 서명도 작성자 권한과 무결성을 확인할 뿐 기능의 옳음을 판정하지 않는다. 여러 검증 계층을 각자의 목적에 맞게 읽어야 한다.

**5. TPM 측정값이 맞으면 서버 전체가 안전한가?** TPM 증거는 설계된 측정 범위와 신뢰 전제 안에서 기대 상태와 실제 상태를 비교하는 데 도움을 준다. 이미 이루어진 침해, 애플리케이션 데이터의 정확성, 미측정 영역의 안전을 자동으로 보증하지 않는다. 공식 위협 모델은 커널·부팅 체인·TPM·운영 호스트에 대한 가정을 적는다. 기대값을 누가 정하고 대상 키를 어떻게 고정했는지도 검증해야 한다.

**6. 오픈소스이니 곧바로 운영에 써도 되는가?** 소스와 위협 모델을 공개해 검토 가능하다는 장점이 있다. 그러나 저장소는 현재 pre-release라고 명시한다. 운영 채택은 코드 공개 여부와 별개로 호환성, 패치 유지, 대응 인력, 장애 복구, 배포 대상 위험을 평가해야 한다. 작은 실험에서 이득을 확인한 후 특정 자산으로 범위를 제한하는 결론도 합리적이다.

**7. GitHub 이슈가 In progress면 에이전트가 실제 작업 중인가?** 공지상 에이전트를 배정하면 상태가 In progress가 되는 자동 규칙이 있다. 이는 배정 이벤트이지 실행 상태의 완전한 증거가 아니다. 에이전트가 권한 오류나 외부 의존성으로 멈췄어도 상태만 남을 수 있다. 마지막 활동과 차단 사유, 작업 산출물을 함께 봐야 한다. 자동 상태를 사람의 진행 보고처럼 해석하지 않는 편이 낫다.

**8. In review면 리뷰할 준비가 완전히 끝난 것인가?** 공지에는 draft PR을 ready로 바꾸거나 open PR을 연결할 때 In review로 넘어가는 규칙이 있다. CI 통과, 리뷰어 지정, 위험 승인까지 자동 완료된다는 뜻이 아니다. 팀이 In review의 진입 조건을 더 엄격하게 쓰고 싶다면 별도 체크와 자동화 조합을 설계해야 한다. 상태가 바뀐 원인 이벤트도 함께 기록하면 후속 조치가 선명해진다.

**9. 새 repository board가 GitHub Projects를 대체하는가?** 공식 글은 저장소 saved view의 보드 레이아웃을 소개하면서 더 고급 계획 기능에는 GitHub Project를 안내한다. 두 기능이 완전히 동일하다는 주장은 없다. 기존 프로젝트의 필드, 자동화, 보고 흐름이 필요한 팀은 이전 전에 기능 차이를 확인해야 한다. 작은 저장소에는 단순 보드가 충분할 수 있고, 여러 저장소를 묶는 업무에는 기존 프로젝트가 적합할 수 있다.

**10. `user_id`가 추가되면 모든 AI 비용이 담당자에게 자동 귀속되는가?** 아니다. 계정에 연결되지 않은 사용량의 ID는 비어 있을 수 있고, 봇 계정 하나가 여러 팀의 작업을 수행할 수 있다. ID는 이름 변경·삭제 계정 문제를 줄이는 안정적인 조인 키일 뿐이다. 실제 비용 책임은 워크플로·작업·조직 맥락과 연결해야 한다. 계정 ID를 직원 ID나 승인자 ID로 자동 변환하면 오배분 위험이 있다.

**11. 새 열 때문에 보고서 합계가 달라지면 GitHub 청구 방식이 바뀐 것인가?** GitHub 공지는 금액 계산 방식은 같다고 설명한다. 삭제 계정 사용량이 새 ID로 분리되고 행별 반올림이 적용되면 합산의 소수점 끝자리가 조금 달라질 수 있다고 한다. 따라서 작은 차이를 요금 변경으로 단정하지 않는다. 반대로 큰 차이가 나면 단순 반올림 설명으로 덮지 말고 파서의 열 밀림과 기간·보고서 종류를 확인해야 한다.

**12. 오늘 세 소식이 하나의 ‘AI 보안 플랫폼’을 이룬다는 뜻인가?** 아니다. Shirudo는 OpenAI·Cisco의 오픈소스 런타임이고, GitHub의 이슈 상태와 비용 보고 변경은 별도 제품 업데이트다. 이 글은 이들을 ‘AI가 생성·진행·배포·측정하는 작업에서 증거가 어떻게 이어지는가’라는 관점으로 비교했다. 공식 통합이나 공동 로드맵이 발표됐다는 주장은 하지 않는다. 구분을 유지해야 각 소식의 적용 범위를 제대로 평가할 수 있다.

9. [GitHub Changelog RSS](https://github.blog/changelog/feed/) — 위 두 공지의 게시 시각 확인.
10. [OpenAI News 인덱스](https://openai.com/news/) — 발표 목록과 날짜 확인.

**마지막 운영 판단:** Shirudo의 인상적인 부분은 ‘AI가 방패를 썼다’는 문장 하나보다, *생성된 방어 후보를 어떤 서명·적재·측정·검증 절차로 실제 시스템 변경에 연결할 것인가*를 공개적으로 설계했다는 점이다. 동시에 공식 저장소가 pre-release와 특수 커널·TPM 요구사항, 위협 모델의 가정을 명시한 만큼 오늘의 결론은 ‘즉시 전면 배포’가 아니라 **조건부 실험과 경계 검토**다. GitHub의 새 상태와 `user_id`도 같은 교훈을 준다. 더 빠른 에이전트 업무를 원한다면 상태 표시와 비용 식별자만 늘릴 것이 아니라, 승인된 의도·실제 변경·대상 상태·비용을 각각 검증 가능한 기록으로 남겨야 한다.

## 내일 다시 확인할 세 가지 관측 질문

첫째, **Shirudo의 공개 코드와 문서가 어떤 속도로 안정화되는가.** 오늘 저장소는 pre-release라고 밝힌다. 앞으로 릴리스 태그, 지원 커널 범위, 배포판별 준비 과정, 공식 보안 권고의 배포 방식이 바뀔 수 있다. 그러므로 현재의 요구사항을 영구적인 제품 규격처럼 저장하지 말고 채택 검토 시점마다 원문을 다시 확인해야 한다. 특히 취약점 공개와 동시에 검증된 방패가 제공되는 운영 체계가 실제로 만들어지는지, 단지 장기 목표로 남는지 구분해야 한다. OpenAI가 설명한 장기 비전은 오늘 완료된 기능 목록과 같지 않다.

둘째, **GitHub 이슈 상태가 실제 에이전트 협업에서 어떤 기준으로 관리되는가.** 공개 미리보기의 자동 전환은 이슈를 분류하는 손이 많이 가는 일을 줄인다. 그러나 팀마다 In progress와 In review의 의미가 다를 수 있다. 에이전트가 이슈를 배정받고 멈춘 경우, CI가 실패한 PR이 In review인 경우, 연결된 PR이 여러 개인 경우를 실제 저장소에서 시험해 보아야 한다. 한두 건의 성공적인 데모보다, 시간이 지나 상태가 오래된 이슈를 어떻게 발견하는지가 협업 품질을 좌우한다. 상태가 자동화될수록 누가 상태를 정정할 책임이 있는지도 정해야 한다.

셋째, **12월 1일 이후 비용 보고의 스키마를 우리 시스템이 실제로 잘 읽는가.** 발표를 읽고 코드를 고친 것만으로 끝나지 않는다. 새로운 파일을 실제로 받은 뒤 헤더, 빈 ID, 삭제 계정, 봇 계정, 행별 반올림의 영향을 확인해야 한다. 파일의 날짜와 API 추출 시각을 함께 기록하면 변경 전후 포맷을 혼동할 위험이 줄어든다. AI 사용량이 비용 의사결정으로 이어지는 조직이라면 이 확인을 다음 달 청구서가 나오기 전에 끝내야 한다. 작은 CSV 열 하나가 잘못된 예산 알림이나 부서별 배분을 만들 수 있기 때문이다.

세 질문의 답은 모두 시간이 지나야 더 분명해진다. 오늘 공식 자료만으로 확인한 것은 제품 발표의 범위, 저장소의 현재 상태, 공개 미리보기 기능, 예고된 보고서 스키마다. **아직 현장에 적용해 얻은 독립 검증 결과는 이 글에 없다.** 그래서 이 글은 채택 결정을 대신하지 않고, 어떤 실험과 운영 기록이 있어야 결정을 내릴 수 있는지를 제시한다. AI 보안 자동화에서 신중함은 속도의 반대말이 아니다. 느리게 만들지 않으면서도 되돌릴 수 있고, 누가 무엇을 바꾸었는지 설명할 수 있도록 만드는 구조가 신중함의 실체다.

### 읽는 사람별 오늘의 한 가지 행동

개발자는 새 취약점 방어 코드의 **허용·거부 테스트를 함께** 작성해 둔다. ‘공격 재현이 막혔다’만으로 합격하지 않고 정상 요청이 보존되는지 확인한다. SRE는 배포 요청 건수와 **실제 적용·독립 확인된 대상 수**를 분리해 본다. 보안 담당자는 서명 키와 부팅 신뢰, 위협 모델의 미해결 영역을 검토한다. GitHub 자동화를 운영하는 팀은 이슈 상태가 업무의 증거처럼 쓰이는 지점을 찾는다. 비용 담당자는 보고서 파서를 열 이름 기반으로 바꾸고 과거·새 포맷을 함께 읽는지 시험한다. 어느 팀도 다른 팀의 검증을 대신했다고 주장하지 않는 것이 중요하다.

마지막으로 경영·제품 책임자는 한 문장을 묻는 편이 좋다. **‘우리가 더 빨라진 것은 어느 단계이며, 그 단계의 실패를 무엇으로 발견하는가?’** 코드 초안이 빨라져도 승인·배포·실제 상태 확인이 느리면 위험 시간은 줄지 않는다. 반대로 전면 배포만 빨라져 실패 발견이 늦으면 운영 위험이 커진다. 오늘의 세 소식은 AI가 만든 속도를 신뢰 가능한 결과로 바꾸기 위해 각각 다른 종류의 증거가 필요하다는 사실을 다시 보여 준다.

### 짧은 편집 주석: 숫자를 읽는 순서

이 글에서 ‘2배’ 같은 표현을 쓸 때 독자는 먼저 **무엇의 두 배인지** 확인해야 한다. 방패 생성 시간이 절반이 됐는지, 취약 상태의 호스트 수가 줄었는지, 악용 재현 성공률이 떨어졌는지, 정상 요청 오류율이 늘었는지는 모두 다른 결과다. 오늘 공식 발표에는 여러 환경에서의 일반적인 배포 성공률이나 평균 성능 개선 수치를 제시하지 않았다. 따라서 이 글도 그런 값을 만들어 비교하지 않는다. 실험 사례는 가능성을 보여 주고, 운영 수치는 별도 측정으로 얻어야 한다.

같은 원칙은 GitHub 보드와 사용량 보고에도 적용된다. 이슈가 In progress인 건수가 증가했다고 팀 생산성이 높아진 것은 아니다. 에이전트 배정 자동화 때문에 상태 분포가 달라졌을 수 있다. 사용량 보고서의 행 수가 늘었다고 청구액이 늘어난 것도 아니다. 삭제 계정이 `user_id`로 분리되면서 행 구성이 바뀔 수 있다. **분모·스키마·이벤트 원인이 바뀌면 숫자의 의미도 바뀐다.** 새 기능을 도입하기 전후의 대시보드를 비교할 때 반드시 같은 정의를 사용해야 한다.

보안 대응의 핵심 수치는 ‘언제 발표했나’가 아니라 ‘언제 내 취약 자산이 실제로 보호됐나’에 가깝다. 발표 시각, 방패 작성 시각, 서명 시각, 배포 요청 시각, 대상의 적재 시각, 독립 검증 시각은 서로 다르다. 어느 시각부터 위험이 실제로 줄었는지는 시험한 공격 경로와 대상 상태를 연결해야 판단할 수 있다. 빠른 발표를 빠른 보호로 오독하지 않는 것이 오늘 기사를 읽는 가장 중요한 습관이다.
