## 배경: 한 개의 에이전트가 여섯 개의 경계를 한꺼번에 넘는다

기존 업무 시스템에서 데이터 표, 문서 검색, 사용자 권한, 지역별 처리, 화면 응답 시간은 서로 다른 팀의 일이었다. 자연어 대화창이 이들을 한 화면으로 묶으면 사용자에게는 간편하지만 시스템의 책임은 사라지지 않는다. 오히려 같은 질문 안에서 여러 책임이 연쇄된다. ‘지난 분기 매출 감소 원인과 관련 계약 조항을 보여 줘’라는 요청은 정형 데이터의 집계와 비정형 계약서의 검색을 모두 요구한다. ‘미승인 휴가를 승인해 줘’라는 요청은 직원의 신원, 해당 조직의 결재권, 현재 결재 상태, 중복 요청 처리를 요구한다. ‘오늘의 업계 소식에 맞는 게시물을 제안해 줘’라는 요청에는 검색의 최신성과 출처 검증이 들어간다. 자연어가 하나라는 이유로 백엔드 권한이나 원천의 차이를 합칠 수 없다.

오늘 여섯 글은 이 경계를 각기 다른 위치에 둔다. Quick 예제는 **자료 결합 위치**를 Space에 둔다. OBO 예제는 **사용자 신원 변환 위치**를 Gateway와 IdP 사이에 둔다. EDB 예제는 **용어와 데이터 권한 위치**를 Postgres에 둔다. Norton 사례는 **시점이 있는 외부 근거의 획득 위치**를 Web Search에 둔다. 음성 글은 **스트리밍과 배포 위치**를 앱·네트워크·추론 엔드포인트로 나눠 보여 준다. 지역 추론 글은 **데이터 처리 위치**를 추론 프로필로 선택한다. 모두 ‘AI 에이전트’라는 이름 아래 묶이지만 제어점은 다르다.

이 구분이 중요한 이유는 실패 대응에 있다. 지표가 틀리면 데이터 정의 또는 SQL을 확인해야 한다. 옳은 데이터인데 다른 직원의 정보가 보이면 접근 제어와 신원 전달을 확인해야 한다. 검색 자료가 낡았으면 발행일·수집 시각·검색 범위를 확인해야 한다. 음성이 늦으면 모델 첫 바이트뿐 아니라 사용자 발화의 종료 판정, 네트워크, TTS 시작 시점을 재야 한다. 인도 처리 요구를 어겼다면 호출 소스 리전만 보지 말고 프로필의 목적지 리전을 확인해야 한다. 모든 문제를 ‘프롬프트를 고치자’로 환원하면 바로잡을 층을 놓친다.

## 1. Amazon Quick: 두 종류의 자료를 묶어도 진실 원천은 하나가 아니다

AWS의 첫 번째 글은 Amazon Quick에서 S3 문서를 지식베이스로 연결하고, 정형 매출 데이터를 데이터세트로 보강한 뒤 Space에 함께 넣는 과정을 단계별로 보여 준다. 사용자는 하나의 채팅 에이전트에 질문하지만, 내부에는 문서를 검색하는 경로와 데이터세트를 질의하는 경로가 있다. 원문은 데이터 계층, Space 계층, 에이전트 계층으로 아키텍처를 나눈다. 데이터 계층에서 S3 파일은 검색 인덱스로, CSV는 SPICE의 정형 데이터세트로 들어간다. Space는 두 자료를 모으는 업무 공간이며, 에이전트는 그 Space를 지식원으로 참조한다. 이 구조는 단순히 파일을 업로드해 모델에게 모두 읽으라는 구성과 다르다. [공식 글](https://aws.amazon.com/blogs/machine-learning/bring-structured-and-unstructured-data-together-with-amazon-quick/)

예제는 AnyCompany의 가상 매출 CSV와 사업 검토 PDF 등을 사용한다. 이런 샘플은 연결 경로를 이해하기에는 충분하지만 실제 회사의 회계 정의, 접근 권한, 데이터 정합성까지 검증한 결과가 아니다. 원문에서는 데이터세트의 자동 추론 타입을 확인하고 날짜·수량·금액 필드를 바로잡는다. 또한 데이터세트의 설명, 열별 설명, 사용 지침을 추가한다. 에이전트가 자연어를 SQL로 바꿀 때 ‘Sales는 할인 후 매출인지’, ‘기간 기준은 주문일인지’, ‘지역 그룹은 어떤 이름으로 묶는지’를 알아야 하기 때문이다. 입력 데이터가 같은데도 의미 정보가 다르면 다른 집계가 나온다. 집계 오류를 모델 성능 탓으로만 돌리기 전에 스키마와 정의를 확인해야 한다.

**‘두 자료를 함께 쓴다’와 ‘두 자료가 같은 결론을 말한다’는 다르다.** 예를 들어 매출 데이터세트는 10월 매출이 감소했다고 보여 주고, 사업 보고서는 그 원인을 특정 캠페인의 중단이라고 서술할 수 있다. 보고서가 9월 버전이라면 그 설명은 현재의 매출 감소를 증명하지 않는다. 정형 지표에는 계산식과 집계 기간을, 문서에는 발행일·적용 기간·소유자를 함께 붙여야 한다. 에이전트의 최종 답변에는 숫자와 설명을 분리해 인용하는 편이 좋다. ‘매출 12% 감소’는 데이터세트의 계산 결과이고, ‘캠페인 중단이 원인’은 문서의 주장일 수 있다. 상관과 인과를 같은 문장에 묶지 않는다.

### 실제 업무에 적용할 때의 데이터 계약

인사시스템에서 ‘지난 분기 팀별 이직률과 퇴사 면담의 공통 주제를 알려 줘’라는 질문을 생각해 보자. 이직률 분모가 기초 재직자 수인지 평균 재직자 수인지 명시되지 않으면 수치는 달라진다. 휴직자·계약직·전출자를 포함하는지도 정해야 한다. 면담 문서는 개별 직원을 식별할 수 있는 민감한 정보가 있으므로 단순히 같은 Space에 넣었다고 관리자 모두가 원문을 볼 수 있어서는 안 된다. 에이전트에는 집계만 보이는 역할과 문서 요약까지 볼 수 있는 역할을 분리해야 한다. 사용자에게는 어떤 기간과 부서를 물었는지 다시 표시해 모호한 범위의 조용한 확대를 막는다.

데이터 계약에는 최소한 `원천`, `갱신 시각`, `적용 기간`, `업무상 정의`, `조인 키`, `권한 범위`, `보존 기간`, `삭제 경로`를 기록한다. 문서 검색 결과에 제목만 있으면 비슷한 이름의 구 버전을 구분하기 어렵다. 데이터세트 결과에 숫자만 있으면 어떤 필터가 적용됐는지 확인하기 어렵다. 동일한 대화에서 둘을 결합할 때는 응답의 각 주장마다 출처 유형을 남긴다. ‘시스템 계산’, ‘문서 인용’, ‘모델의 추론’을 구분하면 검토자가 쉽게 오류를 찾는다. 이 필드는 Amazon Quick 실습이 자동으로 모든 업종에 제공하는 비즈니스 정의가 아니라 제품팀의 구현·운영 제안이다.

### 구축 순서와 우선순위

첫 번째 실험은 모든 회사 자료를 연결하는 것이 아니다. 하나의 지표와 하나의 문서군만 선택한다. 예를 들어 ‘월별 채용 충원율’과 ‘채용 정책’으로 시작한다. 지표 계산을 SQL로 먼저 검증하고, 문서는 승인된 버전만 넣는다. 질문 20개를 유형별로 나누어 ‘숫자만 필요한 질문’, ‘문서만 필요한 질문’, ‘둘을 함께 써야 하는 질문’, ‘권한상 답하지 말아야 하는 질문’을 분류한다. 에이전트가 어느 경로를 택했는지 기록하고, 각 유형에서 답변의 출처가 맞는지 확인한다. 이 검증에 실패하면 모델을 바꾸기 전에 데이터세트 설명과 문서 메타데이터를 살펴본다.

구독과 연결 조건도 계획의 일부다. 원문은 예제에서 데이터세트 생성에 Enterprise 구독이 필요함을 적고, S3 버킷을 같은 리전에 두며, 버킷 접근권한을 별도로 부여한다. 이 조건은 ‘클릭 몇 번이면 누구나 된다’는 식의 제품 소개에서 생략하기 쉽다. 시범 구축의 비용에는 구독, 인덱싱, 저장, 데이터 보강, 접근권한 설계, 운영자 검증 시간을 포함한다. 외부 데이터가 거의 바뀌지 않는 작은 업무라면 기존 보고서나 SQL 뷰로 충분할 수도 있다. 하나의 채팅 인터페이스가 추가하는 효용이 데이터 운영 비용보다 큰지 따로 평가한다.

## 2. OBO 토큰 교환: 에이전트는 서비스 계정이 아니라 사용자의 대리인

에이전트가 ServiceNow에 티켓을 읽거나 수정하러 가는 상황에서 호출 주체를 하나의 애플리케이션 서비스 계정으로만 남기면 문제가 생긴다. 누가 요청했는지 추적하기 어렵고, 사용자별 보기·수정 권한이 서비스 계정 권한으로 뭉개질 수 있다. AWS의 두 번째 글은 AgentCore Gateway가 Microsoft Entra ID와 OBO 토큰 교환을 수행하도록 구성하고, ServiceNow가 원래 사용자를 알아보게 하는 절차를 설명한다. 사용자는 에이전트 애플리케이션의 토큰으로 들어오고, 게이트웨이는 대상 ServiceNow API가 기대하는 audience와 scope의 토큰을 얻는다. ServiceNow는 토큰의 사용자 클레임을 기존 사용자 계정에 매핑하고 자체 권한을 적용한다. [공식 글](https://aws.amazon.com/blogs/machine-learning/servicenow-on-behalf-of-token-exchange-with-bedrock-agentcore-gateway/)

**핵심은 토큰을 그대로 전달하는 것이 아니라 목적에 맞게 교환한다는 점**이다. 에이전트용 토큰을 ServiceNow에 보내면 audience가 다를 수 있다. 반대로 ServiceNow용 장기 토큰을 에이전트에 보관하면 유출과 권한 남용의 범위가 커진다. OBO는 Entra의 위임과 동의를 거쳐 호출 대상용 토큰을 발급받는다. 원문은 AgentCore Gateway의 target에 이 교환을 설정하며, 예제로 `user_impersonation` scope를 만든다. 실제 운영에서는 그 scope가 무엇을 허용하는지 서비스 쪽 API 권한과 함께 확인해야 한다. 토큰에 사용자 이름이 들어 있다는 사실만으로 모든 테이블의 모든 행을 읽을 수 있어도 된다는 뜻이 아니다.

### 인증·인가·업무 승인 세 단계를 분리한다

1. **인증:** 토큰의 발급자, 서명, audience, 만료, 사용자 식별자를 확인한다. 호출자의 주체가 누구인지 알게 된다.
2. **인가:** 그 주체가 특정 API와 객체에 접근 가능한지 서비스와 데이터 계층이 검사한다. OBO로 사용자 신원을 보존해도 권한 정책이 넓으면 보호 효과가 제한된다.
3. **업무 승인:** 대상 사용자가 해당 시점에 해당 상태의 티켓을 승인할 수 있는지 본다. 역할이 맞아도 이미 처리된 티켓, 본인 신청, 기한이 지난 승인 건은 거절될 수 있다.

이 세 단계를 ‘사용자 토큰 하나’로 대체할 수 없다. 실제 인사시스템을 예로 들면 조직장의 휴가 승인 권한은 부서 이동과 직무 대행에 따라 변한다. Entra가 사용자의 신원을 보존하더라도 HR 서비스가 현재 결재선을 확인해야 한다. 에이전트에게는 ‘승인을 제안’하는 도구와 ‘실제 승인’ 도구를 분리할 수 있다. 실제 승인에는 사용자가 확인한 대상, 휴가 기간, 사유 범위를 보여 주고 재인증 또는 명시적 확인을 요구할 수 있다. 이 부분은 AWS 예제의 기능을 그대로 설명하는 것이 아니라 고위험 업무에 적용할 실무 제안이다.

### 구현에서 쉽게 놓치는 경계

원문은 Entra에 에이전트용 등록과 ServiceNow API 커넥터용 등록을 별도로 만들고, 대상 API의 scope와 ServiceNow의 inbound integration을 맞춘다. ServiceNow가 `preferred_username`을 사용자의 이메일 필드에 매핑하는 예를 제시한다. 그렇다면 이메일 변경, 중복 계정, 퇴사자 계정, 외부 협력사 신원은 어떻게 처리할지 검토해야 한다. 사람이 보기에는 같은 사용자인데 서로 다른 시스템의 고유 식별자가 달라 접근이 거부되거나 잘못 연결될 수 있다. 가능한 경우 불변 식별자를 사용하고, 어느 클레임이 사용자 매핑의 근거인지 문서화한다.

Gateway가 토큰을 보관·교환하는 과정과 애플리케이션의 감사 로그도 분리해 생각한다. 토큰 자체를 로그에 남기지 않는다. 대신 요청 ID, 호출 주체의 비민감 식별자, 대상 도구, 시각, 결과 상태, ServiceNow의 감사 이벤트 ID를 연결한다. 거부가 일어나면 ‘Entra 동의 없음’, ‘audience 불일치’, ‘Gateway target 오류’, ‘ServiceNow 계정 매핑 실패’, ‘업무 객체 접근 거부’를 다른 오류로 표시한다. 모두 ‘에이전트가 실패했습니다’로 합치면 운영자가 조사할 수 없다.

보안 테스트는 성공 호출 하나로 끝내지 않는다. 다른 사용자의 티켓을 조회하는 요청, 권한 취소 직후의 호출, 오래된 토큰, 다른 audience, 취소된 사용자, 동일한 승인을 두 번 시도하는 경우를 분리한다. 서비스 쪽에서 최종 거부가 작동하는지 확인한다. 프롬프트에서 ‘이 요청은 관리자만 가능’이라고 적는 것은 보조 설명이며 권한 통제가 아니다. **모델이 어떤 도구를 부르더라도 서버는 자기 정책을 다시 적용해야 한다.**

## 3. Norton Revamp: 실시간 검색을 붙여도 사실 검증은 별도의 단계

세 번째 글은 Gen Digital이 Norton Revamp라는 전문 프로필·콘텐츠 코칭 서비스에 AI-curated News Engine을 넣은 사례다. 사용자의 목표, 최근 활동, 참여 반응을 바탕으로 검색 질문을 만들고, AgentCore Web Search에서 검색 결과를 받아 순위화한 뒤 콘텐츠 제안의 근거로 쓴다. 원문은 결과에 스니펫, 출처 URL, 제목, 발행일이 포함된다고 설명한다. Amazon Nova Lite가 제안 문구를 생성하고, 고객사의 별도 AI Learning System이 관련성·최신성·출처 신뢰도를 반영해 순위를 매긴다. 검색은 MCP 호환 관리형 커넥터를 통해 사용한다. [공식 사례](https://aws.amazon.com/blogs/machine-learning/how-gen-digital-built-norton-revamps-ai-curated-news-engine-with-amazon-bedrock-agentcore-web-search/)

이 사례에서 주목할 것은 ‘웹 검색을 붙였다’보다 **검색 결과가 바로 게시물이 되는 구조가 아니라는 점**이다. 고객사는 목표 설정, 뉴스 피드, 콘텐츠 제안이라는 다른 기능에 실시간 근거를 제공하고, Analyze → Refine → Post의 코칭 흐름을 둔다. 검색 결과는 글을 쓸 소재이고, 사람의 평판을 걸고 발행할 최종 문장과는 책임 수준이 다르다. 특히 검색 스니펫은 문맥을 잘라 낸 부분이다. 제목과 발행일이 있어도 원문이 ‘계획’을 말하는지 ‘실제 출시’를 말하는지 스니펫만으로는 부족할 수 있다. 사용자의 이름으로 게시되기 전에는 원문을 열어 핵심 주장과 날짜를 확인해야 한다.

### 뉴스 엔진의 네 가지 독립 품질 축

**발견율:** 해당 분야에서 중요한 오늘의 자료를 얼마나 찾았는지. 검색된 자료가 정확해도 중요한 발표를 놓치면 뉴스 피드로서는 불완전하다. **시점 정확도:** ‘오늘’이 게시 시각인지 수정 시각인지, 사용자 지역의 날짜인지 구분해야 한다. **출처 품질:** 공식 발표, 규제 기관, 원문 보고서, 2차 해설을 나누고 서로 복제한 기사들을 독립된 근거처럼 세지 않는다. **서술 정확도:** 찾은 원문을 모델이 제안 문구로 바꾸면서 실험 결과를 전 산업의 사실처럼 확대하지 않았는지 점검한다. 네 축은 한 개의 ‘관련성 점수’로 대체할 수 없다.

우리 블로그의 AI Daily News 발행 과정에도 같은 원칙이 적용된다. 오늘 공개 검색 API가 실패했어도 공식 목록과 RSS, 원문을 확인했다. 검색 API가 막혔다고 어제의 기사를 오늘 새로 나온 것처럼 쓰지 않았고, AWS RSS의 UTC 날짜를 KST로 변환해 발행일을 표시했다. 특정 회사의 실제 제품 발표와 고객이 자신의 서비스를 설명하는 글을 구분했다. 뉴스 자동화가 신뢰를 얻으려면 기사 건수보다 **발행 기준 시각, 출처, 원문 확인 방식, 업데이트 시의 정정 경로**가 중요하다. ‘실시간’이라는 표현은 검증 생략의 근거가 아니라 오래된 자료를 피하기 위한 입력 조건이다.

### 고객 측정치를 인용할 때

원문은 팀이 2026년 3월 출시한 서비스의 개발 과정에서 AI를 사용해 기능 구현 속도를 세 배 높였다는 등 내부 성과를 소개한다. UI 코드 70%를 AI로 생성하고, 검토에 전체 시간의 20~30%가 들었다는 기술도 있다. 이는 고객 조직의 작업 방식, 산정 기준, 제품 단계에 묶인 숫자다. 다른 팀이 AgentCore Web Search를 설치하면 같은 비율이 나온다는 근거가 아니다. 특히 개발 과정에 사용한 생성형 AI와 제품 안에서 최종 사용자를 지원하는 생성형 AI를 같은 효과로 합산하면 안 된다. ‘개발이 빨라졌다’와 ‘뉴스 제안의 사실성이 향상됐다’는 서로 다른 평가다.

재현 가능한 평가를 원한다면 검색 경로에는 `검색 시각`, `질문`, `출처 URL`, `게시일`, `원문 확인 여부`, `중복 기사 묶음`, `제안 문장과 근거 문장 연결`을 기록한다. 사람은 최소한 몇 개의 중요한 주장이 실제 원문에 존재하는지, 정정된 기사를 계속 추천하는지, 사용자 목표와 무관한 흥미로운 소식을 과대 추천하는지 확인한다. 인기 지표가 높은 자료가 신뢰할 만한 자료라는 보장은 없다. 참여 반응을 무조건 피드백으로 쓰면 클릭을 부르는 과장된 제목이 상위에 남는 역효과가 날 수 있다.

## 4. EDB Postgres AI: 의미 계층을 프롬프트 바깥의 데이터 계약으로

네 번째 글은 EDB Postgres AI의 AIDB와 Amazon Bedrock AgentCore를 묶어 고객 360 질문을 처리하는 예제다. Postgres의 테이블·뷰·열에 `COMMENT ON`으로 비즈니스 의미를 남기고, 외래 키를 조인 경로의 근거로 삼으며, 업무 용어 별칭을 만든다. AIDB의 Semantic Knowledge Base(SemKB)는 스키마 정의를 인덱싱하고 MCP 엔드포인트를 통해 도구 목록과 질의 기능을 노출한다. AgentCore Gateway가 외부 에이전트와 이 엔드포인트를 연결한다. 포인트는 ‘에이전트가 SQL을 잘 쓴다’라는 추상적인 주장보다 **모델에 제공할 의미와 실행 가능한 데이터 범위를 어디에서 관리하는가**다. [공식 글](https://aws.amazon.com/blogs/machine-learning/build-a-semantic-layer-for-agentic-ai-with-edb-postgres-ai-and-amazon-bedrock-agentcore/)

원문의 고객 데이터 예제에는 `customers`, `locations`, `products`, `purchases`와 `big_spender` 뷰가 있다. 고객의 주(state)는 고객 행이 아니라 연결된 위치 테이블에 있다. 구매 테이블의 `price`는 개당 가격이 아니라 주문 총액이다. 에이전트가 이를 단가로 오해해 수량을 곱하면 원문 예제의 최상위 고객 합계는 **27,991.66달러가 아니라 502,529달러**로 잘못 나온다. 수치의 차이는 모델이 산술을 못 해서가 아니라 **열 이름의 의미를 잘못 읽었기 때문**이다. ‘big spender’도 조직이 정한 업무 용어이며 뷰로 정의한다. 비즈니스 정의를 매 프롬프트에 복사하면 팀별로 표현이 어긋나기 쉽다. 데이터와 가까운 곳에서 정의를 관리하는 장점이 있다.

그러나 주석은 만능이 아니다. `purchases.price`가 주문 총액이라는 주석이 있어도 데이터 적재 과정에서 환불 행과 세금이 섞이면 ‘총매출’ 계산은 다시 정의해야 한다. 외래 키가 있어도 이력 테이블에서 특정 날짜의 소속 부서를 찾아야 하는 경우에는 단순 조인만으로 현재와 과거를 구분하지 못한다. 업무 의미는 주석 한 줄뿐 아니라 계산 규칙, 적용일, 예외, 검증 쿼리를 포함한다. `COMMENT`는 에이전트에게 중요한 힌트를 주지만 데이터 거버넌스의 종착점이 아니다.

### 데이터베이스 권한을 프롬프트보다 먼저 적용한다

원문은 역할별 `GRANT`, 열 단위 권한, 행 수준 보안(RLS)을 사용해 같은 질문도 사용자 역할에 따라 다른 결과가 나오는 구성을 다룬다. 이 접근은 ‘직원의 주민번호를 보여 주지 마’라는 프롬프트보다 강한 경계가 된다. 모델이 금지된 SQL을 만들더라도 DB 역할에 권한이 없으면 데이터 자체가 반환되지 않는다. 물론 DB 계정을 잘못 매핑하거나 단일 고권한 계정으로 모든 사용자를 연결하면 이 이점이 사라진다. 도구를 제공하는 대상 서비스의 자격증명은 AgentCore Identity에 보관하고, 에이전트 코드에 직접 노출하지 않는 구조도 원문에 있다. 이때 Gateway에서 어떤 사용자의 요청이 어떤 DB 역할로 연결되는지 실제 구현을 확인해야 한다. Gateway의 사용자 인증과 Postgres 역할별 데이터 권한은 서로 다른 단계다.

인사시스템에서는 `employee` 테이블에 주민번호, 개인 연락처, 급여, 소속이 한꺼번에 있을 수 있다. 에이전트 전용 역할에 테이블 전체 `SELECT`를 주고 프롬프트로 개인 정보를 숨기려 해서는 안 된다. 업무별 뷰를 별도 생성하고, 분석 업무에는 집계 결과만 노출할 수 있다. HR 담당자는 팀 단위 보고서, 직원 본인은 자기 자료, 결재자는 승인에 필요한 최소 필드만 보도록 나눈다. 행 수준 정책을 적용해도 작은 집단의 집계에서 개인이 드러날 수 있으므로 최소 집계 인원과 결과 반올림 등 공개 규칙을 함께 고려한다. 이 인사시스템 설계는 공식 예제가 아닌 실무 적용안이다.

### 관측성은 ‘답변’을 넘어 쿼리까지 이어져야 한다

원문은 AgentCore의 도구·모델 호출 추적과 AIDB의 SQL 실행 OpenTelemetry 추적을 서로 다른 계층에 둔다. 에이전트가 ‘매출 상위 고객’을 묻고 결과를 잘못 요약했을 때, 도구 호출은 맞았는지, SQL 필터는 맞았는지, 반환 행이 맞았는지, 자연어 요약만 틀렸는지를 분리해야 한다. 요청 ID로 에이전트 추적과 DB 실행 추적을 연결할 수 있어야 한다. SQL 원문이나 결과 행에 민감 정보가 들어갈 수 있으므로 로그 보존과 열람 권한도 데이터 자체와 비슷한 수준으로 관리한다. 많은 로그를 모으는 것만으로 관측성이 좋아지지 않는다. **어떤 질문이 어떤 의미 정의와 역할로 실행됐는가**를 복원할 수 있어야 한다.

평가 세트에는 정답 쿼리가 명확한 단순 질문뿐 아니라 애매한 업무 용어, 조인 경로가 둘 이상인 질문, 권한 밖의 개인 정보 요청, 정책상 답변을 보류해야 하는 질문을 넣는다. 결과가 맞는 숫자라도 허용되지 않은 행을 읽어 계산했다면 실패다. 반대로 DB가 접근을 거부했는데 모델이 그럴듯한 숫자를 꾸며 답하면 거부 처리 실패다. 자동 평가에서는 `SQL 실행 성공률`, `업무 정답률`, `권한 위반 0건`, `근거 표시율`, `미답변의 정당성`을 별도로 기록한다. 하나의 평균 점수에 섞으면 안전 경계의 작은 오류를 놓친다.

## 5. 음성 AI: 첫 오디오 바이트와 전체 대화 시간은 다른 지표

다섯 번째 글은 AWS 파트너 Cartesia가 상태 공간 모델(SSM)을 기반으로 Sonic 음성 합성과 Ink 음성 인식을 제공하고, 이를 AWS 인프라에서 활용하는 경로를 설명한다. Sonic은 텍스트가 모두 완성되기 전에도 오디오를 스트리밍할 수 있으며, 글은 첫 오디오 바이트 약 90ms, 44개 이상 언어, 10초 분량 음성으로 복제 가능하다는 공급자 측 수치를 소개한다. Ink는 실시간 전사와 발화 종료 판정을 다룬다. AWS Marketplace의 SageMaker AI 모델 패키지로 **Sonic을 고객 계정의 VPC 안에 배포**하는 경로와 자체 EC2 GPU 운영 경로가 제시된다. 반면 원문은 **Ink가 현재 Cartesia API 경로**라고 구분한다. 따라서 ‘두 모델이 모두 우리 VPC에서 돈다’는 식으로 합치면 틀리다. [공식 글](https://aws.amazon.com/blogs/machine-learning/building-ultra-low-latency-voice-ai-applications-on-aws/)

상태 공간 모델은 긴 시퀀스를 일정한 상태로 처리하는 특성 때문에 스트리밍 음성에 적합하다는 것이 원문의 설명이다. 그러나 특정 아키텍처의 이론적 성질만으로 실제 서비스의 응답 시간을 예측할 수 없다. 음성 제품의 지연에는 마이크 입력 버퍼, 네트워크 전송, 음성 활동 감지, 발화 종료 판정, 전사 결과, LLM의 첫 토큰, TTS 첫 바이트, 재생 버퍼가 모두 들어간다. 첫 바이트가 90ms라 해도 그것이 사용자의 발화가 끝난 순간부터인지, TTS 요청을 받은 순간부터인지 분모를 확인해야 한다. 사용자는 전체 턴의 침묵 시간을 느낀다. 따라서 공급자 비교표에서는 `TTFB`와 `사용자 발화 종료→첫 음성`, `사용자 발화 종료→답변 완료`를 분리한다.

### 실시간 대화의 운영 예산

대화형 상담 앱을 만든다면 지연 예산을 구간별로 배분한다. 먼저 발화 종료 판정이 너무 느리면 모델 교체보다 endpointing 조정이 효과적일 수 있다. 부분 전사를 LLM에 선제 전달하면 속도는 빨라질 수 있지만, 사용자가 문장을 뒤집거나 정정했을 때 잘못된 의도를 실행할 위험이 있다. 따라서 ‘초안 생각’에는 부분 전사를 쓸 수 있어도 결제·계정 변경·휴가 승인 같은 도구 호출은 최종 발화와 확인을 기다려야 한다. TTS가 스트리밍을 시작한 뒤 답변 내용이 바뀌면 이미 재생된 음성을 되돌릴 수 없다. 음성 인터페이스의 확인 단계는 시각 UI보다 더 명확해야 한다.

동시성도 살핀다. TTS 모델 하나가 빠르더라도 다수 동시 통화에서 GPU 큐가 길어지면 전체 응답은 느려진다. p50만 보면 바쁜 시간의 p95·p99가 숨는다. 음성 합성의 품질은 언어별 발음, 숫자·날짜·고유명사, 끊어 읽기, 길게 말할 때의 안정성으로 검증한다. 인사시스템의 ‘11월 4일’과 ‘11월 14일’이 구분되지 않으면 민감한 일정 업무에서 오류를 낳는다. 복제 음성은 편의 기능일 수 있지만 누구의 동의로 만들었고 어떤 서비스에서 사용할 수 있는지 별도 정책이 필요하다. 이 항목들은 AWS 글의 성능 수치가 자동으로 보증하는 것이 아니라 실제 제품이 따로 관리할 운영 기준이다.

배포 선택은 ‘관리형이 편하다’와 ‘자체 호스팅이 안전하다’ 중 하나의 구호로 끝나지 않는다. SageMaker 모델 패키지는 구독, 리전별 ARN, 지원 GPU 인스턴스, 엔드포인트 가동 비용을 확인해야 한다. EC2·ECS·EKS 자체 운영은 이미지 배포, GPU 자원, 스케일링, 업데이트, 장애 복구를 팀이 책임진다. Cartesia API 사용은 운영 부담이 줄 수 있지만 데이터 경로·계약·네트워크 지연을 다시 확인해야 한다. 음성 데이터가 외부로 나가는지 여부는 **Sonic과 Ink 각각** 분리해 판단한다. 원문이 설명하는 호스팅 경로가 모델 전부에 자동 적용된다고 가정하지 않는다.

## 6. Kimi K3 인도 추론: 호출 리전과 처리 리전의 구분

여섯 번째 글은 Amazon Bedrock에서 Kimi K3를 호출할 때 글로벌 추론 프로필과 인도 지역 추론 프로필을 선택하는 방법을 다룬다. AWS는 `global.moonshotai.kimi-k3`를 일반적인 범위의 선택지로, `in.moonshotai.kimi-k3`를 **뭄바이와 하이데라바드 지역 내 추론 처리**가 필요한 경우의 선택지로 소개한다. 클라이언트가 요청을 보내는 source Region과 실제 추론이 처리될 수 있는 destination Region은 다르다. 프로필이 목적지 후보를 제어한다. AWS 문서는 리전 간 전송이 AWS 네트워크를 사용하고 전송 중 암호화된다고 설명한다. 이 설명은 공개 인터넷을 경유하지 않는다는 네트워크 특성이지 모든 로그·저장·운영 데이터의 거주성 요건을 자동 충족한다는 포괄적 인증이 아니다. [공식 글](https://aws.amazon.com/blogs/machine-learning/introducing-india-based-inference-for-kimi-k3-on-amazon-bedrock/)

지역 선택의 실무 핵심은 이름이 아니라 실제 정책이다. 소스 리전을 뭄바이로 정해도 글로벌 프로필이면 처리 목적지 범위가 넓을 수 있다. 반대로 인도 프로필을 선택했어도 애플리케이션이 입력 이미지를 다른 리전의 S3에 저장하거나 운영 로그에 원문을 남긴다면 전체 워크플로의 지역 요건은 충족하지 못한다. IAM과 서비스 제어 정책(SCP)에서 소스와 대상 리전을 허용해야 하며, 조직 정책이 필요한 호출을 막는지도 확인한다. 원문은 예제 IAM 정책에서 인도 두 리전의 모델 ARN과 인도 추론 프로필을 함께 고려한다. 실제 가용 리전과 목적지 목록은 모델 카드의 최신 정보를 다시 확인하라고 안내한다.

원문은 합성 힌디어 전기요금 청구서를 이미지로 보내 OCR, 정형 필드 추출, 영어 요약, 힌글리시 후속 질문을 처리하는 예제를 제공한다. 샘플은 실제 고객 문서가 아니라 가상의 이름·주소를 쓰는 합성 자료다. 모델이 한 장의 선명한 청구서에서 금액과 납기일을 읽었다고 해서 모든 인도 언어·필체·스캔 품질의 문서에서 정확하다는 뜻은 아니다. 작은 글자를 읽기 위해 이미지 detail을 높이면 입력 토큰 비용이 늘 수 있다. 날짜 형식, 데바나가리 숫자, 금액 소수점, 로마자 음역은 오류 유형이 다르므로 필드별로 평가해야 한다. 개인정보가 들어간 KYC 문서라면 자동 추출 결과를 확정 기록으로 쓰기 전에 정형 검증 또는 사람 검토가 필요하다.

### 고객 성과와 모델 선택을 혼동하지 않는다

Ultrahuman의 인용은 Ring과 포도당 자료를 바탕으로 대답하는 Jade 서비스가 하루 1만 4천 건 이상 대화를 처리하고, Kimi K3를 Bedrock API로 연결했으며, 프롬프트 캐싱으로 비용 80% 절감과 다중 턴 대화 속도 85% 향상을 경험했다고 말한다. 이 숫자는 고객 서비스 구성과 캐싱 전략의 결과다. Kimi K3 모델을 선택하기만 하면 어느 앱에서나 비용이 80% 줄거나 85% 빨라진다는 보장이 아니다. 비교 대상 모델, 프롬프트 길이, 캐시 적중률, 평균 턴 수, 사용자 분포를 모르면 타 서비스의 예산에 그대로 적용할 수 없다. 또한 이 고객 인용의 ‘Mumbai fallback’은 서비스의 특정 경로에 관한 설명이므로 모든 데이터가 언제나 동일 리전에서만 처리되었다는 일반 명제로 바꾸지 않는다.

한국 서비스에 적용할 때도 ‘인도 프로필이 있으니 한국 프로필도 있다’고 추론하면 안 된다. 국가별 제공 프로필과 규제 조건은 각각 확인해야 한다. 데이터 거주성 검토 문서에는 `입력 저장 위치`, `모델 처리 목적지`, `출력 저장 위치`, `로그와 추적 위치`, `백업·재해복구 지역`, `서브프로세서`, `삭제 요청 처리`, `테스트 자료의 민감도`를 각각 적는다. 모델 API의 한 필드는 이 전체 문서를 대신하지 않는다. 리전 정책이 중요하다면 실제 운영 계정에서 호출 기록과 허용 정책을 대조하고, 구성 변경 시 재검증해야 한다.

## 여섯 흐름을 하나의 제품에 적용할 때: 인사시스템 사례

다음은 오늘 여섯 글을 하나의 HR 제품에 억지로 모두 설치하자는 제안이 아니다. 각각이 해결하는 책임을 제품 설계 질문으로 바꾸는 사고 실험이다. 사용자는 ‘올해 채용 속도와 신규 입사자 의견을 요약하고, 이번 주 예정된 온보딩 문의에 음성으로 답해 줘’라고 요청한다. 이 문장에는 정형 지표, 문서, 권한, 최신 일정, 음성 지연, 지역 정책이 섞여 있다. 제품은 질문을 한 번에 대답하는 능력보다 **각 부분의 근거와 허용 범위를 분리하는 능력**이 필요하다.

첫째, 정형 채용 지표는 인사 원장과 계산 정의에서 가져온다. ‘채용 속도’가 공고일에서 제안 수락일까지인지, 입사일까지인지 정한다. 문서형 입사자 의견은 개인정보가 제거된 요약 가능 자료만 검색한다. 둘을 한 문장으로 섞기 전에 기간·조직·표본을 맞춘다. 자료가 다른 시점이라면 ‘수치와 의견의 기간이 다르다’고 알려 준다. Quick 예제의 Space는 이런 결합의 UI·자료 연결 아이디어를 주지만 조직의 데이터 정의까지 대신하지 않는다.

둘째, 팀장의 승인·조회 권한은 로그인 여부와 별개다. 에이전트가 일정 데이터를 가져오거나 온보딩 요청을 생성하려면 사용자의 신원이 대상 서비스에도 전달되어야 한다. OBO는 한 방법이다. 그러나 서비스는 현재 팀 소속, 위임 상태, 요청 객체의 소유권을 검사한다. 취소된 권한이나 결재선 변경도 반영해야 한다. 사용자에게 보이는 답변의 접근 권한과 실제 도구가 호출할 수 있는 범위가 일치해야 한다. ‘일정은 알려 주지만 타인의 민감한 메모는 숨김’ 같은 정책을 프롬프트 문장만으로 구현하지 않는다.

셋째, ‘이번 주’는 기준 시각과 시간대를 가져야 한다. 시스템에 저장된 온보딩 일정은 그 시스템을 진실 원천으로 사용한다. 외부 사이트의 최신 정보를 묻는다면 검색을 쓰되 URL과 발행일을 함께 확인한다. 외부 콘텐츠는 조직 정책의 대체가 아니다. 최신 웹 기사에서 법령 변화를 보았더라도 실제 HR 업무 규정이 확정되었는지 별도의 승인 원천을 확인해야 한다. Norton 사례의 검색과 순위화 아이디어를 가져오더라도 사람의 업무 정책과 혼동하지 않는다.

넷째, 자연어→SQL 경로에는 업무 용어 정의와 DB 역할을 붙인다. ‘신규 입사자’가 재입사자를 포함하는지, 채용 취소를 제외하는지 정의한다. 권한 밖의 개인 행을 조회하지 못하게 DB 뷰·RLS를 둔다. 숫자가 틀리면 어떤 SQL과 어떤 정의를 썼는지 복원할 수 있게 한다. EDB 글이 강조하는 의미 계층의 가치는 이 복원 가능성에 있다. 단순히 모델이 테이블을 읽을 수 있게 하는 것이 목적이 아니다.

다섯째, 음성 응답은 질문을 이해한 뒤 첫 소리가 들리는 시간과 전체 답변의 완성 시간을 나눠 측정한다. 사용자가 발화를 끝내기 전부터 가능한 요약을 준비할 수는 있지만, 실제 권한이 있는 도구 실행은 확정된 요청을 기다린다. 사용자가 ‘휴가 승인해’라고 말한 뒤 다른 문장을 덧붙일 수 있기 때문이다. 음성으로 읽는 개인정보의 범위도 화면보다 신중히 정한다. 주변 사람이 들을 수 있는 환경에서는 민감 정보의 음성 낭독을 제한하거나 이어폰·확인 단계를 요구할 수 있다.

여섯째, 민감한 직원 정보가 어느 지역에서 저장·처리되는지 문서화한다. 모델 호출의 source Region만 보고 끝내지 않는다. 추론 목적지, 파일 저장, 검색 인덱스, 로그와 백업을 확인한다. Kimi K3의 인도 프로필은 지역 옵션의 한 사례다. 우리 제품의 한국·다국가 정책을 자동으로 해결하는 기능은 아니다. 데이터 위치를 명확히 할 수 없다면 고위험 자료의 모델 입력을 중단하거나 비식별 샘플로 범위를 줄인다.

## 개발자에게 의미: 기능 결합의 경계가 새로운 API 설계다

### 1) 질문 하나를 작업 계획으로 쪼개는 기준

에이전트의 계획은 실행할 도구 나열보다 **결과를 검증할 수 있는 단위**로 쪼개야 한다. 정형 집계는 계산식과 필터가 검증 단위다. 문서 인용은 원문 위치와 적용일이 검증 단위다. 외부 검색은 URL·발행일·주장 일치 여부가 검증 단위다. API 행동은 사용자·객체·현재 상태·승인 내역이 검증 단위다. 음성은 구간별 시간과 전사 정확도가 검증 단위다. 지역 정책은 리전별 데이터 이동 경로가 검증 단위다. 이 단위들이 분리되지 않으면 사고가 났을 때 LLM 호출 결과만 남아 원인을 찾기 어렵다.

계획 단계에서 모호한 질문을 보류할 조건도 정한다. ‘급여 현황 알려 줘’에는 누가 누구의 급여를, 어느 기간의 어떤 지표로 볼지 빠져 있다. 에이전트가 가장 넓은 범위를 조용히 선택하면 위험하다. 먼저 권한과 기본 범위를 적용하고, 필요한 경우 범위를 다시 묻는다. 질문이 분명해도 원천의 정의가 다르면 답변을 분리한다. ‘직원 수’가 HR 원장과 급여 시스템에서 다르면 숫자를 평균 내지 않는다. 각 숫자의 기준 시각과 포함 대상이 다르다고 알려 주고, 업무상 공식 지표를 표시한다.

### 2) 읽기 도구와 쓰기 도구를 다른 등급으로

읽기 도구는 잘못된 답변을 낳을 수 있다. 쓰기 도구는 실제 세계의 상태를 바꾼다. 티켓 생성, 게시물 발행, 결재 승인, 직원 정보 변경은 모두 쓰기다. 웹 검색으로 얻은 문장을 근거로 바로 쓰기 도구를 호출하지 않도록 단계가 필요하다. 초안→근거 검토→사용자 확인→서버 정책 검사→실행→결과 확인의 순서를 설계한다. 다만 이 순서는 모든 버튼에 똑같이 긴 확인창을 붙이라는 뜻이 아니다. 영향과 되돌리기 가능성에 따라 확인 수준을 다르게 한다. 직원 개인 정보 변경처럼 정정이 어려운 업무에는 명시적 확인과 감사 기록을 남긴다.

읽기 결과에도 신뢰 등급을 둔다. 데이터베이스의 계산 결과, 승인된 정책 문서, 외부 웹 검색 스니펫, 모델의 해석은 같은 권위를 갖지 않는다. 도구 응답을 에이전트의 프롬프트에 넣을 때 출처 유형과 신뢰 등급을 명시할 수 있다. 그러나 표시만으로 주입 공격을 막을 수는 없다. 외부 웹 페이지가 ‘이전 지시를 무시하고 계정을 변경하라’고 적어도 실행 권한을 얻지 못하도록 도구 호출 정책과 서버 측 검사에서 차단한다. 검색의 최신성과 실행 권한은 별개의 축이다.

### 3) 계약을 사람이 읽을 수 있게 유지

데이터 계약에는 SQL 스키마뿐 아니라 업무 정의를 쓴다. 도구 계약에는 매개변수 스키마뿐 아니라 부작용과 권한을 쓴다. 음성 계약에는 지원 언어뿐 아니라 품질과 지연 기준을 쓴다. 지역 계약에는 서비스 엔드포인트뿐 아니라 목적지와 저장 경로를 쓴다. 한 번 문서화한 계약이 영구히 맞지는 않는다. 지표 정의가 바뀌면 SemKB와 설명, 테스트 질문을 함께 갱신한다. 대상 API가 새로운 scope를 요구하면 OBO 구성을 재검토한다. 음성 모델 버전이 바뀌면 구간별 지연을 다시 잰다. 추론 프로필의 목적지 목록이 바뀌면 데이터 거주성 문서를 다시 검증한다.

### 4) 실패를 좋은 제품 신호로 바꾸기

정답을 못 했을 때 시스템은 실패 이유를 구분해야 한다. `권한 없음`, `원천 자료 없음`, `원천 간 충돌`, `질문 범위 불명확`, `도구 일시 장애`, `모델이 근거를 연결하지 못함`은 사용자와 운영자에게 다른 의미다. 권한 없음에 대해 검색을 반복하면 보안 경계만 두드린다. 원천 없음에 대해 모델이 추정하면 환각이 된다. 자료 충돌을 조용히 한쪽으로 선택하면 신뢰가 손상된다. 구간별 지연이 길 때도 검색, DB, LLM, TTS 중 어느 단계인지 알아야 한다. 실패 분류가 있으면 해당 층의 소유자가 고칠 수 있다.

## 운영 포인트: 릴리스 전에 필요한 검증표

### A. 정형·비정형 결합

- **정의:** 지표의 분모·분자·시간대·기간·제외 항목을 기록한다. 정책 문서에는 시행일과 폐기일을 붙인다.
- **원천:** 숫자는 계산 가능한 데이터셋에서, 서술은 검증된 문서에서 가져온다. 한쪽을 다른 쪽의 증명처럼 쓰지 않는다.
- **권한:** Space나 지식베이스를 만들 때 자료별로 읽기 범위를 설정한다. 원본이 민감하면 검색 인덱스도 민감하다.
- **갱신:** 데이터셋과 문서의 갱신 주기가 다르면 응답에 각 기준일을 표시한다. 삭제·수정된 문서가 검색에 얼마나 오래 남는지 시험한다.
- **평가:** 숫자만·문서만·결합·거절 질문을 따로 시험하고, 어떤 원천을 인용했는지 확인한다.

### B. 사용자 대신 API 호출

- **신원:** IdP의 사용자 식별자와 대상 서비스 사용자 계정의 매핑 규칙을 고정한다. 이메일 변경과 퇴사·재입사 사례를 시험한다.
- **토큰:** issuer·audience·scope·만료를 검사한다. 토큰 원문은 로그에 넣지 않는다.
- **권한:** 대상 API가 현재 사용자와 객체별 권한을 재검사한다. 프롬프트의 역할 설명은 보안 통제가 아니다.
- **동의:** 대리 호출의 범위와 취소 경로를 이해할 수 있게 한다. 쓰기 동작에는 별도 확인과 중복 방지를 둔다.
- **감사:** 사용자 요청부터 Gateway 교환, 도구 호출, 대상 서비스의 상태 변경까지 요청 ID로 연결한다.

### C. 실시간 웹 검색과 콘텐츠 생성

- **시점:** 검색 시각과 기사 발행 시각을 분리한다. UTC 날짜를 현지 날짜로 바꾸되 원문의 원래 날짜를 숨기지 않는다.
- **원문:** 스니펫의 요약을 원문 주장으로 확정하지 않는다. 제품 출시·시험·계획의 표현을 구별한다.
- **출처:** 공식 자료와 2차 해설을 구분하고, 복제 기사를 여러 독립 근거로 세지 않는다.
- **생성:** 기사 내용과 의견을 구분한다. 사용자 이름으로 게시될 글은 사용자가 확인할 수 있게 한다.
- **정정:** 원문이 수정·철회되면 이전 추천과 초안이 어떻게 갱신되는지 확인한다.

### D. 의미 계층과 데이터베이스

- **스키마:** 열 이름만 보고 뜻을 추정하지 않는다. 금액의 단가·총액, 시간의 UTC·현지, 상태의 현재·이력 구분을 명시한다.
- **업무 용어:** 집계 정의를 뷰·검증 쿼리·설명으로 함께 관리한다. 단순 주석 하나에 모든 예외를 우겨 넣지 않는다.
- **접근:** 에이전트 역할에 최소 권한을 주고, 열·행 수준 거부 시험을 수행한다.
- **실행:** 읽기 전용 경로, 쿼리 시간 제한, 행 수 제한을 두고 비싼 조인을 추적한다.
- **추적:** 질문·도구·SQL·결과·답변을 요청 ID로 연결하되 민감 데이터는 로그에서 최소화한다.

### E. 음성 응답

- **지연:** 사용자 발화 종료→전사 확정→LLM 첫 토큰→TTS 첫 바이트→재생 시작→완료를 각각 잰다.
- **품질:** 언어별 이름, 금액, 날짜, 부정문, 정정 발화, 침묵, 겹쳐 말하기를 평가한다.
- **동시성:** p50과 p95·p99를 함께 보고 GPU·네트워크 큐를 분리한다.
- **실행:** 부분 전사를 쓰기 동작의 확정 근거로 바로 사용하지 않는다.
- **데이터:** Sonic 자체 호스팅과 Ink API 경로의 처리 위치·계약을 별도로 확인한다.

### F. 지역 추론과 문서 처리

- **리전:** 호출하는 source와 실제 처리 가능한 destination을 모델 프로필 기준으로 확인한다.
- **주변 저장:** 입력 파일, 검색 인덱스, 출력, 캐시, 로그, 백업의 지역을 따로 적는다.
- **정책:** IAM·SCP가 필요한 리전만 허용하는지 실제 호출로 시험한다.
- **정확도:** 합성 데모가 아닌 실제 문서 유형별 필드 정확도와 수동 검토율을 측정한다.
- **비용:** 이미지 detail, 캐시 적중률, 서비스 티어, 실패 재시도를 포함해 성공한 문서 한 건당 비용을 계산한다.

## 제품팀의 첫 2주 실험안: 작은 질문에서 신뢰 경계까지

**1~2일차에는 질문과 원천을 고정한다.** 공개 자료 또는 비식별 샘플로 하나의 업무 질문을 선택한다. 예를 들어 ‘월간 채용 소요 기간을 계산하고 해당 기간의 채용 정책 변경 사항을 인용해 달라’고 한다. 원천 데이터의 필드, 정책 문서 버전, 담당자, 접근 권한을 적는다. 정답 기준을 먼저 만들고 모델과의 대화를 나중에 시작한다. 질문이 여러 원천을 요구한다면 각 주장에 어느 원천이 필요한지 표시한다. 원천이 없는 주장에는 ‘불명’이 정답일 수도 있다.

**3~4일차에는 데이터 계약을 검증한다.** 지표의 계산을 SQL 또는 재현 가능한 코드로 계산한다. 문서의 시행일과 실제 적용 기간을 대조한다. 두 원천의 기간이 같지 않다면 연결하지 않는다. 가장 단순한 질의에서 결과가 틀리면 에이전트 프레임워크를 늘리지 않는다. 데이터 타입, 조인, 누락 행, 오래된 문서를 먼저 고친다. 숫자와 설명이 모두 맞아도 권한이 틀리면 실패로 기록한다.

**5~6일차에는 대리 권한을 시험한다.** 두 사용자 계정을 준비해 같은 질문을 던진다. 관리자에게 허용된 데이터와 일반 직원에게 허용된 데이터가 실제로 다르게 나오는지 본다. 서비스 계정의 고권한 결과가 둘 모두에게 보이면 중단한다. 읽기와 쓰기의 차이를 검증한다. 토큰이 만료되거나 대상 API가 거부할 때 에이전트가 그럴듯한 성공 메시지를 생성하지 않는지 본다. 업무 승인 API가 있다면 아직 실행하지 않고 모의 상태 또는 테스트 환경에서 확인한다.

**7~8일차에는 최신성과 근거를 시험한다.** 외부 자료를 쓴다면 검색 결과와 실제 원문을 비교한다. 오래된 날짜의 기사, 나중에 정정된 기사, 제목은 비슷하지만 다른 제품의 글을 넣어 본다. 에이전트가 근거 부족을 인정하는지 확인한다. 여러 검색 결과가 같은 보도자료를 복제했을 때 독립된 근거 세 건처럼 말하지 않는지도 본다. 특정 주장을 누르면 해당 URL과 인용 위치를 볼 수 있어야 검토자가 빠르게 판단한다.

**9~10일차에는 체감 지연과 운영비를 측정한다.** 웹 검색, 정형 질의, 모델, 음성 합성을 각각 계측한다. 동일한 질문의 p50과 p95, 대기열이 생긴 상태의 지연을 따로 본다. 음성을 쓰지 않는 제품이라면 이 단계에서 음성을 억지로 넣지 않는다. 음성이 핵심이라면 짧은 응답과 긴 응답, 중간 끊기, 발화 정정, 잘못 들은 날짜를 시험한다. 호출 단가뿐 아니라 재시도, 검색, GPU 대기, 인덱싱, 사람 검토까지 포함해 한 건의 성공 비용을 계산한다.

**11~12일차에는 지역과 보존을 확인한다.** 필요한 데이터가 어떤 리전의 S3, DB, 모델 처리, 로그, 백업에 존재하는지 흐름을 그린다. 추론 프로필 이름을 문서에 적고 최신 목적지 목록을 확인한다. 지역 요구사항이 없다면 이를 억지로 성능 지표와 섞지 않는다. 지역 요구사항이 있다면 설명 페이지 한 줄이 아니라 실제 구성과 로그로 확인한다. 민감 자료가 불필요한 추적에 남지 않도록 로깅 수준을 조정한다.

**13~14일차에는 배포 여부를 결정한다.** 성공 기준을 ‘예쁜 데모’가 아니라 질문 유형별 정확도, 권한 위반 0건, 근거 확인 가능성, p95 지연, 비용, 운영 담당자 수용성으로 적는다. 미달한 유형은 범위를 좁혀 재시험하거나 기능을 보류한다. 모든 유형을 한 번에 출시하지 않아도 된다. 예를 들어 정책 문서 검색만 먼저 제공하고, 정형 지표 결합과 승인 API는 별도 마일스톤으로 둘 수 있다. 단계적 출시가 가능한 구조라면 모델의 좋은 부분을 활용하면서 실패의 범위를 제한할 수 있다.

## 장애와 변경에 대비한 운영 시나리오

### 데이터가 바뀌었을 때

정형 데이터셋에 새 열이 추가되거나 `price`의 의미가 바뀌면 의미 계층의 설명과 평가 질문을 함께 갱신한다. 단순히 인덱스를 다시 만들면 옛 계산 정의가 남을 수 있다. 문서의 새 정책 버전이 들어오면 구 버전을 검색에서 제외할지, 과거 질문용으로 보존할지 정한다. 두 버전이 모두 검색되면 적용일이 답변에 들어가야 한다. 데이터 소유자, 의미 정의 소유자, 검색 운영자가 누구인지 명시하지 않으면 문제 발생 후 아무도 정정하지 않는다.

### 사용자 권한이 바뀌었을 때

부서 이동, 퇴사, 임시 대행, 협력사 계약 종료는 대리 호출의 결과를 바꾼다. 캐시된 토큰이 남아 있거나 대상 서비스의 사용자 매핑이 지연되면 실제 정책과 다르게 보일 수 있다. 권한 변경 후 얼마 안에 반영되는지 측정한다. OBO 교환이 실패했을 때 서비스 계정으로 자동 재시도하는 우회 경로를 두지 않는다. 관리자만 할 수 있는 요청이 일반 계정으로 들어오면 이유를 명확히 알리고 거부한다. 허용 요청인데 실패한다면 토큰, 매핑, 대상 서비스, 업무 상태 중 어느 단계인지 조사할 수 있어야 한다.

### 검색 결과가 바뀌었을 때

검색 결과의 순위가 바뀌는 것은 정상일 수 있다. 하지만 이전에 작성된 초안의 근거가 사라졌거나 수정됐다면 재검토가 필요하다. 콘텐츠 생성 시스템은 초안 생성 시의 URL·발행일·제목·확인 시각을 남긴다. 자동 게시를 운영한다면 게시 직전 근거가 유지되는지 다시 확인하고, 확인 불가 또는 충돌이면 보류한다. 검색 공급자의 결과가 ‘실시간’이라는 이유로 출처 품질을 생략하면 선정적인 2차 기사를 공식 발표보다 앞세울 수 있다. 사용자에게 보여 주는 내용의 책임은 검색 API가 아니라 제품에 있다.

### 음성이 늦거나 끊겼을 때

음성 응답이 늦으면 TTS 모델 자체를 탓하기 전에 발화 종료 판정과 앞단 LLM 지연을 확인한다. 스트림이 중단되었을 때 이미 재생된 문장을 반복할지, 이어 읽을지, 전체 답변을 텍스트로 보여 줄지 결정해 둔다. 음성 모델을 롤백하거나 자체 호스팅 엔드포인트를 전환할 때 언어별 품질이 달라질 수 있으므로 골든 샘플을 재생해 비교한다. p95 악화가 특정 리전·시간·동시성에서만 나타나는지도 본다. 첫 오디오 바이트만 빨라도 전체 답변이 중간에 멎으면 사용자 경험은 나쁘다.

### 지역 구성이 바뀌었을 때

모델 프로필이나 리전 가용성이 바뀌면 도입 시점의 문서가 낡는다. 허용된 destination 리전 목록과 조직 정책을 다시 비교한다. 장애 시 글로벌 프로필로 자동 전환하면 성능은 회복되더라도 데이터 거주성 약속을 깰 수 있다. 폴백 정책에는 ‘사용 가능성 우선’이 아니라 업무 데이터 등급별 허용 범위를 둔다. 민감 데이터에 허용되지 않은 지역 경로밖에 남지 않았다면 호출을 보류한다. 데이터 지역 요구가 없는 공개 콘텐츠는 다른 폴백을 선택할 수 있다. 같은 장애에도 자료 등급에 따라 다른 복구 경로가 필요하다.

오늘 여섯 글은 서로 다른 제품과 회사의 이야기를 담고 있지만, 하나의 설계 원칙으로 연결된다. 모델이 여러 자료를 함께 사용할 때는 **숫자·문서·검색 결과의 진실 원천**을 나눈다. 모델이 사용자를 대신해 행동할 때는 **대리 신원과 대상 API의 권한**을 분리해 확인한다. 모델이 SQL을 만들 때는 **업무 의미와 데이터베이스 접근 범위**를 프롬프트 밖에서도 강제한다. 모델이 실시간 정보를 쓸 때는 **URL·발행일·원문 확인**을 남긴다. 음성 모델을 쓸 때는 **첫 바이트와 전체 턴**을 다르게 측정한다. 지역 모델을 쓸 때는 **호출 리전과 실제 처리 목적지**를 구분한다.

이 원칙은 새로운 제품을 무조건 도입하라는 뜻이 아니다. 현재 시스템의 책임 경계를 더 선명하게 만들라는 뜻이다. 제품이 작은 시기에는 한 명의 개발자가 모든 구간을 볼 수 있지만, 사용자와 자료가 늘어나면 팀별 경계가 생긴다. 그때 시스템이 각 답변의 출처, 각 도구 호출의 사용자, 각 수치의 계산식, 각 음성 응답의 지연 구간, 각 모델 호출의 데이터 이동을 설명할 수 있어야 한다. 좋은 데모는 한 번의 정답을 보여 준다. 좋은 운영 체계는 틀렸을 때 **어느 층에서 왜 틀렸고 어떻게 고칠지**를 알려 준다. 오늘 발표가 개발자에게 남기는 가장 실용적인 메시지는 바로 그 차이다.

## 심화 해설: 여섯 발표를 기능 목록이 아닌 시스템 설계로 읽기

### 질문의 자연어 표면과 실제 실행 경로는 다르다

사용자가 보는 입력창은 하나일 수 있다. 하지만 백엔드에서는 데이터 검색, 정형 집계, 신원 교환, 업무 API, 문장 생성, 음성 합성이 순서대로 혹은 병렬로 실행된다. 제품팀이 UI의 단순함을 시스템 구조의 단순함으로 착각하면 문제가 된다. 예를 들어 ‘내가 신청한 휴가의 잔여 일수와 다음 달 정책 변경을 음성으로 알려 줘’라는 요청은 개인의 잔여 일수를 HR 원장에서 계산하고, 변경 정책 문서를 찾아 시행일을 확인하고, 발화 가능한 문장으로 변환한 뒤 TTS를 호출한다. 잔여 일수의 계산은 오늘 기준일 수 있고 정책 변경은 다음 달 시행일일 수 있다. 둘을 현재 사실처럼 같은 시제로 읽으면 사용자가 잘못 이해한다.

이를 방지하려면 응답의 내부 표현을 하나의 긴 문자열로 시작하지 않는 편이 좋다. 각 주장에 `내용`, `자료 유형`, `원천 ID`, `기준 시각`, `확신 또는 검증 상태`, `민감도`, `표시·낭독 가능 여부`를 붙이는 구조를 생각할 수 있다. 화면에는 출처별로 숫자와 문서를 구분해 보여 주고, 음성에는 민감도에 따라 축약하거나 사용자 확인을 받는다. 원문 여섯 건이 이 데이터 구조를 공통으로 제공한다는 뜻은 아니다. 서로 다른 발표를 제품 아키텍처 관점에서 연결한 제안이다. 핵심은 **모델이 만들 최종 문장과 검증할 원천 사실을 같은 자료형으로 저장하지 않는다**는 것이다.

질문을 분해할 때도 모델의 의도 분류 하나만 믿지 않는다. 애매한 표현을 조직의 업무 규칙과 연결해야 한다. ‘직원 수’를 묻는 질문이 대시보드에는 상근 인원, 인사 원장에는 재직 계약 수, 급여 시스템에는 이번 달 지급 대상 수로 정의되어 있다면, 가장 가까운 테이블을 고르는 것은 오답이다. 해당 제품에서 공식으로 지정한 지표를 먼저 찾고, 없으면 어떤 정의를 원하는지 물어야 한다. Amazon Quick의 의미 보강과 EDB의 의미 계층은 이 문제를 다른 방식으로 다루지만, 둘 다 **업무 정의를 명시적으로 공급해야 한다**는 교훈을 준다. 자동화가 정의를 만들어 내도록 맡기는 것이 아니다.

### 정형 답변과 문서형 답변이 충돌하는 예

정형 데이터에서 11월 1일 기준 승인 완료된 채용 공고가 42개이고, 정책 문서에는 ‘올해 승인 공고는 50개까지 가능’이라고 적혀 있을 수 있다. 사용자는 ‘남은 승인 가능 건수’를 물을 것이다. 단순 계산은 8개다. 하지만 정책 문서의 50개가 회사 전체 한도인지 특정 사업부 한도인지, 42개 집계가 동일한 범위인지, 승인 취소된 건이 포함됐는지 확인하지 않으면 숫자 8은 가짜 정밀도다. 에이전트는 자료 두 개가 있다는 이유로 바로 빼기 연산을 해서는 안 된다. 데이터 범위가 일치한다는 계약이 있을 때만 결합한다. 범위가 불명확하면 ‘42개와 한도 50개는 확인했지만 범위 일치를 검증하지 못했다’고 답하는 편이 신뢰할 만하다.

문서형 답변에서는 단어의 유사성이 오해를 부른다. ‘휴직’과 ‘휴가’, ‘수습 종료’와 ‘계약 종료’는 검색 모델이 유사하다고 볼 수 있어도 법적·업무적 효과가 다르다. 검색 상위에 나온 정책 문서의 제목만 확인하지 말고 해당 조항과 시행일을 봐야 한다. 회사 내부 문서는 초안·검토중·승인·폐기 상태가 있을 수 있다. 문서의 상태가 메타데이터로 관리되지 않으면 에이전트는 문장만 읽고 초안을 현행 정책처럼 인용한다. 이런 오류는 언어 모델의 추론 문제라기보다 문서 수명주기와 인덱싱 범위의 문제다.

### 외부 검색과 내부 지식의 역할 차이

외부 웹 검색은 변화 탐지에 유리하다. 기업 발표, 규제 당국 공지, 오픈소스 릴리스처럼 오늘 처음 나온 자료를 찾을 수 있다. 반면 내부 지식베이스는 조직이 확정해 적용 중인 규칙을 설명하는 데 적합하다. 외부 검색 결과가 내부 정책의 우선순위를 바꾸면 안 된다. 예를 들어 다른 회사가 새로운 휴가 제도를 발표했어도 우리 조직의 휴가 규정이 바뀐 것은 아니다. 외부 자료는 ‘검토할 변화’, 내부 승인 자료는 ‘현재 적용 규칙’으로 표시한다. 뉴스 엔진의 추천 문구와 HR 서비스의 정책 답변을 같은 RAG 파이프라인으로 묶을 때 가장 조심할 지점이다.

외부 자료의 URL도 영구적 근거가 아니다. 게시자가 내용을 수정하거나 주소를 이전할 수 있다. 답변이 나간 시점의 제목·발행일·확인 시각·핵심 인용을 기록하되, 저작권이나 개인정보를 침해하는 방식으로 원문 전체를 무단 보관하지 않는다. 자료가 뒤늦게 정정되었을 때 어떤 사용자에게 이전 답변을 보여 줬는지 알 수 있어야 고위험 영역에서 후속 조치를 판단할 수 있다. 반대로 일상적인 낮은 위험의 뉴스 추천에 모든 사용자를 개별 추적하는 과도한 운영은 비용과 사생활 부담을 늘린다. **자료 위험과 사용 결과의 영향에 비례해 추적 수준을 정한다.**

## Amazon Quick 심화: 데이터세트 보강의 실제 함정

### 열 타입은 파서의 문제가 아니라 질문의 해석 문제다

CSV를 올리면 열의 데이터 타입을 자동 추론하는 기능은 편리하다. 그러나 숫자처럼 보이는 직원 ID를 정수로 바꾸면 앞자리 0이 사라질 수 있다. 날짜처럼 보이는 회계 기간 코드를 실제 날짜로 바꾸면 월말 기준이 왜곡될 수 있다. 원문 예제의 날짜·금액 열 바로잡기는 데이터 타입 점검의 중요성을 보여 주지만, 모든 열을 ‘숫자로 변환 가능한지’만 보고 결정하면 안 된다. 직원 ID, 고객 번호, 우편번호는 산술 대상이 아니다. 금액에는 통화와 부가세 포함 여부가 필요하다. 날짜에는 저장 시간대와 기준일이 필요하다.

정형 데이터의 의미 보강은 에이전트의 자연어→SQL을 돕는다. 예제에서는 데이터셋 설명과 열 설명, 사용 지침을 넣는다. 실무에서는 설명의 유지보수 책임을 정해야 한다. `Sales`의 정의가 바뀌었는데 열 설명이 옛 버전이면 에이전트는 틀린 정의로 정확한 SQL을 만든다. SQL 문법이 맞아도 업무 결과는 틀린다. 메타데이터도 코드와 마찬가지로 변경 리뷰가 필요하다. 새 열, 삭제 열, 계산식 변경, 용어 변경이 있을 때 설명과 평가 질문이 함께 바뀌는지 CI 또는 체크리스트로 확인할 수 있다.

### Space를 ‘다 담는 바구니’로 쓰지 않는다

Space가 여러 자료를 한데 모을 수 있다고 해서 조직 전체의 모든 S3 버킷과 데이터셋을 하나에 넣는 것은 곤란하다. 자료가 많아질수록 이름이 비슷한 지식베이스가 많아지고, 부적절한 문서가 검색 후보에 들어갈 가능성이 높아진다. 권한이 다른 자료를 같은 범위로 묶으면 가장 넓은 사용자 범위가 의도치 않게 적용될 수 있다. 업무 단위로 Space를 나누고, 하나의 Space 안에서도 원천별 접근권한을 확인한다. 조회가 허용된 문서라도 사용자가 답변으로 외부 공유할 권한이 있는지 별개로 보아야 한다.

권한 테스트에는 ‘도구가 접근할 수 있는가’만이 아니라 ‘에이전트가 답변에 인용할 수 있는가’를 넣는다. 모델이 민감 문서를 검색 결과로 받았지만 최종 답변에서 숨기는 방식은 근본적인 통제가 아니다. 필요 없는 문서가 도구 결과로 전달되지 않도록 앞단에서 제한해야 한다. 검색 인덱스가 권한을 반영하지 않는다면 사용자별 자료 집합을 분리하거나 별도의 권한 필터를 적용해야 한다. 인덱스는 원본 데이터의 복사 또는 파생물이다. 원본 S3 버킷의 접근권한만 검토하고 검색 결과 노출을 보지 않으면 보안 설계가 반쪽이 된다.

### 인용을 제품 기능으로 검증한다

정형·비정형 결합의 최종 답변이 인용을 표시한다고 해도 근거로서 충분한지 시험해야 한다. ‘이번 분기 매출은 전기 대비 12% 감소했다’에는 계산한 데이터셋, 집계 기간, 필터와 비교 기준이 필요하다. ‘고객 수요가 줄어서’에는 근거 문서의 해당 문장이 필요하다. 숫자와 원인 추정을 한 문장에 넣고 문서 링크 하나만 달면 무엇이 증명됐는지 불분명하다. UI는 문장별 출처를 제공하거나 숫자 카드와 설명 문단을 분리할 수 있다. 원문에 인용 기능이 있다고 하더라도 **인용이 실제 주장과 같은 범위인지**는 우리 서비스에서 평가해야 한다.

좋은 테스트는 답이 분명한 질문뿐 아니라 일부러 틀린 전제를 가진 질문이다. ‘10월에 모든 지역의 매출이 줄었지?’라고 물었을 때 한 지역이 늘었다면 정정해야 한다. ‘최신 정책에 따르면’이라고 했지만 검색 결과가 이전 정책뿐이라면 최신임을 주장하면 안 된다. ‘왜 줄었어?’라고 묻는데 원인 자료가 없으면 숫자만 말하고 원인은 확인되지 않았다고 해야 한다. 모든 질문에 길고 완성된 문장을 만드는 모델보다, 어떤 부분은 모른다고 말하고 필요한 원천을 안내하는 시스템이 실제 업무에 낫다.

### 운영자가 볼 수 있는 대시보드

운영 대시보드에는 전체 질문 수보다 실패의 층별 분포가 유용하다. `정형 질의 실패`, `문서 검색 실패`, `원천 간 날짜 불일치`, `권한 거부`, `인용 확인 실패`, `사용자 질문 재작성`, `사람 검토로 이관`을 나눠 본다. 숫자 하나인 ‘답변 성공률’은 같은 문제를 다른 원인으로 숨길 수 있다. 데이터를 잘 가져왔는데 설명이 틀린 경우와 데이터를 가져오지 못했는데 모델이 꾸며 낸 경우는 심각도가 다르다. 후자는 ‘성공’처럼 보이는 답변 때문에 발견이 늦을 수 있다. 검토 샘플에서 원문을 열어 보는 인간의 역할도 운영의 일부다.

## OBO 심화: 토큰 교환 전후의 책임 경계

### ‘누구의 권한’이 흐름마다 달라질 수 있다

사용자는 에이전트 화면에 로그인한다. 에이전트 애플리케이션은 Gateway를 호출한다. Gateway는 ServiceNow가 받을 토큰을 Entra에서 얻는다. ServiceNow는 그 토큰을 기존 사용자에게 매핑한다. 네 단계 모두 같은 인간을 가리켜야 하지만 각 단계의 식별자는 다를 수 있다. 화면의 표시 이름, Entra 객체 ID, 이메일, ServiceNow 사용자 ID를 섞어 비교하면 변경 시 오류가 생긴다. 로그에는 가능한 한 안정적인 내부 식별자와 그 매핑 버전을 남기고, 표시용 이름은 권한 근거로 쓰지 않는다. 원문 예제가 `preferred_username`을 이메일에 매핑하는 것은 구성 방법의 한 사례다. 모든 조직에서 그 클레임이 불변·고유하다는 보장은 없다.

토큰 교환의 성공은 대상 API 호출의 성공과 다르다. Entra가 토큰을 발급해도 ServiceNow 사용자가 비활성 상태일 수 있다. 사용자가 활성이라도 특정 테이블 권한이 없을 수 있다. 테이블 접근은 가능해도 특정 티켓의 상태가 변경될 수 없는 단계일 수 있다. 각 단계가 거부 이유를 자신이 아는 범위 안에서 제공해야 한다. 사용자는 불필요한 내부 보안 구조를 볼 필요는 없지만, ‘접근 권한이 없어 처리하지 못했다’와 ‘잠시 연결 오류가 났다’는 구분할 수 있어야 한다. 재시도할 문제와 권한 신청할 문제는 다르다.

### 권한 축소와 위임의 최소 범위

‘에이전트가 사용자를 대신한다’는 말은 사용자의 모든 권한을 에이전트에게 복제한다는 뜻이어서는 안 된다. 사용자는 ServiceNow에서 많은 작업을 할 수 있어도 에이전트가 허용받은 도구는 제한할 수 있다. Gateway target의 도구 목록, Entra scope, ServiceNow 권한, 애플리케이션의 업무 정책을 겹쳐 가장 좁은 범위가 실제로 적용되는지 확인한다. 특정 API는 읽기만 허용하고, 쓰기는 별도의 명시적 확인 뒤 제한된 필드에만 허용할 수 있다. 정책은 ‘AI가 이 일을 해도 되는가’와 ‘사용자가 이 일을 할 수 있는가’라는 두 질문을 모두 통과해야 한다.

예를 들어 HR 담당자가 원래 직원 인사기록을 수정할 수 있어도, 에이전트에는 직원 주소의 초안 작성만 허용하고 실제 저장은 기존 관리 화면에서 하게 할 수 있다. 반대로 낮은 위험의 본인 문의 티켓 생성은 에이전트가 바로 수행할 수 있다. 도구 권한은 사용자의 최대 권한보다 작을 수 있다. 이런 설계는 원문의 OBO 흐름을 부정하는 것이 아니다. OBO는 사용자 식별을 보존하고, 실제 행동 범위는 그 위에 제품이 정의해야 한다는 뜻이다.

### 유효기간과 철회 시나리오

사용자 권한이 변경되거나 세션이 종료됐을 때 이미 발급된 토큰이 언제까지 유효한지 확인한다. 오래 남은 토큰을 통해 퇴사자가 계속 호출할 수 있다면 큰 문제다. 단기 토큰, 재인증, 대상 서비스의 활성 상태 검사, 위험 업무의 실시간 권한 확인을 조합한다. 토큰을 저장할 필요가 있다면 저장 위치와 암호화, 접근권한을 명확히 하고 로그에는 남기지 않는다. OBO 흐름을 위해 클라이언트 시크릿이 필요하다면 회전 절차와 만료 감시도 운영해야 한다. 원문은 구성 순서를 보여 주지만 각 조직의 시크릿 관리 주기와 내부 감사 요구까지 대신 정하지 않는다.

### 테스트 매트릭스: 성공보다 거부가 중요하다

| 조건 | 기대 결과 | 잘못된 결과의 의미 |
| --- | --- | --- |
| 본인의 허용된 티켓 읽기 | 사용자 권한으로 성공 | 실패하면 매핑·scope 조사 |
| 타인의 비공개 티켓 읽기 | 대상 API에서 거부 | 성공하면 권한 누출 |
| 다른 audience의 토큰 제출 | 교환 또는 검증 단계에서 거부 | 성공하면 토큰 경계 취약 |
| 동의하지 않은 scope 요청 | IdP에서 거부 | 우회되면 위임 범위 문제 |
| 권한 철회 직후 재호출 | 정책 시간 안에 거부 | 오래된 자격증명 문제 |
| 동일한 쓰기 작업 두 번 호출 | 한 번만 반영 또는 중복 명시 | 중복 업무 처리 |

테스트 결과를 문서화할 때 HTTP 상태 코드만 적지 않는다. ServiceNow의 실제 상태가 바뀌었는지, 감사 이벤트가 누구의 이름으로 남았는지 확인한다. 네트워크가 끊겨 응답이 없더라도 요청은 성공했을 수 있다. 이런 경우 에이전트가 다시 호출하면 중복 작업이 생긴다. 쓰기 도구에는 idempotency key 또는 업무 객체의 현재 상태 확인을 두어야 한다. 특히 결재·결제·게시처럼 중복의 영향이 큰 기능에는 사용자에게 ‘확인 중’ 상태를 보여 주고 결과를 조회하는 경로가 필요하다.

## Norton Revamp 심화: ‘실시간’이 콘텐츠 품질이 되는 조건

### 검색 질문을 만드는 모델의 편향

고객 목표와 최근 활동을 토대로 검색 질의를 생성하면 개인화가 가능하다. 동시에 사용자 과거 관심사의 반복만 보여 주는 편향이 생길 수 있다. 예를 들어 사이버보안 전문가가 특정 제품군에 관한 글을 많이 올렸다면 검색 질의가 계속 그 제품군으로 좁아질 수 있다. 새로운 공격 기법이나 규제 변경을 놓치면 전문성을 키우려는 목적에 맞지 않는다. 따라서 개인화된 질의와 범용 필수 소스 감시를 분리하는 편이 좋다. 주요 공식 발표·규제 기관·보안 권고처럼 반드시 봐야 할 자료는 사용자 활동 패턴만으로 제거하지 않는다. 이는 원문 아키텍처를 근거로 한 설계 제안이지 고객 서비스가 현재 이 방식으로 동작한다는 주장은 아니다.

검색 결과의 신뢰도 순위도 단순한 도메인 목록으로 충분하지 않다. 공식 블로그가 제품의 좋은 면을 강조할 수 있고, 외부 연구 보고서가 엄격한 방법론을 제공할 수 있다. 어떤 질문에는 공식 API 문서가 가장 중요하고, 어떤 질문에는 규제기관 발표나 원 논문이 우선이다. ‘공식’은 출처의 신원을 확인할 수 있다는 뜻이지 모든 주장에 독립적 검증이 끝났다는 뜻은 아니다. 예를 들어 공급자가 ‘최대 3배 빠르다’고 말했으면 그 문장을 공급자 측 측정치로 인용해야 한다. 제품 사용자에게 ‘모든 환경에서 3배 빠르다’고 바꾸지 않는다.

### 게시물 초안의 근거 문장 연결

콘텐츠 코칭 서비스에서 모델은 여러 자료를 조합해 읽기 쉬운 문장을 만든다. 그 과정에서 인용이 한 문단 끝에 하나만 붙으면 앞의 여러 주장 중 무엇을 뒷받침하는지 모호해진다. 초안 내부에는 주요 주장마다 원문 문장 또는 문단을 연결할 수 있다. 사용자가 게시 전 검토할 화면에는 ‘발표 사실’, ‘고객 의견’, ‘내 생각’을 색이나 라벨로 나눌 수 있다. 이런 제품 설계는 글의 품질뿐 아니라 사용자의 평판을 보호한다. 사용자가 최종 문장을 승인하더라도 근거를 쉽게 볼 수 없으면 실제로 검토했다고 보기 어렵다.

게시물에 인용 링크를 넣는 방식도 채널별로 달라야 한다. 짧은 소셜 포스트에서 모든 문장에 URL을 붙이면 읽기 어려울 수 있다. 그렇다고 링크를 모두 빼면 확인 불가가 된다. 원문 링크와 핵심 주장 몇 개를 포함한 초안을 제공하고, 링크가 길면 게시 채널의 카드 또는 댓글 구조를 고려한다. 사용자가 링크를 빼고 발행하기로 선택했다면 어떤 주장이 자체 의견인지 표현을 조정할 수 있다. 특히 숫자와 제품 지원 범위처럼 오해하기 쉬운 내용은 출처 없이 단정하지 않는 편이 낫다.

### 뉴스 추천을 측정하는 방법

클릭률과 게시 빈도만으로 뉴스 엔진의 품질을 평가하면 자극적인 주제를 우대할 수 있다. 별도로 `중요한 공식 발표 발견율`, `중복 제거율`, `발행일 정확도`, `원문 확인율`, `잘못된 주장 비율`, `사용자 수정량`, `게시 후 정정 건수`를 측정한다. 일부는 자동화가 가능하지만 원문과 최종 문장을 비교하는 사람의 표본 검토가 필요하다. 안전한 범위의 실험에서 두 개의 검색·순위화 전략을 비교할 때는 같은 날짜와 같은 사용자 목표를 사용한다. 다른 주간의 뉴스량이 다르면 단순 클릭 비교는 공정하지 않다.

원문은 고객의 개발 과정 성과를 보여 주지만 제품 뉴스 품질의 객관 벤치마크를 완결해 주지는 않는다. 개발팀의 속도가 빨라진 것은 제품 실험의 비용을 낮출 수 있다. 그러나 빨리 만든 기능이 정확한 추천을 제공하는지, 사용자가 자주 수정하는지, 잘못된 게시물이 줄었는지는 다른 데이터가 필요하다. **개발 생산성, 사용자 참여, 사실성, 평판 위험**을 서로 다른 대시보드에 놓아야 원문 수치를 오해하지 않는다.

## EDB SemKB 심화: 의미를 저장하는 위치가 바뀌면 변경 절차도 바뀐다

### 같은 데이터, 다른 질문: 고객 360 예제에서 배우기

원문의 C360 데이터는 네 테이블과 하나의 파생 뷰로 이해할 수 있다. 사용자는 ‘주별 큰 고객 수’, ‘지출 상위 고객’, ‘가장 많이 팔린 상품’을 묻는다. 테이블 이름만 알아도 일부 질문은 SQL을 만들 수 있다. 하지만 상태(state)가 고객 행의 컬럼이 아니라 위치 테이블에 있고, 구매 가격의 의미가 주문 총액이라는 사실을 알아야 올바른 SQL이 나온다. 그 외 ‘큰 고객’의 기준은 데이터에서 저절로 나오지 않는다. 이를 뷰로 정의해야 팀이 같은 기준을 쓸 수 있다. 자연어 질의의 편리함은 비즈니스 정의를 생략하는 능력이 아니라 **기존 정의를 사람이 질문하는 형태로 호출하는 능력**이다.

한 번 작성한 의미 계층도 변경 관리를 받아야 한다. 예를 들어 `big_spender`의 기준 금액을 바꾸면 과거 대시보드와 새 에이전트의 결과가 달라질 수 있다. 뷰 이름은 같아도 의미가 바뀐다. 변경일과 적용 기간을 기록하고, 과거 데이터를 새 기준으로 다시 계산할지 결정한다. 에이전트 응답에는 어떤 정의 버전을 사용했는지 남길 수 있다. 팀의 단일 진실 원천은 테이블 하나가 아니라 **시간과 버전이 있는 계산 규칙**이다.

### 데이터베이스 안의 권한과 에이전트의 설명

Postgres `GRANT`와 RLS는 모델이 볼 수 있는 결과를 제한한다. 그러나 이 정책의 결과를 사용자에게 어떻게 설명할지도 중요하다. 같은 질문에 관리자는 10명, 일반 사용자는 3명으로 답한다면 일반 사용자가 ‘전체 3명’이라고 오해할 수 있다. 권한상 볼 수 있는 범위가 제한된 경우 ‘현재 권한으로 조회 가능한 범위에서 3명’이라고 표시해야 한다. 반대로 총계만 공개하도록 허용했다면 행은 볼 수 없어도 승인된 집계 뷰의 수치는 보여 줄 수 있다. 권한은 SQL 오류를 막는 것에서 끝나지 않고 답변의 범위 설명으로 이어져야 한다.

고객 360의 개인 식별번호 예제처럼 민감 열은 특히 주의한다. 모델이 ‘민감 정보는 표시하지 않겠습니다’라고 말하는 것은 거부 방식 중 하나지만, 실제 도구 응답으로 번호가 이미 모델에 전달됐다면 노출 위험은 남는다. 열 단위 권한 또는 안전한 뷰에서 원천적으로 차단해야 한다. 도구 응답의 원시 행을 로그나 추적 시스템에 기록하면 별도의 유출 경로가 되므로 로그 정책도 함께 검토한다. **모델 화면에서 숨기는 것과 모델 런타임에 들어오지 않는 것은 다른 보호 수준**이다.

### 쿼리 성능은 보안과 같은 운영 문제

에이전트가 SQL을 생성할 수 있으면 사용자 질문이 의도치 않게 비싼 조인을 만들 수 있다. Postgres 역할이 읽기 전용이어도 테이블 전체 스캔으로 서비스 성능을 떨어뜨릴 수 있다. 도구에는 읽기 전용 트랜잭션, statement timeout, 결과 행 수 제한, 허용 스키마, 쿼리 비용 추정 또는 승인된 뷰만 접근하도록 하는 제약을 고려한다. 모든 질의를 사전에 정형화하면 자연어 질의의 유연성이 줄지만, 아무 제약도 없으면 운영 환경의 안정성이 흔들린다. 업무 위험과 데이터 크기에 맞춰 허용 폭을 정한다. 초기에는 작은 읽기 전용 복제본이나 검증용 데이터셋에서 평가하고, 실제 운영 원장과의 연결은 이후 단계로 둘 수 있다.

Observability 역시 비용과 민감도 사이의 선택이 있다. SQL 텍스트를 모두 수집하면 디버깅에는 좋지만 사용자 질문이나 조건에 개인 정보가 들어갈 수 있다. 쿼리 패턴과 파라미터를 분리하고 민감 값을 가린다. 트레이스 샘플링이 너무 강하면 드문 권한 오류를 놓칠 수 있으므로 보안 거부와 오류는 우선 기록한다. 반면 정상적인 대량 읽기 요청의 전체 결과 행을 남길 필요는 없다. 에이전트의 답변 품질을 검증하려면 충분한 재현 정보가 필요하되, 재현 정보를 위해 직원 원문 자료를 과도하게 복제해서는 안 된다.

## 음성 AI 심화: 빠른 합성과 좋은 대화는 다르다

### 첫 바이트의 착시

음성 모델이 텍스트 입력을 받아 첫 오디오 바이트를 보내는 데 약 90ms가 걸린다는 소개는 흥미롭다. 하지만 사용자가 기대하는 것은 ‘질문을 마치고 답을 듣기 시작할 때까지’다. 말을 끝냈다고 판단하는 데 500ms, 전사 확정에 200ms, LLM이 첫 문장을 만들기까지 800ms, 네트워크 왕복에 100ms, TTS에 90ms가 걸리면 사용자는 1.69초가량의 침묵을 느낄 수 있다. 이 숫자는 실제 측정이 아닌 설명을 위한 가상 예다. 공급자가 제시한 TTS 숫자와 종단 간 사용자 체감 시간을 혼동하지 말자는 뜻이다. 반대로 앞단을 병렬화하고 부분 전사를 잘 활용하면 첫 음성은 더 빨라질 수 있지만 정정 비용도 커질 수 있다.

구간별 계측은 성능 최적화의 출발점이다. `마이크 캡처`, `VAD/endpointing`, `ASR 부분 전사`, `ASR 확정`, `검색·도구`, `LLM 첫 토큰`, `TTS 첫 바이트`, `재생 시작`, `답변 완료`를 요청 ID와 타임스탬프로 연결한다. 네트워크가 느린 모바일 사용자는 서버 안의 TTS 지연보다 패킷 손실과 재생 버퍼의 영향을 크게 받을 수 있다. 사무실의 안정된 Wi-Fi에서 측정한 숫자를 이동 중 셀룰러 환경의 SLA로 삼으면 안 된다. 언어별로 발화 속도와 문장 구조도 다르다. 다국어 서비스는 대표 언어·기기·네트워크를 별도 집단으로 측정한다.

### 끼어들기와 정정 처리

실제 대화에서는 사용자가 AI의 말을 끊고 질문을 바꾼다. TTS가 재생 중일 때 새 사용자의 발화가 시작되면 현재 오디오 스트림을 어떻게 중단하고, 이미 실행한 도구 결과를 어떻게 취소할지 정해야 한다. 단순한 정보 조회라면 답변을 중단하고 새 질문으로 넘어갈 수 있다. 그러나 에이전트가 쓰기 API를 이미 호출했다면 음성 중단이 업무 동작의 취소를 뜻하지 않는다. UI는 ‘말하기를 멈춤’과 ‘요청 취소’를 구분해야 한다. 취소 요청이 도구 실행 전에 도착했는지, 실행 후에 도착했는지도 확인해야 한다. 자연스러운 음성 경험보다 실제 상태의 정확한 표시가 우선이다.

부분 전사는 문장을 완성하기 전의 추정이다. ‘11월 4일로 변경해’가 ‘11월 14일로 변경해’로 수정될 수 있다. 날짜·금액·계정 번호를 포함한 작업에는 최종 전사를 확인하고, 중요한 값은 음성으로 다시 읽거나 화면에 표시한다. 사람이 ‘네’라고 답한 순간에도 어떤 작업에 동의했는지 바뀌지 않은 요약이 필요하다. 승인 대상으로 두 건이 연달아 나타나면 잘못된 건을 승인할 수 있다. 음성 UI의 확인 설계는 단순히 버튼을 음성으로 옮기는 작업이 아니다.

### 모델 배포의 실제 비용

Sonic을 SageMaker AI 모델 패키지로 호스팅하면 데이터 경로를 고객 VPC 안으로 통제하는 선택지가 생긴다. 대신 엔드포인트를 켜 둔 시간의 GPU 비용과 예약 용량, 업데이트가 필요하다. 요청량이 드문 서비스라면 빠른 첫 바이트보다 유휴 GPU 비용이 클 수 있다. 트래픽이 갑자기 몰리는 서비스라면 자체 GPU가 부족해 대기가 늘 수 있다. API 경로는 운영이 간단할 수 있지만 네트워크와 계약상의 데이터 경로를 검토해야 한다. 모델마다 배포 방식이 다르므로 Sonic의 자체 호스팅 가능성을 Ink에 자동 적용하지 않는다.

음성 품질 테스트는 짧은 데모 문장만으로 충분하지 않다. 한국어 숫자, 영문 이름이 섞인 문장, 법률·인사 용어, 긴 문단, 문장 중간의 괄호, 말줄임표, 여러 감정의 톤을 듣는다. 자동 지표가 좋아도 중요한 금액을 잘못 읽으면 서비스에 치명적일 수 있다. 청각 장애인을 위해 음성만이 유일한 결과 경로가 되어서는 안 된다. 텍스트 전사와 화면 요약을 함께 제공하면 정확성 검증에도 도움이 된다. 오늘 원문은 음성 모델과 배포 경로를 설명하지, 특정 한국어 HR 업무에서의 품질을 증명하지 않는다.

## 인도 지역 추론 심화: 데이터 거주성은 파이프라인의 속성

### 프로필 ID를 정책 문서에 남기는 이유

클라이언트의 `region="ap-south-1"` 설정만 보면 호출이 뭄바이에서 끝난다고 생각하기 쉽다. 그러나 Bedrock의 cross-Region inference는 프로필에 따라 요청을 여러 destination Region 중 하나에서 처리할 수 있다. 원문은 글로벌과 인도 geographic 프로필을 구분한다. 이 차이를 코드 리뷰에서 보려면 모델 ID를 환경 변수 하나로만 숨기지 말고, 어떤 업무 데이터 등급에서 어떤 프로필을 허용하는지 정책 문서에 적어야 한다. 설정이 바뀌면 배포 검증이 실패하도록 할 수도 있다. 프로필 이름을 적는 것은 규제 준수의 충분조건은 아니지만, 필요한 조건을 확인하는 출발점이다.

지역 요건이 강한 업무에서는 장애 폴백을 더욱 신중히 정한다. 인도 두 목적지 중 하나가 불가용할 때 허용된 다른 인도 리전으로 가는 것은 정책에 맞을 수 있다. 하지만 글로벌 프로필로 바꾸어 처리 지역을 넓히는 것은 사용 가능성을 높이는 대신 약속을 깨뜨릴 수 있다. 어떤 데이터는 지역 외 처리가 가능하고 어떤 데이터는 불가능할 수 있다. 따라서 모델 호출을 하기 전에 입력 자료의 등급을 알고 있어야 한다. 자료 등급이 불명확하면 기본값을 넓은 경로로 두지 않는다. 폴백이 가능한 데이터와 보류해야 하는 데이터를 구분한다.

### 모델의 다국어 문서 처리 평가

원문은 합성 힌디어 전기요금 청구서를 예제로 들고, OCR 결과와 정형 JSON, 영어 요약, Hinglish 대화를 보여 준다. 실무에서는 문서 유형별로 오류 비용이 다르다. 공과금 청구서의 납기일을 잘못 읽으면 지연 납부가 발생할 수 있다. KYC의 이름이나 식별번호를 잘못 읽으면 계정 인증이 실패하거나 다른 사람에게 연결될 수 있다. 손글씨, 흐린 사진, 접힌 종이, 여러 페이지, 도장 위의 글자, 지역 언어의 혼합 표현을 시험해야 한다. 합성 샘플은 민감 데이터 없이 코드를 익히기에 좋지만 실제 문서 품질을 대표하지 않는다.

평가표에는 단순한 전체 정확도보다 필드별 `정확한 추출`, `누락`, `잘못된 값`, `읽을 수 없음의 정직한 표시`를 기록한다. 모델이 읽을 수 없는 부분을 추측해 채우면 누락보다 위험할 수 있다. 날짜는 ISO 형식으로 바뀌면서 월·일 순서가 뒤집힐 수 있고, 금액은 쉼표와 소수점 처리가 다를 수 있다. 로마자 음역은 유일한 표준이 없는 이름도 있으므로 원문 문자와 음역을 모두 보존해야 한다. 정형 출력 스키마를 강제하면 JSON 형식은 안정될 수 있지만 필드 값의 사실성이 자동으로 보장되는 것은 아니다. 출력 유효성 검사와 이미지 원본 대조는 별도다.

### 캐싱과 서비스 티어의 비용 계산

고객사의 비용 절감 발언에는 프롬프트 캐싱이 포함된다. 캐시가 잘 맞으려면 길고 변경이 드문 시스템 지침이나 도구 설명이 입력 앞부분에 안정적으로 있어야 한다. 사용자별 문서 이미지를 캐시 대상으로 보관하는 것과는 의미가 다르다. 캐시 적중률이 낮으면 예상 비용 절감은 나오지 않는다. 비용 비교에는 캐시 읽기·쓰기 비용, 긴 문서의 입력 토큰, 이미지 detail, 실패 재시도, 서비스 티어를 넣는다. 원문은 덜 급한 요청에 flex 티어가 가격 선택지가 될 수 있음을 언급한다. 가격표와 리전별 제공 조건은 바뀔 수 있으므로 실제 배포 직전 공식 가격과 모델 카드를 재확인한다.

지역 정책과 캐시 정책은 서로 연결된다. 캐시가 어느 지역에서 처리·저장되는지, 로그와 추적이 어디에 기록되는지도 검토한다. 실제로 어떤 세부 처리가 이루어지는지는 해당 서비스의 공식 문서·계약을 근거로 판단해야 한다. ‘데이터가 AWS 네트워크를 떠나지 않는다’는 문장은 ‘특정 국가의 모든 처리·저장·접근 요건을 충족한다’와 같지 않다. 데이터 거주성 문서에는 모델 호출만이 아니라 업로드, 전처리, 추론, 후처리, 저장, 삭제까지 전체 경로를 그리는 이유다.

## 실무 설계 부록 1: 답변 한 건의 계보를 끝까지 남기는 방법

뉴스 여섯 건을 읽고 가장 먼저 만들 수 있는 작은 공통 도구는 ‘답변 계보’다. 사용자에게는 자연스러운 문장을 보여 주되, 운영자는 그 문장을 만든 자료와 행동을 역으로 따라갈 수 있어야 한다. 거창한 에이전트 플랫폼을 먼저 고르기보다 실제 질문 하나의 계보를 종이에 그려 보는 편이 출발점이다. 질문 ID에서 시작해 로그인 주체, 조회한 자료, 실행한 SQL, 검색한 URL, 모델 입력의 버전, 도구 결과, 최종 문장, 사용자 확인을 연결한다. 전부를 원문 그대로 저장하라는 뜻이 아니다. 민감 자료는 참조 ID와 해시 또는 제한된 메타데이터로 남기고, 실제 원문 접근은 별도 권한으로 통제한다.

첫 번째 단위는 **요청의 맥락**이다. 사용자, 세션, 조직, 요청 시각, 시간대, 언어, 선택한 업무 범위를 기록한다. ‘오늘’이나 ‘이번 주’ 같은 말은 이 맥락이 없으면 재현되지 않는다. 요청 시점이 오전 11시 30분 KST인지 자정 UTC인지에 따라 날짜가 달라진다. 모델 입력에 사용한 시스템 지침과 도구 스키마 버전도 남긴다. 같은 질문이 나중에 다른 답을 낼 때 자료가 바뀐 것인지, 지침이 바뀐 것인지, 모델이 바뀐 것인지 분리하기 위해서다. 단, 사용자 발화 전체를 항상 로그에 저장하면 민감도가 높아지므로 업무 위험과 보존 목적에 맞춰 최소화한다.

두 번째 단위는 **자료 선택**이다. 정형 데이터라면 데이터셋 버전, 필터, 기준일, 지표 정의 ID를 남긴다. 문서라면 원문 문서 ID, 버전, 시행일, 참조한 절을 남긴다. 웹 검색이라면 검색 시각, 질의, 반환 URL, 발행일, 실제 원문 확인 여부를 남긴다. 같은 제목의 문서가 두 개 있을 수 있으므로 제목만으로는 부족하다. 외부 URL은 시간이 지나 바뀔 수 있으므로 검증 시각도 중요하다. 자료 선택이 답변의 품질을 좌우하는데, 많은 시스템은 최종 모델 텍스트만 남긴다. 그러면 나중에 정정할 방법이 없다.

세 번째 단위는 **행동과 권한**이다. 어떤 사용자의 토큰으로 어느 Gateway target을 호출했는지, 대상 API의 객체 ID와 결과 상태가 무엇인지 남긴다. 토큰 자체나 시크릿은 저장하지 않는다. OBO에서 교환된 토큰의 `audience`와 권한 범위가 정책에 맞았는지 비민감 메타데이터로 기록할 수 있다. 대상 서비스에서 거부한 이유를 에이전트가 성공처럼 포장하지 않았는지도 연결한다. 쓰기 작업에는 사용자의 확인 기록과 서버의 상태 변경 이벤트를 함께 연결한다. 응답을 받지 못한 호출은 실패로 단정하지 않고 대상 상태를 다시 조회할 경로를 둔다.

네 번째 단위는 **출력과 검증**이다. 최종 답변의 주장마다 자료 유형을 연결한다. 숫자는 SQL 결과, 정책은 문서 절, 뉴스는 원문 URL, 운영 제안은 제품의 권고라는 식이다. 음성으로 보낸 경우에는 같은 내용의 텍스트 버전을 남기고 어떤 TTS 모델·언어를 썼는지 기록한다. 첫 음성의 시간뿐 아니라 실제 사용자가 들은 문장의 범위도 중요하다. 스트림이 중간에 끊겼다면 마지막으로 재생된 부분과 서버가 생성한 전체 답변이 다를 수 있다. 사용자가 ‘AI가 이렇게 말했다’고 신고했을 때 서버 로그의 전체 답변만 보면 실제 재생 내용을 놓칠 수 있다.

이 계보는 사고 대응뿐 아니라 품질 개선에 쓰인다. 최근 오답 20건을 보고 자료 선택 오류가 12건, SQL 의미 오류가 4건, 모델 요약 오류가 3건, 음성 낭독 오류가 1건이라면 최적화 순서가 명확해진다. 모든 오답을 모델 교체로 해결하려 하면 가장 큰 원인인 검색·자료 범위를 놓친다. 반대로 자료가 정확한데 요약이 계속 틀리면 그때 모델·지침·출력 검증을 개선한다. 요청 ID로 경로를 연결하면 팀 간 책임 전가보다 실제 수정으로 이어질 가능성이 커진다.

## 실무 설계 부록 2: 오류를 ‘문장’이 아니라 계층으로 분류

사용자가 잘못된 답변을 신고하면 운영자는 먼저 그 답이 **잘못된 사실을 읽었는지**, **올바른 사실을 잘못 계산했는지**, **올바른 계산을 잘못 설명했는지**, **권한이 없는 사실을 읽었는지**, **올바른 문장을 잘못 전달했는지** 구분한다. 이 분류는 기술팀의 편의를 위한 것이 아니라 사용자 피해를 줄인다. 원천이 오래되었다면 동일한 원천을 쓴 다른 답변도 확인해야 한다. 특정 모델의 설명 오류라면 그 지침 버전에만 영향이 있을 수 있다. 권한 오류라면 내용의 정확성과 무관하게 우선 차단해야 한다. 음성 전달 오류라면 텍스트는 맞아도 사용자는 다른 정보를 들었을 수 있다.

**원천 오류**의 예는 폐기된 정책을 현재 정책으로 인용하거나, 데이터셋에 아직 반영되지 않은 취소 건을 포함하는 것이다. 수정은 인덱스·ETL·문서 상태 관리에서 시작한다. 프롬프트에 ‘최신 자료를 사용해’라고 적어도 현재 유효한 문서가 인덱스에 없으면 해결되지 않는다. **의미 오류**는 `price`를 단가로 해석하거나, ‘현직원 수’의 범위를 잘못 잡는 것이다. 메타데이터·뷰·검증 쿼리를 고친다. **계산 오류**는 같은 정의를 알고도 조인 중복으로 수치를 부풀리거나 기간 필터를 잘못 쓰는 것이다. 실행된 SQL과 원장 결과를 대조한다.

**권한 오류**는 모델이 보여서는 안 되는 정보를 읽거나 쓰는 것이다. 실제 노출이 발생했다면 답변 품질과 별도로 사고 대응을 한다. OBO가 실패해 서비스 계정으로 내려가는 우회 경로, Gateway에서 대상 역할로 잘못 매핑, 데이터베이스 RLS 미적용 등이 원인일 수 있다. 권한 오류를 모델이 ‘민감한 내용입니다’라고 말해 숨기는 식으로 수습하면 안 된다. 먼저 자료 흐름을 끊고, 노출 범위를 조사하고, 정책을 검증한다. **서술 오류**는 원문이 ‘시범 운영’인데 답변이 ‘정식 출시’라고 단정하는 것이다. 원문과 최종 주장의 연결을 보면서 요약 지침과 검증 규칙을 개선한다.

**전달 오류**는 음성·화면에서 발생한다. TTS가 숫자를 잘못 읽거나, 화면 UI가 금액의 단위를 빼거나, 스트림이 끊겨 부정문 마지막을 사용자에게 전달하지 못할 수 있다. 모델의 출력 텍스트만 재검토하면 발견하기 어렵다. 중요 숫자와 단위는 구조화된 값에서 렌더링하고, 음성에는 날짜·금액 읽기 규칙을 적용할 수 있다. ‘승인하지 않습니다’가 재생 도중 ‘승인’에서 끊기는 위험을 줄이기 위해 중요한 부정은 앞쪽에도 명확히 배치할 수 있다. 이런 운영 설계는 모델의 문장 품질과 별도다.

분류표에 ‘원인 미확인’을 남길 용기도 필요하다. 그럴듯한 가설을 원인으로 확정하면 다음 수정이 잘못된다. 사고 초기에는 관찰 사실과 가설을 분리한다. 예를 들어 사용자에게 다른 팀의 자료가 보인 것은 사실이고, RLS가 원인이라는 것은 확인 전 가설이다. 에이전트 로그와 DB 역할, API의 실제 호출을 대조한 뒤 원인을 확정한다. 오늘 EDB와 OBO 글은 각기 다른 권한 계층을 다루므로, 한쪽을 확인했다는 이유로 전체 권한 경로가 안전하다고 판단하면 안 된다.

## 실무 설계 부록 3: 지표를 만들 때 분모를 고정하는 법

AI 제품 성과를 한 문장으로 말하려 하면 지표가 뒤섞인다. ‘90ms 음성’, ‘80% 비용 감소’, ‘3배 개발 속도’는 매력적이지만 단위가 다르다. 음성의 90ms는 특정 모델 경로의 첫 바이트 수치다. 80%는 고객의 캐싱을 포함한 비용 비교 발언이다. 3배는 고객 조직의 개발 생산성 자체 보고다. 이 셋을 ‘오늘 발표는 AI가 3배 빠르고 80% 저렴하다’고 요약하면 사실관계가 무너진다. 기사나 제품 제안서에서 숫자는 반드시 대상, 비교 기준, 측정 구간, 측정 주체를 붙여야 한다.

정형 질의의 품질 지표에는 `정답률`만으로 부족하다. 질문의 유형을 나누어 지표형 질문, 문서형 질문, 결합 질문, 권한 거부 질문을 각각 센다. ‘정답’의 정의도 숫자가 맞는 것인지, 출처가 맞는 것인지, 범위가 맞는 것인지 구분한다. 숫자는 맞았지만 다른 조직의 행을 조회했다면 성공이 아니다. 문서 인용이 맞았지만 구버전이면 실패다. 모델이 답을 보류했더라도 자료가 없고 보류가 옳았다면 좋은 결과다. 총 요청 수를 분모로 하면 이런 차이가 사라진다. 유형별로 정답·정당한 거부·잘못된 거부·근거 없는 답을 분리한다.

검색 품질에는 `recall`과 `precision`의 긴장이 있다. 중요한 공식 발표를 놓치지 않으려면 넓게 찾고 싶지만, 후보가 너무 많으면 검토 부담이 커진다. 자동 게시에 가까울수록 정밀도가 중요하고, 사람이 검토하는 연구용 큐에서는 더 넓은 발견율을 택할 수 있다. 추천 피드의 클릭률이 높아도 사실성이 낮으면 평판 위험이 증가한다. 신뢰도 평가에는 URL의 원문 확인율, 날짜 정확도, 주장·근거 일치율, 정정 대응 시간을 넣는다. 웹 검색 결과가 제공하는 발행일이 실제 원문 날짜와 다른 경우도 있으므로 표본 검사를 한다.

API 행동에는 `도구 호출 성공률`보다 `의도한 업무 결과가 정확히 한 번 반영된 비율`이 중요하다. 네트워크 타임아웃으로 클라이언트에는 실패처럼 보이지만 대상 서비스에 기록은 생성됐을 수 있다. 이를 재시도해 두 개의 티켓이 생기면 HTTP 성공률은 높아도 업무 품질은 낮다. 반대로 대상 API가 권한 때문에 호출을 거부했다면 보안 관점에서는 올바른 결과일 수 있다. ‘실패’로만 기록하면 정책을 완화하라는 잘못된 압력이 생긴다. 상태 변경의 정당성, 중복 여부, 사용자 확인과 감사 기록을 함께 본다.

음성 지표에는 **사용자 턴 기준**의 시간이 필요하다. 서버에 TTS 요청을 보낸 순간부터의 p50만으로는 발화 종료 판정과 검색 지연을 보지 못한다. 실제 앱에서 사용자의 발화 종료부터 첫 소리까지, 마지막 소리까지를 잰다. 언어·기기·네트워크·동시성별 p95를 구분한다. 음성 품질의 자동 점수가 좋아도 숫자 한 자리의 오류가 큰 업무라면 해당 필드를 따로 평가한다. 사용자에게는 느리지만 정확한 답변과 빠르지만 자주 잘못된 답변 중 어느 것이 가치 있는지 업무에 따라 다르다. 속도와 정확도를 하나의 점수로 섞지 않는다.

지역과 비용 지표는 특히 운영 환경에 민감하다. 지역 요건 준수율은 ‘설정 파일에 인도 프로필이 있다’가 아니라 실제 호출과 주변 저장 경로가 정책에 맞는지로 판단한다. 비용은 토큰당 단가가 아니라 성공한 업무 한 건당 총 비용으로 본다. 캐시 적중률이 떨어지는 날, 이미지 입력이 길어지는 문서, 실패 재시도가 많은 시간에는 비용이 달라진다. 고객이 밝힌 80% 절감은 우리 앱의 예산 계획이 아니라 검증할 가설이다. 같은 질문 세트와 같은 출력 기준으로 비교한 뒤에만 비용 절감을 말한다.

### ‘좋은 평균’이 숨기는 위험 사례

전체 정답률 95%는 낮은 위험의 쉬운 질문이 많으면 높게 나온다. 남은 5% 중 권한 위반, 급여 오답, 잘못된 결재가 하나라도 있다면 그대로 출시할 수 없다. 위험 유형은 절대 실패 수와 비율을 함께 본다. 전체 요청이 늘면 비율은 줄어도 피해 건수는 늘 수 있다. p95 지연도 중요한 지역·언어 사용자에게만 나쁘면 전체 평균이 가린다. 품질 보고서에는 큰 집단의 평균과 작은 고위험 집단의 최소 기준을 함께 둔다. ‘이번 주 평균이 좋아졌다’는 말은 변경된 부분의 회귀가 없는지 확인한 뒤에 의미가 있다.

## 실무 설계 부록 4: 하루치 뉴스 자동화 자체의 검증 원칙

오늘 이 글의 주제 가운데 하나가 검색 기반 뉴스 엔진이므로 발행 자동화의 기준도 공개한다. **오늘 날짜의 글인지**는 사이트 파일명과 KST 기준 시각으로 판단한다. UTC 11월 3일 늦은 오후에 공개된 AWS 글은 한국에서 11월 4일 새벽에 접할 수 있다. 기사 발행 시각을 한국 날짜로 옮겨 적되 원문 UTC도 남긴다. 오늘 읽었다는 사실을 오늘 공개되었다는 사실로 바꾸지 않는다. 어제 원문을 오늘 다시 심층 분석할 수는 있지만 그런 경우 ‘오늘의 해설 대상’이라고 명시해야 한다. 이번 호의 여섯 글은 실제로 KST 오늘 새벽에 공개됐다.

**출처 확인**은 검색 결과에서 끝나지 않는다. 오늘 공개 검색 API는 키가 없어 오류를 반환했다. 이때 작업을 중단하거나 검색에 대한 추측으로 기사를 채우지 않고, 공식 목록 페이지와 AWS RSS·원문을 확인했다. RSS의 게시 시각과 URL은 목록에 있고, `content:encoded`에는 본문이 있다. AWS HTML 페이지의 일반 추출기가 사이트 내비게이션만 보여 줄 수 있으므로 ‘URL이 200이었다’는 것만으로 기사 본문을 읽었다고 주장하지 않는다. 자료를 읽지 못했으면 그 항목을 기사에서 제외하거나 다른 공식 경로로 확인한다. 이 원칙은 특정 도구의 결함을 변명하기 위한 것이 아니라 정보의 근거 수준을 유지하기 위한 것이다.

**선정 기준**도 기사 건수를 위한 것이 아니다. 여섯 글 중 Amazon Quick, OBO, EDB, 음성, 지역 추론은 서로 다른 기술 층을 다루고, Norton 사례는 그 층들이 실제 서비스에서 어떻게 연결되는지 보여 준다. 한 공급자의 글이 많다고 AI 산업 전체의 중요한 뉴스가 그 회사에만 있다는 뜻은 아니다. 오늘 확인 가능한 새 공식 자료 중 깊이 있게 읽을 가치가 있는 글을 선택했다. 다른 회사의 공식 목록을 열어 보았지만 같은 기준 시각에 더 적합한 새 발표를 확인하지 못했다. ‘없었다’와 ‘내가 확인한 경로에서 찾지 못했다’는 다르므로 후자로 이해해야 한다.

**사실과 해석의 분리**는 문장 수준에서 지킨다. AWS가 설명한 기능은 원문 링크를 붙이고, 고객이 말한 수치는 고객 사례라고 밝힌다. 글에서 제시한 HR 워크플로, 권한 테스트, 지표, 릴리스 절차는 이 글의 분석이다. 공식 글에 등장하지 않는 성능 보증을 임의로 붙이지 않는다. 특히 ‘약 90ms’, ‘80%’, ‘85%’, ‘3배’ 같은 숫자는 가장 눈에 띄기 때문에 출처와 분모를 본문에서 반복해 확인한다. 공급자의 측정치가 유용할 수는 있지만 우리 환경의 사전 검증을 대신하지 않는다.

**중복과 정정**도 운영 기준이다. 같은 날 다른 일반 포스트가 있어도 AI Daily News는 별도의 카테고리와 permalink로 발행한다. 그러나 AI Daily News 파일이 이미 존재하면 새 글을 덮어쓰지 않는다. 이후 원문이 정정될 수 있으므로, 오보를 발견하면 조용히 문장을 바꾸기보다 정정 시각과 수정 내용을 표시하는 운영 절차가 필요하다. 오늘 기사에 대한 수정이 필요할 때는 어떤 주장과 링크가 달라졌는지 추적할 수 있어야 한다. 자동화의 ‘발행 성공’은 품질 관리의 끝이 아니라 시작이다.

## 실무 설계 부록 5: 여섯 기능을 결합할 때의 안전한 순서

처음부터 검색·SQL·OBO·음성·다지역 추론을 모두 한 에이전트에 연결하면 실패 원인을 식별하기 어렵다. 제품에서 정말 필요한 기능을 먼저 좁힌다. 정형 질문의 가치가 높다면 SQL 정의와 권한을 먼저 확립한다. 외부 변화 탐지가 핵심이라면 검색의 출처·발행일과 편집 검토를 먼저 만든다. 사용자를 대신한 쓰기 동작이 필요하다면 OBO와 대상 API의 정책 검증을 먼저 완성한다. 음성은 화면·텍스트 경로가 정확한 뒤에 더하는 편이 오류를 줄인다. 지역 요구가 강한 자료는 모델 선택 전에 데이터 흐름부터 정한다. 이 순서는 단순히 ‘조심하라’는 말이 아니라 각 단계의 합격 기준이 다음 단계의 입력이 되도록 하는 방법이다.

**1단계: 읽기 전용 질문**. 승인된 자료 한두 종류로 답을 만든다. 원문 인용과 숫자 재현이 가능해야 한다. 권한 밖의 질문을 거부할 수 있어야 한다. 실패하면 자료와 의미 정의를 고친다. 이때 음성이나 쓰기 API를 추가하지 않는다. 자연어 화면의 편리함만으로도 사용자가 가치를 느끼는지 살핀다. 이미 충분하다면 불필요한 기능을 더하지 않는다.

**2단계: 자료 결합**. 정형 지표와 문서 또는 외부 검색을 함께 사용한다. 기간·범위·진실 원천이 서로 맞는지 확인한다. 충돌하면 어떤 원천이 어느 주장에 쓰였는지 분리해 보여 준다. 질문 유형별 평가에서 결합 답변이 단일 원천 답변보다 실제로 도움이 되는지 본다. 결합으로 인해 근거 없는 인과 설명이 늘면 범위를 줄인다. ‘두 자료를 함께 봤다’가 제품 가치가 아니라 사용자 의사결정이 정확해졌는지가 가치다.

**3단계: 사용자 대리의 읽기**. 대상 API에서 사용자별로 허용된 기록을 가져온다. OBO나 동등한 신원 전달 패턴을 적용하되 대상 서비스의 권한 검사를 확인한다. 사용자 계정 두 개 이상의 긍정·부정 테스트를 수행한다. 권한이 바뀐 직후의 반영 지연도 본다. 읽기만 가능해도 개인정보 위험은 충분히 크다. 고권한 계정 하나로 모든 사용자를 처리하지 않는지 감사한다.

**4단계: 제한된 쓰기**. 영향이 낮고 쉽게 되돌릴 수 있는 동작부터 시작한다. 예를 들어 ‘본인 문의 티켓 초안 생성’을 허용하고, 급여 수정이나 인사 승인과 같은 고위험 동작은 보류한다. 실행 전 사용자에게 변경될 값을 보여 준다. 대상 서비스가 객체 권한과 상태를 재검사한다. idempotency key와 결과 재조회가 있어야 타임아웃 후 중복을 막을 수 있다. 실수 발생 시 어떻게 되돌리고 누구에게 알릴지도 정한다.

**5단계: 음성·다국어·지역 확장**. 이미 정확한 텍스트 경로를 음성으로 전달한다. 중요한 값의 낭독을 별도로 평가한다. 실제 모바일 네트워크와 동시성에서 지연을 측정한다. 지역별 데이터 흐름을 문서화하고, 허용된 프로필과 저장 경로를 배포 설정에 고정한다. 언어가 늘면 OCR·ASR·TTS·지표 번역을 각각 시험한다. ‘모델이 다국어를 지원한다’는 문장은 특정 국가의 문서와 업무 용어를 정확히 처리한다는 증거가 아니다.

이 단계들은 팀 규모에 따라 동시에 일부 진행할 수 있다. 그러나 사용자에게 영향을 주는 **합격 판단**은 각 경계마다 별도로 해야 한다. 읽기 품질이 불안정한데 쓰기만 안전하다고 할 수 없고, 사용자 권한이 검증되지 않았는데 음성 UI를 잘 만들어도 출시할 수 없다. 반대로 음성이 늦다는 이유로 정확한 텍스트 검색 기능 전체를 보류할 필요도 없다. 기능을 분리해 출시할 수 있는 아키텍처가 의사결정의 폭을 넓힌다.

## 실무 설계 부록 6: 프로덕션 장애 초동 대응 카드

### 증상: ‘정책 답변이 틀립니다’

먼저 사용자가 본 질문·답변의 요청 ID와 기준 시각을 확인한다. 답변이 인용한 문서의 버전과 시행일을 본다. 문서가 현행인데 모델이 잘못 요약했는지, 폐기된 문서가 검색됐는지 나눈다. 전자라면 원문 문장과 출력 문장의 차이를 재현하고 요약·검증 경로를 고친다. 후자라면 해당 문서를 현재 답변 인덱스에서 제외하고 같은 문서를 인용한 최근 답변의 범위를 확인한다. 정책은 실제 업무 결정을 바꿀 수 있으므로 필요한 경우 담당자가 사용자에게 정정 정보를 제공한다. 뉴스의 외부 검색 결과가 내부 정책 답변에 혼입되었다면 원천 우선순위도 재검토한다.

### 증상: ‘다른 사람의 정보가 보입니다’

답변의 정확성 조사보다 먼저 관련 도구와 접근 경로를 제한한다. 사용자의 로그인 주체, Gateway의 대리 신원, 대상 API의 사용자 매핑, DB 역할, 검색 인덱스 권한을 차례로 확인한다. 모델에 이미 민감 자료가 전달됐는지와 실제 사용자에게 표시됐는지는 별개로 기록한다. 서비스 계정 우회, 넓은 `GRANT`, 누락된 RLS, 잘못된 문서 ACL 중 어느 층인지 찾아 수정한다. 토큰이나 개인 자료를 사고 채팅방에 그대로 복사하지 않는다. 영향 받은 사용자와 자료 범위를 복원하고 내부 절차에 따른 통지를 검토한다. 프롬프트 수정만으로 사고를 종료하지 않는다.

### 증상: ‘티켓을 두 번 만들었습니다’

클라이언트의 타임아웃 또는 재시도 기록과 대상 서비스의 두 생성 이벤트를 대조한다. 각 호출의 요청 ID와 idempotency key가 같은지 본다. 첫 응답이 유실되었는데 에이전트가 성공을 모르고 다시 호출했는지, 사용자 발화가 두 번 전사됐는지, 도구 실행 정책이 두 번 작동했는지 나눈다. 사용자에게 두 건의 상태를 명확히 알리고, 업무상 안전하게 취소할 수 있는 중복 건만 취소한다. 재발 방지는 단순히 재시도를 끄는 것보다 대상의 정확히 한 번 처리 또는 중복 감지와 결과 재조회다. 사용자 확인이 한 번이었는지도 조사한다.

### 증상: ‘뉴스에 이미 철회된 발표가 실렸습니다’

검색 당시 원문과 수정·철회 시각을 비교한다. 검색 스니펫만 읽고 게시했는지, 원문을 열었지만 수정 상태를 놓쳤는지 구분한다. 게시물의 주요 주장과 인용 링크를 찾아 정정 범위를 정한다. 운영 중인 자동 뉴스 피드에서는 같은 URL 또는 같은 발표를 인용한 다른 초안도 확인한다. 앞으로는 원문 확인 시각, 게시 직전 재확인, 공식 정정 신호를 처리할 수 있게 한다. 검색 API가 최신 결과를 돌려주더라도 기사 내용이 이후 바뀔 수 있다는 점을 인정해야 한다. 잘못된 내용을 지운 사실만 남기면 독자가 왜 달라졌는지 이해할 수 없으므로 정정 기록이 필요하다.

### 증상: ‘음성 답변이 숫자를 다르게 말했습니다’

화면의 텍스트, 모델 출력, TTS 입력, 실제 재생 오디오를 순서대로 비교한다. 모델이 이미 숫자를 틀렸다면 데이터·계산·요약 단계 문제다. TTS 입력은 맞는데 오디오가 틀렸다면 음성 합성 또는 숫자 발음 규칙 문제다. 사용자 단말에서 재생이 끊긴 경우에는 스트리밍·네트워크 문제다. 데이터값을 자연어 문장에만 묻어 두지 말고 구조화된 값으로 유지하면 대조가 쉬워진다. 금액·날짜·이름은 언어별 테스트 샘플로 반복 확인한다. 민감하거나 행동을 유발하는 숫자는 화면에도 보이게 하고 사용자 확인을 받는다.

### 증상: ‘지역 정책 때문에 모델 호출이 막혔습니다’

프로필 ID, source Region, destination 허용 목록, IAM·SCP 거부 이벤트를 확인한다. 신규 리전 또는 모델 버전 변경이 있었는지 본다. 정책을 맞추려고 글로벌 프로필로 임시 변경하기 전에 입력 데이터의 지역 요구를 확인한다. 공개 자료라면 허용된 다른 경로가 있을 수 있지만, 민감 자료는 보류가 안전한 결과일 수 있다. 오류 메시지는 사용자에게 내부 ARN을 그대로 노출하지 않으면서 ‘현재 이 자료는 허용된 지역에서 처리할 수 없어 보류했다’고 설명할 수 있어야 한다. 운영팀에는 어떤 정책이 어떤 리전을 막았는지 충분한 기록이 필요하다.

## 의사결정 회의용 질문: 도입 이전에 답해야 할 스무 가지

1. 사용자가 실제로 해결하려는 질문은 무엇이며, 현재 시스템에서 그 질문이 왜 어려운가?
2. 답에 필요한 정형 데이터와 문서, 외부 정보의 각각의 진실 원천은 어디인가?
3. 숫자의 분모·분자·기간·시간대와 문서의 시행일이 명확한가?
4. 같은 질문에 두 원천이 다른 답을 줄 때 누가 결정하는가?
5. 사용자의 권한을 어디에서 확인하고 어느 대상 서비스까지 전달하는가?
6. 에이전트가 호출할 도구는 사용자의 최대 권한보다 더 좁게 제한되는가?
7. 사용자 확인 없이 상태를 바꾸는 도구가 있는가? 있다면 왜 필요한가?
8. 도구 호출이 타임아웃될 때 중복 실행을 어떻게 확인하고 막는가?
9. 검색 결과의 제목·발행일·URL을 원문과 대조하는 단계가 있는가?
10. 공급자의 고객 사례 수치를 우리 환경의 예상 성과로 오해하지 않게 표시하는가?
11. 비즈니스 용어가 테이블·뷰·메타데이터 어디에 정의되어 있고 누가 갱신하는가?
12. 모델이 금지된 SQL을 생성해도 DB가 민감한 행·열을 거부하는가?
13. 답변의 각 주장에 원천과 기준 시각을 연결할 수 있는가?
14. 사용자 발화 종료부터 음성 첫 재생까지의 실제 p95는 얼마인가?
15. TTS 첫 바이트 수치와 전체 턴 시간을 별도로 보고하는가?
16. Sonic 자체 호스팅과 Ink API처럼 서로 다른 음성 경로의 데이터 처리를 구분했는가?
17. 모델 호출의 source와 destination, 로그·백업의 위치를 모두 확인했는가?
18. 캐싱·이미지 입력·재시도·사람 검토를 포함한 성공 건당 비용을 계산했는가?
19. 근거 부족, 권한 거부, 서비스 장애를 사용자에게 다른 결과로 설명하는가?
20. 출시 후 틀린 답을 발견하면 어떤 요청과 자료를 찾아 정정할 수 있는가?

이 질문의 목적은 회의 시간을 늘리는 것이 아니다. 대답하지 못하는 항목이 있으면 기능의 출시 범위를 좁히거나 검증 순서를 바꿀 수 있다. 예를 들어 원천 정의가 없으면 자연어→SQL 모델 비교보다 데이터 계약이 먼저다. 권한을 증명할 수 없으면 쓰기 도구 연결보다 신원 매핑이 먼저다. 지역 경로를 확인할 수 없으면 민감 문서 OCR보다 공개 합성 자료 실험이 먼저다. 지표의 분모가 정해지지 않았으면 공급자 수치를 목표로 삼지 않는다. 미정 항목을 명시하면 도입을 막는 것이 아니라 가장 작은 유효한 실험을 선택할 수 있다.

## 맺음말: 발표를 운영 가능한 계약으로 번역한다

Amazon Quick은 여러 자료를 한 화면에서 질문하는 가능성을 보여 준다. OBO 구성은 사용자 신원을 도구 호출의 끝까지 이어 가는 방법을 보여 준다. Norton Revamp는 오늘의 외부 사실을 콘텐츠 생성에 연결하는 사례다. EDB SemKB는 비즈니스 의미와 데이터 권한을 데이터베이스 쪽에 배치한다. Cartesia 글은 음성의 체감 지연이 여러 구간으로 구성됨을 상기시킨다. Kimi K3의 인도 프로필은 모델 호출의 위치 정책을 명시적으로 선택하게 한다. 이 중 어떤 것이 우리 제품에 필요한지는 사용자의 문제와 데이터의 위험, 팀의 운영 역량에 따라 다르다.

여섯 발표를 ‘에이전트가 더 많은 일을 할 수 있다’는 문장으로 끝내면 가장 중요한 내용을 놓친다. 더 많은 일을 맡길수록 **자료의 의미와 날짜**, **누구의 권한인지**, **주장의 출처**, **성능 숫자의 분모**, **실제 처리 지역**, **장애 시 책임자**가 선명해야 한다. 제품 설계의 성숙도는 모델이 몇 가지 도구를 부를 수 있는지가 아니라, 사용자가 받은 한 문장의 출처와 한 번의 상태 변경의 정당성을 나중에도 설명할 수 있는지로 드러난다. 오늘 확인한 공식 글의 가치도 새 기능의 목록보다 이 책임 경계를 구체적으로 설계할 단서를 준다는 데 있다.

## 독자 질문 12개로 다시 검증하는 오늘의 여섯 소식

### 1. Amazon Quick에 문서와 CSV를 넣으면 같은 질문의 모순을 자동 해결하나?

아니다. 원문 예제는 S3 문서형 지식베이스와 보강된 데이터세트를 Space에 연결해 한 채팅에서 질문하는 경로를 보여 준다. 두 원천의 정의와 기간이 일치하는지 판단하는 업무 규칙은 별도다. 데이터세트의 수치는 현재 분기이고 문서는 지난 분기 리뷰라면 둘을 한 원인·결과 문장으로 묶으면 안 된다. 문서가 확정본인지 초안인지도 확인해야 한다. 먼저 각 원천에 `기준일`, `적용 기간`, `조직 범위`를 붙이고, 결합 가능한 경우에만 계산·설명을 연결한다. 범위가 다르면 사용자에게 그 차이를 보여 주는 것이 자동 결합보다 정확한 서비스다.

### 2. 정형 데이터 설명을 모델의 시스템 프롬프트에만 쓰면 충분한가?

작은 시범에서는 가능할 수 있지만 장기 운영에는 위험하다. 데이터셋의 열 정의가 바뀌면 프롬프트와 실제 스키마가 어긋나기 쉽다. 여러 에이전트가 같은 데이터를 쓰면 각각의 프롬프트에 정의를 복사해야 한다. Amazon Quick의 데이터 보강과 EDB의 SemKB는 의미를 데이터에 가까운 계층에서 제공하는 서로 다른 접근이다. 그러나 그 계층도 자동으로 옳아지지 않는다. 담당자가 계산식과 예외를 검토하고, 데이터 변경과 함께 버전 관리해야 한다. 프롬프트는 어떤 업무 질문을 풀지 안내하고, 데이터 정의는 재사용 가능한 진실 원천으로 관리하는 편이 낫다.

### 3. OBO 토큰 교환을 했으면 에이전트가 사용자 대신 모든 작업을 해도 되나?

아니다. OBO는 사용자 신원을 보존한 대상용 토큰을 얻는 패턴이다. 작업 권한은 대상 서비스가 적용하고, 제품은 에이전트가 제공할 도구 범위를 더 좁힐 수 있다. 사용자가 ServiceNow에서 직접 수행할 수 있는 작업이라도 에이전트에게 자동 실행을 허용하지 않을 수 있다. 예를 들어 읽기나 초안 생성은 허용하고, 삭제·승인은 사용자 확인이 필요한 단계로 둘 수 있다. 토큰 교환이 안전하려면 Entra의 위임 범위, Gateway의 도구 범위, ServiceNow의 객체 권한, 업무 상태 검사가 모두 맞아야 한다. 어느 한 단계의 성공만으로 전체를 증명할 수 없다.

### 4. 사용자 대신 처리한 작업의 감사를 어떻게 남기나?

사람이 UI에서 요청한 시각과 내용, 에이전트가 선택한 도구, Gateway가 대상에 전달한 신원, 대상 서비스의 상태 변경을 하나의 요청 ID로 연결한다. 토큰 원문을 저장할 필요는 없다. 오히려 저장하면 비밀 유출 위험이 커진다. 대상 서비스의 감사 이벤트 ID와 결과 객체 ID, 실행 전후 상태를 남기는 편이 유용하다. 네트워크 오류 때문에 사용자에게 실패처럼 보였지만 실제로 티켓이 생성된 경우도 있으므로 결과 재조회가 필요하다. ‘누가 요청했는가’뿐 아니라 ‘어떤 내용을 확인하고 어떤 변경을 승인했는가’를 복원해야 진정한 감사 기록이 된다.

### 5. AgentCore Web Search가 URL과 날짜를 주면 뉴스 게시에 충분한가?

검색 결과는 원문을 찾는 출발점이다. 제목, 스니펫, 발행일은 유용하지만 기사 본문의 조건과 한계를 모두 담지 않는다. 페이지가 이후 수정될 수도 있다. 특히 모델 발표의 벤치마크, 파트너 사례의 비용 절감, 정책·규제 정보는 원문과 기준 시각을 확인해야 한다. Gen Digital의 뉴스 엔진은 검색 결과를 순위화하고 콘텐츠 제안에 쓰는 사례이지, 검색 결과를 무검토로 외부 게시해도 된다는 증거가 아니다. 게시 전에는 핵심 주장별 근거, 원문 날짜, ‘출시’와 ‘예고’의 차이를 확인한다. 검색 공급자의 실시간성은 편집자의 사실 확인을 대체하지 않는다.

### 6. 검색 API가 실패하면 뉴스 자동화는 어떻게 해야 하나?

공식 발행 인덱스와 RSS가 있다면 그 경로를 먼저 확인한다. 오늘처럼 검색 API 키가 없어 실패했을 때에도 OpenAI·Google·GitHub·Microsoft 공식 목록과 AWS 공식 RSS, 개별 원문을 확인할 수 있다. 자료가 충분하지 않다면 과거 기사를 새 발표처럼 채우지 않고 발행을 보류해야 한다. 공식 RSS에서 발행일과 URL을 얻었더라도 본문을 실제로 읽었는지 확인해야 한다. 웹 페이지 추출기가 내비게이션만 반환하는 경우가 있기 때문이다. 이 방법은 검색 API의 기능을 모두 대체하지는 않는다. 하지만 근거 있는 기사를 만드는 최소 경로는 유지할 수 있다.

### 7. Postgres `COMMENT`만 잘 쓰면 에이전트 SQL은 안전한가?

아니다. 주석은 열과 뷰의 의미를 모델에 전달하는 데 도움을 주지만, 실행 권한과 쿼리 비용을 제한하지 않는다. DB 역할별 `GRANT`, 행 수준 보안, 허용된 스키마, 읽기 전용 실행, 시간 제한이 필요하다. 주석이 정확해도 데이터 자체가 잘못 적재되어 있으면 답이 틀린다. `price`가 단가가 아니라 주문 총액이라는 설명은 원문의 오답 사례를 막는 중요한 힌트지만, 다른 필드의 예외와 환불 처리는 여전히 정의해야 한다. 의미 계층은 보안 정책과 검증 쿼리, 변경 관리와 함께 작동할 때 운영 가능한 계층이 된다.

### 8. 같은 질문을 다른 직원이 했는데 다른 숫자가 나오면 버그인가?

반드시 그렇지는 않다. 행 수준 보안으로 사용자가 볼 수 있는 데이터 범위가 다르면 같은 질문에도 다른 결과가 나올 수 있다. 문제는 답변이 그 범위를 설명하지 않을 때다. ‘조회 가능한 조직 범위에서 3명’이라는 문장은 ‘회사 전체 3명’과 다르다. 반대로 권한 차이가 없는데 다른 숫자가 나온다면 데이터 갱신 시각, 정의 버전, 필터, 모델의 SQL 선택을 조사해야 한다. 제품 테스트에서는 두 사용자의 기대 범위를 먼저 정하고, 결과뿐 아니라 SQL이 접근한 원천을 확인한다. 낮은 권한 계정으로 전체 수치가 나왔다면 우연히 맞았더라도 데이터 누출 가능성을 조사한다.

### 9. Sonic의 약 90ms가 사용자 대화에서도 그대로 나올까?

그렇게 해석하면 안 된다. 글의 수치는 Sonic의 음성 생성에서 첫 바이트에 관한 소개다. 사용자의 발화 종료 감지, 전사, 검색, LLM 문장 생성, 네트워크 전송, 재생 버퍼가 추가된다. 실제 사용자 경험은 발화 종료에서 첫 소리가 들리는 시간과 답변 완료까지의 시간으로 측정해야 한다. 공급자 수치는 기술 선택의 후보를 좁히는 데 유용하지만, 앱의 SLA는 실제 장치와 네트워크, 동시성에서 측정해야 한다. Sonic을 고객 VPC에 호스팅하는 경우에도 GPU 큐와 엔드포인트 용량이 성능을 바꿀 수 있다. Ink의 경로는 별도로 검토해야 한다.

### 10. 음성에 부분 전사를 쓰면 언제나 더 나은가?

부분 전사는 앞단 지연을 줄일 여지가 있지만 아직 확정되지 않은 발화를 잘못 해석할 수 있다. 사용자 의도가 바뀌거나 날짜·금액이 수정될 수 있다. 정보 검색의 준비 단계에는 부분 전사를 쓸 수 있지만, 실제 결재나 기록 변경은 최종 전사와 확인을 기다리는 편이 낫다. 부분 전사로 시작한 검색도 확정 발화가 달라지면 결과를 폐기해야 한다. 빠른 음성 제품은 ‘무조건 일찍 실행’하는 제품이 아니라 일찍 준비해도 안전한 단계와 확정을 기다려야 하는 단계를 구분한 제품이다. 이 구분이 없다면 속도 향상이 잘못된 행동을 앞당긴다.

### 11. 인도 프로필을 선택하면 데이터 거주성 검토가 끝나나?

끝나지 않는다. `in.moonshotai.kimi-k3`는 원문이 설명하는 인도 내 추론 처리 옵션이다. 그러나 애플리케이션의 입력 파일, 검색 인덱스, 결과 저장, 로그, 백업이 어디에 있는지 별도로 확인해야 한다. 호출 source Region과 처리 destination Region도 다르다. IAM·SCP가 실제로 허용하는 지역, 장애 시 폴백, 공급자 계약도 함께 봐야 한다. 인도 지역 프로필이 있다고 해서 다른 국가에서 동일한 프로필이 제공된다고 추론해서도 안 된다. 데이터 거주성은 모델 ID 한 개가 아니라 전체 파이프라인의 속성이다.

### 12. Kimi K3가 합성 힌디어 청구서를 읽었다면 실제 KYC 자동 승인에 써도 되나?

아니다. 합성 청구서의 OCR·정형 추출 예제는 API 사용법과 가능성을 보여 준다. 실제 KYC 자료는 스캔 품질, 표기, 언어, 위조, 누락 필드, 개인정보 처리 요구가 다르다. 정형 JSON 스키마를 만족해도 필드 값이 틀릴 수 있다. 실제 문서 유형별 필드 정확도, 실패 시 보류, 사람 검토, 원본 대조를 시험해야 한다. 자동 승인까지 고려한다면 문서 진위와 신원 매칭, 정책 판단을 별도의 시스템에서 검증해야 한다. 모델의 텍스트 추출 능력과 금융·행정상의 승인 책임은 같은 단계가 아니다.

## 마지막 운영 메모: 내일 바뀔 수 있는 것과 오래 유지될 원칙

내일 다시 확인해야 할 것은 구체적인 모델 가용 리전, 서비스 티어 가격, 파트너 모델 패키지 버전, 고객 서비스의 숫자, 공식 원문의 정정 여부다. 이런 정보는 시간이 지나면 바뀐다. 반면 원천의 뜻을 밝히고, 사용자의 권한을 끝까지 보존하고, 각 주장에 근거를 연결하고, 지연을 사용자 경험 기준으로 재며, 데이터의 전체 경로를 확인하는 원칙은 쉽게 바뀌지 않는다. 오늘 기사의 링크는 발표 시점의 증거이며, 도입 시에는 공식 제품 문서와 실제 계정의 가용성을 다시 확인해야 한다.

결국 에이전트 제품의 성패는 ‘모델이 자연어를 얼마나 잘 이해하는가’만으로 결정되지 않는다. 모델이 읽을 수 있는 자료의 품질, 도구가 허용하는 행동의 경계, 사용자의 의도를 확정하는 방식, 결과를 확인하고 되돌리는 운영 절차가 함께 만든다. 여섯 편의 공식 글은 이 복합적인 설계 공간을 다른 각도에서 보여 준다. Amazon Quick의 결합, OBO의 위임, Web Search의 최신성, SemKB의 의미, 음성의 시간, 지역 추론의 위치는 각각 독립된 도구가 아니라 **사용자에게 신뢰 가능한 한 번의 경험을 제공하기 위해 맞춰야 할 계약**이다.

## 실행 가능한 결론: 팀별로 누구에게 무엇을 맡길 것인가

**데이터 담당자**는 지표와 문서의 내용이 무엇을 뜻하는지 책임진다. 정형 테이블의 열 설명, 계산식, 문서의 시행일, 누가 수정할 수 있는지를 정한다. 에이전트가 틀린 숫자를 반복할 때 데이터 담당자가 원천과 정의를 확인할 수 있어야 한다. 데이터셋을 바꾸면서 의미 설명을 그대로 두면 에이전트만이 아니라 대시보드와 보고서도 틀릴 수 있다. 따라서 의미 계층의 변경은 단순한 AI 설정 변경이 아니라 조직의 지표 변경으로 다룬다. 오늘 Amazon Quick과 EDB 글이 서로 다른 제품을 다루더라도 둘 다 이 책임을 보여 준다.

**보안·신원 담당자**는 사용자 인증, 위임 동의, 대상 토큰의 audience·scope, 계정 매핑, 퇴사·이동 반영 시점을 책임진다. ‘서비스 계정으로 동작하지만 화면에는 사용자 이름을 표시한다’는 방식은 감사와 접근 제어를 혼동한다. OBO는 신원 보존의 기술적 연결고리를 제공하지만 대상 서비스의 업무 권한을 대신하지 않는다. 실제 API 호출이 어떤 사용자로 기록되는지 확인해야 한다. 관리자 역할을 가진 사람이 에이전트에게 모든 관리자 기능을 위임해야 하는 것도 아니다. 도구의 허용 범위는 제품과 보안팀이 협의해 좁게 설계할 수 있다.

**제품·편집 담당자**는 외부 검색 결과를 사용자가 신뢰할 수 있는 문장으로 바꾸는 책임을 가진다. 검색 엔진은 최신 후보를 제공하고, 모델은 읽기 쉬운 제안을 만들 수 있다. 하지만 기사 원문이 실험을 설명하는데 게시물은 정식 출시라고 쓰면 최종 서비스가 잘못한 것이다. 뉴스처럼 시점이 중요한 콘텐츠에서는 원문 발행일, 현지 날짜, 정정 여부를 보여 준다. 사용자의 이름으로 나가는 게시물은 검토 가능성을 우선한다. 추천 클릭률이 높아도 정정률이 높다면 좋은 제품이 아니다. Norton 사례의 실제 서비스 성과를 검토할 때도 뉴스 품질을 개발 속도와 분리해 봐야 한다.

**플랫폼 담당자**는 도구의 신뢰 가능한 실행을 책임진다. 요청 ID, 시간 제한, 재시도, 중복 방지, 관측성, 롤백이 없다면 에이전트가 실제 업무를 바꿀 때 문제가 생긴다. SQL의 읽기 제한, API의 idempotency key, 음성 스트림의 중단 상태, 추론 프로필의 구성 검증은 모델의 프롬프트 밖에서 수행된다. 플랫폼의 책임은 AI를 막는 것이 아니라 AI가 유용하게 일할 수 있는 안전한 실행 표면을 제공하는 것이다. 애매한 오류를 모두 사용자에게 ‘다시 시도하세요’라고 말하는 제품은 운영자가 고칠 단서를 잃는다.

**고객 지원·운영 담당자**는 사용자가 실제로 받은 결과를 이해하고 정정할 수 있어야 한다. 화면 텍스트와 음성 재생이 달랐다면 어느 쪽을 사용자가 들었는지 확인한다. 문서가 수정되었다면 어떤 답변이 영향을 받았는지 추적한다. 권한 오류로 잘못된 정보가 보였다면 모델 품질 이슈가 아닌 보안 사고로 취급한다. 사용자가 원하는 것은 복잡한 내부 구조의 설명이 아니라 자신의 문제와 해결 상태다. 다만 운영자에게는 충분히 구체적인 오류 분류와 요청 계보가 필요하다. 사용자에게 간결하게 말하려면 내부에는 오히려 명확한 기록이 있어야 한다.

### 작은 팀이라면 역할을 합쳐도 책임은 분리한다

스타트업이나 개인 프로젝트에서는 한 사람이 데이터·보안·제품·플랫폼을 모두 맡을 수 있다. 그렇다고 판단 기준까지 합치면 안 된다. 한 번의 코드 리뷰에서도 ‘이 수치의 정의는 맞나’, ‘이 사용자가 읽어도 되나’, ‘도구가 두 번 실행되면 어떻게 되나’, ‘문서 출처와 날짜가 맞나’, ‘데이터가 어느 지역에 저장되나’를 별도로 확인할 수 있다. 역할 분리는 반드시 조직도를 늘리라는 말이 아니다. 실패 원인의 층을 구분하고, 문제를 고칠 순서를 정하자는 뜻이다. 오늘의 발표는 여러 업체의 제품이 서로 다른 층을 맡는다는 점에서 이 분리의 필요성을 잘 보여 준다.

## 최종 확인표: 이 기사에서 단정하지 않은 것

- Amazon Quick 예제가 모든 조직의 정형·비정형 데이터 충돌을 자동으로 해결한다고 주장하지 않았다. 예제의 샘플과 구독 조건, 실제 데이터 정의의 차이를 분리했다.
- OBO 토큰 교환이 대상 서비스의 권한 검사나 사용자 확인을 대체한다고 주장하지 않았다. 사용자 신원 보존과 업무 승인 사이의 경계를 설명했다.
- AgentCore Web Search의 검색 결과가 곧 사실 검증이라고 주장하지 않았다. 검색·원문 확인·게시 전 검토를 다른 단계로 다뤘다.
- EDB의 스키마 주석이나 MCP 연결만으로 SQL이 정확하거나 안전하다고 주장하지 않았다. 계산 정의·DB 역할·쿼리 제한·추적을 추가로 검토했다.
- Sonic의 첫 바이트 수치를 전체 음성 대화의 지연이라고 주장하지 않았다. Ink와 Sonic의 배포 경로도 합치지 않았다.
- 인도 추론 프로필을 모든 데이터의 인도 내 저장 보장이라고 주장하지 않았다. 처리 목적지와 주변 저장·로그의 지역을 나누었다.
- 고객이 말한 비용 80%, 속도 85%, 개발 3배 향상을 다른 서비스의 예상 성과로 옮기지 않았다. 각각의 비교 조건을 검증할 가설로만 다뤘다.

이 구분은 형식적인 면책 문구가 아니다. 기술 발표를 제품 결정으로 옮길 때 가장 자주 발생하는 오류를 막기 위한 작업이다. 공식 글에서 확인 가능한 사실을 출발점으로 삼되, 우리 제품에 필요한 성능·정확성·권한·지역 정책은 우리 환경에서 검증해야 한다. 사용자가 ‘AI가 알아서 할 것’이라고 기대하는 순간일수록 개발자는 어떤 부분을 시스템이 확실히 알고, 어떤 부분은 아직 검증되지 않았는지 보여 줄 수 있어야 한다. 그것이 모델의 유용함을 오래 유지하는 방법이다.

## 검증용 사례집: ‘그럴듯한 데모’가 실패하는 순간

### 사례 A — 숫자는 맞는데 설명이 틀린 경영 보고

에이전트가 매출 데이터셋에서 10월 성장률을 정확히 계산했다. 같은 답변에서 S3 사업 보고서의 ‘하반기 신규 캠페인이 성장을 이끌었다’는 문장도 인용했다. 그런데 그 보고서는 8월에 작성한 계획 문서였다. 성장률 계산은 사실이고, 캠페인이 원인이라는 설명은 확인되지 않은 가설이다. 두 출처를 같은 답변에 넣었다는 이유만으로 인과가 성립하지 않는다. 이런 사례에서는 데이터셋 계산식과 문서의 작성·승인·적용일을 함께 본다. 자료 결합 기능의 성공은 두 결과를 이어 붙이는 것이 아니라 **각 주장이 어느 수준의 증거를 갖는지 유지하는 것**이다.

수정은 두 방향이다. 제품 화면은 숫자와 해석을 다른 블록으로 표시하고, 해석에는 ‘보고서의 예측’ 또는 ‘확인된 원인’ 같은 라벨을 붙인다. 데이터 운영은 문서 상태 메타데이터를 인덱싱하고, 아직 확정되지 않은 계획은 현재 실적의 원인 근거로 쓰지 않는다. 평가 질문에는 일부러 시점이 다른 문서를 넣는다. 에이전트가 두 자료를 발견했더라도 기간이 맞지 않으면 합성을 보류하는지 확인한다. 단순한 정답률보다 이런 충돌 처리 능력이 실제 경영 보고의 신뢰를 좌우한다.

### 사례 B — 사용자는 올바른데 대상 계정이 틀린 승인 요청

직원이 에이전트에 정상 로그인했고, Gateway의 OBO 교환도 성공했다. 하지만 대상 서비스에서는 이메일 주소가 같은 과거 계정과 현재 계정이 섞여 다른 사용자의 권한으로 매핑됐다. 토큰 발급 성공은 신원 연결 전체의 성공이 아니다. 이런 오류가 생기면 사용자에게는 ‘승인 완료’가 보이고 실제 대상 서비스에는 다른 계정의 감사 기록이 남을 수 있다. 복구를 위해서는 Entra의 안정 식별자와 대상 서비스 사용자 ID의 매핑, 계정 활성 상태, 중복 이메일 정책을 확인해야 한다. 화면 이름이나 이메일 문자열이 같다는 이유로 동일 인물이라고 단정하지 않는다.

사전 테스트에는 퇴사 후 재입사, 이메일 변경, 외부 협력사 전환, 조직 변경을 포함한다. 쓰기 호출에서는 실행 전에 대상 서비스가 해석한 사용자 식별자를 비민감 형태로 확인하고, 해당 객체에 대한 현재 업무 권한을 다시 평가한다. 에이전트가 사용자의 요청을 정확히 이해해도 신원 매핑이 틀리면 결과는 위험하다. 그래서 OBO의 목적은 단순히 토큰을 얻는 것이 아니라 사용자 주체를 요청 경로 전체에서 보존하는 것이다.

### 사례 C — 검색은 최신인데 원문이 정정된 뉴스 추천

뉴스 엔진이 오늘 발행일의 기사를 찾았고 콘텐츠 초안을 만들었다. 몇 시간 뒤 출처가 핵심 수치를 수정했다. 검색 결과의 발행일은 여전히 오늘이고 URL도 같다. 발행일과 URL만 저장한 초안은 수정 내용을 자동으로 알기 어렵다. 게시 전 원문을 다시 열어 주요 주장이 유지되는지 확인해야 한다. 이미 게시됐다면 수정 사실을 확인하고 정정할지 결정해야 한다. ‘실시간 검색’은 자료를 빨리 찾는 능력이지 자료가 영원히 변하지 않는다는 보증이 아니다. 검색의 유효기간과 게시 전 재확인이 콘텐츠 운영 설계에 들어가야 한다.

이 사례는 AI Daily News에도 그대로 적용된다. 기사 작성 시 확인한 시각과 게시 시각이 다를 수 있다. 공급자가 보도자료를 수정하거나 모델 지원 지역을 바꾸면 이전 문장이 낡는다. 자동화가 매일 새 글을 쓰는 것과 이전 글의 정정 필요성을 감지하는 것은 다른 작업이다. 적어도 중요한 수치와 제품 가용성은 출처 링크를 유지하고, 정정이 발견되면 독자가 변경을 볼 수 있게 해야 한다. 높은 발행 빈도가 정확성 검토의 면제가 되지는 않는다.

### 사례 D — 정답 SQL이지만 데이터 권한이 틀린 보고

모델이 고객 지출 상위 10명을 계산하는 SQL을 정확히 생성했다. 그러나 실행 계정이 모든 고객 행에 접근할 수 있는 고권한 서비스 계정이었다. 일반 사용자에게 결과를 그대로 보여 주면 숫자의 정확성은 보호가 아니다. DB 역할과 RLS가 적용된 계정으로 실행하고, 허용 범위가 제한된 경우 답변에도 그 범위를 표시해야 한다. DB가 403에 해당하는 거부를 했는데 모델이 이전 대화의 숫자로 답하는 것도 실패다. 에이전트 평가에서 ‘정답’은 계산의 일치뿐 아니라 **허용된 자료로부터 나온 결과인가**까지 포함해야 한다.

원문의 EDB 예제는 역할별 결과 차이를 보여 준다. 실무에서는 역할 정책이 바뀔 때 평가를 다시 실행해야 한다. 부서별 접근이 바뀌거나 소속 이력이 정리되면 어제 허용된 행이 오늘 거부될 수 있다. 캐시된 답변이 과거 권한의 결과를 계속 보여 주지 않도록 캐시 키에도 사용자 범위 또는 권한 버전을 반영해야 한다. 의미 계층과 권한 계층이 모두 올바르게 작동해도 캐시 계층이 이를 우회할 수 있다. 데이터 경계는 쿼리 실행 시점뿐 아니라 결과 재사용 시점에도 적용된다.

### 사례 E — 첫 바이트는 빠르지만 고객은 오래 기다리는 음성 상담

TTS 엔드포인트의 자체 계측은 첫 바이트 90ms 안팎이다. 사용자는 답이 시작될 때까지 몇 초를 기다린다. 조사해 보니 문제는 VAD가 발화 종료를 늦게 판단하고, 검색 도구의 p95가 높으며, 모바일 재생 버퍼가 길게 설정되어 있었다. TTS 모델을 더 빠른 것으로 바꾸어도 체감 개선은 작다. 종단 간 계측이 없으면 가장 눈에 띄는 공급자 수치만 최적화하게 된다. 요청마다 사용자 발화 종료, 전사 확정, 검색 종료, LLM 첫 문장, TTS 첫 바이트, 단말 재생 시작 시각을 연결해야 원인을 찾는다.

사용자가 급한 정보를 묻는 경우에는 첫 음성으로 ‘확인 중입니다’라고 말하는 것이 실제 답변을 빠르게 주는 것처럼 보일 수 있다. 하지만 뒤의 답이 늦거나 틀리면 신뢰가 줄어든다. 도중 안내는 실제 진행 상태를 나타내야 하고, 정확한 결과가 언제 준비되는지 예측 가능한 편이 좋다. 특히 쓰기 작업에서는 ‘처리했습니다’라는 음성을 대상 서비스의 확정 응답 전에 재생하지 않는다. 오디오의 빠른 시작과 업무 결과의 확정은 다른 사건이다.

### 사례 F — 인도 추론은 맞지만 이미지 저장이 국외인 문서 앱

앱은 인도 지역 추론 프로필을 정확히 사용한다. 하지만 사용자가 올린 신분증 이미지는 기본 설정의 글로벌 스토리지 버킷에 먼저 저장되고, 전처리 로그에는 원문 텍스트가 다른 지역으로 전송된다. 모델 호출만 보면 정책에 맞지만 전체 데이터 흐름은 다르다. 이런 사례를 막으려면 업로드, 임시 저장, 전처리, 추론, 결과, 로그, 백업을 선으로 연결한 데이터 흐름도를 만든다. 각 선의 출발과 목적 리전을 확인한다. 소스 코드의 모델 ID를 검사하는 것은 필요한 검증 중 하나지만 전체의 충분조건이 아니다.

장애 때의 폴백도 같은 흐름도에 넣는다. 지역 프로필이 일시적으로 불가용하면 앱이 글로벌 프로필로 바꿔 호출하는지, 사용자에게 오류를 보여 주는지 결정해야 한다. 공개 콘텐츠 처리에는 폴백이 허용될 수 있지만 신원 문서에는 허용되지 않을 수 있다. 업무 자료의 등급을 모르는 상태에서 자동 폴백을 두면 가장 민감한 자료가 가장 넓은 경로로 이동할 수 있다. 처리 지역의 선택은 성능 설정이 아니라 업무 정책의 일부다.

## 평가 샘플을 고를 때의 균형

위 사례집만 시험하면 시스템이 지나치게 보수적으로 거부할 수도 있다. 좋은 제품은 잘못된 답을 피하는 것뿐 아니라 허용된 질문에는 유용한 답을 준다. 평가 세트에는 **정상 사례와 경계 사례를 함께** 넣는다. 정형 지표만 묻는 쉬운 질문, 승인된 정책 문서의 정확한 조항을 묻는 질문, 동일한 기간의 데이터와 문서를 결합하는 질문은 성공해야 한다. 반대로 기간이 어긋난 결합, 권한 밖의 개인 자료, 정정된 외부 기사, 음성에서 헷갈리는 숫자, 금지된 지역 폴백은 안전하게 보류하거나 설명해야 한다. 안전한 거부율만 높고 실제 업무를 해결하지 못하면 제품의 가치가 낮다.

질문 샘플은 실제 사용자 요청의 분포를 반영하되, 드문 고위험 상황을 의도적으로 더 넣는다. 평균 사용자는 자신의 기록만 묻더라도 관리자의 다른 직원 기록 조회, 휴직자의 계정 상태, 협력사 접근은 반드시 검증해야 한다. 빈도가 낮다는 이유로 권한 위반 테스트를 빼면 큰 사고의 확률을 과소평가한다. 반대로 모든 질문을 극단적 공격 사례로 채우면 실제 사용성 개선을 평가할 수 없다. 일반 업무 세트와 위험 세트를 분리해 보고한다. 두 세트가 각각의 기준을 통과해야 출시 판단이 가능하다.

데이터셋과 원문은 시간이 지나 바뀌므로 평가 스냅샷을 만든다. 오늘의 정답이 다음 달의 정책에서는 틀릴 수 있다. 평가에 사용한 문서 버전, 데이터 기준일, 사용자 역할, 모델 버전, 도구 스키마 버전을 기록한다. 같은 테스트 질문이라도 대상 서비스의 권한이 바뀌면 기대 결과가 달라진다. 질문 문장만 남기는 평가는 재현되지 않는다. 원문의 예제 성과와 우리 제품의 성과가 다른 것도 이 입력 조건의 차이 때문이다. 재현 가능한 비교를 위해서는 평가 조건을 먼저 고정해야 한다.

## 오늘의 핵심을 한 문장씩 남기면

- **자료:** 한 채팅이 여러 원천을 묶어도 원천별 정의와 시점을 유지한다.
- **신원:** 사용자를 대신한 호출은 사용자 주체를 대상 서비스까지 보존하고, 실제 권한은 대상에서 다시 확인한다.
- **검색:** 최신 검색 결과는 후보이며, 게시 가능한 사실은 원문과 날짜를 확인한 뒤 결정한다.
- **의미:** 모델에 데이터 의미를 알려 주되, 계산 규칙과 DB 권한을 프롬프트 밖에서도 관리한다.
- **음성:** 공급자의 첫 바이트 지표와 사용자가 느끼는 전체 대화 지연을 구분한다.
- **지역:** 모델 호출의 리전뿐 아니라 입력·저장·로그·백업을 포함한 데이터 흐름의 지역을 확인한다.

이 여섯 문장은 신기술을 거절하자는 결론이 아니다. 자동화가 더 많은 일을 해도 설명 가능하고 수정 가능한 제품을 만들기 위한 최소 조건이다. 오늘 공식 발표의 제품 기능과 고객 사례는 설계의 재료를 제공한다. 실제 사용자에게 어떤 일을 맡길지는 우리 원천과 권한, 품질 기준을 검증한 뒤 결정해야 한다.

## 출시 게이트 예시: ‘통과’의 정의를 미리 합의하기

실험을 오래 끌지 않으려면 출시 판단의 질문을 시작할 때 적어 둔다. 아래 기준은 오늘 원문의 제품들이 기본적으로 보장하는 SLA가 아니라, 사용자 데이터를 다루는 AI 기능을 출시할 때 팀이 조정해 쓸 수 있는 **의사결정 예시**다. 수치 목표는 업무 위험과 사용량에 맞춰 별도로 정해야 한다. 여기서는 기준의 종류와 실패 시 행동을 명확히 하는 데 초점을 둔다.

**자료 게이트:** 대표 질문에서 답변의 핵심 주장마다 출처를 찾을 수 있어야 한다. 정형 수치에는 계산식과 기간, 문서 주장에는 버전과 시행일, 외부 검색 주장에는 원문 URL과 확인 시각이 연결된다. 자료가 충돌하는 질문에서 한쪽을 조용히 우선하지 않고 차이를 설명한다. 이 게이트를 통과하지 못하면 모델의 문장 스타일을 개선하기보다 원천 메타데이터와 결합 규칙을 먼저 수정한다. ‘어떤 문장이 어디서 왔는지’가 불명확한 채로 쓰기 도구를 붙이면 오류의 영향이 커진다.

**권한 게이트:** 서로 다른 역할의 사용자 두 명 이상으로 허용·거부 사례를 모두 시험한다. 허용된 정보는 제공하고, 권한 밖의 행·열·객체는 도구 단계에서 거부된다. 대상 API의 감사 기록에는 실제 요청 주체가 남는다. 에이전트가 금지된 자료를 받았지만 답변에서만 숨기는 구조는 통과로 보지 않는다. 이 게이트에 실패하면 기능을 읽기 전용으로 축소하는 것만으로 충분한지 판단해야 한다. 읽기 자체가 민감하면 해당 자료 연결을 보류한다.

**행동 게이트:** 쓰기 작업의 대상과 변경 내용을 사용자에게 확인시킬 수 있고, 서버가 현재 상태를 다시 검사한다. 타임아웃이나 중복 호출에 대해 정확히 한 번 반영되거나 중복이 명확히 탐지된다. 취소와 롤백 절차가 문서화되어 있다. ‘모델이 올바른 도구를 선택했다’는 것만으로 통과하지 않는다. 대상 서비스에 실제로 기록된 결과와 사용자에게 알려 준 결과가 일치해야 한다. 읽기 기능의 정확성이 높아도 쓰기 게이트가 실패하면 쓰기 기능은 별도 보류한다.

**최신성 게이트:** 외부 정보가 필요한 질문에서 발행일과 확인 시각이 표시된다. 원문을 확인하지 못한 스니펫은 확정 사실로 쓰지 않는다. 공식 자료의 정정이나 철회를 감지했을 때 게시 전 초안과 이미 발행된 글을 처리하는 절차가 있다. 검색 API가 실패했을 때의 공식 인덱스·RSS 경로가 준비되어 있거나, 충분한 근거가 없으면 보류한다. 뉴스·규제·제품 가용성처럼 변화가 빠른 영역에서는 한 번의 성공 검색보다 **오래된 정보가 새 정보처럼 보이는 실패**가 더 중요하다.

**성능 게이트:** 사용자가 실제로 느끼는 지연을 동일한 단위로 잰다. 음성은 발화 종료에서 첫 재생과 답변 완료까지, 텍스트는 제출에서 유용한 첫 답변과 완료까지를 본다. 정상 부하와 혼잡 부하의 p95를 함께 본다. 지연을 줄이는 변경이 정확성이나 권한 검사를 우회하지 않는지 확인한다. 부분 전사를 도입했다면 정정 발화에서 잘못된 쓰기 동작이 시작되지 않아야 한다. 빠른 실패 메시지만으로 성능을 ‘좋다’고 판단하지 않는다.

**지역·비용 게이트:** 민감 자료의 업로드·전처리·추론·로그·백업 경로가 정책에 맞는 리전에 있음을 확인한다. 장애 시 폴백도 자료 등급에 맞는다. 비용은 성공한 사용자 업무 한 건당으로 계산하고, 캐시 적중률과 실패 재시도, GPU 유휴 비용을 포함한다. 특정 고객의 80% 절감 발언을 우리의 예산 목표로 바로 쓰지 않는다. 기능이 유용해도 자료 지역을 증명할 수 없으면 허용 가능한 자료 유형으로 범위를 줄인다. 비용이 불확실하면 작은 사용량으로 시작하고 상한과 경보를 둔다.

### 게이트를 통과하지 못했을 때의 선택지

한 항목이 실패했다고 전체 프로젝트를 폐기할 필요는 없다. 원천 인용이 불안정하면 문서형 질문을 빼고 정형 지표만 제공할 수 있다. 대리 권한이 불확실하면 개인 API 연결을 빼고 공개 자료 검색만 제공할 수 있다. 음성 p95가 나쁘면 텍스트 기능을 먼저 출시할 수 있다. 지역 프로필이 필요한 자료를 처리할 수 없으면 합성 자료로 검증을 계속하면서 실제 민감 자료 입력은 보류할 수 있다. 이렇게 **기능을 분리해 배포할 수 있는 구조**는 위험을 줄이는 동시에 유용한 부분을 사용자에게 전달한다. 반대로 모든 기능을 하나의 에이전트 프롬프트에 넣어야만 동작하는 구조라면 작은 실패 하나가 전체 출시를 막는다.

출시 판단 문서에는 각 게이트의 담당자와 확인한 증거를 적는다. ‘권한 테스트 완료’ 대신 어떤 역할과 객체로 무엇을 거부했는지 적고, ‘음성 빠름’ 대신 어느 장치·언어·네트워크에서 발화 종료부터 첫 재생까지 얼마나 걸렸는지 적는다. ‘인도 지역 처리’ 대신 실제 사용한 추론 프로필과 주변 저장 경로를 적는다. 이런 기록은 회의를 번거롭게 하려는 형식이 아니다. 제품이 성장해 담당자가 바뀌었을 때도 동일한 기준으로 변경을 검토할 수 있게 해 준다.
