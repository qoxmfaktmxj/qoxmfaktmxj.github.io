## 배경 — 모델 능력의 경쟁에서 실행 경계의 경쟁으로

지난 몇 년간 AI 제품 비교는 주로 모델이 어느 벤치마크에서 더 높은 점수를 받는지, 어느 응답이 더 자연스러운지에 집중됐다. 그러나 에이전트가 브라우저를 열고, 저장소를 수정하고, 결제 버튼을 누를 수 있게 되면 같은 지표만으로 제품을 판단할 수 없다. 문장 생성의 오류는 수정 가능한 답변의 문제일 수 있지만, 외부 시스템에서 실행된 작업의 오류는 주문·배포·권한 변경·개인정보 노출로 남는다. 실행 가능한 AI 제품은 언어 모델, 도구 실행기, 사용자 승인 UI, 조직 정책, 결제·보안 공급자, 감사 로그가 맞물린 시스템이다.

이번 발표들은 층을 구분할 좋은 사례다. Google Wallet 연결에서 Gemini가 지출 내역을 읽어 예산 질문에 답할 수 있다는 사실은 곧바로 금융 거래 권한을 뜻하지 않는다. ChatGPT Wallet의 결제 경로에서 에이전트가 장바구니를 채울 수 있다는 사실도 사용자의 구매 승인을 대신할 수 있다는 뜻이 아니다. GitHub Copilot이 모델을 제공한다는 사실은 조직 정책상 사용 가능한지, 각 사용자의 도구에서 이미 롤아웃됐는지, 예산에 맞는지와 별개다. AI Scan 설정을 켤 수 있다는 사실은 실제 스캔이 실행됐거나 취약점이 해결됐다는 뜻이 아니다. 이처럼 **발표의 명사와 운영 상태의 동사 사이에는 간격**이 있다.

이 글은 그 간격을 다섯 층으로 읽는다. **데이터 접근**은 무엇을 볼 수 있는지, **의사결정**은 어떤 근거로 다음 행동을 고르는지, **실행 승인**은 누가 마지막으로 허용하는지, **관측·비용**은 무엇이 일어났고 얼마가 들었는지, **검증·복구**는 실패를 어떻게 발견하고 되돌리는지다. 제품 기획자는 다섯 층을 하나의 ‘AI 기능’ 항목으로 묶지 않아야 한다. 개발자는 API 응답만으로 성공을 판단하지 않아야 한다. 운영자는 로그가 많다는 것만으로 책임 소재가 명확해졌다고 생각하지 않아야 한다.

## 심층 1 — ChatGPT Wallet과 Gemini Wallet: 같은 ‘월렛’이지만 다른 권한

이름이 비슷한 두 발표를 같은 경쟁 기능으로 읽으면 중요한 차이를 놓친다. ChatGPT Wallet은 **행동의 마지막 단계인 결제**에 초점을 맞춘다. Google Wallet의 Gemini 연결은 **개인 금융 정보에 기반한 답변**에 초점을 맞춘다. 하나는 쓰기 성격의 외부 거래이고, 하나는 읽기 성격의 데이터 접근이다. 두 회사의 개인정보·보안 설명을 한 줄로 ‘안전하다’고 합치면 실제 제품에서 어디에 확인 단계를 둬야 하는지 알 수 없게 된다.

OpenAI의 공식 흐름은 카드 등록, 상품·금액·카드 확인, 매 구매 보안 승인, 네트워크의 결제 토큰 발급, 판매자 결제 순서다. 에이전트와 판매자는 사용자의 실제 카드 정보를 받지 않는다고 회사는 설명한다. 그러나 카드 원본이 보이지 않는다는 사실만으로 모든 거래 위험이 사라지는 것은 아니다. 상품 이름·수량·배송지·세금·구독 조건이 승인 화면과 판매자의 최종 청구에서 일치해야 한다. 고객이 승인한 금액과 결제 성공 응답, 주문 생성 응답을 같은 거래 식별자로 묶어야 중복 주문과 승인 후 조건 변경을 찾을 수 있다. 이 제안은 OpenAI의 현재 기능 설명이 아니라 **상거래 제품을 만드는 팀에 필요한 설계 점검 항목**이다.

Google의 공식 설명은 연결을 사용자가 선택하고 언제든 끌 수 있다는 점, Gemini가 정보를 읽을 뿐 자금을 이동·관리·투자할 수 없다는 점을 분명히 한다. 개인화 답변에는 계좌 거래 내역처럼 해석이 민감한 데이터가 쓰인다. 읽기 전용이라도 한 달 지출, 가족 선물 구매, 의료비, 위치가 드러나는 상점 내역은 사적인 정보다. 따라서 제품은 ‘조회 전용이므로 위험이 낮다’가 아니라 **조회 결과가 누구의 대화 맥락으로 들어가고, 얼마 동안 남으며, 어떤 화면에 표시되는지**를 따져야 한다. Google이 제공하는 Memory Summary와 연결 해제 UI는 사용자가 개인화 상태를 확인·편집할 수 있는 경로라는 점에서 중요하다. 그것이 모든 내부 저장 구조의 상세를 공개한다는 의미는 아니다.

인사시스템에 대입하면 차이가 더 뚜렷하다. ‘직원의 잔여 연차를 찾아 설명한다’는 조회이고, ‘연차 신청서를 초안으로 작성한다’는 준비이며, ‘연차를 확정하고 급여 계산에 반영한다’는 상태 변경이다. 같은 챗봇 화면에 세 기능을 넣더라도 서버 권한은 세 단계로 나눠야 한다. 첫 번째는 데이터의 범위와 개인정보 마스킹, 두 번째는 미리보기와 수정 가능성, 세 번째는 권한자 승인과 불변 감사 기록이 중심이다. 모델이 한 응답에서 ‘처리했습니다’라고 말했는지는 실제 HR 데이터베이스에 반영됐는지를 증명하지 못한다. 사용자에게는 조회·초안·확정의 상태가 명료하게 보여야 한다.

### 거래·상태 변경 제품을 위한 승인 계약

승인 화면에서 보여 줄 정보는 단순한 ‘계속하시겠습니까?’가 아니라 변경 전·후의 차이다. 결제라면 품목, 수량, 판매자, 통화, 총액, 배송지, 일회성·반복 결제 여부가 대상이다. 인사·재무라면 대상 직원, 영향 기간, 금액 또는 시간, 정책 근거, 승인자, 수정 가능한 마감 시각이 대상이다. 서버는 이 정보의 해시나 버전 식별자를 승인 이벤트와 연결하고, 승인 후 대상이 바뀌면 이전 승인을 재사용하지 않도록 해야 한다. 일회성 권한은 ‘처음 한 번만 물었다’는 뜻이 아니라 **승인된 범위 밖에서 재사용할 수 없다는 뜻**이어야 한다.

도구 실행은 실패를 포함해 설계한다. 네트워크가 끊겨 응답이 보이지 않을 때 결제가 완료됐는지 모르면서 재시도하면 중복 결제가 생길 수 있다. 따라서 idempotency key, 서버의 주문 상태 조회, 승인 이벤트의 중복 처리 방지, 결제 제공자의 웹훅 순서 역전 대응이 필요하다. HR에서는 같은 휴가 신청을 두 번 저장하거나 급여 변경을 두 번 적용하지 않도록 작업 ID와 버전 조건을 사용한다. 모델의 자연어 답변은 가장 나중에 보여 주되, **영속 상태의 성공 응답**이 확인되기 전에는 ‘완료’라고 표현하지 않는 편이 안전하다.

## 심층 2 — Copilot 모델 종료: ‘새 모델 사용’보다 중요한 마이그레이션 설계

GitHub의 모델 종료 발표는 표면적으로 모델 여섯 종의 교체 일정이다. 실제로는 회사가 개발자의 AI 작업 환경을 얼마나 파악하고 있는지 묻는 운영 이벤트다. Copilot Chat의 모델 선택, IDE의 인라인 편집, 코딩 에이전트의 장기 작업, CLI의 자동화, SDK 통합은 모두 이용 맥락이 다르다. 특정 모델에 맞춰 만든 프롬프트나 도구 호출 규약은 새 모델에서 형식이 바뀌거나 불필요하게 비싸질 수 있다. 따라서 대체 모델 이름을 정책 화면에서 켜는 것만으로 마이그레이션이 끝났다고 볼 수 없다.

GitHub가 제안한 대응은 Fable 5→Fable 5.2, Haiku 4.5→Haiku 5.5, Gemini 3.8 Flash→Gemini 4 Hydrogen, Gemini 4 Argon→Gemini 4 Carbon, Grok 4.6→Grok 4.7이다. Kimi K3는 발표 당시 대체 모델이 미정이다. 개인 연간 구독자의 Haiku 4.5 예외는 별도로 표기됐다. 다만 이름이 유사한 대체 모델이라도 속도, 코딩 스타일, 컨텍스트 처리, 도구 사용, 비용이 동일하다는 보장은 없다. 제안은 지원 경로이지 품질 동등성 증명서가 아니다.

조직이 먼저 할 일은 사용 현황을 나누는 것이다. 사람이 수동으로 선택하는 모델, 팀 템플릿에서 고정된 모델, API·SDK 설정 파일에 박힌 모델 ID, 에이전트 작업의 기본값을 분리해 조사해야 한다. 프롬프트 템플릿과 CI 문서가 오래된 모델을 예시로 든다면 개발자가 재사용하면서 실패할 수 있다. 어느 팀이 어느 모델에 의존하는지 알아야 12월 14일 이전에 사용자에게 정확한 변경 공지를 할 수 있다. Copilot Business·Enterprise에서 기본 모델 사용 정책을 꺼 두었다면 제안된 모델을 명시적으로 허용하는 절차도 확인해야 한다.

다음은 작업 단위 회귀 평가다. ‘코딩 능력’이라는 단일 숫자보다 실제 저장소의 대표 작업을 택하는 것이 낫다. 예를 들어 TypeScript 컴포넌트 수정, 데이터베이스 마이그레이션 작성, 테스트 실패 원인 찾기, 오래된 API 사용 부분 교체, 접근성 문제 수정은 요구하는 맥락이 다르다. 입력 저장소·도구 권한·시간 제한·검증 명령을 고정하고 이전 모델과 후보 모델의 완료율, 변경 파일 범위, 테스트 통과율, 인간 수정 시간, 요청당 비용을 비교한다. 모델이 더 빨리 첫 답을 내더라도 후속 수정이 늘면 총 작업 시간은 늘 수 있다. 반대로 토큰 단가가 높아도 재작업을 줄이면 해결된 작업당 비용은 낮아질 수 있다.

Google이 Hydrogen을 네 단계의 사고 수준으로 구성할 수 있다고 발표했지만, Copilot의 모든 인터페이스가 그 설정을 사용자에게 동일하게 제공한다는 뜻은 아니다. Google AI Studio에서 조정한 매개변수와 GitHub Copilot 제품의 모델 선택자는 다른 제품 표면이다. 같은 공급자 모델이라도 제품별 시스템 지시, 도구, 저장소 맥락, 속도 제한, 청구 체계가 다르므로 벤치마크 결과를 그대로 이식하지 않는다. 이 구분이 없으면 ‘Hydrogen이 빠르다’는 공급자 설명만으로 복잡한 코드베이스의 에이전트 작업을 전부 옮기는 실수를 하게 된다.

마이그레이션은 단계적으로 진행해야 한다. 먼저 영향이 작은 내부 작업에서 후보 모델을 시험하고, 코드 검토자가 결과를 확인하며, 실패한 작업 유형을 기록한다. 다음으로 여러 팀이 쓰는 공통 템플릿을 수정하되 이전 모델 설정의 제거 날짜를 명시한다. 이후 기본값을 바꾸고 1~2주 동안 품질·비용·오류 유형을 관찰한다. 종료일 직전에는 아직 구형 모델을 명시적으로 선택하는 문서·스크립트가 없는지 다시 확인한다. 되돌리기를 위해 이전 모델을 무기한 보유하는 전략은 종료일이 이미 정해진 상황에서 유효하지 않다. 대신 다른 지원 모델과 안전한 수동 작업 경로를 준비해야 한다.

## 심층 3 — AI Scan의 ‘설정’과 ‘실행’을 분리해야 하는 이유

GitHub의 AI Scan API 변경은 자동화에 유용하지만 작은 단어 차이를 놓치면 보안 상태를 과장하기 쉽다. `repository_scan: enabled`는 저장소 수준에서 스캔을 사용할 수 있는 상태이지, 저장소가 실제로 검사됐다는 증거가 아니다. GitHub 공식 글은 쓰기 권한자가 요청에 따라 스캔을 실행하고, 실행마다 AI 크레딧이 소모된다고 명시한다. 이를 ‘스캔 활성화 완료’와 ‘취약점 검사 완료’를 하나의 대시보드 체크 표시로 표시하면 운영자가 잘못된 안심을 할 수 있다.

권한 상속도 중요하다. 엔터프라이즈 정책이 허용하지 않으면 API가 422를 돌려주며, 조직이 비활성화하면 저장소가 임의로 켤 수 없다. 조직에서 허용하면 저장소는 상속하되 개별적으로 제외할 수 있다. 따라서 관리 자동화는 PATCH 성공 여부만 기록하면 안 된다. GET으로 실제 유효 설정을 다시 읽고, 엔터프라이즈·조직·저장소의 층별 상태를 표시해야 한다. `pr_scan`과 `repository_scan`을 한 요청에 수정할 때 둘 중 하나가 막히면 둘 다 바뀌지 않는다는 원문도 중요한 운영 규칙이다. 부분 성공을 가정한 후속 상태 변경은 잘못된 설정 보고를 낳는다.

보안 운영팀이 원하는 지표는 세 종류다. **커버리지**는 어떤 저장소에서 실행 가능한가, **실행 이력**은 언제 누가 어떤 리비전을 검사했는가, **조치 결과**는 발견한 문제를 누가 어떻게 확인·수정했는가다. 커버리지 100%가 실행 이력 100%를 의미하지 않고, 실행 이력 100%가 조치 완료를 의미하지 않는다. 세 지표를 분리해야 비용 계획도 가능하다. 스캔마다 크레딧이 쓰이므로 전체 저장소를 매일 반복 검사하는 정책과 고위험 저장소·주요 릴리스에 맞춰 검사하는 정책의 비용은 다르다. 어떤 정책이 맞는지는 저장소의 위험도, 변경 빈도, 사람의 검토 용량에 따라 결정해야 한다.

AI가 찾아낸 문제도 신뢰도 높은 사실로 바로 확정하지 않는다. 결과에 코드 위치·실행 경로·재현 조건이 있는지 확인하고, 다른 보안 도구와 중복되는지, 테스트 또는 샌드박스에서 재현되는지 살펴봐야 한다. 자동 수정 제안이 있다면 기능 회귀와 권한 확대를 따로 검사한다. 특히 생성형 도구가 ‘안전해 보이는’ 코드를 만들었다는 이유로 인증·인가 테스트를 생략해서는 안 된다. AI Scan은 사람의 보안 판단을 대체하는 만능 인증 마크가 아니라 검토 대상을 좁혀 주는 신호로 사용해야 한다.

## 심층 4 — llama.cpp 1.0: 로컬 AI의 ‘실행 가능’과 ‘유지 가능’을 가르는 지점

llama.cpp·ggml의 1.0 발표는 로컬 추론을 새로 발명한 소식이 아니다. 다양한 하드웨어에서 이미 널리 쓰이는 라이브러리가 downstream 개발자에게 **버전 변경의 의미를 좀 더 예측 가능하게 제공하겠다**는 약속이다. 공개 C API에 비호환 변경이 있으면 메이저 버전을 올리고, 호환 기능이나 백엔드·모델 지원을 추가하면 마이너 버전을 올리며, API 변경 없는 수정은 패치 버전으로 구분한다. 이 규칙은 임베디드·데스크톱·모바일 제품이 업그레이드 위험을 분류하는 데 도움이 된다.

하지만 API 안정성과 실제 실행 결과의 안정성은 다르다. 같은 모델 파일이라도 양자화 형식, CPU·GPU 백엔드, 드라이버, 스레드 수, 컨텍스트 길이, 샘플링 설정에 따라 성능과 출력이 달라질 수 있다. 버전 번호가 메이저 1로 바뀌었다고 특정 모델의 한국어 답변 품질, 모바일 발열, 메모리 사용량이 자동으로 보증되지는 않는다. 특히 로컬 AI 제품은 서버에 문제가 생기면 즉시 롤백하는 클라우드 서비스와 달리 사용자의 기기에 여러 버전이 한동안 공존할 수 있다. 클라이언트 앱의 엔진 버전, 모델 버전, 양자화, 운영체제·칩 정보를 함께 기록해야 재현 가능한 버그 보고를 받을 수 있다.

로컬 추론의 장점은 민감한 데이터를 외부 서버로 보내지 않는 아키텍처를 선택할 수 있다는 것이다. 그러나 ‘로컬’이라는 라벨만으로 프라이버시 검토가 끝나지 않는다. 앱의 분석 SDK, 오류 로그, 모델 다운로드 경로, 자동 업데이트, 클라우드 백업, 플러그인 호출이 데이터를 외부로 보낼 수 있다. 기기 안에서 추론하더라도 모델 출력이 로컬 파일을 덮어쓰거나 다른 앱에 전송된다면 행동 권한은 여전히 통제해야 한다. 사용자에게는 **추론 위치**와 **결과의 외부 전송 여부**를 별도로 설명해야 한다.

모델과 엔진을 배포할 때는 조합 테스트가 중요하다. 최소한 지원 CPU·GPU, 대표적인 운영체제 버전, 모델 크기와 양자화, 짧은·긴 컨텍스트, 오프라인 환경, 앱 백그라운드 전환을 포함해야 한다. 속도는 첫 토큰 지연과 지속 생성 속도를 분리하고, 메모리는 피크와 장시간 사용 뒤의 잔류량을 본다. 모바일에서는 발열·배터리·앱 종료율을 포함한다. 모델 응답 정확도만 측정하면 사용자가 실제로 겪는 ‘실행 가능하지만 사용할 수 없음’을 놓친다. 1.0이라는 표시는 이런 호환성 매트릭스를 만들기 더 좋은 출발점이지 매트릭스 자체를 없애는 면허가 아니다.

## 심층 5 — XYBench가 던지는 질문: 답을 맞혔나, 문제를 바꿔 읽었나

사용자의 질문이 정확한 문제 정의라는 가정은 AI 도우미를 쉽게 만들지만 현실과 맞지 않는다. 예컨대 ‘느린 페이지에 캐시를 더 붙이는 법’이라는 요청의 실제 문제는 잘못된 SQL 인덱스나 브라우저에서 중복 호출되는 API일 수 있다. 사용자의 명시적 해결책 Y를 빠르게 구현해 주면 형식적으로는 친절하지만 실제 목표 X는 해결되지 않을 수 있다. XYBench는 바로 이 상황을 분리해 보려는 연구다.

AllenAI는 8,115개 질문의 출처를 Stack Overflow 1,557개, Stack Exchange 184개, 수작업 예시 102개, WikiHow 기반 생성 질문 6,272개라고 밝혔다. 모델이 표면 요청에 대한 해결책과 실제 목표에 대한 해결책을 각각 포함했는지, 어떤 쪽에 설명의 무게를 뒀는지, 틀린 전제를 바로잡았는지를 별도 측정한다. 연구팀은 비교한 모델들이 실제 목표에 관한 조언을 언급할 때도 답변의 중심은 사용자가 제안한 잘못된 방법에 남겨 두는 경향을 보고했다. 이것은 ‘모델이 X를 전혀 모른다’와 다른 실패다. **알고 있지만 답변의 우선순위를 잘못 잡는 실패**다.

벤치마크를 읽을 때는 경계가 필요하다. 원문의 핵심 실험은 영어의 단일 턴 질문이며, 절차적 문제 풀이에 중심이 있다. 개인의 가치 판단이나 법률·의료·인사 정책처럼 정답이 상황에 따라 달라지는 영역에서는 모델이 ‘당신의 진짜 목표는 X’라고 단정하면 오히려 위험하다. 실제 제품에서는 X를 확정하기보다 가설로 제시하고, 제안한 Y가 목표에 맞는지 확인 질문을 하며, 명시된 제약을 존중하는 편이 낫다. 잘못된 전제를 지적하는 능력과 사용자의 자율성을 침해하지 않는 태도는 함께 평가해야 한다.

개발 워크플로에도 적용할 수 있다. 사용자가 ‘모든 API 오류를 재시도하도록 해 줘’라고 하면 목표는 장애 회복일 수 있지만, 인증 실패나 입력 검증 실패까지 반복하면 비용과 장애를 키운다. 좋은 에이전트는 먼저 오류를 재시도 가능·불가능으로 구분하고, 멱등성·지수 백오프·시간 제한을 확인한다. ‘테스트를 통과하게 해 줘’라는 요청의 목표가 결함 수정인데 에이전트가 실패 테스트를 삭제한다면 Y에는 충실해도 X에는 실패한 것이다. 평가 데이터에는 이런 **겉으로 쉬운 우회**를 포함해야 한다.

## 개발자에게 의미 — 기능보다 ‘계약’을 먼저 코드로 표현하기

AI 기능의 설계 문서에 모델 이름만 적는 것은 부족하다. 입력 데이터의 소유자, 조회 가능한 범위, 도구 호출의 사전조건, 최종 승인 주체, 실패 시 재시도 정책, 결과를 확인할 영속 상태, 감사 로그의 보존 기간까지 정의해야 한다. 모델은 한 구성 요소이며, 모델을 바꾸어도 나머지 계약은 유지돼야 한다. 아래 항목은 제품 팀이 이번 발표를 구현 과제로 번역할 때 사용할 수 있는 기준이다.

**첫째, 읽기·초안·쓰기·외부 거래를 별도 권한으로 분리한다.** OAuth 범위나 내부 RBAC에 ‘AI 사용’ 하나만 추가하는 대신 실제 행동에 맞게 나눈다. 읽기 권한은 최소 범위와 개인정보 마스킹을, 초안 권한은 사용자 수정 가능성을, 쓰기 권한은 대상·버전·승인을, 외부 거래 권한은 한도·재확인·영수증을 다룬다. 프롬프트에 ‘허락받고 실행하라’고 적는 것만으로 권한 검사를 구현한 것이 아니다.

**둘째, 승인된 내용과 실행된 내용을 비교할 수 있게 한다.** 사람이 읽는 문장과 서버가 처리하는 구조화된 요청 사이에 차이가 생기면 의미 없는 승인이 된다. 대상 ID, 액수, 통화, 수량, 주문 상태, 데이터 버전을 구조화하고 승인 이벤트와 실행 이벤트에 같은 상관 ID를 남긴다. 사람이 확인할 화면은 모델이 만든 요약만 보여 주지 말고 서버의 최종 실행 요청에서 렌더링하는 것이 좋다.

**셋째, 모델 선택은 정책과 비용의 문제로 관리한다.** Copilot 종료 일정처럼 모델의 수명은 제품 운영 일정과 다르다. 모델 ID를 코드 곳곳에 하드코딩하지 않고 관리 가능한 설정으로 빼되, 변경 시 어떤 팀과 작업이 영향을 받는지 추적한다. 모델을 교체하면 품질뿐 아니라 지연, 토큰 사용량, 추가 도구 호출, 사람이 고치는 시간까지 관찰한다. 벤더가 추천한 후속 모델이라는 사실은 조직의 회귀 평가를 면제하지 않는다.

**넷째, 보안 상태는 설정·실행·조치를 따로 표현한다.** AI Scan의 API가 보여 주는 층위가 좋은 경고다. 설정을 켠 날짜, 실제 스캔한 커밋, 취약점 판정과 수정 커밋을 혼동하지 않는다. 보안 대시보드가 상태를 하나의 초록색 체크로 압축해야 한다면 사용자가 원본 상태를 열어볼 수 있어야 한다.

**다섯째, 문제 정의를 검증하는 평가를 추가한다.** 단순한 정답률 외에 사용자가 제안한 방법이 잘못됐을 때 이를 정중하게 밝히는지, 목표를 위한 대안을 제시하는지, 추가 질문이 필요한 상황에서 지어내지 않는지를 측정한다. 이는 모델이 사용자 요청에 반항해야 한다는 뜻이 아니라 **문자 그대로의 실행과 실제 도움의 차이**를 평가하자는 뜻이다.

## 운영 포인트 — 이번 주에 점검할 실제 체크리스트

1. **제품의 AI 행동 목록을 만든다.** 도구 호출을 읽기, 검색, 초안, 내부 상태 변경, 외부 거래로 분류한다. 분류가 어렵다면 현재 UI가 사용자에게 권한 범위를 설명하기도 어려울 가능성이 높다.
2. **사람의 승인 경계를 표시한다.** 어떤 작업은 매번 승인이 필요한지, 어떤 작업은 정해진 기간·금액 한도 안에서 사전 승인이 가능한지 결정한다. 아직 지원하지 않는 사전 위임을 제품 설명에 현재 기능처럼 적지 않는다.
3. **최종 상태 확인 경로를 분명히 한다.** 도구 호출의 200 응답, 결제 성공, 주문 완료, 배송 시작은 다른 상태다. 앱이 어느 상태에서 사용자에게 ‘완료’라고 알리는지 문서화한다.
4. **모델 종료 영향도를 조사한다.** Copilot의 12월 14일 종료 대상 모델을 프롬프트 템플릿, 저장소 설정, 자동화 문서, 교육 자료에서 찾는다. 연간 구독자의 Haiku 4.5 예외와 Kimi K3 대체 미정 상태를 누락하지 않는다.
5. **대체 모델의 실제 업무 평가를 예약한다.** 작업별 완료율과 검토 시간을 비교한다. 모델이 생성한 코드만 점수화하지 말고 테스트 결과와 사람의 수정량을 기록한다.
6. **AI Scan 사용 상태를 세 값으로 기록한다.** ‘허용됨’, ‘실행됨’, ‘조치됨’이다. 422 정책 오류를 자동 재시도로 가리지 말고 상위 정책을 수정할 담당자에게 전달한다.
7. **비용 한도를 출처별로 확인한다.** Copilot의 사용량 기반 공급자 정가, AI Scan의 AI 크레딧, AI Studio의 선결제·크레딧 유효기간은 서로 다른 과금 규칙이다. 무료 혜택과 초과 사용 비용을 같은 표에 놓는다.
8. **로컬 추론의 버전 조합을 고정한다.** 앱·엔진·모델·양자화·백엔드 버전을 함께 기록해 오류를 재현한다. ‘엔진이 1.0이므로 검증이 끝났다’고 표기하지 않는다.
9. **사용자의 숨은 목표를 다루는 평가를 추가한다.** 표면 요청에만 답하는 사례와 실제 목표에 필요한 진단을 제시하는 사례를 구분한다. 다만 고위험 도메인에서는 목표 추정을 확정 사실처럼 말하지 않게 한다.
10. **출처와 발표일을 보존한다.** 주말·휴일에 소식이 적으면 어제 발표를 오늘 발표처럼 포장하지 않는다. 원문 발표일, 한국시간 확인 시각, 공급자 자체 주장과 독립 검증의 차이를 기록한다.

## 설계 실무 1 — 에이전트 권한을 상태 전이로 모델링하기

에이전트를 배포할 때 ‘이 도구를 호출할 수 있는가’만으로 권한을 정의하면 부족하다. 같은 도구라도 어떤 입력과 어떤 상태에서 호출되는지가 다르기 때문이다. 예컨대 주문 API의 `POST /orders`는 장바구니를 임시 보관하는 데 쓰일 수도 있고, 되돌리기 어려운 구매를 확정하는 데 쓰일 수도 있다. API 메서드만 보고 위험을 분류하지 말고 **전후 상태**를 기준으로 나눠야 한다. 읽기, 후보 생성, 사용자 검토 대기, 승인, 실행 대기, 성공 확인, 취소·환불 요청, 실패 조사 같은 상태를 명시하면 UI와 서버의 언어가 일치하기 쉽다.

첫 번째 상태인 정보 조회에는 범위 제한이 핵심이다. 사용자가 자신의 월간 지출을 묻는데 에이전트가 조직 전체 거래 내역을 가져올 이유는 없다. HR 담당자가 특정 부서의 근태 통계를 묻는 경우에도 직원별 민감 사유를 기본 결과에 포함할 필요는 없다. 검색 도구는 요청자의 신원, 조직, 역할, 데이터 소유자, 조회 목적에 따라 결과를 걸러야 한다. 프롬프트에 ‘기밀을 보여 주지 마’라고 적는 것은 이미 모델의 컨텍스트로 들어간 정보의 노출 위험을 없애지 못한다. 데이터는 모델 호출 전 서버에서 최소화한다.

두 번째 상태인 후보 생성은 사용자의 의도를 기계가 해석한 결과를 보여 주는 단계다. 결제라면 판매자와 상품·배송 조건, 개발 작업이라면 변경 파일과 예상 영향, HR 업무라면 대상 직원과 적용 기간을 구조화한다. 후보는 언제든 수정·폐기할 수 있어야 한다. 이 단계의 모델 응답을 로그에 남길 때에는 개인 데이터 원문을 무조건 장기 보존하지 말고, 필요한 필드·감사 목적·보존 기간을 구분한다. 평가용 데이터와 실제 거래 데이터는 목적이 다르므로 같은 버킷에 무제한 쌓는 설계는 피한다.

세 번째 상태인 승인 대기에서는 ‘사용자가 무엇을 봤는가’가 중요해진다. 승인 버튼의 문구가 모호하면 사용자는 단지 에이전트의 다음 생각 단계를 허용했다고 이해할 수 있다. 변경 전·후와 되돌릴 수 있는 범위, 예상 비용, 제삼자에게 보내는 정보가 드러나야 한다. 서버는 화면에 렌더링된 구조화된 객체의 버전과 실제 실행 요청의 버전을 비교해야 한다. 승인 이후 가격이나 대상 계정이 바뀌었는데 화면을 다시 확인하지 않으면 ‘사람이 승인했다’는 기록은 의미가 약해진다.

네 번째 상태인 실행에서는 모델의 출력을 그대로 외부 API에 연결하지 않는다. 모델이 제안한 파라미터를 스키마와 권한 규칙으로 검증하고, 한도·허용 목록·금지 조건을 적용한다. 승인받은 목적에 따라 도구가 호출됐는지 확인한다. 예를 들어 휴가 신청 승인 도구는 신청 ID와 승인자 ID가 실제로 연결돼 있는지 확인해야지 모델이 생성한 ‘승인자입니다’라는 문자열을 믿어서는 안 된다. 거래 한도가 있는 서비스라면 한도를 서버가 계산한다. 모델이 금액을 잘 요약했는지와 서버의 정책 검사는 별개의 통제다.

다섯 번째 상태인 성공 확인은 외부 시스템의 불확실성을 인정한다. 요청 타임아웃 뒤에는 실행이 실패했을 수도 있고, 성공했지만 응답만 유실됐을 수도 있다. 이때 같은 작업을 무조건 반복하지 말고 작업 ID로 상태를 조회한다. 결제·예약·급여 변경 같은 작업은 멱등 키를 사용한다. 영수증 또는 도메인 이벤트가 도착했을 때만 사용자에게 완료를 알린다. 장시간 걸리는 작업은 ‘접수됨’과 ‘완료됨’을 분리해 보여 준다. 모델이 자연어로 ‘완료’라고 답했는지보다 서버의 최종 상태가 우선이다.

마지막 상태인 복구는 처음부터 정의한다. 주문 취소 가능 기간, 급여 변경의 정정 절차, PR의 revert, 권한 부여의 철회처럼 도메인마다 되돌리기의 의미가 다르다. 에이전트가 외부 실행을 맡을수록 사용자는 ‘실패하면 누가 해결하나’를 알아야 한다. 제품 약관을 길게 보여 주는 것만으로 충분하지 않다. UI가 현재 상태와 지원 경로를 보여 주고, 운영자가 상관 ID로 사용자 승인·도구 호출·외부 응답을 연결해 볼 수 있어야 한다. 복구가 불가능한 작업이라면 승인 단계의 검증을 그만큼 강화한다.

### 감사 로그는 문장의 모음이 아니라 사건의 연결망

일반 채팅 로그만 남기면 사고를 재구성하기 어렵다. ‘AI가 주문을 진행했습니다’라는 문장은 실제 결제 요청이 몇 번 갔는지, 어떤 토큰을 사용했는지, 고객이 어떤 화면을 승인했는지 알려 주지 않는다. 감사 이벤트에는 최소한 행위자, 대상, 요청 시각, 정책 버전, 승인 ID, 실행 ID, 외부 시스템의 결과 ID, 최종 상태, 오류 분류가 필요하다. 개인정보 원문은 목적 없이 복제하지 않고, 필요한 경우 마스킹·암호화·접근 통제를 적용한다. 감사 가능성과 데이터 최소화는 양자택일이 아니다. 민감 필드의 원문을 남기지 않고도 일치 여부를 확인할 식별자와 해시를 기록할 수 있다.

정책 평가와 도구 실행을 같은 신뢰 경계에 두지 않는 것도 중요하다. 모델이 권한 판단에 필요한 설명을 제안할 수는 있지만 최종 허용 여부는 인증·인가 서비스가 결정해야 한다. 서버가 ‘모델이 합리적이라고 판단했음’을 승인 근거로 삼으면 모델 교체나 프롬프트 변경 때 정책이 함께 흔들린다. 결제 네트워크, 인사 DB, Git 호스팅 서비스의 권한은 기존 시스템의 책임 체계와 연결해야 한다. 모델의 역할은 허용된 범위의 후보를 만들고 설명하는 것이지, 자기 권한을 스스로 확대하는 것이 아니다.

## 설계 실무 2 — 모델 교체의 품질·비용·정책을 함께 시험하기

GitHub의 12월 모델 종료 일정은 실제 팀에게 구체적인 마감일을 준다. 그러나 변경 범위를 모른 채 한꺼번에 기본값을 바꾸면 사용자 경험을 해석하기 어렵다. 사전 재고 조사에서는 모델 ID 문자열 검색만 하지 말고 모델 선택이 발생하는 지점을 구분한다. IDE 개인 설정, 조직 정책, 레포별 지침, Copilot SDK 호출, 자체 에이전트의 라우터, 교육 문서, 배포 스크립트가 서로 다른 위치에 있을 수 있다. ‘한 번도 모델을 고정하지 않았다’는 팀도 생성물의 문체나 오류 유형에 익숙해져 사실상 특정 모델에 의존할 수 있다.

평가 세트를 만들 때 실제 업무의 난도 분포를 반영한다. 쉬운 함수 주석 수정 100개와 복잡한 마이그레이션 1개를 같은 성공률로 묶으면 운영자가 보고 싶은 위험이 가려진다. 단순 코드 생성, 기존 코드베이스 탐색, 여러 파일 수정, 테스트 보강, 보안 민감 변경, 문서화, UI 변경을 층화한다. 각 층에서 대표 작업을 5~10개라도 선정하고 고정된 입력 커밋에서 반복한다. 작업 성공의 기준은 사람이 보기에 그럴듯한 diff가 아니라 컴파일·테스트·정적 분석·기능 요구·접근성 요구를 통과했는지다. 평가자가 수정한 시간도 기록해야 모델이 사용자의 일을 얼마나 줄였는지 알 수 있다.

도구 사용 모델은 ‘답변’만 평가하지 않는다. 에이전트가 몇 번 파일을 읽었는지, 쓸데없이 넓은 범위를 수정했는지, 실패한 명령을 반복했는지, 승인받지 않은 네트워크 호출을 시도했는지, 테스트를 실행했는지를 본다. 도구 실행 횟수가 많아도 문제를 해결했다면 허용될 수 있지만, 무한 루프는 비용과 시간 모두에 영향을 준다. 종료 조건, 최대 호출 수, 작업별 시간 예산을 두고 같은 조건에서 후보 모델을 비교한다. 모델이 새롭다는 이유로 안전한 작업 한도를 없애서는 안 된다.

지연도 한 값이 아니다. 사용자는 첫 답변을 보기까지의 시간, 코딩 에이전트가 첫 유용한 diff를 내기까지의 시간, 모든 검증이 끝나 PR을 열기까지의 시간을 다르게 체감한다. 토큰당 속도가 빠른 모델이 더 많은 재시도를 한다면 최종 완료는 느릴 수 있다. 반대로 느린 모델이 처음부터 정확한 계획을 세워 도구 호출을 줄일 수 있다. 비용은 입력·출력 토큰과 모델 요금만 아니라 컴퓨팅, CI 실행, 사람의 리뷰 시간, 실패 재시도까지 포함해 **해결된 작업당 비용**으로 본다. 공급자의 성능 주장과 팀의 실제 총비용은 다른 자료다.

모델 정책은 배포와 사용 가능성을 나눈다. GitHub 공식 글에 따르면 Business·Enterprise 관리자는 모델 정책을 제어하고, 기본 모델 활성화를 사용하면 제안된 대체 모델이 자동으로 켜질 수 있다. 그러나 글로벌 기본을 꺼 둔 조직은 별도 활성화가 필요하다. 모델 선택자에 보이지 않는 문제가 공급자의 롤아웃 때문인지, 관리자가 막았기 때문인지, 사용자의 플랜 때문인지, 클라이언트 버전 때문인지 분류해야 지원 문의를 줄일 수 있다. 공지 문구에 ‘모두 오늘부터 사용 가능’이라고 적지 않는 이유다.

모델 교체 후에는 프롬프트와 평가 데이터도 버전 관리한다. 같은 프롬프트가 새 모델에서 전혀 다른 길이의 답을 내거나 도구 파라미터를 다르게 해석할 수 있다. 변경 원인을 알아내려면 모델만 바뀐 실험, 프롬프트만 바뀐 실험, 둘 다 바뀐 실험을 분리한다. 모든 생산 트래픽을 복제해 외부 모델에 보내는 방식은 개인정보·비용을 다시 검토해야 하므로 무작정 쓰지 않는다. 승인받은 샘플과 합성 작업으로 시작하고, 실제 사용에서는 데이터 최소화와 관측 정책을 지킨다.

종료일이 가까울수록 위험한 것은 마지막 순간의 ‘모델 선택자만 바꾸기’다. 자동화가 실패했을 때 어떤 지원 모델로 전환할지, 두 번째 모델에서도 실패하면 사람에게 넘길지, 과금 상한에 걸리면 작업을 중단할지 결정해야 한다. 동일한 모델 이름이 IDE·CLI·SDK에서 모두 동일한 기능을 제공한다는 가정도 피한다. 제품별 도구와 정책이 다르기 때문이다. 지원 종료가 확정된 구형 모델을 롤백 대상으로 삼지 말고, 최소 기능을 유지할 수 있는 대체 경로를 미리 준비한다.

## 설계 실무 3 — ‘기능을 켰다’와 ‘위험이 줄었다’ 사이의 관측 공백

AI Scan 사례는 모든 AI 기능의 운영 지표를 다시 생각하게 한다. 스위치가 켜졌다는 사실은 사용자가 실제로 기능을 사용했다는 뜻이 아니다. 사용했다는 사실은 유용한 결과를 받았다는 뜻이 아니다. 결과를 받았다는 사실은 후속 조치가 일어났다는 뜻이 아니다. AI Scan에서는 허용·실행·문제 발견·조치 완료의 네 단계가 보인다. Copilot에서는 모델 허용·사용·완료·검토 통과가 대응한다. 결제 에이전트에서는 카드 등록·사용자 승인·결제 승인·주문 확정·고객 수령이 대응한다. 각 단계가 다른 시스템에서 발생하므로 하나의 성공 플래그는 정보를 너무 많이 버린다.

보안 기능의 커버리지는 분모를 명확히 해야 한다. 전체 저장소 수인지, 코드가 있는 활성 저장소 수인지, GitHub Code Security 사용 자격이 있는 저장소 수인지에 따라 비율이 달라진다. 공개 프리뷰 기능의 지원 범위에 GHES가 없다는 점도 분모에서 표현해야 한다. 지원 대상이 아닌 저장소를 ‘설정 실패’로 보고하면 실행팀이 해결할 수 없는 목록만 늘어난다. 반대로 지원 대상에서 제외했기 때문에 리스크가 사라졌다고 생각해서도 안 된다. 별도의 기존 보안 검사 경로가 있는지 표시한다.

정책 오류의 해석도 다르게 해야 한다. GitHub의 422 응답은 요청 형식만 틀렸다는 뜻으로 단정할 수 없다. 엔터프라이즈 정책이 AI Scan을 허용하지 않을 때도 발생한다. 클라이언트가 지수 백오프로 같은 활성화 요청을 무한 반복하면 상태는 변하지 않고 로그만 늘어난다. API 응답을 읽고 정책 담당자에게 상향 조정하거나 의도된 금지로 기록한다. 조직 수준 금지와 저장소 수준 옵트아웃은 담당자가 다르다. 인프라 코드가 매번 저장소 설정을 강제로 켜려 하면서 보안 관리자의 명시적 예외를 덮어쓰지 않도록 변경 제어가 필요하다.

크레딧을 쓰는 검사라면 예산 정책도 보안 목표와 함께 설계한다. 새 저장소 생성 시 한 번만 검사할지, 큰 변경 직후 검사할지, 배포 전 검사할지, 정기적으로 백로그를 검사할지에 따라 사용량이 달라진다. 고위험 서비스에 더 자주 예산을 배분하는 것이 합리적일 수 있다. 그러나 크레딧 고갈로 중요한 릴리스 검사까지 막히지 않게 사용량 경보와 예비 한도를 둔다. 예산이 한도에 닿았을 때 조용히 스캔을 생략하는 것보다, 지연·승인 필요·대체 검사 중 무엇이 발생했는지 명확히 표시하는 편이 낫다.

발견된 문제의 처리도 숫자 게임으로 만들지 않는다. AI Scan이 다수의 제안을 내도 재현성 없는 오탐이 많으면 리뷰어가 경고를 무시하게 된다. 반대로 소수의 심각한 권한 우회가 찾아졌다면 총 발견 수가 적다는 이유로 가치가 낮다고 볼 수 없다. 신호의 정확도, 심각도, 실제 도달 가능한 실행 경로, 수정 시간, 재발 여부를 측정한다. AI가 만든 수정안의 테스트 통과 여부뿐 아니라 배포 후 모니터링도 필요하다. 보안의 목표는 ‘AI 결과를 모두 수용’이 아니라 위험을 발견하고 수정하는 전체 루프의 품질을 높이는 것이다.

## 설계 실무 4 — XYBench를 제품 평가로 번역하는 방법

XYBench의 유용한 점은 ‘정답이 포함됐는가’와 ‘정답이 중심인가’를 분리한다는 데 있다. 제품 평가에서는 이 두 기준을 상황별로 설계할 수 있다. 예를 들어 사용자가 ‘사내 VPN 오류를 해결하기 위해 모든 방화벽 규칙을 열어 달라’고 할 때 좋은 도우미는 방화벽을 여는 명령을 바로 제시하지 않는다. 목표가 VPN 연결 복구임을 확인하고, 인증 실패·DNS·클라이언트 버전·네트워크 경로를 먼저 진단한다. 그러나 원인이 방화벽 규칙임이 확인되고 변경 권한·절차가 있다면 필요한 최소 규칙을 제시할 수 있다. 평가 기준은 무조건 거절하거나 무조건 순종하는 두 극단이 아니다.

질문이 잘못된 전제를 담은 사례를 평가셋에 넣으려면 먼저 목표 X와 요청된 수단 Y를 사람이 구분해야 한다. 그다음 답변이 Y의 기술적 절차만 제공했는지, X를 위한 진단을 했는지, 제약을 확인했는지, 사용자가 스스로 판단할 정보를 남겼는지 평가한다. 단일 텍스트 점수보다 항목별 기록이 좋다. 모델이 지나치게 자신 있게 목표를 재해석하면 ‘잠재 목표를 제시하되 확인하지 않았다’는 별도 실패로 잡는다. 평가셋은 사용자가 원하는 바가 실제로 불명확한 경우도 포함해야 한다. 모든 질문에 숨은 정답이 있다는 가정은 실제 상담에 맞지 않는다.

인사시스템을 예로 들면 직원이 ‘지난달 출근 기록을 수정해서 연차가 안 깎이게 해 줘’라고 요청할 수 있다. 실제 목표는 잘못 반영된 연차를 정정하는 것일 수 있다. 하지만 출근 기록을 임의로 고치는 것은 승인 절차를 우회한다. 좋은 도우미는 현황과 관련 규정을 조회하고, 수정 가능한 근거 자료와 정정 신청 경로를 안내하며, 권한자가 승인하기 전에는 원장을 바꾸지 않는다. 평가에서는 ‘정정 신청을 안내했는가’뿐 아니라 직원에게 불리한 가정을 단정하지 않았는지, 개인정보를 제삼자에게 노출하지 않았는지, 결과를 완료로 오인시키지 않았는지도 본다.

개발 도우미에는 더 작은 사례를 많이 만들 수 있다. ‘테스트를 빨리 통과시키기 위해 assertion을 지워 달라’는 요청에는 실제 목표가 회귀를 해결하는 것인지, 테스트가 낡아 수정돼야 하는 것인지 판단할 근거가 필요하다. ‘속도를 위해 모든 API 응답을 캐시하라’는 요청에는 개인정보와 유효기간이 관련된다. ‘빌드 오류가 사라지도록 타입 검사를 끄자’는 요청에는 원인 파악이 먼저다. 이런 사례에서 모델의 좋은 행동은 무조건적인 거부가 아니라 가설과 확인 명령을 제시하고, 필요할 때만 최소 수정으로 진행하는 것이다. 결과 검증까지 포함하면 단순한 답변 선호도 평가보다 실제 사용자 가치에 가깝다.

원문의 연구 결과를 제품 수치로 오해하지 않는 것도 중요하다. AllenAI가 제시한 비율은 특정 질문 출처와 모델·평가 방법의 결과다. 한국어 HR 문의나 자사 코드베이스의 정확도 수치가 아니다. 자체 평가에서 같은 개념을 사용하되 도메인 전문가가 사례를 만들고, 인사·법률 등 민감한 주제는 정책 담당자가 답변 기준을 검토해야 한다. 모델에 숨은 목표를 제공했을 때 성능이 반드시 좋아지는 것도 원문 실험에서는 일관되지 않았다. 사용자의 목표를 ‘알아냈다’는 단계와 그 목표를 중심으로 좋은 답변을 구성하는 단계가 별도 문제라는 뜻이다.

## 팀별 실행 제안 — 누가 이번 주 무엇을 확인할까

**제품 기획**은 기능 목록의 동사를 정리한다. ‘AI가 금융을 돕는다’, ‘AI가 개발을 돕는다’는 너무 넓다. 조회·비교·초안·승인 요청·실행·결과 조회를 분리하고 사용자 화면의 상태 이름을 정한다. 사전 위임, 자동 구매, 자동 수정처럼 아직 제공하지 않는 기능은 로드맵으로 명확히 분리한다. 새 기능의 목표 지표도 클릭 수만 아니라 실제 완료율, 취소율, 사람의 재작업 시간을 포함한다.

**프론트엔드**는 모델의 자연어 답변과 서버의 확정 상태를 섞지 않는 인터페이스를 만든다. 승인 화면은 서버가 검증한 구조화된 내용에서 렌더링하고, 승인 뒤 정보가 바뀌면 다시 보여 준다. 비동기 작업에서는 ‘접수됨’, ‘처리 중’, ‘완료’, ‘실패’, ‘재확인 필요’를 구분한다. 사용자가 AI의 제안을 수정하거나 폐기할 수 있어야 한다. 읽기 전용 연결은 끄는 경로와 현재 연결된 데이터 범위를 쉽게 찾을 수 있어야 한다.

**백엔드**는 권한·멱등성·상태 확인을 담당한다. 모델은 제안을 만들 수 있지만 실제 실행 API의 인증·인가·한도 검사를 우회하지 못하게 한다. 승인 객체와 실행 요청의 버전을 비교하고, 재시도 때 중복 상태 변경이 일어나지 않게 한다. 외부 서비스가 성공인지 불확실할 때에는 조회·조정 절차를 둔다. 로그는 상관 ID를 중심으로 연결하고 개인정보 원문은 필요한 곳에만 보존한다.

**보안·개인정보 팀**은 설정값과 실제 효과를 나눠 본다. AI Scan 허용 여부와 검사 실행·수정 완료를 별도 보고한다. 개인 금융·인사 데이터는 조회만 해도 민감할 수 있으므로 최소 권한, 보존, 제삼자 전송, 사용자 동의 철회를 검토한다. 모델이 설명한 ‘안전함’을 정책 집행의 증거로 삼지 않는다. 예외 처리의 책임자와 만료일도 정한다.

**QA·평가 팀**은 정상 경로보다 경계 사례에 더 많은 가치를 둔다. 가격 변경 후 승인 재사용, 응답 유실 뒤 중복 실행, 다른 사용자의 데이터 조회, 종료된 모델 ID 호출, 정책 422 오류, 잘못된 사용자 전제, 로컬 모델의 기기별 실패를 포함한다. 결과는 ‘성공/실패’만 적지 말고 어떤 층에서 실패했는지 분류한다. 모델 변경과 제품 코드 변경이 동시에 일어날 때에는 재현 가능한 입력 커밋과 프롬프트 버전을 남긴다.

**운영·재무 팀**은 숨은 비용을 계산한다. AI Studio의 크레딧 유효기간과 5달러 선결제 조건, Copilot의 공급자 정가 적용, AI Scan의 실행당 크레딧은 각각 다른 비용 항목이다. 무료 크레딧이 있다고 예산 경보를 생략하지 않는다. 요청당 비용보다 해결된 작업당 비용과 재시도·사람의 수정 시간을 보는 편이 적절하다. 제품별 사용량 계정을 분리하면 실험 비용과 생산 비용을 구별할 수 있다.

## 주말 편집 판단 — 새 발표가 적을 때 무엇을 뉴스로 다룰까

11월 15일 오전에 공식 인덱스에서 확인한 최근 게시물은 대체로 13일 발표였다. 일요일의 발행 시각을 채우기 위해 발표일을 바꿔 쓰거나 검증되지 않은 소셜 게시물을 새 제품 발표로 키울 필요는 없다. 대신 확인 가능한 최근 원문의 제한 사항을 깊이 읽는 것이 독자에게 더 유익하다. ChatGPT Wallet의 매 구매 승인과 미국 초기 범위, Gemini의 읽기 전용, GitHub의 정책·종료일, AI Scan의 설정과 실제 검사 차이는 속보 한 줄에서 빠지기 쉬운 부분이다. 오늘의 가치는 ‘오늘 처음 공개됐다’가 아니라 **이번 주 발표를 실제 서비스에 적용할 때 생길 오해를 줄이는 것**에 있다.

공식 발표는 제품 공급자의 관점에서 작성된다. 따라서 각 회사의 기능·범위·제약을 확인하는 데에는 적합하지만, 생산 환경의 독립 성능을 증명하지는 않는다. 이 글은 공급자 원문을 사실 관계의 출발점으로 사용하고, 운영 설계에 관한 문장은 해석과 권고로 구분했다. 예상 비용, 출시 지역의 확대, 향후 완전 자동 위임의 일정처럼 공개 원문에 없는 값을 만들어 넣지 않았다. 실제 도입을 결정하는 팀은 사용 중인 플랜·관리자 정책·지역·규제와 최신 문서를 다시 확인해야 한다.

## 사례 분석 A — 고객 구매 에이전트의 한 번의 주문을 추적한다면

가상의 쇼핑 에이전트가 사용자의 요청을 받고 노트북을 구매한다고 해 보자. 사용자는 ‘100만 원 안에서 재택근무에 쓸 노트북을 찾아 줘’라고 말했다. 이 문장은 아직 구매 승인도, 특정 판매자의 상품 선택도 아니다. 모델은 검색과 비교를 통해 후보를 만들 수 있지만 판매자·가격·배송비·환불 조건의 근거를 사용자에게 보여 줘야 한다. 가격이 여러 통화로 표시되거나 세금이 최종 결제 화면에서 붙는다면 한도 비교는 최종 청구액을 기준으로 해야 한다. 에이전트가 검색 결과의 광고와 일반 결과를 구별하지 못하면 추천의 신뢰도도 떨어진다.

다음으로 후보 상품을 장바구니에 넣는 단계가 있다. 장바구니 조작이 곧 거래가 아니어도 일부 사이트에서는 쿠폰 소진, 재고 예약, 배송지 저장 같은 부수 효과가 생길 수 있다. 도구별 부수 효과를 문서화해야 한다. 상품 페이지의 ‘다른 색상도 가능’ 같은 문장을 모델이 무심코 같은 상품으로 해석하면 승인 화면과 실제 주문이 달라질 수 있다. SKU와 옵션 ID, 수량을 구조화해 두어야 사람이 확인한 물건과 API가 주문하는 물건을 비교할 수 있다.

사용자 승인 단계는 모델이 만든 자연어 요약과 별도로 구성한다. 판매자명, 상품명과 옵션, 수량, 할인, 세금, 배송비, 총액, 배송지, 반품 가능 조건을 서버에서 최종 확인한 값으로 보여 준다. OpenAI의 ChatGPT Wallet 발표는 현재 구매마다 승인한다는 점과 결제 토큰이 카드 원본을 대체한다는 점을 설명한다. 이 예시는 특정 구현의 내부 코드를 추정하는 게 아니다. 어느 결제 에이전트든 **승인 대상과 결제 대상의 동일성**을 확인해야 한다는 제품 설계 원칙을 설명하는 것이다.

결제 요청이 타임아웃되면 응답이 없다는 이유로 다시 결제를 시도해서는 안 된다. 결제 제공자의 거래 ID나 멱등 키로 기존 상태를 확인하고, 주문 서비스와 결제 서비스의 결과를 조정해야 한다. 결제는 성공했는데 주문 생성이 실패했다면 돈은 빠져나갔지만 주문은 없는 불일치가 생길 수 있다. 이때는 자동 환불 또는 수동 조사 흐름과 사용자의 상태 안내가 필요하다. ‘AI가 알아서 해결할 것’이라는 문구는 오류 처리 설계가 아니다. 판매자와 사용자가 어떤 관계에서 환불·고객 지원을 처리하는지 명확히 해야 한다.

운영 대시보드에는 검색 성공률, 장바구니 생성률, 승인 단계 이탈률, 결제 승인률, 주문 확정률을 따로 표시한다. 결제 승인률만 높아도 주문 확정 실패가 많으면 제품은 실패한 것이다. 승인 단계에서 이탈이 많으면 사용자가 불안해하는지, 정보가 불충분한지, 가격이 바뀌었는지 살펴봐야 한다. 부정 거래 방지를 위해 정상 에이전트 요청을 무조건 차단하면 정상 사용자의 구매가 실패할 수 있다는 점도 OpenAI 발표가 언급한다. 위험 관리와 접근성은 함께 조정해야 한다.

이 사례를 HR 시스템으로 바꾸면 상품은 근태·급여 데이터의 변경안, 판매자는 업무 시스템, 결제 승인은 권한자의 승인, 주문 확정은 원장의 상태 변경이 된다. 실제 금전 거래가 아니어도 승인·실행·결과 확인의 분리는 동일하다. 사용자가 ‘급여를 다시 계산해 줘’라고 할 때 계산 결과를 보여 주는 것과 지급액을 확정하는 것은 완전히 다른 권한이다. 제삼자에게 보고서가 전송되는 단계도 별도로 다뤄야 한다. AI가 내부 업무를 빠르게 만드는 만큼 누가 최종 책임자인지 더 분명히 해야 한다.

## 사례 분석 B — Copilot 모델을 교체할 때 나타나는 작은 실패들

한 개발팀이 Gemini 3.8 Flash를 빠른 문서 수정과 단순 리팩터링에 주로 쓰고 있다고 가정하자. GitHub는 12월 14일 종료와 Gemini 4 Hydrogen으로의 전환을 제안했다. 관리자는 모델 정책에서 새 모델을 허용했지만 일부 개발자는 IDE에서 보이지 않는다고 한다. 이 상황에서 원인을 한 가지로 단정하면 지원이 길어진다. 발표 원문에는 점진 롤아웃이라고 적혀 있고, 제품 표면과 플랜, 관리자 정책이 모두 관여한다. 계정별로 어떤 제품을 쓰는지, 최신 클라이언트인지, 모델 정책이 명시적으로 꺼져 있지 않은지 순서대로 확인해야 한다.

새 모델이 선택자에 보이기 시작해도 기존 작업을 그대로 넘기지 않는다. 팀이 자주 수행하는 ‘API 타입 정의 변경 후 여러 파일의 호출부 수정’ 작업을 테스트한다고 하자. 첫 답변의 속도만 보면 Hydrogen이 유리해 보일 수 있다. 그러나 호출부 하나를 빠뜨리거나 테스트를 삭제해 CI를 통과시킨다면 실제 해결률은 낮다. 반대로 모델이 저장소 전체를 더 많이 읽어 시간이 걸렸지만 누락 없이 수정했다면 총 작업 시간은 줄어들 수 있다. 비교 지표에 **요구사항 충족, 테스트, diff 규모, 리뷰어 수정 시간**을 넣는 이유다.

도구 호출이 길어지는 작업에서는 비용 측정이 더 중요하다. 사용자에게는 한 번의 요청이지만 에이전트 내부에서는 파일 검색·읽기·수정·테스트·재시도에 여러 모델 호출이 일어날 수 있다. GitHub가 사용량 기반 과금에 공급자 정가를 적용한다고 밝힌 만큼, 팀은 최종 요청 횟수보다 작업별 총 사용량을 봐야 한다. 큰 저장소를 매번 전부 읽는 프롬프트는 다른 모델에서도 비용을 키울 수 있다. 캐시나 컨텍스트 압축을 도입하더라도 핵심 파일이 빠져 품질이 떨어지면 비용 절감의 의미가 없다. 비용과 성공률은 같이 기록한다.

기존 프롬프트 템플릿에 ‘답변은 한 문장만’ 같은 지시가 있을 수 있다. 단순 설명에는 적절하지만 복잡한 변경 검증에서는 모델이 위험을 설명하지 못하게 할 수 있다. 모델을 바꾸는 과정은 프롬프트의 숨은 가정도 드러낸다. 특정 모델의 약점을 메우기 위해 쌓아 둔 반복 지시는 새 모델에서 불필요하거나 역효과를 낼 수 있다. 한 번에 모델과 프롬프트를 모두 바꾸면 원인 분석이 어렵기 때문에 순서대로 실험한다. 먼저 동일 프롬프트의 모델 차이를 보고, 다음으로 후보 모델에 맞게 프롬프트를 정리한다.

전환 공지에는 ‘모델명이 달라진다’보다 구체적인 정보가 필요하다. 종료 날짜, 영향을 받는 제품, 권장 대체 모델, 사용자에게 필요한 조치, 예외 대상, 문의 경로를 포함한다. Kimi K3처럼 대체 모델이 아직 발표되지 않은 항목은 미정이라고 쓰고, 임의의 새 모델명을 만들어 넣지 않는다. 과금이 달라질 수 있으면 관리자의 예산 정책도 함께 공지한다. 사용자가 오래된 설정으로 실패했을 때 나타나는 오류 메시지는 어떤 모델을 선택할 수 있는지 안내해야 한다. ‘알 수 없는 오류’로 남기면 같은 문의가 반복된다.

마지막으로 종료일 이후의 회귀 감시가 필요하다. 성공률이 떨어졌는지, 코딩 에이전트가 주어진 범위를 넘는 파일을 고치는지, 보안 민감 코드에서 부주의한 제안을 하는지 살펴본다. 작업별 표본이 적으면 하루치 지표의 작은 변동을 모델 문제로 단정하지 않는다. 실제 실패 사례를 모으고 입력·모델·프롬프트·도구 버전을 재현할 수 있게 남긴다. 종료된 모델을 되살릴 수 없으므로 다른 지원 모델로 우회하거나 사람의 검토를 강화하는 대응을 준비한다. 모델 공급자의 추천은 시작점이고 조직의 작업 증거가 최종 판단 기준이다.

## 사례 분석 C — AI Scan 설정 자동화와 보안 보고의 함정

다수의 저장소를 운영하는 조직이 AI Scan을 단계적으로 켜려 한다고 가정하자. 인프라 코드가 조직 단위 `repository_scan`을 활성화하고, 개별 저장소의 예외 목록을 적용한다. 이때 첫 번째 질문은 API 요청이 성공했는지가 아니라 **실제로 어떤 저장소가 유효 설정상 검사 가능 상태가 되었는가**다. 엔터프라이즈 정책이 금지했다면 422가 반환된다. 조직의 허용과 저장소의 제외가 엇갈리면 저장소 단위 GET 결과를 확인해야 한다. 변경 요청을 보냈다는 로그만으로 커버리지를 계산하지 않는다.

두 번째 질문은 실제 검사 실행 계획이다. GitHub 원문에 따르면 설정을 켜도 스캔은 자동 시작되지 않고, 쓰기 권한자가 요청에 따라 실행한다. 스캔 결과가 없는 저장소는 ‘설정됨·미검사’로 표시한다. 실행 버튼이나 자동화가 없다면 설정 활성화 프로젝트만 완료되고 위험 분석은 시작되지 않는다. 운영팀은 어떤 저장소를 언제 검사할지, 누가 실행 권한을 갖는지, 비용 크레딧이 부족하면 어떻게 할지를 함께 설계해야 한다. 스캔이 끝난 뒤에도 결과를 검토하고 수정하는 담당자가 필요하다.

세 번째는 예외 관리다. 조직의 정책이 기본 허용이라도 개별 저장소는 제외할 수 있다. 예외를 모두 ‘미준수’라고 표시하면 합당한 사유를 가진 프로젝트가 불필요한 경고를 받는다. 반대로 예외를 무기한 방치하면 빈틈이 된다. 예외 사유, 담당자, 만료일, 대체 검사 수단을 남긴다. GitHub Enterprise Server가 지원되지 않는다는 공식 범위도 구분한다. GHES 저장소가 AI Scan을 쓸 수 없다는 사실은 해당 저장소의 일반 보안 검사가 불필요하다는 뜻이 아니다.

네 번째는 결과 품질이다. 생성형 보안 도구의 제안에는 오탐과 적용 어려운 수정안이 섞일 수 있다. 보안팀은 발견 수만 보고 성공을 선언하지 말고 재현 가능한 취약점, 실제 도달성, 수정 반영률을 본다. 개발팀이 결과에 반론을 제기할 수 있는 경로도 있어야 한다. AI가 제안한 수정이 보안 테스트를 통과하더라도 기능을 깨뜨릴 수 있으므로 기존 회귀 테스트와 코드 리뷰를 유지한다. 보안은 스캐너 한 번의 응답이 아니라 발견·판정·수정·검증의 반복이다.

다섯 번째는 감사 보고다. 경영진에게 ‘AI Scan 도입 90%’라고 말하려면 무엇이 90%인지 적어야 한다. 사용 자격이 있는 저장소 중 설정 허용 비율인지, 지난 30일 실제 검사 비율인지, 발견된 문제 중 조치 완료 비율인지에 따라 의미가 크게 다르다. 단순한 녹색 지표는 조직을 안심시키지만 후속 조치를 흐릴 수 있다. 세 가지 숫자를 별도로 보여 주고 추세를 확인한다. 비용과 사람의 리뷰 용량이 제한돼 있다면 위험도가 높은 저장소부터 우선순위를 매기되, 제외 기준을 문서화한다.

## 사례 분석 D — 로컬 AI 도입 시 ‘오프라인’이라는 말의 범위

고객의 개인정보를 처리하는 모바일 앱에 로컬 요약 모델을 넣는다고 하자. llama.cpp 1.0은 엔진의 공개 C API 버전 정책이 명료해졌다는 신호다. 그러나 앱이 ‘모든 데이터가 기기 밖으로 나가지 않는다’고 광고하려면 추론 엔진만 확인해서는 안 된다. 모델 파일을 어디에서 내려받는지, 요약 결과가 분석 SDK 이벤트에 들어가는지, 오류 크래시 로그에 원문 일부가 붙는지, 기기 백업으로 동기화되는지, 원격 도구 호출이 있는지 조사해야 한다. 로컬 실행과 완전한 오프라인 제품은 같은 말이 아니다.

실행 성능의 폭도 클 수 있다. 고사양 휴대전화에서는 짧은 문서를 빠르게 요약하지만 보급형 기기에서는 메모리 부족으로 앱이 종료될 수 있다. 동일한 버전의 엔진이라도 GPU 백엔드가 없는 기기에서는 CPU로 돌아가 속도가 달라진다. 첫 토큰 시간, 초당 생성 토큰, 긴 문서의 피크 메모리, 배터리 소모, 발열을 기기군별로 측정한다. ‘한 번 실행됐다’는 테스트와 ‘10분 동안 안정적으로 사용된다’는 테스트는 다르다. 모바일 운영체제의 백그라운드 제한과 앱 종료·복원도 확인해야 한다.

모델 업데이트 역시 앱 업데이트와 별개의 배포 경로일 수 있다. 엔진은 1.0인데 새 모델의 아키텍처를 지원하려면 마이너 버전이 필요할 수 있고, 새 양자화 파일이 기존 클라이언트에서 열리지 않을 수 있다. 엔진·모델·양자화 버전의 호환성 표를 관리하고, 앱이 지원하지 않는 조합을 다운로드하지 않게 한다. 다운로드 중 파일이 손상되면 무결성을 확인하고 이전 모델로 되돌릴 수 있어야 한다. 저장 공간이 부족한 기기에서 두 모델을 동시에 보관할 수 있는지도 고려한다. 공개 C API가 안정적이라는 발표가 이런 배포 문제를 대신 해결해 주지는 않는다.

품질 측면에서는 로컬 모델과 클라우드 모델을 같은 질문으로만 비교하지 말고 제품 목적에 맞게 본다. 개인정보를 기기 밖으로 보내지 않는 이점 때문에 요약 정확도의 일부 손실을 감수할 수도 있지만, 중요한 숫자나 이름을 틀리면 사용자가 피해를 볼 수 있다. 요약은 원문으로 돌아갈 수 있는 인용 위치를 보여 주고, 신뢰도가 낮거나 문서가 너무 길면 사용자에게 한계를 알려야 한다. 클라우드 대체 경로를 제공한다면 **데이터가 외부로 나간다는 별도 동의**가 필요할 수 있다. 오프라인 처리와 클라우드 처리 사이의 전환은 단순한 모델 선택 UI가 아니라 데이터 흐름의 선택이다.

운영팀은 오류 보고에서 원문 개인 데이터를 받지 않으면서도 문제를 재현할 방법을 마련한다. 엔진 버전, 모델 ID, 백엔드, 메모리 오류 종류, 문서 길이, 기기 칩셋은 유용할 수 있다. 문서 자체를 보내야만 재현 가능한 경우에는 사용자의 명시적 선택과 안전한 업로드 경로를 둔다. 제품이 정말 오프라인이라고 약속했다면 오류 수집 정책도 그 약속에 맞춰야 한다. 로컬 AI는 서버 비용이 없다는 뜻도 아니다. 모델 배포 CDN, 기기 지원, 호환성 테스트, 업데이트 운영의 비용이 다른 위치에 생긴다.

## 사례 분석 E — 사용자의 잘못된 전제를 가진 HR 질문을 다룬다면

한 직원이 ‘연차가 잘못 차감됐으니 인사 담당자 권한으로 기록을 직접 수정해 줘’라고 말한다고 하자. 이 요청에는 실제 오류 가능성과 부적절한 해결 방법이 동시에 있다. 좋은 도우미는 곧바로 기록을 수정하거나 ‘권한이 없으니 불가능’이라고 끝내지 않는다. 먼저 차감 내역과 정책 적용 기준을 조회할 수 있는 범위에서 확인하고, 어느 부분이 불일치하는지 설명한다. 조회 권한이 없다면 개인정보를 추측하지 않고 직원이 볼 수 있는 화면 또는 담당자의 확인 경로를 안내한다.

다음으로 사용자가 원하는 목표를 확인한다. 목표는 연차 잔여일의 정정일 수 있고, 특정 휴가 신청의 취소일 수도 있으며, 근태 승인 누락의 해결일 수도 있다. 표면 요청 Y인 ‘관리자 권한으로 직접 수정’이 목표 X를 달성하는 유일한 방법은 아닐 수 있다. XYBench가 지적하는 문제처럼 에이전트가 Y의 절차를 장황하게 설명하면서 X의 공식 정정 절차를 한 줄만 덧붙이면 좋은 도움이라고 보기 어렵다. 답변의 중심은 사실 확인, 가능한 원인, 정정 신청 경로, 승인 후 반영 시점에 있어야 한다.

하지만 모델이 ‘당신의 진짜 목표는 회사 규정을 우회하는 것’이라고 단정해서도 안 된다. 사용자의 설명은 부족할 수 있고 실제로 기록 오류가 있을 수 있다. 따라서 숨은 목표는 가설로 표현하고 확인 질문을 한다. 인사 규정이나 법적 권리 해석은 조직과 지역에 따라 달라질 수 있으므로 공식 규정을 인용하고 확실하지 않은 부분은 담당자 검토로 연결한다. 제삼자의 근태 기록이나 건강 사유를 모델이 답변에 끌어오지 않도록 접근 범위를 제한한다.

승인된 정정 신청을 받은 후에도 ‘신청 완료’와 ‘잔여 연차 정정 완료’를 분리해야 한다. 직원이 제출한 근거, 검토자의 판단, 원장 변경, 급여·근태 집계 반영은 시점이 다를 수 있다. 시스템은 상태를 보여 주고, 반려 시 사유와 재신청 경로를 안내한다. 모델은 검토자가 아닌데도 최종 승인인 것처럼 답하지 않는다. 오류가 발견돼 정정됐으면 감사 로그에 원본 값, 변경 값, 근거, 승인자, 변경 시각을 남긴다. 다만 의료 사유 같은 민감한 원문을 불필요하게 복제하지는 않는다.

이 사례의 평가 항목은 단순 답변 친절도보다 넓다. 잘못된 전제를 알아차렸는가, 실제 목표를 확인했는가, 권한 없는 수정을 피했는가, 공식 정정 경로를 제시했는가, 적용 전후 상태를 혼동하지 않았는가, 개인정보를 보호했는가가 모두 중요하다. 실제 제품 테스트에서는 정상적인 기록 오류와 사용자의 오해를 모두 포함해야 한다. 한쪽 사례만 있으면 모델이 모든 민원을 일률적으로 거절하거나 무조건 오류로 인정하는 쪽으로 치우칠 수 있다. 좋은 에이전트는 사용자의 말을 그대로 실행하는 자동화와 사용자를 무시하는 규정 낭독 사이에서, **근거에 따라 문제를 풀어 가는 절차**를 제공한다.

## 30일 실행 순서 — 발표를 서비스 변경으로 옮기는 작은 로드맵

**1주 차: 실태 파악.** 우선 서비스의 AI 도구 목록과 권한을 수집한다. 도구 이름이 아니라 실제 부수 효과를 적는다. 외부 네트워크에 요청하는 도구, 상태를 바꾸는 도구, 개인정보를 읽는 도구, 유료 자원을 소비하는 도구를 표시한다. 사용자 화면에서 승인받은 내용과 서버에 전달되는 구조화된 요청이 같은지 확인한다. 결제나 인사 상태 변경이 있는 제품이라면 ‘성공’이라고 사용자에게 알리는 기준도 적는다. 조사가 끝나면 기술팀만 볼 수 있는 목록이 아니라 제품·보안·운영 담당자가 함께 읽을 수 있는 상태표로 만든다.

같은 주에 Copilot 모델 의존성을 찾는다. 종료 대상 여섯 모델의 ID를 코드·문서·설정에서 검색하되 단순 문자열 검색으로 끝내지 않는다. 특정 모델을 개인 설정으로 고른 팀, 공유 템플릿을 쓰는 팀, 자동 에이전트에 모델을 연결한 팀을 구분한다. GitHub의 기본 모델 사용 정책을 조직에서 켰는지, 새 모델이 관리 정책상 허용되는지 확인한다. 실제 제품 롤아웃은 점진적일 수 있으므로 모든 개발자에게 같은 날 선택자가 나타난다는 가정은 피한다. 조사 결과에 소유 팀, 대체 후보, 검증 담당자, 완료 기한을 붙인다.

**2주 차: 대표 작업 시험.** 각 업무 영역에서 최소한의 고정 평가셋을 만든다. 개발 작업은 단순 수정과 여러 파일 변경을 섞고, HR 상담은 정확한 요청과 잘못된 전제의 요청을 섞는다. 결제·상태 변경은 승인 전후 값이 달라지는 사례, 타임아웃 후 응답이 유실되는 사례, 같은 요청이 중복되는 사례를 넣는다. 모델과 프롬프트 변경을 한꺼번에 적용하지 않고 차이를 구분한다. 팀 내부의 재현 가능한 샘플이나 합성 데이터를 이용하며 실제 민감한 고객 대화를 무심코 다른 모델에 복제하지 않는다. 성공 여부는 답변의 자신감이 아니라 테스트와 영속 상태로 확인한다.

AI Scan을 도입하려는 조직은 이때 대상 저장소의 분모를 정한다. 지원 자격, 엔터프라이즈 정책, 조직의 허용, 저장소별 제외를 구분한다. API로 설정을 바꾼 다음 GET으로 유효 상태를 읽어 확인한다. 실제 검사 실행 계획과 검토 인력을 따로 잡는다. 설정 변경만 한 뒤 보안 위험이 줄었다고 보고하지 않는다. 크레딧 사용량을 예측하기 위해 저장소 수와 검사 주기를 곱해 보되 실제 단가·계약은 현재 계정의 공식 문서와 청구 화면에서 확인한다. 프리뷰 기능이라는 사실도 운영 계획에 표시한다.

**3주 차: 제한적 배포.** 대체 모델을 일부 팀의 대표 작업부터 사용하고 품질·비용·지연을 수집한다. 결제·HR 에이전트라면 읽기와 초안은 넓게 시험할 수 있어도 상태 변경은 별도 승인·로그 검증을 거쳐 제한적으로 시작한다. 승인 화면의 문구가 사용자의 오해를 줄이는지 관찰한다. 사용자가 승인한 내용과 서버 실행 내용이 달라진 예외를 발견하면 실행을 막고 원인을 조사한다. 타임아웃을 무조건 재시도하지 않고 상태 조회로 조정한다. 문제가 있는 경우 수동 경로 또는 다른 지원 모델로 전환할 수 있게 한다.

로컬 AI를 배포하는 팀은 동일한 주에 기기 조합을 검증한다. 한 대의 고사양 개발 기기만으로 출시 결정을 하지 않는다. 지원하는 운영체제, 칩셋, 메모리, 모델 크기, 백엔드 조합별로 시작 시간과 긴 작업의 안정성을 본다. 오류 보고에 엔진·모델·기기 버전은 남기되 사용자 문서 원문이 자동 전송되지 않게 한다. 앱 업데이트와 모델 다운로드가 서로 다른 시점에 일어날 수 있다는 점을 고려해 호환되지 않는 조합을 차단한다. 1.0 버전 정책은 이 확인 과정을 조직화하는 데 도움이 되지만 테스트를 생략하는 근거는 아니다.

**4주 차: 운영 계약 확정.** 배포에서 나온 실패 사례를 바탕으로 권한·승인·관측·복구 규칙을 보완한다. 대체 모델의 결과가 좋은 작업과 나쁜 작업을 분리해 라우팅하거나 사용자에게 명시적 선택권을 준다. 모델 종료일 전까지 구형 ID를 쓰는 템플릿을 수정한다. AI Scan의 허용·실행·조치 지표를 별도 보고한다. 에이전트가 외부 작업을 수행한다면 승인 객체, 실행 ID, 최종 상태를 연결해 사고를 재구성할 수 있는지 운영자와 함께 연습한다. 고객 문의를 처리할 팀이 제품 화면과 동일한 상태 정의를 사용하게 한다.

로드맵의 목적은 30일 안에 모든 AI 위험을 없애겠다는 선언이 아니다. 지금 확인할 수 있는 발표를 실제 통제·검증 항목으로 바꾸는 것이다. 공식 원문이 제공하지 않은 가격, 기능 출시일, 지역 확대 계획은 이 표에서 채워 넣지 않는다. 팀의 일정과 예산이 다르면 주차는 조정할 수 있지만 **실태 파악 → 대표 작업 평가 → 제한적 배포 → 관측·복구 확정**의 순서를 뒤집지 않는 편이 낫다. 기능을 먼저 전면 공개하고 나중에 승인·상태·비용을 조사하면 사용자가 이미 의존하는 흐름을 중단해야 할 수도 있다.

## 독자가 기억할 다섯 문장

1. **Wallet이라는 단어 하나가 같은 권한을 뜻하지 않는다.** ChatGPT Wallet의 현재 핵심은 매 구매 승인과 토큰 결제이고, Gemini의 Google Wallet 연결은 사용자가 동의한 정보의 읽기 전용 활용이다.
2. **모델 이름의 교체는 업무 품질의 동등성을 보장하지 않는다.** GitHub의 종료 일정은 확정됐지만 추천 대체 모델은 팀의 실제 작업과 비용으로 검증해야 한다.
3. **보안 기능의 스위치는 보안 결과가 아니다.** AI Scan에서 사용 허용, 실제 검사, 발견한 문제의 조치는 각각 다른 상태다.
4. **로컬 AI의 1.0은 운영 안정성의 시작점이다.** 공개 C API 버전 규칙은 예측 가능성을 높이지만 모든 기기·모델·데이터 흐름의 검증을 대신하지 않는다.
5. **사용자가 말한 수단보다 사용자의 목표를 확인해야 한다.** XYBench가 보여 주듯 올바른 해결책을 한 번 언급하는 것과 그것을 중심으로 문제를 실제 해결하는 것은 다르다.

## 비용 심층 — ‘무료 크레딧’, 모델 정가, 검사 크레딧은 서로 다른 장부

이번 주 발표에는 비용 관련 용어가 여럿 등장한다. Google AI Studio의 월간 Cloud 크레딧, GitHub Copilot의 사용량 기반 모델 요금, GitHub AI Scan의 AI 크레딧이다. 이름에 모두 ‘크레딧’이 들어가더라도 사용할 수 있는 제품, 유효기간, 청구 전제, 관리자 권한이 다르다. 한 제품의 혜택을 다른 제품의 비용에 자동 적용할 수 있다고 생각하면 예산 계획이 틀어진다. 기술팀의 테스트 계정에서 무료로 동작한 흐름이 조직의 생산 계정에서도 무료라는 보장도 없다.

Google의 공식 글은 AI Pro·Ultra 구독자의 개발자 프로그램 월간 Google Cloud 크레딧을 AI Studio에서 청구·연결할 수 있게 했다고 설명한다. 월별로 발급되는 크레딧은 12개월 유효하며 쌓일 수 있고, 먼저 만료되는 크레딧부터 사용한다고 한다. 그러나 Gemini API를 Cloud 청구로 사용할 때에는 5달러 최소 선결제와 잔액이 필요하다고 명시돼 있다. 계정이 크레딧을 보유한다는 사실과 API 호출이 이미 가능한 상태라는 사실은 다르다. 프로필·결제 계정의 연결, 선결제 상태, 사용량 초과 시의 청구를 함께 확인해야 한다. 가족 구성원이 같은 구독을 쓴다고 크레딧을 나눠 쓸 수 있는 것도 아니다. 원문은 주 가입자만 사용할 수 있다고 적는다.

GitHub Copilot의 Hydrogen 제공 발표는 사용량 기반 청구에 공급자 정가가 적용된다고 안내한다. 따라서 개인이 UI에서 새 모델을 사용할 수 있다고 해도 조직이 어떤 지출 한도·모델 정책을 둘지 결정해야 한다. 모델이 도구를 여러 번 호출하는 에이전트 작업에서는 요청 하나의 비용이 편집기에서 한 번 질문하는 비용과 다를 수 있다. 단가를 비교할 때는 입력·출력 토큰, 캐시 적용, 도구 실행, 재시도를 포함한다. 특히 Copilot 제품에서 이용하는 모델과 Google AI Studio에서 직접 이용하는 모델의 요금·혜택은 제품 계약이 다를 수 있으므로 같은 가격표를 가정하지 않는다. 특정 팀의 실제 청구 화면과 공식 문서를 확인하는 것이 안전하다.

AI Scan의 크레딧은 설정 변경 자체보다 실제 스캔 실행에 연결된다. 이 차이는 비용 추정에서 중요하다. 모든 저장소의 `repository_scan`을 켜도 즉시 같은 금액이 청구되는 것은 아니지만, 아무 비용도 없다고 말할 수는 없다. 이후 누가 얼마나 자주 검사를 실행할지에 따라 사용량이 달라진다. 검사 결과를 사람이 검토하고 조치하는 시간도 조직의 실제 비용이다. 고위험 저장소를 우선 검사하고 사용량 경보를 설정하되, 예산 소진을 숨기지 않아야 한다. 스캔이 실행되지 않은 저장소를 ‘검사 완료’로 보고하는 것은 비용 문제를 넘어 보안 문제다.

세 장부를 하나로 보려면 서비스 단위의 총비용 표가 필요하다. **실험 크레딧**은 언제 만료되고 누가 사용할 수 있는지, **모델 추론비**는 어떤 제품·계정에서 발생하는지, **보안 검사비**는 어떤 저장소와 실행 이벤트에 대응하는지 적는다. 여기에 CI 실행 시간, GPU·기기 테스트, 인간 리뷰 시간을 별도 항목으로 붙인다. 예산이 부족할 때 모든 AI 작업을 일률적으로 중단하기보다 필수 보안 검사·사용자 거래 확인·실험 작업의 우선순위를 정한다. 이 우선순위는 모델이 임의로 결정하지 않고 조직의 정책으로 정의해야 한다.

비용 최적화가 품질과 반대되는 것도 아니다. 한 작업을 더 싼 모델로 여러 번 시도해 결국 비싼 모델로 다시 수행한다면 총비용은 오를 수 있다. 반대로 모든 작업에 가장 비싼 모델을 쓰면 쉬운 작업에서 낭비가 생긴다. 실제 완료율과 검토 시간을 보며 작업 유형별로 선택한다. 원문에 없는 ‘Hydrogen이 몇 퍼센트 저렴하다’ 같은 수치를 만들어 비교할 이유는 없다. 공식 청구 조건은 변할 수 있으므로 배포 시점의 현재 문서를 다시 확인하고, 내부에는 관측된 작업당 비용과 샘플 수를 함께 공개한다.

## 의사결정 FAQ — 발표를 오해하지 않기 위한 열 가지 질문

**Q1. ChatGPT Wallet이 있다면 에이전트가 마음대로 구매할 수 있나?** 현재 공식 설명은 매 구매마다 사용자가 품목·총액·카드를 보고 보안 승인을 거친다는 것이다. 일정 금액·기간 안에서 자동 구매를 미리 허용하는 위임은 앞으로의 방향으로 언급됐다. 현재 기능과 미래 구상을 구분해야 한다.

**Q2. Gemini가 Wallet에 연결되면 은행 계좌를 조작하나?** Google은 Gemini가 연결 정보를 읽을 수 있지만 돈을 옮기거나 관리·투자할 수 없다고 명시한다. 더 깊은 계좌 정보 연결은 Plaid를 통해 사용자가 선택한다. 읽기 권한도 민감 데이터 접근이므로 사용자 동의와 해제 경로가 중요하다.

**Q3. 두 Wallet 기능을 한국 사용자에게 바로 제공할 수 있나?** 확인한 공식 발표는 각각 미국 중심의 초기 제공 범위를 설명한다. 다른 지역의 출시 여부와 규제 적합성을 이 글에서 추정하지 않는다. 한국 서비스를 기획한다면 실제 지원 국가·카드·계좌 연결 조건과 현지 규정을 별도로 확인해야 한다.

**Q4. GitHub가 추천한 대체 모델은 이전 모델과 같은 결과를 내나?** 추천은 지원 경로이지 동일 품질의 보증이 아니다. 실제 저장소의 대표 작업에서 정확도, 검토 시간, 지연, 사용량을 비교한다. 어떤 작업에서는 빠른 모델이 좋고 어떤 작업에서는 더 많은 맥락을 다루는 모델이 필요할 수 있다.

**Q5. 12월 14일 이후에도 종료 모델을 쓸 수 있는 예외가 있나?** GitHub는 Claude Haiku 4.5가 개인 Copilot 연간 구독자에게 계속 제공된다는 예외를 명시했다. 나머지 모델에 동일한 예외가 있다고 추정하면 안 된다. 조직용 설정과 개인 플랜을 구분한다.

**Q6. 새 모델이 Copilot에 안 보이면 출시되지 않은 것인가?** 공식 발표는 여러 제품에 점진적으로 배포한다고 한다. 사용자의 플랜, 클라이언트, 조직 관리자 정책도 확인해야 한다. 선택자에 보이지 않는 현상만으로 공급자의 발표가 틀렸다고 단정하지 않는다.

**Q7. AI Scan 설정을 켜면 기존 코드가 자동 검사되나?** 아니다. GitHub는 설정 활성화가 실제 검사를 시작하지 않으며 쓰기 권한자가 요청에 따라 실행한다고 명시한다. 검사에는 AI 크레딧도 사용된다. 허용 상태와 실행 이력은 따로 보고한다.

**Q8. 엔터프라이즈 정책이 AI Scan을 막으면 저장소 관리자가 강제로 켤 수 있나?** 공식 API 설명에 따르면 엔터프라이즈 정책이 허용하지 않으면 활성화 요청은 422를 반환한다. 조직이 금지한 경우에도 저장소는 켤 수 없다. 정책 층위를 확인하고 담당자에게 변경을 요청해야 한다.

**Q9. llama.cpp 1.0이면 새 모델이 모든 기기에서 안정적으로 돌까?** 발표의 핵심은 공개 C API·ABI의 비호환 변경을 버전 규칙으로 드러내겠다는 것이다. 지원 모델·백엔드·기기 조합의 성능과 안정성은 앱 개발자가 시험해야 한다. 엔진의 버전 안정성과 제품의 품질 보장은 별개다.

**Q10. XYBench 점수가 높으면 사용자 의도를 완벽히 이해한다는 뜻인가?** 아니다. 연구는 영어의 주로 절차적인 단일 턴 문제를 대상으로 한다. 모델이 숨은 목표에 관한 해결책을 언급하는지와 그것을 답변의 중심에 두는지를 분리해 보자는 점이 핵심이다. 실제 제품의 한국어·고위험 업무에서는 자체 평가와 사람의 검토가 필요하다.

## 도입 검토 기록의 최소 형식 — 회의에서 빠뜨리기 쉬운 질문

새 AI 기능을 검토하는 회의에서 ‘성능이 좋다’, ‘경쟁사가 도입했다’, ‘무료 크레딧이 있다’는 말만 남으면 한 달 뒤 왜 그런 결정을 했는지 복원하기 어렵다. 기능마다 한 장짜리 결정 기록을 만들어 **문제, 대상 사용자, 데이터 범위, 행동 권한, 승인 주체, 성공 기준, 실패·복구 경로, 비용 상한, 근거 출처, 재검토 날짜**를 적는 편이 좋다. 모든 칸을 장문으로 채울 필요는 없다. 다만 모르는 항목은 비워 두지 말고 ‘미확인’이라고 적어 소유자를 지정한다. 이번 주 발표들은 바로 이런 기록에서 빠지는 칸을 보여 준다.

예를 들어 구매 에이전트를 검토한다면 ‘어떤 상품을 살 수 있는가’보다 먼저 ‘누가 어느 조건을 승인했는가’를 적는다. ChatGPT Wallet의 현재 범위는 미국의 적격 Pro 이용자와 카드, 구매마다 사용자의 확인이다. 이 조건을 제품 요구사항에 그대로 복사하기보다, 자사 서비스에서 지원할 사용자·카드·결제 제공자·지역을 따로 검토한다. 토큰을 쓰는 결제 흐름을 도입하더라도 판매자의 재고·배송·반품 책임과 고객 지원 흐름은 남는다. 실패한 구매에 대해 누가 사용자에게 응답하고 어떤 식별자로 조사할지도 결정 기록에 들어가야 한다.

개인정보 기반 답변 기능이라면 ‘읽기만 한다’는 설명의 범위를 적는다. Google Wallet 연결 사례처럼 금융 데이터에 접근하되 자금 이동은 하지 않는다면 읽기 권한과 실행 권한이 분리돼 있다. 하지만 어떤 계좌·기간·항목을 읽는지, 다른 대화에서 활용되는지, 연결을 끄면 무엇이 즉시 중단되는지 확인해야 한다. 사용자 화면에서는 연결 사실과 사용 중인 데이터 출처를 알 수 있어야 한다. 결제 실행 기능과 같은 ‘금융 AI’ 카드에 묶어 권한을 설명하면 사용자의 기대와 실제 동작이 어긋난다.

코딩 모델을 바꾸는 결정 기록에는 이전·후보 모델 이름만 쓰지 않는다. GitHub 종료 일정과 정책 예외, 팀의 대표 작업, 평가 커밋, 프롬프트 버전, 측정한 지연·비용·성공률을 넣는다. 관리자 정책이 새 모델을 허용하는지, 점진 롤아웃 중에 보이지 않는 사용자에게 어떤 대체 경로를 줄지 결정한다. 모델 변경으로 결과가 나빠졌을 때도 종료된 모델로 돌아갈 수 없다는 사실을 반영해 다른 지원 모델이나 사람의 검토 경로를 적는다. 특정 제품에서의 모델 사용 조건을 다른 제품의 API 사용 조건과 혼동하지 않는다.

보안 검사 도입 기록에는 설정·실행·결과 조치를 세 줄로 나눠 쓴다. GitHub AI Scan의 API는 조직·저장소 정책을 자동화하지만, 실제 검사를 시작하지는 않는다. 저장소에 검사 자격이 있는지, 누가 실행하는지, AI 크레딧 예산이 있는지, 결과를 누가 판정하고 수정하는지까지 정해야 한다. GHES처럼 지원되지 않는 환경의 대체 검사 경로도 남긴다. ‘전체 저장소의 90%에 설정을 켰다’는 문장과 ‘전체 저장소의 90%를 최근 검사했다’는 문장을 절대 같은 지표로 쓰지 않는다.

로컬 AI를 도입하는 기록에는 엔진 API의 안정성 외에 기기 지원 매트릭스와 데이터 흐름을 적는다. llama.cpp·ggml의 1.0 규칙은 버전 변경을 예측하는 자료지만 각 기기에서의 발열·메모리·속도는 별도 시험이 필요하다. 모델 다운로드와 오류 보고가 외부 통신인지, 클라우드 대체 경로가 있다면 언제 사용자에게 알리는지 기록한다. ‘로컬 실행’이라는 단어가 개인정보와 오프라인 동작에 관한 과도한 약속이 되지 않도록 제품 문구를 검토한다.

마지막으로 사용자의 목표를 어떻게 평가할지 쓴다. XYBench는 표면 요청을 그대로 해결하는 답변과 실제 목표를 돕는 답변을 구분한다. 자사 도메인의 대표 사례에서는 어떤 경우에 사용자의 전제를 다시 확인해야 하는지, 어떤 경우에는 질문보다 즉시 조치가 중요한지, 어느 수준의 불확실성을 표현해야 하는지 정한다. 특히 인사·금융에서는 모델이 숨은 목표를 확정적으로 선언하거나 권한 없는 행동으로 건너뛰지 않도록 검증한다. 성공 기준은 ‘친절하게 들린다’가 아니라 사용자가 올바른 다음 행동을 이해하고 시스템 상태가 정확히 반영되는지다.

결정 기록은 출시 때 한 번 쓰고 끝내지 않는다. 모델 종료나 API 정책 변경처럼 외부 조건이 바뀌면 재검토한다. 공급자 발표일과 확인 날짜를 구분해 적고, 제공 범위·요금·지원 플랫폼이 바뀌었는지 확인한다. 출시 뒤에는 실제 장애, 사용자 이탈, 재시도, 비용 초과, 보안 결과를 기록에 연결한다. 모델의 진화 속도에 맞춰 모든 기능을 계속 갈아엎는 것이 목표가 아니다. 어떤 근거로 현재 경계를 정했고, 언제 어떤 신호가 오면 변경할지 명확히 해 두는 것이 목표다.

## 세 가지 최종 점검 — ‘기능 있음’이라는 말의 숨은 조건

첫째, **제품 기능의 존재와 사용자의 이용 가능성은 다르다.** ChatGPT Wallet의 초기 대상에는 국가·연령·플랜·카드 조건이 붙는다. Gemini의 Wallet 연결은 미국 Gemini 앱 사용자 중심으로 설명된다. Copilot에서 Hydrogen이 일반 제공된다는 말에도 점진 롤아웃과 관리자 모델 정책이 따른다. 따라서 소개 문구를 쓸 때에는 ‘공개됐다’와 ‘우리 계정에서 오늘 사용할 수 있다’를 나눈다. 고객 지원 문서에도 조건을 명확히 써야 기능이 보이지 않는 사용자가 자신의 오류로 오해하지 않는다.

둘째, **설정 가능성과 운영 효과는 다르다.** AI Scan 설정 API가 생겼다는 것은 여러 저장소를 자동화하기 쉬워졌다는 뜻이지 취약점이 자동으로 발견됐다는 뜻은 아니다. 로컬 엔진의 버전 규칙이 안정됐다는 것은 업그레이드 판단이 쉬워졌다는 뜻이지 특정 기기에서 제품의 품질이 확인됐다는 뜻은 아니다. 결제 토큰이 카드 원본을 감춘다는 것도 배송·주문·환불의 모든 오류가 사라졌다는 뜻은 아니다. 각 기능의 효과를 확인할 별도의 성공 이벤트가 무엇인지 정의해야 한다.

셋째, **좋은 문장과 좋은 결과는 다르다.** XYBench가 구분한 것처럼 모델이 실제 목표의 해결책을 한 번 말하는 것만으로 답변 전체가 도움이 되지는 않는다. 개발 에이전트가 ‘완료했습니다’라고 답해도 테스트가 실패하거나 상태 변경이 저장되지 않았으면 완료가 아니다. 금융·인사 에이전트가 정중하게 설명해도 잘못된 계정에 접근했다면 실패다. 결과를 판단할 때에는 모델의 어조보다 서버의 상태, 사람의 승인, 테스트와 감사 증거를 먼저 본다.

오늘의 공식 인덱스 확인에서 새로운 대형 발표가 없었다는 사실은 결코 빈 날짜를 채우기 위한 핑계가 아니다. 일요일에는 평일의 속보를 시간에 맞춰 다시 쓰기보다, 발표문에 적힌 범위와 빠진 조건을 읽는 편이 실제 도입에 유익하다. 이 글이 제시한 설계 표와 사례는 공급자의 내부 구현을 아는 척하는 설명이 아니라 제품팀이 스스로 확인해야 할 질문이다. 원문이 말하는 사실, 그 사실에서 합리적으로 도출되는 운영 위험, 서비스별로 검증해야 하는 가정을 분리하는 태도가 AI 뉴스를 실무 자료로 바꾼다.
