# AI Daily News | 2026년 11월 25일

**확인 시점: 2026년 11월 25일 11:30 KST.** 오늘은 OpenAI가 11월 24일 공개한 과학 소식 두 건을 함께 읽는다. 첫째, GPT-6 계열이 일반적인 추론과 코딩 도구만으로 단백질의 형태와 아미노산 서열을 설계할 수 있다는 연구다. 발표에는 계산 평가뿐 아니라 실제 제작한 단백질의 결합 실험이 포함된다. 둘째, Codex와 Astra를 이용한 시민 과학자들의 외계행성 후보 탐색 사례다. 공개 천문 관측 자료에서 주기적인 별빛 감소 신호를 찾았고, 독립적인 천문학자가 두 신호를 재발견했다. **첫 소식의 결합 신호는 약물 효능이 아니며, 둘째 소식의 후보 신호는 확인된 행성이 아니다.** 이 구분이 오늘 글의 중심이다.

같은 시간대에 확인한 GitHub 공식 변경 기록에는 12월 1일부터 일주일에 걸쳐 GitHub.com 알림 구독·사유 표시를 바꾸겠다는 11월 24일 공지도 있다. 과학 연구와 직접 연결된 제품은 아니지만, AI 코딩 에이전트의 작업을 이메일·알림 규칙으로 감시하는 팀에는 실제 운영 영향을 준다. 이 공지는 오늘의 보조 뉴스로 다룬다. 11월 23일의 Shirudo와 GitHub 이슈 상태는 어제 글에 이미 다뤘으므로 다시 신제품으로 포장하지 않는다.

이 글은 공식 발표의 **실험 설계, 비교 대상, 분모, 후속 검증 단계**를 나눠 읽는다. 생물학과 천문학의 결과를 직접 재현했다고 주장하지 않는다. 아래의 검사 표와 운영 제안은 발표에 적힌 제품 기능이 아니라, 공개된 사실을 바탕으로 개발팀과 운영팀이 응용할 수 있도록 작성한 편집상의 분석이다. 과학적 발견을 소프트웨어 출시와 같은 성공 기준으로 취급하지 않는 것이 핵심이다.

## 배경 — ‘후보 생성’이 싸질 때 병목이 이동한다

과학의 많은 작업은 거대한 가능성 공간에서 시험할 대상을 추리는 일이다. 가능한 아미노산 배열과 입체 구조는 매우 많다. 망원경은 수많은 별을 관찰하고, 그중 극히 일부의 작고 반복되는 밝기 변화를 찾아야 한다. 과거에는 계산 후보를 만드는 단계가 충분히 비싸서, 더 많은 후보를 얻는 것 자체가 주요 발전이었다. 일반 목적 모델과 코딩 에이전트가 이 단계의 속도를 높일 수 있다면, 다음 병목은 **어떤 후보를 실제로 만들어 보거나 관측할지**가 된다.

이 변화에는 좋은 면과 위험한 면이 함께 있다. 후보가 더 많아지면 사람이 놓쳤을 패턴을 찾을 여지가 생긴다. 그러나 양성처럼 보이는 후보가 늘어날수록 검증 비용과 잘못된 발견의 가능성도 함께 증가한다. 모델이 생성한 설명이 그럴듯하다고 해서 분자의 결합 특성이나 별빛 변화의 원인이 자동으로 밝혀지지는 않는다. 측정 장비와 계산 검증, 다른 연구자의 독립 점검이 중요해지는 이유다.

오늘 두 OpenAI 발표는 각 분야의 **서로 다른 검증 층위**를 비교할 좋은 사례다. 단백질 글은 계산 점수, 실제 결합 실험, 전문 모델의 보조 사용, 아직 다루지 못한 약물 개발 단계까지 비교적 자세히 밝힌다. 외계행성 글은 공개 데이터를 검색한 파이프라인의 발견 수와 독립 재검색 결과를 제시하면서도 확인에 수개월 또는 수년이 걸릴 수 있다고 말한다. 따라서 둘을 묶는 제목은 ‘AI가 생명과 우주를 정복했다’가 아니라, **AI가 발견의 입구를 넓힐 때 어떤 증거로 출구를 좁힐 것인가**에 가깝다.

## Top News 1 — GPT-6의 단백질 설계: ‘내재적 능력’의 범위는 어디까지인가

OpenAI가 11월 24일 공개한 [단백질 연구 발표](https://openai.com/index/gpt-6-models-demonstrate-intrinsic-protein-design-capabilities/)는 GPT-6 계열이 전문 생물학 생성 모델을 **호출하지 않고도**, 일반적인 추론과 코딩 도구로 단백질의 3차원 구조나 아미노산 서열 후보를 만들 수 있다고 주장한다. 발표는 내부 연구 모델이 여러 과제에서 전문 모델에 맞먹거나 앞선 계산 결과를 보였고, GPT-6.2의 설계를 토대로 제작한 후보에 실험실 결합 신호가 있었다고 정리한다. 여기서 ‘전문 모델을 사용하지 않았다’는 말은 **해당 생성 단계**의 의미다. 전 과정에서 전문 모델이 전혀 없었다는 의미는 아니다.

### 먼저 알아야 할 최소한의 생물학

단백질은 아미노산의 서열로 만들어지고, 그 서열은 단백질이 3차원으로 접히는 형태에 영향을 준다. 기능은 단순히 서열 문자열이 그럴듯한지보다, 실제로 접힌 형태가 원하는 표적과 어떻게 상호작용하는지에 좌우된다. 예컨대 표적에 붙는 미니바인더를 설계하려면 접촉 위치, 맞닿는 면의 모양, 접힘의 안정성, 원하지 않는 다른 표적과의 상호작용까지 따져야 한다. 특정 표적에 한 번 붙었다는 결과는 이런 조건을 모두 만족했다는 증거가 아니다.

일반 언어 모델이 이 분야에서 흥미로운 이유는 입력 제약을 자연어로 바꾸기 쉽기 때문이다. 연구자는 결합 위치, 구조를 이루는 나선과 가닥의 수, 원자 사이의 특정 결합 정보 같은 조건을 말로 주고 모델이 코드를 만들어 후보를 탐색하게 할 수 있다. 전문 모델의 입력 형식을 바꿀 때보다 유연할 수 있다는 설명이다. 하지만 유연성은 평가 기준을 대체하지 않는다. 모델이 명령을 잘 따랐는지와 그 결과가 분자적으로 작동하는지는 별개다.

### 실험 1: 미니바인더 형태 설계

발표의 첫 실험에서는 GPT-6.2에 다섯 표적 단백질의 3차원 구조와 결합을 원하는 위치를 주었다. 모델은 전문 단백질 AI 모델 없이 작은 결합 단백질의 **형태 후보**를 코드로 설계했다. 그러나 실제 제작을 위해서는 그 형태로 접힐 아미노산 **서열**이 필요하다. 연구진은 SolubleMPNN이라는 전문 AI 모델로 서열을 제안받았고, 다른 전문 모델로 접힘과 결합 가능성을 평가해 실험할 후보를 골랐다. 이 경로는 ‘일반 모델의 구조 설계 능력’을 시험할 수 있지만 ‘일반 모델 혼자 전 과정을 완료했다’는 증거로 쓸 수 없다.

실험실에서는 5개 표적을 대상으로 322개 미니바인더를 검사했다. 그중 35개, 즉 10.9%가 의도한 표적에 대한 결합 양성으로 집계됐다. 표적별 양성 수는 PD-L1 5개, IL-7Rα 3개, TrkA 1개, VEGF-A 8개, IL-17A 18개다. **표적마다 최소 하나의 결합 후보가 있었다**는 것이 의미 있는 관찰이다. 동시에 분모 322개와 평균 10.9%를 빼고 ‘다섯 표적 모두 성공’만 말하면 실험의 효율과 불확실성을 감춘다.

이 숫자를 전문 모델과 일대일로 비교하기도 쉽지 않다. OpenAI 글은 RFdiffusion 원 연구의 보고된 양성률이 더 높았다고 밝히면서도, 후보를 실험 전에 얼마나 엄격히 걸러 냈는지와 ‘결합’의 정의가 다르면 양성률 비교가 달라진다고 적는다. 그러므로 10.9%는 이 설계·선별·실험 절차에서 나온 숫자다. 특정 플랫폼의 보편적 성공률이나 모든 표적의 성공 확률이라고 읽지 않는다. 각 표적의 난이도도 같지 않다.

**질문은 네 가지로 나눠야 한다.** 어떤 단백질 형태가 제안됐나? 어떤 전문 모델이 서열을 채우고 후보를 골랐나? 실험실에서 어떤 기준으로 결합 양성을 정했나? 그 결합이 실제 생물학적 기능을 바꾸는가? 첫 세 단계의 일부 답은 발표에 있다. 마지막 단계는 이 발표가 완료했다고 말하지 않는다.

### 실험 2: 이미 알려진 형태에 새로운 서열 제안

두 번째 실험은 구조 생성과 다르게 **서열 재설계**를 시험했다. 연구진은 이미 결합이 확인된 미니바인더가 표적에 붙은 구조를 보여 주되 원래 아미노산 서열은 숨기고 GPT-6.2에 새 서열을 제안하게 했다. 전문 모델이 제작·실험할 후보를 고르는 데 도움을 준 점은 동일하게 명시됐다. 초기 실험에서 MDM2는 88개 중 75개, VEGF-A는 42개 중 26개, PD-1은 59개 중 8개가 결합을 보였다. 비율은 각각 발표 기준 85%, 62%, 14%다. 표적별 편차가 크기 때문에 한 수치만 택해 ‘서열 설계 성공률’로 일반화하면 안 된다.

새 서열이 원래 서열과 얼마나 달랐는지도 연구진은 제시한다. VEGF-A에서 중앙값 차이는 50%, MDM2는 43%, PD-1은 15%였다. 그러나 **다른 문자열**이라는 사실이 언제나 **독립적인 생물학적 원리**를 학습했다는 단독 증거는 아니다. 구조 조건과 선별 절차, 학습 자료와의 유사성 등도 고려해야 한다. 특히 원래 확인된 구조를 출발점으로 준 실험은 ‘완전히 아무 정보 없이 새 표적 단백질을 처음부터 찾았다’는 주장과 다르다.

또 다른 실험은 공개되지 않았던 GPT-6.2 설계 구조 세 개를 사용했다. 이 구조들에는 이미 ProteinMPNN이 만든 결합 서열이 있었다. GPT-6.2가 제안한 새 서열을 바탕으로 제작한 107개 단백질 중 14개, 곧 13.1%가 결합했다. 한 PD-L1 미니바인더 구조에서 서로 크게 다른 두 서열이 모두 결합 신호를 보인 사례도 소개됐다. 이 결과는 단순 암기만으로 설명하기 어렵다는 연구진의 해석을 뒷받침하지만, 어떤 새로운 표적에서도 같은 비율이 나온다는 뜻은 아니다.

### 항체의 결합 고리도 시험했다

발표는 IL-4Rα에 결합하는 여섯 개의 작은 항체 VHH에서 결합 고리의 서열을 다시 설계한 실험을 설명한다. 182개 설계 중 128개, 약 70%가 IL-4Rα에 결합 신호를 보였다. 다른 실험에서는 치료용 항체 다섯 개의 결합 고리 세 부분에서 아미노산 절반가량을 바꾸고 원 표적 PD-1 또는 PD-L1에 대한 결합 유지 여부를 항체 **조각**으로 측정했다. 272개 조각 중 179개, 약 66%가 결합했다.

이 결과는 ‘기존 결합 특성을 유지하면서 서열을 상당히 바꿀 수 있다’는 초기 증거다. 그러나 원래보다 더 강하게 결합했는지, 다른 단백질에는 덜 붙는지, 온도와 보관 조건에서 안정적인지, 인체에 투여할 수 있는지는 다른 질문이다. 원문도 이를 친화도 성숙과 선택성 향상으로 가는 **첫 단계**라고 소개한다. 특히 항체 조각으로 한 실험 결과를 완전한 의약품의 작용으로 옮겨 적으면 안 된다.

### 계산 평가: 잘하는 과제와 약한 과제

연구진은 실험실 결과 밖에서도 여러 계산 과제를 제시한다. 특정 원자 배치를 보존하며 나머지 단백질을 설계하는 **모티프 스캐폴딩**에서는 내부 최신 연구 모델의 설계가 43.7%, RFdiffusion의 설계가 27.8%로 보고된 계산 기준을 통과했다. 여기서는 ProteinMPNN이 각 설계에 대해 여덟 개 서열을 제안하고 ESMFold가 접힘을 예측했다. 통과 기준은 적어도 하나의 예측 구조가 모티프를 보존하면서 전체 설계 구조와 가깝다는 것이다. **실험실에서 효소가 실제 반응을 촉진했는지를 측정한 수치가 아니다.** 분모와 후처리 단계를 함께 제시해야만 비교의 의미가 있다.

전체 접힘 형태를 지정해 설계하는 200개 도전 과제에서는 최신 내부 모델 18.9%, 전문 모델 Proteina 17.1%가 해당 계산 기준을 통과했다고 발표한다. 수치 차이는 크지 않고, 통과 조건 자체도 예측된 구조에 대한 것이다. 특정 표면에 붙는 미니바인더 설계, 모티프를 둘러싼 구조 설계, 전체 단백질 접힘을 맞추는 과제는 난이도와 평가 방식이 서로 다르다. 한 분야에서 더 좋은 수치가 다른 과제의 우월함을 보증하지 않는다.

작은 분자가 단백질에 어디에서 어떤 방향으로 붙는지 예측하는 **도킹** 과제에서는 실험적으로 알려진 구조를 숨기고 다시 찾게 했다. PoseBusters 자료의 채점 대상 예측에서 GPT-6.2는 93%, 최신 내부 모델은 96%, 비교한 DiffDock-L은 50%가 관측 구조와 가깝다고 발표한다. 결합 원자 두 개를 알려 주는 Scarpino 자료의 179개 구조에서는 GPT-6.2가 채점 대상 예측의 92%, 내부 모델이 97%, 비교한 DiffDock은 60%를 기록했다. 첫 실험과 둘째 실험의 정보 조건이 다르다. 두 번째는 결합 위치에 관한 사전 정보가 주어진다. 둘을 단순히 같은 시험의 반복으로 보면 안 된다.

항체-표적 도킹에서는 최고 평가 계산량에서 세대별 평균 DockQ가 GPT-5.6 약 0.05, GPT-6 0.28, GPT-6.2 0.57, 최신 내부 모델 0.81로 높아졌다고 소개한다. 그렇지만 원문은 공개 구조가 학습 중 노출됐거나 비슷한 쌍이 있었을 가능성을 직접 적는다. 성능 상승이 흥미롭더라도 **미지 구조에 대한 일반화**를 이 결과 하나로 확정하지 않는다. 공개 벤치마크의 익숙함과 독립적 검증의 필요성은 모델 평가에서 늘 중요한 문제다.

서열만으로 전체 단백질의 3차원 구조를 예측하는 과제는 뚜렷한 약점이다. 평균 TM-score가 GPT-5.6 0.16, GPT-6.2 0.26, 최신 내부 모델 0.38로 향상됐지만 전문 구조 예측 모델 ESMFold2는 0.93으로 보고됐다. TM-score는 1에 가까울수록 실제 구조와 잘 맞으며, 발표는 0.5 이상이면 전체 접힘을 대체로 잡았다고 보는 기준을 설명한다. 이 수치만 놓고 보면 일반 모델의 일부 설계·도킹 강점을 **전체 구조 예측 능력**으로 옮겨 말하기 어렵다. 같은 연구 안에서도 능력의 경계가 들쭉날쭉하다는 점이 중요한 발견이다.

### 원문이 직접 밝힌 제한 사항

OpenAI 발표의 제한 사항은 제목만큼 중요하다. 첫째, 후보 선별에 Boltz-2, OpenDDE, ESMFold2 같은 전문 구조 예측 모델을 사용했다. 따라서 이번 결과는 일반 모델이 **형태 생성과 서열 재설계**라는 두 단계에서 내재적 능력을 보인다는 주장이지, 전문 도구 없이 미니바인더를 종단 간 처음부터 생산했다는 증거가 아니다. 둘째, 전체 단백질 구조를 서열만으로 예측하는 과제에서는 전문 모델보다 크게 약했다. 셋째, 일부 벤치마크의 높은 정확도는 학습 내용의 암기나 데이터 생성 과정의 흔적이 영향을 줬을 수 있다. 넷째, 결합은 실제 유용한 연구 도구나 치료제가 되기 위한 첫 관문일 뿐이다.

**왜 이 제한이 실무적으로 중요한가?** 연구팀이 후보 설계 플랫폼을 도입한다면 ‘모델이 있다’만으로 파이프라인이 완성되지 않는다. 목표 정의와 입력 구조의 품질, 서열 제안 도구, 예측 접힘 검사, 실험 대상 선별, 실험실 측정, 실패 후 재설계라는 여러 단계가 각각 비용과 위험을 가진다. 한 단계의 모델을 바꿔 얻은 개선이 전체 실험 주기를 얼마나 줄이는지는 별도로 측정해야 한다. 오늘 발표에는 몇 차례의 설계-실험 반복을 실제로 줄였는지에 대한 일반적인 생산성 수치를 보편적 결론으로 제시하지 않는다.

생물보안 문제도 발표에 명시돼 있다. 단백질을 설계하는 능력은 질병 연구와 신약 개발에 도움이 될 수 있지만 악용 가능성도 있다. OpenAI는 자사의 Preparedness Framework를 이런 위험을 평가하고 보호 장치를 시험하는 틀로 제시한다. 독자는 이를 위험이 이미 제거됐다는 보증으로 읽어서는 안 된다. 연구 성과, 위험 평가 체계, 배포 정책은 각각 별도 문서와 증거가 필요한 층위다.

### 별빛 감소는 왜 후보 신호인가

별 앞을 행성이 지나가면 우리가 보는 빛이 조금 줄어든다. 이를 **통과(transit)**라고 한다. 시간에 따른 밝기 기록인 광도 곡선에서 감소가 일정한 주기로 되풀이되면 별 주위를 공전하는 물체를 의심할 수 있다. 그러나 두 별이 서로 가리거나 관측 기기의 온도 변화가 측정에 영향을 줄 수도 있다. 통과처럼 보이는 패턴 하나로 ‘새 행성’이라고 말하면 거짓 양성을 과소평가한다. 주기가 안정적인지, 별의 특성과 신호 깊이가 맞는지, 다른 원인으로 설명할 수 없는지를 확인해야 한다.

Bond는 이미 발표된 탐색 방법들을 Codex로 비교·결합하고, 코드 변경이 후보 찾기에 도움이 되는지 시험했다. 한 에이전트는 광도 곡선에서 유망한 신호를 찾고, 다른 에이전트는 후보를 더 자세히 검사하는 식으로 나눴다. 공개 Kepler 자료의 검색 결과 200개 이상의 신호가 표시됐고, 그중 10개는 이미 확인된 행성의 신호였다. 알고 있던 행성 신호를 다시 찾은 것은 탐색 파이프라인의 **기본적인 감도 점검**이다. 그러나 알려진 행성 열 개를 찾았다고 해서 표시된 나머지 190개 이상이 모두 행성이라는 뜻은 아니다. 또한 이미 확인된 행성의 재발견은 신규 발견 수와 합산하면 안 된다.

특히 눈에 띈 별은 KIC 5689121과 KIC 6691030이다. 첫째에서는 13.8일마다 밝기가 감소하는 신호가 보였다. 만약 행성이 원인이라면 빛을 가리는 정도는 지구 지름 약 2.4배 크기의 물체와 맞을 수 있다. 둘째에서는 4.8일 주기의 감소가 나타났고, 행성이라면 해왕성보다 작을 가능성과 일치한다고 발표는 설명한다. **‘만약 행성이라면’이라는 조건절이 핵심이다.** 크기 추정은 원인 가설에 기대고 있으며 지금의 공식 문서도 확정된 발견이라고 부르지 않는다.

Byrd는 하나의 검색을 외계행성 후보 전반에, 다른 검색을 별의 **거주 가능 영역**에 초점을 맞췄다. 거주 가능 영역은 적절한 대기 조건을 가진 행성 표면에 액체 물이 있을 수 있는 별과의 거리 범위다. 이 정의는 그 범위에 있는 모든 행성에 물이나 생명이 있다는 뜻이 아니다. 발표에 따르면 TESS와 다른 공개 관측 보관소의 자료를 대상으로 한 1차 탐색은 49개 후보를 냈다. 유력 후보 하나는 TESS 관련 연구진의 추가 분석을 기다리고 있고 다른 두 후보는 제출을 기다린다. 검색 자체도 계속되고 있다. 49는 **첫 단계 후보 수**이며, 확인된 행성 49개가 아니다.

### 오늘의 두 파이프라인을 분리해서 읽기

| 항목 | Bond의 Codex 검색 | Byrd의 Astra 검색 |
| --- | --- | --- |
| 출발 자료 | Kepler 관측의 약 10만 개 별 | TESS와 다른 공개 자료의 약 1,900만 개 별 |
| 방법 | 발표된 검색법을 비교·결합하고 에이전트를 탐색·후보 검사로 분리 | 후보 전반과 거주 가능 영역을 겨냥한 두 검색을 설계 |
| 처음 표시된 결과 | 200개 이상의 신호, 그중 기존 확인 행성 신호 10개 | 1차에서 후보 49개 |
| 독립 점검 | SETI Institute 연구자가 같은 Kepler 자료에서 두 신호를 독립 검색으로 재발견 | 후보 하나가 TESS 관련 연구진의 추가 분석을 기다림 |
| 현재 지위 | 두 별의 주기적 밝기 감소는 유망한 신호, 원인 미확정 | 후보군이 진행 중이며 확인된 행성 수가 아님 |
| 후속 과제 | 다음 예상 통과 시점의 관측과 다른 원인 배제 | 연구진 분석, 후보 제출, 추가 관측 |

두 검색의 별 개수는 단순한 생산성 비교에 쓰면 안 된다. Kepler와 TESS의 자료 특성, 관측 기간, 대상 별의 종류, 사전 처리, 찾으려는 신호의 약함이 다르다. 10만 개에서 200개 신호와 1,900만 개에서 49개 후보를 나눠 계산해 어느 에이전트가 우월하다고 말할 근거가 없다. **분모가 크다는 사실은 발견의 품질을 의미하지 않는다.** 출발 자료와 선별 기준이 달라 원시 후보 비율의 비교 자체가 잘못된 질문일 수 있다.

### 독립 확인은 어떤 순서로 강해지는가

첫 단계는 원시 광도 곡선과 전처리 코드를 다시 확인하는 것이다. 누락 구간이나 이상값 처리, 장비 조건, 시간 표시가 잘못되면 주기적 패턴을 만들 수 있다. 둘째는 다른 분석자가 같은 자료를 별도 검색법으로 다뤄 신호의 재현성을 보는 것이다. Bond의 두 후보에 관해 오늘 확인된 것은 이 단계에 가깝다. 셋째는 예상되는 다음 밝기 감소 시점에 맞춰 새 관측을 모으는 것이다. 넷째는 두 별이 서로 가리는 현상 등 다른 천체물리학적 설명을 검토하는 것이다. 다섯째는 가능하다면 시선속도 등 다른 방법으로 별의 움직임을 살펴 행성 가설을 추가로 시험한다. 발표는 이런 후속 관측과 동료 검토가 필요하다고 설명한다.

이 절차를 소프트웨어 프로젝트의 테스트 단계에 곧장 동일시할 필요는 없다. 다만 개발자에게 유용한 비유는 있다. 검색 코드가 **기존 정답 열 개를 다시 찾은 것**은 회귀 테스트처럼 작동한다. **200개 넘는 신호를 낸 것**은 후보 생성이다. **별도 연구자의 독립 재검색**은 독립 구현으로 같은 결과를 보는 검증이다. **새 관측**은 실제 환경의 새로운 데이터에서 가설을 시험하는 단계다. 각 단계는 앞 단계를 보강하지만 뒤 단계를 자동으로 충족시키지는 못한다. 특히 기존 정답을 되찾는 테스트만 통과하고 새 후보의 원인을 확정했다고 주장하면 검증의 범위를 과장하는 셈이다.

NASA의 [Exoplanet Archive](https://exoplanetarchive.ipac.caltech.edu/)도 11월 19일 주간 업데이트를 통해 새로 확인된 행성들과 전송 스펙트럼을 별도로 알렸다. 이 공식 보관소의 **확인된 행성 목록**과 오늘 OpenAI 글의 **검토 중인 후보**를 같은 목록으로 취급하지 않는다. 11월 19일 자료는 천문학 발표 맥락을 보는 보조 자료이지, Bond와 Byrd의 후보가 이미 보관소에 확정 등록됐다는 근거가 아니다.

### 시민 과학의 가치와 한계

OpenAI 발표의 흥미로운 점은 거대 연구소의 모델이 전문 천문학자만을 위한 닫힌 도구가 아니라, 호기심 있는 개인의 분석 작업에도 사용됐다는 것이다. 공개 관측 자료, 기존 연구 방법, 코드를 쓰는 에이전트, 외부 연구자의 검토를 연결하면 새로운 후보를 만들 수 있다. 하지만 ‘누구나 코드를 만들 수 있다’와 ‘누구나 발견을 확정할 수 있다’는 다르다. 분석 대상 선택, 통계적 검증, 관측 계획, 자료 공개 방식에 대한 전문성은 여전히 중요하다.

이 사례에서 개발자에게 배울 부분은 **파이프라인을 읽을 수 있게 만드는 것**이다. 입력한 관측 자료 버전과 구간, 전처리 규칙, 사용한 탐색 방법, 후보 점수와 기각 이유가 기록돼야 후속 연구자가 재검토할 수 있다. 같은 후보를 다시 발견했다고만 쓰기보다 어떤 자료와 방법으로 찾았는지 보여 줘야 한다. AI 에이전트가 코드를 만들수록 코드 작성자의 내부 기억 대신 실행 기록과 검증 가능한 산출물이 중요해진다. 발표는 이 모든 운영 세부사항이 완성됐다고 주장하지 않으므로, 여기의 항목은 응용 프로젝트를 위한 편집상의 권고다.

## 보조 뉴스 — GitHub.com 알림 변경이 에이전트 업무 감시에 주는 영향

[GitHub의 11월 24일 변경 공지](https://github.blog/changelog/2026-11-24-more-predictable-notifications-on-github-com/)는 12월 1일부터 약 일주일 동안 GitHub.com의 알림 시스템을 이전할 계획이라고 밝혔다. 공지 시점에 즉시 전체 사용자에게 적용된 변경이 아니다. GitHub Enterprise Server에는 적용되지 않는다. 이전 기간에는 사용자마다 알림 동작이 다르게 보일 수 있다고 GitHub는 설명한다. 사용자에게 별도 조치는 필요 없지만, 알림 사유로 이메일을 분류하거나 자동화를 만들었다면 규칙을 점검할 필요가 있다.

첫 변화는 **수동 구독 해제의 의미**다. 이전에는 댓글 작성, PR 리뷰 제출, 스레드 상태 변경, 머지 큐 활동 등이 수동으로 구독을 해제한 사람을 다시 구독시키는 경우가 있었다. 변경 후에는 그런 일상적인 활동만으로 다시 구독되지 않는다. 반면 직접 멘션, 담당자 지정, PR 리뷰 요청처럼 주의를 요청하는 이벤트는 여전히 재구독을 일으킨다. 따라서 ‘내가 이 스레드에서 한마디 했으니 이후 모든 알림을 받겠지’라는 기대도, ‘구독 해제했으니 리뷰 요청도 안 오겠지’라는 기대도 둘 다 틀릴 수 있다.

둘째는 **팀 멘션과 현재 팀 구성원**의 관계다. 팀을 떠났거나 팀 멘션이 삭제되면 그 팀 멘션을 이유로 한 미래 알림은 중단된다. 기존에는 팀 멘션을 받은 뒤 팀에서 나가도 알림이 이어질 수 있었다. 반대로 스레드에서 팀이 멘션된 뒤 새로 팀에 합류하면 그 스레드의 이후 활동에 대한 알림이 가능해진다. 단, 댓글 참여 등 다른 구독 사유가 있다면 팀 멘션이 제거되어도 알림이 계속될 수 있다. **알림 한 건은 한 가지 사유만으로 설명되지 않을 수 있다**는 점이 실무적으로 중요하다.

셋째는 **Subscriptions 페이지의 목록 의미**다. 앞으로 그 페이지에는 사용자가 직접 추가한 구독만 보인다. 작성자, 댓글 작성자, 담당자, 멘션 대상, 리뷰 요청 대상이라는 이유로 받는 알림은 그 페이지에 모두 나타나지 않는다. 이런 알림을 관리하고 대량으로 구독 해제하려면 알림 받은편지함을 써야 한다. 페이지의 목록이 줄었다고 실제 알림이 사라졌다고 판단하면 안 된다.

넷째는 **표시되는 notification reason의 우선순위**다. 기존에는 최근 활동에 따라 이유가 달라 보일 수 있었다. 변경 후에는 멘션, 팀 멘션, 담당자 지정, 리뷰 요청, 댓글, 수동 구독, 작성자, 상태 변경, 구독됨 순의 우선순위를 적용한다. 이슈에서는 담당자 지정이 가장 높은 우선순위다. 따라서 이유가 `comment`에서 `mention`으로 보이거나 그 반대가 아니더라도 실제 이벤트 자체가 바뀌었다고 단정하지 말아야 한다. 표시 규칙이 바뀌기 때문이다. 이메일 헤더에는 적용 가능한 모든 알림 사유가 들어가도록 변경된다. 메일 필터가 단일 값만 있다고 가정하면 분류가 어긋날 수 있다.

### AI 코딩 에이전트 팀에 필요한 점검

에이전트가 PR을 만들고 리뷰를 요청하는 워크플로에서는 알림이 사람에게 일을 넘기는 중요한 통로다. 알림 사유나 구독 상태를 **승인의 유일한 기록**으로 삼는다면, 이번 이전 중 사람이 확인해야 할 작업이 누락되거나 중복 알림으로 보일 수 있다. 명시적인 리뷰어 지정, PR 상태, CI 결과, 실제 머지 여부를 원본 이벤트로 다루고, 이메일 알림은 전달 경로로 다루는 편이 낫다. 이는 GitHub가 새로운 AI 기능을 발표했다는 뜻이 아니라, 기존 개발 협업의 신호 체계를 더 정확히 해석하자는 운영 제안이다.

| 단계적 적용 | 사용자별 동작 차이를 버그나 정책 위반으로 성급히 단정하지 않는가? | 관측 시각과 사용자별 배포 상태 |

## 개발자에게 의미 — 좋은 후보 생성기보다 좋은 검증 파이프라인

세 소식의 공통 교훈을 억지로 하나의 제품 이야기로 합칠 필요는 없다. 단백질 연구는 일반 모델의 전문 과제 능력을, 외계행성 사례는 시민 과학의 데이터 탐색을, GitHub 공지는 협업 알림 체계의 변화를 다룬다. 그러나 개발 조직이 이들을 읽을 때 반복해서 나오는 질문은 같다. **자동화가 낸 결과를 다음 사람이 어떻게 검토할 수 있게 만들 것인가?**

### 1. 결과의 이름을 단계에 맞춰 붙인다

실험실에서 한 번 결합한 단백질을 ‘치료제’라고 부르지 않는다. 광도 곡선에서 반복되는 신호를 ‘새 행성’이라고 부르지 않는다. PR에 코멘트가 달린 것을 ‘승인 완료’라고 부르지 않는다. 이 세 문장은 분야가 다르지만 실패 원인이 비슷하다. 중간 단계의 관찰을 최종 목표의 이름으로 부르면 다음 검증 단계를 건너뛰기 쉽다. 대시보드나 보고서의 필드 이름부터 `candidate`, `binding_positive`, `confirmed`, `review_requested`, `approved`처럼 구분해야 한다. **이 필드 예시는 편집자의 구현 제안**이지 오늘 세 회사가 제공한 공통 스키마가 아니다.

### 2. 분모와 선별 과정을 남긴다

단백질 결합 35개를 말할 때 제작·검사한 322개를 함께 말한다. 천문 후보 49개를 말할 때 검색 대상과 1차 필터의 정의를 남긴다. 에이전트가 만든 PR 중 사람이 리뷰를 마친 비율을 말할 때, 자동으로 닫혔거나 리뷰 요청조차 없던 PR을 어떻게 셌는지 적는다. **분모가 보이지 않는 성공 사례**는 성취의 크기를 판단하게 해 주지 않는다. 더구나 후보 선별에 전문 모델이나 사람이 개입했다면, 그 단계의 역할을 숨길수록 다음 팀이 결과를 재현하기 어려워진다.

### 3. 독립적인 측정을 준비한다

모델이 만든 구조를 또 다른 모델의 예측으로만 확인하면 동일한 데이터 편향이나 평가 취약성을 공유할 수 있다. 실험실 결합 검사는 다른 종류의 증거다. AI가 찾은 천문 신호를 같은 코드로 다시 그리는 것보다 다른 연구자가 별도 방법으로 찾는 것이 더 강하다. 그렇더라도 같은 관측 자료를 분석한 결과와 미래의 새 관측은 다르다. 코딩 에이전트도 자기 코드가 통과했다고 보고하는 말보다 CI의 독립 실행, 사람이 확인한 요구사항, 실제 운영 지표가 더 강한 증거다. 각 분야에서 독립의 정도를 표시해야 한다.

### 4. 음성 결과도 학습 자산으로 남긴다

322개 중 양성이 아닌 후보가 다수였다는 사실은 단순 실패가 아니다. 어떤 형태와 표적 조건에서 결합이 없었는지 알면 다음 설계를 더 잘할 수 있다. 광도 곡선에서 표시된 신호가 장비 원인이나 쌍성 때문이었다는 결과도 탐색 코드를 개선한다. 코딩 에이전트가 잘못된 테스트를 고치거나 알림 이유를 오해한 사례도 이후의 자동화 규칙을 다듬는 자료가 된다. 단, 실패 기록이 개인정보, 비공개 코드, 실험실의 민감한 서열 등과 결합될 수 있으므로 공개 범위와 보존 정책은 별도로 정해야 한다. 오늘의 발표는 이런 데이터 거버넌스의 완성된 답을 제공하지 않는다.

### 5. 검증 비용을 성능 지표에 포함한다

후보를 한 시간에 백 개 만들었다는 사실만으로 연구가 빨라졌는지는 알 수 없다. 검증팀이 백 개를 하나하나 확인하느라 병목에 걸리면 전체 주기는 늘 수도 있다. 단백질 파이프라인에서는 제작·측정 가능 개수, 양성 뒤의 기능 평가, 다음 설계 반복까지 시간이 중요하다. 천문 검색에서는 후속 관측 기회의 희소성, 관측 가능한 계절과 시간, 데이터 품질이 중요하다. 소프트웨어에서는 리뷰어 대기 시간과 배포 뒤 결함 발견 시간이 중요하다. **모델의 출력량이 아니라 검증된 결과까지의 주기**를 살펴야 한다.

### 6. 근거의 종류를 데이터 모델에 담는다

과학 후보 관리 도구라면 ‘후보가 있다’만 저장하지 않고 출처를 나눌 수 있다. 예를 들어 `computational_prediction`, `independent_reanalysis`, `laboratory_binding`, `new_observation`, `functional_validation`처럼 근거 종류를 구분한다. 이런 값은 오늘 발표의 API 명세가 아니라 편집자가 제안하는 설계 예시다. 핵심은 단계별 증거를 덮어쓰기보다 누적하는 것이다. 하나의 상태값만 바꾸면 예전 가설과 이후 반증의 흔적이 사라질 수 있다. 버전, 시각, 측정 조건, 평가자가 함께 기록돼야 결과의 경로를 설명할 수 있다.

### 7. 한 작업에서 강한 모델을 다른 작업까지 일반화하지 않는다

오늘 단백질 발표가 가장 분명히 보여 주는 것은 **과제별로 다르게 나타나는 능력**이다. 모티프 스캐폴딩이나 일부 도킹에서 좋은 계산 결과가 나오지만 전체 구조 예측에서는 전문 모델과 큰 격차가 남는다. 이것은 모델을 비난할 이유도, 만능이라고 광고할 이유도 아니다. 채택하려는 업무에서 필요한 입력과 출력, 오류 비용을 따로 측정하라는 뜻이다. 천문 사례 역시 Codex가 광도 곡선 검색 코드를 잘 만들었다고 해서 모든 물리학적 해석에 강하다는 증거가 아니다.

### 8. 알림은 신호, 원본 상태는 따로 둔다

GitHub의 이번 이전은 알림 이유 표시와 구독 동작이 바뀔 수 있음을 보여 준다. 사람의 주의를 끄는 신호가 업무의 실제 상태와 동일하지 않다는 사실은 에이전트 운영에서 중요하다. 멘션을 받았지만 아직 리뷰하지 않았을 수 있고, Subscriptions 페이지에 스레드가 없어도 댓글 작성 때문에 알림을 받을 수 있다. ‘알림이 왔는가’만으로 작업 책임을 판단하는 자동화는 표시 규칙 변화에 취약하다. 원본 PR·이슈 이벤트와 알림 전달 결과를 별도로 기록해야 한다.

## 운영 포인트 — 바로 적용할 수 있는 검증 질문

다음은 오늘 발표의 요약을 넘어 실제 팀이 검토할 수 있는 질문들이다. 제품의 구현 완료를 주장하는 체크리스트가 아니다. 각 팀은 자신의 자료 접근 권한과 연구·배포 목적에 맞게 범위를 줄여 써야 한다.

### 과학·연구 소프트웨어 팀

1. **입력 계보:** 구조 파일, 서열, 광도 곡선의 원본 주소·버전·수집 시각이 남는가? 공개 데이터라 해도 수정 이력이 있을 수 있다.
2. **전처리:** 누락값과 이상값 처리, 표준화, 관측 구간 선택이 결과에 얼마나 영향을 주는가? 전처리 코드를 바꾸면 이전 후보를 다시 평가할 수 있는가?
3. **후보의 정체:** 모델이 직접 만들었는지, 전문 모델이 보완했는지, 사람이 선택했는지 단계별 역할이 구분되는가?
4. **실패 분모:** 생성 후보, 계산 필터 통과 후보, 실제 제작·관측 후보, 양성 결과의 수가 모두 남는가?
5. **비교 조건:** 다른 모델과 같은 입력, 같은 계산 예산, 같은 후처리, 같은 성공 기준을 썼는가? 아니라면 차이를 표기하는가?
6. **독립 평가:** 같은 모델의 자기 평가만 돌리지 않았는가? 다른 분석자나 실험실, 새 관측 자료를 쓸 수 있는가?
7. **해석 범위:** 결합을 기능으로, 후보를 확정으로, 통계적 연관을 원인으로 바꾸지 않았는가?
8. **반증 계획:** 어떤 결과가 나오면 가설을 기각할지 미리 적었는가? 긍정 사례만 고르지 않았는가?
9. **보존과 접근:** 민감한 생물학 설계 자료나 비공개 관측 협업 정보를 누가 볼 수 있는가?
10. **재현 가능성:** 원문에 없는 세부 절차를 추측으로 채우지 않고, 직접 실험에 필요한 미상 조건을 목록화했는가?

### 일반 개발·제품 팀

1. **모델 선택:** 한 벤치마크의 최고 점수를 전체 제품 요구사항의 통과로 오독하지 않는가?
2. **파이프라인 소유권:** 생성, 필터링, 검증, 승인, 실제 적용 단계의 책임자가 각각 정해졌는가?
3. **평가 데이터:** 모델이 학습 중 보았을 가능성이 있는 공개 예제와 새 내부 사례를 구분하는가?
4. **성공 지표:** 후보 수 대신 검증된 성과, 사용자 영향, 회귀 비용까지 측정하는가?
5. **실패 복구:** 새로운 후보가 잘못됐을 때 원인 추적과 롤백이 가능한가?
6. **관측 시각:** 발표 시점과 우리 시스템에 적용된 시점을 구분하는가?
7. **알림 의존:** 이메일 reason이나 구독 화면 하나가 승인·감사의 유일한 증거가 되지 않는가?
8. **단계적 변경:** GitHub처럼 일주일에 걸친 배포에서는 계정별 동작 차이를 기록하는가?
9. **문서 문구:** 마케팅·사내 공지에서 ‘도움’, ‘후보’, ‘결합’, ‘검증’, ‘확정’의 범위를 정확히 쓰는가?
10. **후속 질문:** 지금 확인된 결과와 아직 필요한 실험을 같은 문단 안에 분명히 놓는가?

### 권장되는 한 장짜리 실험 기록

새 AI 탐색 도구를 시험한다면 다음의 최소 기록을 한 장에 모으는 편이 유용하다. **목적:** 무엇을 개선하려는가. **입력:** 자료의 출처와 시점은 무엇인가. **생성:** 어떤 모델과 코드가 어떤 후보를 냈는가. **선별:** 어떤 전문 도구나 사람이 후보를 줄였는가. **검증:** 계산, 독립 분석, 직접 측정 중 어느 층위인가. **분모:** 각 단계에서 몇 개가 들어오고 나갔는가. **실패:** 어떤 오탐과 불확실성이 남는가. **다음 실험:** 무엇이 관찰되면 가설이 강화되거나 기각되는가. 이 기록이 있으면 발표가 바뀌거나 새로운 논문이 나와도 오늘의 결론을 다시 평가할 수 있다.

## 숫자를 읽는 순서 — 과장을 줄이는 열두 가지 질문

1. **숫자의 대상은 무엇인가?** 분자의 결합, 구조의 점수, 별빛의 주기성, 이메일 알림의 표시 이유는 서로 다른 대상이다.
2. **분모는 무엇인가?** 35개 양성은 322개 제작 후보라는 분모와 함께 읽어야 한다.
3. **선별이 언제 일어났는가?** 제작 전 전문 모델이 걸러낸 후보와 아무 선별 없는 원시 생성 후보는 성공률의 분모가 다르다.
4. **비교 대상의 조건은 같았는가?** RFdiffusion 원 논문의 양성률과 이번 실험의 비율을 직접 비교하기 어렵다고 발표 자체가 말한다.
5. **평가는 계산인가 실험인가?** 모티프 스캐폴딩의 계산 통과와 실험실 결합은 증거의 종류가 다르다.
6. **실험은 기능을 측정했는가?** 표적에 붙는다는 사실과 세포의 생물학적 반응을 바꾼다는 사실은 다르다.
7. **새 자료에서 확인했는가?** 공개 구조가 학습 자료에 있었을 가능성이 있다면 새 구조에서의 일반화 평가가 중요하다.
8. **독립 분석은 어느 정도 독립인가?** 같은 Kepler 자료의 새 검색과 새 망원경 관측을 구분한다.
9. **원인에 대한 대안은 무엇인가?** 별빛 감소는 행성 외의 원인으로도 생길 수 있다.
10. **적용 시점은 언제인가?** GitHub 알림 변경은 11월 24일 공지됐지만 12월 1일에 단계적으로 시작한다.
11. **범위는 어디까지인가?** GitHub.com 공지를 GitHub Enterprise Server의 변경으로 옮기지 않는다.
12. **후속 검증이 무엇인가?** 답하지 못한다면 후보와 확정을 분리한 문장이 아직 필요하다.

이 열두 질문은 과학 발표를 깎아내리기 위한 목록이 아니다. 성취의 정확한 위치를 찾기 위한 도구다. 일반 모델이 전문 분야에서 쓸 만한 구조를 제안했다는 사실은 중요하다. 시민 과학자가 AI 에이전트로 대규모 자료를 뒤져 독립적인 관심을 끄는 신호를 낸 것도 중요하다. 오히려 결과가 중요할수록 **무엇을 했고 무엇은 아직 안 했는지** 적어야 다음 연구자가 그 위에 제대로 쌓을 수 있다.

## 편집자의 적용 시나리오 — 검증 단계를 생략하지 않는 자동화

가상의 연구 플랫폼이 GPT 계열로 단백질 후보를 만든다고 하자. 사용자는 표적, 접촉 위치, 원하는 물성 조건을 입력한다. 시스템은 설계 결과를 곧바로 ‘활성 단백질’ 목록에 넣지 않고 **구조 후보**로 등록한다. 그다음 서열 생성 단계가 어떤 도구를 썼는지 기록하고, 접힘·도킹의 계산 점수와 필터 조건을 연결한다. 실제 제작한 후보에는 배치와 측정법, 음성·양성 판정 기준을 붙인다. 마지막으로 기능 실험과 선택성 시험을 별도 상태로 둔다. 한 번 결합 양성이 나와도 이 사다리의 뒤 단계가 남아 있음을 UI에서 보여 주는 것이다. 이는 오늘 OpenAI가 출시했다고 발표한 플랫폼이 아니라, 발표의 한계를 제품 설계에 반영한 **가상 예시**다.

또 다른 가상의 천문 검색 플랫폼은 AI가 찾은 신호를 별 이름과 예상 주기, 원시 광도 곡선, 분석 코드 버전, 알려진 행성과의 대조 결과와 함께 저장한다. 재검색한 분석자의 이름과 방법, 새 관측 날짜, 쌍성 가능성의 평가가 각각 별도 근거로 붙는다. ‘후보’ 상태를 사람의 승인 클릭 하나로 ‘행성’으로 바꾸지 않고, 어떤 논문과 관측이 확정 판단을 뒷받침하는지 기록한다. 여기서 중요한 기능은 화려한 AI 설명이 아니라 **재현 가능한 증거의 연결**이다.

GitHub 알림 변화에 대비하는 팀이라면 에이전트가 PR을 만들었을 때 리뷰 요청 이벤트를 직접 기록하고, 사람에게 이메일이 도착했는지 별도 지표로 관측한다. 12월 첫 주에는 알림 표시 사유가 사용자마다 다르게 바뀔 수 있으므로 한 사용자의 화면만 보고 전체 규칙이 깨졌다고 하지 않는다. 알림 이메일 헤더에 여러 이유가 들어올 수 있으므로 문자열 전체 일치 필터는 샘플을 받아 재검증한다. Subscriptions 페이지가 줄어도 리뷰 요청이나 담당자 지정을 원본에서 찾는다. 이 역시 GitHub가 권장하는 특정 구현법을 그대로 재현한 것이 아니라, 공식 변경 내용을 읽고 제안한 운영 절차다.

세 가상 시나리오가 강조하는 것은 **상태와 근거를 분리**하는 일이다. 상태는 사람이 빨리 읽기 좋지만 근거를 잃기 쉽다. 근거는 많아 복잡하지만 이의 제기와 재평가가 가능하다. AI가 대량의 후보를 만들 때 상태는 더 간결해져야 하고, 뒤쪽 증거 기록은 더 충실해져야 한다. 제품은 두 요구를 함께 만족해야 한다.

## 심층 분석 A — 단백질 발표를 실제 연구 계획으로 번역할 때

오늘의 단백질 발표는 ‘범용 모델이 생물학을 한다’는 문장만으로는 정확히 읽히지 않는다. 연구 계획서로 바꿔 보면 최소한 **문제 정의, 구조 입력, 생성, 서열화, 계산 필터, 실험실 결합, 기능 시험, 후속 설계**의 흐름이 드러난다. 각각의 단계에서 필요한 전문성이 다르고, 성공의 의미도 다르다. 모델의 추론과 코딩이 앞 단계를 빠르게 만들었다고 하더라도 뒤 단계의 비용이 자동으로 사라지지 않는다. 이 절에서는 발표에 나온 각 실험이 그 흐름에서 어디에 놓이는지 더 세밀하게 나눈다. 다음의 연구 설계 질문은 OpenAI가 배포한 표준 운영 절차가 아니라, 발표의 숫자를 오독하지 않기 위한 편집상의 질문이다.

### A-1. 구조와 서열은 왜 한 묶음으로 다루면 안 되는가

아미노산 서열은 단백질의 일차적인 구성 정보이고, 3차원 구조는 그 서열이 물리적 환경에서 접힌 결과에 가깝다. 연구자가 바라는 것은 종종 ‘이 모양의 표면으로 저 표적에 붙는다’는 구조적 요구다. 그러나 컴퓨터가 그럴듯한 3차원 형태를 그렸다고 해서 어떤 서열이 실제로 그 형태를 안정적으로 만들지 결정되는 것은 아니다. 형태를 제안하는 모델, 서열을 제안하는 모델, 접힘을 예측하는 모델은 같은 질문의 다른 부분을 맡는다. 오늘 첫 실험에서 GPT-6.2의 역할이 형태 설계였고 SolubleMPNN 등 전문 모델의 역할이 서열화와 선별이었다는 점은 이 분업을 보여 준다.

연구 소개에서 ‘전문 생물학 모델을 사용하지 않았다’는 문장을 떼어 내면 오해가 시작된다. 어떤 **단계**에서 사용하지 않았는지를 붙여야 한다. GPT-6.2가 최초 형태를 만드는 동안 전문 생성 모델을 호출하지 않았다는 것은 의미 있는 주장이다. 하지만 후보를 제작 가능한 서열로 만들고 검사할 때 전문 모델의 도움이 있었다는 사실도 동시에 의미 있다. 두 문장은 서로 모순이 아니다. 자동화 파이프라인을 설계하는 팀도 자신들의 도구 목록을 숨기지 않고 각 도구가 어떤 의사결정에 기여했는지 기록해야 한다. 일반 모델을 사용했으므로 기존 도메인 도구를 모두 제거해도 된다는 결론은 이번 발표에서 나오지 않는다.

어떤 서열이 설계 구조로 접히는지를 계산으로 예측하는 과정은 실험 비용을 줄이려는 필터다. 필터가 강하면 실패 가능성이 높은 후보를 덜 만들지만, 좋은 후보를 버릴 수도 있다. 필터가 느슨하면 다양한 후보를 보존하지만 실험실의 부담이 커진다. 그래서 35/322 같은 실험 양성률은 앞 단계 필터의 기준과 분리해서 생각할 수 없다. 지나치게 강한 필터가 있었다면 원시 생성 후보의 잠재력을 제대로 측정하지 못할 수 있고, 지나치게 약한 필터가 있었다면 제작 비용 대비 낮은 양성률이 나올 수 있다. 발표 원문은 모든 후보의 상세 선택 규칙을 일반 독자가 즉시 재현할 수 있도록 완전한 실험 프로토콜로 정리한 것이 아니므로, 이 글은 알 수 없는 필터 성능을 임의로 채우지 않는다.

### A-2. 다섯 표적의 결과를 하나의 평균으로 평탄화하지 않기

PD-L1, IL-7Rα, TrkA, VEGF-A, IL-17A는 이름부터 다른 표적이다. 발표가 제시한 양성 수는 각각 5, 3, 1, 8, 18이다. 이 표만 보고 표적별 ‘성공률’을 계산하려면 각 표적에서 실제로 몇 개를 제작하고 검사했는지라는 분모가 필요하다. 전체 분모 322만 알려진 상태에서 18개가 나온 표적이 나머지보다 몇 배 더 쉬웠다고 말할 수는 없다. 특정 표적에 더 많은 후보를 배정했을 수도 있고 선별 기준이 달랐을 수도 있다. 연구 결과를 사업 계획에 옮길 때는 표적별 분모, 실험 반복, 결합 강도 분포, 실패한 후보의 종류를 추가로 확인해야 한다.

또한 ‘다섯 표적 모두에서 적어도 하나’와 ‘모든 설계가 잘 작동한다’는 전혀 다른 명제다. 연구팀이 다섯 조건의 다양한 예를 보여 준 것은 결과가 단일 표적의 특이한 우연만은 아니라는 초기 증거가 된다. 그러나 표적 집합이 얼마나 대표적인지, 질병 관련 표적과 비질병 표적이 섞여 있는지, 표면의 접근 가능성과 크기가 어떤지에 따라 실제 적용 범위는 달라진다. 따라서 새 표적을 맡은 팀은 다섯 표적의 10.9%를 자신의 성공 확률로 예산표에 복사하기보다, 유사한 실험 조건과 실패 원인을 먼저 살펴야 한다. 오늘 자료에는 새 표적별 성공 확률을 예측할 충분한 정보가 없다.

결합 양성의 기준 역시 중요하다. 스크리닝 실험에서 양성은 정해진 조건과 임계값을 넘어서는 측정일 수 있다. 농도, 측정 장비, 반복 횟수, 결합 강도, 비특이 결합의 처리에 따라 해석이 달라진다. OpenAI 발표는 실험실에서 표적 결합의 증거를 보고하지만, 이 글은 결과를 ‘특이적이고 강하며 생물학적으로 유효한 결합’으로 재해석하지 않는다. 연구 설계 검토자는 양성 여부와 함께 얼마나 강하게, 얼마나 안정적으로, 다른 표적에는 어떻게 붙었는지 찾아야 한다. 이 질문을 생략하면 양성률만 높은 방향으로 후보를 최적화하고 실제 쓰임과 동떨어진 결과를 얻을 수 있다.

### A-3. 알려진 결합 구조에서 새 서열을 만드는 과제의 의미

서열 재설계 실험은 원래의 서열을 숨겼지만, **이미 결합하는 구조 정보**를 제공했다. 연구자 입장에서 이것은 유용한 현실적인 문제다. 알려진 결합 부위를 바탕으로 새로운 서열 변형을 찾아 더 나은 제조 가능성이나 특성을 노릴 수 있기 때문이다. 그러나 이것은 미지의 표적에서 결합 위치도 구조도 아무것도 모르는 상태의 탐색보다 쉬울 수 있다. 발표의 MDM2, VEGF-A, PD-1 결과를 읽을 때는 ‘새로운 서열을 찾았다’와 ‘새로운 생물학적 표적의 최초 결합체를 발견했다’를 분리해야 한다.

세 표적의 양성 비율 차이도 연구에 중요하다. MDM2에서는 75/88, VEGF-A에서는 26/42, PD-1에서는 8/59였다. 숫자만 보면 같은 접근이 표적에 따라 훨씬 다른 결과를 낸다. 왜 그런지는 이 기사만으로 단정할 수 없다. 표적의 표면 구조, 주어진 결합체의 품질, 구조 자료의 정확도, 서열 생성 제약, 후보 선별법, 실험 조건 등 여러 요인이 있을 수 있다. 원인을 모르는 상태에서 ‘PD-1에는 모델이 약하다’고 결론 내리는 것도 지나치다. 분포 차이는 **추가 실험 질문**을 만든다는 점에서 가치가 있다. 연구팀은 실패한 PD-1 후보와 성공한 MDM2 후보를 같은 형식으로 기록해야 향후 기전을 비교할 수 있다.

원래 서열과 얼마나 다르게 만들었는지도 조심스럽게 읽어야 한다. 공개된 중앙값 차이 50%, 43%, 15%는 새로 제안한 서열이 단순 복제만은 아니라는 신호다. 그러나 서열 차이가 크다고 해서 기능상 더 새롭거나 더 안전하다고 뜻하지 않는다. 20개의 위치가 바뀌어도 구조와 기능이 거의 같을 수 있고, 한두 핵심 위치의 변화가 접힘이나 결합을 크게 바꿀 수도 있다. 어떤 위치가 바뀌었는지와 그 변화가 실험에서 무엇을 했는지가 중요하다. 서열 변화율을 혁신의 정도처럼 마케팅하는 것은 좋은 과학적 설명이 아니다.

미공개 구조 실험의 14/107 결과에는 별도의 장점이 있다. 발표에 따르면 이전에 공개되지 않았던 구조들에 대해 새 서열을 제안했고, 같은 구조에서 상당히 다른 서열 두 개가 결합한 예가 있다. 공개 데이터의 구조·서열을 그대로 외워 내놓았다는 설명으로는 이런 사례를 충분히 설명하기 어렵다는 연구진의 해석은 합리적인 출발점이다. 그렇지만 미공개 구조라는 한 가지 보호 장치가 모든 암기나 데이터 누수 가능성을 제거하는 것은 아니다. 구조 자체의 출처와 이전 설계 과정, 유사한 구조의 노출 가능성 등을 고려한 후속 독립 평가가 있으면 결론은 더 강해진다.

### A-4. 항체 고리 재설계는 무엇을 측정했는가

작은 항체 VHH의 세 결합 고리를 다시 설계한 실험은 기존 항체의 형태와 대부분의 서열을 유지하면서 중요한 부분만 바꾼 경우다. 182개 중 128개가 원 표적 IL-4Rα에 결합했다는 것은 상당한 설계 여지가 있음을 시사한다. 다만 ‘원 표적에 대한 결합 유지’는 ‘원래보다 더 좋다’는 말이 아니다. 결합 강도, 선택성, 발현량, 응집 경향, 안정성, 제조 용이성은 각각 별도로 봐야 한다. 실제 치료용 후보의 개발에서는 환자 안전성과 일관된 제조도 중요하다. 이 발표의 초기 결합 실험을 임상 단계의 성공으로 연결하지 않는 이유다.

치료용 항체 다섯 개의 결합 고리를 바꾼 실험은 완전한 항체가 아닌 **조각**을 대상으로 했다. 이 점은 작아 보이지만 해석에 큰 차이를 만든다. 항체 전체의 다른 부분과 결합할 때 구조가 달라질 수 있고, 제조나 안정성도 조각과 다를 수 있다. 272개 중 179개의 결합 양성은 ‘설계한 조각이 원 표적에 여전히 붙는가’를 답하는데, ‘새 치료제가 된다’는 질문에는 답하지 않는다. 특히 PD-1이나 PD-L1이라는 치료 관련 표적 이름을 보았다고 약효가 검증됐다고 생각해서는 안 된다. 표적과 약물 개발의 언어는 사람에게 강한 인상을 주지만, 실험의 측정 대상은 훨씬 좁다.

이 구분을 연구 보고서에 반영하려면 결과 테이블에 `assay_object` 같은 항목을 둬 **완전한 단백질인지 조각인지**를 기록하는 방식이 있다. 또 `measured_property`에 결합 여부인지, 결합 강도인지, 기능 변화인지를 따로 둔다. 이것은 편집자가 제안하는 데이터 모델이며 오늘 발표에 있는 데이터베이스 구현을 설명한 것이 아니다. 이렇게 하면 발표를 다시 인용하는 사람이 ‘항체 조각의 결합’이라는 정확한 단위를 놓치기 어렵다. 좋은 데이터 모델은 과장을 막는 작은 안전장치가 될 수 있다.

### A-5. 계산 벤치마크는 실제 실험의 대기열을 어떻게 바꾸나

MotifBench의 모티프 스캐폴딩에서는 특정 구조 특징을 유지하면서 주변 단백질을 만드는 과제를 평가했다. 원문은 30개 도전 과제를 사용했다고 설명한다. 내부 모델의 43.7%와 RFdiffusion의 27.8%는 **설계가 계산 검사 기준을 통과한 비율**로 소개된다. 그 기준에는 ProteinMPNN이 제안한 서열과 ESMFold의 예측 구조가 관여한다. 따라서 ‘기본 일반 모델이 전문 모델보다 효소를 더 잘 만들었다’고 번역하면 평가 단계가 바뀐다. 올바른 질문은 이 계산 기준을 통과한 후보가 실험실에서 얼마나 자주 원하는 기능을 보이는지다. 발표도 효소가 의도한 반응을 실제로 촉진하는지에는 실험이 필요하다고 명시한다.

계산 검사는 비용 대비 후보 우선순위를 정할 때 매우 유용하다. 하지만 검사 도구와 생성 도구가 비슷한 학습 자료나 구조적 편향을 공유하면, 점수의 개선이 실제 실험 성공의 개선보다 크게 나타날 수 있다. 이 가능성이 구체적으로 이번 결과에서 일어났다고 단정하는 것은 아니다. 연구팀이 무엇을 확인해야 하는지를 말하는 것이다. 서로 다른 평가 모델을 쓰거나 일부 후보를 점수와 무관하게 무작위로 뽑아 실제 실험해 보면 필터가 우수 후보를 얼마나 잘 가려내는지 볼 수 있다. 단순히 높은 점수만 제작하면 낮은 점수 영역에 진짜 성공 후보가 있었는지는 알기 어렵다.

전체 접힘 지정 과제에서는 내부 모델 18.9%, Proteina 17.1%가 보고됐다. 수치가 가깝기 때문에 평가 반복, 과제별 분포, 계산 예산의 차이가 있으면 해석이 달라질 수 있다. 이 글에는 통계적 유의성이나 신뢰구간이 공개 원문에서 확정된 것으로 제시되지 않았으므로, 근소한 차이를 확정적 우월성의 증거로 쓰지 않는다. 무엇보다 전체 접힘의 예측 일치 여부와 그 구조가 실제 세포에서 안정적으로 유지되는지는 다른 문제다. 도전 과제의 정의를 분석할 때는 성공 조건이 최소 한 서열의 예측 구조에 의존한다는 점을 기억해야 한다.

도킹 과제의 높은 백분율도 실험 상황을 한 줄로 압축하면 손실이 크다. PoseBusters에서는 단백질 구조와 작은 분자의 연결 정보가 주어지고, 결합 위치와 방향을 예측한다. Scarpino 자료에서는 단백질과 작은 분자 사이 특정 원자 결합을 미리 알려 준다. 두 번째는 실제 연구에서 중요한 조건부 예측이지만 정보량이 다르므로 두 수치를 같은 난이도의 시험처럼 비교하지 않는다. 발표에서 말하는 ‘채점된 예측’이 어떤 사례를 포함하는지와 제외하는지도 상세 평가를 위해 중요하다. 백분율만 빼서 모든 단백질-소분자 도킹의 성공률이라고 인용하면 시험 범위가 사라진다.

### A-6. 구조 예측의 약점을 왜 굳이 강조하는가

가장 좋은 보도가 가장 큰 성공 수치만 나열하는 것은 아니다. 오늘 발표에서 전체 구조 예측 TM-score의 격차는 중요한 경계 조건이다. 최신 내부 모델의 평균 0.38은 이전 일반 모델보다 개선됐지만, ESMFold2의 0.93과 큰 차이가 있다. 일반 모델이 특정 구조를 **설계**하는 과제나 제한된 조건에서 **도킹**하는 과제에서 강할 수 있으면서, 주어진 서열로부터 전체 단백질 구조를 **예측**하는 과제에서는 약할 수 있다. 이것이 발표가 말한 불규칙한 능력 경계다. 기술 도입에서 이 경계를 무시하면 강한 과제의 결과를 약한 과제의 보증으로 착각한다.

따라서 실험 계획에서 ‘모델이 무엇을 입력받는가’를 표의 첫 열로 두어야 한다. 표적의 3차원 구조가 있는가, 결합 위치를 아는가, 기존 결합체의 형태를 아는가, 원자 사이의 결합 정보를 아는가, 서열만 있는가. 입력 정보가 많아질수록 어떤 과제는 쉬워지고, 적어도 다른 과제가 된다. ‘모델 이름’만 적은 비교표는 실제 업무에 필요한 정보를 주지 못한다. 같은 GPT-6.2라도 구조 설계, 서열 재설계, 도킹, 전체 접힘 예측의 성과가 다르다. 모델 선택은 과제와 입력의 조건에 묶어야 한다.

### A-7. 검증을 위한 실제 회의 질문

과학팀과 엔지니어링팀이 함께 발표를 검토한다면 첫 회의에서 묻기 좋은 질문이 있다. *우리가 목표로 하는 단백질의 역할은 단순 결합인가, 생물학적 반응의 조절인가?* *원하는 결합 위치를 이미 아는가?* *새로운 형태를 원하나, 기존 구조의 서열 변형을 원하나?* *실험실에서 몇 개 후보를 만들 수 있나?* *실패를 어떻게 분류할 것인가?* *기존 전문 모델을 제거하려는 것인가, 도구 조합을 개선하려는 것인가?* 이 질문들에 답하기 전에는 기사 속 최고 수치가 우리 팀의 성공률을 예측하지 못한다.

다음 회의에서는 평가 설계를 따져야 한다. 동일한 표적 자료와 동일한 후보 선별 기준에서 일반 모델과 전문 모델을 비교할 수 있는가? 원래 알고 있던 결합체와 새로 찾는 결합체를 분리할 수 있는가? 실험자는 후보의 출처를 모르게 하여 측정 편향을 줄일 수 있는가? 반복 실험과 음성 대조군을 어떻게 둘 것인가? 이런 질문은 발표가 옳고 그르다는 논쟁보다 생산적이다. 과제의 경계가 명확해야 어느 단계에서 일반 모델의 유연성이 진짜로 전체 연구 주기를 줄이는지 알 수 있다.

셋째 회의는 결과의 표현을 검토한다. 내부 대시보드에 ‘표적 결합 양성’과 ‘유망한 치료제’를 구분했는가? 긍정 결과뿐 아니라 모든 시험 분모와 실패 유형을 기록했는가? 전문 모델이 선별한 사실을 자료의 주석이 아니라 파이프라인 단계로 표시했는가? 바이오보안 검토가 필요한 후보의 접근 통제를 누구에게 맡길 것인가? 과학적 결과의 정확한 표현은 법무·홍보만의 일이 아니다. 파이프라인을 만드는 개발자의 데이터 구조와 버튼 이름에서 시작한다.

## 심층 분석 B — 천문 탐색을 재현 가능한 데이터 파이프라인으로 보기

외계행성 기사는 화려한 ‘AI가 행성을 찾았다’는 표현보다 **공개 자료, 알려진 탐색법, 에이전트가 만든 코드, 독립 연구자의 검사**라는 연쇄에서 배울 점이 많다. 오늘 사례가 가치 있는 이유는 출발점과 중간 결과를 어느 정도 드러내면서도 끝을 확정하지 않았다는 데 있다. 별빛 감소의 원인을 결정하는 일은 시간과 관측 자원이 필요한 과학의 문제다. 코딩 에이전트의 기여는 탐색을 시도할 수 있는 사람의 폭을 넓히고 기존 자료를 다시 읽는 노동을 줄였다는 쪽에서 읽는 편이 정확하다.

### B-1. 공개 데이터라는 말에 포함되지 않는 것

Kepler와 TESS의 관측 자료가 공개되어 있다는 것은 누구나 같은 질문을 할 출발점이 있다는 뜻이다. 그러나 자료가 크고 복잡하므로 누구나 같은 답을 바로 얻는다는 뜻은 아니다. 관측 시간 범위와 별의 선택, 품질 플래그, 결측 구간, 기기의 변화, 밝기 보정 방식이 모두 검색 결과에 영향을 줄 수 있다. AI 에이전트가 공개 자료를 다루는 코드를 빠르게 만들수록 이런 전처리 결정이 묻히기 쉽다. 재현하려는 사람에게는 모델의 멋진 설명보다 구체적인 자료 버전과 실행 가능한 코드, 환경 정보가 더 중요할 수 있다.

또한 검색 대상 수가 클수록 우연한 패턴도 많아진다. 약 1,900만 개 별을 살펴보면 매우 드문 기기 아티팩트나 통계적 우연이 후보 목록에 남을 가능성이 있다. 이것은 Byrd의 49개 후보가 잘못됐다는 주장도, 검색의 가치가 낮다는 주장도 아니다. 대규모 탐색에서는 후보 점수의 임계값과 거짓 양성률, 후속 검사 비용을 함께 설계해야 한다는 일반적인 이유다. 분모를 크게 늘리는 AI 도구가 있으면 검증 단계의 설계도 그에 맞춰 커져야 한다. ‘엄청난 양을 검색했다’는 사실과 ‘확정 발견이 많다’는 결과를 혼동하면 안 된다.

### B-2. 알려진 행성 열 개는 어떤 테스트인가

Bond의 파이프라인이 이전에 확인된 행성의 신호 열 개를 다시 찾았다는 사실은 중요한 내부 점검이다. 기존에 정답이 있는 표본을 놓치지 않는다는 것은 탐색 코드를 신뢰할 첫 근거가 된다. 하지만 정답 열 개의 특징이 새로 찾으려는 희미한 신호의 특징과 다르다면 테스트의 강도는 제한된다. 밝은 별, 큰 행성, 깨끗한 관측 조건에서 보이는 신호를 잘 찾더라도 약한 신호에는 성능이 낮을 수 있다. 반대로 기존 정답 열 개만 찾아도 수많은 비행성 신호를 잘못 표시할 수 있다. 감도와 정확도는 별도 지표다.

개발팀의 회귀 테스트에 비유할 때도 이 제한을 포함해야 한다. 알려진 정답을 재발견하는 테스트는 코드가 기본 기능을 유지하는지 알려 준다. 그러나 새로운 입력에서의 일반화나 오탐 비용은 알려 주지 않는다. 천문학에서는 이미 확인된 행성의 신호를 일부 숨겨 두고 탐색법의 개선 여부를 시험하거나, 가짜 통과 신호를 자료에 주입해 복구율을 살펴보는 방법을 생각할 수 있다. 이 글은 Bond가 이런 방법을 모두 사용했다고 주장하지 않는다. **후속 평가를 설계한다면 무엇이 필요한가**를 설명하는 예시다.

### B-3. KIC 두 신호를 기사 제목으로 바꿀 때

KIC 5689121의 13.8일 주기, KIC 6691030의 4.8일 주기는 각 후보를 다시 관측할 수 있는 구체적인 단서다. 주기를 알면 다음 통과가 예상되는 시간을 계산할 수 있고, 여러 번 같은 깊이와 모양의 감소가 나타나는지 확인할 수 있다. 그러나 달력에 예상 시각을 적는 것과 그날 실제 신호가 반복된다는 것은 별도다. 오늘 공식 자료에는 새 관측으로 원인이 최종 확인됐다는 기록이 없다. 그래서 이 글은 두 별을 ‘새로운 행성이 있는 별’이 아니라 ‘주기적 밝기 감소가 포착된 별’로 부른다.

첫 별에서 ‘지구 지름의 약 2.4배’라는 추정 역시 행성 가설과 별 크기에 관한 추정에 의존한다. 밝기 감소의 깊이와 별의 크기가 알려져야 가리는 물체의 크기를 추정할 수 있다. 쌍성계나 관측 범위 안의 다른 별이 섞인 경우에는 해석이 달라질 수 있다. 두 번째 별의 ‘해왕성보다 작은 행성’ 가능성도 같은 조건부 표현이다. 특정 숫자가 있는 문장은 확정처럼 느껴지기 쉬우므로, 기사에서는 수치 앞이나 뒤에 **가설이 맞다면**이라는 조건을 반드시 남겨야 한다.

SETI 연구자가 같은 두 신호를 별도 검색에서 찾았다는 사실은 코딩 에이전트가 우연히 그린 그래프만은 아닐 가능성을 높인다. 이 결과를 무시해서도 안 된다. 동시에 원천 관측 자료가 같은 Kepler라면 기기나 원천 자료의 체계적 오류를 완전히 독립적으로 배제하는 데는 한계가 있다. 다른 관측기기, 다른 시점, 다른 물리적 측정 방법이 추가되면 증거는 더 강해진다. 독립성은 ‘있다/없다’의 한 단어가 아니라, **코드, 분석자, 자료, 장비, 이론적 방법** 중 무엇이 독립인지의 여러 축이다.

### B-4. 거주 가능 영역이라는 말이 낳는 오해

Byrd의 두 검색 중 하나는 별의 거주 가능 영역에 초점을 맞췄다. 이 용어는 생명 발견을 암시하는 듯하지만 과학적 정의는 더 좁다. 별로부터의 거리가 일정 범위에 있어 적절한 조건의 행성 표면에 액체 물이 가능할 수 있다는 개념이다. 적절한 대기가 실제로 있는지, 행성 표면이 어떤지, 물이 존재하는지, 생명체가 있는지는 별도 문제다. 거주 가능 영역의 후보를 발견했다고 해도 **생명체의 증거**가 되는 것은 아니다. 오늘 기사에는 그런 발견도 없다.

보도나 제품 설명이 이런 용어를 다룰 때 조건문을 생략하면 독자가 결과를 몇 단계나 앞질러 이해하게 된다. 후보가 별의 거주 가능 영역에 있을 ‘가능성’이라는 말과 확정된 지구형 행성, 실제 물, 생명 존재는 각각 다른 증거가 필요하다. AI가 데이터를 검색하는 속도가 높아지면 선정적인 중간 결과가 더 자주 등장할 수 있다. 편집자가 용어 정의를 짧게 붙이는 일은 단순한 문장 교정이 아니라 잘못된 연구 우선순위를 막는 장치다.

### B-5. 미래 관측은 왜 대기열 문제인가

외계행성 후보를 더 확인하려면 다음 통과 시각에 맞춰 관측을 예약해야 할 수 있다. 대상 별이 관측 가능한 위치에 있는지, 날씨와 장비 조건이 적절한지, 동일한 시간대에 다른 중요한 관측이 있는지에 따라 일정이 달라진다. 짧은 주기의 신호라도 매번 충분한 품질로 기록되는 것은 아니다. OpenAI 글이 확인에 수개월 또는 수년이 걸릴 수 있다고 하는 이유를 단순히 천문학이 느리기 때문이라고 읽지 말아야 한다. 새로운 자료를 얻는 비용과 여러 다른 원인을 검토하는 절차가 있기 때문이다.

검색 파이프라인이 하루에 내놓는 후보 수가 늘면 관측 대기열을 정하는 일도 중요해진다. 어떤 후보가 가장 강한지, 언제 관측할 수 있는지, 무엇을 관측하면 경쟁 가설을 가장 잘 구별할 수 있는지 정해야 한다. AI가 후보 순위를 제안할 수 있더라도 그 순위의 기준을 과학자가 검토해야 한다. 단순히 ‘모델 점수 상위’만 관측하면 훈련 자료나 코드가 선호한 특정 종류의 신호에 자원이 쏠릴 수 있다. 가끔은 점수가 낮지만 새로운 종류의 후보를 확인하는 것이 방법론 개선에 더 유용할 수 있다. 이것은 오늘 두 시민 과학자의 실제 관측 우선순위가 어땠다는 주장이 아니라, 후보가 많아질 때 생기는 일반적인 운영 문제다.

### B-6. 데이터 제품을 만든다면 어떤 기록이 필요한가

가상의 외계행성 후보 플랫폼에 필요한 최소 엔터티를 생각해 보자. **관측 자료 집합**에는 망원경, 수집 구간, 다운로드 시각, 자료 버전이 들어간다. **전처리 실행**에는 사용한 코드의 커밋, 설정, 누락값 처리, 품질 필터가 들어간다. **후보**에는 별의 식별자, 예상 주기, 밝기 감소의 크기, 신호 점수, 찾은 방법이 들어간다. **검증 결과**에는 독립 분석자, 새로운 관측 여부, 다른 원인의 검사와 결론이 들어간다. **지위**에는 후보, 추가 분석 중, 기각, 확인 같은 구분이 있을 수 있다. 이 설계는 오늘의 공식 서비스 스키마가 아니라, 재현성과 과장 방지를 위한 편집상의 예시다.

이 기록이 없다면 한 후보가 다른 코드 버전에서 사라졌을 때 이유를 찾기 어렵다. 자료가 바뀌었는지, 임계값이 바뀌었는지, 버그가 고쳐졌는지 알 수 없기 때문이다. 또 이미 확인된 행성을 새 후보로 다시 세는 중복도 생길 수 있다. 공개 자료 탐색에서는 같은 별을 다른 카탈로그 식별자로 부르는 일도 있을 수 있으므로 식별자 매핑이 중요하다. 발표는 실제 두 사례의 모든 데이터베이스 구조를 공개하지 않았고, 따라서 이 단락은 일반적인 제품 설계 관점에서의 제안이다.

### B-7. 시민 과학자와 전문 연구자의 역할을 대립시키지 않기

AI 도구를 통해 개인이 전문 분야에 기여한 이야기는 흥미롭다. 하지만 시민 과학자가 모든 검증을 직접 해야 한다거나, 전문 연구자가 AI로 대체된다는 식으로 읽을 필요는 없다. Bond와 Byrd의 작업은 기존 공개 자료와 발표된 탐색법 위에 서 있다. 두 신호의 독립 재검색에는 SETI 연구자의 전문성이 들어갔다. 후보를 더 확인하려면 장비 운영과 천체물리 해석을 아는 연구자의 시간이 든다. 이런 협업 구조가 있었기에 후보가 독립적인 관심을 끌 수 있었다. AI의 역할을 제대로 평가하려면 **사람이 이미 구축한 자료와 방법, 그리고 뒤에서 검증하는 사람**을 함께 보여 줘야 한다.

동시에 전문 지식이 있어야만 첫 질문을 할 수 있다는 문턱이 낮아질 수 있다는 점도 인정해야 한다. 공개 자료가 아무리 많아도 도구 사용과 코드 작성이 어려워 탐색을 시작하지 못했다면 중요한 후보가 묻혀 있을 수 있다. 자연어로 방법을 비교하고 코드를 만들고 돌리는 능력은 다양한 관심을 가진 사람이 데이터에 접근하는 방법을 넓힌다. 좋은 협업 모델은 ‘전문가 대 시민’의 승부가 아니라, 열린 자료에서 더 많은 질문을 만들고 그 질문을 전문가가 엄밀하게 검토할 수 있도록 전달하는 절차다.

## 심층 분석 C — GitHub 알림 변경을 운영 사고 없이 받아들이는 법

GitHub 공지는 오늘의 과학 뉴스와 직접적인 관련이 없지만, AI 에이전트가 코드를 만들고 사람에게 검토를 넘기는 팀에는 별도의 중요한 소식이다. 알림은 사실상 사람과 자동화 사이의 업무 전달 수단이기 때문이다. 이번 변경은 알림을 더 예측 가능하게 하려는 시스템 이전이며, 12월 1일에 시작해 약 일주일 동안 사용자별로 순차 적용된다. 여기서 첫 운영 원칙은 **공지일, 적용 시작일, 내 계정의 실제 관측일**을 분리하는 것이다. 어제 공지가 나왔다고 오늘 현재의 화면이 이미 새 규칙을 따른다고 쓰지 않는다.

### C-1. 구독 이유가 여러 개인 스레드

한 사람이 PR을 작성하고 리뷰를 요청받고 댓글을 쓰고 팀 멘션에도 포함될 수 있다. 이런 스레드의 알림은 하나의 원인으로만 설명되지 않는다. 이전 규칙에서 멘션을 제거했을 때 다른 참여 사유가 있어도 알림이 멈추는 문제가 있었다고 GitHub는 설명한다. 새 규칙에서는 멘션이 제거돼도 댓글 참여나 담당자 지정 등 다른 사유가 남아 있으면 구독이 이어진다. 반대로 팀을 떠난 사람은 그 팀 멘션만을 이유로 한 미래 알림이 멈춘다. 보이는 알림 이유 하나만 보고 모든 구독 경로를 추론하면 틀릴 수 있다.

사람이 수동으로 구독을 해제했다는 이벤트의 뜻도 더 안정된다. 단순한 댓글이나 리뷰 제출, 스레드 상태 변경, 머지 큐 활동만으로 다시 구독되지 않는다. 그러나 직접 멘션, 담당자 지정, 리뷰 요청은 사람의 주의를 명시적으로 요구하므로 다시 구독될 수 있다. 이 차이를 회피 방법으로 생각하면 안 된다. 예를 들어 구독을 해제한 사람에게도 리뷰가 꼭 필요하다면 댓글을 남기는 대신 올바르게 리뷰 요청을 해야 한다. 반대로 조용히 지나가게 하고 싶은 스레드에서 사람을 직접 멘션하면 기대와 달리 새 알림이 간다.

### C-2. 표시 reason과 실제 발생 이벤트

GitHub 받은편지함에 표시되는 알림 사유는 새 우선순위 규칙을 따른다. 같은 스레드에서 최근 댓글이 달렸더라도 그 사람이 멘션 대상이면 표시 사유가 멘션으로 남을 수 있다. 이는 최근 댓글이 없었다는 뜻이 아니다. 표시 reason이 이벤트 로그와 다르다는 기본적인 구분을 자동화에 반영해야 한다. 이메일 본문이나 헤더를 읽어 ‘현재 처리해야 하는 일’을 분류하는 팀이라면 단일 reason이 최신 활동이라고 가정한 규칙을 검토해야 한다. GitHub가 이메일 헤더에 모든 적용 가능한 이유를 넣겠다고 했으므로 헤더가 복수값을 담을 가능성을 수용해야 한다.

우선순위의 자세한 순서는 멘션, 팀 멘션, 담당자 지정, 리뷰 요청, 댓글, 수동, 작성자, 상태 변경, 구독됨이다. 이슈의 담당자 지정은 별도로 가장 높다. 이 순서를 모든 문맥의 중요도 순위라고 해석해서는 안 된다. 조직마다 리뷰 요청이 멘션보다 더 중요한 업무일 수 있고, 보안 이슈의 상태 변경이 일상 멘션보다 긴급할 수도 있다. GitHub의 순서는 **하나의 알림에 어떤 reason을 보여 줄지** 정하는 표시 정책이지, 팀의 업무 우선순위를 대신하지 않는다. 따라서 사람의 업무 큐를 구축한다면 원본 이벤트 종류와 내부 우선순위를 따로 정해야 한다.

### C-3. 받은편지함과 Subscriptions 페이지의 서로 다른 역할

Subscriptions 페이지가 이제 수동으로 추가한 구독만 보여 준다는 변화는 많은 사람에게 조용히 체감될 수 있다. 목록이 갑자기 짧아져도 알림 시스템이 스레드를 잊은 것은 아닐 수 있다. 작성자·댓글 참여·담당자·멘션·리뷰 요청으로 발생한 알림은 받은편지함에서 관리한다. 사용자가 ‘왜 이것이 여기에 안 보이나’를 묻는다면 페이지가 오류라고 단정하기 전에 해당 스레드에 수동 구독을 한 적이 있는지 확인해야 한다. 제품 운영팀이라면 이 차이를 12월 첫 주의 짧은 내부 안내에 담을 수 있다.

알림을 대량으로 정리하는 작업도 페이지에 따라 달라진다. 수동 구독 목록을 정리하려는지, 지금 받은 모든 업무 알림을 관리하려는지를 먼저 묻는다. 전자라면 Subscriptions 페이지가 맞고, 후자라면 알림 받은편지함이 맞다. PR 리뷰 요청을 놓치지 않도록 하기 위해 두 화면이 같은 스레드 수를 보여야 한다는 잘못된 기대를 버려야 한다. 숫자의 차이는 시스템 이전이 아니라 페이지 정의의 차이일 수 있다. 물론 실제 누락이 없다는 확인은 원본 PR의 리뷰 요청과 받은편지함을 대조해 해야 한다.

### C-4. 단계적 배포의 관측 방법

GitHub는 이전 기간 중 사용자마다 알림 동작이 다를 수 있다고 명시했다. 따라서 같은 조직에서 A는 새 reason 우선순위를 보고 B는 아직 이전 reason을 보는 상황이 잠시 생길 수 있다. 이는 변경 공지가 예고한 상태이므로 한 계정만으로 전체 사용자 경험을 일반화하지 않는다. 자동화 규칙을 점검하려면 사용자별 시점, 알림을 일으킨 원본 이벤트, 받은 이메일 헤더, 받은편지함의 표시 reason을 함께 기록하는 것이 좋다. 개인정보와 회사 정책에 맞게 필요한 범위만 수집해야 한다.

검증용 시나리오를 미리 정해 두면 변경을 받아들이기 쉽다. 예컨대 수동 구독 해제 후 댓글만 쓴 경우, 다시 직접 멘션된 경우, 팀에서 나간 뒤 과거 팀 멘션 스레드에 새 댓글이 달린 경우, 멘션이 삭제됐지만 여전히 담당자인 경우를 살핀다. 테스트용 비공개 저장소에서 조심스럽게 관측할 수 있지만, 조직의 실제 권한과 설정에 따라 결과가 달라질 수 있다. 공개 공지가 현재의 모든 계정에서 이미 적용됐다고 가정한 자동 판정 스크립트는 피해야 한다. 실험 결과를 기록할 때도 이번 변경의 **적용 범위가 GitHub.com이고 GitHub Enterprise Server는 제외**된다는 점을 붙인다.

### C-5. 사람의 주의와 승인 기록은 다르다

AI 코딩 에이전트가 PR을 만들고 자동으로 리뷰 요청을 보내는 팀에서는 알림이 ‘검토가 필요한 일이 생겼다’는 신호다. 사람이 이메일을 읽었거나 알림이 배달됐다는 사실이 코드 승인을 뜻하지 않는다. 반대로 이메일이 스팸 필터에 걸렸더라도 PR의 리뷰 요청 상태는 남을 수 있다. 팀의 감사 추적에는 PR의 작성자, 커밋, CI 결과, 리뷰어의 실제 승인 또는 변경 요청, 머지 시각을 원본으로 써야 한다. 알림 기록은 전달이 제대로 됐는지 평가하는 보조 지표다. 이 분리 덕분에 GitHub의 표시 reason이 바뀌어도 승인 체계의 의미가 흔들리지 않는다.

어제 다룬 GitHub issue status와 오늘의 알림 공지를 혼동하지 않는 것도 중요하다. 이슈의 상태는 업무 단계의 표현이고, 알림 reason은 스레드를 왜 보게 됐는지에 관한 표현이다. 하나는 일을 **어디까지 했는가**, 다른 하나는 **왜 나에게 알림이 왔는가**를 답한다. 에이전트가 이슈 상태를 `In review`로 바꿨다고 해서 특정 인간 리뷰어가 실제로 알림을 받았다는 보증은 아니다. 리뷰 요청이 발생했다고 이슈가 자동으로 올바른 단계로 이동했다는 뜻도 아니다. 여러 자동화가 연결될수록 각 상태의 원본과 책임자를 분리해야 한다.

## 심층 분석 D — 과학 뉴스를 위한 재현성·통계 체크

오늘 사례는 일반 독자가 곧바로 실험을 재현할 수 있는 완전한 방법 문서가 아니다. 그렇다고 독자가 숫자를 그대로 받아들이거나 완전히 무시할 필요도 없다. 공개 발표의 정보와 아직 확인할 정보를 표로 나눠 보면 다음 읽기가 명확해진다. 재현성은 모든 사람이 같은 장비를 즉시 가질 수 있다는 뜻이 아니라, 연구 결과의 경로를 추적하고 가능한 부분을 독립적으로 시험할 수 있다는 뜻이다.

### D-1. 연구 결과의 단위 정의

단백질 실험에서 가장 작은 단위가 ‘생성 프롬프트’인지 ‘설계 구조’인지 ‘서열 후보’인지 ‘제작한 단백질’인지 먼저 정해야 한다. 한 구조에서 여러 서열이 나왔다면 제작 후보 수와 독립 구조 수는 다르다. 같은 표적에서 여러 후보가 결합해도 그것이 독립적인 설계 원리를 여러 개 발견했다는 뜻은 아니다. 오늘 322개, 107개, 182개, 272개는 서로 다른 실험의 서로 다른 제작·검사 단위다. 이 숫자들을 합쳐 ‘총 몇 개 중 몇 개 성공’이라고 새로운 전체 성공률을 만들면 문제가 달라진다. 생물학적 목적과 선별 절차가 다르기 때문이다.

천문 탐색에서도 ‘별’, ‘광도 곡선’, ‘표시된 신호’, ‘후보 천체’, ‘확인된 행성’은 다른 단위다. 한 별에서 여러 구간과 여러 주기가 표시될 수도 있고, 같은 천체가 여러 카탈로그에 등장할 수도 있다. Bond의 약 10만 개 별과 200개 이상 신호, Byrd의 약 1,900만 개 별과 49개 후보는 같은 단계의 분자·분모가 아니다. 독자는 각 수치 옆의 단위를 읽어야 한다. 뉴스가 단위 없이 ‘AI가 200개 행성을 찾았다’라고 쓰면 공식 원문보다 훨씬 앞선 주장으로 바뀐다.

GitHub 알림에서는 ‘알림 건수’와 ‘고유 스레드 수’, ‘구독 이유 수’, ‘실제 리뷰 요청 수’가 다르다. 이메일 헤더에 이유 여러 개가 들어가면 알림 한 건의 reason 수가 늘 수 있지만 새로운 업무가 생긴 것은 아닐 수 있다. Subscriptions 페이지의 항목 수가 줄어도 실제 구독 이유의 전체 수는 줄지 않을 수 있다. 분야마다 단위는 다르지만, **단위를 먼저 정의하고 비교한다**는 습관은 공통이다.

### D-2. 성공률이라는 단어의 네 가지 얼굴

첫째는 **생성 후보 중 계산 검사 통과율**이다. 이것은 모델과 평가 도구의 조합을 반영한다. 둘째는 **실제 제작·측정 후보의 양성률**이다. 이것은 앞 단계의 선별과 실험 조건을 반영한다. 셋째는 **표적별 유용한 기능을 보인 비율**이다. 결합보다 더 좁고 실무에 가까운 성공 정의다. 넷째는 **전체 프로젝트에서 실제로 사용할 수 있는 결과를 얻은 비율**이다. 제조, 비용, 안전, 규제까지 포함하면 더 좁아질 수 있다. 오늘 발표의 10.9%는 둘째에 가까우며 넷째가 아니다. 이 구분 없이 한 단어로 ‘성공률’이라고만 쓰면 독자의 기대가 움직인다.

천문학의 성공률도 마찬가지다. 알려진 행성 신호를 다시 찾는 비율은 검색의 회수 능력을 본다. 표시된 후보 중 실제 행성인 비율은 정밀도를 본다. 새 관측까지 이어져 연구 공동체에서 확인되는 비율은 검증과 관측 자원의 영향을 받는다. 오늘 자료에는 200개 이상 신호 중 행성 확정 비율이 제시되지 않았다. 따라서 확인된 열 개의 신호를 포함해 몇 퍼센트가 맞았다는 새 계산을 만들지 않는다. 검증되지 않은 후보를 분모에 넣어 모델의 정밀도를 추정할 수 없기 때문이다.

### D-3. 공개 자료와 학습 자료의 겹침

단백질 구조와 도킹 과제 중 일부는 공개된 데이터셋에 기반한다. 일반 목적 모델의 훈련 자료에 해당 구조나 비슷한 사례가 들어 있었을 가능성을 완전히 제거하기 어렵다. OpenAI 발표도 항체 도킹의 공개 구조에 이런 가능성이 있다고 적는다. 이 가능성 때문에 모든 좋은 결과를 암기로 치부해서는 안 된다. 반대로 공개 데이터 평가만으로 처음 보는 생물학 문제에 대한 일반화가 입증됐다고 해서도 안 된다. 새로 수집한 실험 자료, 공개되지 않은 구조, 시간상 나중에 생성된 자료에서 결과를 보는 설계가 중요하다.

천문 자료에서도 공개된 확인 행성 목록은 검색 코드의 기본 테스트에 유용하지만, 새로운 후보의 확인을 대체하지 않는다. 이미 알려진 행성이 어디에 있는지 알고 나면 코드를 그 사례에 맞게 조정할 수 있다. 그런 조정이 일반적인 약한 신호 탐색에도 도움이 되는지는 별도 평가가 필요하다. 개발자가 검증 세트를 반복해서 보며 규칙을 바꾸면 사실상 그 세트에 과적합할 수 있다는 점과 비슷하다. 그렇기 때문에 공개 자료의 재탐색과 미래 관측의 역할을 나눠야 한다.

### D-4. 선택 편향을 의식하기

뉴스는 대개 가장 보여 주기 좋은 사례를 고른다. 단백질 그림에는 구조가 잘 맞는 후보가, 천문 기사에는 흥미로운 두 신호가 등장할 수 있다. 그런 사례는 방법을 설명하는 데 유익하지만 전체 결과의 분포를 대체하지 않는다. 숫자 표와 실패 사례, 제한 사항이 필요한 이유다. 오늘 OpenAI 단백질 글은 전체 분모와 약한 과제를 함께 적어 이러한 위험을 일부 줄인다. 외계행성 글도 두 신호를 확정하지 않았고 처음 표시된 신호 수를 제시한다. 그렇더라도 독자는 대표 사례와 전체 평가를 구분해야 한다.

코딩 에이전트의 데모도 비슷하다. 에이전트가 단번에 복잡한 버그를 고치는 영상은 가능성을 보여 준다. 그러나 여러 저장소에서 반복될 때의 실패율, 사람의 수정 시간, 도구 비용을 알려 주지는 않는다. 오늘 과학 뉴스가 개발자에게 유용한 것은 바로 이 평가 습관 때문이다. 모델이 실제로 할 수 있는 일을 인정하면서, 보고 싶은 장면이 아니라 **전체 파이프라인의 분포**를 요청하게 만든다.

### D-5. 비교를 위한 통제 가능한 변수

단백질 설계 접근을 비교한다면 같은 표적 집합, 같은 표적 구조, 같은 결합 위치 정보, 비슷한 후보 생성 예산, 같은 전문 선별 도구, 같은 실험 양성 기준이 필요하다. 한쪽에 더 많은 서열 후보를 주거나 다른 필터를 적용하면 구조 생성 단계의 차이를 보기 어렵다. 모든 변수를 완전히 같게 하기 어려울 수 있지만, 다른 부분을 명시해야 해석할 수 있다. 오늘 발표의 RFdiffusion 비교를 조심스럽게 읽는 이유도 후보 필터와 결합 정의가 결과에 큰 영향을 줄 수 있기 때문이다.

천문 검색 접근을 비교하려면 같은 별 집합, 같은 관측 구간, 같은 품질 필터, 같은 후속 확인 기준이 있어야 한다. Kepler와 TESS의 자료를 섞어 도구 순위를 매기면 망원경과 관측 계획의 차이가 모델 차이처럼 보일 수 있다. 알려진 행성을 어떤 세트에 배치했는지와 새 후보의 실제 판정이 얼마나 진행됐는지도 중요하다. 보도 자료에는 모든 비교 변수를 상세히 담기 어렵지만, 우리 조직이 도구 채택을 결정할 때는 이런 통제 설계를 요구할 수 있다.

### D-6. 실험의 부정적 결과를 다루는 언어

결합이 없었던 단백질 후보는 설계 모델이 ‘쓸모없다’는 판정이 아니라, 그 조건에서 그 후보가 원하는 측정 기준을 넘지 못했다는 결과다. 별빛 감소의 원인이 기기 효과로 밝혀진 후보도 탐색 시도가 ‘무의미했다’는 뜻이 아니다. 오탐의 특징을 알면 다음 검색을 개선할 수 있다. 반대로 긍정 결과가 나왔다고 전체 시스템의 약점이 사라진 것도 아니다. 연구에서는 **조건과 측정법을 붙인 좁은 결론**이 훨씬 유용하다. 실패를 추상적인 평가로 바꾸지 않고 다음 설계에 쓸 수 있는 자료로 남겨야 한다.

AI가 후보를 더 많이 만들면 실패 결과도 더 많이 쌓일 수 있다. 잘 정리된 실패는 향후 모델과 필터를 개선하는 데 가치가 있다. 다만 모든 실패를 모델 학습 자료로 즉시 투입하는 것은 별도 결정이다. 자료 사용 권한, 생물안보, 개인정보와 협업자의 기여, 평가 데이터의 독립성까지 고려해야 한다. 오늘 OpenAI 발표는 이런 모든 정책의 실행 방안을 제공하지 않는다. 우리는 데이터가 쌓일수록 의사결정의 경계도 함께 설계해야 한다는 운영 결론만 제안한다.

## 심층 분석 E — 발표를 읽은 뒤 팀이 작성할 수 있는 의사결정 문서

과학 뉴스를 읽는 개발팀은 바로 모델을 바꾸거나 대시보드를 만드는 대신, 한 페이지짜리 **결정 기록**을 남길 수 있다. 그 문서의 목적은 기술을 늦추는 것이 아니라 기대와 검증 기준을 일치시키는 것이다. 오늘 두 OpenAI 소식은 분야가 다르지만 어떤 질문을 문서화해야 하는지 잘 보여 준다. 단백질 분야는 후보의 물리적 제작과 실험이 필요하고, 천문학은 새로운 관측과 원인 배제가 필요하다. 개발팀의 일반적인 AI 기능 역시 사용자 목적과 실제 실패 비용을 기준으로 평가해야 한다.

### E-1. ‘무엇을 자동화하는가’를 한 문장으로 쓰기

‘단백질 연구를 AI로 자동화한다’는 문장은 너무 넓다. ‘알려진 표적 구조와 지정된 결합 위치를 받아 미니바인더의 3차원 형태 후보를 생성한다’처럼 쓰면 오늘 첫 실험과 비교 가능한 범위가 생긴다. ‘외계행성을 찾는다’보다 ‘공개 Kepler 광도 곡선에서 반복되는 낮은 진폭의 감소 신호를 후보로 추린다’가 낫다. ‘PR 리뷰를 자동화한다’보다 ‘에이전트가 만든 PR의 리뷰 요청 이벤트를 담당자에게 전달하고 실제 승인 상태를 별도로 기록한다’가 낫다. 입력, 출력, 사람의 책임이 한 문장 안에 들어가면 과장된 성공 기준이 줄어든다.

이 문장을 쓰지 못한 상태에서 성능 비교를 시작하면 서로 다른 과제를 한 표에 놓기 쉽다. GPT-6.2의 도킹 점수와 전체 접힘 예측 점수를 비교해 모델의 평균 능력을 논하거나, Kepler 검색의 표시 신호 수와 TESS 검색의 후보 수를 비교하는 식이다. 일을 좁게 정의하면 어떤 자료가 실제 근거이고 어떤 자료가 참고 맥락인지 분리할 수 있다. 문장이 좁아지는 것은 비전을 포기하는 게 아니라, 다음 실험이 답할 수 있는 질문을 고르는 일이다.

### E-2. 최소 유효 증거를 미리 정하기

도입 결정을 내리기 전에 ‘어떤 결과가 나오면 다음 단계로 갈 것인가’를 적어 두어야 한다. 단백질 형태 생성 도구의 경우 계산 점수만으로 제한된 실험 대상에 들어갈지, 첫 결합 양성이 나와야 추가 예산을 쓸지, 기능 시험 전에는 어떤 주장도 외부에 발표하지 않을지를 미리 정할 수 있다. 외계행성 탐색이라면 독립 분석을 통과한 후보만 후속 관측 대기열에 넣을지, 이미 알려진 행성 재발견 결과를 기본 품질 확인으로만 쓸지 정할 수 있다. 이런 기준은 팀의 목표에 따라 달라지며 오늘 발표에 정답이 적혀 있지는 않다.

기준을 나중에 고르면 긍정 결과에 맞춰 골대를 옮기기 쉽다. ‘예상보다 후보가 많이 나왔으니 성공’이라고 하다가 실제 확인된 결과가 없으면 ‘탐색 범위를 넓힌 것이 성공’이라고 다시 정의하는 식이다. 발견 단계의 폭을 넓힌 성취 자체도 가치가 있지만, 처음 목표가 무엇이었는지는 남겨야 한다. 그래서 생성량, 검증 통과량, 최종 유용 결과, 소요 시간과 비용을 별도 칸으로 정해 둔다. AI 도구의 평가가 장기 연구 성과를 하루 만에 판정할 수 없더라도, 관측 가능한 중간 지표의 의미는 정확히 정의할 수 있다.

### E-3. 책임의 인계 지점

일반 모델이 후보를 만들고 전문 모델이 선별하면 어느 단계의 오류를 누가 조사할까? 후보 형태가 물리적으로 불가능했는지, 서열화가 실패했는지, 접힘 예측이 낙관적이었는지, 실험이 재현되지 않았는지 구분해야 한다. 천문 파이프라인에서는 데이터 수집과 전처리, 주기 검색, 사람의 후보 검토, 독립 관측이 각각 인계 지점이다. 이 단계들이 한 사람이나 한 에이전트의 내부 대화에만 있으면 오류 원인을 찾기 어렵다. 산출물을 넘길 때 입력·방법·버전·불확실성도 함께 넘기는 관례가 필요하다.

GitHub 알림 체계의 변경도 인계 지점을 드러낸다. 에이전트가 PR을 작성해 리뷰를 요청하는 순간 업무는 사람에게 넘어간다. 알림 이메일이 생성된 순간과 사람이 실제 리뷰를 한 순간은 다르다. 리뷰어가 팀에서 이동했거나 스레드의 팀 멘션이 제거됐더라도 PR의 리뷰 요청과 담당자 정책을 따로 확인해야 한다. ‘알림이 왔으니 사람이 봤겠지’라는 가정은 승인 절차가 아니다. 자동화는 원본 요청이 누구에게 전달되도록 설계됐고 실제로 누가 응답했는지를 별도로 관측해야 한다.

### E-4. 위험 등록부의 초안

단백질 도구의 위험 등록부에는 최소한 **허위 결합 예측, 실제 결합의 비특이성, 기능 부족, 구조·서열 자료의 누수, 생물보안 검토 누락, 선별 도구의 편향**을 적을 수 있다. 각 항목에는 탐지 방법과 중지 기준이 필요하다. 예를 들어 계산 점수는 높지만 실험에서 결합이 없으면 생성 모델뿐 아니라 선별 모델과 실험 조건을 함께 검토한다. 원하지 않는 표적에 결합하는 경우는 결합 양성 수치에 가려질 수 있으므로 선택성 평가를 추가한다. 이 목록은 오늘 연구의 실제 사고 기록이 아니라 도입팀이 검토할 수 있는 가상의 위험 목록이다.

천문 도구의 위험 등록부에는 **장비 기원의 주기 신호, 두 별의 가림 현상, 전처리 오류, 카탈로그 식별자 혼동, 후속 관측 불가, 확정 전 홍보**가 들어갈 수 있다. 주기 신호를 발견했을 때 별도의 분석으로 확인하고, 관측 가능성을 검토하며, 공개 문구를 ‘후보’로 제한하는 대응을 붙인다. 과학 검증과 커뮤니케이션 검증이 둘 다 필요하다. 후보가 틀렸을 때 신뢰를 잃지 않으려면 처음부터 불확실성을 명시하는 편이 낫다.

GitHub 운영의 위험 등록부에는 **reason 기반 필터의 오분류, 수동 구독 화면의 오독, 팀 구성원 변경 시 알림 차이, 단계적 배포 중 계정 간 불일치**를 넣을 수 있다. 실제 원본 이벤트와 알림 전달을 분리해 비교하면 문제가 어느 층에서 생겼는지 알 수 있다. 이전 기간이 끝난 뒤에도 계정별 관측이 기대와 다르면 공식 공지의 설명과 실측 자료를 근거로 조사하면 된다. 공지의 모든 동작을 한 번의 수동 시험으로 완전히 증명하려고 할 필요는 없다.

### E-5. 비용 모델을 후보 단위가 아니라 검증 단위로 바꾸기

AI가 후보를 싸게 만들면 후보 한 개당 계산 비용은 작아질 수 있다. 그러나 실험실 제작, 망원경 시간, 사람의 리뷰는 여전히 희소할 수 있다. 그래서 예산표에는 모델 호출 비용만 아니라 **실험 또는 관측 한 건의 비용, 거짓 양성 후보를 검토하는 시간, 진짜 양성을 놓쳤을 때의 손실**을 넣어야 한다. 어떤 필터가 양성률을 높였더라도 좋은 후보를 과도하게 버리면 전체 발견 수가 줄 수 있다. 반대로 후보를 거의 걸러내지 않으면 후속 검증 대기열이 감당할 수 없게 된다. 최적점은 목표와 자원에 따라 달라진다.

기술 시연에서 ‘과거에는 100개의 후보를 만드는 데 며칠이 걸렸는데 이제 몇 분’이라고 말하는 것만으로 생산성 향상을 결론 내리면 안 된다. 실험 결과가 돌아오는 주기, 다시 설계하는 데 필요한 시간, 승인과 안전 검토의 지연을 합쳐야 한다. 종단 간 주기가 단축되는지 확인하지 않으면 생성 단계의 속도만 높아질 수 있다. 오늘의 과학 두 소식은 그 가능성을 보여 주지만, 모든 연구팀에서 비용 효율이 얼마나 좋아졌는지라는 보편 수치를 제공하지 않는다. 따라서 각 팀은 자신의 자료로 측정해야 한다.

### E-6. 보도 문구에 쓸 수 있는 좁은 표현

정확한 보도 문구는 길 필요가 없다. ‘GPT-6.2가 제안한 단백질 형태를 전문 모델의 서열화·선별과 결합해 제작한 322개 중 35개에서 표적 결합 양성을 확인했다’는 문장은 길지만 무엇이 측정됐는지 보존한다. 더 짧게는 ‘일반 모델의 설계가 실험실 결합 후보로 이어졌다. 전문 모델의 후속 단계가 함께 쓰였다’고 쓸 수 있다. ‘GPT-6.2가 약물을 만들었다’는 문장은 짧지만 사실의 단계를 몇 개나 건너뛴다. 정직한 문장은 기술을 덜 흥미롭게 만드는 것이 아니라, 실제 다음 연구의 의미를 정확하게 전달한다.

외계행성에 대해서는 ‘AI를 이용한 공개 자료 검색에서 새 후보 신호가 나왔고 두 신호를 독립 연구자가 같은 Kepler 자료에서 다시 찾았다. 행성 여부는 미확정이다’가 핵심이다. ‘새로운 행성 두 개를 발견했다’는 아직 이르다. GitHub에 대해서는 ‘12월 1일부터 약 일주일 동안 GitHub.com 알림 구독과 표시 reason을 순차 변경한다’가 맞다. ‘오늘 모든 GitHub 사용자의 알림이 바뀌었다’는 공지의 적용 일정을 지운다. 기술 기사에서 동사와 시제 하나가 증거의 범위를 바꾼다.

## 심층 분석 F — 분야를 가로지르는 검증 질문 20개

아래 질문은 회의 중 원문과 우리 팀의 실험을 나란히 놓고 확인하기 위한 도구다. 모두를 한꺼번에 답할 필요는 없다. 목적은 ‘AI가 잘했다’와 ‘AI가 못했다’ 사이의 성급한 이분법 대신, 무엇을 더 측정해야 하는지 구체화하는 것이다.

1. **오늘의 결과가 직접 측정한 물리량은 무엇인가?** 단백질 결합 신호인지, 구조 예측의 일치인지, 별의 밝기인지, 알림 reason의 표시인지 먼저 적는다.
2. **그 물리량에서 최종 목표까지 몇 단계가 남는가?** 결합에서 약효까지, 밝기 감소에서 행성 확인까지, 알림에서 승인까지 각각 단계가 다르다.
3. **입력 정보 중 사람이 이미 알고 준 것은 무엇인가?** 결합 위치와 구조, 알려진 원자 결합, 행성의 기존 목록 같은 정보는 과제를 바꾼다.
4. **생성 단계 외에 어떤 도구가 개입했는가?** 전문 서열·접힘 모델이나 사람의 선별 역할이 빠지면 기여도를 잘못 나눌 수 있다.
5. **실험 대상은 어떻게 골랐는가?** 선별이 강할수록 제작 후보의 양성률만으로 생성 모델을 평가하기 어렵다.
6. **실패 후보의 수와 종류는 남아 있는가?** 긍정 사례만 저장하면 다음 개선에 필요한 정보가 사라진다.
7. **기존에 알려진 사례를 다시 찾은 것인가?** 알려진 행성 재발견은 기본 점검이지만 새 발견과 합산하지 않는다.
8. **평가 자료가 모델 학습과 독립적인가?** 공개 구조의 노출 가능성을 점검하고 새로운 자료에서 확인한다.
9. **원본 자료와 평가 코드의 버전이 남는가?** 나중에 결과가 달라졌을 때 원인을 찾을 수 있어야 한다.
10. **같은 결과를 다른 사람이 다른 방법으로 얻었는가?** 독립 분석의 범위를 분석자, 코드, 자료, 장비별로 표현한다.
11. **경쟁 가설은 무엇인가?** 별빛 감소의 쌍성·기기 원인, 단백질 결합의 비특이성처럼 대안을 적는다.
12. **어떤 새 관측이 경쟁 가설을 구분하는가?** 반복 측정과 다른 방법의 측정을 우선순위에 넣는다.
13. **수치의 불확실성과 표적별 편차를 알고 있는가?** 10.9% 하나로 모든 표적의 기대를 대표시키지 않는다.
14. **공식 원문의 제한 사항을 함께 인용했는가?** 성공 수치가 가장 크더라도 약한 과제와 보조 도구를 숨기지 않는다.
15. **비교 대상에 같은 예산과 후처리를 적용했는가?** 조건이 다르면 단순 우월성보다 차이를 서술한다.
16. **후속 검증의 자원이 준비돼 있는가?** 후보 생성량이 실험실이나 관측팀의 처리량보다 크면 병목을 관리한다.
17. **진행 상태와 전달 알림을 분리했는가?** GitHub reason이 실제 승인·머지 상태를 대신하지 않는다.
18. **변경의 적용 시점과 범위를 기록했는가?** GitHub.com의 순차 적용을 전체 GitHub 서비스의 즉시 완료로 쓰지 않는다.
19. **대외 문구에 ‘후보’, ‘결합’, ‘확인’의 차이가 남는가?** 표현을 점검해야 잘못된 기대가 퍼지지 않는다.
20. **다음 검증에서 무엇이 나오면 현재 결론을 바꿀 것인가?** 결론을 반증 가능하게 써야 연구와 운영의 학습이 이어진다.

이 질문 목록은 오늘 세 소식에 각각 다른 형태로 적용된다. 단백질 연구에서는 모델의 내재적 생성 능력과 전문 모델의 후속 역할을 함께 설명하게 한다. 외계행성 사례에서는 공개 자료 검색의 가능성을 인정하면서 확정 전의 검증을 남긴다. GitHub 공지에서는 원본 업무 상태와 알림 전달을 분리하게 한다. 세 분야가 같다는 뜻이 아니라, **중간 결과를 확인 가능한 다음 단계로 연결한다**는 설계 습관이 이들 모두에 유용하다는 뜻이다.

## 마무리 — 더 빠른 탐색과 더 느린 확정 사이

오늘 가장 인상적인 사실은 일반 모델이 전문 분야의 입력과 제약을 받아 **실험할 가치가 있는 후보**를 만들었다는 점이다. 단백질 설계에서는 실제 결합 양성이 나왔고, 천문 탐색에서는 독립 연구자가 다시 볼 만한 신호가 나왔다. 동시에 두 성과의 의미는 다음 단계가 남았기 때문에 더 분명해진다. 결합 뒤에는 선택성·기능·안전성이 있고, 주기 신호 뒤에는 원인 배제와 새 관측이 있다. 어떤 경우에도 발견의 속도를 높인 도구가 검증의 기준까지 혼자 정할 수는 없다.

개발팀이 가져갈 한 가지 행동은 **후보 수와 검증된 결과 수를 같은 대시보드에서 다른 지표로 놓는 것**이다. 그 사이에 어떤 필터, 전문 도구, 사람의 판단, 독립 실험이 있었는지 추적할 수 있다면 모델 성능을 더 정확히 개선할 수 있다. 반대로 후보만 늘고 검증 지연이 커진다면 자동화의 성공으로 보기 어렵다. GitHub 알림 변화는 같은 원칙을 운영 업무에 적용하게 한다. 알림은 누군가의 주의를 끄는 단서이지 작업 완료나 승인 자체가 아니다.

**내일 다시 확인할 질문은 세 가지다.** 단백질 연구의 추가 재현 자료가 나오면 전문 모델의 도움 없이 어디까지 일반 모델이 해냈는가? 외계행성 후보는 새 관측에서 같은 주기와 원인을 보여 주는가? GitHub의 12월 첫 주 이전이 실제 알림 필터와 사람의 리뷰 흐름에 어떤 차이를 만드는가? 오늘의 정직한 결론은 세 질문에 모두 ‘아직 확인 중’이라는 문구가 붙는다는 것이다. 후보를 찾은 성취를 충분히 인정하되, 확정의 권한은 남은 증거가 채울 때까지 유보해야 한다.
